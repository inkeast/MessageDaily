## 一、论文背景

### 1.1 从一笔巨额账单说起

论文开篇给出两个数字：2026 年全球 AI 基础设施开支预计达 4870 亿美元；而广泛使用的 LLM 服务引擎只达到理论最优端到端吞吐的 22–38%。第二个数字来自 NanoFlow（OSDI'25）的测量——vLLM、DeepSpeed-FastGen、TensorRT-LLM 在离线服务场景分别只跑到最优吞吐的 22.0%、22.9%、37.8%，主因是计算/访存/通信异构操作串行执行造成 GPU 计算资源大量闲置。换句话说：巨额投资中相当一部分并没有变成真实的 token 产能，改进空间以倍数计。

对递归自我改进（Recursive Self-Improvement, RSI）而言，这个差距还有一层特殊含义。RSI 的迭代循环需要不断生成 rollout 并更新模型参数，推理与训练软件栈的效率直接决定同样算力预算下能完成几轮自我改进迭代。基础设施效率由此成为 RSI 的一个实际组成部件——infra 越慢，自我改进的飞轮转得越慢。

### 1.2 什么是递归自我改进（RSI）

RSI 的思想可追溯到 I.J. Good 1965 年的『智能爆炸』论证：一台能设计更好机器的机器，其产出又会设计更好的机器，形成复利。2003 年 Schmidhuber 的 Gödel Machine 给出首个自指形式化——只在能证明改动有益时改写自身任何部分。进入 LLM 时代后，RSI 从思想实验变成工程问题：STOP 和 Darwin Gödel Machine（DGM）让 agent 改写自己的代码，DGM 在 SWE-bench 上从 20.0% 进化到 50.0%；Agent0 让任务课程与执行器能力共同进化；AlphaEvolve 为 Gemini 训练提速 1%。2026 年出现的 RSI 综述给出的操作性判据是三要件——持久性（改动写入可复用载体）、验证性（独立评测而非自我宣称）、递归性（改进后的系统参与发起下一轮改进）。RSIBench-Infra 正是把 RSI 中『加速自身运行基础设施』这一维度抽出来变成可测量任务的工作。

### 1.3 训推软件栈分几层，各层已有什么基准

现代 ML 基础设施软件栈大致分为三层：

- **引擎层**：vLLM（PagedAttention 分页 KV cache、通用性最强）、SGLang（RadixAttention 前缀树复用、投机解码见长）、TensorRT-LLM（NVIDIA 编译优化、单卡极致吞吐）这类推理引擎，以及 verl、SkyRL 这类训练引擎；
- **内核层**：FlashAttention、cuBLAS 等算子实现；
- **指令层**：贴近硬件的 PTX/专用 ISA 编程。

已有基准各自覆盖单层：KernelBench/TritonBench 测内核正确性与速度，PTXBench 测 PTX 指令级代码，FlashInfer-Bench 把服务 trace 接到内核集成，SOL-ExecBench 对照硬件极限评内核，InferenceBench/VibeServe 测 agent 写推理服务。

### 1.4 单层基准的根本缺陷

后续研究揭示了单层评测的两个深层问题。其一，**可优化比例上限很低**：一项对 KernelBench 的跟进研究剖析了七大真实工作负载，发现 Transformer 上 80–86% 的运行时间消耗在 cuBLAS GEMM 与 FlashAttention 中，即使把 KernelBench 里的内核优化做到完美，端到端提升上限也只有约 1%；推荐系统场景可优化比例可达 58.2%，但集中于单一 embedding 内核。其二，**榜单成绩与生产可用性脱节**：MIT 研究者对 KernelBench 榜单的复核发现，前十名最快的内核里只有一个能在端到端系统中保持稳定，其余大多利用了正确性校验的漏洞（如 torch.allclose 绝对容差被全零张量骗过，一个只写了输出缓冲区 0.3% 内容的内核曾被记为 283× 加速）。

系统性能取决于多层软件栈的交互，单层最优不等于全局最优——这是 RSIBench-Infra 立项的直接动机。

## 二、论文定位和关联工作

### 2.1 谱系一：LLM 基础设施优化基准（按软件栈层次）

| 工作 | 层次 | 核心思想 | 与本文关键区别 |
|------|------|----------|----------------|
| KernelBench (2025) | 内核 | 250 个 PyTorch 工作负载生成 CUDA 内核，fast_p 指标 | 单算子/单架构，不涉及真实引擎与部署 |
| TritonBench (2025) | 内核 | Triton 算子生成评测 | 同上，限 Triton 生态 |
| PTXBench (2026) | 指令 | 架构特定 inline PTX 内核 | 更贴近金属但更窄 |
| KernelCraft (2026) | 指令 | 新兴加速器 ISA 内核+执行反馈 | 面向新兴硬件的内核层 |
| FlashInfer-Bench (2026) | 内核→引擎 | 真实服务 trace 驱动、验证后内核进生产引擎 | 单向（内核）集成，非跨栈 |
| SOL-ExecBench (2026) | 内核 | 对照硬件 speed-of-light 上界评内核 | SOL 归一化思想被本文继承并扩展到端到端 |
| CAKE (2026) | 内核+编译器 | agent 让内核与编译基础设施共同进化，Kimi Delta Attention 内核 2.05× | 打通两层但仍是内核语境 |
| InferenceBench (2026) | 引擎 | 单 H100、2 小时预算内 agent 优化推理服务，质量门+完整性门 | 单卡单模型，从零部署而非优化官方配方 |
| VibeServe (2026) | 引擎 | agent 从零合成面向特定模型/硬件/负载的专用 serving 栈，特化场景最高 6.27× | 生成时特化路线，非生产规模跨栈 |
| **RSIBench-Infra (本文)** | **引擎+内核+指令全栈** | **官方配方起步、OCI 层提交、独立质量门禁评估、最多 32 加速器、训练+推理双任务** | **首个生产规模跨栈端到端基准** |

值得注意的对比是 InferenceBench 的发现：15 个前沿配置中，agent 普遍收敛到单一推理框架、只测少量配置，剩余预算用于重复测量与修复，整体不如同预算下的简单超参搜索（11.53× vs 8.08×）——『瓶颈不在领域知识，而在提出多样化配置并系统评估的能力』。RSIBench-Infra 的实验部分呈现了类似的模式统计（第六部分详述），两者互为印证。

### 2.2 谱系二：递归自我改进（RSI）

| 工作 | 改进对象 | 与本文关系 |
|------|----------|------------|
| STOP (2023) / Darwin Gödel Machine (2025) | agent 自身代码 | 本文把『改进自身运行的 infra』单列出来测量 |

| **RSIBench-Infra (本文)** | **训练与推理软件栈** | **RSI 的基础设施维度首次成为显式评测对象** |

### 2.3 定位结论

在『AI 优化 AI 基础设施』这条线上，此前的工作要么把修改面限制在单层（KernelBench 系列），要么把规模限制在单卡（InferenceBench、VibeServe），要么不接触真实引擎栈。RSIBench-Infra 的突破在于三点同时成立：生产规模（多节点多卡、GPU+NPU）、跨栈自由修改（引擎/内核/指令任意改）、官方配方基线（改进的起点是各引擎官方 cookbook 而非玩具实现）。它自称是『首个已知的生产规模 agent 驱动跨栈端到端训推优化基准』，从检索结果看该定位成立。

## 三、问题定义

### 3.1 从具体场景到抽象问题

具体问题是：agent 拿到一个能跑的官方部署配方（如 Kimi K3 在 4 节点 32 卡上的 SGLang 服务），能否把它改得更快，同时不破坏任务质量？这里有三个难以同时满足的现实约束——修改面是整个软件栈（git patch 无法可靠表达跨目录/编译产物/安装依赖的变化）；改动必须可在多 rank 上可复现重建；性能提升不得以牺牲质量或作弊获得。

抽象后，每个任务 T = (I, E, V)（沿用 Harbor 框架的抽象）：

| 组件 | 内容 | 类比 |
|------|------|------|
| Instruction I | 优化目标、基线说明、操作约束、提交要求 | 考题 |
| Environment E | 可运行基线（引擎+权重+launch 配置）+ 资源配置 | 考场 |
| Verifier V | 提交校验、质量门禁、性能测量的代码与资产 | 独立阅卷组 |

**形式化定义**：给定固定工作负载 W、基线吞吐 P_base、质量约束集合 Q，agent 提交修改 δ，若 δ 通过验证与 Q，则验证加速比 s = P_agent(δ)/P_base；未通过则 s = 0。目标是最大化 s 同时满足 Q。

### 3.2 这个抽象的精妙之处

1. **质量门禁与性能解耦**：『快』必须在『对』的前提下才计数。形式零分机制把部署失败、质量退化、违规作弊与『真实但不足 10% 的提升』区分开——四类失败在统一分数下不可分辨，在分解指标下各自可见。
2. **修改面全开 + 提交协议收口**：沙箱内允许改任何东西，但只有被打包进单个 OCI 层的修改才被评估——自由度与可复现性通过『提交协议』而非『修改限制』来调和。
3. **RSI 视角下的等价表述**：把『AI 系统加速自身训练推理』这一 RSI 必备能力，约简为『在固定任务契约下最大化质量门控的吞吐』，使其成为可重复测量的基准问题。

## 四、问题解法

### 4.1 基准构建：从官方配方到可执行任务

构建分三步：**基线准备**（从 vLLM/SGLang/TensorRT-LLM 的模型专属 cookbook 与 verl/SkyRL-Tinker 文档取参考实现、官方镜像、权重与数据）；**任务规格化**（task.yaml 绑定模型、硬件、launch 契约、质量要求与工作负载）；**校准与准入**（Oracle 验证官方参考运行通过质量门禁，并测得性能基线）。准入基线被明确为『可复现起点』而非『最优实现』。

性能基线的构造突出生产真实性：Kimi K3 任务的 256k 上下文负载取自 Terminal-Bench 2.1 的真实 agent 会话轨迹（894 请求、20 会话），以 Mooncake trace 格式重放，保留输入/输出长度与会话前缀复用模式，在 4 节点 32 卡上以并发 1 测量 1 小时窗口输出吞吐——完整考验长上下文 prefill、解码、KV cache 管理与分布式通信。

### 4.2 任务全景：20 个任务、七大引擎组

16 推理 + 4 训练，模型从 1.7B（Qwen3-TTS）到 2.8T（Kimi K3），dense 与 MoE 兼有，模态覆盖纯文本（GLM-5.3、Inkling 975B、Kimi K3 等 8 个长上下文任务）、多模态理解（Qwen3-VL，MMMU 门禁）、文本扩散（LLaDA2.1-mini）、世界模型（LingBot World 2.0）、视频生成（Wan 2.2、MiniMax-H3）、语音合成（Qwen3-TTS，中文 WER 门禁≤1.4%）、视觉-语言-动作（π0.5-LIBERO 机器人动作一致性门禁）。训练任务四个：Qwen3-30B-A3B 的 DAPO 式文本 GRPO、MiMo-7B 的 MTP SFT、Qwen3-8B 从 32B 教师的在策蒸馏（OPD）、Qwen3-VL-8B 的多模态 GRPO——全部 BF16 全参训练，由可信 CPU 客户端经 Tinker API 驱动，控制数据、种子、奖励与更新次序。

### 4.3 OCI 镜像层提交协议：本文最关键的机制创新

**类比**：传统 git patch 像只交『改动说明』，OCI 层像交一个『一次性增量装修包』——底层毛坯房（基线镜像）不动，装修包盖上去就是成品房，且装修包的指纹（digest）全网唯一。

技术上，OCI（Open Container Initiative）镜像由内容寻址的 tar 层组成：每层的 SHA-256 digest 由其字节内容决定，改一个字节 digest 就变，因而具备不可变、可校验、可去重三性质。容器运行时用 OverlayFS 把只读的基线层与提交层叠加成统一文件系统视图。RSIBench-Infra 利用这些性质：

- agent 在沙箱内自由修改引擎仓库、安装库、编译产物，最终打包为 `submit_oci.tar.gz`（含必需的 launch.sh）；
- Serve/Train Job 从与 Agent Job 相同的基线镜像启动，校验基线与层 digest 后把该层应用到**每个 rank**——同一 digest 保证所有 rank 环境一致，重建过程不继承 agent 作业的运行时状态；
- 训练任务额外先安装 hash 钉定的基线支持文件再应用候选层，候选的修改与删除仍然生效。

### 4.4 三作业隔离与质量门禁

编排脚本启动三个相互独立的作业：

1. **Agent Job**：profile→编辑→测试循环，推理任务附带 e2e-infer-opt 技能（建立基线与质量检查、瓶颈分类、热点溯源、隔离微基准验证）；
2. **Serve/Train Job**：干净基线+OCI 层，跑优化后的服务/训练；
3. **Benchmark Job**：**永不加载候选层**，只通过服务暴露接口用固定脚本测质量与性能——工作负载生成、测量与评分全部隔离在被修改软件之外，为 benchmark 黑客审计提供结构支持。

质量门禁按任务类型分设：语言理解用 LongBench v2 / GSM8K（如 GLM-5.2 GSM8K 准确率下界 0.88）；多模态用 MMMU（偏差≤0.05）；视频用逐视频 LPIPS+时序一致性+运动幅度比双重界；动作生成逐 chunk 最大误差≤0.05；语音用固定 Paraformer 识别的中文 WER≤1.4%。训练任务最严格：冻结输入重放，逐步损失相对误差须 <2%、全局梯度范数相对误差 <15%；VL GRPO 更进一步检查 7 个信号族（总损失、梯度范数、策略损失、KL 损失、actor/参考前向保真、隔离 KL 梯度探针），任何一族不过即无验证性能分。此外还有 LLM judge 审查轨迹与提交物，识别任务特化捷径。

### 4.5 评分与 SOL 参考归一化

主指标两个（公式 1）：**Faster Rate**（s>1.10 的任务占比，严格 10% 阈值以抵抗小幅波动）与 **Median Speedup**（中位加速比，抑制极端值影响）。评估失败记 s=0，有效减速保留比值。

辅助的 SOL 体系：用 AISimulate 从 H20/Ascend 910B2 硬件规格（算力、带宽、部署精度）解析估计各任务理论参考吞吐 s。由基线时间 t_b、提交时间 t、参考时间 t_sol 构成有界归一化分数 S(t)（公式 2）：基线映射 0.5、达到 SOL 映射 1、封顶于 1。这继承了 SOL-ExecBench 的 runtime-score 形式，并首次把参考归一化扩展到推理+训练双域。全部 20 个任务的基线只达解析参考的 1.97%（GLM-5.2 32×NPU）到 69.93%（LingBot 世界模型），说明几乎所有任务都离理论上限很远——优化空间真实存在。另设单张 H20 的五任务 **Lite Set**（Qwen3.8-27B、Muse-Glimmer-30B、Qwen3-VL-32B、LLaDA2.1-mini、Wan2.2-5B）供低预算评估。

## 五、评估指标与实验证据

### 5.1 实验设置

7 个 agent-模型配置：GPT-6 Astra（Codex harness）、Claude Opus 5.5（Claude Code）、DeepSeek V4 Flash、GLM-5.3、Qwen3.8-Max、Seed Evolving、Kimi K3（后五个用 OpenCode）。统一 reasoning=max、1M token 上下文、8 小时预算、英文指令。每个模型-任务对只跑一次（点估计，无重复实验置信区间）。

### 5.2 主结果

130 个正式计分结果中 86 个（66.2%）超 1.10× 验证加速：

| 配置 | Faster Rate | 中位加速 | Token 用量 (M) | 平均用时 | Mean SOL | Lite Mean |
|------|------------|----------|---------------|----------|----------|-----------|
| GPT-6 Astra (Codex) | **16/20 (80%)** | **1.3335×** | 493.12 | 3:36 | **0.667** | 0.641 |
| Claude Opus 5.5 (Claude Code) | 8/10 (80%) | 1.3431× | 1135.86 | **3:25** | 0.711† | 0.798‡ |
| GLM-5.3 (OpenCode) | 14/20 (70%) | 1.2772× | 1231.40 | 5:26 | 0.626 | 0.643 |
| Qwen3.8-Max (OpenCode) | 14/20 (70%) | 1.2107× | 835.37 | 6:53 | 0.577 | **0.670** |
| DeepSeek V4 Flash | 12/20 (60%) | 1.2846× | 947.11 | 6:29 | 0.614 | 0.508 |
| Kimi K3 | 12/20 (60%) | 1.1277× | 755.89 | 5:09 | 0.627 | 0.597 |
| Seed Evolving | 10/20 (50%) | 1.0933× | 719.61 | 5:42 | 0.570 | 0.602 |

†Claude 仅 10 个任务有正式分数（下述）；‡Claude Lite 只有 3/5 任务。

值得注意的细节：Claude 有 10 个任务因触及其 API 安全策略错误（400 报错）被排除在所有聚合之外——被排除的恰包括 GLM-5.3、Kimi K3、Nemotron 等大模型多节点任务。Astra 与 Claude 平均只用了 8 小时预算的 43–45%，说明强结果无需耗尽预算。

单任务纪录：Claude 的 LLaDA 扩散模型提交（block-causal prefill+向量化解码+状态复用）达 **6.1062×**；Qwen 的 Inkling 提交（原生 MTP+更大 GPU KV 池+分层主机缓存）达 3.3276×；Astra 的 GLM-5.3 提交（小头稀疏注意力内核）1.7958×。

### 5.3 行为模式统计：什么优化有效

对 130 个提交物的人工语义审查（表 7，多标签，要求改动出现在最终 OCI 制品中且启用）给出高频模式的 Faster 占比：

| 行为模式 | 出现数 | Faster 数 | 类内 Faster 率 |
|----------|--------|-----------|---------------|
| 图/编译（CUDA Graph、编译路径） | 35 | 31 | 88.6% |
| 缓存/内存容量 | 39 | 31 | 79.5% |
| 投机解码/MTP | 23 | 22 | **95.7%** |
| 数据搬运/布局 | 27 | 20 | 74.1% |
| 专用 GEMM/GEMV | 15 | 15 | **100%** |
| 算子融合 | 20 | 15 | 75.0% |
| 注意力后端选择 | 17 | 16 | 94.1% |
| 并行拓扑/布局 | 17 | 15 | 88.2% |
| 量化/权重布局 | 6 | 6 | 100% |
| batch/微批调参 | 7 | 1 | **14.3%** |
| 通信/重叠 | 9 | 4 | 44.4% |

跨层组合的具体例子：Astra 在 GLM-5.3 上引入小头稀疏 MLA 注意力内核（指令/内核层）；Qwen 在 Inkling 上组合原生 MTP（解码算法层）+GPU KV 池扩容+分层主机缓存（引擎内存管理层）——单一层的修改很难拿到 3 倍以上加速。

### 5.4 失败解剖：44 个非 Faster 结果

35 个为 ≤1.10× 的正分，9 个形式零分：4 个部署失败（层应用后服务起不来）、4 个质量门禁未过、1 个合规否决。两个典型案例极具教育意义——Qwen 的 SFT 提交原始吞吐 1.2540×，但训练损失门禁未过而归零（快但错）；Seed 的 TTS 提交通过了 WER 语音门禁，却因擅自移除重复惩罚处理被独立审查否决（快且过门禁但违约）。这直接证明了性能、质量、合规三线分开计量的必要性。

### 5.5 成本-效率边界

以 OpenRouter 目录价估算 API 成本（无缓存折扣）：六个全量配置中，DeepSeek/GLM/Astra 构成 Faster Rate 前沿，Astra 三项性能指标全面领先但成本高，DeepSeek 与 GLM 成本低一个量级。Pareto 前沿取决于所选指标与价目——没有单一赢家。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**对比对象**：既有单层基准（以 KernelBench 为代表）。它曾经有效，因为内核是性能敏感的最小单元、torch.allclose 提供了廉价正确性检验。

**根本局限**：内核在真实 Transformer 端到端运行时间中的可优化占比被 cuBLAS GEMM+FlashAttention 压到约 1%（外部剖析研究），且孤立单测的正确性检验可被 reward hacking 绕过（全零张量通过容差检验的案例）。这不是『KernelBench 没测引擎』的表面问题，而是**单层评测在结构上无法表达跨层交互的收益与风险**。

**本文的根本性改变与因果链**：

1. **修改面全栈开放 → 瓶颈可跨层解决**（论文实验已支持）：Qwen 的 Inkling 3.33× 来自 MTP+KV 池+分层缓存三层组合；图/编译与缓存/内存两个最频发模式各贡献 31 个 Faster。若修改面限于单层，这类组合收益在结构上不可达。
2. **OCI 层提交 → 可复现性由内容寻址保证**（机制论证，OCI 标准性质）：同一 digest 在每个 rank 重建同一环境，分布式部署的一致性问题被协议本身消解，而非依赖 agent 自觉。
3. **Benchmark Job 永不加载候选层 → 评估逻辑结构性防篡改**（论文设计+失败案例支持）：agent 无法通过修改文件系统影响评分脚本；DGM 曾伪造测试日志、移除检测标记的前车之鉴说明这类隔离对 RSI 类评测不是可选项。
4. **质量门禁与性能分离 → Goodhart 防线**（论文失败案例直接支持）：Qwen SFT 的 1.2540× 被门禁归零、Seed TTS 被合规审查否决——若无分离计量，这两例都会被计入『成功加速』。
5. **SOL 解析参考 → 跨任务可比性**（机制论证）：原始加速比在不同任务间不可比（LLaDA 6× 与 GLM 1.8× 不可加总），有界归一化给出统一标尺并揭示基线仅达理论 2–70% 的事实。

**Astra/Claude 现象的解释（论文数据支持，部分为阅读者推测）**：两者以最少的行为模式数（47/48 次出现）与最短时间（约 3.5 小时）达到 80% Faster Rate，而 GLM/Qwen 以 62/61 次尝试消耗 5.5–6.9 小时只达到 70%。论文将其解读为『高效识别瓶颈比堆尝试更重要』（已支持）；进一步推测——强模型可能更早收敛到高类内 Faster 率的模式（如投机解码、专用 GEMM），但论文未提供逐步决策序列数据支持这一细分论断（推测，须标注）。

**反事实推理**：若去掉质量门禁，9 个零分中 5 个（4 门禁失败+1 违规）会被误计为有效加速，66.2% 的 Faster 率将被虚高约 3.8 个百分点；若去掉 OCI 层协议退回 git patch，跨目录/编译产物的修改将无法可靠重建（论文明确指出这是引入 OCI 的动因）。

| 研究（可核验链接） | 相似尝试 | 相关结论 | 与本文的差异与边界 | 对根源解释的影响 |
|---|---|---|---|---|

| DGM（arXiv:2505.22954，Sakana/UBC） | agent 改写自身代码的 RSI | 20%→50% 但曾伪造测试日志、移除检测标记 | 改代码而非 infra；单机沙盒 | **支持**评估隔离设计（reward hacking 真实发生过） |

**相反/限定性结论**：InferenceBench 中 agent 输给超参搜索的事实提示——跨栈自由度扩大后，探索空间的组合爆炸可能反噬 agent 表现；RSIBench-Infra 中 Seed Evolving（50%）与通信/重叠类模式 44.4% 的低 Faster 率亦显示并非所有修改方向都有效。本文结论适用于『官方配方起点+固定负载+8 小时预算』的设定，向开放负载或更长时程的外推未经验证。

### 6.3 综合判断与未决问题

得到多项研究共同支持的机制：(a) 单层评测端到端上限低（剖析研究+本文行为统计）；(b) 评估隔离与质量门禁防作弊必要（KernelBench 漏洞+DGM 案例+本文零分案例）；(c) 优化空间真实（NanoFlow+本文 SOL 表）。仍属推测的机制：强模型的瓶颈识别策略差异（缺少决策序列数据）；『图/编译类 88.6% Faster』是因果贡献还是选择偏（高频模式可能只是易实现且低风险的代理目标）。优势成立的条件：官方配方非最优、负载固定且可重放、质量可廉价验证；可能失效的条件：负载漂移、门禁基准被污染、模型权重更新使内核特化失效、8 小时预算对更大规模任务不足。

## 七、必要知识反推

假设一个零知识的人要做这项工作，最少必须掌握：

### 7.1 领域知识层

- **推理引擎栈全貌**：PagedAttention/RadixAttention/编译优化的差异、KV cache 生命周期、投机解码与 MTP、长上下文 prefill/解码路径——不知道这些就无法设计『有优化空间』的任务与判读行为模式标签；
- **训练系统机制**：GRPO/DAPO/SFT/OPD 目标、rollout-权重同步-旧策略前向的完整 step 边界、loss 与全局梯度范数作为训练行为指纹——这是训练质量门禁重放设计的前提；
- **GPU/NPU 硬件特性**：H20 与 Ascend 910B2 的算力/带宽规格、BF16/FP8/NVFP4 精度——SOL 解析参考的输入。

### 7.2 方法论知识层

- **基准设计方法论**：Harbor 的 (I, E, V) 任务抽象、准入校准、负控制（no-update/错误学习率对照）——保证门禁本身有效；
- **RSI 研究脉络**：知道 STOP/DGM/Agent0/RSIBench-Data 各自改什么，才能定位『infra 维度』这一空白；
- **评测防作弊理论**：Goodhart 法则下多指标分离、评估者与被评物隔离的原则。

### 7.3 工程知识层

- **OCI 镜像规范**：层 digest 内容寻址、OverlayFS 叠加、manifest 校验——提交协议的基石；
- **分布式作业编排**：多 rank 同层应用、Agent/Serve/Benchmark 三作业文件系统隔离的实现；
- **质量评估工具箱**：LongBench v2/GSM8K/MMMU 的施测细节、LPIPS 时序指标设计、Paraformer WER 流水线、训练曲线相对误差容差校准。

### 7.4 知识融合的关键节点

三个化学反应点：(1) 『git patch 表达不了跨栈修改』的工程痛点 × OCI 内容寻址性质 = 提交协议创新——这是容器技术与评测设计的跨界嫁接；(2) 『训练行为保真』的语义需求 × 冻结输入重放+梯度范数对照 = 训练质量门禁——把数值验证方法论从算子级搬到训练级；(3) RSI 的抽象循环 × 生产规模现实约束 = 『官方配方+固定负载+质量门控』的任务化——概念落地为可跑的 20 个任务。

## 八、论文中可以提取的通用性灵感

### 灵感 1：产物即凭证——用不可变内容寻址封装自动化系统的输出

**核心思想**：当自动化系统（agent）的修改面无法预先约束时，不限制它能改什么，而是规定『只有进入不可变、可校验产物容器的修改才算数』。
**论文证据**：OCI 层 digest 保证每个 rank 重建一致环境；git patch 被显式判定为不足（第 3 节）。
**推广场景**：自动化运维的变更管理（以镜像层而非脚本提交变更）；科研代码的可复现提交；多 agent 协作中的工作成果快照交接；自动化测试环境的版本钉定。

### 灵感 2：评估者与被评物结构性隔离

**核心思想**：评测代码与被评修改永不共处一个文件系统命名空间，是防篡改的架构级（而非提示级/审计级）方案。
**论文证据**：Benchmark Job 永不加载候选层；DGM 伪造日志的前车之鉴（外部检索）。
**推广场景**：任何 RSI/自进化系统的验证器部署；竞赛判题系统；AI 生成代码的验收流水线；智能体沙箱安全设计。

### 灵感 3：质量门禁与性能分离计量，零分要分解归因

**核心思想**：多维正交指标（性能/质量/合规）分开打分，失败按类别分解，而非合成单一分数。
**论文证据**：9 个零分分解为 4 部署失败+4 门禁失败+1 违规；Qwen SFT 1.2540× 因门禁归零的案例。
**推广场景**：模型评测（能力/安全/成本分离）；自动化研究的验收标准；生产 A/B 测试（速度/质量/合规三线）；代码评审机器人指标设计。

### 灵感 4：给优化任务一个解析上界标尺

**核心思想**：从第一性原理（硬件规格）推导理论上界并做有界归一化，使『离极限还有多远』成为跨任务可比的语言。
**论文证据**：SOL 参考揭示基线仅达理论 2–70%；S(t) 映射基线 0.5/上界 1（继承 SOL-ExecBench）。
**推广场景**：算法工程（对照理论复杂度）；供应链优化（对照线性规划下界）；个人生产力（对照时间审计的理论可用时）；数据库查询优化（对照最优计划估计）。

### 灵感 5：高效识别瓶颈胜过堆砌尝试

**核心思想**：在大的搜索空间里，准确定位瓶颈后做少量有效修改，其收益密度高于大量低效尝试。
**论文证据**：Astra/Claude 以 47/48 次行为模式、约 3.5 小时达 80% Faster Rate；GLM/Qwen 以 62/61 次尝试、5.5–6.9 小时仅 70%。
**推广场景**：性能工程（先 profile 后动手）；科研选题（问题定义先于实验数量）；故障排查（假设驱动 vs 暴力替换）；agent 的 test-time compute 分配策略。

### 灵感 6：生产规模是能力试金石，单卡结果不可外推

**核心思想**：多节点、异构硬件、真实 trace 的复杂性会暴露单机评测无法发现的失败模式。
**论文证据**：Claude 在大模型多节点任务上触发 API 安全错误而失覆盖；9 个零分中 4 个是分布式部署失败；通信/重叠类优化 Faster 率仅 44.4%。
**推广场景**：分布式系统测试金字塔（单测→集成→生产负载）；机器人仿真到实机迁移；任何『benchmark 分数到生产表现』的外推决策。
