## 一、论文背景

### 1.1 人机协同设计是什么

Web 应用的开发从来不是"一次写完"，而是**反射式的迭代循环**：看一眼现有页面（inspect）→ 提出修改（request）→ 评估结果（assess）→ 再来一轮。这个循环最早由 Schön 在 1983 年的《反思性实践者》中描述，如今由编程 Agent（coding agent）参与执行：Agent 检查可视化上下文、修改源文件、执行应用，把用户的意图翻译成应用的可用修订。

问题的关键在于：**真实用户的修改请求很少是纯文本的**。一条请求可能同时包含截图（"照这个样子改"）、音频（一段语音说明）、视频（一段操作录屏）、文档（一张收据、一份规格表），并且同时涉及布局、交互和应用状态的联动修改。Agent 必须把多模态证据连接到界面与行为的依赖性修订上。

### 1.2 现有基准覆盖了什么、漏了什么

论文将已有 Web 编码基准归为四类（Table 1）：

| 类别 | 代表工作 | 核心做法 | 局限 |
|------|---------|---------|------|
| 参考重建 | Design2Code、WebSight、WebRenderBench、IWR-Bench | 给截图/交互视频，重建页面，与参考页比对 | 只测"复刻"，不测"修改已有应用" |
| 页面级编码 | MT-Web2Code、DesignBench、WebCompass | 预定义编辑操作或版本历史对，做局部修改 | 编辑来自预定义池或版本对，非真实用户会话 |
| 仓库级 SE | SWE-bench M、SWE-Lancer | GitHub issue / 自由职业需求 + 可执行测试 | 面向后端式 issue，不覆盖设计会话中的复合修订 |
| 从零生成 | WebGen-Bench、FrontendBench | 文本生成整站 + 功能测试 | 缺少"在现有应用上改"的场景，且非真实用户请求 |

**空白地带**：跨越"局部多模态编辑"和"仓库协同修改"两个尺度、从真实用户编码会话中恢复的**复合修订**（compound revisions）没有基准覆盖。论文举了一个典型例子（Figure 1b）：体育集锦编辑器的需求——"添加片段、限制数量与时长、缩放时时间轴锚点对齐、删除/拆分片段后恢复可添加状态"。这条请求把成功标准绑定在**多个相互作用的需求同时满足**上，任何一个单独看都不难，合在一起才是真实世界的难度。

### 1.3 Agentic 执行让旧基准"饱和"了

另一个动机来自执行体制的变化。论文做了一个预实验：在 150 个 WebCompass-edit 任务上，同一个 qwen3.7-plus 模型，从单次生成（single-shot）切换到 agentic 执行（可迭代检查、修改、执行），特性完成率从 73.6% 提升到 95.1%（+21.5pp）；opus-4-8 在 agentic 执行下达到 99.4%。也就是说，**在旧基准上，只要换执行方式，分数就接近满分**——基准失去了区分度。这不是模型突然变强，而是"题目"对 agentic 执行来说太容易了。要继续测出差距，需要更难、更真实、更复合的任务，以及能识别"部分完成"与"完整交付"的评估协议。

## 二、论文定位和关联工作

### 2.1 研究谱系定位

Co-Design Bench 站在三条研究线的交汇处：

**谱系一：多模态 Web 生成与编辑**。Design2Code（2024，截图转代码）开创了多模态前端评测；IWR-Bench（2025）把输入扩展到交互视频；WebCompass（2026）引入预定义编辑操作 + reference-free 判分。Co-Design Bench 的推进是：任务不再来自预定义池，而是**从生产编码会话中恢复**，保留可运行起始应用、会话上下文和附件，隐藏标准不依赖金码或目标截图。

**谱系二：仓库级软件工程评测**。SWE-bench（2023）确立了"真实 issue + 可执行测试"范式；SWE-bench Multimodal（2024）扩展到含视觉元素的 JavaScript 软件；SWE-Lancer（2025）用自由职业需求 + 浏览器 E2E 测试。Co-Design Bench 的差异：聚焦编码会话内的设计+功能复合修订，RE track 覆盖组件、路由、状态、数据流的协同修改，并与 ME track 共享任务接口和验收协议，使两个尺度可在同一标尺下比较。

**谱系三：Agent 评估与对抗验证**。Agent-as-a-Judge（2024）提出用 Agent 评估 Agent，对齐率 90.44%（LLM-as-a-Judge 为 70.76%）；同时 G-Eval、Panickssery 等工作揭示 LLM 评审者的自我偏好（self-preference）与可靠性问题。Co-Design Bench 吸收了这一教训：初始判分后必须经过**独立 LLM 驳斥者**挑战正判决，并强制证据审计。

### 2.2 定位对比表

| 维度 | 之前的路线 | Co-Design Bench 的突破 |
|------|-----------|----------------------|
| 任务来源 | 预定义编辑池 / 版本对 / GitHub issue | 26,314 个真实用户编码会话，37,463 条去重查询 |
| 输入模态 | 文本 + 图片（多数） | T/I/V/A/D 五种（文本/图/视频/音频/文档） |
| 起始状态 | 截图或仓库 | 可运行的 pre-edit 应用（容器化、过构建渲染门） |
| 验收方式 | 与参考截图/金码比对 | Reference-free：隐藏专家标准 + 基线锚定 |
| 评估体制 | 固定测试重放 / 单次判分 | Agentic 评估：源码+浏览器证据 + 驳斥 + 审计 |
| 对抗验证 | 无 | 独立 LLM 驳斥者挑战 PASS/PARTIAL 判决 |
| 报告指标 | 平均完成率 | 标准/任务双轨：criterion coverage + full-pass rate |

**定位结论**：这是第一个把"真实用户会话恢复 + 可运行起始应用 + 多模态附件 + 仓库级协同修改 + reference-free 对抗式验收"五件事同时做齐的基准，核心关注点从"平均分多高"转向"**部分满足与完整成功的差距**"。

## 三、问题定义

### 3.1 从具体场景到抽象问题

具体场景：用户在一个能跑的 Web 应用上提出一条混合了图片/音频/视频/文档附件的修改请求，Agent 要交付修订后的应用。

抽象问题：**给定一个可运行的初始状态和一组隐藏的需求约束，评估一个自主执行体在多大程度上同时满足了全部约束——并区分"平均满足程度"与"全部满足的比例"。**

### 3.2 形式化定义

每个任务 t = (S, I, C)：

- **S = (B, E)**：可运行 pre-edit 基线 B 及其容器化环境 E
- **I = (q, X, K)**：规范化请求 q、可选多模态附件 X、保留的会话历史 K
- **C = {c_i}**：n_t 条隐藏专家验收标准，规定期望结果与显式架构约束，允许多种有效实现

求解过程：在 harness H 下，Agent A 将 (S, I) 经执行轨迹 τ 映射为修订后状态 Ŝ = Edit_τ(S)。验收只针对**最终应用状态**，基线 B 锚定"什么必须变、什么必须保留"，因此不需要金码或目标截图。

### 3.3 这个抽象的精妙之处

第一，**基线取代参考答案**。传统基准要一份"标准答案"（金码/目标截图），但真实修改没有唯一正确答案。pre-edit 应用本身就是锚：请求说"改 X"，那基线里 X 之外的无关内容是否保留就成了可审计的标准（preservation constraints）。

第二，**标准级分解取代任务级二值判定**。一个复合请求被专家拆成可独立审计的标准（如"片段数上限""删除后恢复添加"），使"完成了 70%"第一次变得可度量、可归因——你能看到具体哪条需求没满足。

第三，**双层指标暴露"平均陷阱"**。若只报平均完成率，一个"每题都完成 70%"的模型和一个"70% 题目全对、30% 题目零分"的模型得分相同，但产品意义完全不同。Strict Completion（R̄）与 Full-Pass Rate（F）的分离正是为此设计。

## 四、问题解法

解法分两半：**数据侧**构建高质量任务包，**评估侧**构建可信的验收协议。可以类比考试出题（题库要真、要难、要有隐藏评分细则）与阅卷（要防作弊、要有复核）。

### 4.1 数据构建管线：从 39,325 条查询到 273 个任务

**类比**：像考古挖掘——从生产环境的会话遗迹中，恢复出当时"可运行的应用 + 用户请求"的完整现场。

**第一步：恢复可运行起始状态**（Figure 2a）。从会话日志、仓库归档或 HTML bundle 中重建应用；定位目标编辑轮次，用源码哈希快照恢复仓库、资产和上下文。候选必须通过依赖解析 → 构建 → 容器启动 → Playwright 渲染四道门；修复采用"诊断→修复→复查"循环（P0 脚本化批量修复 / P1 agentic 修复 / P2 结构剪枝），不可恢复的服务直接剪除。产出标准任务包：`baseline/ + env.manifest + request + media/ + validation.log`。

**第二步：请求筛选与标准撰写**（Figure 2b）。五道工序：
1. **去重**：精确哈希 + 近重复（Jaccard > 0.8）→ 37,463 条唯一查询
2. **规范化**：解码附件、重写粘贴图片引用、可选隐私筛查（OCR + 内容检查）
3. **硬过滤**：F1–F6 滤掉环境阻塞、闲聊、模糊、非编辑请求
4. **排序**：r(q) = d + v + f——难度 d∈[0,5]（d=1 改一个 CSS 属性；d=4–5 跨组件重构/跨文件数据传播）、可验证性 v∈[0,3]（静态源码 diff=1 / 渲染 DOM=2 / 交互后状态转移=3）、历史失败信号 f∈[0,2]（用户重复改写 ≥4 次或回滚 = 2）
5. **合并**：每会话最多 3 条合格查询（r>1）合并为一个有界任务，专家撰写隐藏标准

**关键细节**：失败信号利用了会话中的"隐性负反馈"——用户反复重新表述或回滚，说明这条请求当时就没被做好，天然构成难例。这类似于推荐系统把"用户重试次数"当作不满信号。

### 4.2 两个赛道

| 属性 | ME（Multimodal Editing） | RE（Repository Editing） |
|------|--------------------------|--------------------------|
| 任务数 / 标准数 | 100 / 553（均值 5.5，中位 6，最大 11） | 173 / 1,778（均值 10.3，中位 8，最大 46） |
| 编辑尺度 | 局部视觉/结构/内容编辑 | 组件、路由、状态、数据流协同修改 |
| 输入附件 | 无附件 20 / 图 4 / 视频 27 / 音频 32 / 文档 17 | 82% 含图像锚定素材，均值 5.1 张捕获图 |
| 起始工件 | 79 单页 HTML + 21 打包应用 | 98.8% React 应用（171/173） |
| 编辑类型分布 | — | 结构 151 / 样式 133 / 交互 131 / 内容 112（可重叠；96% 任务多类型） |

两个赛道共享 (S, I, C) 接口与 PASS/PARTIAL/FAIL 判决——这是"局部编辑"与"仓库修改"首次在同一标尺下可比较。

### 4.3 Judge-then-Refute 评估协议

**类比**：像论文评审 + 程序委员会复核（PC chair rebuttal）——初审给分后，另请一位独立审稿人专门"挑刺"，正判决必须扛住驳斥才算数。

**阶段 A：证据提取与主评估**（Figure 3a）。
1. 候选应用镜像进隔离沙箱，修复非阻塞环境问题后执行 vite 构建（或静态 HTML 管线）→ 启动服务 → headless Chrome 渲染
2. 提取四类证据：源码 diff、DOM 树与 body 文本、视口截图（PNG+状态）、源码到入口的可达性日志；交互检查激活时 Playwright 记录动作序列与网络遥测
3. 固定的 agentic 评估器（Agent-as-a-Judge 架构）对每条标准给 PASS/PARTIAL/FAIL

**证据匹配原则**（这是该协议的灵魂）：证据类型必须匹配声明类型——
- 静态属性 → 源码检查即可
- 视觉声明 → 必须有成功渲染 + 截图
- 交互声明 → 必须有录制的浏览器动作 + 结果状态转移
- **源码里有一个 handler ≠ 用户能在渲染界面上到达并操作该功能**；构建失败或 DOM 节点缺失直接使渲染依赖的标准失效

**阶段 B：对抗验证与归因**（Figure 3b）。
1. **独立 LLM 驳斥者**（与主评估器分离）接收初审判决 + 全部证据，专查：桩代码（stub）、硬编码输出、不可达入口、输入变化下的失败、需求错配——目标是否定不实的完成分（注意：它不负责证明否定判决正确）
2. **强制证据审计**：视觉声明无截图、交互声明无浏览器日志 → 违规直接中止评估（而非给零分），防止"证据缺失被当作未通过"
3. **条件性失败归因**（针对 G_t < 0.8 且基线独立渲染通过启动门的案例）：并行运行**可解性探针**——在隔离沙箱中打最小补丁、stub 掉不可达网络端点，把失败归因为 模型局限 / 环境阻塞 / 混合 / 起始工件缺陷 四类；原始分数与分母保持不变，环境调整分只在做实基础设施失败时才给
4. 判决、证据、驳斥日志全部留档，每条标准判断可回溯到支撑观察

**人工兜底**：两位前端专家复核了 200 个任务-模型输出的标准评分。

### 4.4 打分公式

任务级：R_t = (1/n)Σ1[v_i=PASS]（Strict）；G_t 用 g(PASS)=1, g(PARTIAL)=0.5, g(FAIL)=0（Graded）。集合级取任务等权平均，F = 全部标准 PASS 的任务比例。恒有 F ≤ R̄ ≤ Ḡ。

## 五、评估指标与实验证据

### 5.1 指标体系

| 指标 | 定义 | 衡量的能力 |
|------|------|-----------|
| Strict Completion（R̄） | 仅 PASS 计满分的任务内标准通过率均值 | 完整满足单条需求的覆盖面 |
| Graded Completion（Ḡ） | PARTIAL 记 0.5 分 | 部分进展（区分"完全没做"与"做了一半"） |
| Full-Pass Rate（F） | 全部标准 PASS 的任务占比 | **完整交付能力**（论文最看重的差距指标） |
| R̄ − F gap | 覆盖率与全过率之差 | "未完成需求分散在多少任务里" |

### 5.2 主实验：10 端点 × 273 任务 = 2,730 对

共享 Claude Code harness、容器 manifest、系统提示、工具接口，3 小时 / 120 轮上限。综合榜（Table 5）：

| 模型 | Strict ↑ | Graded ↑ | Full (%) ↑ |
|------|---------|---------|-----------|
| gpt-6-astra | 0.699 | 0.753 | 26.4 |
| opus-5 | 0.661 | 0.719 | 18.3 |
| qwen3.8-max-0902 | 0.653 | 0.716 | 16.5 |
| qwen3.8-27b | 0.644 | 0.709 | 15.0 |
| kimi-k3 | 0.629 | 0.695 | 15.8 |
| gpt-5.6-sol | 0.611 | 0.679 | 14.3 |
| opus-4-8 | 0.581 | 0.649 | 10.3 |
| glm-5.3-flash | 0.573 | 0.639 | 10.6 |
| glm-5.2 | 0.567 | 0.637 | 9.5 |
| grok-4.6 | 0.511 | 0.580 | 6.6 |

**核心发现 1：覆盖 ≠ 交付**。最强模型 R̄=0.699 但 F=26.4%——73.6% 的任务至少剩一条标准未完全满足。ME 上 gpt-6-astra 达 R̄=0.754 / F=41.0%，RE 上 0.667 / 17.9%。

**核心发现 2：排名随赛道变化**。跨赛道排名相关（Spearman ρ=0.818）但有个体反转：kimi-k3 从 ME 第 4 掉到 RE 第 6；qwen3.8-27b 从 ME 第 5 升到 RE 第 2（R̄=0.645，超过 opus-5 的 0.642）。端点间分差 ME 达 28.7pp、RE 仅 13.0pp——综合榜会掩盖赛道特异性强弱。

**核心发现 3：执行开销与完成度脱钩**。ME 上 gpt-6-astra 用 32 轮中位 / 1.24M token 拿到 R̄=0.754，glm-5.2 用 69 轮 / 7.29M token 只有 0.572；RE 上 qwen3.8-27b 烧 6.72M token（0.645）不敌 gpt-6-astra 的 2.33M（0.667）。**更多的努力不等于更好的结果**。

### 5.3 任务层分析

**按附件模态**（ME，Figure 4a）：纯文本任务 qwen3.8-27b 领先（0.779）、图片任务 opus-5 领先（0.891）、视频/音频/文档任务 gpt-6-astra 领先。池化均值 0.584–0.652。**文档任务池化分最高（0.652）但全过率仅 18.2%，纯文本任务全过率 37.0%**——两种指标对"难"的刻画不同。工具轨迹显示多样的媒体处理策略：OpenCV 出现在 68.5% 的视频轨迹，ffmpeg 占 31.5% 视频 / 25.0% 音频，faster-whisper 占 4.4% 音频；部分 Agent 甚至从 HuggingFace 下载预训练感知模型（AST 音频分类、CLAP 音文相似度、Whisper 转写、OWLv2 检测）来"看懂"附件。

**按编辑广度**（RE，Figure 4b）：1–2 种编辑类型（53 任务）池化 0.654，3–4 种（120 任务）0.591，**6.3pp 差距且全部 10 个端点在宽编辑组都更低**；全过率相近（9.1% vs 9.7%）但零分率从 0.9% 升至 5.8%——广编辑拉低覆盖面、制造彻底失败。

**按能力维度**（Table 3）：Functional Implementation 最大组（126 任务，46.2%）池化分最高（0.619）但全过率最低（10.3%），对比 Grounded Understanding（0.604 / 20.2%）与 UI Transformation（0.615 / 13.6%）。97.1% 任务带多个能力标签，63.7% 跨维度——真实任务本来就是复合的。

### 5.4 三组消融与鲁棒性

1. **执行体制**（Appendix A）：同模型同评分管线，single-shot 73.6% → agentic 95.1%（WebCompass-edit 150 题，全过率 32.7%→69.3%）——证明 agentic 循环的必要性，也证明旧基准对 agentic 执行饱和。
2. **评估器敏感性**（Appendix C）：换 GLM-5.2 / kimi-k3 / Qwen3.8-27B 三种评审重判 kimi-k3 与 qwen3.8-27b 的存档输出，绝对分最大漂移 0.053，**kimi-k3 ME 领先 / RE 落后的交叉排序在四种配置下全部保持**——结论对评审者稳健。
3. **跨 harness 敏感性**（Appendix H）：同模型换 codex / opencode / qwen-code 三种 harness，**ME 上 harness 排名在两个 solver 之间完全反转（ρ=−1.00）**；kimi-k3 与 qwen3.8-27b 的差距在 ME 摆动 10.0pp、RE 摆动 16.2pp——模型排名必须与 harness 绑定报告。

### 5.5 实验设计如何证明论点

论文的主张是"部分满足与完整成功存在系统性差距，且该差距有结构"。证明链：双层指标（R̄ vs F）定义了差距 → 最强模型 69.9% vs 26.4% 量化了差距的量级 → 差距随编辑广度系统性变化（全部端点一致）→ 差距在能力维度上分化（功能实现全过率最低）→ 评估协议本身的稳健性由消融 2、3 背书。特别注意作者的自我约束：明确声明工具分布、模态对比等是**描述性统计而非因果效应**（任务内容在不同组间不同），这种克制反而增强了主张可信度。

## 六、效果优势的根源解释

本部分回答：为什么这个基准能暴露出旧基准看不到的现象？其评估协议为什么可信？

### 6.1 根源机制与证据链

**因果链 1：真实会话 + 失败信号排序 → 任务本质上更难**

- 方法差异：任务从生产会话恢复而非合成/预定义，并用 r = d+v+f 排序，其中 f 显式利用"用户重复表述/回滚"作为历史失败信号
- 机制变化：合成的编辑任务（如 WebCompass 的预定义操作池）难度由设计者想象决定，而真实会话中的请求**已经让真实用户挣扎过**；难度锚定在"人机交互的实际失败点"上，而非"看起来难"
- 指标体现：同一批模型在 WebCompass-edit 上 agentic 执行达 95.1%/99.4%，在 Co-Design Bench 上最强只有 69.9%——饱和现象消失【论文实验已支持】
- 反事实：若去掉失败信号排序（f 项），入选任务将偏向"一次就解决"的请求，难度分布下移——论文未做此消融，此为阅读者推测

**因果链 2：标准级隐藏 rubric → "部分满足"首次可度量**

- 方法差异：传统基准以任务为单位（通过/失败），或与参考产物比对
- 机制变化：专家把复合请求分解为可独立审计的标准（均值 8.6 条/任务），每条绑定证据类型。这让"完成 70%"从模糊印象变成可枚举、可归因的判断——具体哪条没过、为什么没过，都能回溯到证据
- 指标体现：R̄−F gap（69.9% vs 26.4%）只有在这种分解下才可计算；发现"全部 10 端点在 3–4 种编辑类型上都更低"也依赖标准级粒度【论文实验已支持】

**因果链 3：证据-声明匹配 + 独立驳斥 → 判分可信度高于单次 LLM 判分**

- 方法差异：普通 LLM-as-a-Judge 一次判分；本协议要求 (a) 视觉声明必须截图、交互声明必须动作日志，(b) 独立驳斥者专查 stub/硬编码/不可达功能
- 机制变化：第一层堵住"源码存在≠功能可达"的漏洞——一个 handler 写在代码里但用户点不到，拿不到交互分的证据；第二层针对 LLM 评审的系统性正偏（倾向于给生成内容高分）。两道防线合起来压缩了"虚假完成分"的空间
- 指标体现：人工复核 200 个输出的标准评分；评审者更换时绝对分漂移 ≤0.053 且交叉排序稳定【论文实验已支持】

**因果链 4：执行努力与完成度脱钩，指向长时程能力瓶颈**

- 现象：glm-5.2 在 ME 烧 7.29M token / 69 轮只得 0.572；gpt-6-astra 用 1.24M / 32 轮得 0.754
- 机制解释（阅读者推测，论文仅报告相关性）：高完成度更可能来自"每轮决策质量 + 需求保持（不遗漏后写入的标准）+ 闭环自验证（改完真的去渲染检查）"，而非蛮力重试。RE 的 Edit/Write 占比从 ME 的 7.3% 升到 27.6%，说明仓库编辑的瓶颈在修改规划而非感知

### 6.3 综合判断与未决问题

**多项研究共同支持的机制**：(1) agentic/证据增强评估优于单次 LLM 判分（Agent-as-a-Judge + 本文消融2）；(2) LLM 评审存在需要制度性纠偏的正偏倾向（Panickssery + 本文设计动机）；(3) harness 是与模型同级的一级变量（Harness Effects 研究 + 本文附录 H）。

**仍属推测的机制**：真实会话任务"本质上"比合成任务难（缺乏同模型同协议下两类任务的直接对照）；执行努力与完成度脱钩的解释（每轮决策质量假说未被直接检验）。

**优势成立的条件与可能的失效条件**：驳斥协议防的是"不实的完成分"，不防"误判的失败"（论文自认：驳斥不负责证明否定判决正确）；隐藏 rubric 依赖专家撰写质量，若标准写得过细可能惩罚合理的替代实现；harness 结论基于 2 solver × 3 harness 的网格，未含重跑方差，反转现象（ρ=−1.00）在小网格上可能被噪声放大。

## 七、必要知识反推

假设让一个没有任何背景的人完成这项工作，最少需要掌握什么？

### 7.1 领域知识层

- **前端工程全栈知识**：React/Vite 构建管线、DOM/CSS 渲染、单页应用与打包应用的区别、路由/状态/数据流的耦合方式——不懂这些就无法设计"结构/样式/交互/内容"的编辑类型学，也无法撰写可审计的验收标准
- **真实用户协作流程**：编码会话的形态（附件、粘贴图、多轮澄清）、用户的失败信号（重述、回滚）——不懂这些就想不到把"用户挣扎痕迹"编码为难度信号 f
- **反射式设计循环**（Schön 1983）：人机协同设计的迭代本质——这是"为什么任务是修订而非从零生成"的理论根基

### 7.2 方法论知识层

- **基准设计方法论**：去重（精确哈希+Jaccard 近重复）、硬过滤+启发式排序、任务有界化（每会话≤3查询）——从 39,325 条原始查询筛出 273 个任务，整套数据管线的纪律性来自测量方法论
- **LLM 评估的偏差文献**：G-Eval、自我偏好（Panickssery）、Agent-as-a-Judge——不知道 LLM 判分会正偏、会自偏，就不会设计独立驳斥者
- **软件测试的证据分层**：静态检查 / 渲染快照 / 交互后状态转移三层证据各自能证明什么、不能证明什么——"源码有 handler ≠ 功能可达"的洞察直接来自测试工程的可达性概念

### 7.3 工程知识层

- **环境容器化与可复现**：源码哈希快照、env.manifest、构建-启动-渲染三道验证门、P0/P1/P2 分级修复——2,730 次评估能跑起来靠的是这套基础设施
- **浏览器自动化**：Playwright 的动作录制、网络遥测、headless 渲染——交互标准的证据采集全靠它
- **评估器工程**：沙箱隔离、固定渲染恢复启发式、审计追踪（每条判决链接到证据）——大规模 LLM 评估的可审计性工程

### 7.4 知识融合的关键节点

三个"化学反应"节点值得注意：

1. **测试工程 × LLM 评估**：把软件测试的"证据分层/可达性"概念迁移到 LLM 判分协议中，得到"证据必须匹配声明类型"这一核心规则——这是纯 NLP 背景或纯测试背景的人都难以独立到达的设计
2. **用户行为挖掘 × 数据集构建**：把会话日志中的失败信号（重述/回滚）当作难度先验注入选题排序——把"数据集构建"从抽样问题变成了"挖掘人类- Agent 交互中的困难样本"问题
3. **评测学 × 产品思维**：双层指标（R̄ vs F）来自"平均完成率会掩盖交付失败"的产品洞察——评测设计直接服务于"Agent 能否真正交付"这一产业问题

## 八、论文中可以提取的通用性灵感

### 灵感 1：平均值掩盖交付失败——评估复合任务要同时报"覆盖率"和"全过率"

- **核心思想**：对多约束任务，单一平均分会把"每题 70%"与"70% 全对+30% 零分"混为一谈；必须双指标分离
- **论文证据**：最强模型 R̄=69.9% vs F=26.4%；文档任务池化分最高但全过率倒数第二低（18.2% vs 纯文本 37.0%）
- **推广场景**：(1) 自动驾驶评估：平均违规率低 ≠ 单趟零违规；(2) RAG 系统：平均引用准确率 ≠ 每篇文档无幻觉；(3) 医疗 AI：平均诊断分 ≠ 病例完整覆盖；(4) 自动化测试生成：平均通过率 ≠ 全套回归绿；(5) 项目管理：任务完成百分比 ≠ 里程碑全达成

### 灵感 2：把"用户挣扎痕迹"编码为难度信号

- **核心思想**：用户与系统的交互历史（重试、重述、回滚）是免费的困难样本标注器
- **论文证据**：排序公式 r = d+v+f 中 f∈[0,2]：4 次以上重复追问或显式回滚记满分 2；被选中的任务让 10 个顶级端点零分率达 5.8%（宽编辑组）
- **推广场景**：(1) 搜索引擎：改写查询序列作为难查询挖掘信号；(2) 客服系统：转人工前的对话轮数标注困难工单；(3) IDE 补全：撤销/重打序列标注低质量补全；(4) 教育：学生反复修改的题目进错题本；(5) 推荐系统：重搜索行为作为不满信号

### 灵感 3：证据类型必须匹配声明类型

- **核心思想**：验收任何声明时，先规定"什么证据才能证明它"，证据缺失即中止而非默认失败/通过
- **论文证据**：视觉声明无截图、交互声明无动作日志 → 中止评估；"源码有 handler"不能证明"界面可达"
- **推广场景**：(1) 安全审计：说"已修复"必须给复测记录而非代码 diff；(2) 科研复现：声明"复现成功"必须附原始日志；(3) 供应链：声称"合规"须提供溯源凭证；(4) 法务取证：书证/物证/电子证据的证明力分层；(5) ML 实验：声明 SOTA 须开源代码+可重跑脚本

### 灵感 4：判分者需要独立的驳斥者——正判决必须扛住对抗审查

- **核心思想**：LLM（和人）判分天然正偏；用第二个独立判分者专职否定（而非复核全部），成本更低且针对性强
- **论文证据**：驳斥者专查 stub/硬编码/不可达功能；与自我偏好文献（Panickssery 2024）的动因一致；换评审者最大漂移仅 0.053 且排序稳定
- **推广场景**:(1) 代码评审：merge 前专项"挑刺"审查员；(2) 风控：授信通过后的反欺诈复核；(3) 编辑部：事实核查员只查"待发表声明"；(4) 对齐评估：奖励模型打分后的 red-team 验证；(5) 招聘：offer 前的背调专门验证候选人声明

### 灵感 5：模型排名与执行环境是绑定的——报告结果必须披露 harness

- **核心思想**："模型 A 比模型 B 强"永远是不完整命题，完整版是"模型 A 在 harness H 下比……"
- **论文证据**：跨 harness 实验 ME 排名完全反转（ρ=−1.00）、同模型差距摆动 10–16.2pp；外部研究（arXiv:2609.32459）在另一任务域得到 19.4pp 的 harness 差距
- **推广场景**：(1) 模型选型：采购评测必须固定并披露推理框架/提示模板；(2) 竞技体育：成绩与装备、场地条件绑定记录；(3) 云服务：基准测试须披露实例规格与网络配置；(4) 药物试验：疗效结论须绑定给药方案与人群；(5) 教育测量：考试成绩须结合考试形式（机考/笔试）解释

### 灵感 6：起始状态本身可以做验收锚（reference-free 评估）

- **核心思想**：当任务定义为"修改"，修改前的状态就是天然的参考系——不需要也不可能有一份"标准答案"
- **论文证据**：基线 B 锚定"什么必须变/什么必须保留"，验收无需金码或目标截图；preservation constraints（无关内容保持）成为标准的一部分
