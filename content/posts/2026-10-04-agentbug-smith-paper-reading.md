## 一、论文背景

### 1.1 什么是 Agent Harness

如今的 LLM 智能体（agent）系统并不是"一个大模型"那么简单。一个能干活的智能体 = **骨干 LLM（大脑）+ Agent Harness（脚手架/编织层）**。Harness 是与骨干 LLM 协同塑造智能体行为的软件基础设施，负责：

- **上下文管理**：决定哪些信息进入模型的上下文窗口；
- **安全护栏**：防止智能体执行危险操作；
- **编排（orchestration）**：规划、多智能体协作、控制循环；
- **工具集成**：调用外部工具、服务、模型提供商 API。

随着智能体能力越来越强，harness 的规模也在急剧膨胀——论文举例，OpenClaw 的 harness 实现已达 **20 万行代码（200K LoC）** 量级。这已经是一套不折不扣的大型软件系统。

### 1.2 什么是 Harness Bug

既然 harness 是软件，就必然有 bug。**Harness bug** 指源于智能体特有结构与行为的实现缺陷，典型场景包括：

- 复杂工作流编排出错（如重试逻辑、循环控制）；
- 与外部资源交互出错（工具调用、模型提供商 API、网络服务、动态环境）。

它与传统软件 bug、以及骨干 LLM 本身的失败（如幻觉、推理错误）是三类不同的问题。**本文聚焦第一类：harness 代码里的缺陷。**

举个例子（论文附录 K 的真实案例）：智能体框架 strands-agents 的 harness-sdk 曾有一个 bug——调用结构化输出接口时，`system_prompt` 没有被传入 `structured_output`，导致智能体行为异常。这就是一个典型的、藏在编排层代码里的 harness bug。

### 1.3 为什么 Harness Bug 难修

前作 AgentIssue-Bench（NeurIPS 2025）给出了一个刺眼的数字：**SOTA 软件智能体修复 harness bug 的正确率仅 4.67%，而同一批智能体在传统软件基准 SWE-bench Verified 上能达 40.67%**。近十倍的差距，根源在于 harness bug 的三个特殊性：

1. **依赖实时交互**：bug 的触发依赖智能体与 LLM 提供商、工具、网络服务等外部资源的实时交互，失败往往只在特定执行状态与交互上下文下显形；
2. **非确定性**：LLM 输出本身不确定，同一输入可能时好时坏；
3. **跨组件失败**：错误可能横跨工具注册、记忆管理、编排控制等多个组件，定位困难。

### 1.4 现有基准的局限

想研究"如何修 harness bug"，先得有可执行的评测集。但现状是：

| 基准 | 面向 | 规模 | 构建方式 | 问题 |
|---|---|---|---|---|
| SWE-bench 系列（ICLR 2024 起） | 传统软件 bug | 大 | GitHub issue + 人工/半自动 | 不覆盖智能体特有组件与外部依赖 |
| AgentIssue-Bench（NeurIPS 2025） | harness bug | 本文引述为 43 个可执行 bug | 约 150 人工小时 | 小而固定、有训练数据污染风险 |
| SWE-Factory / SWE-bench-Live 等自动复现技术 | 传统软件 | — | 自动化流水线 | 无智能体感知，处理不了外部资源依赖 |

一句话总结背景：**harness bug 很重要、很难修，但评测它的基础设施既小又旧、还造不起——人工构建一个可复现的 harness bug 平均要花数小时。这就是本文要打破的僵局。**

## 二、论文定位和关联工作

### 2.1 本文在研究版图中的位置

本文处在三条研究线的交汇点：

1. **自动化 bug 复现 / 基准构建**：SWE-Factory（FSE 2026，多智能体自动构建评测环境 + 基于 exit code 的 fail2pass 验证）、SWE-bench-Live（持续更新防污染的活基准）、Repo2Run、SWE-rebench、R2E-Gym、BugSwarm、SWE-smith 等——但它们全部面向**传统软件或合成 bug**；
2. **智能体系统维护**：AgentIssue-Bench 首次系统刻画了 agent issue 的六类二十子类分类法，并用 500 人时构建了 50 个任务的基准（本文引述其中 43 个为可执行 harness bug）——但**规模小、固定、依赖重人工**；
3. **递归自我改进智能体（recursively self-improving agents）**：让智能体把真实世界的失败转化为可执行的评测实例与可复用的知识，进而改进自身——本文明确将此设为终极目标。

### 2.2 与最近邻工作的差异化

| 维度 | AgentIssue-Bench | SWE-Factory / SWE-bench-Live | **AgentBug-Smith（本文）** |
|---|---|---|---|
| 目标 bug 类型 | harness bug | 通用软件 bug | harness bug |
| 构建方式 | 人工为主 | 全自动 | **全自动、零人工介入** |
| 外部资源处理 | 人工设计 Docker 环境 | 无智能体感知 | **容器级 mock 重定向** |
| 无 IPT 的 bug | — | 复现数为 0 | **自动合成测试，复现 21–29 个** |
| 基准活性 | 固定 | SWE-bench-Live 持续更新 | **双流发现，持续吸收新 bug** |
| 规模 | 43 个（本文引述） | 数百至数千（通用域） | **当前 200 个，可无限扩充** |

一个值得注意的细节：本文与前作 AgentIssue-Bench 是同一核心团队的迭代——前作用 500 人时证明了"harness bug 极难修"这一命题，本文则解决"基准造不起、跟不上"的工程瓶颈。这种"先诊断、后给药"的研究节奏本身就很值得学习。

## 三、问题定义

把论文的工程叙事抽象出来，其本质问题是：**如何自动复现"失败依赖实时模型调用与外部资源交互"的 bug？**

一个合格的"复现"必须满足 fail-to-pass 标准：

- 在 **buggy commit** 上，以 issue 描述的相同方式失败；
- 在 **patched commit**（开发者修复后）上通过。

这个定义看似简单，对 harness bug 却有三个层层递进的子难题：

1. **发现问题**：从海量 GitHub 仓库和 issue 中，自动判断哪些是智能体系统、哪些 issue 是真正的 harness bug（而非普通 utility bug）——需要"识别"能力；
2. **构建环境**：harness 的运行时深度依赖 LLM 提供商 API、工具服务、网络——评测环境既要装得起来，又要**把这些外部依赖隔离掉**，否则复现不可重复、费用不可控——需要"隔离"能力；
3. **生成测试**：统计显示**仅 47.11% 的修 bug PR 自带 in-patch test（IPT）**，过半 bug 没有现成测试可参考——需要"合成"能力。只复现有 IPT 的 bug，会让基准系统性偏向"开发者写了测试"的那一小撮 bug。

三个子难题分别对应下一节的三个流水线阶段。

### 3.1 形式化表述

把上述问题形式化：给定一个开源智能体系统的 issue 集合，目标是自动产出三元组 **（D, T, 元数据）**——

- **D**：可构建的 Dockerfile，其容器内智能体系统可运行，且外部资源（模型 API、网络服务）被透明 mock 到本地；
- **T**：失败复现测试，满足在 buggy commit 上以 issue 描述的方式失败、在 patched commit 上通过（fail-to-pass）；
- **元数据**：issue 描述、关联 PR、buggy commit、patched commit 四元组。

流水线的优化目标即：在零人工介入约束下，最大化产出有效三元组的 issue 覆盖率（复现成功率），同时保证每个三元组确实是"真实复现"（而非形式上满足 fail-to-pass 的假阳性）。

## 四、问题解法：三阶段全自动流水线

AGENTBUG-SMITH 是一个多智能体（multi-agent）流水线，数据源与 SWE-bench 系列一致（GitHub issues），但全程零人工介入。

### 阶段一：Harness Bug 识别（双流仓库发现 + Repo Judge）

**怎么找到"哪些仓库是智能体系统"？** 论文设计了双流发现机制：

- **Stream I 静态初始化**：一次性基于 14+ 个社区维护的 awesome lists（如 awesome-agents、awesome-ai-agents、awesome-llm-powered-agent、Awesome-Chinese-LLM、Awesome-LLMOps 等）大批量初始化仓库池，并用五族关键词扩展（agent 身份 / LLM 与提供商名 / 工具与记忆 / 控制流 / 提示与框架名，覆盖 CrewAI、AutoGen、LangChain、MetaGPT、AutoGPT 等）；
- **Stream II 增量更新**：持续处理 GH Archive 小时级事件流（push、PR、issue、star、fork、release 均计为活跃），捕捉新兴活跃智能体仓库。两流合并去重形成候选池。

**质量门禁**有两条：① 充分社区采用——**≥50 GitHub stars 且含测试**；② 符合常见智能体结构——由 **LLM-based Repo Judge** 判定。Judge 的规范相当考究，包含：

- 核心组件表（LLM 大脑 / 感知 / 动作工具 / 编排 / 提供商集成 / 运行时工件）；
- 区别于传统软件的特征（非确定性、外部依赖、跨组件失败、prompt 一级公民、工作流导向）；
- 7 个 hook 证据（如 LLM provider 依赖、prompt 目录、记忆/向量库、tools 目录、控制循环、模型配置）；
- AS1–AS6 检查清单：≥3 个 yes 判 likely，≥5 个判 highly likely；纯文档集、教程、论文列表、独立工具库剔除。

对识别出的 issue，进一步用**六类二十子类的 Harness Bug 分类法**（A 提供商不兼容 / B 工具 / C 记忆 / D LLM 操作 / E 工作流 / F 通用 utility 需剔除）配合 HB1–HB6 检查清单过滤，确保基准不被 utility bug 污染。每个入选 bug 记录四元组元数据：issue 描述、关联 PR、buggy commit、patched commit。

### 阶段二：执行环境构建（迭代 Dockerfile + 容器级 Mock）

目标是为每个 bug 自动合成 Dockerfile，构建隔离执行环境。分三步：

**（1）规则引导初始化**：先跑规则式扫描，解析包描述符（依赖清单、构建配置、CI/CD workflow），推断运行时配置（语言、版本约束、包管理器、安装命令、测试运行器）；再以**单次 LLM API 调用**从官方最小镜像生成初始 Dockerfile，推理成本极低。

**（2）迭代精化**：工具型智能体根据构建报错迭代修正 Dockerfile；构建成功后**采样约 20 个现有测试**做环境冒烟测试——刻意轻量、不跑全量，避免开销与 flaky 测试带来的假阳性；断言失败不计入诊断反馈，只关注收集/导入/依赖等环境类错误。循环至成功或达最大尝试次数。

**（3）Mock 外部资源（本文最关键的设计）**：在**容器层注入 mock 服务环境变量**，把外部模型客户端调用**透明重定向**到本地测试 harness——无需侵入式修改代码库，即可实现评测期的严格隔离。

这一步直接回应了"harness bug 依赖实时模型调用"的核心矛盾：既排除了真实 LLM API 的非确定性与费用，又保留了 harness 代码路径的真实执行。

### 阶段三：失败复现测试生成（含测试-环境联合优化）

- **利用 IPT**：部分修 bug PR 自带 in-patch test，天然可作失败复现测试——但只有 47.11% 的 issue 有；
- **自动合成**：LLM 拿到 buggy 代码仓、issue 描述、开发者 patch 等上下文生成初始测试。**两条硬约束**：测试必须 import 并真正执行**真实 buggy 实现**；**只允许在 model-client / 网络边界 mock**（隔离非确定性外部网络与第三方模型 API），被测函数本身禁止 mock——确保复现的失败确实源于真实缺陷，而非测试替身；
- **联合优化（Co-fix）**：合格标准是 fail-to-pass。不满足时先迭代修正测试；但失败有时源于**测试与环境的错配**而非测试本身，此时联合精化测试 T 与 Dockerfile D。论文附录 F 给出实例：AgentScope issue #1297（断开的 Studio hook 重试后抛 ConnectionError 使 agent 崩溃，patch 无 IPT），test-only 优化 5 轮共 25 次尝试仍失败，co-fix 一次诊断同时修正容器为 editable install（/app/src 置于 PYTHONPATH 首位）并改写测试模拟 requests.post 失败，最终达成首个 fail-to-pass。

### 产物：LIVE-HARNESS-BENCH

把流水线持续跑在野外开源智能体系统上，就得到"活的"基准 **LIVE-HARNESS-BENCH**：当前发布含 **200 个可复现 harness bug**，可随新 bug 报告持续自动扩充（时间覆盖含 2026 年 8 月的最新 bug），以缓解训练数据污染。

## 五、评估指标与实验证据

### 5.1 识别准确率与稳定性（Table 1）

设置：从 225 个 harness bug 相关 issue 中随机抽 132 个人工标注（95% 置信水平、5% 误差限），两位标注者 Cohen's kappa = 0.88；稳定性为每 issue 独立分类 5 次的报告指标。

| 方法 | S_set ↑ | S_entropy ↓ | 仓库准确率 | Issue 准确率 |
|---|---|---|---|---|
| Vanilla LLM（基线） | 0.72 | 0.89 | 35% | 46% |
| **AGENTBUG-SMITH** | **0.92** | **0.94** | **95%** | **92%** |

### 5.2 复现成功率：核心对比（Table 2）

三个骨干 LLM 驱动流水线，与两个通用软件自动复现 SOTA 直接对比（公平起见，所有方法作用于同一批 225 个 harness bug 相关 issue）：

| 骨干 LLM | 方法 | 复现成功率 | 平均成本/issue |
|---|---|---|---|
| GPT-4.1-mini | SWE-Factory | 21/225（9.33%） | $0.09 |
| | SWE-bench-Live | 6/225（2.67%） | $0.41 |
| | **AGENTBUG-SMITH** | **45/225（20.00%）** | $0.56 |
| Kimi-k2.5 | SWE-Factory | 19/225（8.44%） | $0.37 |
| | SWE-bench-Live | 6/225（2.67%） | $0.66 |
| | **AGENTBUG-SMITH** | **46/225（20.44%）** | $0.91 |
| DeepSeek-v3.2 | SWE-Factory | 31/225（13.78%） | $0.31 |
| | SWE-bench-Live | 1/225（0.44%） | $1.05 |
| | **AGENTBUG-SMITH** | **63/225（28.00%）** | $2.44 |

- 复现成功率提升 **10.67–27.56 个百分点**，跨所有骨干 LLM 一致；
- **重叠分析**：跨全部骨干 LLM 合并共复现 **75 个 bug，其中 45 个为两个 baseline 均无法复现的独有 bug**；
- **人工校验**：75 个复现 bug 全量人工检查，**74 个（98.67%）为真实复现**（并非仅满足 fail-to-pass 形式）。

两个关键结论：环境构建成功率的提升达 **10.67–35.11 个百分点**；**两个 baseline 在无 IPT 时复现数均为 0**，而 AGENTBUG-SMITH 仍复现 21/26/29 个——测试生成组件结构性扩大了可复现 bug 的范围。

### 5.4 失败模式分析（附录 G，Table 7）

对未成功复现的 issue 做失败模式归类，三个模型的失败总数分别为 DeepSeek-v3.2：162、GPT-4.1-mini：180、Kimi-k2.5：179。主要失败模式（按三模型分布）：

| 失败模式 | DeepSeek-v3.2 | GPT-4.1-mini | Kimi-k2.5 |
|---|---|---|---|
| 依赖安装 | 44 | 33 | 19 |
| Docker 构建配置 | 19 | 15 | 40 |
| 缺 import 或 API 不兼容 | 15 | 25 | 7 |
| Python 打包元数据 | 15 | 27 | 4 |
| 原生构建/编译器 | 12 | 28 | 5 |
| 容器磁盘耗尽 | 12 | 0 | 40 |
| verifier/Docker 日志缺失 | 11 | 5 | 56 |
| oracle 或执行行为 | 17 | 30 | 4 |
| 测试崩溃或超时 | 4 | 9 | 1 |
| 环境+测试耦合 | 13 | 8 | 3 |

可见剩余瓶颈高度集中在**环境工程**（依赖安装、Docker 配置、打包元数据、原生构建）——这也从反面印证了本文把环境构建与测试生成做联合优化的设计方向是正确的：进一步提吞吐的空间不在"更聪明的测试写法"，而在更鲁棒的依赖解析与容器管理。

## 六、效果优势的根源解释

数字之外，更值得深挖的是**机制因果链**：为什么这套设计能赢过通用复现 SOTA？论文的每个组件都精准对应 harness bug 的一个特殊性。

**根源矛盾：harness bug 的触发依赖智能体与外部资源（LLM 提供商、工具、网络服务、动态环境）的实时交互，失败只在特定执行状态与交互上下文下显形——通用复现技术直接迁移必然失效。**

对应的机制链：

1. **容器级 mock 外部资源 → 解决"依赖实时模型调用"**：环境变量透明重定向，不侵入代码。效果：排除真实 LLM API 的非确定性与费用，同时保留 harness 代码路径的真实执行——这是无智能体感知的 baseline 做不到的；
2. **边界受限 mock 原则 → 保证复现有效**：测试必须执行真实 buggy 实现，只许在 model-client/网络边界 mock。效果：失败确定来源于缺陷本身而非测试替身——98.67% 人工校验有效率是直接佐证；
3. **规则引导 + 迭代精化的环境构建 → 处理智能体特有的依赖结构**：成本极低的单次 LLM 调用出初始 Dockerfile，报错驱动迭代，20 个采样测试冒烟。效果：环境构建成功率高出 baseline 10.67–35.11 个百分点；
4. **测试-环境联合优化（co-fix）→ 解锁错配型失败**：承认失败可能源于 T 与 D 的错配。效果：AgentScope #1297 案例中 test-only 25 次尝试失败、co-fix 一次成功——解锁单靠测试优化无法复现的 bug；
5. **面向无 IPT 的测试合成 → 扩展复现窗口**：47.11% 的 issue 有 IPT 意味着过半 bug 无现成测试。效果：baseline 无 IPT 复现全部为 0，本文拿到 21–29 个——覆盖范围的结构性扩大，这也是 45 个独有 bug 的主要来源；
6. **Harness 专属识别规范 → 保证基准纯度**：六类二十子类分类法 + HB1–HB6 检查清单把 harness bug 与 utility bug 严格分离。效果：识别准确率 92%、稳定性 0.92/0.94，基准不被通用 bug 稀释；
7. **双流仓库发现 → 保证"活"性**：awesome-lists 静态初始化 + GH Archive 小时级事件流增量更新。效果：持续吸收新 bug（含 2026 年 8 月），对抗训练数据污染——这是固定基准在机制上无法提供的。

**技能蒸馏的结果还揭示了一个更深的洞察**：不微调模型、只注入纯文本 SKILL.md + 模式扫描器，就能把正确修复率提升 6.32 个百分点、函数级定位翻近一倍（34.60% → 66.41%）。这说明当前智能体修 harness bug 的瓶颈**主要在上下文知识（不知道该怀疑哪里、该用什么模式），而非推理能力本身**——补知识比换更强的模型性价比高得多。这也正是通往"递归自我改进智能体"的现实路径：失败 → 评测实例 → 蒸馏知识 → 修复能力提升 → 更强的智能体去复现更多失败，形成闭环。

## 八、通用性灵感

即便不做智能体基准研究，这篇论文也有若干可迁移的思想：

1. **活基准范式**：基准不必是一次性工程。把"数据构建"本身做成可持续运行的服务（双流发现 + 自动流水线），基准就从静态快照变成随领域演化的基础设施。任何快速迭代领域的评测都可以借鉴——用更新对抗污染，用规模换取代表性；
2. **失败转资产**：智能体系统的 GitHub issue 不只是待修的麻烦，而是免费的、人类开发者已标注并验证（通过修 bug PR）的评测素材与知识素材。同一个失败被利用了两次（评测实例 + 蒸馏知识），这是对"真实世界信号"的极致榨取；
3. **边界 mock 原则**：测非确定性系统时，在**外部边界**（model-client/网络）做透明重定向、在**被测本体**保持真实——这条原则适用于任何依赖外部服务又需要可重复测试的系统（不只 LLM 应用）；
4. **联合优化思维**：当一个组件调不通时，考虑失败可能源于组件间的错配（测试 × 环境），而不是无限迭代单组件——AgentScope 案例里 25 次 vs 1 次的对比是最好的注脚；
5. **经验蒸馏为 SKILL.md**：不微调、不改架构，把成功修复的模式沉淀为受安全约束的纯文本技能 + 轻量扫描器，就能显著提升智能体表现。对于没有训练资源的团队，"上下文里补知识"是性价比最高的自我改进路径；
6. **先诊断、后给药的研究节奏**：同一团队先用 AgentIssue-Bench 证明问题难（500 人时），再用 AgentBug-Smith 解决基准造不起的瓶颈——每篇论文解决上一篇暴露的一个瓶颈，研究线因此越走越宽。

## 结语

AgentBug-Smith 把"harness bug 难以自动复现"这个卡住整个领域的问题，拆成了识别、隔离、合成三个可工程化的子问题，并用双流发现 + Repo Judge、容器级 mock、fail-to-pass 测试生成与联合优化逐一击破——复现成功率提升 10.67–27.56 个百分点、98.67% 人工校验有效、200 个 bug 的活基准、9% vs 40.67% 的修复率落差、+6.32 个百分点的技能蒸馏，构成了完整的证据链。

更长远地看，这篇论文是把"智能体系统的真实失败"接入"递归自我改进"闭环的关键一环：失败变成可执行的评测实例，评测实例蒸馏出可复用的修复技能，技能再让智能体变得更强。当 harness 规模奔着几十万行代码而去、而最强智能体也只能修好不到十分之一的 harness bug 时，这条自动化流水线的价值才刚刚开始显现。
