> **论文链接**：[Termination Lag: Coding Agents Solve Early but Stop Late](https://arxiv.org/abs/2611.14960)
> **发表时间**：2026 年 11 月（arXiv:2611.14960v1，2026-11-11 提交，cs.AI）
> **机构**：The Pennsylvania State University（Musa Cim、Burak Topcu、Mahmut Taylan Kandemir）——纯高校，无企业参与（开源模型经 Argonne Aurora 超算以 vLLM 提供）

## 一、论文背景

### 1.1 最终 patch 评分制造了一个巨大的观测盲区

编码 agent 的评测有一个约定俗成的范式：给 agent 一个自然语言的 issue 描述和一个真实仓库，让它自主探索、编辑、测试，最后提交一个 patch；评测系统拿基准自带的隐藏测试跑一遍这个 patch，通过即得分。SWE-bench（Jimenez et al., 2024）及其衍生基准（Verified、Multilingual、Pro 等）都是这个范式。

问题在于，这个分数只描述**终点的状态**，完全不描述**过程**。论文开篇给了一个精准的例子：两个 agent 都在第 10 步做出了正确的编辑，一个立刻提交，另一个又跑了 40 步——重新跑测试、检查调用方、反复审查 diff——才停。两者得到完全相同的分数，但效率天差地别。

更隐蔽的伤害在另一头：一个 agent 可能中途就产出过正确 patch，然后继续"完善"，甚至把它改坏——最终提交的 patch 通不过测试，被判失败。可事实上这个任务它**早就解出来了**（Kim et al., 2026 的 Coherence Collapse 也观察到了这一现象）。失败分数掩盖了一次已经完成的成功。

### 1.2 论文的核心概念：TTFCP、TL、NTL

为了把"何时做对"和"何时停止"分开，论文定义了三个量（以 agent 步为单位，一步 = 模型推理 + 选择动作 + 工具执行）：

- **TTFCP**（Time to First Correct Patch）：首个能通过官方基准测试的 patch 出现的步数 F；
- **TL**（Termination Lag，终止滞后）：TL = S − F，即首个正确 patch 之后 agent 又执行了多少步才自行停止（S 为 agent 自己停下的步数）；
- **NTL**（Normalized Termination Lag）：NTL = (S − F)/S，即首个正确 patch 之后的步数占整条轨迹的比例，用于跨不同长度轨迹比较。

一句话概括论文发现的现象：**agents solve early but stop late**——TTFCP 远小于 S，TL 大得惊人。

### 1.3 为什么这件事重要

知道何时停止和做出正确修复一样关键。每多一步都是一次对不断膨胀的上下文的模型调用，烧 token、加延迟，还引入改坏已能工作的代码的风险。但又不能一刀切地要求 agent 少验证——agent 看不到基准测试，只能靠自己的证据判断 patch 是否可靠，一定量的验证是必要的。真正的空白是：没人系统量化过"正确 patch 出现之后，agent 到底还走了多少步、这些步在干什么、对 patch 命运有何影响"。这篇论文就是补这个空白。

## 二、论文定位和关联工作

论文的相关工作分四条脉络，都可以理解为"和停止行为擦肩而过、但没正面命中"的研究：

| 脉络 | 代表工作 | 做了什么 | 与本文的差异 |
|---|---|---|---|
| 过度思考/过度生成 | Chen et al. 2024（overthinking）、Guo et al. 2024（学习停止信号）、Solovyeva & Castor 2026 | 推理模型早早答对还继续写；用停止信号或"过测试即停"截断 | 只管**单次模型响应内部**的生成冗余，不管跨步骤的 agent 行为 |
| agent 成本与低效 | Wu et al. 2026（token 随语言变化）、Weinberger & Hozez 2026（提示诱发额外验证）、Majgaonkar et al. 2025、Zhao et al. 2026（失败轨迹更长）、Sahoo et al. 2026（AgentLens "lucky pass"）、Mohsin et al. 2026（自测常放过错误 patch） | 刻画 agent 努力花在哪里 | 没有系统量化**首个正确 patch 到停止之间**隔了多少步 |
| 早停、预算与重启 | Pham et al. 2026（AgentStop 省能耗）、Wang et al. 2026、Guo et al. 2026（EET）、Shi et al. 2026（EarlyEval）、Gao & Peng 2025、Li et al. 2026（TokenEconomizer） | 从轨迹预测失败或成功来提前停，或直接限步数/成本 | 它们预测的是**成功/失败**；本文直接测量 patch **何时已经正确**，给出"按成功停止"的理论上界收益 |
| 中间 patch 研究（并发工作） | Kim et al. 2026（中途正确修复被改丢）、Jain & Vedam 2026（19 个任务逐步测 patch 辅助重启决策）、Shen et al. 2026（从中间状态估计最终成功概率） | 同样开始关注中间 patch | 本文是覆盖面最广的系统测量：3 基准 × 5 模型 × 2 框架 |

论文的站位很清晰：它不提出停止算法，而是提供**测量基础设施与参考点**——TL 给出"在最恰当的时刻停"最多能省多少，被改坏的运行给出"继续走"的额外代价。任何实用的停止规则都需要这两个数字做基准线。

## 三、问题定义：把两种能力解耦

### 3.1 抽象化：一个被评分制度掩盖的解耦

论文最深的一个观点写在引言里：**最终 patch 评测混淆了两种截然不同的能力——产出正确修复的能力，和认识到修复已完成的能力。**

用一个类比：这就像考试只收最后一页草稿纸誊写的答案，不管你第 10 分钟就解完了、后面 50 分钟都在验算甚至涂改。分数上区分不出"快而果断"和"快而优柔寡断"的学生，也区分不出"写对过又改错"和"从未写对"的学生——但用人单位显然在意这个区别。

抽象成能力维度：

- **修复能力**：轨迹中是否存在某个状态，其 patch 通过官方测试（对应 TTFCP 是否有限）；
- **停止能力**：agent 能否在拿到正确修复后，基于运行时自己可见的证据，及时终止（对应 TL/NTL 的大小）；
- **保持能力**：拿到正确修复后是否守得住（对应 patch 是否被后续步骤改坏）。

### 3.2 形式化定义

对一条包含 S 个 agent 步的轨迹，令 F 为**最早**一个 patch 能通过官方基准评估的步数：

- TTFCP = F（式 1）
- TL = S − F（式 2）
- NTL = (S − F)/S（式 3）

其中 S 是 agent **自行停止**的步数（撞到步数或上下文预算上限的少数运行按最后一步计，这类占每设置 1-4%）。报告对象主要是"以正确 patch 收尾的成功轨迹"；此外定义**首 patch**为第一次编辑源码后记录的 patch，并统计到达首个正确 patch 前产生的不同 patch 数。

注意一个实验设计上的关键点：这些指标里的"正确"由官方隐藏测试判定，而 agent 全程看不到这些测试——所以测量本身不会改变 agent 行为（详见下一节的 logging proxy 设计）。

## 四、问题解法：给每一步的 patch 拍快照

### 4.1 Logging proxy：夹在 agent 与模型端点之间的记录仪

要测量 TTFCP，必须知道**每一步结束时代码库长什么样**。论文的做法非常工程化：

1. **逐步记录**：在 agent 与模型端点之间部署一个 logging proxy。每当 agent 完成一步、等待下一次模型响应时，proxy 先把当前 patch 记录下来再转发请求。一步 = 模型推理 + 选定动作 + 工具执行，正好是行为的基本单元。
2. **临时 Git index 构造 patch**：每个记录的 patch 是当前仓库状态与任务 base commit 的 diff。构造过程用**临时 Git index**完成，完全不触碰 agent 的工作仓库——测量是零侵入的。
3. **离线评估 + 去重**：运行结束后，在**隔离容器**中用基准官方评估流程测试每个记录的 patch；内容相同的 patch 只评估一次。
4. **无反馈回路**：这套回溯式评估的结果不会以任何形式返回给 agent，因此正确性追踪不影响 agent 后续决策。

这个设计解决了一个方法论死结：如果你让 agent 在线看到"测试通过与否"，它的行为就变了，测出来的就不是自然停止行为。事后离线评估让论文能拿到 agent 自己都不知道的 ground truth。

### 4.2 实验覆盖面

- **框架**：OpenHands（主框架，全部 5 模型）+ mini-SWE-agent（Qwen3-Coder on Verified 复验，检验发现是否依赖框架）；
- **模型（5 个）**：开源 Qwen3-Coder-30B-A3B、Laguna-XS.2（vLLM on Aurora 超算，跑全量 Verified 500 任务与 Multilingual 300 任务，预算 100/250 步、上下文 131K/256K）、Seed-OSS-36B（SWE-bench Pro，150 步）；闭源 Claude Haiku 5.5、GPT-6 Luna（API，Verified，100 步预算）；
- **基准（3 个）**：SWE-bench Verified（Python，500 任务）、Multilingual（9 种语言，300 任务）、Pro（更长程的难任务）；
- **核心设置**：Qwen3-Coder 与 Laguna-XS.2 在 Verified + Multilingual 上的四个组合，论文正文的主要数字都来自这里。

### 4.3 五类步骤活动分类

对成功轨迹中首个正确 patch 之后的每一步，按记录的工具调用及其参数做规则分类：

| 类别 | 包含的活动 |
|---|---|
| **Verify（验证）** | 跑仓库现有测试、写并执行额外测试脚本、构建项目 |
| **Explore（探索）** | 检查文件、在仓库内搜索、用 Git 命令查看改动 |
| **Edit（再编辑）** | 对实现的进一步源码修改 |
| **Wrap-up（收尾）** | 删除临时文件、提交最终响应 |
| **Think/other（思考与其他）** | 其余步骤 |

另外独立追踪每条到达过正确 patch 的轨迹（含最终失败的）中 patch 正确性的演化。

## 五、评估指标与实验证据

### 5.1 RQ1：正确 patch 出现得有多早——首编辑即正确 38-82%

在所有到达过正确 patch 的运行里（Table 2）：

| 模型 @ 基准 | 首 patch 中位步 | 首正确 patch 中位步 | **首 patch 即正确** | 平均尝试次数 |
|---|---|---|---|---|
| Qwen3-Coder @ Verified | 30 | 30 | **82%** | 1.3 |
| Qwen3-Coder @ Multilingual | 34 | 34 | 66% | 1.7 |
| Laguna-XS.2 @ Verified | 36 | 38 | 70% | 1.9 |
| Laguna-XS.2 @ Multilingual | 45 | 51 | 48% | 2.8 |
| GPT-6 Luna @ Verified | 9 | 9 | 80% | 1.7 |
| Seed-OSS @ Pro | 17 | 26 | 38% | 3.6 |

首编辑中位步在 9-45 之间；跨所有设置，**38-82% 的运行第一次改源码就改对了**，到达正确平均只需 1.3-3.6 个不同 patch。Qwen3-Coder 在 Verified 上首 patch 与首正确 patch 的中位步同为 30——大多数成功任务真的是"一击即中"。任务越难（Seed-OSS @ Pro）"一击率"越低（38%），但依然有超过三分之一。

### 5.2 RQ2：停得有多晚——中位 TL 6-57 步、NTL 35-60%

核心设置的完整数据（Table 1，成功运行的中位数）：

| 设置 | Solved | TTFCP | 终步 S | **TL** | **NTL** | 上下文增长 |
|---|---|---|---|---|---|---|
| Qwen3-Coder @ Verified | 43.8% | 30 | 48 | **16 步** | **35%** | +30% |
| Qwen3-Coder @ Multilingual | 22.3% | 34 | 54 | **18 步** | **37%** | +28% |
| Laguna-XS.2 @ Verified | 56.0% | 38 | 95 | **57 步** | **60%** | +78% |
| Laguna-XS.2 @ Multilingual | 48.0% | 50 | 108 | **56 步** | **54%** | +55% |

泛化设置同样成立：Claude Haiku 5.5 @ Verified 中位 TTFCP 9、TL 10 步、NTL 54%；GPT-6 Luna @ Verified TL 仅 6 步、NTL 36%；Seed-OSS @ Pro 同样出现分离；换 mini-SWE-agent 框架（Qwen3-Coder @ Verified）TL 12 步、NTL 37%。

三个基准、五个模型、两个框架，结论一致：**成功运行中约三分之一到超过一半的步骤，花在首个正确 patch 之后**。Laguna-XS.2 是极端案例——60% 的轨迹是"事后努力"，且这段滞后让它的上下文又膨胀了 78%。

框架对比（Table 4，同为 Qwen3-Coder @ Verified，500 任务）还给出一个有趣的细节：mini-SWE-agent 解决率更低（32.4% vs 43.8%）但更省——每任务中位未缓存计算 token 22.2K vs 39.0K，末步上下文 20.5K vs 42.9K。同一模型在不同 harness 下的"停止性格"差异明显。

**Oracle 早停收益**：如果有一个全知的停止器，在每个运行的首个正确 patch 处刹车（从未正确的运行不动），成功运行可省中位数 35%（Qwen3-Coder @ Verified）到 60%（Laguna-XS.2 @ Verified）的步骤，同时保留每一个原本解出的任务。这是任何实用停止规则的理论上界。

### 5.3 RQ3：滞后步都在干什么——verify 48-63%、explore 15-29%

成功轨迹中首个正确 patch 之后的步骤构成（Table 3）：

| 设置 | Verify | Explore | 再编辑源码 | Wrap-up | Think/其他 |
|---|---|---|---|---|---|
| Qwen3-Coder @ Verified | **63%** | 21% | 2% | 6% | 7% |
| Qwen3-Coder @ Multi | 62% | 15% | 5% | 7% | 12% |
| Laguna-XS.2 @ Verified | 59% | 29% | 4% | 6% | 3% |
| Laguna-XS.2 @ Multi | 48% | 29% | 6% | 9% | 8% |
| GPT-6 Luna @ Verified | 55% | 22% | 5% | 12% | 6% |
| Seed-OSS @ Pro | 50% | 22% | **19%** | 7% | 3% |

两个信号极强的事实：第一，**验证是每个设置中最大的活动类别**（48-63%）——跑测试、写检查、构建；探索又占 15-29%。第二，**再编辑源码极其罕见**（2-6%），唯一例外是最难基准 Pro 上的 Seed-OSS（19%）。agent 在做对之后几乎不"继续写代码"，它是在反复确认"我真的做对了吗"。

### 5.4 RQ4：继续干对 patch 有什么影响——1-8% 改坏收场

所有到达过正确 patch 的运行中，patch 的最终命运（Table 3 下半）：

| 设置 | 保持正确到最后 | 破坏后又修复 | **破坏且以失败收场** |
|---|---|---|---|
| Qwen3-Coder @ Verified | 96% | 3% | **1%** |
| Qwen3-Coder @ Multi | 82% | 10% | **8%** |
| Laguna-XS.2 @ Verified | 84% | 11% | **5%** |
| Laguna-XS.2 @ Multi | 61% | 31% | **8%** |
| GPT-6 Luna @ Verified | 88% | 8% | **4%** |
| Seed-OSS @ Pro | 79% | 17% | **4%** |

61-96% 的运行守住了正确 patch；3-31% 中途破坏但后来修复；**1-8% 破坏后没能恢复，以失败收场**——这些运行只要在首个正确 patch 处停下，基准分数就是成功的。Laguna-XS.2 @ Multilingual 最触目：31% 的运行经历过"把对的改坏"。

### 5.5 局限

论文自己列的边界：每个任务只跑一次（无法估计运行间方差）；1-4% 撞限运行按最后一步计；步数只是计算成本的近似；活动分类靠工具调用上的规则；Seed-OSS @ Pro 解出任务少、统计样本小；结论未必迁移到其他设置。

## 六、效果优势的根源解释

这篇论文的价值不在"打败谁"——它是测量研究，没有方法 baseline。值得解释的是：为什么这些发现成立、为什么这种测法能成立。分三个子节。

### 6.1 自证的必要性 vs 过度验证：结构性根源

**【证据等级：论文正文论断 + 间接数值证据】**

为什么 agent 不能做完就交？因为**agent 看不到基准测试**。它没有任何直接渠道知道"我的 patch 已经通过了官方判定"，只能靠运行时自己收集的证据——跑仓库测试、写新测试、构建——来推断 patch 可靠。所以一定量的验证是任务结构决定的**必要成本**，不是纯浪费。

但数值说明必要成本解释不了全部：成功运行 35-60% 的步骤花在事后，其中 verify 占 48-63%、explore 占 15-29%、再编辑只有 2-6%。如果验证只是为了确认正确性，几轮测试就该收敛；近三分之二（Qwen3-Coder @ Verified 63% verify + 21% explore）的滞后步在"确认已正确的事情"，而几乎不在改进代码。必要的自证与过度的反复之间的差值，就是停止规则可以挤掉的水分。oracle 早停能省 35-60% 而不丢任务，证明这部分至少在基准意义上是纯冗余。

### 6.2 停止决策的不确定性：行为层面的根源

**【证据等级：数值模式的解释性假设】**

论文的机制解读是：滞后主要源于**停止决策的不确定性，而非修复能力不足**。支撑这个解读的数值模式：

- 滞后步几乎不改代码（再编辑 2-6%），说明不是"修复能力不够、还在试错"；
- 滞后步大量是验证与探索，说明 agent 处在"我倾向于相信做对了，但不敢确定"的状态；
- 1-8% 的运行在此期间反而把正确的 patch 改坏——犹豫期的动手操作带来回归风险；
- 上下文在滞后期间还在膨胀（+28% 到 +78%），每一步的边际成本越来越高，而边际信息收益越来越低。

换句话说，这是决策论意义上的"何时收手"问题：agent 的修复能力（首编辑 38-82% 即正确）普遍强于其判断"何时该交卷"的能力（中位拖 6-57 步）。模型间差异也佐证这是个独立的"能力"：GPT-6 Luna 中位 TL 只有 6 步，Laguna-XS.2 高达 57 步——修复能力强（solved 56%）不等于停得利索（NTL 60%）。

### 6.3 与 agent efficiency 研究的交叉验证

**【证据等级：外部独立工作的旁证】**

论文的发现不是孤例，相关的独立测量工作从侧面交叉印证：

- Sahoo et al. 2026（AgentLens）发现部分通过验证的运行在已验证修复后仍继续探索——"lucky pass"问题的另一面；
- Weinberger & Hozez 2026 发现仅是提示中要求确定性就会诱发额外验证——验证倾向部分是可提示驱动的，说明有压缩空间；
- Zhao et al. 2026、Majgaonkar et al. 2025 发现失败运行更长且在变得不可挽回后仍在继续——"不停"是跨成败状态的普遍行为偏置；
- Mohsin et al. 2026 发现 agent 自写的测试经常放过错误 patch——这解释了为什么 agent 不敢轻易相信自己的验证结果，加重了停止决策的不确定性；
- Chen et al. 2024 在推理模型上发现的 overthinking（早早答对继续写）提示这可能是 LLM 的一个更底层倾向，在 agent 场景被多步循环放大。

论文在这些工作之上的增量在于：首次用逐步 patch 记录 + 离线官方评估的方法，把"解决"与"停止"之间的距离量化成了跨 3 基准 × 5 模型 × 2 框架一致的数字。

## 七、必要知识反推

要读懂并复现这篇论文的工作，需要三层知识，以及把它们焊在一起的融合节点。

### 7.1 基础层

- **LLM agent 基本循环**：ReAct 式（Yao et al., 2023）的"推理 → 动作 → 观测"循环，理解"一步"是什么；
- **Git 基础**：diff、index、base commit 的语义——论文的 patch 记录完全构建在 Git 机制上；
- **容器与可复现评估**：为什么隔离容器 + 官方评估流程能保证测量的公正性；
- **描述统计**：中位数、分位数（p90）、为什么轨迹长度差异大的场景要用 NTL 归一化。

### 7.2 领域层

- **SWE-bench 家族**：Verified（500 Python 任务）、Multilingual（300 任务、9 语言）、Pro（长程难题）的构成与评测协议，F2P/P2P 测试的概念；
- **agent 框架**：OpenHands 的工具集（文件查看、编辑、命令执行）与 mini-SWE-agent 的极简 bash-only 设计，以及框架/harness 对行为的塑造作用；
- **推理服务**：vLLM 部署、API 访问、上下文窗口与步数预算这类实验约束；
- **中间量产业脉络**：overthinking、early termination、agent 成本分析的研究史（第二节的四条线）。

### 7.3 方法层

- **proxy 架构**：在 agent 与模型端点之间做中间人记录——零侵入测量的通用工程手段；
- **离线回溯评估**：事后评估 + 无反馈回路，解决"测量改变行为"的观察者效应；
- **行为分类学构建**：用工具调用及其参数做规则化活动标注（verify/explore/edit/wrap-up/think）；
- **Oracle 参照系设计**：用全知停止器给实用方法定理论收益上界。

### 7.4 融合节点

真正的门槛不在任何单层，而在三处焊接：

1. **"步"与"patch 状态"的对齐**：把离散的 agent 步序列与连续演化的仓库正确性状态对上——需要同时懂 agent 循环（基础层）和 Git patch 语义（领域层）才能实现 logging proxy；
2. **测量 vs 行为的解耦**：意识到"在线评测正确性"会污染行为，从而设计出离线评估方案——这是实验方法论层面的洞察；
3. **指标设计的动机**：为什么定义 TTFCP/TL/NTL 三个量而不是只报一个——因为要比较不同长度轨迹（NTL）、要区分"何时做对"（TTFCP）与"拖了多久"（TL），这来自对评测混淆两种能力这一概念问题的先验把握。

## 八、通用性灵感

### 灵感一：为"完成时刻"建立可测的 ground truth，把能力解耦成独立维度

**核心思想**：任何只看最终产物的评分制度都在混淆多种能力。用事后离线评估为过程中的关键事件（此处是"首个正确 patch"）建立 ground truth，就能把"做到"与"知道做到了"解耦成可独立测量的维度。

**论文证据**：logging proxy + 临时 Git index + 隔离容器离线评估，首次让 TTFCP/TL/NTL 可测；测出首编辑即正确 38-82%、NTL 中位 35-60%。

**推广场景**：
1. 深度研究 agent：逐步保存"当前报告草稿"，离线用事实核查 rubric 评估，可测"何时达到可交付质量"与"何时停止"的差距；
2. 数学证明 agent：每步尝试提取并形式化验证当前证明草图，定位"其实已证完还在绕"的滞后；
3. GUI 操作 agent：逐步判定任务目标是否已达成（如订单已提交），测量达成后多余的点击与页面刷新；
4. 人机协作系统：给人类监督者展示"agent 可能已经完成"的信号，降低等待成本；
5. 教育评测系统：用过程性测评区分"会做但不确定"与"不会做"的学生，前者需要的是决断力训练而非知识训练。

### 灵感二：Oracle 参照系——给任何优化问题先量出理论上界

**核心思想**：在设计启发式方法前，先构造一个全知的 oracle 版本，量出完美策略的收益上界。这个数字既告诉你值得投入多少，又为后续所有实用方法提供基准线。

**论文证据**：oracle 停在首个正确 patch 可省成功运行中位 35-60% 的步骤且保留全部已解任务——这是所有实用停止规则的理论天花板。

**推广场景**：
1. 上下文压缩：oracle 每步删除"未来不再被引用"的信息，量出压缩收益上界；
2. 缓存与预取系统：oracle 知道未来访问序列，预划最优缓存策略收益上界；
3. 测试选择：oracle 知道哪些测试能杀掉本次改动引入的 bug，给测试优先级算法定上界；
4. 多 agent 协作：oracle 知道任务真实难度，预先分配最优路由，量化调度算法的改进空间；
5. 早停训练：oracle 知道泛化性能曲线的真实拐点，为学习率调度/早停准则提供极限。

### 灵感三：犹豫期是风险期——多余动作有回归成本，"停"本身要被优化

**核心思想**：继续执行的代价不只是资源消耗，还有**破坏已有成果的回归风险**。1-8% 的失败是"做对了又改坏"造成的。停止不是消极行为，而是一个需要被显式优化的决策点。

**论文证据**：61-96% 保持正确，3-31% 破坏后修复，1-8% 破坏且以失败收场——这些失败只需在首个正确 patch 处停手即可避免；滞后期再编辑虽少（2-6%）但每次动手都有破坏风险。

**推广场景**：
1. 数据管道：ETL 任务成功后跳过"优化性重跑"，避免把正确数据集覆盖坏；
2. 自动交易系统：策略达标后强制冷却期，防止高频微调引入新风险；
3. 代码重构工具：引入"已通过全量测试后锁定"机制，后续改动需显式解锁；
4. agent 框架设计：在 harness 层提供"验证通过即建议提交"的检查点信号，降低模型自行判断的负担；
5. 基础设施运维：变更自动化在健康检查通过后自动收尾，而非继续"加固"。

### 灵感四：结构化的行为分类学让"时间都去哪了"变成可比较的科学问题

**核心思想**：把开放式的 agent 轨迹按活动类别（verify/explore/edit/wrap-up/think）做规则化标注，"agent 在干什么"就从轶事描述变成了可跨模型、跨基准比较的分布。分布的异常点直接指向诊断结论。

**论文证据**：verify 48-63% 一家独大 + 再编辑 2-6% 极低 → 滞后源于停止不确定性而非修复不足；Seed-OSS @ Pro 的 edit 19% 异常 → 难基准上行为模式真的不同。

**推广场景**：
1. agent 训练数据配比：统计成功/失败轨迹的活动分布差异，针对性补充稀缺类别的训练信号；
2. 模型选型：把"停止性格"（NTL 分布）作为部署选型指标——延迟敏感场景选停得快的模型；
3. 复杂工具使用分析：把工具调用聚类成语义活动，定位 agent 浪费在哪类操作上；
4. 人类工作流研究：对开发者 IDE 事件流做同样分类，量化人类"验证循环"的占比，与 agent 行为对照；
5. 安全审计：审计轨迹中 explore 类操作是否越权访问敏感路径，把行为学变成审计手段。

### 灵感五：测量基础设施本身是贡献——零侵入、无反馈回路的观测设计

**核心思想**：当你无法观测某个量时，先造一台不改被观测系统行为的测量仪器。零侵入（不碰工作区）+ 无反馈（不给 agent 任何评估结果）是让测量保持真实性的两个关键不变量。

**论文证据**：logging proxy 只在 agent 等待模型响应的间隙抓取快照，用临时 Git index 不触碰工作仓库，离线评估结果永不回传——agent 的行为与没有测量时完全一致。

**推广场景**：
1. 生产环境 LLM 应用观测：在网关层记录每次调用的完整上下文快照，做质量回溯而不影响线上行为；
2. 分布式系统追踪：中间件旁路记录请求-状态映射，定位"系统早已进入稳态还在空转"的浪费；
3. 可观测性 + 隐私：证明观测通道与控制通道隔离，测量不构成信息泄漏面；
4. 科学化的产品 A/B 分析：先离线建立"如果用户在第 k 次交互就达成了目标"的回溯判定，再评估 funnel 优化的真实空间；
5. agent 评测平台设计：把"逐步快照 + 事后评估"做成基准平台的标准能力，让所有停止/重启研究共享同一测量底座。

## 结语

这篇论文没有提出新模型、新算法，却很可能改变我们看 agent 分数的方式：resolve rate 告诉你 agent **能不能**解题，TTFCP/TL/NTL 告诉你它**何时**解出、**多晚**才肯承认。当模型修复能力越来越强（首编辑 38-82% 即正确），"知道自己已经做完了"正在成为效率与可靠性的下一个瓶颈——中位三分之一的步数浪费在事后，1-8% 的成功甚至被犹豫亲手改没。对评测者，停止行为应成为独立报告的维度；对框架开发者，验证通过的检查点信号是低垂的果实；对研究者，oracle 早停 35-60% 的收益上界标出了一片值得开采的矿脉。
