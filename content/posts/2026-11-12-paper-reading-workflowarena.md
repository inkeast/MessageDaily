## 一、论文背景

### 1.1 从"单兵作战"到"系统智能"

LLM agent 正在经历一次范式转变：从单一模型在单一上下文里完成任务，到被部署为**多智能体系统**——一个主 agent 可以实例化 worker agent、编写协调它们的可执行工作流。Claude Code 的 dynamic workflows、Codex 的并行委派都属此类。这意味着一件根本性的变化：**系统的组织结构不再由开发者在写代码时固定，而是由模型在运行时自己决定**。

论文借用了一个概念叫"系统智能"（system intelligence，引自 Graph Engineering 综述 [4]）：把多个智能组件组织成一个连贯、自适应整体的能力。当任务变长，限制因素从"单个 agent 能做什么"转移到"工作如何被组织"——单一上下文要保留全部工作历史很快成为瓶颈，长程任务由需要不同专长、需要独立验证的相互依赖子任务构成。

### 1.2 什么是"工作流编排"

论文将其形式化为 **workflow orchestration**：一个工作流是关于"任务如何在 agent 之间划分、每个 agent 收到什么上下文、中间结果如何被验证与整合"的**可执行规范**。这些决策发生在任何单个 agent 的控制之外，却塑造整个系统的行为：

- 并行运行独立单元可以缩短关键路径，但增加协调成本；
- 显式验证点可以在错误传播到下游前捕获它；
- 合适的组织方式取决于任务的依赖结构与可用预算。

关键论点：**同样的 agent 集合，组织得好就能成功、组织得差就会失败**——所以编排是系统级能力，而非实现细节。这个前提论文在 §4.5 用实验直接检验。

### 1.3 现有评测为什么不够

三类现有基准各有盲区：

1. **端到端 agent 基准**（SWE-bench、WebArena、OSWorld 等）在真实环境里度量任务完成度，但把 agent 当**黑箱单单元**——工作怎么拆分完全不可见；
2. **多智能体基准**（MultiAgentBench 等）评测预设协调协议下的协作——被评测的结构是**基准设计者选的**，不是模型选的；
3. **工作流基准**（FlowBench、WorFBench、OrchBench）评测生成的计划与结构，但大多**离线或在模拟中**——评的决策从未在真实工件上落地。

没有一类基准观察过"模型自己写、并在 worker 回报真实结果后继续修订"的工作流。这就是 WorkflowArena 要填补的空白，其中心问题一句话：**LLM agent 能在多大程度上自主编排多智能体工作流来完成现实的长程任务？**

### 1.4 类比理解

可以把这件事类比为公司的项目管理：传统基准像只看"项目交付了没"，多智能体基准像"按公司规定流程走一遍看结果"，工作流基准像"审计划书但不开工"。WorkflowArena 做的是：给一个资深经理（主 agent）一笔预算（4 小时墙钟）、一批可雇用的员工（最多 16 个并发 worker，都是经理自己的克隆）、一个真实项目（145 个专业任务之一），然后**既看交付物，也全程记录他怎么招人、怎么分活、怎么验收**——管理费从项目预算里扣。

## 二、论文定位和关联工作

### 2.1 长程 Agent 基准谱系

- **环境扎根系**：AgentBench（异构环境）、WebArena（网站）、OSWorld（操作系统）、AppWorld（应用）、SWE-bench（软件仓库）——把评测从"问答题"推进到"真实环境中的结果验证"。
- **办公/专业任务系**：GAIA、AssistantBench 评工具使用助理；WorkArena/WorkArena++ 研究企业软件与组合式工作流；TheAgentCompany（职场任务）、MLE-bench（机器学习工程）、ScienceAgentBench（科学编程）、τ-bench 家族（策略约束交互）把评测推到长程、相互依赖的步骤。
- **共同局限**：这些基准的任务已经很"长程"，但 agent 始终被当作**单一单元**打分。WorkflowArena 保留其可执行环境与独立验证，但让**工作的组织可见**——每次委派都被记录在交付物旁边。

### 2.2 多智能体系统设计谱系

- **人工框架系**：MetaGPT（角色分工）、ChatDev（对话式开发）、AutoGen（可编程会话）。MAST（Why Do Multi-Agent LLM Systems Fail?）则系统归类了这类系统的失败模式。
- **自动设计系**：ADAS（自动搜索计算图）、AFlow（MCTS 搜索代码化工作流）、AgentSquare（模块化搜索）、MaAS（从学习到的 supernet 采样查询依赖系统）、MAS-Loop（用执行轨迹自我精化）。值得注意 ADAS 与 AFlow 都报告"搜索到的设计可跨模型迁移"——这与 WorkflowArena §4.5 的迁移实验精神呼应。
- **运行时自适应系**：DyLAN（动态选择连接 agent）、Magentic-One（执行中委派与重规划）、DynaFlow（生成可执行工作流程序）。
- **关键区别**：这些方法通过设计流程、固定控制器或训练出的 orchestrator 产生结构，并用下游任务准确率评估。WorkflowArena 反过来把**结构当作被评测模型的输出**，且其迁移实验固定执行器，把工作流的贡献与作者模型的贡献分开度量。

### 2.3 工作流生成与评测谱系

- ReAct/Reflexion（执行-观察-反馈交织）、ReWOO（规划与观察解耦）、LLMCompiler（并行函数调度）奠定执行范式；
- FlowBench（带供给工作流知识的规划）、WorFBench（生成序列/图结构 + 下游实用性）、OrchBench（确定性模拟隔离评测编排计划质量）把"结构质量"与"实现效用"分开——但结构大多离线或在模拟中评；
- SWE-agent 与 Agentless 表明接口设计与简单执行管线本身就能实质影响任务表现——这为"模型要连同 harness 一起评"提供动机。

### 2.4 定位总结

| 维度 | 端到端基准 | 多智能体基准 | 工作流基准 | **WorkflowArena** |
|---|---|---|---|---|
| 环境真实 | ✅ | 部分 | ❌（离线/模拟） | ✅（真实专业工件） |
| 结构由谁定 | 开发者 | 基准设计者 | 模型生成 | **模型运行时自主决定** |
| 组织可见性 | 不可见 | 可见但预设 | 可见但不执行 | **可见且真实执行** |
| 组织成本入账 | 不适用 | 通常不记 | 不适用 | **与工作共享 4h 预算** |
| 编排/执行分离 | ❌ | ❌ | 部分 | ✅（固定执行器迁移实验） |

定位结论：WorkflowArena 是第一个把"模型自主编排可执行工作流"作为独立评测对象、并用迁移实验把编排质量从单体能力中剥离出来的基准。

## 三、问题定义

### 3.1 从具体场景到抽象问题

**具体问题**：怎么知道一个 agent 系统会不会"组织工作"？直接看任务完成率不行——强的模型不组织也能做完，弱的模型组织了也做不完，完成率混杂了编排与执行两种能力。

**核心洞察**：任务完成是"执行能力 × 组织方式"的联合产物。要单独度量组织能力，需要两个条件：(a) 任务必须"组织敏感"——有足够多可分离又相互依赖的工作单元，拆分与整合的决策会改变结果；(b) 必须能**固定一个因子、扰动另一个因子**——这就是迁移实验的设计原理，固定执行器、只换工作流作者。

**形式化**：一个任务 τ = (s₀, g, U, E, B, V)：初始环境状态 s₀、目标 g、公开动作/工具面 U、任务工件与执行环境 E、资源预算 B、独立验证器 V。agent 只见公开部分，从不见验证器、金标或隐藏测试。执行中 agent 做出组织决策（经工具调用与工作区更新记录在执行历史 h_T 中），预算内到达终态 s_T，验证器给出：

r = V(s_T, h_T) ∈ [0, 1]

**关键设计**：奖励只依赖任务结果与过程约束，**不依赖 worker 数量或工作流形状**——单 agent 顺序执行也是合法工作流。基准奖励"适合任务的组织"而非预设"多 agent/并行更好"，把选择权完全留给模型。

### 3.2 这个抽象的精妙之处

1. **去偏**：不奖励委派本身，避免基准把模型推向"为委派而委派"；
2. **可观测**：每个委派经过被记录的接口（原生 sub-agent 机制被禁用），组织过程成为可分析的数据而非黑箱；
3. **成本对称**：组织时间与工作共享同一墙钟预算——管理是有价格的，防止"无限协调"的免费午餐；
4. **因子分离**：V(s_T, h_T) 只看结果与过程，配合固定执行器，工作流本身成为可迁移、可度量的资产。

类比：这就像把"公司绩效 = 员工能力 × 管理水平"中的管理水平单独拎出来评——方法是雇同一批员工（固定执行器），换不同经理（工作流作者）写工作手册，看业绩变化。

## 四、问题解法

### 4.1 基准构造：让"组织"变得有后果

五项设计要求（对应五节论证）：**组织有后果**（consequential）、**自主**（autonomous，规定角色/流程就变成考合规而非考选择）、**整合敏感**（integration-sensitive，各自正确但未协调的组件不得满分）、**组织成本入账**（accounted）、**组织可观测**（observable）。

任务构造流水线四步（Figure 2）：

1. **真实来源**：开源仓库 PR 与 release tag、Lean blueprints 与 mathlib4、科学挑战与论文、SEC 10-Q 财报、MAUD 并购协议与判决、开放电影与公共报告、支出数据、自 authored 图纸与场景——每个来源记录 source/revision/license/hash；
2. **适宜性筛选**：可分解但有耦合——实质工作单元（推理或实现工作）+ 跨单元依赖（共享接口与约束）+ 非平凡整合（结果须调和成一个交付物）；
3. **任务构造**：只定目标不定工作流。重建型任务"移除目标工作"（如删掉 repo 里的 feature、把证明换成 placeholder、把 iXBRL 换成无标签 HTML、判决换成纯事实），公开工作区保留任务上下文但排除隐藏答案与检查；专家从清晰度、工作量、整合性三方面复审；
4. **验证与发布**：验证器对照参考解（期望满分）与应失败提交测试——**空输出得零分、"组件正确但无整合"不能全过、经无效过程到达正确终态被拒**，这三个对照组保住了整合敏感与过程约束的有效性。

**整合敏感的典型设计**：合同组合任务里每份协议可逐条分析，但交付物还要求跨合同的关系与冲突，分开生产的分析必须调和成一致报告；多实体合并报表中每个实体的调整会经公司间余额传播进合并账本；形式化证明里后继结果依赖前序；3D 场景里分开建的组件必须在共享空间接口处相遇。OPS 类任务还额外评动作历史——因为正确终态可能经无效过程到达。

### 4.2 任务目录：145 个任务，8 领域 17 形式

| 领域 | 任务数 | 形式（数量） | 来源举例 | 接受证据 |
|---|---|---|---|---|
| SWE 软件 | 17 | feature 实现(11)、子系统重建(6) | 开源 repo PR/修订 | 隐藏 feature+回归测试 |
| OPS 运营 | 18 | 策略约束流程执行(6)、跨系统业务编排(6)、多方信息协调(6) | 公共支出记录+authored 策略 | 结果+动作历史+约束 |
| SCI 科学 | 16 | 盲预测建模(8)、已发表结果复现(8) | CAPRI/CASP/DREAM/SAMPL 挑战 | 官方指标、数值容差 |

### 4.3 评测协议：组织有价格，委派有记录

- **预算**：4 小时（14,400 秒）墙钟，主 agent 与全部 worker 共享；环境准备与评分不计入。Docker 容器隔离，worker 并发上限 16，broker 另限上游并发、240 秒排队超时。
- **Agent 接口**：完整工作区访问（shell、测试、直接编辑文件）+ **Workflow 工具**（启动后台工作流、检查、停止、修订）。Workflow 程序是 JavaScript，组合 agent/parallel/pipeline 原语与普通控制流，两个 harness 收到同一接口。另有 WorkflowList/Output/Stop/Control 四个管理接口。
- **Worker 即克隆**：每个 worker 是 agent 自身的新鲜实例——同模型、同 harness、同 effort。worker 从全新上下文出发、只共享工作区，所以主 agent 必须**决定每个 worker 需要知道什么**——上下文分配本身成为被评测行为。原生 sub-agent 机制禁用，一切委派走被记录的 Workflow 接口；使用工具完全可选。
- **打分**：连续分 S_t = 100·r_t ∈ [0,100]；Overall Score 是 8 领域等权均值；任务"resolved"当提交满足该领域全部接受标准（Appendix F，如 SWE 需构建通过+全部测试通过+覆盖率验证+无测试完整性违规；LAW 合同分析需条款抽取 ≥90% 且聚合问答精确正确 ≥75%），Overall Resolved（8 领域 resolved 率等权均值）为主指标。agent 报错、缺交付物、预算耗尽不作特判，统一按任务规则打分。
- **评分器**：内容与 3D 工件由 Gemini-3.8-Flash 按任务 rubric 评，其余领域用程序化验证器。
- **资源核算**：token 分四类归一（未缓存输入 I、缓存读 R、缓存写 W、输出 O），成本按 2026-11-09 价格快照与式 C = 10⁻⁶(p_I·I + p_R·R + p_W·W + p_O·O) 估算（如 Opus：输入 $4/输出 $20 每百万 token；Luna 便宜两个数量级）。

### 4.4 实验设计全景

25 个配置 = 9 模型：Opus/Sonnet（Claude Code）与 Astra/Sol（Codex）各扫 low→max 五档 effort，Luna（Codex@max）、Kimi/GLM/DeepSeek（Claude Code@max）、Doubao（Claude Code@high）。每个配置跑全部 145 任务。分析分四层：任务表现（§4.2）、资源使用（§4.3）、委派模式（§4.4）、**固定执行器迁移**（§4.5）+ 3D 案例研究（§4.6）。

2. **没有全能冠军**：Opus@max 领跑 SWE/SCI/MATH，Sonnet@max 领跑 LAW/CDN 并列 3D 第一，OPS 由 Astra@high 与 Doubao 以 27.78% 领跑；
3. **MATH 分层最尖锐**：最强配置解决 >90%，Kimi 37.50%、Luna 25.00%，Doubao/GLM/DeepSeek 全军覆没——形式化数学最能区分模型档次。

**Effort 弹性家族差异**：Claude 系对 effort 高度敏感（Opus 22.02%→36.95%，Sonnet 16.88%→33.21%），GPT 系迟钝得多（Astra 27.34%→30.80%，Sol 25.63%→29.50%，且 Sol@low 反而高于 medium/high）。且更高 effort 并非普遍有益。

### 5.2 资源前沿：token 与成本两本账

- **Token 前沿全是 Opus**：Opus@high 以 **7.36M tokens/任务** 换 34.11%，该分辨率在任何 token 预算下无其他模型能达。Sonnet@max 用 3.2× 于 high 的 token 换 7.95 分 resolved 提升；Sol@xhigh 用 1.9× token 只换 1.91 分。
- **价格重排资源榜**：因单 token 价格相差超一个数量级，成本前沿混合得多——从 Luna 一路经低 effort Sonnet、多个 Sol 配置到 Opus。**成本前沿：Sol@low 27.59% @ $3.61/任务**，Opus@high 34.11% @$6.66；而 Astra@xhigh 30.80% 要 $29.26——比 Opus@high 贵 4.4 倍还低 3.31 分。
- **连续分视角补充**：Overall Score 上 Opus@high 最高（80.21，SWE 连续分 96.98 但 resolved 仅 17.65%）。两指标 Spearman 相关 0.90，但域内差异巨大——SWE 连续分比 resolved 高 66.16、LAW 高 67.76，说明这些领域普遍"拿大量部分分但过不了验收线"；MATH 只差 11.23（验收≈打分规则本身）。附加 token 更多贡献于"把任务做完"而非"部分推进"（Sonnet max vs high：resolved +7.95 但连续分仅 +2.96）。

### 5.3 委派模式：两个流派

两个刻画量：**Workflow calls/task**（含无调用任务的均值）与 **worker invocations/Workflow**（以已启动 Workflow 为分母）。

**high effort 下（Figure 5）**：

| 系统 | Workflow 次数/任务 | worker/次 |
|---|---|---|
| Opus (Claude Code) | 0.86 | 5.55 |
| Sonnet (Claude Code) | 0.76 | 6.14 |
| Astra (Codex) | **2.09** | **1.72** |
| Sol (Codex) | **1.94** | **1.69** |

Claude 系"**少次大批**"：有委派的任务里单次调用占 Opus 70%/Sonnet 68%，而非空 Workflow 中 9+ worker 占 Opus 24%/Sonnet 30%；Codex 系"**多次小批**"：约 99% 的 Workflow 至多 4 个 worker，单次调用占比仅约 32%。

**Effort 的影响也分流派**：Codex 系随 effort 升调用频率大增（Astra low→max 调用 +67%，worker 组大小基本不变 ±5%；Sol +79%/±12%）；Claude 系反而在 xhigh 达调用峰值，Sonnet 从 xhigh 2.33 次×4.15 worker 到 max 变为 1.57 次×~4.35 worker。

**领域塑造委派**：LAW 中 Opus/Sonnet 平均 14.29/8.45 worker/次，Astra/Sol 仅 1.73/1.66（调用频率反序）；Kimi/Luna 在 MATH 高频小额委派（9.67/6.46 次×1.74/1.26 worker）但 Kimi 的组在 LAW/FIN 涨到 5.84/5.08；OPS 所有模型委派都小（0.17–1.72 次×1.00–2.00 worker）。**结论：单看调用频率不能刻画协作规模。**

### 5.4 核心实验：固定执行器迁移（Table 2）

32 个难任务子集（覆盖 8 域、选更难者）。Opus 与 Astra（均 max effort）当工作流作者；Kimi、DeepSeek、Luna、Doubao 当执行模型——**每个 worker 都是执行模型的实例，源模型两模式下都不许碰工作区**。static 模式：源模型读题写完 Workflow 程序即停，冻结程序在新工作区跑（内部分支/循环/并行照常执行）；dynamic 模式：源模型启动 Workflow、观察 worker 结果、持续修订。工作流生成计时入预算。因 32 任务 resolved 率步长太粗，报连续分。

| 执行模型 | Self(dynamic) | Astra static | Astra dynamic | **Opus static** | **Opus dynamic** |
|---|---|---|---|---|---|
| Kimi K3.1 Pro | 35.75 | 29.69 | 33.80 | 45.04 | **46.61** |
| GPT-6 Luna | 25.08 | 24.87 | 29.22 | **30.37** | 25.35 |
| Doubao | 20.39 | 22.07 | 24.25 | **28.04** | 27.46 |
| DeepSeek | 18.37 | 12.85 | 17.69 | 21.79 | **25.24** |
| **均值变化** | — | **−2.53** | +1.34 | **+6.41** | **+6.27** |

**两组对照读数**：

1. **Opus 工作流全面提升**：四执行器平均 static +6.41 / dynamic +6.27；Kimi 从 35.75 → 46.61（**+10.86**），DeepSeek 18.37 → 25.24（**+6.87**），Luna/Doubao 最高分都出自 Opus static（30.37/28.04）。由于源模型从不编辑工作区，增益全部来自其撰写的工作流——包括给每个 worker 的指令。
2. **Astra 工作流大多帮倒忙**：static 均值 **−2.53**，dynamic +1.34；两种模式下都拉低 Kimi 与 DeepSeek。而 Astra 本身（max 27.34% resolved）远强于四个执行器（最高 16.48%）——**单体强不等于会指挥别人**，编排能力不是任务完成能力的副产品。

（论文 Limitations 诚实指出：源模型也写 worker 指令，增益可能混合了更好的组织与注入指令中的任务知识；且迁移实验只用子集与两个源模型。）

### 5.5 案例研究：3D 场景构建的组织学

三个 3D 任务对比 Opus 与 Astra 的组织形态：宫殿任务两者都分布构建（Opus 7 个 builder + 组装 + 迭代修复；Astra 先建共享地基再单 worker 组装）；教堂任务 Opus 做两次顺序全场景尝试，Astra 把场景分给 3 个区域 builder + 独立组装 worker（在共享结构位置引入接口）；堡垒任务两者都用单一全场景 builder，但 Opus 先做 7 次图纸分析再施工，Astra 边施工边并行审图。委派由此显出两种用途——**并行构建组件** 与 **为中心 builder 准备输入**，整合与修复进入工作流的阶段也不同。

## 六、效果优势的根源解释

本文的"效果"核心是迁移实验的结论：为什么 Opus 写的工作流能普遍提升弱执行器，而单体更强的 Astra 写的不行？

### 6.1 根源机制与证据链

**因果链 1：上下文分配质量是工作流迁移的核心载体。**
worker 从全新上下文出发、只共享工作区，所以工作流作者必须为每个 worker 显式打包必要上下文（任务约束、接口约定、领域惯例）。Opus 的高分工作流意味着它写的 worker 指令让弱模型"在正确的子问题里做正确的事"——相当于把一个模糊大任务翻译成一组边界清晰的小任务。链条：作者的任务分解 → worker 收到的约束上下文 → 弱执行器被"锚定"在正确子问题 → 错误传播减少 → 联合交付物分数上升。【论文实验已支持的部分：迁移增益存在且源模型未接触工作区；"约束上下文锚定弱模型"的微观机制是阅读者推测，论文未逐 worker 分析指令质量】

**因果链 2：验证与整合结构弥补弱执行器的自检缺失。**
弱模型的典型失败是"部分正确但未调和"（§5.2 显示 SWE/LAW 连续分与 resolved 差 66+ 分，说明普遍卡在验收线）。好的工作流把验证点与整合步骤显式编入程序（如 Opus 宫殿案例的"组装+迭代修复"阶段），相当于把"检查作业"从执行器能力中剥离、写进流程。链条：工作流内建验证/修复阶段 → 组件错误在传播前被捕获 → 弱执行器的输出被流程性补救 → resolved 边缘任务跨过验收线。【论文已支持：3D 案例中可见组装/检查/修复阶段；跨领域普遍增益与该机制一致但论文未做消融——推测成分中等】

**因果链 3：编排能力与单体能力部分解耦。**
Astra 单体远强于执行器（27.34% vs ≤16.48%），其工作流却平均 −2.53 分，说明存在一种不同于"自己会做"的能力——估计子任务难度与依赖、判断 worker 需要知道什么、决定何时整合。这更像管理者素质而非工程师素质，训练分布（各自 harness 的委派交互模式）塑造了不同流派：Claude 系少次大批（默认任务可并行分解、值得一次性铺开），Codex 系多次小批（默认小步快查）。Astra 的小批工作流在弱执行器上可能"切得太碎"，上下文重复打包与整合开销吞掉收益。【"切得太碎"是推测；论文证据是 99% Astra/Sol Workflow ≤4 worker + 迁移负增益的相关性】

**因果链 4：组织成本入账使"过度协调"受罚。**
4 小时共享墙钟下，每次协调消耗与工作同一资源。Opus 的低频大批策略减少协调轮次、缩短关键路径；Astra 高频小批把预算花在反复启动上。Kimi 在 MATH 的 9.67 次×1.26 worker 就是高频小额委派仍可低效的例证。【部分支持：论文展示频率/规模分布与预算协议；"预算惩罚导致差异"未直接测量——推测】

### 6.3 综合判断与未决问题

**多研究共同支持**：工作流结构携带独立于执行器的可迁移价值（AFlow/ADAS 的离线证据 + 本文的运行时证据三方汇聚）；编排能力与单体能力可分离（本文迁移实验 + MAST 失败模式分析间接支持）。

**仍属推测**：Opus 工作流增益的具体微观机制（上下文打包质量 vs 验证结构 vs 任务知识注入，论文自己承认无法区分）；"Claude 大批 vs Codex 小批"孰优——系统级结果 Opus 领先但不能归因于委派风格单独一个变量（模型与 harness 捆绑评测，论文 Limitations 明确承认非 GPT 模型在 Claude Code 只提供部分分离依据）。

**适用条件与可能失效**：迁移增益在"挑战性子集 + 4 个弱执行器 + 2 个源"范围内成立；换成强执行器（差距缩小）或超长任务（4h 预算不够组织）可能失效；static 与 dynamic 差异小（6.41 vs 6.27）提示修订闭环的价值依赖任务可观察性，这些边界均待更多源模型与执行器组合检验。

## 七、必要知识反推

假设一个没有任何背景的人要做这个工作，他最少需要知道什么？

### 7.1 领域知识层

- **Agent harness 生态**：Claude Code 的 dynamic workflows 与 Codex 的委派机制各是什么、为何"原生 sub-agent 可禁用、委派可经统一接口代理"——不知道这些就无法设计"所有委派可记录"的协议；
- **八领域的专业工作形态**：Lean/mathlib4 的证明依赖结构、并购合同组合分析要调和什么、多实体合并报表的调整传播、SEC 10-Q 的 iXBRL 标签、Blender 场景的空间接口——不知道"专家怎么把这些活拆开又合上"就造不出"组织敏感"的任务；
- **公司项目管理的通用经验**：委派、验证点、关键路径、协调成本——论文的组织语言几乎全部借自管理学，这是把"多 agent"从算法问题翻译成"组织问题"的概念底座。

### 7.2 方法论知识层

- **基准设计方法论**：结果验证 vs 过程验证、防 benchmark 污染（隐藏验证器/金标）、防"部分分通胀"（resolved 与连续分双轨制）、验证器的对照测试（参考解应满分、应失败提交应失败）——尤其是"组件正确但无整合不能过"这一对照组，是 integration-sensitive 的操作性落地；
- **评测中的因子分离思想**：系统级结果 = 编排 × 执行，迁移实验是经典的"固定一个因子扰动另一个"的实验设计迁移到 agent 评测；
- **Pareto 前沿分析**：性能-token/成本二维的非支配集分析，需要懂为何 token 前沿（纯量）与成本前沿（加权价）会重排配置。

### 7.3 工程知识层

- **大规模评测基础设施**：Docker 容器资源管理（CPU/内存 admission control）、单调时钟的墙钟预算执行、API broker（并发限制、队列超时、指数退避、防嵌套重试）、token 四类归一化（Responses 式与 Messages 式计费口径不同）与跨厂商成本估算、SHA-256 归档保证 trial 可复现——145 任务×25 配置×4 小时的实验没有这些工程保障根本跑不下来；
- **MCP 工具接口设计**：Workflow 及四个管理接口的 JSON schema 经 MCP 供给两个 harness，保证"同一接口跨 harness"的公平性。

### 7.4 知识融合的关键节点

1. **洞察节点**：把"多 agent 系统的结构"从设计对象重定义为**评测对象**——这是管理学直觉（组织影响产出）与 agent 工程（harness 可代理委派）的融合点；
2. **设计节点**：任务必须"可分解但耦合"——来自对专业工作（合同分析、合并报表、形式化证明）依赖结构的领域理解与"组织敏感"评测需求的对接；
3. **实验节点**：迁移实验 = 经典实验设计（因子分离）× 多 agent 工程（worker 可实例化为任意模型）× 预算协议（源模型不碰工作区，增益只能来自工作流）；
4. **度量节点**：双指标体系（resolved 抓"完整交付"、连续分抓"部分推进"）× 资源双账（token/成本）——四者交叉才得出"追加 token 更贡献于完成而非部分推进"这类精细结论。

## 八、论文中可以提取的通用性灵感

### 灵感 1：把"组织结构"从实现细节升格为评测对象

**核心思想**：任何系统中"结构由谁决定"本身就是一种能力/属性，可以被独立度量与比较。
**论文证据**：同样 145 任务，工作流作者的差异（Opus vs Astra）使固定执行器集合的平均分摆动 ±6 分以上（+6.41 vs −2.53）。
**推广场景**：(1) 评测 RAG 系统的检索策略选择能力而非固定 pipeline；(2) 评测代码生成器的架构决策（模块划分）而非仅最终正确性；(3) 组织管理中评估经理的"任务分解质量"；(4) 评测编译器的自动调度策略。

### 灵感 2：因子分离实验——固定执行、扰动编排

**核心思想**：要度量一项"meta 能力"，把它产出的产物（工作流/计划/手册）迁移到不同的执行者上，看增益是否保持。
**论文证据**：static 模式冻结 Opus 工作流给 4 个弱模型，平均 +6.41；Astra 工作流 −2.53，证明增益源于产物而非源模型亲自动手。
**推广场景**(1) 教学法评估：好教案换普通老师仍有效吗；(2) prompt 评估：跨模型迁移测 prompt 的"结构性价值"；(3) 管理：标准化流程手册对新人团队的外溢价值；(4) 编译优化：IR pass 序列跨后端迁移。

### 灵感 3：让协调付出与工作同价的机会成本设计

**核心思想**：评测（或激励）系统时，把"组织行为"的成本记入与"实际工作"同一预算，防止免费协调带来的过度工程。
**论文证据**：4 小时共享墙钟下，高频小批委派（Astra 2.09 次/任务）与低频大批（Opus 0.86 次×5.55 worker）的资源画像完全不同；OPS 域所有模型都只做小额委派——任务结构让协调不再划算。
**推广场景**：(1) 会议制度设计：开会时间计入项目工期；(2) 搜索算法：协调开销与探索收益同价（如多臂老虎机的臂启动成本）；(3) 分布式系统：一致性协议的协调成本入账；(4) API 产品定价：编排层调用与执行层调用同价。

### 灵感 4：双指标制区分"部分推进"与"完整交付"

**核心思想**：只看连续分会奖励"广撒部分分"，只看验收率会丢失梯度信息；两者结合能分辨"稳定做完小事"与"常常做完大事"两类系统。
**论文证据**：SWE 连续分与 resolved 差 66.16 分、LAW 差 67.76——系统普遍拿大量部分分但过不了验收线；Sonnet@max 按 Overall Score 排 15、按 Overall Resolved 排 4，两指标重排系统。
**推广场景**：(1) 学生评价：平时分 vs 结业考核双轨；(2) 软件交付：测试覆盖率 vs 全功能验收；(3) 销售：线索转化漏斗 vs 成单；(4) 医疗：指标改善 vs 治愈标准。

### 灵感 5：强单体 ≠ 好老师/好指挥

**核心思想**：完成任务的能力与组织他人完成任务的能力是两种能力，不能从前者推断后者，需分别评测与培养。
**论文证据**：Astra 单体 27.34% resolved 远超四执行器（≤16.48%），其工作流却平均降低执行器分数（static −2.53）。
**推广场景**：(1) 人才晋升：顶级工程师 ≠ 合格技术管理；(2) 模型蒸馏：强模型生成的课程/分解未必适合弱模型学习；(3) 求职培训：行业专家写教材未必适合新手；(4) LLM API 选型：贵而强的模型未必是当 orchestrator 的最优选——便宜模型配好工作流（Sol@low $3.61/任务 27.59%）可能更划算。

### 灵感 6：可观测性要靠"强制单一接口"而非事后日志清洗

**核心思想**：想观察/治理某类行为，最可靠的方式是让该行为只能经一条可记录的通道发生。
**论文证据**：禁用两个 harness 的原生 sub-agent 机制，所有委派必经 Workflow 工具——组织行为因此完整可分析（委派频率、规模、修订模式）。
**推广场景**：(1) 金融合规：所有交易经统一清算通道；(2) 微服务治理：服务间调用经 service mesh；(3) 网络安全：出站流量经代理；(4) 团队管理：跨部门协作经统一工单系统。

## 附录：读者可能想追问的几个点

- **数据/代码开放吗？** 论文给出主页 lab.einsia.ai/workflowarena；任务包遵循 Harbor 执行接口（instruction.md + environment/ + tests/ + 元数据），未在正文看到完整开源仓库链接。
- **LLM 评分可靠吗？** 内容与 3D 领域用 Gemini-3.8-Flash 评 rubric，论文在 Limitations 承认未测量与人类评分者的一致率——这是当前所有 LLM-judge 基准的共同软肋。
- **单次评测无方差？** 每配置每任务只跑一次，作者明确指出相近配置的差异报告不含方差估计——解读 Table 1 中 1 分以内的差距时应保持克制。
- **下一步？** 论文展望：编排者与 worker 异构的系统研究、自适应预算、交互式任务执行。结合迁移实验，"编排模型 × 执行模型"的组合优化（哪个模型适合当 orchestrator）是一个立即可做的方向。
