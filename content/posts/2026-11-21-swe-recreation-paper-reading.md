## 一、论文背景

### 1.1 智能体已经会"用软件"和"写软件"了，但它们总是被"告知要做什么"

过去三年，语言模型智能体在两个方向上突飞猛进：

- **用软件的智能体（computer-use / web agent）**：给定一个目标（比如"在购物网站找出最便宜的马克杯并下单"），智能体在真实浏览器或操作系统里一步步点击、输入、完成操作。代表基准有 WebArena（812 个网页长程任务）、OSWorld（369 个真实桌面任务）、AndroidWorld（移动端）等。
- **写软件的智能体（coding agent）**：给定一份明确的规格——一张截图、一份设计稿、一个 issue 描述——智能体产出代码。代表基准有 SWE-bench（真实 GitHub issue 修复，2,294 个任务）、Design2Code（484 个真实网页截图转 HTML/CSS）等。

但论文开篇就点破了一个安静的共性假设：**这两类智能体都被告知了要达成什么**——要么有明确目标，要么有现成的 mock-up（设计样稿）或演示。SWE-bench 给你 issue 文本；Design2Code 给你截图；WebArena 给你任务指令。规格说明书（specification）总是有人提前替智能体写好了。

### 1.2 人类开发者的真实处境：没有说明书的陌生产品

现实中的人类开发者经常面对更难的处境：接手一个没有任何文档的陌生产品，没有手册、没有需求文档。人的解决办法是——**反复使用这个产品，直到理解它为什么这样工作，然后自己动手重建它**。逆向工程、竞品分析、遗留系统迁移，都是这个模式。

一个智能体能不能做到同样的事？这个问题在本文之前**基本没有被测试过**。这就是 SWE-Recreation 的出发点：不给目标、不给截图样稿、不给演示视频，只给一个正在运行的陌生应用，看智能体能不能像人一样"用明白它，然后做出来"。

### 1.3 用一个类比理解"主动黑盒重建"

论文定义的任务叫**主动黑盒应用重建（active black-box application reconstruction）**。可以用一个画画类比来理解：

> 想象你被带进美术馆，面对一幅只许**观看和临摹**的画：你可以反复看、凑近看、甚至上手触碰画布看颜料如何反应，但你**不许揭开画布看底稿**（源码）、不许问画家用了什么配方（DOM/网络请求/日志）、也不许拆画框（后端）。看完之后，你要闭卷重画一幅"功能等价"的画——评委不会拿放大镜对比笔触是否一致（布局、样式、措辞都不算分），而是当场出题：『把这幅画的遮罩层掀开，下面应该露出什么？』答对了才算数。

三个关键约束让这个任务成为"对自主性的真实测试"：

1. **纯像素接口**：智能体每一步只能看到渲染后的截图和光标位置，只能通过坐标级鼠标/键盘/触摸操作。没有 DOM、无障碍树、源码、网络流量、存储、URL、选择器。像素和指针输入是**所有**网站和应用都暴露的唯一通用接口——凡是一个人能用的地方，这种智能体理论上都能用。
2. **完全自主**：没有任务清单、没有演示、没有探索计划、没有规定的笔记格式。"看什么、什么时候算看够了"，全由智能体自己决定。
3. **行为等价评分**：复刻品只按可观察行为评分，静态"看上去像"的 mock-up 骗不过评委。

### 1.4 为什么现有评测体系测不出这种能力

从评测指标角度看，现有基准还有一个盲区：它们只看**最终产物**的分数，不区分失败发生在哪个环节。一个智能体复刻失败，可能是因为（a）它压根没发现那个功能，（b）它看到了但理解错了，（c）它理解了但写不出来。这三种失败对应完全不同的能力短板，而一个总分无法区分它们。论文的指标设计（第五部分）正是冲着这个盲区去的。

## 二、论文定位和关联工作

### 2.1 研究谱系一：用软件的智能体

WebVoyager、Mind2Web、WebArena、VisualWebArena、OSWorld（及其 2.0 版）、AndroidWorld、GAIA、UI-TARS、OS-Atlas 等工作，让智能体在真实界面里执行指令，感知侧配套发展了 Pix2Struct、屏幕解析、网页 grounding、原生 GUI 动作模型，组织形态多围绕 ReAct 式"推理-行动"循环。**共同点：目标被给定，界面已存在，智能体只需执行，从不需要"恢复再重现界面背后的规格"。**

### 2.2 研究谱系二：写软件的智能体

pix2code（2017）开创截图转代码；Design2Code（484 真实网页）与 WebSight、Web2Code、ScreenCoder、DesignBench 等构成 UI-to-code 谱系；WebGen-Bench、AppForge 等从自然语言需求或产品简报生成应用；SWE-bench 系（含 Multimodal）、OpenHands 等在既有仓库里修 issue。**共同点：目标以截图、原型、需求文档或 issue 的形式被供给，挑战在于忠实实现一份已知规格。**

### 2.3 研究谱系三：从观察重建（与本文最近的邻域）

这是离本文最近的一族，论文逐一指出它们各自"差一步"：

- **Interaction2Code / InterWebCoder**：以标注的状态转移为条件——观察已被别人选好。
- **IWR-Bench（上海 AI Lab 等，ICLR 2026）**：给一段录制好的用户交互视频 + 全部静态资源，让模型复现交互网页；最佳模型 GPT-5 总分仅 36.35，交互功能分（IFS）24.39 远低于视觉保真分（VFS）64.25。**但视频是别人录的——"看什么"不由模型决定。**
- **Video2Code / WebVR**：同样沿固定轨迹或视觉 rubric 评分。
- **RecreationWorld（阿里 Token Hub，同期工作，arXiv 2609.22000）**：最接近的同期工作——让智能体自主探测运行中的参考应用。但它给智能体**代码级和工具级访问**（可以读内部机制），等于"读机器而不是读屏幕"；其 RecreationBench 上 GPT-6-Astra 总分 58.1%，但通过全部程序化测试的任务仅 2.8%。

### 2.4 评分方法谱系

论文的评审设计建立在 LLM-as-a-judge（Zheng 等，MT-Bench/Chatbot Arena）与 agent-as-a-judge（Zhuge 等；Mind2Web 2 的 agentic search 评审）之上，但强调单一固定模型 + 统一配置 + 每个评分必须引用像素证据。

### 2.5 定位对比表

| 维度 | SWE-bench 类 | Design2Code 类 | IWR-Bench 类 | RecreationWorld | **SWE-Recreation（本文）** |
|---|---|---|---|---|---|
| 规格来源 | issue 文本 | 截图 | 录制视频 + 资源 | 运行中的应用 | **运行中的应用** |
| 观察通道 | 仓库代码 | 静态截图 | 他人选好的视频帧 | 代码/工具级访问 | **仅像素** |
| 探索被测试？ | 否 | 否 | 否 | 部分（有代码捷径） | **是（核心被测项）** |
| 结构化访问 | 有（文件系统） | 无需 | 无需 | 有（DOM/源码级） | **无（运行时强制隔离）** |
| 评分方式 | 跑测试 | 视觉相似度 | 固定轨迹 + agent 评审 | 程序化/视觉断言 | **自适应 judge + 像素证据** |
| 失败定位能力 | 只知过/不过 | 只知像/不像 | 只知跟没跟上 | 部分 | **ECov/D2I 拆解探索与实现** |

**定位结论**：SWE-Recreation 是第一条"纯像素、无脚手架、探索与实现分别计量"的软件重建评测路线。它把"智能体能否像人一样理解软件"这个问题第一次变成了可测量的基准。

## 三、问题定义

### 3.1 从具体场景到抽象问题

- **具体场景**：智能体面对一个从未见过的运行中应用，要造出功能等价的复刻品。
- **难点**：什么算"理解了一个应用"？无法直接定义——但可以行为式地定义：**能支撑其全部隐藏工作流的应用就是被理解了的应用**。
- **抽象问题**：在纯像素黑盒接口下，把"探索发现规格"与"实现规格"绑在一条自主决策链上，同时测试两者。

### 3.2 形式化定义

记源应用为 A*，隐藏工作流集合 W = {w1, …, wN}（对智能体不可见）。一次运行包含四段：

1. **探索**：通过人类式接口操作 A*；
2. **生成**：产出可运行的复刻品 Â；
3. **自检**：智能体自己先检查 Â；
4. **评估**：评审对照 W 给 Â 打分。

**人类式接口的精确定义**：每步观测 = 渲染截图 + 光标位置；动作 = 坐标级 click/drag/scroll/type（web）或 tap/swipe/type/back（移动端）。动作回执只报告动作是否被接受，**绝不报告命中了什么元素**。这条边界由运行时（而非指令）强制执行——智能体想作弊也没有通道。

**输出与范围**：复刻品只能基于观察到的内容 + 公开虚构素材构建；只按可观察行为评分；布局、措辞、样式、技术栈一律不计分——行为等价的复刻品通过，静态 mock-up 不通过。多用户协作、支付、实时数据、生成式功能、外部集成等单机无法忠实复现或验证的行为构成**排除集 X**，既不要求也不计分。

**自主性**：探索完全开放式，只有宽裕到几乎不构成约束的动作/时间上限。

### 3.3 这个抽象的精妙之处

| 设计 | 排除的干扰 | 抓住的本质 |
|---|---|---|
| 纯像素接口 | 结构化捷径（DOM/源码）带来的"读机器" | 类人感知与 grounding |
| 隐藏 W | 人类作者替智能体选好观察对象 | 自主探索规划 |
| 行为等价评分 | 像素级抄袭也能得分的假象 | 功能理解 |
| 排除集 X | 单机原理上不可复现的任务拖累公平性 | 评测边界的显式化 |
| 运行时强制 | 靠提示词"恳请"模型别作弊 | 约束的可信性 |

失败因此在结构上有**三个不同的入口**：从未发现某能力、误读了观察到的东西、理解了却无法实现。这一区分是后续全部指标设计（ECov/D2I）的种子。

## 四、问题解法

### 4.1 基准构造：54 个真实应用与 1,446 条隐藏需求

**目标选择**。54 个真实应用：28 个活跃网站（知乎、Reddit、YouTube、Notion、Trello、Google Calendar、Excalidraw、diagrams.net、Desmos、Google Maps、Spotify 等）+ 26 个 Android 应用（Joplin、VLC、AnkiDroid、Minesweeper 等），分六类。选择标准是**富含有状态、长程行为**（筛选过滤、编辑持久对象、跨视图保持记录一致），而非静态展示。

**清单构建（人机协同流水线）**：

1. 标注员手工操作应用，录 20–40 张覆盖主要功能与状态转移的截图；
2. 视觉语言模型（gpt-6-astra）根据轨迹**起草**清单；
3. 第二位标注员对照真实应用逐条核验，删除模糊或不可测项。

每条需求包含：有序步骤序列 + 用自然语言（而非机械断言）写成的预期结果 + 持久化/多用户标志。web 目标另有标注员撰写的**排除清单**（每条记录被排除界面、处理方式与理由），探索与评估共享同一边界文件。

**统计口径**：

| 统计项 | Web | Mobile |
|---|---|---|
| 应用数 | 28 | 26 |
| 需求总数 | 848 | 598 |
| 每应用均值 | 30.3 | 23.0 |
| 每应用范围 | 12–57 | 13–77 |
| 持久化需求 | 143（16.9%） | 135（22.6%） |
| 排除条目 | 438（213 硬排除 + 113 默认 + 96 条件排除 + 16 条件包含） | ——（离线单用户，无需排除） |

**环境**。移动端跑在容器化 Android 系统（应用预装）；web 跑在锁定浏览器。两端都由 **MCP 服务器作为唯一桥梁**，只暴露原语工具（截图、点击/轻触、滑动/滚动、输入），隐藏一切设备级机制。生成阶段给固定脚手架 + 虚构素材包（公共素材 + 每目标虚构内容），不需要真实用户数据；web 端不规定技术栈，移动端面向固定原生栈产出可安装应用。

### 4.2 评估协议：自适应评审 + 像素证据

评审（judge）通过同样的纯像素接口在复刻品上执行每条隐藏工作流，并与参考实例对照。关键设计：

- **自适应功能测试**：评审不回放预定义脚本，而是**自主导航复刻品、逐条演练工作流、对照预期结果验证行为**——这容纳了结构各异的应用与行为等价的实现，无需为每个任务手写评估脚本，同时能戳穿"看起来像"的惰性界面。
- **代码层约束**：强制引用的观察帧、封闭的评分词表、需求全覆盖、固定报告 schema；语义判断留给评审模型。
- **单一固定评审模型**（GPT-6-Astra，不在被评系统之列），避免评审漂移与自评，但论文坦承这并未消除评审偏见本身。
- **持久化需求**须提供"改动前 / 改动后 / 重载或重启后"三段证据才算满分。

### 4.3 指标体系：四组问题、各答其一

评审对每条需求 r 给出四档判级并折算学分：

| 判级 | 含义 | 学分 ω(g) |
|---|---|---|
| FULL | 工作流完整可复现 | 1 |
| PARTIAL | 部分可复现 | 0.5 |
| PLACEHOLDER | 只有装饰性/惰性占位 | 0.25 |
| BROKEN | 完全坏损 | 0 |

**（一）保真（Fidelity）**：加权保真分 WFS = 全部需求学分的均值；判级份额 F/P/Pl/B；持久化保真 P-WFS（只对持久化需求子集）；非功能率 NFR = PLACEHOLDER 与 BROKEN 之和占比；web 补充"幻象率" IR 额外标记 rationale 中描述假/装饰/惰性行为的条目。

**（二）转化（Conversion，本文的招牌设计）**：

- **探索覆盖率 ECov**：另一个事后覆盖评审（coverage judge）在探索关键帧上判断每条需求是否被"证据性到达"（reached），ECov = 到达比例。cr=0 只意味着"未见证据"，不证明未探索；缺失判断不计零分。
- **发现到实现率 D2I**：在"证据性到达"子集上的平均学分——**条件实现质量**。

论文明确声明：这些指标不做因果归因；未到达/未观察的需求也可能得分，所以 WFS 不必等于两者之积。

**（三）接地（Grounding）**：变化帧数、有效动作率 EAR（相邻帧像素变化超阈值的观测占比）、无效动作率 IAR、覆盖折扣视觉相似度 VSim（CLIP ViT-L/14 嵌入，乘以覆盖与判级门控）。

**（四）过程（Process）**：探索步数、挂钟分钟、自修正轮数 SCR（初检后的修订次数）、平台归因失败 PAF（崩溃 + 破坏环境的动作；平台缺陷修复后重跑）。

### 4.4 全景流程小结

原始软件 →（人工探索 + 截图采集 + 清单合成）→ 隐藏清单与排除集；构建智能体 →（纯像素观察 + 类人动作，规划-探索-实现-验证-修订循环）→ 复刻品；评审 →（逐条演练工作流 + 像素证据 + 状态对齐比较）→ 判级与清单对齐分数；覆盖评审 →（探索关键帧事后判断）→ ECov/D2I。三层分离——探索、实现、验证——是整个流水线的骨架。

## 五、评估指标与实验证据

### 5.1 实验设置

五个"模型 + 框架"系统端到端评测，同一接口、同一素材、同一实际上不构成约束的交互上限，无任务提示、无特权访问。平衡研究覆盖 16 个公共网站 + 全部 26 个 Android 应用 = 42 目标、1,111 条需求、210 次运行、5,555 个判级，每系统每目标一次。固定评审 GPT-6-Astra **不在被评系统之列**。目标等权，因此完整合并均值按 16:26 加权两个平台。

### 5.2 评审可靠性的人工验证

4 名 GUI 领域专家（硕士/博士级训练）抽检 20 个样本，**超过 95% 的评审判定被专家认定正确**——为自动评审在受检样本上的可靠性提供了证据。

### 5.3 主结果：五系统 WFS 榜

| 系统（框架 + 模型） | F% | P% | Pl% | B% | **WFS** | P-WFS | NFR↓ | ECov | D2I | VSim |
|---|---|---|---|---|---|---|---|---|---|---|
| Kimi Code + Kimi K3 | 22.9 | 52.2 | 15.9 | 9.0 | **0.530** | 0.535 | 0.249 | 0.377 | 0.598 | 0.295 |
| DeepSeek Harness + V4.1-Flash | 18.9 | 45.9 | 21.3 | 13.9 | **0.472** | 0.486 | 0.352 | 0.352 | 0.560 | 0.271 |
| ZCode + GLM-5.3-Flash | 13.5 | 39.4 | 11.7 | 35.3 | **0.362** | 0.380 | 0.471 | 0.259 | 0.459 | 0.191 |
| Codex + GPT-6-Sol | 13.4 | 30.7 | 25.8 | 30.2 | **0.352** | 0.363 | 0.559 | 0.349 | 0.445 | 0.253 |

- P-WFS 与 WFS 接近，但子集不同，不能据此断言"可用行为一般能在重载后存活"。

### 5.5 语义类别：功能类型 × 得分（web 513 条需求 AI 辅助语义编码）

| 语义类别（micro credit） | 得分 | ECov | D2I | 失败定性 |
|---|---|---|---|---|
| browse/navigate（浏览/导航） | **0.487**（最高） | 高 | 有定义 | 相对无短板 |
| automation/recurrence（自动化/周期任务） | **0.058**（最低） | 无任何 reached 对 | **无定义** | **探索缺口** |
| math/dependencies（数学/依赖） | 0.232 | **31.7%** | **0.333** | **实现短板**（覆盖了、没做出来） |
| 其余七类（检索/创建编辑/社交/视图/图形/导入导出/集成工作流） | 介于其间 | —— | —— | 中间排名随平均方式变化 |

三个警示性案例：

- Trello 36 条需求中 26 条是 automation——应用难度结论受**清单构成**强烈制约；
- Desmos Geometry 均分 0.203、极差仅 0.066——全线一致地低；其"交集链"需求在 5 条中 2 条有正向 reach 判断的情况下仍得零分；
- Squoosh 的"返回并加载"工作流在仅 2/4 正向 reach 下拿满分——覆盖证据与得分的关系是非对称的。

论文的结论很克制：**难度同时取决于被测工作流与应用本身**，因此需求级报告必须与应用级排名并列。

### 5.6 联合分布证据（图 7）

5,555 个需求-系统对（web 2,565 + Android 2,990）的"证据 × 判级"联合计数显示：**reached 与 not-reached 两组里都同时存在 FULL 和 BROKEN**——覆盖状态不决定实现质量，反之亦然。这是"探索与实现是两个独立短板"论断的直接经验证据。

### 5.7 指标如何支撑核心主张

论文的核心主张是：该任务暴露了两类不同的失败（探索证据缺口 vs 实现短板），而聚合保真分无法区分它们。支撑链：三入口失败分类（结构论证）→ ECov/D2I 定义（度量实现）→ 语义类别表 + 联合分布（经验验证：automation 属第一类、math 属第二类）→ 5 系统 WFS≤0.530（任务难度的总量证明）。实验设计与主张严格对齐。

## 六、效果优势的根源解释

本部分解释：为什么这个基准能"暴露出普通基准看不到的东西"，以及领先系统领先的机制是什么。按模板分三个子节。

### 6.1 根源机制与证据链

**因果链总览**：

```
纯像素接口 + 隐藏需求清单 + 自适应 judge（任务设计）
   ↓
失败被结构化地拆到三个入口：
   ①从未发现（exploration gap）/ ②误读 / ③无法实现（implementation shortfall）
   ↓
ECov（是否到达）× D2I（到达后实现质量）联合分布
   ↓ 把两类失败分离开
经验发现：
   - automation 类：micro credit 0.058，无任何 reached 对 → 纯探索缺口
   - math 类：覆盖 31.7% 但 credit 仅 0.232、D2I 0.333 → 纯实现短板
   - reached 与 not-reached 组内都有 FULL 和 BROKEN → 两维独立
   ↓
领先系统画像：Kimi/DeepSeek 双平台领先，伴随更长探索轨迹
（133.9–167.9 步 vs 其他 59.4–102.5 步）
   ↓ 论文明示：描述性关联，非因果
```

逐环标注证据等级：

1. **"三入口失败分解"——论文实验已支持的结构论证**。这是任务定义的直接推论：观察由智能体自选（入口①②存在），实现独立于观察（入口③存在）。论文引言与指标节明确给出这一分解。
2. **"ECov/D2I 分离两类失败"——论文实验已支持**。语义类别数据（automation 无 reached 对；math 覆盖 31.7% 而 D2I 0.333）与联合分布数据（图 7）是直接经验证据。**反事实推理**：若只有 WFS 一个总分，automation（0.058）和 math（0.232）都只是"低分"，无从知道前者几乎没人碰到过、后者碰到了却做不出——两类失败会被混为一谈，改进方向（多探索 vs 提升实现）无从选择。这正是双指标设计的必要性证明。
3. **"更长探索轨迹与领先的关联"——论文报告的相关事实 + 论文自己标注为非因果**。论文原文：更强的动作轨迹刻画了两名领先者，但"努力、迭代与保真度的关联需要受控研究后才能作因果解释"。且过程数据自带反例：DeepSeek 167.9 步只用 45.1 分钟，Kimi 133.9 步用 112.9 分钟——步数与时间投入并不等价，"更多动作"至少有两种成分（更广探索 vs 更多重复）。
4. **【阅读者推测】automation 类探索缺口的一个可能机制**：自动化/周期任务（如 Trello 的规则触发）在界面上往往是"配置后静默生效"的——不像按钮点击有即时视觉反馈，探索信号天然稀薄。这与纯像素接口下"视觉反馈因果歧义"（同一画面变化可能源于本地 UI 状态/共享数据/校验/持久化）叠加，使入口①在 automation 上最难通过。论文未做此机制归因（明确说 Trello 案例不识别原因），此为笔者的机制假设。
5. **【阅读者推测】领先系统的探索优势可能部分来自训练分布**：Kimi/DeepSeek 是国产模型，基准含知乎、语雀等中文生态应用，预训练暴露差异可能贡献了一部分探索效率（论文在局限性里承认活跃目标可能出现在预训练中，但未按语言拆分）。标注为推测。

### 6.3 综合判断与未决问题

**得到多项研究共同支持的机制**：

1. "视觉易、功能难"的失衡（本文 + IWR-Bench + RecreationWorld 三处独立出现）——实现交互与计算逻辑是跨设定的一致短板；
2. 探索与实现是可分离的两个失败维度（本文联合分布 + RecreationWorld 的静态/交互分层间接支持）；
3. 更多步数/算力的边际收益递减（Elo-per-token + CMU + 本文的 EAR-WFS 反例）。

**仍属推测的机制**：

1. automation 探索缺口的界面反馈稀薄假说（笔者提出）；
2. 训练分布/语言生态对探索效率的贡献（论文承认预训练暴露但未拆分）；
3. 领先系统长会话的上下文管理优势（由 CMU 天花板 + Kimi 耗时特征间接推断）。

**优势成立条件与失效条件**：上述结论在"单机可复现行为 + 纯像素接口 + 需求级隐藏清单"的设定下成立。若应用为多用户实时系统（排除集未覆盖干净）、清单构成高度偏斜（如 Trello 案例）、或评审模型与被评系统同族且偏差系统性偏向某类实现，结论的适用性都会受损。论文自己列出的未决项：每系统单次运行、需求内相关性、语义编码未经独立人工标注、15 处源文本不一致项、Android 无 rationale/截图导出——都意味着这些数字是"描述性画像"而非"机制定论"。

## 七、必要知识反推

假设让一个毫无背景的人复现这项工作，他最少必须掌握什么？

### 7.1 领域知识层（研究对象如何运作）

- **GUI 交互与 grounding**：不理解"截图 + 坐标级动作"这一交互闭环（及 DOM/无障碍树等被排除的通道各自提供什么信息），就无法设计出"运行时强制"的隔离边界，也说不清为什么纯像素是通用性最大的接口。
- **web 与 Android 的运行环境差异**：锁定浏览器 vs 容器化 Android、web 技术栈自由 vs 移动固定原生栈——不理解就无法构建跨平台一致的"人类式接口"。
- **真实软件的功能形态**：什么是有状态工作流、持久化、跨视图一致性；哪些行为单机原理上不可复现（多用户、支付、实时、生成式）——这是设计排除集 X 的前提。

### 7.2 方法论知识层（研究脉络与度量理论）

- **基准构建方法学**：SWE-bench 的"隐藏测试、执行验证"思想，Design2Code 的"截图-代码对照"范式——知道前人怎么测，才能发现"规格总是被给定"这一共性盲区。
- **LLM/agent-as-judge 评测方法**：Zheng 等、Zhuge 等的评审范式及其已知偏差——才能设计"固定评审 + 像素证据 + 封闭词表 + 代码层约束"的折中方案，并知道要请 4 名专家抽检。
- **度量与统计常识**：条件均值（D2I 是"到达子集上的均值"）、缺失判断的处理（缺失≠零）、应用等权 vs micro 均值的差异、以及**描述性关联与因果识别的区别**——论文通篇的克制表述建立在这套统计素养上。

### 7.3 工程知识层（系统实现）

- **MCP 服务器封装**：把设备访问收敛为 screenshot/tap/swipe/type 四个原语工具，需要服务端工具开发能力。
- **大规模多模型评测流水线**：5 系统 × 42 目标端到端运行、5,555 个判级的采集、按目标/需求 ID 的多源数据 join（含语义 ID 与数字 ID 的别名表）、SHA-256 哈希与全量导出审计——工程不严谨则结论不可审计。
- **素材虚构化与容器化**：虚构素材包避免真实用户数据；Android 容器保证可复现。

### 7.4 知识融合的关键节点

知识不是简单叠加，而是在三个创造性节点上发生化学反应：

1. **"探索"与"实现"解耦的度量发明**：把软件工程直觉（失败有不同入口）× 条件概率（到达子集上的均值）× 事后评审（不干扰被评系统）融合成 ECov/D2I——这是全文最核心的创造性合成。
2. **公平边界的显式化**：排除集 X + 16 条条件包含，把"什么不该考"变成与需求清单同等地位的一等公民数据。
3. **行为等价的操作性定义**：自然语言预期结果 + 自适应评审演练 + 像素证据引用，让"功能等价"这个哲学味浓厚的概念变成可执行的评分协议。

## 八、论文中可以提取的通用性灵感

### 灵感一：把失败拆到"入口"，而不是只看"出口"分数

- **核心思想**：任何"先获取信息、再执行"的任务，失败都应按发生环节归因——没找到信息 / 误读信息 / 找到读懂了但做不到。只看最终分数会把三种病当一种治。
- **论文证据**：ECov/D2I 把 automation（无 reached 对的探索缺口）与 math（覆盖 31.7% 而 D2I 0.333 的实现短板）分成两类失败。
- **推广场景**：①安全审计（没扫到资产 / 误报 / 扫到但利用失败）；②医学诊断（没做检查 / 误读报告 / 确诊但无法治疗）；③需求分析（没访谈到需求 / 理解错 / 知道但做不出方案）；④RAG 系统（没检索到 / 检索到但用错 / 用对了但生成失败）。

### 灵感二：覆盖与转化是两个独立维度

- **核心思想**：用"覆盖率"（到了多少）与"转化率"（到了之后做成多少）的联合分布替代单一总分，能诊断漏斗中真正的瓶颈。
- **论文证据**：reached 与 not-reached 组内同时存在 FULL 与 BROKEN 判级（图 7）；WFS 与 ECov 相关仅 r=0.53 而与 D2I 相关 r=0.79。
- **推广场景**：①销售漏斗（触达 vs 成交）；②教育评估（学了 vs 会了）；③推荐系统（曝光 vs 点击 vs 转化分层归因）；④自动化运维（告警覆盖 vs 告警处置）。

### 灵感三：显式的"排除集"是评测公平性的基础设施

- **核心思想**：在基准里明确声明并结构化记录"什么不考、为什么不考"，与声明"考什么"同等重要——否则不可解任务会污染全部分数。
- **论文证据**：438 条 web 排除（含 213 硬排除、16 条件包含），探索与评估共享同一边界文件。
- **推广场景**：①招聘笔试（明确超纲知识点）；②模型安全评测（明确不可测试的灰色地带）；③KPI 设计（明确不计入指标的外部因素）；④法律合同的责任排除条款。

### 灵感四：自适应评审优于固定脚本——为"行为等价"而设计验收

- **核心思想**：当正确实现允许多样性时，验收者应像人一样临场探索和出题，而不是回放固定脚本——固定脚本只能验证"跟原来一样"，自适应评审才能验证"功能上一样"。
- **论文证据**：自适应 judge 容纳行为等价实现并戳穿惰性 mock-up，4 专家抽检 >95% 判定正确。
- **推广场景**：①QA 验收（探索式测试 vs 回归脚本）；②招投标评审（功能等价而非方案雷同）；③图灵测试式产品评估；④代码评审中按行为而非写法判断。

### 灵感五：最严格的接口 = 最普遍的适用性

- **核心思想**：主动选择最贫瘠的信息通道（只有像素和指针），反而换得最大范围的适用性（凡是人能用的地方它都能用），同时逼出真实能力。
- **论文证据**：像素和指针是所有网站/应用唯一都暴露的接口； withholding 捷径使探索与规划本身成为被测对象。
- **推广场景**：①无障碍设计（面向最受限通道的设计惠及所有人）；②跨平台工具（不依赖私有 API 的方案永不失效）；③鲁棒通信协议（最保守编码通吃最差链路）；④教育（先学不依赖工具的原理再用工具）。

### 灵感六：诚实标注"描述性关联"是可信分析的底线

- **核心思想**：单次运行、混合构成、无干预的数据只能支撑描述性结论；把相关性明示为相关性，是研究可信度的护城河。
- **论文证据**：论文反复声明相关系数"不是因果"、Trello/Desmos 案例"不识别原因"、结论节直言需要重复运行与受控干预。
- **推广场景**：①数据分析报告规范；②A/B 测试之外的观察性数据解读；③新闻中的统计数字报道；④模型评测榜单的解读纪律（榜单名次≠能力因果）。
