## 一、论文背景

### 1.1 lead–worker 架构成为主流，但它悄悄改变了记忆的形态

过去两年，LLM 应用的主流扩展路径从"把一个模型做强"转向了"把多个 agent 组织起来"。其中最具代表性的是 lead–worker（编排者–执行者）架构：一个 lead agent 负责规划任务、拆分子任务、汇总结论，若干 worker agent 各自拥有独立的上下文窗口，并行执行子任务后把摘要交回 lead。微软的 Magentic-One、Anthropic 2025 年 6 月公开的多 agent 研究系统（lead 用 Opus、worker 用 Sonnet，内部评测比单 agent 高 90.2%）、以及当前各家编码 harness 的 subagent 机制，本质上都是这个模式。

这个架构的卖点是"并行探索 + 关注点分离"：每个 worker 拿到一个干净的上下文窗口，不会互相污染，可以彻底探索自己的子方向。Anthropic 的报告甚至量化过：在 BrowseComp 上，token 消耗量一项就能解释 80% 的性能方差——多 agent 之所以强，很大程度上是因为它花得起 token、装得下信息。

但硬币的另一面是：**委派重塑了 agent 的工作记忆**。单 agent 系统里，工作记忆是同一个上下文窗口里连续累积的状态；一旦委派，任务信息就分散在了多个 agent 的私有上下文、agent 之间的消息、以及共享工件（如共同编辑的报告草稿）里。一条事实被 worker W1 读到、被写进摘要、被 lead 收到、被写进最终报告——这是四段彼此独立的旅程，任何一段都可能丢失。

### 1.2 一个具体的失败场景：证据在眼前，冲突却消失了

论文用 Figure 1 给出了一个极具说服力的场景。假设文档 A 说 CorpX 2025 财年营收是 1.2 亿美元，文档 B 说是 1.5 亿美元，任务要求审查文档并标记潜在冲突（red-flags report，法律尽调中的常见交付物）：

- **单 agent 模式**：一个 agent 先后读到 A 和 B，两条矛盾声明共存于同一个上下文，比较发生在一处，冲突容易被发现。
- **多 agent 模式**：lead 把文档分区派给两个 worker。W1 读到 A（1.2 亿），W2 读到 B（1.5 亿）。W1 准确总结了自己负责的分区，W2 也准确总结了自己的分区——**没有任何一个 agent 犯错**——但 W2 的摘要里"1.5 亿"这个数字被省略了（在 W2 看来这只是个普通的营收数字，孤立地看毫无问题）。lead 只收到 1.2 亿一条线索，报告写完，冲突从未被发现。

这就是论文标题所说的"事实冲突消失之处"：冲突不是被模型推理错的，而是在证据流的交接中被静默丢弃的。每个环节的个体行为都合理，系统级的结论却错了。

### 1.3 已有研究为什么没回答这个问题

论文把这个空白拆成了三层：

1. **多 agent 有效性研究**只看端到端结果。MAST（Cemri et al., 2025）整理了 14 种失败模式、HiddenBench（Li et al., ICML 2026）证明了分布式信息下多 agent 集体推理的系统性失败（30.1% vs 单 agent 完整信息 80.7%），但它们都没有追踪**具体某条事实**在流水线里的存亡。端到端的正确率把"检索增益"和"协调损失"合并成一个数，两者互相抵消后你看不到结构。
2. **知识冲突研究**（context-memory、inter-context 冲突，如 WikiContradict、ContraDoc）把矛盾的段落**喂给同一个模型**，考察它如何裁决；而本文的场景要求**不同的 agent 分别检索并上报两条声明**之后，任何模型才有机会比较它们。冲突检测的前置条件——两条声明到达同一个决策点——本身就是会断的。
3. **Agent 记忆研究**（MemGPT 的分层记忆、G-Memory 的多 agent 记忆图、MIRIX 的六类记忆多 agent 管理）关注怎么存、怎么取、怎么组织，但几乎没有工作度量过"任务相关证据在跨 agent 传递后是否仍然可用"这个一致性问题。

于是核心的研究问题浮现了：**在 lead–worker 多 agent 系统中，事实冲突究竟在哪个环节消失？为什么检索更多的证据反而检出更少的冲突？**

## 二、论文定位和关联工作

### 2.1 研究谱系一：多 agent 系统的有效性之争

这条线上存在针锋相对的两派：

- **乐观派**：Anthropic 多 agent 研究系统报告 +90.2% 提升；STORM、DeepResearch Bench 展示了多 agent 深度研究的潜力。
- **怀疑派**：Cognition 的 Don't Build Multi-Agents（Yan, 2025）主张 agent 应共享完整轨迹而非摘要；Tran & Kiela (2026) 证明等思考 token 预算下单 agent 多跳推理反超多 agent；Jwalapuram et al. (2026) 称多 agent 优势是"幻觉"；Kim et al. (2026) 的受控比较（260 种配置）显示收益强烈依赖任务结构，可分解任务 +80.8%，顺序规划任务 −70.0%。

本文的定位是给这场争论**提供一个显微镜**：不站队，而是把"多 agent 究竟在哪一步丢东西"量化出来。它不提出新架构，而是提供基准 + profiler，让争论的各方第一次能基于证据流结构而非端到端分数对话。

### 2.2 研究谱系二：多 agent 失败分析与分布式证据

- **MAST**（Cemri et al., NeurIPS 2025 D&B）：标注 1,600+ 条轨迹，14 种失败模式三大类（系统设计、agent 间失调、任务验证），其中 agent 间失调约占 37%。本文与 MAST 的区别：MAST 是**事后归类**失败轨迹，本文是**事前植入**已知冲突并**正向追踪**其存亡——从"哪里错了"变成"证据在哪丢的"。
- **HiddenBench**（Li, Naito & Shirado, ICML 2026）：基于社会心理学的 Hidden Profile 范式，把信息分发给不同 agent，发现多 agent 无法利用潜在信息不对称（30.1% vs 80.7%）。关键区别：HiddenBench **直接分发**信息给 agent，跳过了检索阶段；本文的单/多 agent 都必须先从文档集合中自己检索证据，再经历上报和汇总——暴露的是 worker 选择性上报前后的完整链条。
- **信息论视角**（He et al., ICLR 2026）：把为另一个模型压缩上下文的模型视为噪声信道，证明压缩前后上下文的互信息预测下游性能（R²=0.71）。本文可以说是这项工作在"具体声明粒度"上的实证补全：不再算整体互信息，而是直接数"这一对数字是否都活过了压缩"。

### 2.3 研究谱系三：Agent 记忆与知识冲突

- **单 agent 记忆管理**：MemGPT（Packer et al., 2023）用操作系统式分页管理上下文；LongMemEval、LoCoMo 考察跨会话长期记忆；本系列此前精读的 AdMem、StaleBench、JetRiever 等评测关注的是**单 agent 在时间维度上**的记忆（记忆过期、记忆检索、技能腐化）。
- **多 agent 记忆**：G-Memory（Zhang et al., NeurIPS 2025）用三层图组织多 agent 协作轨迹；MIRIX（arXiv 2507.07957）用六类记忆（Core/Episodic/Semantic/Procedural/Resource/Knowledge Vault）加多 agent 记忆管理器协调更新与检索，在 LOCOMO 上拿到 85.4% SOTA。这些工作优化的是记忆的**组织与召回**，默认记忆内容在 agent 间传递时是完整的。
- **StateFuse**（Volkov et al., 2026）设计确定性冲突保留记忆接口；**Facts Without Rules**（Wang et al., EMNLP 2026 Findings）追踪隐私约束在交接中的丢失——后者与本文的"交接丢信息"现象同构，但丢的是使用规则而非事实对。
- **知识冲突**：Xu et al. (EMNLP 2024) 的综述把知识冲突分为 context-memory、inter-context、intra-memory 三类；WikiContradict、ContraDoc 评测矛盾段落。这些评测的共同前提是"证据已在同一个上下文里"，本文恰好补上了"证据如何到达同一上下文"这段被跳过的路程。

### 2.4 定位总结

| 维度 | 之前的工作 | 本文的突破 |
|------|-----------|-----------|
| 度量粒度 | 端到端任务正确率 / 失败类别归类 | 植入的**具体声明对**在四阶段证据流中的存亡 |
| 冲突来源 | 真实语料中已有的矛盾（不可控） | 受控数值替换，73 个冲突、答案由评估者持有 |
| 考察对象 | 单 agent 记忆（跨时间）或 agent 间通信（类别级） | **lead–worker 架构下跨 agent 的证据分布一致性** |
| 检索与协调 | 合并在一个分数里 | Pair Recall（证据覆盖）与 Judge Pass（语义检测）**分离测量** |
| 证据归属 | 不区分 | Same（一个个体持有两端点）/ Split（只有并集持有）配对分解 |

一句话定位：**这是第一篇把多 agent LLM 系统的记忆一致性拆解为阶段式证据流、并在受控冲突上完成配对实证的论文**——它回答的不是"多 agent 好不好"，而是"多 agent 的证据在哪丢、为什么丢"。

## 三、问题定义

### 3.1 从具体场景到抽象问题

具体场景：法律尽调中，agent 团队审阅文档目录并撰写红旗报告，需要标记文档间的数值矛盾（如两份文件对同一财年营收给出不同数字）。

核心洞察：**冲突检测的证据条件是"两条声明同时到达一个决策点"**。这把问题从"模型能不能发现矛盾"（语义问题）转化为"证据对能不能完整穿过流水线"（一致性问题）——后者可以用分布式系统的语言精确描述：每条声明是一个数据项，worker 到 lead 的交接是消息传递，lead 的证据集合是共享状态，冲突检测要求共享状态满足"完备性约束"（数据对完整到达）。

### 3.2 形式化定义

论文的度量体系建立在如下形式化之上：

- 对每个植入冲突 i，定义声明对 Gi = {Ai, Bi}（如 {1.2 亿, 1.5 亿}）。
- 定义四个测量阶段的证据集 Et_i：Source Reads（源工具输出中可见的端点）、Worker Reports（worker 外发消息中的端点）、Lead Evidence（lead 收到的消息 + lead 自身被允许的源读取）、Final Report（定稿工件中的端点）。
- **Pair Recall**（改编自 FEVER 的完整证据组原则）：R_pair = (1/N) Σ 1[Gi ⊆ Et_i]。只有两条端点都在才算命中，与无关证据无关。前三阶段再按归属分解：**Same**（某个个体独自供给两条端点）+ **Split**（只有贡献者的并集包含两条端点），且 Same 优先。最终报告是单一工件，只有 Both，无 Same/Split 之分。
- **Judge Pass**：LLM 裁判（claude-sonnet-5）按每冲突两准则打分——是否指出差异、是否正确处理数量比较，须含对指定冲突的显式标记。

给定三种委派策略（None / Optional / Required，见第四节）、等预算约束，求：Pair Recall 在各阶段的衰减轨迹，以及 Judge Pass 与各阶段证据覆盖的关系。

### 3.3 这个抽象的精妙之处

Pair Recall 与 Judge Pass 的**分离**是全文最关键的设计决策：

- 如果只看 Judge Pass（端到端），你会得出"强制委派让检测变差 3 个百分点"这样笼统的结论，不知道该修哪里。
- 拆开后你会看到：Required 在 Source Reads 阶段**更好**（68.7% vs 50.2%），在 Worker Reports 阶段**崩塌**（24.4%），于是改进目标被精确定位到 worker 上报协议，而不是笼统的"模型能力"或"委派本身"。

而 Same/Split 分解则回答了配对比较中的老大难问题：多 agent 检索到的证据和单 agent 检索到的证据"难度不同"（多 agent 检出的对可能是单 agent 根本没读到的），直接比 Judge Pass 有混杂。Same/Split 按证据归属分层后，"证据在几个人手里"这一变量与"证据是什么"被解耦了。

## 四、问题解法

### 4.1 基准构造：Harvey LAB 上的受控冲突注入

类比：这相当于在药物临床试验中做"挑战试验"——不是等病人自然发病，而是给受控剂量，精确观察病理过程。

具体做法：选取 11 个 Harvey LAB（Grupen et al., 2026 开源的法律长时程 agent 基准）尽调任务，保留原始指令和文档集合。对每个冲突 i，选定一个在文档中重复出现的数值 Ai（如营收 1.2 亿美元），在指定目录中把部分出现替换为 Bi（1.5 亿美元），其余位置保持 Ai 不变。每条冲突规格记录：数值、源位置、允许的等价表示（如 $120M / 120,000,000 / 1.2 亿美元）、编辑清单、评分标准。每任务 5–7 个冲突，共 73 个。

关键约束：agent 只拿到普通任务提示和编辑后的文档；**冲突规格和评分细则保留在评估者手中**——agent 不知道哪些数字被动了手脚，杜绝应试。判分要求：报告标记差异、说明需要核查、正确处理数量比较；仅罗列两个数字不算通过。

### 4.2 三种委派策略：把"是否委派"与"如何执行委派"解耦

| 策略 | 源访问 | 委派 | 现实对应 |
|------|--------|------|---------|
| None | 单 agent 自己读写 | 无 | 传统单 agent 基线 |
| Optional | lead 可自读源 + 可派工，允许重叠评审 | 酌情 | 当前主流实践（各家 harness 的默认） |
| Required | lead **只看消息不读源**，worker 分区读源 | 强制，最多 10 个并发 worker | 刚性分区流水线（类比 Magentic-One 的协调/执行分离与 AgentOrchestra 的 planner 委派） |

Optional 度量的是**模型选择**是否委派（不同模型差异极大：Haiku 22/22 全派，GPT-5.6 仅 9/22），Required 度量的是**委派执行**本身——把选择偏差从执行效果中剥离，这是三策略设计的方法论要点。

### 4.3 证据流 profiler：给每条声明装上行程追踪

类比：分布式系统的全链路追踪（如分布式追踪给每个请求标记 trace ID 穿透微服务调用链）。

实现：本地代理捕获所有模型请求/响应，与 SDK 事件、原生 trace、工具输出、报告工件做关联；agent 与工具调用标识符把每条证据归属到读取者、发送者或接收者。四阶段中 Source Reads / Worker Reports / Lead Evidence **累积**到被评分的检查点为止（只算产出该报告的轨迹前缀），Final Report 只度量选定交付物。统一匹配器通过事实锚点（fact-specific anchors）和验证过的等价表示识别端点——这就是冲突规格里记录等价表示的用途。GPT-6 的委派执行用明文协作 trace 区分外发消息与接收回执。

### 4.4 实验设置速览

3 模型 × 3 策略 × 2 轮 × 11 任务 = 198 次执行、1,314 次冲突观察（每模型/策略 146，池化每策略 438）。预算控制：每任务 59.60 美元生成额度（覆盖 lead 和 worker 全部调用，含修订、压缩、付费中断，裁判不计费），各模型/策略均值 0.95–1.02 倍——三种策略花基本一样的钱，比较才公平。

## 五、评估指标与实验证据

### 5.1 指标体系

- **主指标（证明核心悖论）**：Source Reads Pair Recall（检索覆盖）与 Judge Pass（最终检测）的**分离对比**——一升一降即"检索更多、检出更少"。
- **诊断指标（定位断点）**：四阶段 Pair Recall 衰减轨迹，特别是 Source→Worker 的落差（交接保留率）。
- **解混杂指标（归因）**：Same/Split 配对队列上 Required vs None 的 Judge Pass 差。
- **控制指标**：Cost（相对预算倍率），确保结论不被"花的钱不一样"解释。

### 5.2 核心结果一：检索更多，检出更少（池化，等预算）

| 策略 | Source Pair Recall | Worker Pair Recall | Lead Pair Recall | Final Both | Judge Pass | Cost |
|------|-------------------|--------------------|--------------------|------------|-----------|------|
| None | 50.2% | — | 50.2% | 18.3% | 16.2% | 0.95× |
| Optional | 62.8% | 12.8% | 54.8% | 25.8% | **24.2%** | 0.96× |
| Required | **68.7%** | 24.4% | 24.4% | 15.8% | 13.2% | 0.98× |

三个数字定住全文论点：Required 把源检索拉高 18.5 个百分点，最终检测反而掉 3 个百分点；Optional 两头都好（检测全场最高）；None 的 Lead=Source（没有交接，自然无衰减）。

逐模型看悖论更清晰（None→Required）：GPT-5.6 源 +8.9pp、检测 −5.5pp；GPT-6 源 +2.1pp、检测 −5.5pp；Haiku 源 +44.5pp、检测仅 +2.1pp。**没有一个模型把检索增益传导为检测增益**。

### 5.3 核心结果二：断点定位在 worker→lead 交接

438 个 Required 观察中，Source Reads 含完整证据对 301 例（68.7%），到 Worker Reports 只剩 107 例（24.4%）。**在已被 collective 检索到的 301 对里，worker 们只同时上报了两条声明的 106 对（35.2%）**——接近三分之二的证据对死在了"worker 决定汇报什么"这一步。且 Worker Reports 与 Lead Evidence 标签完全一致（24.4% = 24.4%），说明 loss 全部发生在源读取与 worker 上报之间，lead 转发环节没有额外丢失。

Figure 3c 的逐模型分解同样支持：Required 的 Source→Lead 落差（GPT-5.6 为 54.8pp、GPT-6 为 43.2pp、Haiku 为 34.9pp）远大于 None（None 无此段损失，只有 Lead→Final 的 6.2–12.3pp）。

### 5.4 核心结果三：Same 占优、Split 崩塌（配对同例比较）

以 Required 的证据分布定义 Same/Split 队列，None 在**完全相同的** model/run/task/conflict 实例上评估：

| 分层依据 | 队列 | Required Judge Pass | None Judge Pass | 结论 |
|---------|------|--------------------:|----------------:|------|
| Source Reads | Same（n=111） | **34.2%** | 22.5% | Required +11.7pp |
| Source Reads | Split（n=190） | 10.0% | **18.9%** | None +8.9pp |
| Lead Evidence | Same（n=72） | **72.2%** | 33.3% | Required +38.9pp |
| Lead Evidence | Split（n=35） | 17.1% | **28.6%** | None +11.5pp |

两个方向都成立：**当同一个 worker 读到两条冲突声明时，强制委派反而优于单 agent**（分工让阅读更专注）；**当两条声明分散在不同 worker 手里时，单 agent 反而更好**（至少两条在同一上下文里有机会相遇）。方向在两种分层下一致，结果稳健。

结论链收尾的两个数字：Split 案例中 worker 漏报一条或两条的占 73.2%（Same 时 50.5%）；即使两条都到达 lead，来源分裂仍拖累裁决——单贡献者供给时 lead 检出 72.2%，跨报告分裂时仅 17.1%。

### 5.5 委派行为分化（为什么必须有 Required）

Optional 下三模型行为迥异：Haiku 22/22 全派工（其 worker 上报 Pair Recall 达 37.0%），GPT-5.6 仅 9/22、GPT-6 仅 10/22 派工（两者 Optional 下 worker 上报 Pair Recall 都只有 0.7%，近乎不干活）。若只测 Optional，"模型是否愿意委派"的偏差会淹没"委派执行质量"的比较——这正是 Required 存在的理由。

### 5.6 实验设计如何支撑主张

论文的主张是结构性的："断点在交接处，且 Split 是主要死因"。支撑链条：等预算（排除花钱差异）→ 植入已知冲突（排除检索难度混杂，答案在评估者手里）→ 四阶段分解（把"检索增益"与"交接损失"拆开）→ Same/Split 配对（把"证据在谁手里"与"证据是什么"拆开）→ 方向一致性（两种分层、三个模型、两轮重复均同向）。每一环都在堵一个替代解释，这是比任何单项数字更有说服力的设计。

## 六、效果优势的根源解释

本文的"效果"不是打赢 baseline，而是**解释力的优势**：为什么端到端指标会给出误导性结论，以及为什么分阶段测量能纠正它。以下按因果链展开，并做外部交叉验证。

### 6.1 根源机制与证据链

**因果链 1：分区摘要丢失跨文档语境 → worker 无从判断孤立数字的重要性 → 上报环节系统性丢证据。**

- worker 被指定读某个分区，它看到"营收 1.2 亿"只是一个普通数字；判断该数字"值得上报"需要知道别处还有个"1.5 亿"——而这恰是它看不到的。信息的重要性是**关系性**的，分区恰恰切断了关系。
- 论文实验已支持：35.2% 的交接保留率、Split 案例 73.2% 漏报率。反事实佐证：Same 队列（同一 worker 读两条）漏报率降到 50.5%，检出率 34.2% 反超 None 的 22.5%——**把两条声明放进同一个头脑，问题就消失大半**。

**因果链 2：即使证据齐全，来源分裂也削弱裁决 → lead 对跨报告数字对的比对弱于对同源数字对的比对。**

- 论文实验已支持：Lead Evidence Same 72.2% vs Split 17.1%（两者都以到达 lead 为前提，检索已不是瓶颈）。
- 机制推测（标注为阅读者推断）：跨报告的两条声明在 lead 上下文里相距更远、伴随的框架（framing）不同（一个来自财务报告摘要、一个来自董事会纪要摘要），注意力上更难建立"同一实体+同一属性"的配对；这与 lost-in-the-middle（Liu et al., 2024）和 Summary of a Haystack（Laban et al., 2024）揭示的长上下文聚合困难一致，但论文未直接做距离/框架的消融，此步仍是合理假设。

**因果链 3：Optional 之所以全场最优，是因为它保留了"重叠读取"这个安全冗余。**

- Optional 允许 lead 自读源 + 允许 worker 重叠评审，等于在架构里内建了 Same 路径的概率；池化检测 24.2% 全场最高。
- 论文实验已支持（Table 1 池化行）。这也是论文给设计者最直接的可操作建议：**跨文档核查任务上，不要刚性不重叠分区**。

### 6.3 综合判断与未决问题

**多项研究共同支持的机制**：(a) 摘要交接是有损压缩，丢失不可恢复（He et al. 的信息论 + 本文的 35.2% 保留率 + Facts Without Rules 的规则丢失）；(b) 证据跨个体分裂损害综合判断（本文 Same/Split + HiddenBench 的 Hidden Profile 失败 + 人类群体记忆研究）。

**仍属推测的部分**：lead 对 Split 证据对裁决率低的具体机制（上下文距离？框架不一致？注意力分配？）论文未做消融；"重叠评审优于分区"在非数值冲突、非法律领域是否成立未知。

**适用边界**：结论建立在 11 个 Harvey LAB 任务、73 个数值冲突、每模型仅 2 轮之上；数值冲突有干净的等价表示匹配，语义冲突的端点匹配会难得多（论文自己承认 judge 有 3 例误记邻接比较）。Required 策略捆绑了强制委派 + 分区 + 限制 lead 读源三个变量，无法归因单一变量。优势条件：跨文档一致性核查类任务；可能的失效条件：证据天然无重叠的深度并行检索任务（此时 Split 不可避免，重点应转向 lead 端的对账协议）。

## 七、必要知识反推

假设一个没有任何背景的人要复现这项研究，最少必须掌握什么？

### 7.1 领域知识层

- **lead–worker 架构的实际运作**：必须用过 Codex SDK / Claude Code SDK 的 subagent 机制，知道 worker 如何派生、如何回传、lead 能看到什么。不了解这套机制就无法设计三种策略，也想不到 Optional 下各模型行为差异如此之大。
- **法律尽调任务形态**：知道 red-flags report 是什么、文档目录长什么样，才能选对 Harvey LAB 作为宿主基准并设计"看起来自然"的冲突注入。
- **数值在文档中的等价表示**：$120M / 120,000,000 / 1.2 亿必须被识别为同一端点——这是匹配器的事实锚点设计前提。

### 7.2 方法论知识层

- **评测方法论**：FEVER 的完整证据组原则（Pair Recall 的直接来源）、LLM-as-judge 的双准则 rubric 设计、以及"为什么必须把证据覆盖与语义检测分开测"——这需要对评测混淆因素的敏感度。
- **受控实验设计**：等预算控制（59.60 美元/任务）、配对同例比较（Same/Split 队列 + None 在相同实例上重评）、选择偏差与执行效果的分离（Optional vs Required）。这些是经典实验设计知识在 agent 评测上的迁移。
- **分布式系统一致性思维**：四阶段证据流本质上是给多 agent 系统装上分布式追踪。知道 CAP、共享状态一致性、消息传递语义的人会自然想到"证据的存活轨迹"这个视角——通讯作者课题组的计算机体系结构背景（Yu et al. 2026c 从体系结构视角论多 agent 记忆）在此处发挥了作用。

### 7.3 工程知识层

- **本地代理 + SDK 事件关联**：捕获全部模型流量并与工具调用、工件对齐， attributing 证据到具体 reader/sender/recipient——这是可观测性工程，不是模型研究。
- **预算控制器**：让系统在低于额度时原生续跑、保留历史与累计花费——没有这个，等预算比较不成立。

### 7.4 知识融合的关键节点

最有创造性的一步是把三个不相邻领域的知识焊在一起：**分布式系统的追踪思想**（给声明对装 trace）+ **NLP 评测的证据组原则**（FEVER 的 Pair Recall）+ **社会心理学的信息分布范式**（Hidden Profile 式的 Same/Split 分层）。单有任何一个都不够：只有追踪没有受控冲突，你只能看热闹；只有受控冲突没有追踪，你只能得到端到端分数；有了两者没有 Same/Split 分层，你无法把"检索"与"归属"解耦。论文标题里的 Inconsistency 一词正是这种融合的产物——它把一个工程现象（数字对不上）升格为一个可度量的系统属性（证据流一致性）。

## 八、论文中可以提取的通用性灵感

### 灵感 1：端到端指标会掩盖结构性对冲

**核心思想**：当一个复合系统的总分数由方向相反的两个分量构成（检索增益 vs 协调损失）时，端到端指标会把它们相加后呈现一个"看起来还行"的数，使人误判系统健康。

**论文证据**：Required 端到端只比 None 差 3.0pp（13.2% vs 16.2%），拆开后是 +18.5pp 检索增益对撞 −21.5pp 级别的交接损失。

**推广场景**：(1) RAG 系统的召回率与重排质量互相掩盖；(2) 编译器优化的 pass 收益分析；(3) 组织管理中"招更多人（检索面广）但会议对齐成本上升"的产出假象；(4) 医疗诊断中的多科会诊（信息广度 vs 综合质量）；(5) 模型 MoE 架构中专家覆盖与路由损失的分解。

### 灵感 2：重要性是关系性的，分区切断关系

**核心思想**：判断一条信息"是否重要"往往需要看到它与其他信息的关系；按任何单维度把信息分区给独立处理者，会系统性地丢失"只在关系中出现的重要性"。

**论文证据**：孤立看"营收 1.2 亿"毫无异常，Split 案例 73.2% 漏报；同一 worker 读到两条时漏报率降 19pp、检出反超单 agent。

**推广场景**：(1) 安全审计中的日志分区（单条日志无害、跨区组合才是攻击链）；(2) 数据库的列存/行存选择对跨行约束检查的影响；(3) 法庭证据的分卷阅读（单卷无罪、合卷有罪）；(4) 微服务架构中跨服务 invariant 的无人负责问题；(5) 科研合作中两个组各持一半关键数据。

### 灵感 3：给度量对象"装行程"，把品质问题变成追踪问题

**核心思想**：与其争论系统好坏，不如给关键实体（这里是声明对）标记并在每个交接点记录存活状态——失败会自己显形为某一跳的陡降。

**论文证据**：Pair Recall 四阶段轨迹让"68.7% → 24.4%"这一跳直接指向 worker 上报协议；Worker 与 Lead 标签一致又排除了 lead 转发嫌疑。

**推广场景**：(1) 数据管道的字段级 lineage 追踪；(2) 供应链的物料批次追踪；(3) 多轮对话 agent 的承诺（promise）追踪（承诺过的事是否被履行）；(4) 代码评审中的需求条目到代码变更的可追溯矩阵；(5) 隐私合规中个人数据在系统间的流转记录。

### 灵感 4：解耦"选择执行"与"执行效果"才能做公平比较

**核心思想**：评测一个机制时，若参与者的"是否使用该机制"是自选的，选择偏差会污染执行质量的估计——需要强制组来剥离。

**论文证据**：Optional 下 GPT 系模型几乎不派工（9/22、10/22，worker 贡献 0.7%），Haiku 全派工（37.0%）；只有 Required 才能横向比较委派执行质量。

**推广场景**：(1) A/B 测试中的自选择偏差修正；(2) 编程语言比较中"选择该语言的项目"与"语言本身"的混淆；(3) 医疗中自愿治疗组 vs 强制随机组；(4) agent 框架比较时模型是否愿意调用某工具的混杂。

### 灵感 5：冗余读取是分布式系统的纠错码

**核心思想**：允许（而非禁止）多个个体重叠读取同一信息，等价于给关键证据加了纠错冗余——代价是资源，收益是对冲单点摘要丢失。

**论文证据**：Optional（允许重叠 + lead 可自读）池化检测 24.2% 全场最高，超过单 agent 的 16.2% 与强制分区的 13.2%；论文结论明确警告跨文档核查任务上的刚性不重叠分区。

**推广场景**：(1) 分布式存储的副本因子与一致性等级权衡；(2) 团队知识管理中的"关键文档人人读过一遍"制度；(3) 混沌工程里主动注入副本不一致；(4) ensemble learning 中模型多样性与重叠覆盖；(5) 新闻编辑部的事实核查双人制。

| 术语 | 含义 |
|------|------|
| Pair Recall | 两条冲突端点均在某阶段证据集中出现的比例（改编自 FEVER 完整证据组） |
| Same / Split | 单一个体供给两条端点 / 仅贡献者并集包含两条端点（Same 优先） |
