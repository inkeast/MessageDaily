## 先说结论

这是 The AI Daily Brief 难得不谈新闻的一期长读：主播 NLW 把过去几个月 Stripe、Shopify、Uber、Ramp、Cloudflare 等最激进采用者陆续公开的「生产环境怎么跑 agent」材料通读一遍，归纳出 AI 原生公司的七个做法——它们几乎全部指向同一件事：怎么管理上下文。他同时给出本期更具挑衅性的第二个论断：2026 年初从 OpenClaw 爆发开始流行的「agent as teammate（把 agent 当同事）」心智模型，并没有反映最成熟用户的实践；更贴近现实的是「按需聘请咨询公司」——你带目标去，一个编排者组建一次性团队，交付物带证据回来，你签字、你负责，项目结束团队解散、方法论沉淀下来。他自己给的 TL;DR 只有一句：公司变成一台系统（the company becomes a system）。对读者的直接价值在于：这七个做法理论上「听完就能开始抄」，而它们共同的前提——先建上下文资产、再建编排与验证——比给 agent 起名字、建名册重要得多。

## 公司变成一台系统：七个做法的总览，以及它的样本偏差

先把故事线摆正。2026 全年「agents as teammates」的想象被 OpenClaw 爆发点燃，NLW 自己就是重度用户：他自述曾养过一整队 OpenClaw——做研究的、写作的、若干项目协调员，最上面还压着一个幕僚长（chief of staff）agent。如今他承认，这套编制与最成熟用户的实际做法已经对不上了。选题动机也很直白：中国间谍案与芯片管制丑闻刷屏太久，他想做点实用的；而他长期观察的痛点是——相对于变化速度，关于「新能力究竟怎么进入既有系统」的公开信息实在太少。答案的来源地也因此具体：近几个月 Stripe、Shopify、Uber、Ramp、Cloudflare 等公司以及一批更小的 AI 原生创业公司开始公开自己的 agent 生产配置，个体操盘手也在 X 上持续晒工作流，读得多了图景自然浮现。

样本偏差必须先交代（主播原话级别的自我限定）：本期的例子多数来自软件工程，这不只因为代码先用上 agent，而是因为代码有测试、可验证、「完成」有清晰定义；把这些做法搬到其他领域未必同样成立。但他附赠了一条普适观察法，值得原样记住：想知道自己组织三到六个月后的样子，去看工程师今天在干什么。七个做法如下，后文按主题串讲：

1. **上下文极大化**——给 agent 员工能看的全部，甚至更多；
2. **全职能部署**——不是只有工程团队在用 agent；
3. **信号触发**——工作由事件自动启动，而不是等人下 prompt；
4. **编排者＋子 agent 舰队**——一个主 agent 按需拉起临时团队，而非一群常驻 agent；
5. **互查验证**——agent 互相检查工作并出示证据，验证本身是独立工种；
6. **按风险分级的人审**——不全审也不不审，且永远有具体的人对结果负责；
7. **单一共享系统**——全组织在同一套可演进的系统里工作，而不是各用各的。

## 上下文极大化：给 agent 比员工更完整的视野，以及「囤积上下文」的政治学

第一个做法对老听众毫不意外：上下文。主播的判断是，对有意义的知识工作，瓶颈早已不是模型——很久以前就不是了——而是模型能接触到的上下文、信息与系统。最先进的 AI 原生组织因此给 agent 整幅图景：员工能看的一切，某些场景下甚至超过任何单个员工，因为 agent 是跨职能干活的。本期选题的灵感源头之一，是 Francis Davidson 在自己的公司被 OpenAI 收购后发布的博文（据节目，这家公司成立不到一年）：他将其命名为 content maxing（上下文拉满）——agent 通过 MCP 或 CLI 接入一切：每场会议录音、Slack、邮件、Drive、公司使用的每一个工具。同文还有一条 NLW 点名「可偷学」的做法：为每个决策写干净的共享文档，由 agent 持续维护这套知识库，留下的是决策本身加上「当时怎么定的、依据是什么」的完整轨迹。这条线索在其他公司的公开材料里反复出现：Ramp 用每日管道把 Slack、Notion、Linear 和日历拉进持久记忆，agent 会话从不冷启动；Uber 从 30 多个内部系统建出一张「上下文图谱」；Shopify 的 agent 干脆在 monorepo 里工作——同一个仓库装着代码，加上技能（skills）、规范、runbook 和专门写给 agent 读的指令文件。

但主播同样如实转述了两个反作用力。其一，上下文层本身成了需要运营的资产：Ramp 发现它的分析 agent 在上下文层过期或失养时会明显变差——喂得再多，不维护就反噬。其二更微妙，是 Hebbia CEO George Sivulka（转写作 Savolka/Hevia，已按公开拼写校正）发现的政治问题：对自己前途不安的员工，开始把囤积上下文当作工作安全感——「如果你清楚自己的价值所在，为什么要把交给 agent？」主播判断这是文化问题远甚于技术问题，领导者必须正面处理。（写作者注：至于给 agent 这么大访问权的安全边界，主播明说本期「 blissfully 无视」，本文照实记录这一留白。）

## 让工作自己找上门：全职能部署、信号触发与编排者舰队

第二个做法纠正一个常见误解：AI 原生不等于「工程团队很 AI 原生」，而是整个组织 AI 原生。Odessia 把 agent 铺到了战略、商务合作、产品设计、营销、客服支持、法务和财务，各团队之间还互相交流各自的用法差异。Anthropic 的增长营销团队据节目所称曾长期只有一个人：一套工作流让 agent 读取数百条在投广告的 CSV、标记表现不佳的条目、再由子 agent 批量写标题和描述——最终能做到几分钟产出数百条新广告。OpenAI 的 Enterprise Signals 研究则给出三家创业公司的例子：Basis 用 agent 跑客户 onboarding，Clay 给每个账户配一个 workspace 加专属子 agent 做客户管理，Exa 用 agent 跑开发者生态增长。NLW 自己的 agentic 视频流水线那一期，也是工程之外的一例。

第三个做法最抽象也最提纲挈领：开工的是信号，不是 prompt。在非 AI 原生公司，AI 不动，除非有人明确叫它动；在 AI 原生公司，工作由触发器自动开始——客户消息、发票、续约、运营告警，发生后不需要人把触发器翻译成一句指令。Runlayer（转写作 RunLayer，已按官方拼写校正）的工作来源包括客户来电、定制 Slack 频道、构建失败、Slack 提及，以及用户直接钉在产品界面上的 pin；更激进的是 Uber——按节目转述，其大多数 agent 会话现在由其他 agent 发起，围绕代码评审、自愈式 CI、on-call 分诊这类场景。主播给读者的换脑筋练习值得照抄：把「我该让 AI 做什么」这个问题，换成「业务里哪些事情发生后，应该自动开工」——一个流失信号、一次临近的续约、一张到账的发票，都是候选答案。

第四个做法由此顺理成章：团队不再面对一群常驻 agent，而是一个主（编排）agent，按眼前挑战拉起其他子 agent。Anthropic 的研究系统是节目引用的最清晰公开例：lead agent 负责规划，然后并行拉起子 agent；每个子 agent 拿到自己的任务、自己的上下文、自己的输出格式，甚至不知道其他 agent 的存在；规模随任务伸缩——简单事实核查一个就够，难题十个以上。据节目引用 Anthropic 自己的数字，这套架构在其内部研究评测上比单 agent 高出约 90%。Warp 的编排者则只路由不干活：为每个任务挑选用哪个或哪些 agent、哪个模型、给它们哪一片上下文；Ramp 也有一个进入团队共享域的编码 agent，名叫 Inspect（转写口径，未核实）。机理又绕回上下文窗口：编排者持有摘要与关键上下文，每个工人只拿窄指令与一张干净的白纸——理论上刚好够用。

## 验证、问责与单一系统：从互查到「总有人负责」

第五个做法直面新瓶颈：此时此刻几乎一切知识工作的瓶颈都已从「做出工作」移到「验证工作」，AI 原生公司因此把验证当成独立工种、为它专门设计系统——agent 交出产出，不等于完工。Shopify 的安全系统把每一个发现（finding）当作一条必须证明的「主张」：如果写不出一段真正利用该漏洞的测试，这条发现就被拒绝或降级，而且负责检查的模型与发现问题的模型不是同一个。Runlayer 的版本是一条流水线：agent 修完问题开出带前后截图或录屏走查的 PR，第二个 agent 对它做对抗性评审，上线之后还有 QA agent 继续试图在生产环境把它搞坏。主播的归纳只有两条：一要查工作，二要检查者不同于生产者。

第六个做法把人放回系统：人审按风险分级，且永远有一个具体的人负责。AI 原生公司既不审查一切，也不什么都不审，而是事先决定哪些类型需要人。Uber 的做法是每次 agent 之间的交接都保留责任链、最终追溯到具体的人——每一次 agent 调用都携带整条链的记录，所以再长的 agent 对 agent 交接也能追到那个责任主体。Stripe 的版本朴素而坚决：agent 写代码，人合并，每次合并都有人类评审。Runlayer 反过来让小而低风险的变更自动合并、人只在被请求时介入；Ramp 甚至把这套逻辑做成了商品——财务 agent 可自主批准低风险支出、或附上理由推荐决策，而每个客户自己划定 agent 能独自做到哪一步、哪里必须停下。Snap 的数字是本期最反直觉的投入结构：据节目转述，其 agent 投资的一半以上花在护栏（guardrails）上，而不是 agent 本身。

第七个做法关乎一致性：多数公司——哪怕在非常努力地用 AI——不同人、不同部门用 AI 的方式仍然千差万别；组织越 AI 原生，越倾向于一套单一但足够动态的系统，人人都在同一系统里改进。Ramp 的共享技能库收着 350 个共享工作流，还配了按角色推荐技能的工具；Uber 的技能库有 3,600 个技能、每天运行超过 30,000 次；Shopify 让编码 agent 只在公共 Slack 频道工作、绝不走私聊，于是每次会话都是一份人人可搜索、可学习的记录；Warp 用评分 agent 给完成的运行打分，再由另一个 agent 以 PR 形式提议对系统本身的改进、由人审合入——用 agent 的力量持续检视 agent 系统。附带一条度量告诫：Shopify 不数 AI 写了多少行代码、开了多少 PR，看的是「变更被回滚的频率」这类结果指标。

## Agent 不是同事，是按需咨询公司：一个心智模型的退场

七个做法里没有「agent teammates」——至少不是几个月前人们谈论的那种。NLW 承认这有语义洁癖的风险、也承认不同公司与个人体验各异，但他认为值得讲清楚实际演化为什么不同。当初的想象是：每个员工有自己的数字分身，或公司里有特定的、持久的、拥有各自角色的 agent，你给它们起名字、拟人化。这个模型的历史功劳是真的：它帮人们把观念从「一个能求助的聊天窗口」推进到「能自己出去干活的 AI」，完成了从辅助式到 agentic 的过渡。没有兑现的部分在于结构假设：teammate 模型默认一个固定名册——固定数量的 agent、各拥一个角色、身份持久。而现实走向的是随任务伸缩的动态舰队：名册换成随活走的产能，持久身份换成每个任务全新的上下文，单一长期角色换成可以更换的模型与工人，个人记忆让位于公司级知识与上下文。节目引用 Anthropic 的多 agent 系统指南作为佐证：按职能拆分 agent（规划者、编码者、测试者、评审者）往往适得其反——每次交接都变成一场传话游戏；在一个实验里，按角色拆分的 agent 花在互相协调上的精力超过了干活本身。NLW 把这称为「苦涩教训」（bitter lesson）的又一版本：人类很自然地用管理人的经验去组织 agent，而更好的做法也许是让它们自己组织自己——适合 agent 的结构可能长得跟适合人类的不一样。旁证还有 Every：年初实验给每人配一个 proxy agent，随后意识到完全不划算，更合理的是少数驻守在交叉点的 agent、按需通过子 agent 扩张。NLW 自己就是活样本：年初那套 OpenClaw 研究员／协调员／幕僚长编制，如今在 Claude Code 和 Codex 里变成了围绕仓库共享上下文组织的项目——每次会话更像临时拉起一个新的编排 agent，没有持久具名、拟人化的 agent，只有一捆持久的上下文，任何一组 agent 随时可以放进去干活。

于是有了本期那句更贴切的类比：按需咨询公司（on-demand consulting firms）。把一次咨询委托拆开看：你带去的是目标——那就是 prompt 或信号；负责这个 engagement 的项目主管去组队——那就是编排者；你从不管理、甚至永远见不到干活的具体员工；交付物带着证据回来；你签字验收，你对结果负内部责任；engagement 结束，做事的 agent 与「人」都散了，但工作与工作记录留下；做得好的话，这家事务所的方法论每次委托都在变好。主播自评「不完美，但方向上更近」。最后一块拼图来自研究：《哈佛商业评论》五月刊出的 BCG 研究里，经理们审阅同样埋了错误的文件，唯一变量是署名——一个 AI 工具、一位名叫 Alex 的人类同事、还是一个名叫 Alex Three 的「AI 队友」。当工作署名来自 AI 队友时，经理们检查得更潦草；效应在自称「已经把 AI 当员工」的公司里最明显——据节目口述，审查强度下降约 16%（写作者注：BCG 就该文发布的公开摘要口径是「识别出的错误减少 18%」，与节目口述略有出入，两个数字均未独立核实）。一位经理谈到自家名叫 Kevin 的 agent 时说得最直白：问题在于 Kevin 犯错时，Kevin 没法被问责。NLW 照例自我设限：这是单一研究、且做于 agent 采用极早期；如果你的公司在 teammate 类比下运行良好，请继续用。至于 Meta 与 ChatGPT 正引导用户给个人 agent（如 Muse、Dot）起名字的趋势，是否与上述矛盾？他认为不矛盾：那些个人 agent 本质上就是编排者——理论上握有你生活的全部上下文，最有条件编排你需要的任何 agent 与子 agent，而你始终只面对一个接触点。两条线会不会最终合一，还是各自覆盖 AI 体验的不同部分，现在下结论为时过早。

## 这对行业意味着什么，又该怎么观察

把七条做法连起来看，行业层面的信号是：竞争优势正在从「谁能用上最强模型」移向「谁把上下文、触发器、验证与问责组织成一台系统」——模型是租来的，系统才是自己的资产。「teammate」隐喻的退场也不必感伤：它完成了帮人从辅助式 AI 走到 agentic AI 的过渡使命，但继续拿它当组织蓝图，会撞上固定名册、传话游戏与问责真空三重摩擦，而「按需咨询公司」至少在目前的实践证据里摩擦更小。给读者一份可操作的观察清单：判断一家公司的 AI 原生成色，可以看它的 agent 会话是否还要冷启动（上下文层）、有多少工作由信号而非人的指令启动（触发器）、每个产出有没有独立于生产者的检查者（互查）、每条 agent 链条能不能追到一个具体的人（问责）、全组织是否共享同一套可演进的技能库（一致性）；度量上，回滚率这类结果指标远比「AI 代码行数」诚实。接下来几个月最值得盯的指标，是有没有非工程职能开始公开自己版本的七做法：软件工程先行，是因为「完成」在那里可以被验证定义——当营销、法务、财务也写出各自的「可验证的完成」，这场组织改造才算真正越过早期采用者的小圈子。
