## 一、论文背景

### 1.1 什么是多模态 Agentic Coding

想象你让 AI 完成这样一类任务：给它一张网页设计稿截图，让它写出等价的 HTML/CSS 代码；给它一张插画，让它生成能重新画出这张插画的 SVG 矢量代码；给它一组 3D 物体的四个视角图，让它写出一段 Blender Python 脚本，程序化地把这个 3D 模型建出来。

这就是**多模态 Agentic Coding（多模态智能体编码）**：agent 需要在"写代码"和"看图"之间反复交替——先观察目标图，写出初版代码；把代码渲染成图片，再观察渲染结果与目标的差距，修改代码，如此循环，直到两者足够接近。它不同于一次性代码生成，关键在于**闭环精修（closed-loop refinement）**：看图 → 写码 → 渲染 → 再看图 → 再改码。

这类任务的难点在哪里？在于**验证**。纯文本编码任务中，agent 可以通过运行测试来验证代码对错；但"渲染出来的页面像不像目标设计稿"是一个视觉问题，必须"看"才能判断。看不准，就改不对。

### 1.2 现行主流范式：Thinking-with-Images

2025 年 4 月，OpenAI 在发布 o3/o4-mini 时提出 [Thinking with Images](https://openai.com/index/thinking-with-images/)（随图思考）：模型在推理链中直接嵌入图片，可以自主放大、裁剪、旋转图像再观察——视觉信息成为思维链的一部分，而不只是输入。这一能力随后成为多模态编码 agent 的主流配置：论文中引用的 Visual Sketchpad（NeurIPS 2024，为 MLLM 配备画笔与图像操作以实现"视觉草稿链"）、Design2Code（NAACL 2025，让 MLLM 检查渲染截图并自我修正 HTML/CSS）等，本质都是让 agent 依靠**自身内置视觉（intrinsic vision）**去检查图像。

但"自己看"有一个天然问题：**感知与决策被绑死在同一个模型里**。模型的视觉编码器有多强，看图的上限就有多强——这就是论文所说的"内在感知瓶颈"（perceptual bound）。对文本 agent（如 GLM-5.2 这类没有视觉输入能力的纯文本模型）来说，问题更彻底：它们连"看"都做不到，直接被排除在这类任务之外。

社区对此已有两条补救路线，但都有明显缺陷：

- **固定视觉模块**：给文本 agent 外挂 captioner（看图说话）、OCR（文字识别）、布局检测器等专用小模型。代表工作有 MM-REACT、Visual ChatGPT、HuggingGPT（通过自然语言编排调用视觉专家），以及 VisProg / ViperGT（生成 Python 程序来组合预定义视觉 API）。问题是这些模块的感知能力是"写死"的窄条带——captioner 只会给一段泛泛描述，无法回答"这个按钮的圆角半径是多少"这类按需、细粒度、可迭代的问题。
- **VQA 导向的解耦管线**：如 SeeingEye、DRP，用一个小的视觉翻译器把图片转成结构化文本描述，再交给文本推理器。这类设计面向**静态的单轮看图问答**，无法支撑编码 agent 需要的"渲染-比对-定位-修改"多轮闭环。

### 1.3 工具调用与 Harness：本文所站的地基

与此同时，文本 agent 生态在另一条线上高速进化。Toolformer（[arxiv.org/abs/2302.04761](https://arxiv.org/abs/2302.04761)，Meta，2023）证明了语言模型可以自我学会在生成过程中插入 API 调用；Model Context Protocol（[MCP](https://www.anthropic.com/news/model-context-protocol)，Anthropic 2024 年开源的标准协议）让"给 agent 挂载外部工具"成为即插即用的行业标准。而 Claude Code 这类编码 agent 的 harness（执行框架）则展示了一种极简工具哲学：只给 agent 少数几个通用原语——Read 读文件、Bash 执行命令、Write/Edit 写改文件——agent 就能用它们组合出无穷任务。**工具不在多，在于通用、正交、可组合**，正如 Unix 哲学中 grep 负责搜文本、diff 负责比文件，几个小工具撑起了整个软件工程。

本文正是把这条"shell 工具哲学"的地基，搬到了视觉域：**视觉感知为什么不能像 grep/diff 一样，成为可调用的原子工具？**

### 1.4 本文要打破的两个限制

回到编码场景，现行 Thinking-with-Images 范式的两个结构性限制（论文 Introduction 明确总结）：

1. **多模态 agent 的天花板 = 自身感知**：即使设计任务专用工作流（DesignRepair 修前端、Chat2SVG 修矢量图、BlenderAlchemy 修 3D），视觉解释最终仍依赖 agent 内在感知，输出质量被它封顶，而且专用 workflow 牺牲了跨任务通用性。
2. **文本 agent 完全出局**：没有原生视觉就无法接入该范式；固定模块与 VQA 管线又撑不起闭环精修。

破局思路只有一个动词：**解耦（decouple）**——把"看"从编码 agent 身上拆下来，变成按需调用的外部服务。

## 二、论文定位和关联工作

本文处在多条研究脉络的交汇点。下面按谱系梳理前序工作，说明每条路线与本文的关键区别。

### 2.1 谱系一：Thinking-with-Images（内在视觉路线）

| 工作 | 核心思想 | 与本文的关键区别 |
|------|---------|----------------|
| OpenAI Thinking with Images（2025） | 模型在思维链中直接操作图像（缩放/裁剪） | 感知仍在模型内部，上限=内置视觉；VaaT 将感知外置为工具 |
| Visual Sketchpad（NeurIPS 2024） | 给 MLLM 画笔与图像操作，画出中间草图辅助推理 | 操作结果仍送回**同一模型**的视觉编码器再观察；VaaT 把解释权交给独立 MLLM |
| Design2Code（NAACL 2025） | 建立"截图→HTML"基准，agent 自查渲染截图自改代码 | 检查者=生成者，自检盲区共享；VaaT 的 diff 由外部模型执行 |
| DesignRepair（ICSE 2025，[arxiv.org/abs/2411.01606](https://arxiv.org/abs/2411.01606)） | 渲染页分析 + 设计规范检索修复前端代码 | 任务专用工作流，仅限前端；VHarness 五动作跨 HTML/SVG/3D 通用 |
| Chat2SVG（CVPR 2025） | MLLM 视觉检查 + 扩散引导优化精修矢量模板 | 专为 SVG 设计；VHarness 统一接口 |
| BlenderAlchemy（ECCV 2024，[arxiv.org/abs/2404.17672](https://arxiv.org/abs/2404.17672)） | VLM 评估渲染 3D 场景，迭代编辑 Blender 脚本 | 3D 专用；感知仍在同一 VLM 内闭环 |

**共性局限**：视觉解释最终都压回 agent 自身（或工作流内置）的感知能力上，天花板内建；且任务专用化导致不通用。

### 2.2 谱系二：给文本 agent 外挂视觉（固定模块 / VQA 管线路线）

| 工作 | 核心思想 | 与本文的关键区别 |
|------|---------|----------------|
| MM-REACT / Visual ChatGPT / HuggingGPT（2023） | 用 LLM 编排 captioner/OCR/检测器等视觉专家 | 专家能力固定、感知原语过窄；VaaT 用通用 MLLM，感知能力随提示语义伸缩 |
| VisProg（CVPR 2023 best paper）/ ViperGPT（ICCV 2023） | 生成 Python 程序组合预定义视觉 API | 程序一次性生成、单向执行；VaaT 是 agent 迭代闭环中按需调用的工具 |
| SeeingEye（[arxiv.org/abs/2510.25092](https://arxiv.org/abs/2510.25092)）/ DRP | 小视觉翻译器蒸馏结构化中间表示给文本推理器 | 面向静态 VQA 单轮问答；VaaT 面向"渲染→比对→修改"多轮闭环，且有 align/diff 这类断言与比对动作 |

### 2.3 谱系三：Vision-to-Code 任务基准

pix2code（EICS 2018）开创"截图→GUI 代码"；Design2Code 将其基准化；StarVector（CVPR 2025）做图像→SVG；CAD-Coder 与 3DCodeBench（[arxiv.org/abs/2606.01057](https://arxiv.org/abs/2606.01057)）做多视图图像→3D 建模脚本。本文注意到关键一点：**现有 2D 基准已近饱和**——Design2Code 的网格模板和简单图标上，现代 MLLM 乃至微调轻量模型都接近天花板，无法区分感知能力。因此本文自建了高复杂度 HTML（100 例，含杂志排版、海报、幻灯片等不规则结构）与 SVG（100 例，多层贝塞尔曲线与渐变）基准，并从 3DCodeBench 采样 100 例构成第三任务。3DCodeBench 官方报告还印证了闭环精修的价值："更高思考预算与多轮精修总体提升性能"。

### 2.4 本文定位结论

| 维度 | 之前的路线 | 本论文的突破 |
|------|-----------|-------------|
| 感知归属 | 绑定在编码 agent 内在视觉 | 外置为可调用工具 U_φ，与编码 agent P_θ 解耦 |
| 文本 agent | 被排除 / 只能做单轮 VQA | 完整外包视觉，首次闭环执行视觉编码任务 |
| 多模态 agent | 天花板=内置感知 | 按需动态增强，突破内在感知上限 |
| 接口设计 | 任务专用工作流 或 泛泛的自然语言 | 五个原子动作（shell 工具哲学），跨任务统一 |
| 评估 | 简单基准近饱和 | 高复杂度自建基准 + 全模型全指标对照 |

一句话定位：**本文是"shell 工具哲学 × agent harness × MCP 工具生态"三股力量在视觉编码领域的交汇点**——它不是发明了更强的视觉模型，而是重新设计了视觉能力的**供给方式**。

## 三、问题定义

### 3.1 从具体场景到抽象结构

具体问题：编码 agent 在闭环精修中"看不准"——多模态 agent 受制于内置感知，文本 agent 没有感知。表面解法似乎可以是"换个更强的多模态模型"或"外挂一个 captioner"，但前者是能力军备竞赛、不解决结构问题，后者感知原语太窄。

论文的深层洞察是一个**结构性类比**：

> **视觉感知之于编码 agent ≈ 外部工具之于文本 agent**

文本 agent 不需要内置搜索引擎也能查资料（调搜索工具）、不需要内置解释器也能跑代码（调 Bash）——能力的供给方式从"内置"迁移到了"调用"。那么视觉感知为什么必须内置？完全可以外置。

第二个洞察是接口设计层面的：软件工程师不需要 100 个专用工具，只需要 grep/diff 等少数正交原语。**视觉感知的操作空间同样可以收敛为少数原子动作**——转写结构、定位元素、细看局部、断言校验、比对差异，恰好覆盖"读图→写码→验证"闭环的全部感知需求。

### 3.2 形式化定义

论文第 2.1 节给出两条范式的对照式（这是全文最本质的两行公式）：

- **Thinking-with-Images**（式 1）：第 t+1 轮代码生成

  $$\hat{c}_{t+1} \sim P_\theta\left(c_{t+1} \mid x,\ \hat{z}_{1:t},\ \hat{c}_{1:t},\ \hat{v}_{1:t},\ \tau(V_t)\right)$$

- **Vision-as-a-Tool**（式 2）：

  $$\hat{c}_{t+1} \sim P_\theta\left(c_{t+1} \mid x,\ \hat{z}_{1:t},\ \hat{c}_{1:t},\ \hat{v}_{1:t},\ \tau(V_t),\ U_\phi(a_t, V_t)\right)$$

符号含义：x 是目标图；$\hat{c}_t$、$\hat{z}_t$、$\hat{v}_t = R(\hat{c}_t)$ 分别是第 t 轮的代码、思考、渲染图（R 为渲染环境）；$V_t \subseteq \{x, \hat{v}_{1:t}\}$ 是当前选中的图像子集；$\tau(\cdot)$ 是像素级操作（裁剪/缩放）；$P_\theta$ 是参数为 θ 的编码 agent；$U_\phi(a_t, V_t)$ 是参数为 φ 的外部视觉工具在原子动作 $a_t$ 上对 $V_t$ 的调用结果。

**两式唯一的差别就是多了 $U_\phi(a_t, V_t)$ 这一项**。但这一项带来两个结构性自由度：

1. **对文本 agent**：直接令图像输入 $(x, \hat{v}_{1:t})$ 从条件中消失——P_θ 无需看图，全部视觉信息经 $U_\phi$ 转成文本反馈进入条件，视觉感知**完全外包**。
2. **对多模态 agent**：$U_\phi$ 与内在视觉并存，agent 自主选择用哪个、何时用——内在感知**按需增强**而非被动封顶。

### 3.3 这个抽象的精妙之处

- 问题被收敛为纯粹的**信息流结构问题**：感知信息以什么路径进入代码生成的条件分布。一条路径（内置）还是两条路径（内置 + 外调），在数学上仅差一项，在工程上却是"单体"与"模块化"的分野。
- 它把"感知上限"从 P_θ 的属性变成了 U_φ 的可替换属性——换更强的视觉后端（φ 更新）无需动编码 agent，反之亦然。**两个模型可以独立升级、独立组合**，这是解耦带来的自由度。
- 约束条件同样清晰：不预设固定工作流、不设最少迭代数，动作由 agent 自主调度（on-demand），以保证通用性。

## 四、问题解法：VHarness 与五个原子动作

VHarness 是 VaaT 范式的参考实现。工程上：基于标准 Claude Code agent harness（200K 上下文），五个动作通过 FastMCP 实现为持久化 MCP 服务器（`mcp__atomic__*` 命名空间），视觉后端统一用 Gemini-3.8-Flash——**外部视觉工具本身就是一个通用 MLLM，没有任何任务专用训练**。

### 4.1 核心类比：视觉域的 shell 工具箱

软件工程师的日常被几个正交原语覆盖：`grep` 搜文本、`diff` 比文件、断言做检查。VHarness 把这套哲学映射到视觉域，得到五个原子动作：

| 原子动作 | 视觉域功能 | Shell 世界对应 | 输入 → 输出 | 典型使用时机 |
|---------|-----------|---------------|------------|-------------|
| **transcribe** | 全局结构转写：生成整体布局描述或结构草稿 | `tree` / 项目脚手架 | 目标图 → 结构化 JSON 骨架（layout 树/3D 部件分解） | 开工前先摸清全局 |
| **grep** | 视觉元素定位：按文字描述找元素 | `grep` 定位文本行 | 图 + 文字描述 → 边界框列表（归一化 0-1000，含类别/置信度/文字） | "标题栏在哪个区域？" |
| **inspect** | 细粒度局部观察 | `cat` / 调试器查看变量 | 图或局部区域 → 精确文字转写 + 排版属性（字族/字重/字宽/斜体/墨色 #RRGGBB）或细节描述 | "这段文字的确切字号颜色？" |
| **align** | 视觉断言校验 | `assert` / 单元测试 | 图/区域 + 目标文本/规格 → 布尔判定 `{"match": true/false}` | "渲染出的文字和目标一致吗？" |
| **diff** | 图对图差异比对 | `diff` 比文件 | 目标图 + 渲染图 → 按视觉显著度排序的差异列表（结构先行、细节殿后，双框定位） | 渲染后的复盘，定位下一轮修什么 |

三点设计细节值得注意（来自论文附录 A.3/A.4 的后端提示词）：

1. **输出契约严格**：grep 要求"严格 JSON 数组、无匹配返回 []"；inspect 的排版描述限定在固定词表（八种字族、七档字重）；diff 要求"宏观差异先于微观差异，不许让琐碎细节挤占显著差异"。这些约束把自由生成的 MLLM 输出驯化成**结构化、可解析、可复用**的工具返回值——这正是 shell 工具"输出可管道化"的视觉版。
2. **diff 的双框设计**：错位的元素在目标图与渲染图中坐标不同，diff 为每个失配元素同时给出 `target_bbox` 与 `render_bbox`（缺失则为 null）——这是为"渲染后修正"这一闭环场景量身定制的接口。
3. **transcribe 的克制**：明确指示"只输出结构骨架，不写代码、不给坐标/颜色/字体"——把"是什么结构"与"怎么实现"分离，避免越俎代庖。

### 4.2 按需执行（On-Demand Agentic Execution）

VHarness **不规定工作流**。五个动作作为可调用工具注册进 harness 后，agent 自主协调三种信息源：内在视觉（若有）、代码编辑、外部视觉工具。一次典型轨迹：先 transcribe 建骨架 → grep/inspect 解决区域摆放与细节 → 写码渲染 → diff 找差距 + align 核对文本 → 针对性修改 → 再渲染……直到判定完成。

**终止条件**是解法中最微妙的一环：基线（无 VHarness）与 VHarness 都不强制迭代数或 token 预算，都在"认为渲染已完成"时停止。区别在于——基线的"认为"来自内在视觉（经常漏看细节、**过早终止**）；VHarness 的"认为"有 diff/inspect 持续提供的外部差异报告作为依据。也就是说，**外部工具不仅提升了"看"的质量，还改变了"何时停"的判据**——这一点在第六部分的根源分析中会反复出现。

### 4.3 五动作接口全景对照

| 设计维度 | 固定视觉模块（captioner 等） | Freestyle（单一自由 MLLM 接口） | VHarness（五原子动作） |
|---------|---------------------------|------------------------------|----------------------|
| 感知范围 | 预定义窄条带 | 理论上无限 | 收敛为五个正交原语，覆盖闭环全需求 |
| 输出格式 | 各专家各异 | 自由文本，不稳定 | 严格 JSON 契约 |
| 调用一致性 | 固定管线 | agent 自由发挥，重复调用漂移 | 像标准 shell 工具一样稳定复用 |
| 迭代支撑 | 单向、一次 | 可迭代但不可靠 | 原生为多轮闭环设计 |
| 论文证据 | 论文 Related Work 分析 | 消融实验（Freestyle）实测逊于五动作 | 主实验全指标最优 |

注意第三列不是论文凭空的断言：论文用消融实验（见第五部分）实测了中间列（Freestyle）——同一个 Gemini-3.8-Flash、同一个 MCP 通道，只是不封装成五动作——效果显著落后。接口设计本身贡献了可量化的增益。

## 五、评估指标与实验证据

### 5.1 实验设置总览

**任务与数据**：三个 vision-to-code 任务各 100 例——Image-to-HTML（自建：网页、杂志、海报、幻灯片等不规则排版，素材预提取、剥离坐标元信息）、Image-to-SVG（自建：多层贝塞尔、渐变、细粒度构图，纯矢量、禁止位图嵌入）、Image-to-3D（3DCodeBench 官方采样：四正交视图 → Blender 脚本 → GLB 网格）。作者还对齐修复了 3DCodeBench 官方数据中输入图与 ground truth 网格不匹配的问题（官方仓库 Issue #2）。

**对照设计**：同一 Claude Code harness 内做同模型对照——基线（w/o VHarness）允许视觉 agent 用自带图像处理库辅助自查；处理组（w/ VHarness）在此基础上注册五动作 MCP 工具。这样唯一的变量就是 VaaT 范式本身。多模态 agent 四个：GPT-5.5、GPT-5.6-sol、Claude Opus 4.8、GLM-5.3-Flash；文本 agent 一个：GLM-5.2（无视觉，只能配 VHarness 跑，因预算限制在每任务 50 例子集上评估）。

### 5.2 指标体系：三组九项

| 指标组 | 指标 | 计算方式 | 方向 | 衡量的能力 |
|-------|------|---------|------|-----------|
| 2D 感知 | SigLIP2 | 448×448 重叠分块（步距 224）密集嵌入余弦相似度 | ↑ | 语义级整体相似 |
| | DINOv2 | 分块 [CLS] 特征对应余弦相似度均值 | ↑ | 自监督特征级相似 |
| | LPIPS | AlexNet 深度特征感知距离 | ↓ | 人类感知意义上的差异 |
| 2D 结构 | SSIM 局部/全局 | 窗口化 / 全图统计的结构相似性 | ↑ | 局部纹理与整体明暗对比布局 |
| | Pixel MSE | 归一化像素均方误差 | ↓ | 逐像素保真 |
| | Edge P/R/F1 | Canny 边缘图带容差匹配 | ↑ | 轮廓与结构线对齐 |
| 3D 几何 | Uni3D | 8192 点云（坐标+RGB 六维）经 Uni3D-giant 编码的余弦相似度 | ↑ | 3D 表征级整体相似 |
| | Chamfer | 单位球归一化双向平方 Chamfer 距离（四旋转取最小） | ↓ | 几何表面误差 |

这套组合的巧妙在于**互补三角**：感知组抓"语义像不像"、结构组抓"布局对不对"、几何组抓"3D 形状准不准"——分别对应视觉编码三类不同性质的失败（内容走样 / 排版错位 / 体积变形），避免单一指标幻觉。

### 5.3 主结果（Table 1 摘录）

Image-to-HTML（100 例）代表数值：

| 模型 | VHarness | SigLIP2↑ | DINOv2↑ | LPIPS↓ | SSIM g.↑ | Edge F1↑ |
|------|---------|---------|---------|--------|----------|----------|
| GPT-5.5 | w/o | 0.5773 | 0.8881 | 0.2277 | 0.6950 | 0.5389 |
| GPT-5.5 | w/ | 0.6319 | 0.9046 | 0.1820 | 0.7201 | 0.5820 |
| Claude Opus 4.8 | w/o | 0.3908 | 0.7167 | 0.4596 | 0.4539 | 0.3257 |
| Claude Opus 4.8 | w/ | 0.5077 | 0.8715 | 0.2974 | 0.6211 | 0.4316 |
| GLM-5.3-Flash | w/o | 0.6743 | 0.9019 | 0.1486 | 0.7696 | 0.7089 |
| GLM-5.3-Flash | w/ | **0.7553** | **0.9216** | **0.0937** | **0.8196** | **0.8059** |
| GLM-5.2（文本，50 例） | w/ | 0.6044 | 0.8949 | 0.2028 | 0.7242 | 0.5907 |

Image-to-3D（100 例）代表数值：

| 模型 | VHarness | DINOv2↑ | SSIM g.↑ | Uni3D↑ | Chamfer↓ |
|------|---------|---------|----------|--------|----------|
| GPT-5.6-sol | w/o | 0.7046 | 0.7515 | 0.7738 | 0.0157 |

四条核心结论（每条都直接支撑论文主张）：

1. **全模型 × 全任务 × 全指标一致提升**——4 个多模态 agent、3 个任务、每任务 7-9 项指标，无一例外。这不是挑 favorable case，是范式级效应。
2. **跨层级差距收窄甚至反转**：GPT-5.5 + VHarness 在 Image-to-3D 上全面反超更强的 GPT-5.6-sol 基线——外部工具能补足模型代差。
3. **文本 agent 反超多模态基线**：GLM-5.2 + VHarness 三任务全部超过 Claude Opus 4.8 基线，HTML/SVG 近乎全指标超过 GPT-5.5 基线。这直接证明"内在视觉不是视觉编码的必要条件"。
4. **最强者愈强**：基线最强的 GLM-5.3-Flash 加 VHarness 后拿下表中全部最优值——工具增强与模型能力不冲突、可叠加。

### 5.4 消融实验：两问两答

**问题一：内在视觉变强后，范式还成立吗？** 用更强的 GPT-6-astra 在 SVG 上做同模型对照（Table 2）：基线已超过 Table 1(b) 所有配置，但加 VHarness 后仍全指标提升（如 LPIPS 0.0572→0.0473，Edge F1 0.8310→0.8546）。**范式对感知强度鲁棒**。

**问题二：五个动作能否合并成一个自由接口？** Freestyle 消融（GPT-5.6-sol，3D，Table 3）：把五动作换成单个通用 MLLM MCP 工具（同一 Gemini-3.8-Flash 后端，附使用示例）。轨迹显示 agent 会自发模仿 diff/inspect 的问法，但无法做到"像标准 bash 工具那样准确、一致地调用"。结果居中：

| 指标 | w/o | Freestyle | w/ VHarness |
|------|-----|-----------|-------------|
| SigLIP2↑ | 0.6400 | 0.6677 | **0.7212** |
| Uni3D↑ | 0.7738 | 0.8255 | **0.8496** |
| Chamfer↓ | 0.0157 | 0.0070 | **0.0035** |

这组三段式数据是全文最有信息量的实验之一：**外接 MLLM 有用（基线→Freestyle），原子化封装才是完整增益（Freestyle→VHarness）**——把"用了外部模型"与"接口设计对了"两个混杂因子干净地分开了。

### 5.5 代价与行为分析（附录 C）

Token 消耗普遍放大 3-5 倍（如 GPT-5.5 HTML 从 5.3 万→17.3 万；GLM-5.2 最高单任务近 197 万 token）——精修更深、轮次更多。动作分布上（GLM-5.2，Table 6）：HTML 任务 grep 199.5 次 + inspect 264.8 次 + diff 246.5 次/例；3D 任务 diff 高达 351.8 次/例——**任务形态驱动动作组合**，无固定套路。精修轨迹（Figure 4/16）显示 VHarness 在相同早期迭代点得分更高、且在基线停机后继续上升——印证 5.4 的"终止判据"差异。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**对比对象**：基线是 Thinking-with-Images——agent 用内在视觉 + 像素操作（裁剪/缩放）自查。它为何曾经有效？因为视觉编码器与代码生成器共居一个模型，延迟低、集成零成本，且在简单基准（网格网页、简单图标）上感知够用。

**baseline 的根本局限**（机制层面，不是"它没用工具"这种表面描述）：

1. **感知-决策耦合 → 自检盲区共享**。检查者与被检查者是同一个模型：模型看漏的细节，恰好也是它写错的细节——错误在自查环节不可见。这不是能力问题而是结构问题：换更强的模型，盲区随能力移动但不消失（GPT-6-astra 消融证明仍有提升空间）。
2. **终止判据内置 → 过早收敛**。基线"看够了"就停，而"看够"的标准正是那个有盲区的内在视觉。附录 C 的直接证据：基线频繁漏看布局偏移、矢量轮廓缺失、3D 几何错位而提前终止；VHarness 的 diff/inspect 持续暴露剩余差异，驱动持续精修。
3. **无定位信号 → 修改盲目**。内置视觉给的是整体印象（"大概像了"），而闭环修改需要可操作的定位（"哪个元素、在哪、差多少"）。

**因果链**（每步标注证据等级）：

- 链一（信息通道）：五动作 JSON 契约 → 视觉差异变成结构化、可定位的文本反馈 → 消除"检查者盲区" → 全指标一致提升。【论文实验已支持：主实验全指标提升 + 严格 JSON 输出设计】
- 链二（终止判据外部化）：diff 按显著度排序的差异报告 → "完成"有了外部可验证依据 → 精修轮次延长、每轮增益更高 → 3D Chamfer 约 4.5× 改善。【论文实验已支持：Figure 4/16 轨迹对比 + 附录 C.1 终止行为分析】
- 链三（接口原子化）：固定语义边界的动作 + 固定词表输出 → 跨轮次调用一致、可组合 → agent 能像用 bash 工具一样"肌肉记忆"式调度 → Freestyle 与 VHarness 的差距（Chamfer 0.0070 vs 0.0035）。【论文实验已支持：Freestyle 消融直接对照】
- 链四（文本 agent 路径）：视觉信息完全经 $U_\phi$ 转文本 → 纯文本推理器无视觉也获得完整感知通道 → GLM-5.2 反超多模态基线。【论文实验已支持；但"文本推理能力 ≥ 视觉感知能力时该结论才成立"这一适用条件属阅读者推测，见 6.3】

**反事实推理**：去掉五动作保留外接 MLLM（Freestyle），增益缩水一半左右（Chamfer 0.0035→0.0070，仍优于基线 0.0157）——证明原子化封装是必要组件而非锦上添花；去掉外部工具（基线），增益归零——证明外置感知是增益来源主体。

### 6.3 综合判断与未决问题

**多项研究共同支持的机制**：结构化语言化的视觉反馈驱动迭代精修（ChartIR、VFLM 与本文三方一致）；感知-推理解耦的可行性（SeeingEye 与本文）；接口设计独立于工具存在的贡献（工具接口研究与本文 Freestyle 消融方向一致）。

**仍属合理推测的部分**：链四中"文本推理强于视觉感知时外包更优"的适用边界（论文未做弱文本 agent 对照）；VHarness 增益中"延长精修"与"提高每轮质量"的精确分解（论文轨迹图支持二者叠加，但无正交化实验）。

**适用条件与可能失效场景**：静态单目标（单页/单图/单物体）任务上验证，交互式应用与时序 3D 场景（论文自述局限）未验证；token 成本放大 3-5 倍（GLM-5.2 单任务近 200 万 token），成本敏感场景需权衡；U_φ 后端自身的感知误差在长闭环中的累积效应未被量化；当任务的瓶颈不在感知而在代码知识（如不熟悉的 API）时，视觉工具的边际增益应当有限——论文未测此边界。

## 七、必要知识反推

假设一个零背景的人要完成这项工作，他至少需要掌握哪些知识？

### 7.1 领域知识层

- **多模态编码任务栈**：HTML/CSS 渲染（Playwright/Chromium 截图）、SVG 光栅化、Blender Python API（bpy/bmesh/mathutils、Principled BSDF 程序化材质、GLB 导出）——不理解三个渲染环境就无法搭建"代码→图"的闭环。
- ** Thinking-with-Images 范式的实证边界**：知道它强在哪、卡在哪（感知绑定），才能提出正确的解耦问题。
- **视觉工具使用研究的谱系**：从 Visual Sketchpad 到 VQA 解耦管线，知道前人为什么不够，才不会重复固定模块的老路。

### 7.2 方法论知识层

- **Unix 工具哲学与 harness 设计**：正交原语、可组合、输出可管道化——五个原子动作的命名与契约直接复刻自 grep/diff。没有这层软件工程直觉，"视觉操作空间该收敛为哪几个动作"就没有设计依据。
- **工具调用与 MCP 协议**：Toolformer 以来的 API 调用范式、FastMCP 服务器的实现——外置感知的工程通道。
- **受控实验方法论**：同模型对照（唯一变量=VHarness）、三段式消融（无工具/自由接口/原子接口）、子集对齐验证（50 例共享子集重跑确认排序不变）——这是结论可信度的方法论保障。
- **评估指标学**：SigLIP2/DINOv2/LPIPS/SSIM/Edge/Uni3D/Chamfer 各自的原理与盲区，才能组合出互补三角。

### 7.3 工程知识层

- **提示词工程**：五个动作的后端提示词需要精确限定输出词表、排序规则、双框协议——把生成式模型驯化为契约化工具的关键手艺。
- **基准数据工程**：高复杂度案例的筛选标准（非线性阅读流、多列不对称网格、贝塞尔细节）、素材人工校验、坐标元信息剥离、甚至发现并修复 3DCodeBench 官方数据的对齐 bug——没有足够难的干净数据，范式差异根本测不出来。

### 7.4 知识融合的关键节点

- **节点一（范式洞察）**："agent 工具化"的通用经验 × "视觉感知"的具体瓶颈 → 视觉能力也该是工具。这是跨域类比产生的化学反应，不是任何单一领域的既有知识。
- **节点二（接口设计）**：shell 原语哲学 × 编码闭环的感知需求分析（开工要骨架、定位要查、细节要看、验收要断言、复盘要比对）→ 五动作集合。命名直接借力既有心智模型，agent 的预训练知识中本来就充满 grep/diff 用法——**接口设计与模型先验对齐**，这是 Freestyle 消融差距的一个隐性解释（阅读者推测）。
- **节点三（评估闭环）**：任务难度诊断（旧基准饱和）→ 自建三域高难基准 → 同模型对照 + 三段消融。难度、对照、消融三者缺一，"范式有效"都无法与"模型恰好变强"区分开。

## 八、论文中可以提取的通用性灵感

**灵感一：能力的供给方式可以从"内置"迁移为"调用"**
核心思想：任何被绑定在系统内部的能力（感知、记忆、知识），都可以重构为按需调用的外部工具，从而解除"系统上限=内部能力"的封印。论文证据：文本 agent GLM-5.2 外包视觉后反超多模态基线；GPT-5.5+VHarness 反超更强模型基线。推广场景：① 推理 agent 外挂验证器工具（数学证明调用 Lean）；② 语音助手外挂声纹识别而非内置；③ 数据分析 agent 外挂统计专家系统；④ 机器人外挂场景理解服务。

**灵感二：检查者不能等于生成者——双模型互检优于单模型自检**
核心思想：自检的结构性缺陷是盲区共享：漏看的恰好是写错的。引入外部独立检查者，错误才在验证环节可见。论文证据：diff/align 由独立 Gemini-3.8-Flash 执行，全指标提升；外部检索中 IVT 证明朴素自检反而崩溃。推广场景：① 代码评审引入异构模型交叉审查；② 文档写作用第二个模型做事实核查；③ 安全审计的 red team/blue team 分离；④ 自动驾驶的规划器与监督器异构冗余。

**灵感三：终止判据需要外部化、可验证**
核心思想："何时停止"若依赖系统内部判断，会系统性过早收敛；把完成标准做成外部可验证的信号，才能把算力转化为持续改进。论文证据：基线因内在视觉漏看差异而提前终止，VHarness 的 diff 持续暴露剩余差异驱动延长精修（轨迹图：基线停机后 VHarness 继续上升）。推广场景：① 迭代优化算法的收敛条件外置化；② 学生自评改为对照评分细则；③ 长时间自主任务的完成验收协议设计。

**灵感四：工具接口的原子化与契约化优于自由自然语言接口**
核心思想：同一个模型能力，封装成语义边界清晰、输出 schema 固定的少数正交动作，比一个"什么都能问"的泛化接口更可靠——原子化降低了调用歧义与跨轮漂移。论文证据：Freestyle 消融中，同一 MLLM 自由接口显著逊于五动作封装（Chamfer 0.0070 vs 0.0035）；外部工具接口研究（arxiv 2608.11386）在通用场景得出一致方向。推广场景：① API 设计：细粒度正交端点优于一个大而全端点；② 人机协作指令集设计；③ 数据库视图/查询原语的设计；④ 教育：把复杂技能拆解为可组合的原子操作训练。

**灵感五：旧基准饱和时，先造更难的尺子再谈方法优劣**
核心思想：当现有评测无法区分方法差异时，方法创新的前提是评估创新——难度不足的基准会让范式级改进"看起来没用"。论文证据：作者明确指出 Design2Code 等已近天花板，自建 100 例高复杂度基准（并顺手修复了 3DCodeBench 的数据对齐 bug）后才测出全指标差异。推广场景：① 算法竞赛出题的区分度设计；② 招聘评测的难度校准；③ 产品 A/B 测试的灵敏度检验；④ 模型评测卡的饱和监控与基准迭代。

## 附录：读这篇论文可以带走的三句话

1. **公式只差一项，结构差一个时代**：$\ U_\phi(a_t, V_t)$ 这一项，把感知从"模型属性"变成"可替换服务"。
2. **最好的接口设计往往已经有答案**：grep/diff/inspect/assert——软件工程五十年的工具哲学，直接平移到视觉域就够用。
3. **别只问"用了什么模型"，要问"检查者是谁、何时停、怎么定位"**——闭环系统的质量藏在信息流结构里。
