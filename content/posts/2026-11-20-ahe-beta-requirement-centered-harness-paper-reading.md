# 一、论文背景

## 1.1 什么是 harness，为什么它值得单独进化

用过大模型编程助手的人都以为是"模型"在干活，但实际上模型外面还裹着一层决定成败的工程壳——**harness（脚手架）**：系统提示词、工具定义与实现、中间件（消息路由、中断处理、进度上报）、记忆与子代理配置等。它决定模型看到什么信息、能做什么动作、何时结束一轮对话。同一个模型换不同 harness，性能可以差数倍；而好 harness 往往是模型特定的，模型一升级就可能失配——这构成了"harness 进化"这个研究方向的动机：让 harness 像软件一样被持续迭代。

前序工作已经把这件事自动化了：复旦团队自己的 AHE（Agentic Harness Engineering，arXiv:2604.25850）用三大可观测性支柱（组件/经验/决策可观测性）让进化 agent 自主编辑 harness，10 轮迭代把 Terminal-Bench 2 的 pass@1 从 69.7% 提到 77.0%；斯坦福等机构的 Meta-Harness（arXiv:2603.28052）用一个能通过文件系统读取全部历史候选代码、分数与执行轨迹的 agentic proposer 搜索 harness 程序。这些方法证明了"自动进化 harness"可行。

## 1.2 但分数驱动的进化有个致命盲区

现有方法的循环是：跑 benchmark → 看 verifier 结果与分数 → 让单一进化 agent 改 harness → 分数涨了就保留。问题出在三个环节：

- **评估环节**：benchmark rollout 只产生执行轨迹和 verifier 判定，捕获不到**隐式需求**——用户没说出口的范围与成本偏好、中途纠错暴露的期望、对及时回复和可见验证证据的需要。
- **修改环节**：进化 agent 直接"修观察到的失败"，从不显式定义失败背后的用户需求，容易产出窄补丁。
- **选择环节**：分数本身无法区分"通用修复"和"任务特化补丁"。外部研究已经实锤了这一点——"Do Agent Optimizers Compound?"（arXiv:2607.14004）在 Terminal-Bench 2.0 上做持续学习评估，GEPA 优化后的 agent 在新任务上**低于未优化基线**（提示词从 5 行膨胀到 195 行，塞满了训练集的文件路径和错误字符串）；Meta-Harness 能迁移但第二轮预算下完全停滞。分数驱动选择会强化过拟合，把进化困在 benchmark 特定的局部最优。

## 1.3 另一半盲区：交互本身是被评估遗漏的能力

与此同时，交互式基准的兴起揭示了另一半盲区。Scale AI 的 SWE-INTERACT（arXiv:2606.30573）把 SWE 任务从"一次性给全规格说明"改成"用户模拟器逐步揭示需求"，前沿模型解决率直接**腰斩**（约 50% 降到约 25%）——通过对话发现目标、记住中途约束、响应用户纠偏，是单轮基准根本没测量的正交能力。这意味着：一个 harness 哪怕 benchmark 分数不错，也可能在真实用户手里糟糕透顶（论文里 137 个 verifier 通过的会话中，有 34 个从未交付完整回复，用户评分直接打 1 分——验证器读工作区，用户只看到 harness 报了什么）。

真实世界的 harness 工程从来不是靠 benchmark 分数驱动的：用户提需求（显式写在请求里 + 隐式藏在期望中），工程团队用两条腿走路开发，靠"是否解决了用户问题"来决定一个变更是否合并。AHE-Beta 的出发点就是把这套真实工程实践完整搬进自动进化循环。

# 二、论文定位和关联工作

## 2.1 谱系一：自动 harness 工程（直接前序，本文批判并继承）

| 工作 | 核心思想 | 与本文关键区别 |
|---|---|---|
| AHE（复旦，2026.04，arXiv:2604.25850） | 三大可观测性支柱让每次编辑成为可证伪契约，自主进化不塌缩成试错 | 反馈来自任务 verifier，用 benchmark 分数选变更——正是本文要替换的两个环节 |
| Meta-Harness（Stanford/MIT/UW-Madison/KRAFTON，2026.03，arXiv:2603.28052） | agentic proposer 经文件系统访问全部历史候选的代码/分数/轨迹，摆脱反馈过度压缩 | 选择信号仍是评测分数；无用户概念 |
| Self-Harness（2026.06，arXiv:2606.09498） | 弱点挖掘驱动的自我改进 | 同上，verifier 驱动 |
| HarnessCompass（2026.08，arXiv:2608.01901） | 第一人称反馈引导进化向可泛化方向 | 反馈来自任务执行而非用户交互 |
| DemoEvolve（2026.05，arXiv:2605.24539） | 人类示范缓解稀疏反馈 | 依赖人工示范而非自动模拟用户 |

本文作者团队与 AHE 高度重叠（Jiahang Lin、Shichun Liu 等继续署名），AHE-Beta 可视为该团队对自家范式的"贝塔版重做"：把进化信号从 verifier 换成用户。

## 2.2 谱系二：用户模拟与交互式评估（本文的评估信号来源）

- **SWE-INTERACT**（arXiv:2606.30573）与 Dialogue SWE-Bench、SWE-Together、Asuka-Bench 等：把用户模拟器放进编码基准，验证了"隐式需求要通过多轮交互才暴露"。但它们只用模拟用户**评估** agent，AHE-Beta 进一步用模拟用户**驱动进化**。
- **Tom-SWE**（arXiv:2510.21903）：给 agent 建立用户心智模型；相关研究还覆盖了何时提问、如何维持目标账本。AHE-Beta 的 goal ledger（目标账本）设计直接受此启发。
- **Elicitron / UXCascade**：把模拟用户反馈聚合成需求文档或可用性报告——用途是设计评估，而非驱动代码变更。

## 2.3 谱系三：多代理软件工程（本文的组织形态来源）

ChatDev、MetaGPT、SOEN-101、AgileCoder 等把需求-架构-实现-评审分工给专门角色；MARE、iReDev 等做需求工程。这些团队"为给定任务造一个产品"，AHE-Beta 把同样的分工制搬来**进化 harness 本身**——产品是那个包裹模型的程序。

## 2.4 谱系四：提示/上下文优化（更早的技术源头）

从 APE、OPRO、PromptBreeder、TextGrad、DSPy/MIPROv2 到 GEPA（arXiv:2507.19457，用自然语言反思进化提示词，平均超 GRPO 且 rollout 少至 35 倍）。GEPA 证明了"语言信号比标量奖励更丰富"这一命题——AHE-Beta 把这个命题从提示词推广到了整个 harness 与整条需求链。

## 2.5 定位结论

| 维度 | 之前的路线 | 本文的突破 |
|---|---|---|
| 进化信号 | 任务 verifier 结果 + benchmark 分数 | 模拟用户多轮交互的 issue + 评分 |
| 修改者 | 单一进化 agent 改代码 | Gitea 四角色团队（Triage/Architect/PM/Developers） |
| 选择标准 | 分数涨即保留 | 需求被验证 + 评审通过才合并；分数仅事后评估 |
| 优化目标 | benchmark 分数 | 显式 + 隐式用户需求的满足 |

一句话：**AHE-Beta 是首个把"需求中心"的完整软件工程闭环（用户→需求→团队→评审）作为 harness 进化选择机制的工作。**

# 三、问题定义

## 3.1 从具体场景到抽象问题

具体场景：怎样自动改进一个 coding agent 的 harness？现有答案都是"跑任务、看分数、改代码"。论文的深层洞察是一个**结构性相似**：harness 进化 ≈ 软件产品迭代。用户需求（显式+隐式）→ 需求蒸馏 → 通用实现 → 评审合并，这条链在人类软件工程里运行了五十年，而"分数梯度"只是它最粗糙的投影——分数告诉你"变好了没有"，需求告诉你"为什么该变、变成什么样、哪些用户会受益"。

## 3.2 形式化定义

- **给定**：固定基座模型 M，初始 harness H₁，用户画像库 U（含人格维度），进化任务集 X，轮数 T。
- **求**：进化后的 harness H_T，使其同时满足显式需求（任务验证器可测，如 pass@1）与隐式需求（用户评分可测），并在**未见任务、未见模型**上泛化。
- **约束**：进化全程不得使用 benchmark 分数或 verifier 结果做选择信号；每次合并必须绑定一个被证据支撑的需求。

## 3.3 这个抽象的精妙之处

约束"选择信号与 benchmark 分数解耦"是全文最关键的一步棋：它把过拟合的根源（用评测集分数当选择器）从机制上切除了，而泛化能力只能在留存任务上"被动测量"，不能被"主动优化"。这就像禁止学生参加模拟考、只能靠吃透错因来提分——分数驱动是向测试集泄压，需求驱动是向问题本质收敛。

# 四、问题解法

AHE-Beta 的 harness 代码放在 Gitea 仓库里，每轮循环三步，需求是贯穿三步的红线（一个"需求"= 与具体任务无关的 harness 应有行为陈述 + 验收标准 + 会话证据）。

## 4.1 第一步：用户驱动评估（收反馈）

**类比**：招聘 50 位真实背景的"云用户"对新版产品做内测，边用边骂，骂完打分。

- **Persona 库**：50 张画像卡，从真实开发者的公开写作（博客/推文/访谈，32 张）和 GitHub 仓库 issue/PR（18 张）提炼，每张定义 7 个维度：评估能力（blind/competent/expert）、验收标准（runs/functional/idiomatic/rigorous）、委托粒度、监督风格、出错反应、信任姿态、自治期望。进化用 15 张（全部具备 competent 或 expert 评估能力），留存评估用 1 张库外固定画像。
- **多轮交互协议**：用户模拟器只通过用户可见界面观察 harness（回复、进度、帮助文档），**看不到内部实现**。每轮交互先用自己的话陈述意图（Norman 的意图-行动-评估认知模型），再从动作菜单选择，并记录"意图与选项之间的落差"——这个设计让用户能表达"现有选项满足不了的需要"。跨轮维护目标账本（goal ledger），记录原始任务 B0、新增目标与修订理由。
- **反馈形式**：过程中的 issue（用第一人称口吻写，像跟同事吐槽而非正式工单）+ 结束时 1–4 分用户评分及理由。

## 4.2 第二步：团队式修改（蒸馏并实现需求）

**类比**：把用户吐槽扔进一个有正规流程的开发团队。两条并行路线（issue 路线 + 会话路线）在"准入"处汇合。

| 角色 | 输入 | 职责 | 关键约束 |
|---|---|---|---|
| Triage | 单条 issue + 会话记录 + harness 日志 | 拒绝与 harness 无关/不成立/已满足的 issue；改写为去除项目名/任务 ID/具体答案的通用需求 | 不做跨 issue 去重（留给 Architect）；日志判不了的事实要求 harness 记录事实而非瞎猜根因 |
| Architect | 本轮全部需求 + 历史全部会话评分 | 把共享根因的需求合并为"整合需求"（须引用 ≥2 个来源） | 停留在机制层，禁止点名函数或实现步骤 |
| PM | 全部会话的评分/理由/目标摘要 | 挖掘用户**没说出口**的需求，写成 PRD | 每轮 ≤3 份；停留在产品能力层；绕过 Architect 直达准入 |
| Developers | 准入后的需求/PRD + 证据包 | 写 RFC 设计文档（目标/约束/非目标/候选设计对比）→ 拆 2–6 个文件集不相交的有序任务 → 分支实现 → 开 PR | 代码注释引用 RFC 与任务号；跑 lint 与测试 |

## 4.3 第三步：需求驱动选择（两道门）

- **准入（Admission）**：只把有会话证据支撑的需求/PRD 交给 Developers，附证据包（harness 运行日志、公开任务描述、执行条件）。用户对话、隐藏测试、评分器一律不进包；原始 issue、被拒 issue、被整合需求永远到不了 Developers。
- **评审与合并**：实现前设计评审（RFC 是否保目标、改在拥有该行为的层、覆盖接口与状态边界、给出可证伪的测试）；实现后代码评审（对照 RFC 验收标准、全测试套件、PASS 或 REWORK）。合并后 main 分支即 H_{t+1}，每个变更是 git commit，可随时回滚。
- **全场约束**：进化期间无任何 verifier 运行，benchmark 分数只在进化完成后用于评估。

## 4.4 全景对照

| 循环环节 | 分数驱动进化 | AHE-Beta |
|---|---|---|
| 评估 | benchmark rollout + verifier | 50 persona 多轮交互 + issue + 评分 |
| 归因 | 轨迹分析对分数 | Triage 逐条核证 → Architect 按根因聚类 → PM 补未言明需求 |
| 实现 | 单 agent 改代码 | RFC → 任务拆分 → PR |
| 选择 | 分数涨即保留 | 证据准入 + 双重评审 |
| 变更形态 | 窄补丁 | 跨任务通用机制（71 个合并变更中 39 个基于 ≥2 个任务的证据） |

# 五、评估指标与实验证据

## 5.1 指标体系

- **pass@1（主指标，显式需求）**：每任务单次尝试、经审计的通过比例。衡量任务验证器可检测的目标达成。
- **用户评分（主指标，隐式需求）**：评估 persona 在不看隐藏测试结果下打出的 1–4 分均值。衡量过程体验与需求满足，只在带交互评估中产生。
- **Token（效率指标）**：每任务执行 token 均值（百万计，不含用户模拟）。
- **盲测人类 A/B（终极效度）**：真实用户成对偏好与五维评分（1–7 分）。

## 5.2 数据集：Harbor-index 留存任务

Harbor-index v1.4（arXiv:2609.04298）从 6,627 个候选任务经难度过滤 + AI 审计 + 人工审计蒸馏出 82 个高难任务（最强 agent-模型组合不超过 30% 通过率），是区分方法优劣的可靠标尺。本文固定用 38 个任务：Coding 14 / Optimization 12 / Analysis 7 / Tool Use 5，来源覆盖 SWE-bench Verified/Pro、Terminal-Bench、AlgoTune、GSO、GAIA/Gaia2、BigCodeBench 等 14 个基准；**任何进化任务实例都不在这套评估里**，确保测的是泛化而非记忆。

## 5.3 主实验：RQ1——为什么选需求中心而不是分数驱动 / 人工工程

38 任务、GLM-5.3-Flash、带交互评估（三次运行均值）：

| Harness | pass@1 ↑ | 用户评分 ↑ | Tokens ↓ |
|---|---|---|---|
| Claude Code（人工工程标杆） | 27.2% | 2.46 | 2.89 |
| Meta-Harness（分数驱动进化） | 21.1% | 1.69 | 2.26 |
| AHE（分数驱动进化） | 23.7% | 2.53 | 2.07 |
| Base Harness（起点） | 21.9% | 2.59 | 2.40 |
| **AHE-Beta** | **33.3%** | **3.04** | **1.42** |

关键不对称：AHE-Beta 的 pass@1 与用户评分**同涨**，而三个外部 harness 的用户评分全部跌破 Base Harness——分数驱动的进化会优化验证器看得见的东西，牺牲用户体验。六轮进化中留存用户评分 2.59→3.04、pass@1 21.9%→33.3% 单调上升，增益可积累。盲测人类 A/B：48 个有效对中 31 对偏好 AHE-Beta，五维全高（过程可理解性 4.13→5.33 提升最大），方向与模拟器一致——模拟用户的偏好预测了真实用户。

## 5.4 消融：RQ2——用户反馈与交互贡献了什么

| 设置 | pass@1 | Tokens |
|---|---|---|
| Base Harness | 21.9% | 2.40 |
| AHE-Beta (N=8, 无交互，只看最终结果) | 23.7% | 3.15 |
| AHE-Beta (N=8, 带交互) | 28.9% | 1.71 |

去掉进化期交互（用户只终审最终回复与只读 diff），pass@1 掉 5.2pp 且 token 反升 45.7%——中途纠错与涌现需求是单一终审捕获不到的。反向消融同样关键：评估时去掉用户模拟器（无交互评估），所有 harness 的 pass@1 都下降，但 AHE-Beta 仍以 26.3% 最高且 token 最低——优势不来自评估时用户"陪跑"。另有 137 个 verifier 通过会话中 34 个未交付回复被打最低分，证明 pass@1 之外的隐式需求真实存在且只有用户评分能捕获。

## 5.5 泛化：RQ3——超越进化任务与进化模型

| 执行模型 | Base pass@1 | AHE-Beta pass@1 | Δ |
|---|---|---|---|
| GLM-5.3-Flash（进化模型） | 21.9% | 33.3% | +11.4pp |
| GLM-5.3（免再进化迁移） | 23.7% | 39.5% | +15.8pp |
| DeepSeek-V4.1-Flash（免再进化迁移） | 36.8% | 42.1% | +5.3pp |

四个领域全面改善：Tool Use 0.0%→26.7%，Optimization 19.4%→38.9%。跨模型免再进化仍增益，说明进化出的是模型无关的通用工程机制而非模型特定的提示技巧。

## 5.6 进化成本与产出

N=32 主配置五轮共耗 1.92B token（98% 为输入），Developers 占 68%。160 个会话产出 131 条 issue → Triage 拒 36 条 → 115 条需求 → Architect 整合出 22 条 + PM 14 份 PRD + 35 条独立需求 = 71 个合并 RFC。harness 代码从约 1,100 行长到 18,000 行，系统提示从 18 行到 63 行。

# 六、效果优势的根源解释

## 6.1 根源机制与证据链

**因果链一：信号 richer → 归因更准 → 通用修复**

多轮交互暴露中途纠正与涌现需求（论文实验已支持：无交互消融掉 5.2pp）→ Triage/Architect 把同根因 issue 合并为机制级变更（论文实验已支持：整合需求中位覆盖 3 个进化任务的证据；71 个合并变更无一带任务名/仓库名）→ 变更天然跨任务泛化（论文实验已支持：四域全升 + 跨模型迁移 +15.8pp）。对照组 Meta-Harness/AHE 用 verifier 信号 + 分数选择，在留存任务上用户评分反而低于 Base——信号里根本没有"用户"这个变量。这与 GEPA 的发现同构：自然语言反思携带的诊断信息远超标量分数（GEPA 比 GRPO 少用至 35 倍 rollout）。

**因果链二：选择与分数解耦 → 过拟合被机制性抑制**

分数驱动选择的根本局限不是"分数不准"，而是**分数把通用修复与任务特化补丁映射到同一个标量上**，选择器无法区分（阅读者推测，外部证据强支持：Do Agent Optimizers Compound? 证明 GEPA 负迁移、Meta-Harness 二轮停滞）。AHE-Beta 的准入要求证据包 + 需求覆盖 ≥2 任务的硬约束，等价于把"可泛化性"写进了合并条件（论文实验已支持：39/71 变更基于 ≥2 任务证据；留存 pass@1 六轮单调升）。这与 RELAI-VCL 的 no-regression 约束殊途同归——都用**非分数的结构性约束**当泛化过滤器。

**因果链三：需求倒逼过程可见性 → token 反降 40.8%**

用户需求里高频出现"我想知道它在干什么"（supervision 维度）→ 进化出 stall notice（停顿通知）、fact-anchored progress（事实锚定进度）、stage checkpoint（阶段检查点）等中间件 → 模型调用更少、输入更短（论文实验已支持：双方都通过的任务上 token 仍省 53.6%；外部基线 98% token 是输入，重复上下文提交减少是主要贡献）。token 节省不是刻意优化出来的，是"过程透明"需求的副产品——这是需求中心范式独有的红利。

**反事实推理**：若去掉"Architect 按根因合并"，issue 将逐条变成窄补丁——这正是 AHE（前作）的形态，其留存用户评分 2.53 < Base 2.59；若去掉"分数解耦"，选择器回到 benchmark 梯度——外部证据（2607.14004）显示该路线增益不可积累。两条反事实都指向同一结论：不是"加了 X 所以好"，而是把选择信号换成了结构上必然更通用的东西。

## 6.3 综合判断与未决问题

- **多研究共同支持**：(1) 非分数结构约束（需求验证 / no-regression）是泛化增益可积累的关键——本文与 RELAI-VCL 从两端独立到达；(2) 多轮交互暴露单轮不可见需求——本文消融与 SWE-INTERACT 的失败模式审计互证；(3) 语言级需求信号优于标量分数——GEPA 已证，本文推广到 harness 全栈。
- **仍属推测**：50 persona 库的代表性（论文自认局限：单模拟器模型、最多 32 场景、6 轮预算）；"需求覆盖 ≥2 任务"阈值 2 的选取未见敏感性分析；AHE-Beta (N=16) 用户评分局部回落提示机制间可能存在非加性干扰。
- **适用条件**：优势成立于"隐式需求丰富"的场景（交互式编码、工具使用）；若任务的全部需求都被 verifier 显式覆盖且用户偏好无关紧要，分数驱动可能同样有效。模拟器与真实用户偏好方向一致仅在一个 A/B（48 对）中验证，更大规模部署下 persona 偏差可能使进化偏向特定用户群——论文自己引用的 action-boundary 研究也提醒：需求不清时过度主动的 harness 可能越权。
- **可能的失效条件**：模拟用户与真实用户分布漂移；issue 质量极端低（Triage 全拒，进化空转）；需求间相互冲突且 Architect 无法整合时。

# 七、必要知识反推

假设找一个零知识的人重做这项工作，他至少需要：

## 7.1 领域知识层

- **harness 的解刨学**：提示/工具/中间件/记忆各层各管什么行为——不知道这个，Architect 的"改在拥有该行为的层"就无从谈起。
- **coding agent 的真实失败模式**：中断后请求排队无人读、长时间流式无输出、模型只读不写、验证通过但回复未交付——这些是 persona 场景设计的需求来源（论文 8 个机制种子全部对应一个机制）。
- **真实用户行为学**：开发者如何委托（one-liner 到 spec level 谱系）、如何监督、出错时如何反应——persona 七维度是对真实用户群的工程化压缩。

## 7.2 方法论知识层

- **harness 进化研究脉络**：AHE/Meta-Harness/Self-Harness 的循环结构与已知病灶（分数选择过拟合）——这是问题定义的靶子。
- **用户模拟技术**：从 Schatzmann 议程式模拟到 persona 条件模拟、目标账本（Bratman 计划理论）——多轮协议的认知科学依据（Norman 意图-行动-评估）决定了"先陈述意图再选动作"这一关键设计。
- **软件工程流程知识**：issue triage、PRD、RFC、设计/代码评审、准入——四角色分工不是发明而是移植。
- **可证伪性与实验设计**：留存任务隔离、跨模型迁移、消融对照、盲测 A/B——证明"需求驱动"优于"分数驱动"需要把选择变量单独拎出来。

## 7.3 工程知识层

- **Gitea/Git 工作流**：label 体系、PR 绑定 head 合并、commit 级回滚——"每个变更可回退"是评审敢于放行的前提。
- **评估基础设施**：Harbor 适配器、E2B 沙箱、token 记量、时间预算分摊（用户评分 600 秒不计入任务时限）。
- **提示工程（给角色的）**：Triage/Architect/PM 的提示中大量"禁止越界"条款（不做跨条去重、不写实现步骤、不虚构根因）——每个禁止都对应一类已观察到的角色越权失败。

## 7.4 知识融合的关键节点

1. **"软件工程实践 = 需求中心循环"这一抽象**：把五十年工程管理知识与 agent 进化对接，是全文的创造原点。
2. **"模拟用户既是评估器又是进化信号"的双重角色**：交互式基准（评估用）+ harness 进化（优化用）两条线的交叉点，产生"用用户驱动进化"的洞察。
3. **"分数解耦 = 结构性泛化约束"**：把持续学习文献的 no-regression 思想，以"需求验证 + 评审"的工程形态重新发明。
4. **"用户评分与 pass@1 的正交性"**（34 个 verifier 通过但用户打 1 分的会话）：这一实证发现同时定义了新指标、验证了 persona 设计、支撑了整套动机——是证据链上的枢纽节点。

# 八、论文中可以提取的通用性灵感

## 8.1 灵感一：把人类组织的成熟流程做成自动进化的选择机制（范式迁移类）

- **核心思想**：当一个自动优化循环过拟合其评测指标时，不要急着换更强的优化器，而是把一个已经运行几十年、天然抗过拟合的人类组织流程（需求→开发→评审）整体移植进来当选择机制。
- **论文证据**：分数驱动的 AHE/Meta-Harness 用户评分跌破基线，需求驱动的 AHE-Beta 同涨且跨模型迁移 +15.8pp。
- **推广场景**：① 推荐系统的召回策略迭代用"模拟用户投诉→产品评审"替代 CTR 梯度；② 编译器 pass 顺序调优引入"程序员需求工单"；③ 数据管道 schema 演进由模拟分析师的需求驱动；④ 游戏 NPC 行为树迭代以玩家 persona 反馈为准入；⑤ 法律合同模板自动优化以模拟当事人异议为门。

## 8.2 灵感二：与评测分数解耦的选择信号是泛化的结构性保证（机制类）

- **核心思想**：任何"在评测集上变好就保留"的循环都内置了过拟合许可；把选择标准换成独立于评测的结构性证据（需求覆盖 ≥2 任务、评审通过），泛化是机制副产品而非运气。
- **论文证据**：六轮留存 pass@1 单调升；39/71 变更基于 ≥2 任务证据；对照文献中 GEPA 负迁移、Meta-Harness 停滞。
- **推广场景**：① 学生模型蒸馏时用"跨教师一致"而非验证集损失做早停；② 药物分子生成用"多靶点活性"而非单靶体外分数做候选晋级；③ RAG 系统以"跨域检索一致性"做组件升级门；④ 微服务重构以"≥2 团队受益"作为公共库抽象准入；⑤ 内容审核规则的上线门槛设为跨语言命中一致性。

## 8.3 灵感三：交互过程本身是单轮评估不可见的信号矿（信号利用类）

- **核心思想**：只在结束时打一个总分，会丢掉过程中最有信息量的部分——中途纠错、目标修订、意图与界面的落差；把这些过程信号结构化（goal ledger、意图先行、gap 标记），等于给系统装了需求探测器。
- **论文证据**：无交互消融 pass@1 掉 5.2pp、token 反升 45.7%；SWE-INTERACT 独立证实交互能力腰斩前沿模型。
- **推广场景**：① 客服系统从"会话结束 CSAT"升级为逐轮情绪轨迹驱动迭代；② IDE 补全以编辑中途的撤销/重打模式为训练信号；③ 教学助手记录学生目标修订事件而非只看测验分；④ 网页 A/B 测试引入鼠标轨迹与回滚行为而不仅是转化率；⑤ 机器人协作中人在环接管时机作为需求信号。

## 8.4 灵感四：用户画像要"有根有据"，且评估能力的分层决定反馈质量（紧凑性/表征类）

- **核心思想**：模拟用户不是越像越好，而是要按能力维度（能否自己验证结果）分层——blind 用户提供体验信号，expert 用户提供诊断信号；画像从真实行为证据提炼（引语锚定）而非凭空捏造。
- **论文证据**：50 卡中 45 张的"出错反应"维度有引语级 grounding；进化种子全部选 competent/expert 评估能力，避免噪音 issue 淹没 Triage。
- **推广场景**：① 医疗 AI 用不同健康素养分层的患者模拟器测试解释质量；② 无障碍测试按辅助技术熟练度分层构建用户模型；③ 产品内测招募按"能写复现步骤"分层；④ 教育软件按元认知水平分层模拟学习者；⑤ 自动化安全测试中红队人员能力画像分层。

## 8.5 灵感五：过程可见性需求会"免费"带来效率（关注点分离类）

- **核心思想**：把"让用户看懂过程"当一等需求去满足，中间产物（阶段检查点、事实锚定进度、运行报告）会同时减少系统的无效功——透明与效率不是权衡，是同构。
- **论文证据**：token 反降 40.8%，且双方都通过的任务上仍省 53.6%；stall notice 在 29 个任务上 59 次直接触发后续编辑。
- **推广场景**：① 长任务流水线暴露阶段产物可减少重复计算；② 数据库查询引擎输出中间计划反而利于缓存命中；③ 分布式训练日志结构化到步骤级可及时发现僵尸步；④ 法务/财务自动化出具中间工作底稿降低返工；⑤ 科研自动化记录每步实验证据便于中断续跑。

# 附录：进化机制落地示例（71 个合并变更中的代表）

- **Stall notice（停顿通知，中间件层）**：连续 4 步只读 ≥60s 或 120s 无编辑 → 向下一次模型调用注入 [action-notice]。留存任务 33/38 触发；Pillow filter 上 Base 三连败，AHE-Beta 151s 收到通知、22s 后动手、926s 以 2.0x 加速通过。
- **Early persistence（尽早落盘，提示层）**：能独立工作的单元立即写入工作区。matrix square root 任务 AHE-Beta 在 551s 写出首版 solver，会话超时无回复但磁盘文件通过隐藏检查；Base 把代码囤在 /tmp 从未通过。
- **Measurement first（测量先行，运行时层）**：任务含数值阈值时先建最薄端到端版本、先报首测数值再深化。Detector 命中 8 个留存任务（含全部 5 个 AlgoTune）。
- **Bounded correction delivery（有界纠错送达）**：用户消息排队 >90s 即切断当前模型调用、带消息重试。pydicom 种子三轮接力（排队→回执→90s 上限），用户评分从 1 升到 3——论文图 5 的完整案例展示了"用户抱怨 → Triage/Architect/RFC → 运行时行为改变 → 下一轮用户体验改善"的全链路。

这些变更没有一个名字里带进化任务或仓库——需求中心的流水线让"通用性"成为产出物的默认属性。
