## 一、论文背景

### 1.1 为什么 C/C++ → Rust 迁移是热点

内存安全漏洞（越界访问、use-after-free）长期困扰系统软件——它们源于内存不安全语言中**普通的实现模式**，而非罕见的编码失误。静态分析、sanitizer、加固技术只能"在仍允许不安全内存行为的语言内部打补丁"。Rust 的所有权与借用系统在**编译期**强制内存安全，因此 NSA/CISA 等机构持续推动向内存安全语言迁移，改造遗留 C/C++ 系统的 Rust 化成为工程刚需。

### 1.2 为什么"项目级 C++ 迁移"特别难

论文的关键观察：C++→Rust 迁移**不是翻译问题，而是项目级重设计问题**——必须在"语义保真"与"Rust 式重建"之间走钢丝：

- **源结构保持式迁移**（C2Rust 一系）：可追溯低层行为，但会把源语言的组织方式、unsafe 惯用法、项目假设原样搬进 Rust，产出"长得像 C 的 Rust"；
- **直接 agent 翻译**（ClaudeCode 等）：模型有重建自由，但**语义覆盖取决于模型能否自己识别必须保留的源行为**——而这正是 C++ 的死穴：C++ 的关键行为藏在对象模型、析构函数驱动的生命周期协议、模板实例化、重载解析、回调、资源所有权约定、构建期约定里，**跨文件分布、只在跨模块交互与编译行为中显形**。

### 1.3 既有工作的空档

C→Rust 有成熟的规则式/精炼式路线，但 C 的结构与语义相对显式、过程化；C++ 侧 Cpp2Rust 只支持子集；LLM 翻译工作（含 RAG-LLM）停留在代码片段/特性/翻译单元级别。**没有一条路线在项目级显式建模"迁移意图"**——语义保留全靠模型隐式推断。这就是本文要填的坑。

## 二、论文定位和关联工作

### 2.1 谱系一：源保持式迁移到 Rust

C2Rust 奠定 C→Rust 源到源基线；后续 OOPSLA/PLDI/CAV 系列工作做 unsafe 缩减、所有权推断、别名分析、类型迁移、输出参数改写、union 翻译、I/O API 迁移；近期系统再加 LLM、静态分析、依赖恢复、FFI 验证、历史检索、编译器反馈修复（含同团队的 His2Trans 骨架优先框架）。共同局限：**始终绑在源结构/骨架上**，目标侧的重建不是重心。

### 2.2 谱系二：C++→Rust 翻译

Cpp2Rust 证明受支持子集可自动译到安全 Rust；RAG-LLM 工作用文档/示例检索做单元级翻译；实证研究（Yan et al.）梳理了 C++ 特有的 LLM 失败模式。这些工作证明可行性，但**特性支持 ≠ 项目级迁移**——真实 C++ 项目把行为分布在类不变量、生命周期协议、模板工具、回调、构建依赖里。

### 2.3 谱系三：Agentic 精炼与验证反馈

ClaudeCode 类系统把代码当可执行状态（inspect-modify-recheck）；迁移系统用编译反馈、测试、FFI 验证、静态分析、等价性检查改进产出。局限：**修复的上限是证据的上限**——未被测试覆盖、未被显式建模的源义务即使项目可执行也可能永远隐形。

### 2.4 定位总结（论文 Table I）

| 迁移设定 | 代表 | 局限 |
|---|---|---|
| 规则式 C→Rust | C2Rust 及精炼系 | C++ 对象/生命周期/模板/构建语义弱 |
| 规则式 C++→Rust | Cpp2Rust | 子集限制，无端到端项目重建 |
| LLM 代码翻译 | 翻译研究/框架 | 函数/单元级，非项目级 |
| LLM C++→Rust | RAG-LLM、实证研究 | 片段级，无项目级保真建模 |
| 直接 coding-agent | ClaudeCode | 保真隐式 |
| **Req2Rust** | 本文 | **MRS+RDS+验证报告：项目级 LLM C++→Rust 重建** |

Req2Rust 的独特站位：**把"保留义务"从模型隐式上下文中拉出来，变成显式的、语言中立的中间制品（MRS）**，再用 RDS 决定 Rust 侧怎么组织，最后用三类验证器闭环精炼。

## 三、问题定义

### 3.1 核心洞察

项目级 C++ 迁移的根本困难是**"保什么"与"怎么建"两个决策纠缠在同一个生成过程中**。当 LLM 一边读 C++ 一边写 Rust 时，它必须同时做两种本质不同的推理：

- 保真推理：哪些外部可见行为/依赖假设/状态资源效果/安全约束**必须**原样保留？
- 重建推理：Rust 侧应该用什么文件划分、模块结构、所有权模型来实现这些义务？

这两个推理的耦合正是失败之源：模型容易为了"像 Rust"而悄悄改掉迁移面 API 的形状（后文 paho.mqtt.cpp 案例中 ClaudeCode 把 byte-slice 构造改成 `Vec<u8>`、丢掉 C 消息重建路径就是典型）。

### 3.2 形式化

- 给定：C++ 项目/模块 + 源码、接口、构建三类证据；
- 求：可编译、可检查、可在验证报告下精炼的 Rust crate；
- 约束：①外部可见行为保留义务显式化；②迁移面接口（public API 形状）可被测试观测；③边界 unsafe（ABI/FFI/平台资源）与可缩减 unsafe 区分对待。

### 3.3 抽象的精妙之处

MRS 作为**语言中立的中间表示**，扮演了 C++ 证据与 Rust 实现之间的"契约层"——类比建筑改造：先由结构工程师出具《必须保留的承重与管线清单》（MRS），再由建筑师出《新平面设计图》（RDS），施工队（单元生成）按图施工，监理（三验证器）按清单逐项验收。清单让"改了不该改的"在验收时**可定位、可归因**（验证报告直接挂回 MRS 条目与源证据），这是纯 agent 循环做不到的。

## 四、问题解法

Req2Rust 三阶段流水线：**A. 需求建模 → B. 需求引导重建 → C. agent harness 精炼**。

### 4.1 阶段 A：迁移需求规约（MRS）

需求规划 agent 从源项目提取 MRS，按迁移视角分组：

- **外部可观测接口**：public API 身份、所有权、可调用形状、参数、返回行为、可见性；
- **行为事实**：正常行为、输入输出约束、失败行为、状态效果、依赖效果；
- **外部依赖与暴露符号**：区分"源项目自己实现的行为"与"委托给外部库/平台 API 的行为"；
- **跨 API 状态/资源事实、跨 API 关系、待验证的开放迁移项**。

MRS 把源语言语法从主生成目标中移除——后续阶段不再面对 C++ 代码，而是面对"义务清单"。

### 4.2 阶段 B：需求引导的 Rust 项目重建

**B-1 需求驱动的 Rust 设计合成（RDS）**：把保真义务翻译成 Rust 项目组织——目标文件与模块角色、公共 Rust 面、自有符号与依赖、**全局设计约束**（跨文件共享的数据结构、错误处理约定、资源所有权、序列化/格式化路径——防止每个源片段被当孤立翻译任务）、有序实现单元（每个单元 = 一个 Rust item：函数/类型/trait/impl 块/常量/辅助，记录签名、职责、调用关系、要满足的 MRS 条目）+ MRS 覆盖链接 + 开放设计假设。

**B-2 设计引导的项目实现**：五步落地——

1. 实现规划器按文件目标与调用依赖排序单元、分组成构造批次；
2. 渲染器生成**标记骨架**（文件、crate 结构、模块声明、占位区）；
3. **并行单元代码生成**：各单元在 MRS/RDS 约束下独立生成函数体；
4. 单元体写回骨架（body application）；
5. crate 组装（crate root、manifest、模块导出、依赖骨架），供普通 Rust 工具链使用。

**关键设计：初始 Rust 项目被当作"可执行精炼状态"而非最终产物**——真实项目的实现细节与惯用法只有在构建和验证时才可见，精炼阶段才是消化它们的地方。

### 4.3 阶段 C：agent harness 精炼

harness 维护项目当前状态，循环执行"调用验证器 → 汇总报告 → 喂给精炼 agent → 更新项目"。三个翻译 harness 验证器：

- **编译器验证器**：可构建性检查，定位编译失败、缺失项、类型/API 不匹配（cargo check）；
- **语义验证器**：把当前 Rust 项目与 MRS+源证据按**可观测契约**对照——正常行为、边界与错误行为、状态与资源效果、公共面覆盖；由并行语义审计子 agent 执行，报告把潜在分歧挂到相关保真义务、Rust 位置、源证据与修复理由；
- **unsafe 缩减验证器**：用同样的保真视角区分**边界 unsafe**（ABI 兼容、布局保持、extern 调用、资源、回调、跨迁移接口所有权转移所需——保留）与**可缩减 unsafe**（可用安全 Rust 抽象或更小 unsafe 包装表达等价可观测行为——上报）。

精炼 agent 按报告编辑项目；独立发现可分派给并行子精炼 agent、合并后再验证。循环终止于验收标准满足或预算耗尽。

### 4.4 具体制品追踪（论文 Figure 3，paho.mqtt.cpp 两例）

- **消息模型追踪**：源构造函数证据 → MRS 命名义务（topic/payload 构造、从 C MQTT 消息重建、QoS/retained setter、属性更新）→ RDS 指派 `src/message.rs`（struct Message + impl 单元）→ 初版代码缺 `from_c_message` 与若干 setter → 验证报告点名 → 修复后补全（topic 用 `Arc<str>`、`from_c_message` 拷贝 payload/properties、三个 setter 齐备、cargo 通过）。
- **客户端发布追踪**：publish API 证据链（消息创建→delivery token 注册→`MQTTAsync_sendMessage`→成功记录→失败时 token 清理）→ MRS 记为 publish/buffer/user-context/listener 义务 → RDS 路由到 `src/client.rs`（依赖 message/token/options/error/threading 五模块）→ 初版用占位发送结果 `Ok(1u16)`、回调/消费路径不完整 → 修复后 publish 走 `publish_internal`、C 回调构建 Message 并分发到 handler/callback/consumer_queue、最终门通过。

这两条追踪展示了核心机制：**源片段从不被孤立翻译——先转成命名义务、指派到文件与单元、再用来限定验证报告的范围**，使精炼 harness 能修复具体行为缺口而不丢失"这个缺口为什么重要"的源证据。

### 4.5 全景对照

| 环节 | ClaudeCode 基线 | Req2Rust |
|---|---|---|
| 保留决策 | 隐式（在模型上下文中） | **显式 MRS 义务清单** |
| 项目组织 | agent 自由发挥 | **RDS 显式设计（文件/模块/全局约束/单元）** |
| 代码生成 | 交互式整体编辑 | **骨架+并行单元生成+组装** |
| 反馈信号 | 编译/测试执行 | **编译+语义（对照 MRS）+unsafe 缩减三验证器** |
| 修复定位 | 依赖 agent 自己找 | **报告挂回义务+源证据+修复理由** |
| unsafe 观 | 无区分 | **边界 unsafe 保留 / 可缩减 unsafe 上报** |

## 五、评估指标与实验证据

### 5.1 实验设置

- **通用项目组**：7 个多文件 C++ 项目（有测试、领域多样、规模不同），每项目覆盖 7–10 个 C++ 特性类（论文 Table II 十类分类：基础声明/函数与调用语义/指针与低层内存/资源与生命周期/类与对象模型/继承与多态/模板泛型/STL/错误处理/并发）；
- **OpenHarmony 组**：5 个模块（wmserver、deviceprofile core、graphics effect、notification ans service、relational rdb），全部覆盖 10 类特性——增量迁移场景：Rust crate 替换被选 C++ 模块、其余代码库原地不动，须保留源面接口、平台调用、资源回调边界与构建假设；
- **基线**：ClaudeCode（state-of-the-art 通用 agentic coding 系统），**双方都用 DeepSeek-V4-Pro 底座**——控制了模型能力变量；未用 Cpp2Rust 做基线因其子集不覆盖全部对象；
- **指标**：Compilable（可编译性）、Test pass rate（可用测试通过率）、Unsafe rate（unsafe 占比）。

### 5.2 RQ1：通用项目迁移（Table III）

|---|---|---|---|---|
| bitsery | 33 / 6041 / 623 / 10 | 93.3% | 83.3% | 1.93% / 2.67% |
| paho.mqtt.cpp | 26 / 5379 / 666 / 9 | **100.0%** | **3.3%** | 6.83% / 0.00% |
| uriparser | 17 / 5012 / 861 / 7 | 83.3% | 93.3% | 3.22% / 0.00% |
| HFSM2 | 52 / 10859 / 415 / 9 | 66.7% | 33.3% | 0.36% / 0.00% |
| hsmcpp | 36 / 5351 / 431 / 9 | 100.0% | 90.0% | 0.93% / 0.00% |
| fkYAML | 26 / 14702 / 1747 / 8 | 100.0% | 96.7% | 0.06% / 0.00% |
| csv-parser | 33 / 6459 / 700 / 10 | 100.0% | 86.7% | 0.11% / 0.00% |
| **均值** | 31.9 / 7686 / 778 / 8.9 | **91.9%** | **69.5%** | 1.78% / 0.31% |

**双方 100% 可编译**——差距全在行为层。三个代码级案例解剖差距根源：

1. **paho.mqtt.cpp（最大差距 96.7pp）**：源暴露 byte payload 构造、retained 标志、C MQTT 消息结构重建；ClaudeCode 造了个"更 Rust"的抽象（`Vec<u8>` 构造器）但**改掉了迁移测试所用的构造器/访问器形状**、丢掉 C 消息构造路径；Req2Rust 保留 byte-slice API + `from_c_message`。
2. **HFSM2**：ClaudeCode 用泛型 `Vec<bool>` 表达活动状态；Req2Rust 用 const-generic `BitFlatSet<UNIT_COUNT>`（`[u8; N]` 存储）重建**字节背衬的固定容量位集行为**（get/set/clear/clear_all 的位级语义），覆盖运行时位访问、跨字节访问、零容量、掩码一整簇测试。
3. **fkYAML（项目结构层）**：两者都编译且通过率接近，但 Req2Rust 的 crate 有 parse/serialize/convert/io/tag/anchor/encoding 七个公共模块对应源职责；ClaudeCode 以 `YamlNode` 为中心、parser/serializer 是 crate 私有、公共迭代器里留着 `unimplemented!()`——**局部翻译 API 而不先重建项目级义务的风险的直观展示**。

注意 uriparser 上 ClaudeCode（93.3%）反超 Req2Rust（83.3%），论文诚实承认：紧凑解析导向的行为上直接 agent 迁移仍有竞争力。

### 5.3 RQ2：OpenHarmony 增量迁移（Table IV）

| 模块 | 规模（文件/行/函数） | Req2Rust | ClaudeCode | unsafe 率（Ours/CC） |
|---|---|---|---|---|
| wmserver | 117 / 18,967 / 1,009 | 83.3% | 50.0% | 0.60% / 0.00% |
| deviceprofile core | 148 / 14,630 / 676 | **100.0%** | 26.7% | 0.98% / 0.00% |
| graphics effect | 157 / 10,018 / 533 | 100.0% | 97.3% | 0.21% / 0.13% |
| notification ans service | 238 / 26,537 / 1,257 | **100.0%** | **0.0%** | 1.01% / 0.00% |
| relational rdb | 115 / 18,590 / 1,323 | 56.3% | 53.1% | 3.43% / 0.10% |
| **均值** | 155 / 17,748 / 960 | **87.9%** | **45.4%** | 1.07% / 0.03% |

**+42.5pp 的差距**，且模块规模（平均 1.76 万行）远大于通用组。两个关键案例：

1. **notification ans service（最大差距 100pp）**：源的 `DistributedDeviceStatus` 只更新 `controlFlag` 选中的状态位、把 liteWearable 更新映射到 wearable 通道，测试通过 `deviceStatus_.Find(...)` 与 `ReadVal(...)` 观测；ClaudeCode 译成简单的两参状态 map（能编译但不暴露控制位/映射面行为）；Req2Rust 用 Rust provider 抽象保留可探测的 set/get 路径。
2. **wmserver 的平台边界**：源调用 RenderService/window-token API（surface 边界更新、事务刷新、焦点应用注册、缩放变换传播）；ClaudeCode 把这些建模为本地 Rust 状态；Req2Rust 把调用隔离在 `rs_adapter.rs`/`token_adapter.rs` 等显式适配模块、unsafe 包裹 FFI 调用。**unsafe 率更高（0.60% vs 0.00%）但这反映的是被保留的平台边界**——增量迁移中 Rust 要复用周边系统而非隔离重建，这些 unsafe 是必要的 ABI/FFI 通道。这颠覆了"unsafe 越少越好"的单一叙事：**指标必须相对迁移语境解读**。

### 5.4 RQ3：消融研究（Table V，7 个通用项目）

| 变体 | Build | Tests | Unsafe |
|---|---|---|---|
| Full Req2Rust | 7/7 | **91.90%** | 1.7757% |
| 无语义验证器 | 7/7 | **28.10%** | 1.3227% |
| 无 unsafe 缩减 | 7/7 | 91.90% | **4.9950%** |
| 仅初始 Rust 项目 | **0/7** | 0.00% | 3.3392% |

三个决定性读数：

1. **语义验证器是行为收益的支柱**：去掉后测试通过率雪崩 **−63.8pp**（91.90→28.10），尽管仍 100% 可编译——编译器只能保证"是合法 Rust"，语义验证器才保证"是行为等价的 Rust"。机理案例（Figure 9）：无语义变体中 token 完成只记结果+唤醒等待者，但**漏掉回调调用与从客户端移除已完成 token**——这些跨文件完成效应只有对照 MRS 才能发现；完整版恢复 `listener.on_success(self)` 与 `remove_self_from_client()`。
2. **精炼闭环不可或缺**：初始 Rust 项目 **0/7 可编译、0% 测试通过**——骨架+并行生成产出的"拼图"必然有缝，验证器引导的精炼才是把拼图变成可执行迁移结果的过程。这也反证了"把初始项目当可执行精炼状态"设计的合理性。
3. **unsafe 缩减独立有效**：去掉后 unsafe 率从 1.7757% 涨到 4.9950%（+3.2pp），测试通过率不变 91.90%——它改善安全画像而不伤行为，与语义验证器**正交**。机理案例（Figure 10）：uriparser 的文本范围构造从裸指针算术（`as_ptr().add(...)`）改为基于输入索引的安全 helper `TextRange::from_indices`。

### 5.5 实验设计如何支撑主张

- 同底座（DeepSeek-V4-Pro）对比 ClaudeCode，隔离"harness 设计"这一变量；
- Compilable/Test/Unsafe 三指标 + 逐项目代码级案例解剖（Figure 4–10），既有聚合数字又有机制证据；
- 消融的四个变体恰好切在流水线的三个关节上（语义验证、unsafe 缩减、整个精炼环），每个组件的边际贡献可分离；
- 效度威胁一节明确承认：行为 oracle 只覆盖公共 API 与选定行为，不证明完全语义等价；结果对模型/提示/运行时决策敏感。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**根源一：显式义务清单消除了"保真决策"的隐式性，而隐式保真是 agent 迁移失败的主要模式。**

因果链：C++ 关键行为跨文件分布且只在交互中显形 → 直接 agent 迁移中"保什么"由模型隐式决定 → 模型偏好目标语言惯用形（"更 Rust"），系统性地漂移迁移面 API 形状（`Vec<u8>` 取代 byte-slice、向量取代位集、简化状态 map 取代控制位协议）→ 测试通过率坍塌。MRS 把保真决策前置于代码生成、语言中立化 → 生成与修复全程有可对照的义务锚点。**论文实验已支持**：paho.mqtt.cpp（100.0 vs 3.3）、notification ans service（100.0 vs 0.0）两个最大差距案例的代码级解剖都展示同一机理；消融中去掉"对照 MRS"的语义验证器掉 63.8pp。

**根源二：编译器只能验证"合法"，行为等价需要独立 oracle——而 MRS 恰好提供了这个 oracle 的载体。**

因果链：无语义验证的变体仍 100% 可编译但只有 28.10% 通过 → 可编译性与行为保真是两个几乎正交的维度 → 语义验证器以 MRS 为对照面，能发现编译器永远看不见的"静默行为缺失"（回调未调用、token 未清理）→ 报告挂回义务+源证据，让修复有的放矢。**论文实验已支持**（Table V + Figure 9）。

**根源三：把初始产出定位为"可执行精炼状态"，让 harness 用执行证据补足生成盲区。**

因果链：项目级重建的细节（跨单元接口咬合、构建假设）只有在编译/验证时才可见 → 追求"一次生成成功"不可行（初始项目 0/7 可编译） → 骨架+并行生成负责结构与覆盖、精炼环负责咬合与修正 → 分工让两类问题各自在擅长的阶段被解决。**论文实验已支持**：0/7→7/7 的编译转化。

**根源四：unsafe 的"好坏"取决于它守的是什么边界。**

因果链：独立重写中 unsafe 越少越好；增量迁移中 Rust 必须继续调 C/C++ 平台服务（RenderService、window token、SQLite、OS helper）→ 边界 unsafe 是复用周边系统的通道、应保留并隔离在适配模块；可缩减 unsafe 才应消除 → Req2Rust 的 unsafe 率高于 ClaudeCode（1.07% vs 0.03%）却伴随 +42.5pp 的行为保真——ClaudeCode 的低 unsafe 部分来自"把平台调用改写成本地状态"的行为丢失。**论文实验已支持**（Table IV + Figure 8）。**阅读者推测（标注）**：适配模块化 unsafe（rs_adapter.rs 等）还便于未来审计与渐进 safe 化，论文未做此后续实验，此为设计意图层面的推断。

### 6.3 综合判断与未决问题

- **多证据共同支持**：①显式保真建模优于隐式推断（两大案例 + 消融 63.8pp + 外部实证研究同向）；②编译与行为是正交维度（无语义变体 7/7 可编译 vs 28.10%）；③验证证据决定修复上限（与 Sactor/Vert 一致）。
- **仍属推测**：MRS 提取本身的完备性——若需求规划 agent 漏掉某义务，后续全链路都无法发现（"开放迁移项"机制只是部分缓解）；论文效度威胁一节也承认测试不证明完全等价。
- **适用边界**：uriparser 反例说明紧凑解析型项目上通用 agent 可竞争力十足；模板重度、奇异构建系统或稀有语言特性的项目泛化未知；结果绑定 DeepSeek-V4-Pro，换模型绝对值会变。
- **可能失效条件**：项目义务超出 MRS 分类学（如高度时序敏感行为、未测试路径）；平台耦合极强导致边界 unsafe 占比过高时，"缩减"空间有限；agent 变异性（提示措辞、工具轨迹）带来的运行间方差。

## 七、必要知识反推

### 7.1 领域知识层

- **C++ 隐式语义地图**：对象模型、构造/析构生命周期协议（RAII）、模板实例化、重载解析、回调、资源所有权约定、构建期约定——不知道这些"藏行为的地方"，就写不出 MRS 的分类学；
- **Rust 所有权/借用模型与 crate 生态**：模块组织、公开面设计、FFI/ABI 边界、unsafe 的语义——不知道"Rust 式重建"的选项空间，RDS 就无从设计；
- **内存安全漏洞的分类与治理谱系**：越界/UAF、sanitizer、加固、内存安全语言运动的政策背景（NSA/CISA）。

### 7.2 方法论知识层

- **需求工程思维**：义务（obligation）建模、规约语言、可追踪性（traceability）——MRS/RDS 的覆盖链接本质是经典需求追踪矩阵的翻版；
- **软件迁移研究脉络**：源保持式 vs 重建式的张力、C2Rust 系的精炼技术（unsafe 缩减、所有权推断、别名分析）；
- **LLM 代码翻译的失败模式**：语义 bug、类型/API 不匹配、源目标语义鸿沟——知道模型怎么错，才能设计验证器去抓；
- **Agentic 系统设计**：可执行状态、验证-修复循环、并行子 agent 的分派与合并、预算控制。

### 7.3 工程知识层

- **构建系统与验证工具链**：cargo/cargo check、gtest、编译错误定位——三验证器的实现基座；
- **大规模真实代码库的增量迁移约束**：OpenHarmony 式"替换模块、保留周边"的接口兼容、平台调用、构建假设；
- **评测设计**：特性分类学（10 类）用于刻画基准难度、三指标体系、同底座控制变量。

### 7.4 知识融合的关键节点

1. **转译节点**：把软件工程的"需求规约/追踪"经典方法（需求工程）嫁接到 LLM 迁移（新问题域）——产生 MRS 这一语言中立契约层，是全文最具创造性的融合。
2. **分工节点**：结构化规划（RDS/骨架）与并行生成、执行反馈精炼的三段分工——承认"生成不可能一次对"，把错误消化移到证据最充分的阶段。
3. **语境化节点**：对 unsafe 指标做语境化解读（边界 vs 可缩减）——拒绝把"unsafe 率低"当普适优点，这需要对增量迁移工程现实的深刻理解。

## 八、论文中可以提取的通用性灵感

### 灵感一：把"什么不能变"从模型上下文里拉出来，做成显式契约

- **核心思想**：当任务同时包含"保真约束"与"自由重建"两种冲突要求时，先显式抽取约束清单（语言/框架中立的中间制品），再让重建在其约束下进行，可大幅减少系统性漂移。
- **论文证据**：MRS 使 paho.mqtt.cpp 从 3.3% 到 100.0%；ClaudeCode 的失败模式恰是"为像 Rust 而改掉迁移面 API 形状"。
- **推广场景**：数据库 schema 迁移（先列兼容性义务再重设计）；API 大版本升级（先冻结行为契约再重构实现）；UI 改版（先定义用户操作路径不变量）；合规系统改造（先固化监管义务再技术选型）。

### 灵感二：验证维度要与失败模式一一对应，编译通过 ≠ 目标达成

- **核心思想**：每种验证器只覆盖一种失败面（编译器→语法/类型；语义 oracle→行为；安全分析→unsafe），多验证器正交组合才能覆盖多目标。
- **论文证据**：无语义验证器 7/7 可编译但 28.10% 通过率；unsafe 缩减只动安全率不动通过率——三者贡献完全解耦。
- **推广场景**：代码生成的"编译+测试+风格"三关；内容生成的"语法+事实+安全"三审；自动驾驶仿真的"可行驶+交规+舒适"多层验收；金融模型的"数值稳定+监管合规+业务正确"分层验证。

### 灵感三：把首次产出定位为"可执行精炼状态"而非终稿

- **核心思想**：复杂系统的一次性生成必然有缝，正确的架构是"结构化初稿 + 证据驱动的精炼闭环"，而不是追求一次到位。
- **论文证据**：初始 Rust 项目 0/7 可编译，精炼后 7/7 且 91.9%——初稿的价值在结构与覆盖，精炼的价值在咬合与修正。
- **推广场景**：文档起草（大纲→初稿→审校环）；芯片设计（RTL→综合→时序收敛环）；产品设计（原型→用户测试→迭代）；数学证明（骨架→引理填充→审查）。

### 灵感四：指标的善恶取决于语境——unsafe 率的双面性

- **核心思想**：同一个量化指标在不同部署语境下含义相反（独立重写中 unsafe 是债、增量迁移中 unsafe 是必要的互操作通道）；好的系统应区分"守边界的 unsafe"与"可消除的 unsafe"。
- **论文证据**：Req2Rust 在 OpenHarmony 上 unsafe 率 1.07% 高于 ClaudeCode 的 0.03%，但行为保真高 42.5pp；ClaudeCode 的"干净"部分来自把平台调用改写成本地状态的行为丢失。
- **推广场景**：技术债指标（框架内的 hack vs 集成边界的适配层）；模型参数量（过参数化 vs 容量必需）；测试覆盖率（为覆盖率写的空测试 vs 真行为测试）；代码行数（膨胀 vs 必要显式性）。

### 灵感五：先分解设计再并行生成，用全局约束防"局部最优拼盘"

- **核心思想**：并行生成单元级产物前，必须先有携带全局约束（共享数据结构、错误处理约定）的设计层，否则各单元各自"翻译得好"却拼不成 coherent 项目。
- **论文证据**：RDS 的全局设计约束（通用数据结构/错误处理/资源所有权约定）显式防止"把每个源片段当孤立翻译任务"；fkYAML 案例中公共模块边界对应源职责。
- **推广场景**：微服务拆分前的领域契约定义；多团队并行的接口先行；多 agent 协作的 shared scratchpad 约束；模块化产品设计的总线规范。

### 灵感六：修复要携带"为什么重要"的证据链

- **核心思想**：验证报告不止指出"哪里错了"，还要挂回义务条目与源证据——修复 agent 因此能判断修复方案是否满足原始意图，而非只让检查通过。
- **论文证据**：语义验证报告连接"潜在分歧→保真义务→Rust 位置→源证据→修复理由"五元组；Figure 9 修复恢复了回调调用+token 清理两个"测试外可见"的完成效应。
- **推广场景**：code review 评论附需求链接；CI 失败附规格条目；客服工单附用户原始诉求；法务审查附条款依据。
