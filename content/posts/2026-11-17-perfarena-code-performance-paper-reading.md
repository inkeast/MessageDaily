## 一、论文背景

### 1.1 LLM 已经在写全世界的代码，但我们只检查它"对不对"

2025 年，微软报告其 20–30% 的代码由 AI 生成；Google 在 2024 年底报告该比例超过 25%，2026 年达到 75%。当开发者的实现工作越来越多交给 LLM，**线上软件的效率就越来越取决于 LLM 写出的代码的效率**。可现实是：社区评判 LLM 代码的标准几乎只剩下"功能正确性"。

这里需要理解主流评测范式的来历：

- **HumanEval（2021）** 奠定了函数级评测的基本形态：给 LLM 一个函数签名和文档字符串，生成代码后跑一组单元测试，通过即成功，指标叫 **pass@k**（采样 k 次、至少一次通过的概率）。它像一场"及格制考试"——60 分和 100 分都算过。
- **EvalPlus（NeurIPS 2023）** 发现很多"看起来对"的代码其实有隐藏缺陷，于是加强测试套件来揭穿伪正确解。
- **LiveCodeBench（ICLR 2025）** 为了对抗训练数据污染（题目早被背下来了），持续加入新发布的题。

这条脉络的全部精力都花在"把正确性测得更严"上，**运行成本从来不进入评分**。与此同时，前沿模型在 LeetCode 类题集上的 pass@1 已普遍超过 90%——正确性基准趋近饱和，区分度自然消失。本文的实测也印证了这一点：13 个 LLM 中 12 个在 99 道 LeetCode 题上正确率超过 90%。

### 1.2 为什么 LLM 写的代码格外可能低效

论文引用作者自己的前作：LLM 生成的 Android 应用中，性能反模式（performance anti-pattern，即低效的代码写法）密度是人类等价物的 **10 倍**，作者称之为 "performance loop of hell"（性能地狱循环）——恶性循环的机制是：

1. LLM 从人类代码中学习，而人类代码本来就很少优先考虑性能；
2. LLM 厂商的优化目标又几乎只有功能正确性；
3. 于是 LLM 产出的低效代码被下一次训练继续学走， inefficiency 被循环放大。

此外多项研究指出 LLM 擅长"分析"和"优化"性能的结论并不乐观。这意味着：**低效不只是一时的工程瑕疵，而是被当前训练范式系统性强化的偏差**。

### 1.3 已有"效率基准"为什么还不够

近年确实出现了一批效率导向的基准，但各有缺口：

| 基准 | 测什么 | 缺什么 |
|---|---|---|
| EffiBench（NeurIPS 2024） | 延迟、峰值内存 | 单语言（Java），无能耗 |
| Mercury（NeurIPS 2024） | 延迟 | 无能耗、无内存 |
| ENAMEL（ICLR 2025） | 延迟 + eff@k 指标 | 无能耗、无内存 |
| EvalPerf（COLM 2024） | CPU 指令数（代理指标） | 不实测真机延迟/内存/能耗 |
| EffiBench-X（NeurIPS 2025） | 延迟、内存 × 6 语言 | 无能耗 |
| EnergyBench（FLTA 2025） | 正确性 + 能耗 | 关注 prompt 敏感性，非持续排名 |

更早的一批实证研究（Islam、Cursaru、Solovyeva、Apsan 等）各自测过 LLM 代码的能耗，但任务集、硬件平台、测量协议互不相同，**结果无法互相比较，每出一个新 LLM 都得把整个研究重做一遍**。

于是论文指出了真正的缺口：效率评测缺少正确性评测已经拥有的东西——一个**共享的竞技场**：对每个解同时报告功能正确性、延迟、峰值内存和能耗，让新发布的 LLM 可以直接和前辈同台竞技，而不必重跑整个研究。

## 二、论文定位和关联工作

PerfArena 站在三条研究脉络的交汇处：

### 2.1 谱系一：代码生成正确性基准 → 效率基准

HumanEval 确立 pass@k 范式后，EvalPlus 强测试、LiveCodeBench 抗污染、NoFunEval 把考察面扩展到效率/安全/可维护性等非功能需求（发现功能强的 LLM 在非功能需求上普遍翻车）。效率专项基准中：EffiBench 测 Java 延迟与内存；Mercury/ENAMEL 测延迟，ENAMEL 提出 eff@k（把 pass@k 从"对不对"扩展到"快不快"）；EvalPerf 用指令数作代理规避延迟测量噪声；COFFE 也数指令；PIE 干脆在 gem5 模拟器里计时（因为作者发现在真机上 identical 程序竟能测出 1.12× 的假加速）；GSO/SWE-Perf/SWE-fficiency 把任务搬到真实仓库（测 LLM 能否给出保正确又提速的补丁，GSO 发现 LLM 在 C/C++ 等低级语言上特别挣扎）；KernelBench 则要求生成更快的 GPU kernel。

**关键区别**：这些基准要么单语言、要么用代理指标、要么是固定快照。PerfArena 直接上真机实测三指标、七语言、持续更新。

### 2.2 谱系二：竞技场（Arena）形态

- **Chatbot Arena**：人类投票两两比较，Bradley-Terry 模型把偏好转成排名；
- **MathArena**（NeurIPS 2025，PerfArena 名字即致敬它）：不用人类投票，以数学竞赛的标准答案自动判分，用题目新鲜度对抗污染；
- **Copilot Arena**（ICML 2025）：把竞技场搬到代码补全，但以开发者"接受哪个补全"为信号，**不执行代码、不测性能**。

**关键区别**：PerfArena 借 Chatbot Arena 的两两对决 + Bradley-Terry 排名机制，但每场对决由**测量结果**裁决而非人类投票；借 MathArena 的自动判分与持续更新，但比的是性能。且每场对决严格限定在"同一题×同一语言"的固定赛格内。

### 2.3 谱系三：跨语言能耗测量

Pereira et al.（2017/2021，SLE/SCP）用 RAPL 硬件计数器实测 CLBG 上多语言的延迟/内存/能耗，发现最快与最慢语言能耗差近两个数量级——**语言本身的影响可能淹没模型差异**，这是 PerfArena 坚持"只在同一语言内比较"的直接原因。其测量框架（隔离环境、专用基准机）被 PerfArena 继承（MIT 许可）。后继 Kempen et al.（ASE 2025）用因果模型发现控制实现后语言实现对能耗无显著独立影响；Koedijk et al.（ICT4S 2022）则指出更短的运行时间不一定更省电——能耗与延迟的关系至今仍有张力，PerfArena 选择分指标单独报告而非合成单一分数。

### 2.4 定位总结

| 维度 | 之前的路线 | PerfArena 的突破 |
|---|---|---|
| 评分对象 | 正确性（pass@k）或单一效率代理 | 正确性门槛 + 延迟/内存/能耗三指标实测 |
| 语言覆盖 | 多为单语言（Python/Java），至多 6 语言 | 7 语言（GitHub Top8 去 Shell） |
| 排名机制 | 固定快照、算术平均 | 同 cell 对决 + Bradley-Terry + Pareto 分层，持续更新 |
| 可复现性 | 各自为政 | 每条测量盖章记录机器/能耗工具/运行 ID，全链路 provenance |
| 形态 | 一次性论文 | 开源平台 + 在线排行榜，新 LLM 一次 sweep 即可入榜 |

一句话定位：**PerfArena 把代码效率评测从"每篇论文各测各的"升级为"共享赛制、持续运行的竞技场"**，就像 Chatbot Arena 之于聊天模型。

## 三、问题定义

### 3.1 从具体场景到抽象问题

具体场景：给定一堆 LLM、一堆编程题、一堆语言，怎么公平地回答"谁写的代码跑得最快、最省内存、最省电"？

这件事的敌人有三个：

1. **测量噪声**：毫秒级的计时受进程启动、频率调度、缓存状态干扰；能耗读数有精度下限。
2. **混杂变量**：题目难度、语言快慢、运行时开销都会淹没"模型写代码的能力"这一目标变量。
3. **不可比性**：不同研究用不同机器、不同测试输入，数字放不到一张表里。

核心洞察：论文发现这场比较的本质结构是**体育联赛**——选手（LLM 解）之间的比较只有在"同一场地、同一规则"下才有意义。于是抽象出：

### 3.2 形式化定义

定义**赛格（cell）**= 一道题 × 一种语言。给定：

- LLM 集合 $\mathcal{M}$（13 个）、问题集 $\mathcal{P}$（99 + 10 题）、语言集 $\mathcal{L}$（7 种）；
- 每个 LLM 在每个赛格生成一个解 $s_{m,p,l}$；
- 正确性判定函数 $C(s) \in \{0,1\}$（正确性 oracle）；
- 测量函数 $F(s) = (\text{latency}, \text{peakMem}, \text{energy}) \in \mathbb{R}^3_{+}$（性能 oracle）。

求：基于 $\{F(s_{m,p,l}) : C(s_{m,p,l})=1\}$ 的、对 $\mathcal{M}$ 的稳健排序，满足：

1. **正确性硬门槛**：$C=0$ 的解不进入性能排名（避免"错误程序骗取效率冠军"），以 pass@1 单独报告；
2. **同格对决**：只在同一 $(p, l)$ 内比较两个解；
3. **噪声感知**：差异小于测量噪声判平局，不奖励噪声。

排序模型选用 **Bradley-Terry**：给每个 LLM 一个强度 $\beta_m$，胜率 $P(i \text{ beats } j) = \beta_i / (\beta_i + \beta_j)$，由全部对决结果拟合。

### 3.3 这个抽象的精妙之处

- "同格对决"一次性消灭了语言与题目两个最大混杂变量——这正是 Pereira 谱系十年教训的浓缩；
- 平局阈值不是拍脑袋，而是由测量统计（95% 置信区间）推导，让"排名"自带误差棒；
- 正确性与性能解耦报告，避免把"会做题"和"做得优雅"混为一谈——论文后面的核心发现正依赖这一点。

## 四、问题解法

PerfArena 的技术方案可以拆成五个组件。整体架构：REST API 调度 + 数据库 + Web 排行榜；提交先过正确性 oracle（步骤 4–5），只有 Accepted 才进入性能测量（步骤 6–7）——两条边界（先正确后测性能；只在 cell 内比较）贯穿全流程。

### 4.1 竞赛构建：选出"能分出快慢"的题

**类比**：体育比赛要选"能拉开差距"的项目——让所有运动员都跑 3 秒结束的短赛道没有区分度。

LeetCode 大部分题太轻（判断回文词等微秒级完成，快慢解的差异小于测量噪声）。PerfArena 的筛选流程：

1. **收集延迟分布**：向 LeetCode GraphQL API 查询每题历史通过解的延迟直方图，算出 P10/P50/P95 分位数；
2. **过滤可测题**：中位数延迟 ≥ 10 ms、P95−P10 差 ≥ 10 ms、分布覆盖 ≥ 15 个桶；
3. **排名区分度**：按 P95/P10 比值排序（该比值消除了测试用例数量的影响——它衡量"慢解比快解慢几倍"，即算法选择对延迟的影响强度），每个难度档保留前 33 题。

最终从 1,973 题筛出 99 题（886 过阈值 → 去 22 道付费题 → 每档取 33）。CLBGComp 则直接取 CLBG 的 10 个计算密集基准（binary-trees、n-body、fasta 等），并把每题的工作负载参数校准到测量机上：C++ 参考程序须跑 ≥ 1 秒（高于能耗计数器噪声底），Python 须在 1200 秒作业上限内完成（实测中位 Python 解跑 binary-trees 比中位 C++ 解慢约 51 倍，两个约束的夹缝就是校准空间）。

### 4.2 测量工作负载：SimPoint 式指纹聚类

**类比**：考试不必把题库每道题都做一遍——挑出覆盖每种"题型"的 representative 即可，再按题型出现频率加权。

对 LeetCodeComp 的 8,103 个候选测试用例（每题 ≤ 100 个）：

1. **行为指纹**：在裸金属机上用 perf + RAPL 跑每个用例 0.3 秒，记录 6 个硬件计数器（指令数、周期、分支、分支缺失、缓存访问、缓存缺失）的对数向量 + 缓存缺失率、分支缺失率、IPC；
2. **归一化 + PCA**（保留 90% 方差）防止大数值计数器碾压小数值的；
3. **k-means 聚类**（簇数由 silhouette 分数选定），同簇用例干同样的活 → 只保留离质心最近的 medoid；
4. **附加规则**：额外保留全题能耗最高的用例（低效解的真实代价要靠最重输入暴露）；不足 5 个用例的题用 maximin 策略（每次选与已保留集合最不相似者）补到 5；
5. **加权**：每个被丢弃的用例归入它最像的保留用例，权重 = 归属比例，各题权重和为 1。

结果：8,063 个 profile 过的用例只保留 501 个（6.2%），中位数每题 5 个、至多 8 个。验证：在 20 个 cell 上用全部用例重测，保留集只让 1.5% 的延迟对决、0.6% 的能耗对决翻盘。

跨语言复用：所有语言读同一份 JSON 输入文件（输入无需翻译）；题解骨架、harness、构建脚本由 Claude Opus 4.8 从 Python 翻译生成，逐用例对照 LeetCode judge 校验，错则重生成。

### 4.3 正确性验证：严格的裁判 + 防误判审计

LeetCodeComp 用 LeetCode 在线 judge（或离线 harness）；CLBGComp 用自建 oracle 比对 C++ 参考输出。关键细节是**防误判审计**——直接逐字节比对会冤枉正确解，PerfArena 依次放宽：空白/大小写归一化、独立行的顺序无关（并行解可能乱序输出）、浮点容差 10⁻⁶（n-body 等求和顺序问题）、mandelbrot 位图允许 ≤16 字节差异（集合边界的浮点舍入语言差异）。审计过程带来 21 处比对机制修复。同时防"作弊解"：跑得比同格中位数快 2 倍以上的解被标记人工审查——这次 campaign 抓到 5 个（如一个 Python n-body 解用 FFI 调 C 编译产物，快 64 倍；4 个 binary-trees 解用公式直接算校验和、从不建树，快 22–262 倍），全部移出性能排名与参考集，但仍计入 pass@1。

### 4.4 性能测量：统一协议下的三指标实测

**LeetCodeComp 的每调用 harness**（一次调用可能只有微秒级，进程启动开销会淹没它）：

- 1.5 秒预算内：前 30% 反复调用预热（让缓存和 JIT 稳定），后 70% 计时窗内数调用次数；
- 每次调用结果折叠进 checksum，防编译器死代码消除（DCE）；C++ harness 额外加优化屏障防编译器把重复调用优化成一次；
- 能耗工具（CodeCarbon）包裹整个 harness 进程，按计时窗时间占比折算窗内能耗；
- 延迟/能耗 = 窗口值 ÷ 调用次数；每题取测试用例的加权平均；峰值内存单独一趟测（读内核 `ru_maxrss`），避免内存记账干扰计时。

**CLBGComp 整程序测量**：先跑一次热身（文件进缓存），再多次完整运行计时（含运行时启动成本，因为这正是整程序的真实代价）。

**测量纪律**：

- 专用裸金属机（i7-7600U、Ubuntu 22.04、开 RAPL），单任务串行，任一核占用超 60% 拒绝开测；
- 每个延迟/能耗测量重复 **7 次**，中位变异系数 1.3%（LC）/2.8%（CLBG），95% 置信区间压到 ±1.2%/±2.6%；
- 能耗优先用 Intel **RAPL** 硬件计数器（约每毫秒更新一次，对 ≥1.05 秒的测量窗误差 ≤0.1%），无 RAPL 时退回软件功耗模型；CodeCarbon 的恒定 RAM 估计功率（10 W）被减去只留 package 能耗；
- 编译在计时区外完成，编译器 flag 变化即新测量档案；
- **每条测量记录盖章**：机器、能耗工具、运行 ID——排行榜上每个数都能追溯到产生它的硬件与工具。

顺带一个重要的实证发现：LeetCode judge 自己报告的延迟并不可靠——同一程序 5 次提交，最大/最小读数比值中位数 1.26、最坏 8.5。这正是自建性能 oracle 的动机。

### 4.5 排名：Bradley-Terry + Pareto 分层

- **对决**：两个 LLM 在共同解出的每个 cell 各赛一场，值低者胜；差异小于噪声判平（各半分）。平局阈值由测量统计推出（如 LC 延迟 1.7%、能耗 3.7%，内存按语言 0.7%–9.8%）；
- **BT 拟合**：MM 算法拟合强度，报告**胜率**（win probability，对其他 LLM 的平均取胜概率，50% 即平均水平）；
- **比值（ratio）**：每个解除以该 cell 参考解（本次 campaign 中该格该指标的最佳正确解）的值，取几何平均——衡量"离最好差多远"，1.0 即最佳；
- **统计检验**：LLM shuffle 置换检验（模型间是否真有差异）+ bootstrap 重采样（哪些配对显著不同）+ Holm 多重校正；
- **Pareto 支配**：三指标无公共单位，也不该预设权重（云端在乎延迟、移动端在乎能耗、容器在乎内存）——若 LLM A 在至少一项显著优于 B 且无一项显著更差，则 A 支配 B。被支配者在任何加权下都劣，非支配集（Level 1）对每种部署场景都包含了最优选择。

## 五、评估指标与实验证据

### 5.1 实验设置

- **选手**：13 个 LLM、6 家厂商（OpenAI gpt-6-astra/5.6-sol/5.6-luna/5.5/5.4-mini，Anthropic claude-opus-5-5/opus-4-8/sonnet-5-5/fable-5-1，Google gemini-3.8-flash，DeepSeek deepseek-v4.1-flash，xAI grok-4.6，Zhipu glm-5.3-flash），价格从 $0.2/1M 到 $10/1M 输入 token；
- **统一 prompt 模板**（锁死函数签名形状）+ 每格单样本；尽量请求温度 0（实际只有 grok-4.6 与 glm-5.3-flash 生效，各家 reasoning API 不接受）；
- **语料**：9,455 个正确且完成测量的解；
- **成本**：整个 campaign 生成花费 $162（1,970 万响应 token），验证+测量 291 小时，全程约 15 天；平均加入一个新 LLM：LeetCodeComp $8.11/22 小时，CLBGComp $4.35/5 小时——**测量（而非生成）占了大部分时间**。

### 5.2 核心结果对照三个研究问题

**RQ1：单项指标谁最强？**

| 指标 | LeetCodeComp | CLBGComp |
|---|---|---|
| 延迟 | gpt-6-astra（62%）、claude-opus-5-5（58%）并列领先 | gpt-6-astra 72%（与 7 个 LLM 并列） |
| 能耗 | gpt-6-astra（61%）、claude-opus-5-5（58%）、gemini-3.8-flash（56%）并列 | gpt-6-astra 72% |
| 峰值内存 | **无显著差异**（全员 49–51%，p=0.09）——语言运行时占了内存大头 | gpt-6-astra 65%（仅 5/78 配对可分） |

**RQ2：三指标合起来谁最强（Pareto）？**

gpt-6-astra 在两个竞赛中都是**唯一非被支配 LLM**（LC 上支配 11 个对手，CLBG 上支配 10 个）；LC 的 Level 1 还有 claude-opus-5-5，CLBG 的 Level 1 还有 glm-5.3-flash 与 gemini-3.8-flash。垫底的：LC 是 grok-4.6 与 claude-opus-4-8，CLBG 是 claude-opus-4-8、gpt-5.6-luna、deepseek-v4.1-flash。

**"正确 ≠ 高效"的直接证据**：

| 发现 | 数据 |
|---|---|
| 正确率饱和 | LC pass@1：88.5%（gpt-5.4-mini）→ 99.7%（gpt-6-astra），12/13 超过 90% |
| 正确解的速度差 | 其他 LLM 的正确解平均延迟是 gpt-6-astra 的 **1.14–1.61×**（LC）、**1.20–3.61×**（CLBG） |
| 正确性与速度脱钩 | LC 上 pass@1 与延迟胜率相关但不显著（ρ=+0.59，未过 Holm 校正） |
| 语言改变领跑者 | LC 上 claude-opus-5-5 在 Python/PHP 领先，gpt-6-astra 领先其余五语言；但正确性跨语言高度一致（89.7% 的 LLM-题对在全部 7 语言判决一致） |

**RQ3：贵 = 快吗？**

- gpt-6-astra 每 token 单价属于最贵档，但每正确解成本 $0.011（LC）/$0.039（CLBG），因为它的正确率最高、token 最省（LC 每解 321 token，全场最少之一）；
- LC 上最贵的 claude-fable-5-1、gpt-5.5 每正确解成本是 gpt-6-astra 的 2.6×/2.5×，代码却不更快；CLBG 上最贵的 glm-5.3-flash 达 9.3×，代码也不更快；
- 反向的便宜陷阱：gpt-5.6-luna、gpt-5.4-mini 每正确解便宜 8–12 倍，但代码慢 1.23×（LC）到 3.61×（CLBG）；
- CLBG 上成本与速度正相关（ρ=+0.81），但主要由四个最便宜也最慢的模型驱动；LC 上完全无关（|ρ|≤0.33）。

### 5.3 这些实验为什么能证明论点

- "正确 ≠ 高效"不是抽样印象，而是 9,455 个解在噪声感知排名下的系统性差距，且经过置换检验（LLM 间延迟/能耗差异 p<0.001）与 Holm 校正的配对检验背书；
- "贵 ≠ 快"同时从两端论证（贵的不更快 + 便宜的不白便宜），并拆解了成本（token 数 × 单价 ÷ 正确解数）让读者看清 gpt-6-astra 的优势来自"一次做对"而非单价；
- 单 host 测量避免了跨机混杂，代价是外推性受限（作者在效度威胁 E1 中自己承认）。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

PerfArena 的"效果"体现为：它能稳定区分正确率几乎相同的 13 个 LLM（延迟维度分出 42/78 个显著配对），而此前任何正确性基准都做不到。为什么这套设计**结构上必然**有这个区分力？因果链如下：

1. **正确性门槛把"无效解的假效率"清零**（论文实验支持）：错误程序可以任意"快"（少干活），不过门槛就参赛，性能排名才不被污染。反例证据：5 个走捷径的"正确"解（FFI 调 C、公式算校验和）被抓出后剔除，说明没有审计的正确性同样会漏假效率。
2. **同 cell 对决剥离语言与题目混杂**（论文实验支持）：Pereira et al. 证明语言间能耗可差两个数量级；若跨语言聚合，一个 LLM 可能仅因"常在 C++ 出赛"而登顶。PerfArena 的胜率对每位对手只在其共同解出的 cell 内计算，失败不奖不惩（以 pass@1 另行报告），模型实力与出勤模式解耦。附录里有一个精彩反证：若改用"对参考解比值的几何平均"跨 cell 排名，gpt-5.4-mini 会凭"只做简单题"冲到延迟第二——正是同格对决堵住了这条作弊路径。
3. **测量噪声被压到与解间差距可分离的水平**（论文实验支持）：重复 7 次 + 专用静默主机 + 预热协议，把单解变异系数压到 1.3–2.8%，而中位 cell 内最快与最慢正确解差 2.1×（LC）/4.3×（CLBG）——信噪比足够，对决才判得动。对照：LeetCode judge 自身读数的最大/最小比值中位就有 1.26，直接用它的数字会大面积误判平局。
4. **平局阈值从噪声推导而非固定常数**（论文实验支持）：让排名对噪声透明——这解释了为什么 LC 峰值内存全员 ~50%（读数噪声相对解间差异太大），诚实的"测不出差异"好过虚假的名次。
5. **能耗排名紧随延迟（ρ=0.91/0.97）的机制**（论文实验支持）：每调用能耗 ≈ 延迟 × harness 进程平均功率，而 90% 解的功率集中在 13.1–16.0 W 的窄带——所以 LC 上能耗区分度继承延迟区分度。这既是设计的自然结果，也提示在功率差异大的场景（如 CLBG 上双核满载的最快解）能耗才可能脱离延迟独立说话（附录 I：CLBG 上 13/13 个 LLM 的能耗比值低于延迟比值）。

以上 1–5 全部由论文内部实验支撑；下面转向外部检索交叉验证。

### 6.3 综合判断与未决问题

**多项研究共同支持的机制**：

- 正确性 ≠ 效率（EvalPerf、COFFE、Niu 与本文四路一致）；
- 效率差异真实且可测（EffiBench 系列、Islam 等）；
- 能耗必须实测且与延迟关系不稳定（EnergyBench、Koedijk、Kempen）；
- 语言内比较是硬前提（Pereira 谱系）。

**仍属合理推测或单源支撑的部分**：

- LC 上峰值内存"无差异"归因于语言运行时占大头——机制合理（harness 进程级 ru_maxrss），但论文未直接分解运行时/解的内存占比，属阅读者推断的合理假设；
- 7 次重复 + 1.5 秒预算在更长任务上的充分性（C# 预热不足 3.1% 的偏移已被作者量化并证明不改排名，但这是 10 题抽样上的结论）。

**优势成立条件与可能失效条件**：

- 成立条件：同题同语言、同硬件同工具链、测量噪声低于解间差距（本文中位 cell 差 2×+，噪声 1–3%）；
- 可能失效：(a) 换硬件——Apsan 等表明相对能效可翻转，PerfArena 单 host 排名是"该测量档案下的真相"；(b) 训练数据污染——LeetCode/CLBG 题目及最优解公开，LLM 可能在背答案而非推理（作者在 E3 承认，EffiBench/本文均无法检测记忆复用）；(c) 公开题库固化——若前沿 LLM 全员背下最优解，区分度将消失，届时需换私有/新生成题；(d) 温度未统一——11/13 个 LLM 以默认温度采样，单样本排名存在抽样波动（I5），作者以"每排名建立在至多 99×7 场对决上"自我辩护，未做多样本方差分析。

## 七、必要知识反推

假设让一个零基础的人重做这项工作，TA 必须掌握：

### 7.1 领域知识层

- **代码生成评测范式**：pass@k 的定义与缺陷、污染问题（EvalPlus/LiveCodeBench 的应对）——不理解"正确性已饱和"就找不到选题动机；
- **LLM API 生态**：OpenAI 兼容接口、各厂温度参数的实际接受情况（论文被迫记录"谁真正在温度 0 采样"）、计费按输出 token 含推理 token；
- **性能工程基础**：延迟/峰值内存/能耗三指标的语义与测量陷阱（启动开销、JIT 预热、DCE、缓存效应、频率调节）。

### 7.2 方法论知识层

- **系统测量方法论**：隔离测量环境、预热协议、重复测量与置信区间、变异系数——全部继承自 Pereira et al. 的跨语言测量框架（MIT 许可复用）；
- **统计推断**：Bradley-Terry 配对比较模型与 MM 算法（1952 年的方法在 LLM 竞技场复活）、bootstrap、置换检验、Holm 多重校正、Kendall τ、Spearman ρ、Pareto 支配——排名的每一层都需要对应的检验；
- **工作负载表征**：SimPoint 的指纹-聚类-代表点思想（2002 年体系结构方法）、PCA、k-means 与 silhouette——把 8 千个测试用例压缩成 501 个加权代表。

### 7.3 工程知识层

- **裸金属测量环境**：RAPL 计数器读取与精度特性（约 1ms 更新）、perf 计数器、`ru_maxrss`、CodeCarbon 的组成（package + 恒定 RAM 估计——论文显式减掉）；
- **多语言构建链**：七种语言的编译/解释、harness 生成、防 DCE 的 checksum 手法、FFI 捷径的识别；
- **平台工程**：REST API 异步调度、provenance 记录（每条测量可溯源到机器/工具/运行）、在线排行榜。

### 7.4 知识融合的关键节点

1. **洞察节点一：联赛隐喻**。把"Pereira 的跨语言测量纪律"（不能跨语言比）与"Chatbot Arena 的 BT 排名"（两两对决聚合）嫁接——前提是意识到二者天然互补：前者提供"同 cell"的实验单元，后者提供跨 cell 聚合的统计工具。没有这个嫁接，要么做成不可比的拉通大排名，要么做成无法汇总的一堆小表格。
2. **洞察节点二：噪声即平局阈值**。把测量误差统计（置信区间）注入排名规则（差异 < √2×单测噪声即平局），统计方法从"事后检验"变成"赛制的一部分"。
3. **洞察节点三：SimPoint 的跨界迁移**。体系结构里用来挑模拟代表点的方法，迁移到"挑测试用例代表"，并在锚定语言（Python）上指纹、全语言复用同一输入——一步同时解决测量成本与跨语言一致性。
4. **洞察节点四：正确性与性能解耦**。失败解计 pass@1 miss 而非任意性能惩罚——让"会不会"与"快不快"两个信号各自干净，后面的"正确≠高效"发现才有干净的呈现基础。

## 八、论文中可以提取的通用性灵感

1. **饱和之处，换维度**。核心思想：当一个评测维度趋近天花板（全员 90%+），区分力必然转移到被忽视的维度（成本类指标）。论文证据：LC 正确率 12/13 超九成，但正确解延迟差 1.14–3.61×。推广场景：agent 评测从"任务完成率"转向完成成本（token/时间/费用）；RAG 评测从"答案正确"转向延迟与索引成本；模型评测从 benchmark 分数转向服务稳定性；招聘从学历筛选转向真实产出效率。

2. **同格对决：控制变量的极端形式**。核心思想：任何跨实体比较都应在"同一任务×同一条件"的格内进行，聚合时只统计共同参与的格子，缺席不奖不惩。论文证据：跨 cell 的几何平均排名会让只做简单题的 gpt-5.4-mini 冲到第二，同格对决把它打回第九。推广场景：A/B 测试中按用户分层配对；多模型评测按 prompt 配对；跨团队生产力比较按项目类型配对；教育评估按起点配对（增值评价）。

3. **噪声感知的平局：诚实的不确定性优于虚假的精度**。核心思想：把测量误差写进决策规则——差异小于噪声就判平，置信区间而非点估计说话。论文证据：平局阈值由 7 次重复的 95% 置信区间导出（LC 延迟 1.7%）；LC 峰值内存因此诚实报告"无显著差异"。推广场景：基准测试报告效应量+区间；线上实验不因 0.1% 的波动改版；监控告警带噪声带；性能回归检测的阈值设定。

4. **代表子集 + 权重 ≈ 全集**。核心思想：用行为指纹聚类挑选代表性样本、按归属比例加权，可用 6% 的样本逼近全集的平均行为。论文证据：501/8,063 用例保留 85% 对决结果一致、仅 1.5% 翻盘。推广场景：评测集瘦身（LLM eval 抽样）；用户调研的代表性样本加权；回归测试精选（failure cluster 代表）；数据标注的分层抽样。

5. **门槛前置 + 信号解耦**。核心思想：进入昂贵测量前先过廉价硬门槛（正确性），两类信号（会不会/好不好）分开报告，绝不互相折算。论文证据：失败解只计 pass@1，不赋任意延迟罚值——"惩罚值怎么定都会污染分布"。推广场景：竞赛先资格赛再正赛；招聘先硬技能门槛再看软素质；安全评测先功能开关再看性能；搜索先召回再精排。

6. **provenance 是可信度的地基**。核心思想：每个数字都可追溯到产生它的机器、工具与配置，环境变化即新档案，绝不混池。论文证据：每测量行盖机器/能耗工具/运行 ID 戳；不同硬件注册为不同 oracle；编译 flag 变化即新 profile。推广场景：MLOps 实验追踪；数据集版本化；审计链；新闻溯源。

## 附录：读这篇论文可以顺手学到的技能点

- 用 GraphQL API 拿平台延迟分布做基准筛选（P95/P10 比值是衡量"算法敏感性"的便宜代理）；
- 单机能耗测量最小工具链：RAPL（package 能耗）+ `ru_maxrss`（峰值内存）+ 重复测量的置信区间；
- BT 模型 + MM 算法把任意两两对决变成排名（`choix`/` BradleyTerry2` 一类库即可上手）；
- 防 DCE 基准写法：结果折叠进 checksum + C++ 优化屏障（`DoNotOptimize` 模式）；
- 用 bootstrap 重采样 + Holm 校正给 78 个配对比较去伪。
