## 先说结论

TWIML AI Podcast 第 781 期（2026 年 10 月 21 日发布）请到了 Airbnb CTO Ahmad Al-Dahle——他在苹果参与过初代 iPhone 的开发，在 Meta 领导过 Llama 团队（转写误作 Ahmed Al Dalle / Amit，已对照节目官方页面核实）。这期对话的核心不是又一家公司在用 AI 编程，而是一个更结构化的问题：**当 agent 已经能读代码库，真正的瓶颈变成了公司里那些从没写下来的知识**——为什么某个系统这样设计、哪条政策适用于哪种情况、老员工遇到文档失灵时怎么问。Airbnb 的答案是 Project Everest「公司大脑」，但嘉宾最坦率的部分恰恰是承认：知识共享系统自己会腐烂，架构大概率要重写。对任何想给 agent 建「组织记忆」的团队，这期节目是一份少见的正反面都摊开的案例。

## 三条前线与「craft」的约束

Al-Dahle 把 Airbnb 的 AI 采用归纳为三条前线：工程师生产力、市场侧离线 agent（用户看不见但提升信任、可靠性、质量）、以及面向房客与房东的体验 agent。他加入的时点恰逢 agentic coding 刚刚可用，而 Airbnb 在 AI/ML 基础设施上有长期积累，所以他的工作主要是「加速」。

方法论上，他给出了一个区分公司气质的观察：有些公司的信条是「move fast」，AI 部署就围绕速度展开；Airbnb 文化强调 craft（打磨），所以生产力度量不只看 PR 吞吐量和 token 消耗，还要看缺陷率和可靠性指标——用判断力给速度加护栏。在他看来，全公司通用的做法有三条：把整个公司「MCP 化」，让 agent 能就任意任务取用所需能力；在代码库内构造足够的上下文（比如支付栈这种受监管的复杂领域，agent 提交的 PR 要能让支付团队愿意审）；以及最被低估的一条——机构知识的提取与编码。

工具链上，Airbnb 从单一工具店转向了「多模型店」，理由是行业迭代太快。内部有叫 AirChat 的入口，把各家 harness 包上自己的 MCP 后供工程师自选；产品侧则自研 harness 并改造开源组件。开源立场方面，客服 agent 框架是早于开源社区生态成熟前自建的，但团队会持续评估，若开源方案领先就迁移甚至反哺——Al-Dahle 自称「在能开放的地方公开构建」的立场众所周知。

## Everest：公司大脑怎么做、怎么防中毒

Everest 的机制是从使用中学习：工程师（最初是产品工程师，现在已扩散到 Airbnb 称为 product marketer 的产品经理群体，未来设计团队也会接入）在日常使用 AI 的过程中，把「怎么做事情」的隐性知识沉淀进一个共享上下文池。Al-Dahle 的目标是把它做成学习所有人工作流的「公司上下文图谱」。

主持人 Sam Charrington 用知识管理的老问题追问：agent 能从工作发生的地方自动记录，但文档太多、或记错重点，反而「毒化水井」。嘉宾的回应分三层：

- **评测是方向盘。** Everest 用固定任务集持续基准测试，典型例子是定价域（Airbnb 最复杂的领域之一，堆满政策和特定工作方式）：给一条「应用新定价规则」的 prompt，看 Everest 积累的上下文能否让 PR 又快又准。
- **存储形态未定。** markdown 文件有天然优势——前沿模型本来就是照着文件系统导航训练的，能走很远；但失控的 markdown 文件恰恰是他警告的那个问题：难检索、上下文毒化，「模型特别擅长找到那条旧的、错的记录」。向量检索他也直言难以扩展到全公司规模。最终大概率是某种混合体：中间有一层智能负责检索策略和**上下文的渐进披露**——「你能犯的最大错误，是过快地向模型暴露太多上下文；正确做法是只给它够往前走一步的上下文，然后让它主动要更多」。
- **架构会被重写。** 他明确说现在并不确信拿对了架构（「I'm not convicted that we have the right architecture」），节目结尾再次承认 Everest 规模化后是变有用还是被污染，「我们不知道」。

与之配套的是 Airbnb 的 agentic 评测体系：资深工程师委员会定义任务，自建 agentic evals 跑在所有开源和闭源模型上，用校准过的 virtual judge 打分，画成本-准确率曲线。难点是模型们挤在 92–93% 附近拉不开差距。嘉宾给出两种解读：要么评测不够好，要么模型对多数任务已经够用、剩下的只是成本与速度的取舍——但他补充，分不出前沿与非前沿模型时，他多数时候「怀疑的是评测」。

## Token 治理：不设上限，看下游

主持人搬出 Uber 的段子（鼓励工程师放开用 agentic coding，过一阵子被账单吓到）问成本治理。Al-Dahle 的立场是「激励目标，而不是约束执行」：Airbnb 没有搞一刀切的 token 上限，token 用量只被当作信号——零使用说明需要帮助；大量使用需要理解，而他发现大量使用者分两类，一类需要效率辅导，一类在做高价值的大迁移，「那就放手干」。真正的离群信号是那种把单一前沿模型钉死在最大思考档、上万次工具调用、每个子 agent 都用前沿模型的用法——慢，且未必必要。

度量上他不锚定用量而锚定下游：PR 吞吐量上升只说明产出变多，不说明产出有用；最好的指标是**路线图整体左移、被压缩**——同样的事在更短时间内做完。主持人立刻指出这里面混杂因素太多（PR 粒度、路线图距离都在变），嘉宾承认没有完美指标，但坚持趋势线有效：如果能持续把更多事情做快，「混杂因素几乎不重要」。至于主持人「能力变强路线图应该扩张才对」的质疑，他的回答很直白：那是「事情没有多到做不完的公司」才成立的问题，Airbnb 的路线图「相当疯狂」——从核心住宿市场扩展到「物理世界能做的一切都在平台上」，重造整个技术栈，并变成 AI native 的公司。

工作方式的改变被他认为是被低估的部分：过去是 MLE→产品工程师→设计师→PM→法务→政策的瀑布式交接，每个角色产出不同的中间产物；现在所有人（包括设计师、PM、政策、法务）直接跳到写代码出原型，用实现代替事前谈判。

## 市场侧：冰山下的信任机器与 50% 的客服

Airbnb 的可见产品只是冰山一角：水下是数百万房东、支付、保险、客服构成的双边信任市场。离线 agent 已经在支付纠纷识别、欺诈检测、行程质量问题上规模化运行。

客服是重头。Al-Dahle 给出的数字是：**约 50% 的客服会话由 AI 纯粹独立解决**——明确强调不是「AI 辅助人类」，而是 AI 对用户直接解决。信息型查询（改预订这类）天然适合，配合作卡片让用户一键自助，本质已是 agentic。原则是透明：AI 就自称 AI，用户说「转人工」就真的转人工，不做那种按十八次零才放行的呼叫中心陷阱。但他也承认，有「百分之几十」的用户无论问题多简单都只要真人——这是心理问题而非能力问题，是最难的一层天花板。

真正的前沿难题是**双边调解**：Airbnb 不拥有产品，纠纷发生在两个人之间、平台居中，双方各自优化对自己有利的结果，且证据不可物理验证——他举的例子是房客可以拍张桌子照片让 AI 修掉一条桌腿来索赔，平台无法实地查验；同时平台又必须不偏袒任何一方、严格执行退款政策。用他的话说，把 agent 塞进群聊的「multiplayer」今天「勉强能用」，而让一个 AI 在房客、房东、平台三方之间完成有约束力的财务调解，现有模型做不好。所以 Airbnb 在硬案例上保留人类判断、只做研发投入，让 AI 先啃长尾。

## 搜索、MCP 与「信任优先于便利」

搜索方面，房源的深层信息（藏在图片和评论里的信号）远多于筛选器暴露的部分，但实验发现用户不要聊天框——来回打字是摩擦，「45 句话的查询」没人想输。正在测试的形态是自然语言输入框（去哪、和谁去、为什么去、找什么）返回结果，但保持多模态浏览和用户控制权，不让 AI 直接拍板那一两家房源。他的判断是预订旅程本身是数周维度的社交过程（收藏、和家人商量、反复回访），AI 应该增强而不是剥夺这种探索。

主持人顺势抛出尖锐问题：为什么不干脆把 Airbnb 做成 MCP server，让用户的私人 agent 去筛房源——反正 computer use 已经能绕过没有 API 的限制，只是慢。Al-Dahle 的回应是逐案判断的体验标准，外加旅行业的特殊性：**「便利不是关键，信任才是」**。他引用节目口径称美国约 40% 的人已用 AI 做旅行灵感，但一万美元的行程预订，用户信的是有保险、支付、客服兜底的市场，而不是「某个随机的 MCP server」。

模型策略上，强延迟约束加上高 QPS（搜索就是例子）让 Airbnb 自建了后训练基础设施和 RL 环境，把小模型蒸馏到在窄任务上打败前沿模型——客服政策遵循不用担心数学能力回退，搜索用「能用的最小模型」。他把这归因于消费体验的「锯齿状边缘」：行业在炫耀解千禧年大奖难题（转写误作 million-year prize problem），而「在旅行网站上可靠地操作计算机」这类问题反而不需要十万亿参数（嘉宾提及英伟达 Nemotron 等小模型家族，转写误作 Neutron）。他甚至透露 Brian Chesky（转写为 Brian Down，按上下文应为 Airbnb 联合创始人/CEO）有一个本地化的「第二大脑」上下文图谱，喂过他经手的每份文档、愿景稿、邮件，用来辅助日常决策——CEO 如此，全公司的热情可想而知。

## 这期节目值得带走的判断

把嘉宾的论述整理成几条可观察、可迁移的链条：

1. **机构知识是 agent 时代的下一块瓶颈资产。** 代码可读、文档可搜，但「为什么这么做」的判断藏在人身上。谁先把隐性知识接入 agent，谁就先获得复合收益——但二阶效应是知识库本身成为新的腐烂面。观察指标是固定任务评测随知识积累的曲线。给团队的启发：建记忆系统之前先建评测，先设计渐进披露，而不是全量倾倒。
2. **用量治理的正确对象是产出结构，不是 token 数字。** 一刀切限额会误杀大迁移；信号式管理（零用量的拉一把、离群的理解清楚）配合下游指标（吞吐、缺陷率、路线图压缩），才与「AI 真正改变工作方式」的假设自洽。
3. **部署 agent 要把「永远不交给它的部分」当设计输入。** 50% 客服自动化之所以可信，恰恰因为 Airbnb 明说了硬案例留人类：对抗性调解、不可验证证据、政策公平三重约束下，模型能力不足不是耻辱而是部署边界。
4. **消费场景的模型经济学在向窄任务专用化走。** 高 QPS×低延迟的场景里，自建后训练管线蒸馏小模型可以打出比前沿模型更好的成本-准确率帕累托前沿——这解释了为什么应用公司要持有模型能力，哪怕只是小模型。

不确定项也要说清：50% 客服解决率、40% 灵感使用率、evals 聚焦 92–93% 区间等数字均为嘉宾在节目中的陈述，未经独立核实；Everest 的最终架构、客服能否爬到 100%、以及 Airbnb 会不会开放 MCP 接口，嘉宾本人都标记为开放问题。这期节目最大的价值，是让一个正在从零到一构建「公司大脑」的 CTO 亲口说出哪些地方他还没有答案。
