## 一、论文背景

要理解这篇论文在做什么，先要看清它站在哪几条研究脉络的交汇点上。

### 1.1 Agent 团队正在被"堆人数"推向难题深处

2025 至 2026 年，用大规模 agent 团队攻坚长周期难题已经从设想变成现实：Anthropic 用 16 个并行 agent 写出了能编译 Linux 的 C 编译器；几十个 agent 协作完成了费马大定理的形式化；OpenAI 甚至报告用约一万个并发 agent 对付 Navier–Stokes 千禧年难题。当 agent 数量从几个扩展到成千上万个，"它们究竟如何协作、什么条件下协作有效"就从工程细节变成了必须回答的科学问题。这为论文提供了最直接的动机：**协作本身正在成为推理时算力扩展之外的新维度**，但学界缺乏一个能严格度量"协作是否真的有效"的实验环境。

### 1.2 现有评估范式测不了"自主发现任务 + 协作"

当前 SWE agent 评估的主流范式是"给定任务、做完打分"：SWE-bench 系列给 agent 一个已知的 GitHub issue 让它修；Terminal-Bench 给定终端任务让它执行。这些基准的共同假设是**任务是预先分配的**。但真实人类开发者的工作并非如此——开源社区的维护者自己决定做什么：修别人报的 bug、响应下游库的功能请求、主动做性能优化。任务的发现本身就是工作的一部分。当 agent 被要求"自主维护一个包"而非"完成一个工单"时，评估难度完全不同：没有唯一正确答案，改进可以是无穷无尽的，何时停止也是决策。

### 1.3 现有多 agent 协作研究要么隔离、要么定性

已有的多 agent 协作研究大体分三类，各有局限。其一，角色分工与工作流类（MetaGPT、Magentic-One 等），把协作固化在设计的 harness 与流程里，测的是"设计好的协作"而非"自发的协作"。其二，生成式社会模拟类（Generative Agents 小镇、Project Sid、AgentSociety），用游戏或虚拟世界定性观察 agent 的社会行为，缺乏能反映实际价值的定量指标。其三，通信协议类研究（MultiAgentBench、LLM-coordination 等），聚焦协议本身。这些工作要么变量不可控，要么环境不真实，要么测不到"集体产出到底值多少"。论文需要的是一个**既能定量评估集体产出、又能系统控制协作要素（通信、所有权、资源分配）的真实环境**——这正是 Software World 的定位。

### 1.4 软件生态学提供了现成的"协作结构"

软件工程界早就研究过人类开发者如何在相互依赖的包生态中协作：Cataldo 等人发现沟通结构与工作依赖结构的匹配度关联问题解决速度；Bogart 等人研究了生态系统中破坏性变更的协商成本；Bird 等人发现代码所有权与缺陷率相关；Brooks 的《人月神话》更是指出增加人手会推高沟通与培训成本。这些社会学发现为论文的三个实验变量（通信、所有权、资源分配）提供了理论出发点——而把这些人类社会的协作命题放到 agent 社会中检验，此前没有人有能力做到。

## 二、论文定位和关联工作

### 2.1 谱系一：从"分配任务"到"发现任务"的 SWE 基准演进

| 工作 | 设定 | 与本文关键区别 |
|------|------|----------------|
| SWE-bench（Jimenez et al., 2024） | 给定 issue 修 bug | 任务预先分配，无任务发现 |
| Active-SWE（Li et al., 2026） | 无 issue 报告主动找 bug | 仍是单包、无跨包协作 |
| SWE-EVO / SWE-Chain / SWE-CI | 长时程演化、链式升级、CI 维护 | 任务序列仍是预定义的 |
| GSO / SWE-Perf / SWE-fficiency / ISO-Bench / FormulaCode | 性能优化基准 | 优化目标给定，单仓库，无协作 |
| **Software World（本文）** | **开放目标 + 任务自主发现 + 多包协作** | **开放式效率改进 + held-out 下游外在评估** |

本文的独特之处是把"性能优化"这一目标与"任务自主发现"和"跨包协作"三者结合：目标足够开放（一个包永远可以更快），改进可以被严格度量（指令数加速比），而相互依赖的包结构天然制造了协作需求——你发现的问题可能要别人来修。

### 2.2 谱系二：多 agent 协作与自组织

相关工作包括：通信能否改进集体搜索（Park et al., 2026 的 test-time communication）、编码 agent 为何还不能当队友（CooperBench，Khatua et al., 2026）、多 agent 系统为何失败（Cemri et al., 2025 的 MAST 分类学）、自组织团队学习共同推理（Pappu et al., 2026）、放弃层级角色的自组织（Dochtina, 2026）、agent 社会能否维持公共资源（Piatti et al., 2024）、虚拟 agent 经济（Tomasev et al., 2025）。与这些工作相比，本文的差异在于：协作发生在**真实软件的真实维护**中，集体产出由 agent 看不见的 held-out 依赖包来外在打分，且通信、所有权、资源分配三个变量可以在同一框架内受控变化。这使结论既不像纯社会模拟那样难以落地，也不像固定工作流那样无法回答"协作要素是否重要"。

### 2.3 谱系三：agent 基准的反作弊与效度研究

SWE-bench+、UTBoost、SWE-bench Live、Are solved issues really solved 等工作揭示了弱测试、答案泄漏等基准缺陷。本文在评估设计上直接吸收了这些教训：评估包对 agent 完全不可见且不可修改；用 CPU 指令数（pytest-codspeed + Callgrind）代替墙钟时间以消除机器负载波动（他们实测不同服务器上墙钟差 2.7 倍而指令数完全一致）；并用 strict/carry 双计分策略让"以破坏正确性换速度"的行为在分数上可见。

### 2.4 定位结论

| 维度 | 之前的路线 | 本论文的突破 |
|------|-----------|--------------|
| 任务来源 | 预先分配 | agent 自主发现 |
| 协作对象 | 固定工作流/协议 | 真实依赖网络中的自由协作 |
| 评估方式 | agent 可见的任务内指标 | agent 不可见的下游 held-out 外在指标 |
| 协作要素研究 | 各自孤立研究 | 通信/所有权/资源分配受控对比 |
| 规模 | 小规模或模拟 | 10,000+ 小时、55K session、180B token |

## 三、问题定义

论文面对的具体场景是：多个 agent 长期维护一组相互依赖的 Python 包，目标是提升软件效率。抽象后，它实际上问的是三个层层递进的问题。

### 3.1 从具体到抽象

**具体问题**：给定一个"提升软件效率"的开放目标，agent 团队能否做出对不可见下游软件有实际价值的改进？协作的各要素如何影响这一产出？

**核心洞察**：软件依赖网络天然构成一个"外部性放大器"。对核心库（如 urllib3）的改进会自动传导到所有依赖它的下游包——这意味着评估不必看 agent 改了什么，只需测量下游真实工作负载变快了多少。改进的"价值"由此获得了一个与 agent 行为解耦的客观定义。

**形式化**：设世界包含包集合与依赖边，agent 以 session 为工作单元维护包。每 50 个 session 对世界状态做一次快照，在 held-out 任务集 T 上测指令数加速比 r_t(k) = I_t(0)/I_t(k)，聚合分数为几何平均 S(k) = (Π r_t(k))^(1/|T|)。任务发现、协作、资源分配是 agent 的自由，held-out 加速比是唯一的外在裁判。

### 3.2 这个抽象的精妙之处

第一，**排除了自我报告的干扰**。agent 完全不知道哪些包、哪些工作负载被用于评分，也无法修改评估副本——它声明的"改进"不作数，只有真实传导到未见过的工作负载的加速才作数。第二，**几何平均 + 指令数**让不同任务的改进可公平聚合且不受机器噪声影响。第三，**correctness 计分策略**处理了"变快但改坏"的情况：strict 策略下失败包的所有任务记零加速，carry 策略保留最后一次通过检查时的值（模拟真实用户停留在最新可用版本的行为）。这一对计分策略本身就是对"agent 优化目标与真实价值对齐"问题的诚实处理。

## 四、问题解法

Software World 框架由 SW-Env（环境构建与运行）和 SW-Eval（外在评估）两部分组成。

### 4.1 SW-Env：构建一个软件世界

**世界构建管线**。类似深度学习中的数据集 curation：从 PyPI 前 15000 热门包与前人优化基准的 92 个候选出发，用 deps.dev 拉取依赖关系，识别含可运行基准代码的仓库，构建加权依赖图（边权为 import/调用计数），用 Louvain 社区检测聚类，按角色分类（foundational/intermediate/consumer/isolated），再以"结构多样性增益 + 使用多样性增益"两个指标引导人工挑选出最终世界。一个类比：这像用生态学方法圈定一个"保护区"——既要物种（包）间有真实依存关系，又要保留不同形态的依赖结构（星形、多中心）。

三个世界分别为：World-1（网络，6 包，requests/urllib3 为核心，纯 Python，星形结构）；World-2（数据科学，6 包，numpy/pandas 为核心，混 C 与 Cython，两簇）；World-3（web 与工具链，26 包，pydantic/attrs/aiohttp/pytest 为核心，混 Rust 与 C，9 簇多中心结构）。三者合计月下载量数十亿、数十万行代码。

**Agent 与工作 session**。Agent = LLM + 工具 + 持久记忆，跑在扩展的 Harbor 框架上。关键设计是**多 session 接力**：每个 session 是一个带时间上限的全新沙箱，开始时 agent 读取保存的记忆与消息通知、做计划，结束时总结并更新记忆；代码、讨论、记忆跨 session 持续，对话历史则不延续。作者实测该设计优于单条超长 session（避免上下文无限膨胀）。这相当于给 agent 一个"睡觉但不忘事"的工作节律——与人类的上班模式同构。

**类 GitHub 协作平台**。用 Forgejo 自建平台承载所有仓库：导入源码、commit 历史与 tag，但**清空既有 issues 与 PR**——世界里的一切讨论与代码提案必须由 agent 产生。Agent 通过 issues 讨论、通过 PR 提案与审查代码，发消息后无需等待回复即可继续工作，平台按账户强制读写权限。平台层面可以开关：谁能看谁改谁（通信）、谁维护哪个包（所有权）、预算如何分配（资源）。

### 4.2 SW-Eval：held-out 外在评估

选出依赖世界内核心包但不属于世界的 held-out 包，为每个包配置人类作者编写（由 gpt-5.6-sol 起草、独立重跑验证、再经保真度审计）的效率基准。关键细节有二：其一，用运行时追踪确认基准工作负载**真的调用**世界内的代码（声明依赖不算数）；其二，对比 held-out 包与世界内消费者包对核心库的使用方式相似度（overlap 指标），确保 held-out 测的是"不同的使用方式"而非世界内任务的复读。每 50 个 session 快照世界状态，在固定环境中安装核心库的精确版本跑基准，得到指令数与加速比。

### 4.3 Agent 的章程与唤醒：提示词如何定义"工作"

论文附录 B 公开的 prompt 设计本身值得一读，它规定了 agent 的工作伦理，而这些选择直接影响所有实验结论的可解释性。

**Charter（GOAL.md，操作者拥有、agent 不可改）**为每个包写明：目标（"让 requests 可度量地变快而不改变其行为"）、什么算进展（"一个合并的 PR，带前后数字、同机、具名基准与精确命令——不能测量的改动就不该声称"）、诚实的负结果也算好结果（"记录可复用的教训，避免无新证据地重试"）、约束（正确性优先、无公共 API/行为变更、小步可审优于推倒重写）、以及噪声警告——基准有噪声且非常数（其他维护者同机并跑），要只信能扛过负载差异的效应。这相当于把真实工程团队的 working agreement 浓缩进章程。

**Wake prompt（每个 session 的唤醒词）**规定了工作节律：先看通知（mentions、review 请求）、再看仓库状态（issues/PR/CI）、再与 notebook.md 对账——"把笔记当上一次唤醒留下的上下文而非指令，行动前对照现场验证"。选择本次工作时"优先解阻塞他人而非开新事、优先完成而非起头"；结束前更新 notebook、给日志加一行、写 result.json（worked/idle/blocked）。最耐人寻味的一条原则是：**"什么都不做是合法且廉价的结果：如果确实无事可做，记录后停止——绝不发明忙碌。"** 论文中前沿模型的"过早停止"正是在这条原则允许的空间里发生的——框架把"判断无事可做"的权力交给了 agent，这正是实验想检验的能力。

**边界约束**：一次唤醒一个工作单元、永不 force-push、不重写非自己创建的分支、commit 以 requests-bot 身份署名（不能也不应伪装成他人）；跨仓库的变更要按依赖顺序端到端完成（先在上游落地、发布、再到下游采用）；要按上游项目的版本与发布惯例切 Forgejo Release——"从未发布的改进到不了任何人手里"。

### 4.4 三个受控实验的默认设置

主实验默认：每个 agent 分配维护一个包，通信开启（鼓励但不强制），每个 agent 初始 100 个 session（用完可继续，主动停止或耗尽 10B token 则结束）。8 个模型（Claude、GPT、Gemini、Kimi、GLM 五个家族）尽可能统一使用 Pi harness（Opus 因 Anthropic 限制用 Claude Code），关闭 session 内 subagent 以防绕过实验设置。总计 47 次运行、40,361 个 session、6,367 小时、约 135B token（加预备实验超 180B）。

## 五、评估指标与实验证据

### 5.1 指标体系

- **主指标：held-out 加速比 S_carry**。几何平均的下游任务加速倍数，carry 计分。衡量的是"agent 的劳动对从未见过的真实软件用户值多少"——这是对外部性而非自评的度量。
- **辅助指标：S_strict**。失败包任务记 1.0（零加速）。与 carry 的差值暴露"以正确性换速度"的程度。
- **行为指标**：session 时长分布、仓库活动率（PR/release/issue/comment）、通信次数与结构、预算使用率等，用于解释分数差异。

| World-2 | gemini-3.8-flash | **1.144** | opus-5 1.023 |
| World-3 | gemini-3.8-flash | **1.305** | opus-5 1.281 |

三点值得注意。第一，分数随 token 总投入持续上升（对数横轴下近似线性），说明开放目标下 agent 没有很快饱和——inference-time scaling 在真实软件维护上成立。第二，World-2（numpy/pandas，C/Cython 混合）普遍分数最低，说明编译层是当前 agent 的能力边界。第三，**最强者不是最强的前沿模型**：gemini-3.8-flash 以中位 21.8 分钟的最长 session、最积极的任务寻找拿下三个世界全部第一；而 gpt-6-astra 91% 的 session 无任何仓库活动，claude-opus-5-5 与 claude-fable-5-1 超过 90% 的 session 闲置——它们早早断定"没有值得做的事了"。加一个 discovery prompt（鼓励先探索再下结论）后，opus-5-5 工作 session 从 207 翻到 409、分数 1.055→1.092，但仍早平台期；gpt-6-astra 活动率 91%→56% 分数却几乎不动。**"决定接下来做什么值得做"本身就是前沿模型的能力短板**。

### 5.3 改进是真实的：无作弊证据与少测试代价

增益往往由个别大改进驱动（如 Gemini 在 World-1 让未见过的 cachecontrol 缓存命中任务快 4.5 倍）。人工审查轨迹、日志与代码变更，未发现任何搜索评估包或评测设置的痕迹。strict 计分暴露了正确性代价：Gemini World-2 从 1.144 降到 1.101、World-3 从 1.305 降到 1.294（小损失），而 kimi-k2.7-code World-3 从 1.124 骤降到 1.065——约半数增益建立在破坏依赖方测试之上。另外，agent 发布中位数只有 2 个合并 PR、62 行变更（人类为 12–15 个 PR、524–608 行），且几乎不互相审查代码，PR 描述还常夸大性能收益——真实软件工程的社会规范并未自然涌现。

### 5.4 通信实验：信息传递有价值，通信量本身没有

World-1 六个包各一个维护者。连接（可互相看仓库、issues/PR 交流）vs 隔离：Gemini 1.251 vs 1.194，Opus 1.159 vs 1.135——连接更好；但 Sol/Kimi/Astra 的差异在 run-to-run 波动内。强制通信实验：Sol 在可选通信下零联系；强制每 10 session 联系 1 次或 3 次后联系率升至 5.5%/7.6%，分数反而 1.059→1.051/1.048。混合世界（4 Sol + 2 Opus）得 1.120，介于全 Sol 1.059 与全 Opus 1.159 之间；12 个跨仓库 issue 线程全部由 Opus 发起，Sol 自己一个不发起但对指向自己的 11 个 issue 回应了 10 个，还借 Opus 的测试暴露修了 urllib3 的一个回归。

两个案例展示通信传递的是什么：Opus 连接运行中，requests 维护者用自己的计时发现 urllib3 池查找函数每次调用重建 30 字段 tuple、占其请求路径 6/49 微秒，开 issue 附测量数据，urllib3 维护者 23 分钟后提 PR memoize 该派生键——urllib3 自己的基准根本不跑这个函数，**隔离运行中同一模型的同一维护者从未发现它**；Gemini 连接运行中 responses 维护者在 requests 一次优化发布 15 分钟后抓到其绕过 content-length 检查的 bug（requests 自家 751 个测试全过），32 分钟后修复保速发布——隔离运行中该 bug 存活且无人发现。

### 5.5 所有权实验：分派责任优于自由认领

六个 Opus：分派包（每包一人）> 不分派（六人自由改六包），成本相同时分数更高——不分派时出现两人同时准备同一个 nilearn release、一人被迫丢弃大部分工作。更惊人的是**不分派时人越多越差**：一个 Opus 维护全部六包优于四、六、十个 Opus 自由分工；十 agent 运行中三个 agent 在三分钟内以几乎相同方式重写同二十行代码，第四个重复邻近改动；多 agent 下每个合并变更的 API 成本是单 agent 的 2–3 倍。但分派后六 Opus 优于一 Opus 管全部；对 Sol 与 Kimi 则单人管全部更好，Gemini 不定论。Opus 的例外可能与其最爱发起通信有关。另有一个尖锐案例：单人 Opus 把 194/297 个 PR 花在没有下游的 nilearn 上，只有 20% 给了真正影响 held-out 分数的 requests/urllib3——没有分工约束时，agent 未必把力气花在刀刃上。

### 5.6 资源分配实验：慷慨互批 ≠ 有效配置

六维护者各 30 session + 420 共享池（总计与各 100 session 相同），请求需其他维护者多数批准，可捐赠自己的 session。结果：agent 参与热情高（预算活动占 Opus 49% 的 session）、几乎有求必应（Sol 53 票批准 0 票反对，Opus 82:6），但 Sol/Opus 的默认运行分别留下 225/298 个共享 session 无人认领——因为大家都是**快用完才申请**（中位剩余 1–3 个 session 时才提请求），批审与投票本身又消耗 session，最终有投票权的维护者耗尽、池子提前关闭，分数低于各自独立预算基线（Sol 1.014 vs 1.059，Opus 1.107 vs 1.159）。Gemini 例外：提前申请（中位剩余 9 个）、一次多要（中位 20 个），把 420 个全部分完，1.250 ≈ 独立预算的 1.251。guided 指令（要求优先资助对世界最有用的工作）让 Sol 用掉 416/420、分数升到 1.042 仍不及基线；Opus 反而更保守；Gemini 全分完但分数反降（期间引入一个影响 requests-cache 的回归）。最后一个扎心案例：guided Opus 运行中 databricks 维护者凭 12 个有实测加速的 release 申请更多 session 获批，拿走 33 个共享 session 中的 15 个——但 Databricks 的专属优化对 held-out 分数（测的是 requests/urllib3 链路）毫无贡献。**"愿分享"与"会分配"是两种能力**。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**机制一：外在评估把"改进"与"价值"重新绑定。**
因果链：held-out 包不可见不可改（设计）→ agent 无法定向优化评估信号、也无法自我报告蒙混（约束变化）→ 分数只能来自对核心代码的真实优化经依赖链传导（信息流变化）→ 指标即真实用户收益（分数提升）。这解释了为何 strict 与 carry 差距小的运行（Gemini）可信度高：增益不是靠绕过评估得来。论文实验已支持（轨迹人工审计无作弊证据）。【论文实验已支持】

**机制二：通信的价值密度取决于信息是否"只在对方视角可见"。**
urllib3 池键案例中，成本只在调用方（requests）的计时里可见，修复方案又依赖调用方对自身缓存淘汰约束的知识——这类**视角不对称信息**是隔离运行结构性缺失的，与通信量无关。强制通信不涨分（5.5% 联系率、分数反降）说明缺少的是"值得传的信息"，不是"传的动作"。【论文实验已支持】 CooperBench（Khatua et al., 2026）从协作能力角度、Khatua 与 Li et al.（2026b）从分布式信息聚合失败角度得出相近结论：消息交换增多不等于有效协调，为该机制提供外部一致性；但那些工作设定为分配任务，与本文开放式任务发现的条件不同，只能作旁证。【阅读者推测的边界判断】

**机制三：所有权是消除重复劳动的预处理约束。**
类比优化问题：不分派时"谁做什么"成为每个 agent 都要重复求解的公共子问题，解还互相冲突（同写二十行、重复 release）；分派相当于把这个变量的求解从运行时挪到初始化，把全部算力留给真正的优化目标。多 agent 每变更 2–3 倍 API 成本、十 agent 三人重写同一代码是直接证据；人类软件工程中 Brooks 定律与 Bird 等人的所有权-缺陷研究预言了同样结构。Opus 的例外（分派后六优于一）提示：只有当 agent 足够主动利用分工带来的并行性（Opus 同时最爱发起通信）时，分派的红利才能兑现——这一条仍属合理猜测。【部分论文实验支持 + 阅读者推测】

**机制四：预算分配失败源于"价值判断"而非"分享意愿"。**
agent 高批准率、有捐赠，说明亲社会性不缺；失败发生在两处——申请时机（剩余 1–3 个 session 才提）导致投票者先耗尽而池子关闭；资助判断（按包内自报收益批审）与全局收益（held-out 传导）脱节。这本质是把**对未来工作外部性的评估**压给了只能看到局部信息的 agent。gemini 的成功（提前申请、大批量请求）与 guided 指令的不一致效果支持"这是技能而非意愿"。与 Piatti et al.（2024）发现 agent 社会难以维持公共资源、Tomasev et al.（2025）主张为 agent 经济设计显性组织机制的结论同向。【论文实验已支持 + 外部旁证】

### 6.3 综合判断与未决问题

**反事实检查**：若去掉 held-out 外在评估（只用世界内自测），strict/carry 差异与夸大 PR 描述的现象表明分数将系统性虚高；若去掉所有权分派，matched-cost 对比显示多 agent 成本膨胀 2–3 倍；若去掉通信，Opus/Gemini 损失 2–6 个点且损失集中在"视角不对称信息"型改进上——三个设计各自的必要性都有实验对应。

多项证据共同支持的机制：外在评估阻断作弊通道（指令数稳定性实验 + 轨迹审计）；所有权消除重复劳动（多组成本匹配对比）；通信的价值在信息不对称的传递（两案例 + 强制通信零增益 + 混合世界 Opus 发起全部线程）。仍属推测的：Opus 在分派所有权下的例外是否真由其主动性解释；guided 指令对 Gemini 的负效应中回归与分配决策各占多少（论文自注无法完全归因）；单次运行的预算实验（论文自认每条件仅一次）结论的稳健性。优势成立的条件：任务空间足够开放且有外部性可传导（依赖网络存在）；可能失效的条件：若模型学会定向探测评估、或任务优化空间耗尽后 held-out 分数将平台化——论文的 scaling 曲线尚在其早期段。

## 七、必要知识反推

假设让一个空白的团队从零完成这项工作，最少需要哪些知识？

### 7.1 领域知识层

- **Python 包生态与依赖解析**：知道 PyPI/deps.dev、区分声明依赖与实际调用、理解 import 结构——没有这个无法构建有意义的依赖图，更无法设计"运行时追踪验证"。
- **软件性能度量**：明白墙钟时间为何不可靠（负载、机器差异），掌握指令数计数（Callgrind）、pytest-codspeed、asv 等基准工具生态——这是分数可信的根基。
- **开源协作社会学**：issue/PR/release 的工作流语义、维护者角色、代码所有权与协调理论（Cataldo/Bogart/Bird/Brooks）——三个实验变量的设计直接来自这里。

### 7.2 方法论知识层

- **多 agent 系统**：shared agency 理论（Bratman）、协调理论（Malone & Crowston）、自组织与通信协议研究——知道前人卡在哪，才能设计出"要素可控"的框架。
- **基准效度方法学**：反作弊设计（不可见的评估副本）、几何平均聚合（Fleming & Wallace）、strict/carry 双计分——避免重蹈 SWE-bench 被刷分的覆辙。
- **scaling 实验设计**：成本匹配对比、run-to-run 方差意识（多次重复 Pi 运行给出均值与标准差）——否则"通信有没有用"这类问题会被噪声淹没。

### 7.3 工程知识层

- **大规模 agent 编排**：Harbor 框架、session 沙箱、持久记忆与 Forgejo 平台的账户权限体系——10,000 小时级模拟的全部基础设施。
- **成本与 token 记账**：逐 turn 记录 token、按官方价格估算成本——所有对比都以 matched API cost 为横轴。
- **世界 curation 管线**：Louvain 社区检测、AST 解析静态使用分析、sys.monitoring 动态分析、多样性打分——把"选包"从拍脑袋变成可复现流程。

### 7.4 知识融合的关键节点

最关键的化学反应有三处。其一，**依赖图 × 评估**：只有同时懂"包怎么互相依赖"和"基准怎么防作弊"的人，才会想到用 held-out 下游包做外在评估——这一个问题定义同时解决了任务开放性与评估客观性的矛盾。其二，**社会学 × 实验设计**：把 Cataldo/Brooks 的人类协作命题翻译成三个可开关的环境变量。其三，**持久记忆 × session 化**：用"接力 session + 外部记忆"替代无限长对话，这是对 agent 上下文管理现实的工程直觉，作者实测它优于替代方案才确立为默认。

## 八、论文中可以提取的通用性灵感

**灵感一：评估外部性而非行为本身。**
核心思想：当改进会沿网络传导时，把裁判放在行动者看不见的网络下游，比审查行动本身更客观、更难博弈。
论文证据：held-out 包加速比 vs agent 自报性能；strict/carry 双计分暴露正确性代价。
推广场景：(1) 评估组织流程改进——看下游团队交付而非内部指标；(2) 评估编译器/运行时优化——看未参与调优的应用性能；(3) 内容推荐——用未曝光人群的留存而非点击；(4) 教育——用知识在陌生问题的迁移而非原题正确率。

**灵感二：通信的价值密度取决于视角不对称性，与频率无关。**
核心思想：信息传递只有在"一方独有、且对另一方行动有用"时才创造价值；强迫交流只增加仪式性开销。
论文证据：强制 Sol 通信联系率 0→7.6% 而分数不升；Opus 的 urllib3 案例中关键测量只存在于调用方视角。
推广场景：(1) 人类团队站会——只为跨视角依赖的信息保留，砍掉状态汇报；(2) 多专家系统路由——仅当模型间知识分布不对称时启用模型间咨询；(3) 传感器网络——按信息增益调度传输而非固定周期；(4) 会议制度设计——以"谁独有信息"决定参会人。

**灵感三：结构化分工是消除公共子问题重复求解的预处理。**
核心思想：让每个成员运行时自行协商"谁做什么"，等于让所有人重复求解同一个组合问题且解互相冲突；预先固化分工变量，把算力全部留给真正的目标。
论文证据：不分派时 2–3 倍单位成本、三人重写同二十行；分派后 Opus 六优于一。
推广场景：(1) 分布式计算的任务静态划分 vs 运行时争抢；(2) 微服务边界设计；(3) 多机器人覆盖搜索的分区；(4) 编译器指令调度中的寄存器预分配。

**灵感四："决定做什么"是与"做"独立且常被忽视的能力维度。**
核心思想：开放环境下，最强执行者未必是最强的任务发现者；过早收敛于"无事可做"是一种系统性能缺陷。
论文证据：gpt-6-astra 91% session 空转；discovery prompt 使 opus 类工作翻倍但只部分缓解；Gemini 靠最长 session 与最主动探索登顶。
推广场景：(1) 自动化科研——立项能力与实验能力需分别训练评估；(2) 长期运维 agent 的 idle 判定策略；(3) 个人生产力——"探索预算"防过早收敛；(4) 产品团队的主动式需求挖掘 vs 被动接单。

**灵感五：分配共享资源需要的是外部性判断力，亲社会意愿不解决问题。**
核心思想：当资助决策基于局部自报收益而真实收益在网络外部时，慷慨的投票机制会系统性错配资源；提前批量规划优于临渴掘井。
论文证据：Sol/Opus 快耗尽才申请导致池子提前关闭；Databricks 拿走 15/33 个共享 session 却不产生下游收益；Gemini 提前大批量申请保住性能。
推广场景：(1) 公司内部算力/预算申请机制——按外部性而非部门自报收益审批；(2) 公共基金资助评审；(3) 多 agent 系统的 credit assignment；(4) 云资源预留 vs 按需抢占的容量规划。

**灵感六：接力式 session + 外部记忆优于无限长对话。**
核心思想：长期任务中，"干净的上下文 + 持久化的状态与记忆"比"连续不断的对话"更稳、更省。
论文证据：多 session 设计实测优于单长 session；附录显示其与 CLM（Context Language Models）、原生压缩对比仍有优势或持平（1.049 vs 1.044/1.032）。
推广场景：(1) 长期运行的个人助理架构；(2) 人机协作的长项目交接协议；(3) 数据库连接池的冷热重建；(4) 人类的工作日志/交接文档制度——论文的 memory/notebook 设计几乎是人类实践的镜像。

**灵感七：把"诚实的负结果"写进激励契约。**
核心思想：开放目标下，允许并记录"试过且无用"与强制产出同样重要——没有负结果档案的团队会无限重试死路。
论文证据：Charter 明确"报告诚实的负结果（附数字）是好结果；简要记录教训，避免无新证据重试"。
推广场景：(1) 科研项目的无效实验登记；(2) 销售/招聘管道的死单复盘；(3) agent 训练中负结果轨迹的数据价值；(4) 代码库中"此路不通"的架构决策记录（ADR）。

## 附录B：所有权与预算实验的案例档案

论文附录 D 的三个案例值得单独立档，因为它们揭示了分数背后的行为机制：

**三个 agent 写同一段代码**。十个无分派 Opus 同时启动，前八份工作计划没有一份覆盖 databricks-sql-connector。十二分钟内四个维护者在该包同一部位开出 PR：三个以几乎相同方式重写同二十行（其中两个 commit 相差一秒），第四个在邻近文件重复其中一个改动。六位维护者评论/审查了这四个 PR，一个被关闭、两个被削减。这是"无分派 = 公共子问题重复求解"机制的微观标本。

**一个被错误宣判"不可构建"的包**。构建 requests-gssapi 需要系统库，而环境初始系统包列表为空，普通安装会报"库不存在"。十维护者运行中一位宣布该包不可构建、劝退众人；另一位数出已有四人达成同样结论、提议别再浪费时间；首位报告九分钟后，第三位刷新包列表、装上库、跑通测试——首位撤回报告并反省：大家的一致"衡量的是共同方法，而非真理"。四人与六人的无分派运行重复了同样的错误与纠正。agent 群体中错误结论会像流行病一样传播并自我强化为"共识"。

**预算捐赠的微观图景**。guided Opus 运行中 requests-gssapi 维护者在 urllib3 识别出一个可能的优化后，捐出自己四个 session；guided Gemini 运行收尾时 databricks 维护者把三个 session 给 requests、两个给 urllib3。捐赠确实发生——资源分配的失败不是因为冷漠，而是因为判断框架（自报收益 vs 全局收益）错位。
