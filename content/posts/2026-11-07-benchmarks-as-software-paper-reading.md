> **领域标签**：cs.AI / Agent 评测 / 基准工程

## 一、论文背景

### 1.1 Agent 基准的「保质期」问题

Coding agent 是当前 LLM 经济价值最高的落地场景之一，而 agent 基准分数直接塑造产品宣传与研究投资方向。我们习惯把基准当成「静态数据集」：发布时验证一次，之后分数就可以长期比较。但这篇论文的开篇洞察是——**agent 基准不是静态数据集，而是活在一个持续演化的生态系统（依赖、基础设施、agent 本身）中的软件系统**。

传统静态数据集（如 ImageNet）的失效模式主要是「过拟合/污染」：模型见过测试数据。而可执行 agent 基准多了一类独有失效模式：**任务本身会烂掉**。论文称之为 benchmark maintenance debt（基准维护债）——任务侧缺陷不断累积，导致基准分数与它本来要测的能力之间出现越来越大的鸿沟。

### 1.2 维护债从哪里来：任务生命周期上的三个「失败面」

论文将一个 agent 任务的生命周期分为任务设计、agent 执行、验证三个阶段，每个阶段都会引入特定缺陷（Fig. 1），归纳为三大类：

- **指令-验证不匹配（instruction–verification mismatch）**：任务说明书（instruction.md）和评分代码（tests/）打架。子情形包括：指令欠规范——隐藏约束只出现在测试里，agent 无从得知；测试过规范——agent 按说明书做对了却被判错。
- **环境问题（environment issues）**：任务原则上可解，但 Docker 环境、CPU/内存/磁盘/网络配置让 oracle（参考解）、verifier 甚至正常的 agent 解无法可靠运行。典型如贡献者按自己机器的资源用量设置预算，结果预算太紧。
- **任务漂移（task drift）**：任务依赖的外部状态（包版本、公共 API、网页内容）在发布后发生了变化，导致失败与 agent 能力无关。

### 1.3 为什么「发布时验证」救不了你

Terminal-Bench 2.0（TB2.0）是一个绝佳的实证案例：它的任务在发布前经历了**人工审查、LM 辅助审计、exploit 红队测试**三重关卡——这已经是业界最严格的上线流程之一。然而发布数月内，其 issue 跟踪器累积了 **50+ 个被标记为任务缺陷的公开报告**。这说明：发布时的验证无论多严格，都无法覆盖「时间」这个维度引入的缺陷。

而且缺陷报告本身不等于缺陷确认：一份报告不能确立原因，也不能证明某个修复是对的。论文观察到一些社区提议的修复只是「贴创可贴」——比如放宽一个正则或扩大接受条件——治标不治本。维护者需要一套一致的流程来：确认缺陷成立 → 审查修复方案 → 检查修复保留了任务本意。

### 1.4 已有应对路线的局限

- **冻结环境**：用保真度换可复现性（环境冻结了，与真实生态脱节）。
- **过滤任务**（如 SWE-Bench Verified）：用覆盖面换精确度（基准变小了，没有修复）。
- **刷新题库**（如 LiveCodeBench/LiveBench）：保持任务未被模型见过，但**不修复发布后烂掉的任务**。

三条路线都把验证当成一次性动作（one-shot curation pass）。本文的主张是第四条路：**像维护软件一样持续维护基准**——毕竟基准有版本、有依赖、有 bug 报告、有回归测试需求，它本来就是软件。

### 1.5 另一条暗线：资源预算也是测量规范的一部分

同一任务在不同时限、内存限制、沙箱配置下会表现出不同结果。论文的第二个主张是：**资源预算不是工程的琐碎细节，而是测量规范（measurement specification）的一部分，必须与任务本身一起被验证**。这为后文「harness 差距主要是速度差异」的发现埋下伏笔。

## 二、论文定位和关联工作

论文把自身置于「基准审计」研究谱系中，并明确与三类前序工作划清边界：

### 2.1 谱系一：基准修订与重采样验证

- **Recht et al. 2019（ImageNet-V2）**：重采样 ImageNet/CIFAR 测试集，用原测试集与新测试集的秩相关（rank correlation）判断基准是否测得稳定的构念（construct）。**本文直接沿用该协议**（比较修订前后的 Spearman ρ），但应用到一个不同的失效模式上：可执行 agent 基准的任务侧缺陷，而非静态图像数据集的分布漂移。

### 2.2 谱系二：验证-过滤路线

- **SWE-bench Verified（OpenAI 2024）**：雇佣专业开发者审计 SWE-bench，发布保守过滤后的子集。
- **WebArena Verified（ServiceNow 2026）**：对 WebArena 应用类似的「验证子集」方法。
- **相关审计工作**（Yu et al. 2025 UTBoost、Zhu et al. 2025 ABC）：识别出解泄漏、弱测试套件、任务/结果有效性失败等问题。

这些方法的共同局限：**把验证当作一次性整理，产出是缩小的基准而非修复的基准**。

### 2.3 谱系三：时间窗/刷新路线

- **LiveCodeBench（Jain et al. 2025）、LiveBench（White et al. 2025）**：持续加新题以对抗污染与过时。精神上最接近持续验证，但它们靠「换血」而非「治病」。

### 2.4 谱系四：审计工具栈

- **ABC 检查清单（Zhu et al. 2025）**：提供结果有效性与任务有效性的审计准则（rubric）——本文的审计 rubric 直接以其为基础，但改造为「面向维护」的少量动作导向缺陷标签。
- **Docent（Meng et al. 2025）、LangSmith**：摄取基准轨迹供大规模检视的证据收集工具。
- **红队工具**：搜索 agent 骗过测试的路径。

本文的组合创新：rubric 定标准 + 证据收集 + 红队找候选缺陷 + 人类裁决，**首次将这些成分组装成持续运行的工作流并实际发布了一个修复版基准（TB2.1）**。

### 2.5 谱系五：Agentic 评测的 harness/环境效应

- **SWE-agent（Yang et al. 2024）等**：agent-computer 接口显著影响表现——harness 效应有据可查。
- **Merrill et al. 2026（Terminal-Bench 论文）**：平均而言 harness 选择的影响小于模型选择。
- **Anthropic 2026**：仅基础设施配置就能移动 agent 编码分数。

本文在两点上扩展：(1) 平均值掩盖了厂商内部的巨大 harness 差距（部分模型约 20pp）；(2) 这些差距在默认时限下**主要反映速度而非能力**。

### 2.6 与同期 Z.ai 审计的关系（重要对照）

Z.ai 曾发布 Terminal-Bench 2.0 Verified（TBV）：对全部 89 个任务应用环境修复（如安装 procps、限制 caffe-cifar-10 可见核心数），仅环境修复就把 Claude Opus 4.5 从 52.4% 抬到 57.9%（+5.5pp，环境缺陷而非任务内容也能移动榜单的早期证据）；另修复 11 个指令与测试不一致的任务。TB2.1 修复了这 11 个任务中的全部，其中 4 个采纳了 TBV 的修复。两个核心分歧：

1. 指令与测试冲突时，**TBV 改指令**（把评分器的期望写进说明书，等于告诉 agent 部分解法）；**TB2.1 更常改测试**（接受任何正确解，保持任务难度为贡献者本意）。
2. TBV 把任务镜像适配到特定 harness（甚至加注释告诉 agent 别用 Read 工具读图片/PDF）；**TB2.1 不做任何 harness 特定修改**，所有 agent 面对同一任务。

### 2.7 定位总结

| 维度 | 之前的路线（过滤/冻结/刷新） | 本文的突破 |
|---|---|---|
| 验证时机 | 发布时一次性 | 发布后持续（post-release continuous） |
| 对缺陷的处理 | 过滤掉 / 回避 / 换新题 | 修复并记录（repair + document） |
| 谁来审计 | 人工专家（贵、慢） | agent 工作流初筛 + 人守门 |
| 资源预算 | 工程细节，不验证 | 测量规范的一部分，随任务一起验证 |
| 产出 | 缩小的子集 | 修复的完整基准（TB2.1）+ 可复用工作流 |

## 三、问题定义

### 3.1 从具体场景到抽象问题

**具体场景**：TB2.0 发布几个月后出现 50+ 缺陷报告，维护者人肉逐条核对根本看不过来；而且就算修了，也不知道修复会不会颠覆已有排行榜结论。

**核心洞察**：基准维护与软件维护存在深层结构相似性——可以把「基准维护」类比为「持续集成软件工程」：

| 软件工程概念 | 基准维护中的对应物 |
|---|---|
| bug 报告 / 崩溃日志 | 社区 issue / agent 执行轨迹 |
| 静态代码分析 | rubric 驱动的任务审计 |
| 单元测试 / 回归测试 | oracle 重建 + 参考解重跑（/oracle 检查） |
| code review + 门禁 PR | 维护者审查 agent 起草的修复 diff |
| 版本发布（tag + changelog） | 带编号的数据集版本 + 任务级 digest |
| CI 触发（push/PR 自动跑） | GitHub Actions 手动/自动触发 /audit、/oracle |

**抽象问题**：给定一个已发布的可执行 agent 基准 B = {任务 t₁...tₙ}，以及三类持续可得的证据流（任务规范文件、历史执行轨迹、社区报告），设计一个工作流 W，输出每个任务的审计结论（缺陷标签 + 引证证据 + 候选修复 diff），并满足三个约束：

1. **一致性**（agent 无关性）：不同 auditor agent 在同一 rubric 下给出相似的缺陷归因；
2. **可负担性**：低成本模型也能承担大部分初筛；
3. **安全性**（propose-only）：agent 永远不能直接改仓库状态，人类守门放行。

再加一个测量论层面的问题：修复后，**哪些结论是稳定的**（排行榜大体不变？）**哪些会翻**（个体分数？效率结论？）——即把 Recht et al. 2019 的秩相关协议从数据集修订迁移到任务侧修复。

### 3.2 形式化设定

- **任务五元组**：Instruction（自然语言题目）/ Environment（Docker 镜像）/ Oracle（已知正确解）/ Test（评分代码）/ Resources（CPU、内存、wall-clock 预算）——「任务是一份带资源约束的限时考试」。
- **agent / harness / trial**：agent = 模型 + 工具；harness = 给模型配工具与环境交互的系统；trial = 一次独立尝试。
- **指标**：p̂ₐ,ₜ 为 agent a 在任务 t 上 nₐ,ₜ 次 trial 的平均奖励；coverage（pass@k）用 Chen et al. 2021 的无偏估计子。
- **两套数据**：证据数据（外部证据 + 榜单 trial 数据，用于发现并修复缺陷、产出 TB2.1）；评估数据（19 个 agent 在 TB2.0/TB2.1 上的 trial，用于测量修复效果）+ 一个故意偏离基准指南的加大资源条件（成本原因只跑了部分 agent）。

### 3.3 这个抽象的精妙之处

把「修基准」从「人肉考古」变成「证据编译 + rubric 判定 + oracle 回归测试 + 人审门禁」的流水线，每一步都可审计、可复现、可交给 agent 但最终由人负责——这正是软件工程几十年沉淀出的 CI/CD 智慧。缺陷分类（三大类）刻意做成「动作导向」（tied to likely repairs）：标签直接暗示修复方向，而非宽泛的自由文本有效性判断，这让跨 agent 报告可比较，也给维护者具体的审查靶点。

## 四、问题解法

### 4.0 全景：三 agent 持续验证流水线

```
01 COLLECT EVIDENCE ──► 02 AUDIT BENCHMARK ──► 03 VERIFY REPAIR ──► 04 RELEASE UPDATE
  证据收集 agent              审计 agent               验证 agent             人审放行
  ├ 任务静态文件              ├ 应用 rubric             ├ 重跑 oracle           TB2.1
  ├ 历史 agent 轨迹           ├ 缺陷标签+引证           ├ 挑战标签              (repair & re-audit)
  └ 外部社区报告              └ 候选修复 diff           └ 查缺失证据
```

### 4.1 组件一：证据收集 agent（Evidence Collector）

**输入**：任务规范（instruction.md、environment/、tests/、solution/）、公开的执行轨迹、社区报告。
**输出**：结构化的任务级证据报告。
**设计原则**：**观察与裁决分离**——它只负责把三类互补证据流组织好供给下游 auditor，自己不下结论。这类似软件工程里「日志收集器不做告警判断」的关注点分离。

### 4.2 组件二：审计 agent（Auditor）与 rubric

**为什么必须有 rubric**：没有 rubric，agent 能标记可疑行为，但行为不一致、输出难解析。本文在 ABC 指南基础上改造，要求 auditor 给出**一个主缺陷类别 + 可选次级标签**，四选一：

| 主标签 | 判定条件 |
|---|---|
| No defect found | 任务规范良好、oracle 被接受、verifier 检查预期行为、资源预算充足 |
| Instruction–verification mismatch | 指令与 verifier 不一致（欠规范指令的隐藏约束只在测试里 / 过规范测试拒绝按说明书正确的解） |
| Task drift | 发布后因可变外部状态（包版本、网络资源、公共 API、网页内容）任务变了 |
| Environment issues | 任务原则可解，但环境/资源阻止 oracle、verifier 或有效 agent 解可靠运行 |

**输出**：主缺陷标签 + 简短理由 + 缺陷位置 + 候选修复。产出以「带证据的草稿 PR」形式进入修复工作流。

### 4.3 组件三：验证 agent（Verifier）——为「任务漂移」而设

verifier 审查证据与 auditor 的标签：**运行 oracle、挑战提议的标签、识别缺失证据、检查修复是否治本**。增设这一阶段的直接原因：试运行中发现**仅靠审计对 task drift 的捕捉不可靠**（低成本 auditor 对 drift 的逐类一致性 κ 只有 0.21–0.41）。而漂移缺陷天然有个确定性检测器——**每个漂移缺陷都会破坏参考解的执行**，所以「重跑 oracle」这条确定性检查（/oracle）不管 auditor 标签怎么打都能兜住 drift。这个「LLM 判不准的地方用确定性程序兜底」的分工是整个工作流最实用的工程智慧之一。

### 4.4 修复约定（Repair Conventions）——修复不是机械活

每类缺陷的修复原则（涉及人类判断，遵循 Zhu et al. 2025 的专家指南）：

- **指令-验证不匹配**：任何满足「按说明书写的任务」的解都被接受；无效解被拒绝。
- **任务漂移**：尽可能移除依赖使任务可复现；移除不了就 pin 住版本。
- **环境问题**：设定**可行性下限（feasibility floor）**——已知正确的 oracle 解与 verifier 必须在基准预算内可靠运行。
- **资源调整细则**：把起约束作用的资源轴（wall-clock/内存/CPU，可多条）调到「最接近原始提议的因子，或至少 oracle+verifier 观测需求的 1.5 倍」。双重目的：(1) 防止基础设施噪声造成假阴性（正确解不该因为 verifier 勉强塞进预算而失败）；(2) 不过度放水——资源设定任务难度，尽量贴近任务贡献者的本意。作者拒绝按任务逐个调优预算（那需要对任意资源做反复扫掠，还会引入额外主观设计选择）；可行性规则虽保守，但**可审计**。
- **共享修复规则**：修复若改变了任务难度，**记录变化而不是把任务调回原来的通过率**——不向通过率看齐，这是维护诚实度的重要纪律。

### 4.5 工程落地：GitHub Actions + propose-only 安全模型

流水线实现为 GitHub Actions，可手动调用或在对某任务的 PR 上自动触发。暴露两个检查命令：

- **/audit**：调 auditor agent 审查任务指令与可用 trial 日志；
- **/oracle**：重建任务环境并运行参考解，检查已知正确解仍能通过。

**安全设计（关键）**：尽管技术上可以给 agent 合并 PR 的权限，工作流被刻意限制为 **propose-only**——每次运行上限 5 轮修复迭代；agent 可开 PR 但**不能直接改仓库状态**；修复以维护者可审查的 diff 形式输出到 `audit/changes/<task>.diff`；人类审查门禁放行后才进入发布。整个 rubric 已集成进 Terminal-Bench 主仓库的持续任务审查流程（TASK_REVIEW_AUTOMATION.md）。

### 4.6 防泄漏与评估协议

为防止 auditor 从社区报告（工作流设计要消费的证据）中「抄答案」造成评估泄漏，**所有评估运行禁用 auditor 的 web 搜索工具**（部署时保持开启）。工作流评估沿三个维度：agent 无关性（不同 auditor 标签是否一致）、低成本可用性（便宜模型行不行）、作为维护者在环 triage 系统的精度/召回。缺陷类别定义来自 15 任务试点子集 + 约 1500 次 TB2.0 执行 trial（试点只固定类别定义，不固定逐任务标签，避免循环论证）。

## 五、评估指标与实验证据

### 5.1 指标体系一览

| 指标 | 定义 | 衡量什么 | 方向 |
|---|---|---|---|
| Cohen's κ（审计者间一致性） | 两个 auditor 对同一任务集合标签的一致程度（校正 chance） | 工作流的 agent 无关性 / 低成本可用性 | 越高越好 |
| Precision / Recall（vs TB2.1） | 工作流标记 vs 人裁修复集 | triage 系统的过滤质量 | 越高越好 |
| Spearman ρ（TB2.0 vs TB2.1 排名） | 19 agent 两版榜单秩相关 | 排名稳定性（沿 Recht 2019 协议） | 越高越稳 |
| Accuracy（%） | 平均奖励 | 基础能力 | 越高越好 |
| Coverage（pass@k 无偏估计） | 至少一次成功的概率估计 | 资源预算扫描下的能力上界 | 越高越好 |
| 超时占比（% of failed trials） | 失败 trial 中超时结束的比例 | 效率瓶颈定位 | 越低越好 |

### 5.2 数据集与规模

- **审计对象**：TB2.0 全部 89 个任务（Terminal-Bench 2.0，ICLR 2026，89 个高难度真实终端任务，含 Docker 环境/oracle/tests）。
- **评估对象**：19 个 agent（模型 × harness 组合），来自 Anthropic（Claude Opus 4.6/Sonnet 4.6）、OpenAI（GPT 5.5/5.4/5.4 mini/5.3 Codex）、Google（Gemini Pro 3.1/Flash 3/Gemma 4 31B）、Z.AI（GLM 5.1）、Moonshot（Kimi K2.6）、Alibaba（Qwen 3.5 9B/27B）；harness 含 terminus-2（基线）、claude-code、codex、gemini-cli。
- **外部验证**：Harbor-Index v0.1 开发中 80 任务快照里随机抽 34 个（来自 29 个源基准的共享格式重实现）。

### 5.3 实验一：工作流本身的可靠性（κ 一致性）

**结果 1——强 auditor 高一致**：Claude Code (Opus 4.6) 与 Codex (GPT-5.4) 两个托管编码助手在全部 89 个任务上的主缺陷类别（含「无缺陷」）一致性 **κ = 0.80**。

**结果 2——低成本 auditor 可用于 triage 但不擅归因**：低成本 API auditor 在二元 triage（flag vs clean）上 pairwise κ = 0.55–0.77（gpt-4o-mini vs gemini-2.5-flash 最高 0.769，即 89 题中 79 题一致）；但逐类归因一致性（one-vs-rest）中等偏低的：指令-验证不匹配 κ=0.60、环境问题 κ=0.59、**任务漂移 κ=0.21–0.41（低）**。

**为什么这不致命**：因为每个 drift 缺陷都破坏参考解执行，确定性 /oracle 检查能无视标签兜住 drift。结论：强 auditor 在 triage 和归因上都基本 agent 无关；低成本 auditor 可靠做 triage，归因交给 oracle 检查 + 维护者审查。

**注意**：一致性衡量的是 consistency 而非 correctness——两个 auditor 可以一致地错。

**结果 3——对最终 TB2.1 的回顾性精确率/召回率**：57.1% precision / 71.4% recall。作者诚实声明：由于工作流本身参与了修复集构建，这些指标衡量的是与发布的回顾性一致而非独立缺陷发现——**工作流应被视为 triage 工具，输出由维护者审查过滤**。

### 5.4 实验二：审计发现了什么（TB2.0 → TB2.1）

工作流在 TB2.0 中暴露 **28 个任务有问题（约占基准 1/3，28/89）**。来源合并：先前 Terminal-Bench Verified 标记的 11 个 + 公开 issue/PR 处理的 5 个 + 审计新发现的 14 个（有任务在多个来源重复出现，合计 28）。逐任务缺陷类别分布（一题可多标签，来自论文 Fig. 3a 与 Table 2）：

| 缺陷类别 | 占 28 个修订任务比例 | 任务数 | 典型例子 |
|---|---|---|---|
| 指令-验证不匹配 | **57%** | 16 | query-optimize：verifier 强制求数据库文件逐字节保留——指令里根本没这要求；修复=把限制显式写明 |
| 任务漂移 | **43%** | 12 | 依赖外部状态的 mteb-leaderboard/mteb-retrieve 等；修复=移除依赖或 pin 版本 |
| 环境问题 | **29%** | 8 | 预算太紧，oracle/verifier/agent 撞内存或磁盘上限（Fig. 3c）；执行后端 Docker/Dayona 在文件系统隔离、内存限制、网络暴露上的差异 |

修复难度分布：28 个修订任务中 **19 个 hard、7 个 medium、2 个 easy**——修的大多是难题，这直接预测了修复收益将集中于强 agent（弱 agent 本来就做不出难题）。

### 5.5 实验三：修复如何改变评测结论（核心结果）

**准确率整体抬升但排名基本稳定**：19 个 agent 在 TB2.0 vs TB2.1 上的准确率 Spearman **ρ = 0.958**（task-bootstrap 95% CI [0.881, 0.979]），OLS 拟合 TB2.1 = 2.1 + 1.04·TB2.0。但个体分数移动非平凡——**整体准确率提升 10+ 个百分点级别的分布移动，榜位最多移动 3 名**：

- Claude Code + Claude Opus 4.6 比拟合线高出 7pp+，攀升 3 位；
- 两个最弱 agent（TB2.0 准确率 < 40%）双双低于拟合线且在 TB2.1 上掉分（难题修复与它们无关，部分任务反而被收紧）。

**收益集中在指令-验证不匹配**：5 个任务修复（以 verifier 为中心）后从「通过率 ≤15%」跃升到「>50%」，贡献了修改任务子集总绝对通过率变化的约 **62.7%**——本质是 TB2.0 一直没认出 agent 的正确解。反面也有：审计移除假阳性分或收紧规范后，23 个其余修改任务部分出现 TB2.1 通过率下降（如 overfull-hbox 从 53.3% 降到 36.7%——TB2.0 里一个坏的环境构建让 verifier 丢了 ground truth，把错误输出也计了分）。修复后**没有任何任务保持无人解出**。

代表性逐任务通过率变化（Table 7 摘录，跨全部 agent 平均）：

| 任务 | TB2.0 | TB2.1 | 变化 |
|---|---|---|---|
| caffe-cifar-10 | 5.0% | 69.2% | +64.2pp（环境+内存+CPU 修复） |
| sam-cell-seg | 0.0% | 53.3% | +53.3pp |
| polyglot-c-py | 5.0% | 80.0% | +75.0pp |
| polyglot-rust-c | 5.0% | 66.7% | +61.7pp |
| torch-tensor-parallelism | 15.0% | 66.7% | +51.7pp |
| install-windows-3.11 | 0.0% | 23.3% | +23.3pp |
| mteb-retrieve | 15.0% | 41.7% | +26.7pp |
| overfull-hbox | 53.3% | 36.7% | −16.6pp（收紧：修复了误判分的 verifier） |
| make-doom-for-mips | 6.7% | 1.7% | −5.0pp（收紧） |

### 5.6 实验四：资源预算与效率前沿

**超时主导失败**：默认时限下，**全部失败 trial 中 50%+ 以超时告终**；按 harness 分层：claude-code **68%**、Terminus-2 67%、Codex 25%、gemini-cli 18%（Fig. 3b）。对最弱的 agent-模型对，超时完全主导（Appx. C.2 白名单分解：Gemma 4 31B、Kimi K2.6、Qwen 3.5 9B、GPT 5.4 mini 配 terminus-2 的格子大多在 agent 结束前就耗尽）。另一个细节：**11.8% 的超时 trial 按当时状态评分后其实通过**（超时不等于失败）；约 27% 的上游 trial 因基础设施错误（runner 失败、provider 中断、认证错误、沙箱崩溃、setup 超时）被过滤。

**预算扫描设计**：对每个 agent-模型对，把 wall-clock 预算提升至原任务超时的 **32×**，测量覆盖随预算的爬升（agent 做完可提前退出，32× 是上界）。除最小的 Qwen 3.5 外，最大预算下几乎没有超时残留——**剩下的失败不是超时伪影，这些任务在测试配置下就是无人能解**。

**六个 agent-模型对的效率前沿（Fig. 5）**：

- **GLM 5.1（配 Claude Code 作参考点，处在效率前沿上）**：曲线显著靠左——以小得多的预算达到高覆盖；TB2.1 上比 TB2.0 多解 8 个任务，**超越 GPT 5.4**（后者覆盖几乎不变）——效率排名也会被基准版本改变。
- **GPT 5.4**：最终覆盖也高，但以更多 token 为代价。
- **小模型（Qwen 3.5 9B/27B、Gemma 4 31B）**：预算加大能多解不少任务，但曲线在更低覆盖处变平。

**Harness 差距主要是速度（Fig. 6，within-vendor 诊断）**：默认时限下 Codex harness 大幅领先 Terminus-2：

| 模型 | 1× 超时 Codex / Terminus-2 | 32× 超时 Codex / Terminus-2 |
|---|---|---|
| GPT 5.4 | 74.2% / 53.9%（**差距 ~20pp**） | 74.9% / 68.2%（差距收窄到 ~7pp） |
| GPT 5.4 mini | 75.3% / 37.1%（**差距 ~38pp，默认协议下 30pp 级**） | 67.0% / 62.9%（**差距缩至 ~5pp**） |

（注：摘要口径为「延长时限关闭 GPT 5.4 上 20pp harness 差距、把 GPT 5.4 mini 的 30pp 差距缩到 5pp」。）结论：harness 选择对 GPT 5.4 的影响（~20pp）可与模型间差异相提并论，但**给慢 harness 更长时间能收回大部分差距——差距主要反映时限下的速度而非能力**。因此固定预算是一个任意操作点：应设定有原则的可行性下限并做预算敏感性测试，而不是对某组 agent/模型校准。

### 5.7 实验五：外部有效性（Harbor-Index v0.1）

把工作流应用到 Harbor-Index v0.1 开发中 80 任务快照的随机 34 个任务（29 个源基准、共享格式重实现——重实现天然带来指令/环境/评分逻辑的新缺陷机会）。Harbor 团队人工审查全部 34 个（含工作流未标记的）：

- 工作流标记 14 个，人工确认 12 个为缺陷——**精确率 86%（12/14）**；
- 发现的缺陷含指令-验证不匹配、基础设施失败、可变外部状态依赖。实例：数个 GAIA2 任务因辅助评分服务在错误条件下被调用而拒绝正确参考解；GSO 的指令漏了 grader 要求的条件；
- **漏检案例**（诚实披露）：Lab-Bench 的错误参考答案、QCircuitBench 的非确定性评分、HLE 指令存在两个合理正确答案——提示需要基准特定检查、重复执行与领域专家介入；另有共享评分代码的 2 个 bug 波及 13 个任务（GSO grader 把 agent 产出的程序执行了两次；GAIA2 grader 错误处理特殊字符）。

结论：工作流可迁移到 Terminal-Bench 之外；漏检案例界定了其能力边界。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**解释 1：为什么持续 agent 工作流能发现「发布时三重验证」漏掉的缺陷？**

因果链：发布时验证（人审+LM 审计+红队）只能检查「当下」的任务快照 → 漂移类缺陷随时间发生（发布时不存在，无法被当时发现）+ 人工审计带宽有限无法逐条消化 50+ 报告 → 持续工作流把三类增量证据流（新轨迹、新报告、静态文件）持续编译成结构化审计对象，并用确定性 /oracle 回归测试兜底 → 缺陷发现从「一次性全量人检」变为「持续增量 triage + 人审瓶颈环节」。
【论文实验已支持：28 个缺陷中 14 个为审计新发现；drift 12 例为发布后新增失败面；/oracle 对 drift 的确定性捕获弥补了 κ=0.21–0.41 的 auditor 归因短板。】

**解释 2：为什么修复指令-验证不匹配带来最大的分数抬升？**

因果链：该类缺陷的本质是「测量仪器坏了」——verifier 系统性拒绝正确解 → 修复后 agent 的真实能力第一次被计分 → 通过率从 ≤15% 跳到 >50%（5 个任务贡献 62.7% 的绝对变化）→ 这不是 agent 变强，而是**假阴性被消除**。
【论文实验已支持：Sec 6.1 的逐任务数据；对照 overfull-hbox 反向案例——假阳性被消除时分数下降，同一机制的两面。】

**解释 3：为什么 harness 差距主要是速度而非能力？**

因果链：固定 wall-clock 预算把「能力」与「单位时间产出」卷积成一个数 → 慢 harness（如 terminus-2 的 JSON-action 解析、通用脚手架开销）在预算内完不成任务 → 32× 预算解除了速度约束 → 差距从 ~20pp 收到 ~7pp、从 30pp+ 收到 ~5pp → 说明默认协议下的 harness 差距大部分是「时限下的效率」而非「可达覆盖」。
【论文实验已支持：Fig. 6 的 within-vendor 对比；Fig. 5 中除小模型外最大预算下几乎无超时残留。】【边界标注（阅读者推测）：速度差距的内部来源（工具调用粒度、上下文压缩策略差异）论文未分解，「32× 后仍剩 ~5–7pp」的残差是能力差异还是收敛噪声，论文未给出显著性检验。】

### 6.3 综合判断与未决问题

- **多研究共同支持的机制**：(1) 测量栈因素（任务缺陷、环境、资源预算）对 agent 基准分数的影响是真实且量级可观的——本文（10+pp 分布移动）、Z.ai（5.5pp）、Anthropic（infrastructure noise）三方独立一致；(2) rubric 驱动审计能发现指令-验证类缺陷——ABC 与本文均以其实证；(3) 修订后排名秩相关协议可量化稳定性——Recht 协议在两种基准形态下均可用。
- **仍属推测/单源的机制**：「harness 差距 ≈ 速度差距」目前主要来自本文 32× 扫描的 within-vendor 证据，残差归因未做统计检验；低成本 auditor「可靠 triage、归因弱」的模式是否泛化到其他 rubric/基准未知。
- **优势成立条件**：工作流假设存在活跃的社区报告与公开轨迹（证据流依赖社区健康度）；propose-only 门禁依赖有带宽的维护者；修复效果结论基于「28 个缺陷任务」这一特定修复集，更大的修复比例（如 >50%）是否仍保持 ρ≈0.96 存疑。
- **可能的失效条件**：基准无社区（无 issue 可收）；任务无 oracle（无法跑 /oracle 回归）；执行轨迹不公开（证据流缺失）；预算扫描成本高昂（32× 时间×多采样只覆盖了部分 agent）。

## 七、必要知识反推

假设让一个完全没背景的人复现这项工作，最少必须掌握：

### 7.1 领域知识层

- **Agent 基准的解剖学**：instruction/environment/oracle/test/resources 五件套，以及 harness、trial、pass@k 的含义。不懂这个就无法定义「任务侧缺陷」的攻击面。
- **Terminal-Bench 生态**：TB2.0 的发布验证史（人审/LM 审计/红队）、issue 跟踪器、GitHub 工作机制——证据流的来源全在这。
- **三大缺陷类别的领域语义**：能区分「agent 做错了」「任务错了」「环境错了」三件事——这是 rubric 设计的前提。

### 7.2 方法论知识层

- **测量论与秩相关协议**：Recht et al. 2019 的「修订-重相关」方法、Spearman ρ、task-bootstrap 置信区间——排名稳定性结论的统计基础。
- **标注一致性理论**：Cohen's κ 的含义、chance 校正、one-vs-rest 多标签降级——没有它无法评估「工作流是否 agent 无关」。
- **ABC 审计准则**（Zhu et al. 2025）：rubric 的前身；以及「标签要动作导向、绑定修复」的维护工程直觉。
- **无偏 pass@k 估计**（Chen et al. 2021）：覆盖曲线的统计工具。

### 7.3 工程知识层

- **Agent 工作流编排**：多 agent 分工（收集/审计/验证）、propose-only 权限模型、5 轮修复迭代上限、GitHub Actions 触发机制（/audit、/oracle 命令）。
- **可执行基准基础设施**：Docker 环境构建、oracle 重建与重跑、Docker/Dayona 后端在文件系统隔离/内存限制/网络上的差异——环境修复的实操知识。
- **大规模评测运维**：19 agent × 两版基准的 trial 管理、基础设施失败白名单过滤（~27% 上游 trial 被滤）、超时 trial 仍评分（11.8% 通过）等细节——不懂这些会把基础设施噪声当模型行为。
- **模型/harness 配置矩阵**：reasoning_effort、temperature、proactive summarization 阈值（8K→131K 的调整逻辑：Gemma 4 31B/Kimi K2.6 的 256K 窗口下默认阈值导致压缩过晚）——控制变量的前提。

### 7.4 知识融合的关键节点

1. **「基准=软件」的类比迁移**：把 CI/CD 的「证据→分析→回归测试→人审门禁→版本发布」心智模型迁移到基准维护——这是三 agent 工作流形态的来源，没有这个类比，最自然的做法还是「再组织一轮人工审计」。
2. **「确定性检查兜住 LLM 弱项」的分工洞察**：发现 drift 是 auditor 一致性最低的类别（κ=0.21–0.41），同时观察到「每个 drift 都破坏参考解」——把 LLM 判不准的类别交给 /oracle 确定性检查，是统计诊断与工程可行性融合的节点。
3. **「预算即测量规范」的视角转换**：把资源预算从「工程参数」提升为「测量规范的一部分」，才有了 32× 扫描对 harness 差距的因果分离（速度 vs 能力）——这是把评测方法论（构念效度）与系统性能分析（效率前沿）融合的节点。
4. **「修测试不改指令」的修复哲学**：与 Z.ai Verified 的分歧点（改指令=泄题给 agent；改测试=保住任务难度）需要同时理解任务有效性理论与 agent 行为——两个知识域在修复约定上交汇。

## 八、论文中可以提取的通用性灵感

### 灵感 1：评测资产的「维护债」视角——评测是软件，不是数据

- **核心思想**：任何依赖外部世界（包、API、网页、基础设施）的评测资产都会持续腐烂，必须像软件一样版本化、持续验证、带变更记录地维护。
- **论文证据**：发布前三重验证的 TB2.0 数月内累积 50+ 缺陷报告；28/89 任务有缺陷；12 例 drift 全部发生在发布后。
- **推广场景**：(1) RAG 系统的知识库评测集（网页内容漂移）；(2) 推荐系统的离线评测（用户行为分布漂移）；(3) 自动驾驶仿真场景库（地图/路况数据过时）；(4) 医疗 AI 评测（诊疗指南更新）；(5) 金融风控模型回测（监管规则变化）。

### 灵感 2：确定性检查兜底 LLM 判断——用「必然被破坏的预言机」捕获 LLM 测不准的类别

- **核心思想**：当某类缺陷天然伴随一个可机械验证的信号（如「漂移必然破坏参考解执行」），就让确定性程序负责该类别，LLM 只负责它擅长的语义判断。
- **论文证据**：低成本 auditor 对 drift 归因 κ=0.21–0.41，但 /oracle 重跑参考解对 drift 的捕获与标签无关。
- **推广场景**：(1) 代码审查 agent + 编译/单测兜底；(2) 数据清洗 LLM + schema 校验器；(3) 法务合同审查 LLM + 条款编号完整性检查；(4) 翻译质检 LLM + 术语表匹配；(5) 科学复现 agent + 数值回归测试。

### 灵感 3：propose-only 门禁——AI 参与维护时的权限最小化设计

- **核心思想**：让 agent 参与高质量维护工作（审计+起草修复），但严守「只能提案、不能落笔」，人类掌握最终合并权，并以可审查 diff 形式输出。
- **论文证据**：工作流可开 PR 但禁止直接改仓库状态，每次运行上限 5 轮修复迭代，diff 落盘到 audit/changes/<task>.diff。
- **推广场景**:(1) 数据库 schema 变更的 AI 助手（只出迁移脚本草稿）；(2) 生产配置调优 agent（只出 PR）；(3) 法规合规修改建议（只出对照稿）；(4) 自动化运维（AI 诊断+人批执行）；(5) 学术同行评审辅助（AI 意见仅供参考，编辑决定）。

### 灵感 4：固定预算是任意操作点——报告能力应配效率前沿而非单点分数

- **核心思想**：任何带资源约束（时间/内存/token）的评测，单点分数把「能力」与「速度」卷积在一起；应报告预算-覆盖曲线，或至少做预算敏感性测试。
- **论文证据**：32× 超时使 Codex/Terminus-2 在 GPT 5.4 上 ~20pp 差距基本消失、GPT 5.4 mini 从 30pp 级缩到 ~5pp；50%+ 失败 trial 是超时（claude-code 68%）。
- **推广场景**：(1) 云函数性能评测（冷启动时间 vs 吞吐曲线）；(2) 竞赛编程评测（时间限制对语言的系统性偏置）；(3) 机器人任务评测（电量/时限约束）；(4) 人机交互实验（任务时限对被试群体的偏置）；(5) 数据库查询基准（超时阈值对引擎结论的翻转）。

### 灵感 5：修改评测要「记录难度变化」而非「校准回旧通过率」

- **核心思想**：修复评测资产后，不要为了让历史分数可比而把难度调回原通过率——诚实记录难度变化，让版本号承载不可比性。
- **论文证据**：修复约定明确「修复改变任务难度时记录变化，而不是调回先前通过率」；TB2.0 与 TB2.1 作为两个编号版本并存比较。
- **推广场景**:(1) 考试改革后的分数线衔接（公布而非暗调）；(2) A/B 实验指标口径变更；(3) KPI 体系修订的年度对照披露；(4) 体育规则修改后的纪录分段；(5) 评级机构方法论变更的版本披露。

### 灵感 6：审计标签要「动作导向」——每个标签绑定一个修复方向

- **核心思想**：给 AI 审计者的分类体系应从「学术taxonomy」改为「维护 taxonomy」：少量类别、每类直接暗示修复动作，使报告跨运行可比较、给人明确审查靶点。
- **论文证据**：论文明确说明在维护场景中「少量动作导向缺陷标签」比「宽泛自由形式有效性判断」更有用，四类主标签各自绑定修复约定。
- **推广场景**：(1) 客服工单分类（按处理动作而非情绪极性）；(2) 代码 smell 分类（按重构手法）；(3) 医学检验异常标注（按干预路径）；(4) 安全漏洞分级（按修补策略）；(5) 内容审核标签（按处置动作）。
