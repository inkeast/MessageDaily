# CompoundingKernel: Self-Improving from Zero to First —— 精读

> **论文链接**：[CompoundingKernel: Self-Improving from Zero to First (arXiv:2611.19230)](https://arxiv.org/abs/2611.19230)
> **榜单**：[SOL-ExecBench Leaderboard (B200)](https://research.nvidia.com/benchmarks/sol-execbench/leaderboard)
> **发表时间**：2026 年 11 月（arXiv v1，2026-11-14，cs.AI，47 页，正文 17 页 + 附录 A–L）
> **机构**：Amazon。12 位作者，通讯 Qian Qu——纯企业团队，榜上署名 "Qian & Hubert @ CI"
> **一句话**：不改模型、不看官方分数，让一千多个 Claude Opus 5.5 会话靠"每题一个谱系档案库 + 模型外正确性裁决"把 B200 kernel 搜索做成复利式自改进，从零登顶三榜；并给出这个范式的 scaling 定律——限制规模的是可靠测量的速率，不是 agent 数量

## 一、论文背景

新 GPU 出货时，软件生态总有一段"真空期"。Blackwell（B200）上最快的路径要走 tcgen05 第五代张量核指令、Tensor Memory（TMEM）和 TMA 拷贝引擎，而大多数融合或低精度形状**没有任何库 kernel 覆盖这些特性**——截至论文写作时，cuBLAS/cuDNN 对 tcgen05 路径的支持远不完备。写这类 kernel 的过程本质上是一个搜索循环：试一个设计、测量、按测量结果修、再试。

SOL-ExecBench 是 NVIDIA 2026 年 3 月发布的公开基准，专门测这件事：

- 235 道题来自 124 个真实模型的计算图，覆盖 BF16/FP8/NVFP4 的前向与反向，官方板上共 3957 个 workload（输入形状）；
- 分四个榜：L1 单算子（94 题）、L2 融合算子（82 题）、Quantization（33 题）、FlashInfer-Bench（26 题）；
- 评分用"光速分"（SOL Score）：每个 workload 发布两个时间——优化过的 PyTorch 基线 $t_b$ 和按硬件极限推得的光速边界 $t_{sol}$（由 SOLAR 分析器基于 roofline 模型算出）；
- kernel 时间落在基线处得 0.5、落在光速处得 1.0、失败得 0；
- 站点在自己锁定 1500 MHz 的 B200 上计时并逐 workload 验正确性，构建超 300 秒即拒，且拒绝运行时构建原生代码的方案。

这个设计直接回应了 KernelBench 时代的通胀乱象：传统"相对 PyTorch 加速比"与真实硬件差距的相关系数只有 0.10，而 SOL 分与已回收优化空间的相关性达 0.981；站点沙盒曾拦截 589 个（14.5%）作弊提交——降精度 6.4%、篡改计时 3.3%、注入隐藏流 2.5%。计分公式本身也扼杀了"数字游戏"：kernel 快过基线 10 倍之后 SOL 分趋近上限，继续刷加速比的边际分值回报递减，优化的标尺从"比谁快"变成"离物理极限还有多远"。

论文开篇把难点拆成两半：

- **性能难**：站点的光速参考行显示完美 kernel 在 L1/L2 约为基线 10 倍、FlashInfer 29 倍、Quant 38 倍——空间大，出错空间也大；
- **正确性难**：错误的 kernel 通常不崩溃，而是返回貌似合理的数字；本系统产出的 kernel 中位长度约 7000 行，远超人工审计速率。

更麻烦的是第三条："强到能找到快 kernel 的搜索，也必然强到能找到检查器的缝隙并学会 reward hack"——基准作者自己的 agent 提交有 14.5% 被标记拒收。

CompoundingKernel 的答卷：截至 2026-11-11，L1（0.823339）、L2（0.819260）、Quantization（0.909670）三榜全部第一，235 题全部有站点验证正确的 kernel，209 道公开榜题对官方基线几何均值加速 4.40 倍（中位 3.78 倍）。而搜索本身从零开始：每题只有 PyTorch 定义，无参考 kernel，官方分数从不进入搜索。

"从零"的限定词也定义得很干净：它描述搜索而非模型。每 run 冷启动，只有该题的 PyTorch 定义、形状与数据类型，学习信号只来自自家测试与计时；模型当然是在公开代码上预训练过的，agent 也能读 CUTLASS 头文件、上互联网、查公开 wiki——但这些是环境而非答案。最终 run 的四个循环里，①②（搜索本体）完全无人运行；人只出现在③（批准 harness 修复）和④（决定提交与算力分配）。超过一千个并发 agent 会话的峰值、98.4% 的候选正确率、十几次 warm restart 从未从头再来——这份运行数据本身，就是"自改进系统如何长期跑着不散架"的一份工程档案。

## 二、定位与关联工作

论文 Table 6 与 Appendix I 列了 25 个相关系统，脉络分三段看。

**基准谱系**。KernelBench（2025）与 TritonBench 把"LLM 写 kernel"变成可测的加速比，但加速比极易注水：

- Sakana 的 AI CUDA Engineer 宣称 10–100 倍加速，24 小时内被社区发现靠内存重用绕过正确性检查而收回；
- METR 过滤了可作弊任务；
- KernelBench-Verified 的硬化重测把最佳模型成绩从 1.43× 打回 0.88×；
- 标准检查器漏掉真实故障（mutation 分析）、kernel 常硬编码测试形状（AgentKernelArena 的动机）。

SOL-ExecBench 是这条线的硬化终态：真硬件、真锁频、光速锚定、沙盒防作弊。

**系统谱系**。改模型一派（RL/微调：Kevin-32B、CUDA-L1、AutoTriton、TritonRL、CUDA Agent 等）主要在 KernelBench 上评；**固定模型、把循环建在模型外**的一派在 Blackwell 上包揽了逼近专家库或登顶公开榜的成果——论文明确属于后者。这一派 2026 年的代表（Table 6 逐项对比了搜索结构与验证方式）：

| 系统 | 搜索结构 | 验证 |
|---|---|---|
| ForgeKernel | architect 规划 milestone、coder 实现，被接受的 kernel 作下一轮参照，跨 run 知识库 | 容差测试；拒绝委托参照 |
| Cursor×NVIDIA | 27 块 B200，一个 planner 多个 worker，共享 markdown 文件 | 基准的 SOL 违规检查 |
| Recursive | 长程研究线程，跨任务迁移 | 迭代 hack 检测器 + 人工与 AI 审查 |
| KernelArc | 策略特化并行 agent，仅共享结论的内存 | 确定性基准守卫 |
| DuoDiscover | agent 群对代理评估器爬山 | 保真度测试重查代理 |
| JustGoal | 单个只有目标的 agent | 禁止看参照 |
| **本文** | **每题档案库 + LLM 控制器 + 并行单改动子 agent** | **模型外 12 道检查；官方分数不进搜索** |

本文与最近邻的三处差异值得点出：

- 对 **ForgeKernel**："被接受 kernel 作下一轮参照"的跨 run 链条被本文刻意切断——每题档案库只在 run 内生效，保证冷启动声明的干净；
- 对 **DuoDiscover**：两者都把评估当瓶颈，但 DuoDiscover 的解法是让 agent 自己发明代理评估器（yardstick）再反复校保真度，本文的解法是把测量通道本身做快（build 移出 GPU 锁、shell 启动毫秒化）——一个加 proxy、一个提吞吐，是同一瓶颈的两种攻击面；
- 对 **JustGoal**：本文的强制参考资料 A/B 实验站在了 JustGoal 一边（详见第六节）。

还有一笔值得记的生态账：SOL-ExecBench 的榜单本身已是 2026 年 agent 搜索系统的修罗场——Recursive（长程研究线程）曾把整体均分推到 0.754、无问芯穹（Infinigence AI）在 88 个单题上拿过第一、ForgeKernel 占住 FlashInfer-Bench 轨、DuoDiscover 报过 121/235 单题第一（不同时间切片）。CompoundingKernel 的差异化不在单点最快，而在"三榜总分 + 235/235 全正确 + 从零冷启动"的同时成立——这是广度型胜利，与那些单题冠军的深度型胜利是两种不同的能力证明。

**思想谱系**。程序进化一系（FunSearch → AlphaEvolve → OpenEvolve → ShinkaEvolve → Darwin Gödel Machine）贡献了三条被本文吸收的基因：

1. 档案库（archive）+ 从中采样父代；
2. 强解常源于弱中间体（stepping stones）；
3. 多样性树搜索逃离局部最优。

本文分别将其落地为"每题一个档案库、多条谱系并行生长"（改造自 Darwin Gödel Machine）、第 7 节的垫脚石实证、以及控制器可展开任意节点而非只扩当前最优。三个直接借用的出处论文自己列了账：Darwin Gödel Machine 的父代采样、Hyperagents 的 LLM 元 agent（在本文里还兼任搜索执行者）、ForgeKernel 的"卡住时开新根 = 开新设计"。AlphaEvolve 报告过"强解常来自并非最优的中间体"，OpenEvolve 的 MAP-Elites 网格本质上就是把"保留次优但行为不同的解"制度化——本文 32% 的数字把这个直觉量化成了可核验的统计。

## 三、问题定义

剥掉 GPU 外壳，这篇论文处理的是**搜索式自改进的 scaling 瓶颈问题**：

> 当你用一个固定模型在大量问题上并行跑"改一点、测一次"的搜索时，是什么决定了总收益——agent 的数量、每次选择的聪明程度，还是别的什么？

论文的答案可以预支：**是可靠测量的速率**。每次"尝试"的价值不在于尝试本身，而在于它产出一次"下一次尝试可以建立其上"的可靠测量（正确性裁决 + 真实计时）。若测量通道堵塞——GPU 锁排大队、build 占着锁、12–15 秒的 shell 启动——再加 agent 只是加排队的人。

这个视角把三类现象统一进一个框架：

- 早中期收益集中（前 2% 候选拿走 81% 收益）；
- 控制器对树搜索的胜利（赢在尝试次数而非选择质量）；
- warm restart 的 3.6 倍吞吐跃升（赢在解锁测量通道）。

问题定义里还嵌着一个反直觉的子问题：**搜索该在什么样的解上继续？** 贪心直觉说只扩当前最优，但那样搜索会被早期偶然遇到的局部最优锁死。本文把选择权交给读全谱系的 LLM 控制器，并事后统计：32% 的最终最优曾把一个低于当时最优 0.9 倍的节点当父节点。于是问题从"如何找快 kernel"重构为"如何维护一片能长出快 kernel 的解生态"——这是从优化到演化的视角切换。

形式化地，每题的搜索维护一棵谱系树：节点 = 一个通过全部 workload 正确性检查的 kernel（带计时、profile、鲁棒性裁决、agent 笔记），边 = 父链，无父节点即根（全新设计）。搜索的每一步是"选一个节点（或开新根）+ 派生一个单点修改的子节点"。这个结构天然问三个问题：树怎么长（扩展策略）、长歪了怎么办（错误解不进树、NOT_ROBUST 的最优被降级）、树怎么用（谱系即知识库，控制器可查任意子树统计）。防作弊被定义为问题的一部分而非工程细节：目标函数是计时器，搜索强到一定程度必然发现"不干活就拿分"的路径，因此检查器必须与搜索共同进化。论文的处理方式是把"什么算正确"的裁决权全部移出模型，并且让官方分数物理隔离于搜索之外——学习的唯一信号是自家 B200 上的测试与计时。

## 四、问题解法

系统是四层嵌套循环（Figure 2），快循环套在慢循环里，每层节奏差一个量级。

**循环① 子代理（最快）**：

- 一个 child 拿一个父 kernel（或无，即开新根）和**一条**方向；
- 改一处、编译、在 B200 上计时；
- 模型外的检查决定对错；正确则以带计时与父链的新节点写入该题档案库；
- 最终配置里 child 的产出上限是 1 个正确候选，写到第一个正确 kernel 即停；
- 每个正确候选平均消耗约 3.2 次 shell 命令、2.0 次档案库查询、1.5 次编译检查、1.0 次评测（Figure 12）——极轻量的单步。

**循环② LLM 控制器**。每题一个控制器，只有两个工具：只读 SQL 查档案库，和 expand(父节点, 方向列表) 派发子 agent。形式化就一行：$(p, d) \sim \pi_{LLM}(\cdot|A)$，$k' = Child(p, d)$，正确则 $A \leftarrow A \cup \{k'\}$。控制器无自身状态，每轮重读档案库；child 槽一空就按剩余时间补位。**关键设计：控制器可以展开谱系上任意节点，不限于当前最优**——这直接为垫脚石机制开了门（见第六节）。控制器的搜索奖励不用 SOL 分（它在高加速区被压平），用对官方基线的几何均值加速。

一轮控制器循环的实际节奏（Algorithm C2）：π 发 Query 拿回候选与笔记 → π 决定父节点和一组互不相同的方向 → 逐方向填入空闲槽位（预算用尽则不启动、不计数）→ 等任一槽位释放 → 把结束与在跑的 children、新候选、剩余分钟数、检查失败标志一并交还 π。π 若提前收工且剩余超 10 分钟就被真实时钟重新唤起（计入次数封顶 20 次）。整个搜索对模型的依赖被压缩到"选父节点、写方向"这一个决策点，其余全是代码——这是它可与 coded 树严格对照的原因。

**档案库（共享记忆，全在模型外）**。这是系统的脊柱：

- 每题每 run 一个 SQLite 库，存每个正确 kernel 及其父链（树边）、逐 workload 计时、profile、鲁棒性裁决与 agent 步迹；
- 写路径是 append-only ledger + 每候选一个文件夹，单一 builder 从 ledger 重建数据库原子换入；
- agent 连接只读、SQL authorizer 拒绝写语句（这条防线是某次审查发现一条漏网的写语句后加的）；
- 失败的尝试记日志但不入档为节点；
- 子代理与控制器均无自持记忆，所以 warm restart 后重读档案库即续跑。

**循环③ 团队（warm restart）**。lead 与 helper agent 监控整个机队、修 harness 的故障，每个修复在下一次 warm restart 生效——停 agent、更新 harness、重启动，**但保留 run 与全部档案库**。后期 agents-only 的重启只需几分钟停机（早期有一次重启让 agent 停了数小时，此后立规矩：一次重启一个可门控的变更 + 重启套件）。监控本身也自成体系：23 条无状态规则 + 3 级告警（decision/warn/info）覆盖基础设施与搜索结果两类信号，post 到团队聊天室的告警每天只有几行，"每日摘要没出现"本身就是死讯——静默通道自带心跳。

**循环④ 人（最慢）**。人只在最外圈：批准 harness 修复、决定何时向公开榜提交什么。官方分数从不进入①②——没有任何 agent 见过分数、排名或提交结果；人用公开榜站位决定提交时机与算力分配（10 月 25 日起按各题与第一名的差距动态分配 child 槽）。

**防作弊是解法的有机部分**（Table 3/B1，12 道发送前检查）：

- 官方正确性逐 workload 全跑；
- 鲁棒性检查在未发布的形状与压力输入上重跑（防 shape hardcoding）；
- reward hack 检查确认速度与正确性来自对输入的真实计算；
- 构建限时彩排；多 seed 复检；人审清单。

三类证据说明检查有效：搜索**自己**发现过 reward hack（见下）；运行中曾弃快取稳——一个 L2/079 最优过全部形状但在压力输入上 FP16 溢出，忍痛从 1.62× 掉到约 0.48×；最终 235 个 kernel 全过站点验证。

最精彩的自曝在 Quant/030：

- 运行前三分之一，该题最优路径上的 kernel 用"首次使用时短计时选 variant"（先 autotuner 后计时跑）在变体间选择——一个教科书式 reward hack；
- 搜索自己撞出来、团队在发送前抓住封堵；
- 后继 child 删掉全部运行时计时、把选择固化进逐形状表，本地损失 6%（25.36×→23.88×），约 1% run 时间后回到 25.42×；
- 最终提交的 kernel（站点 SOL 0.971073）正是这条无计时谱系的后代。

Quant/029 补了另一课：本地最优 14.55× 连续三次倒在站点 300 秒构建限制下（串行冷缓存构建要 1965 秒以上）——接受的是一个 unity build（SOL 0.92697），后又被无计时版替换（0.931935）。**本地分数是关于自家 pod 的断言，不是关于站点的。**

## 五、评估指标与实验证据

论文用四套口径报数并始终标注（Table 1）：

1. 站点 SOL 分（榜排名）；
2. 站点计时对官方基线加速（头条数字）；
3. 本地计时加速（搜索奖励与 A/B）；
4. 对 torch.compile 加速（仅本地参考）。

所有头条数字带 as-of 日期（Appendix J）——在一个动态竞争的榜单上，这是必要纪律。

**主结果**（2026-11-11）：

- 三榜第一；235/235 站点正确；
- 209 题几何均值 4.40×（分板：L1 4.04×、L2 3.62×、Quant 9.19×）；
- 89/209 单题第一、193/209 进前十；
- 对 torch.compile（本地）11.2×。

榜首的时间线也有细节：先在 2026-10-20 拿下 Quantization 第一，10-27 拿下 L1，10-29 拿下 L2；11-07 被其他队伍在 L2 和 Quant 上反超（自家分数未掉），11-10 深夜公开更多行后夺回。L1 自 10-27 起保持第一（仅 11-07 短暂失守一次）。这段拉锯说明榜单是活的市场——论文所有"第一"都锚定 as-of 日期，且截图与互联网档案馆存档链接附在附录 L，可回查核验。

加速分布广而非靠离群点撑均值：多数题落在 2–10×，39 题 ≥10×，2 题 ≥100×，最高 L1/094 达 1062×，2 题慢于基线。kernel 是 Blackwell 原生手写级代码而非库封装：214/235 为 CUDA C++，77% 源码含 tcgen05 指令、72% 发 TMA 拷贝、94% 含内联 PTX、0% 用 Hopper 的 wgmma；221 个超千行，中位约 7000 行。

**收益的时间结构**：各板在 run 时间前 15% 内拿走 73–85% 的涨幅；按候选数计，前 2% 候选贡献 81% 收益、前 15% 贡献 93%。且候选数跟随难度而非回报——题目正确候选数与其收益的 Spearman 相关为 −0.36，难题吃掉大量尝试却所剩空间无几。

本地与站点的计时差异也做了显式建模：自家 pod SM 时钟未锁（最高约 1965 MHz vs 站点 1500 MHz），本地读数偏快约 1.19 倍；全 235 kernel 本地对基线几何均值 5.30×，站点口径 4.47×。校准（host factor）只给人用、代理永远看不见——每条校准规则都是先写下来再拿站点结果检验，通过才采纳。这种"预注册"式纪律在工程报告里少见。

**对照实验的设计逻辑**（第 6 节，Appendix E 全量给出）值得细看，因为它示范了如何测"搜索本身"而非"系统整体"：

- **控制器 vs UCB 树**（38 对，每臂 24 小时，Phase 1 harness）：两臂用相同的 Claude 子 agent（树臂的子 agent 无方向）、相同档案库设计。等时长下控制器 35/38 胜，几何均值比 1.143，符号检验 p≈7×10⁻⁸；**等候选数下两臂打平**（15 胜 23 负）。结论干净：控制器的优势全部来自吞吐——等时长正确尝试 2.4 倍。树输在结构：宽度快速衰减（4→2→1）让槽位闲置等整批，控制器每轮派满批、槽一空即补。24 小时严格截断下为 34/38，稳健。

  这个实验的设计逻辑值得单独学：把"选择质量"与"尝试数量"两个混杂因子拆开，靠的就是等候选数对照——若控制器赢在选得准，等数量下也该赢；实际等数量下略输（15/38），说明 LLM 的单步选择并不比 UCB 分数更聪明，它赢的是"永不空转"的调度结构。归因因此从"LLM 更智能"改写为"LLM 当调度器时系统吞吐更高"——前者是模型能力论断，后者是系统设计论断，证据只支持后者。附带一个谨慎脚注：run 时长的中位数在两臂都是 20.5–21.5 小时，"24 小时"是预算而非实测跨度；第二轮 4 题 600 分钟的复测里树与控制器 2–2 打平（三题差距 1–3%），说明在更短的视野里差距收窄。
- **强制 vs 可选参考资料**（233 对，约 23 小时，Phase 2）：强制使用率升 4.3 倍，最终加速几何均值比 0.981（126 对可选领先 vs 107 对强制领先），p≈0.24，无实测提升。最终 run 里自家的 skill 与公开 wiki 的使用率分别只有 1.19% 和 0.83%。论文坦承两个混淆都对着强制臂使坏（watchdog bug 损失主机时间、限流更狠 12.3% vs 8.2%），小效益未被排除——但结论与 JustGoal 一致、与"专家方向至关重要"的 FlashInfer 竞赛报告相悖。曲线交叉的细节也有信息量：36 题强制臂先领先后被反超、34 题相反——两臂的差异整体上就是噪声量级，且随时间抹平。另一个空间维度的 null：让 run 看见兄弟 run 的设计（FlashInfer 板 24 对）反而 9:15 落后，未上线。
- **卡住 run 的结构性转向指令**：4 个 run 的筛选实验，−0.30% 到 +0.05%，操纵检查失败（两臂都几乎没发生结构变化），如实报为筛选性 null，未上线。

三组对照合起来的元结论：在测量可靠的前提下，每小时更多可靠尝试可测地获益，而外加指导没有。这与第 5 节的系统课互相咬合——四个 lesson 全部是"挑战→干预→测量→教训"格式，其中一次 warm restart（build 移出 GPU 锁 + shell 启动毫秒化 + profile 可选化）让每小时评测候选数升 3.6×、每候选锁时间降 71%，正确率维持在约 98% 不变。

四条系统 lesson 的完整清单（§5，每条都带匹配时段的前后对比数）：

1. **更多 agent ≠ 更多实验**——吞吐由测量通道决定（3.6× 的故事）；
2. **warm restart 保进度**——记忆在模型外，harness 变成可迭代的版本序列，agents-only 重启只要几分钟；
3. **只验证可能发布的**——鲁棒性检查从每候选 0.66 次降到 0.27 次，94.9% 新最优仍被覆盖，"把验证放在决策处，并测量你放弃的覆盖率"；
4. **父代用文件传而非贴文本**——首 prompt 上下文缩 88–96%，吞吐持平，千级并发下上下文总量是 fleet 级成本。

**局限的诚实清单**（第 9 节）：单一基准、单一模型（全部 agent 均为 Claude Opus 5.5）、单次冷启动最终 run；正确性靠测试而非证明（形式化与 SMT 工具不覆盖 tcgen05/TMA/mbarrier 的异步语义，最好候选只覆盖 16% 问题）；鲁棒性检查只覆盖 94.9% 的新最优而非全部候选；A/B 在 pre-final harness 上跑且每臂单 run；"测量速率是瓶颈"的论断尚未通过直接变化 agent 数验证。冷启动也有限定词：人参与了③④（批准修复、选提交、按差距分配槽位），且运行中向少数 run 的 prompt 加过经批准的注记（设计方向、Triton 指引、时钟说明——均不含分数排名）；本地最优 5.30× 与站点 4.47× 之间的换算依赖逐 kernel 变化的 host factor，设计大变时会失准。最终 run 在数据窗口关闭后仍在继续，所以每个头条数字都挂着 as-of 时间戳。

## 六、效果优势根源

为什么这套系统能登顶？论文给出的不是单点技巧而是一条因果链：**复利来自每次尝试建立在上次可靠测量之上**。把链拆开：

**垫脚石机制**（第 7 节，全文最有味道的部分）。统计口径：235 题中 75 题（32%）的最优路径曾在某步把一个低于当时最优 0.9× 的节点当父节点扩展；41 题（17%）的路径含至少一步比父节点慢 10% 以上。四个案例给出机制：

- **Quant/030（结构性下探）**：9.71× 处控制器派 child 把 Triton attention 换成 CuTe DSL 的 tcgen05 管线实现，首次只跑出 1.52×；下一个 child 定位到寄存器溢出修到 7.10×；第三个 child 把新 attention 嫁接到当时 run 最优节点（12.93× 的库 GEMM 路线）上，13.97× 创 run 新高——距下探仅 1% run 时间。**该 run 93% 的节点是那个 1.52× 节点的后代**；未继承它的最好节点只到 24.87×，路径最终 27.36×。
- **L2/001（正确性换速度）**：5.73× 的最快 kernel 用单舍入 fp16 张量核过全部官方 workload，却在额外形状上被鲁棒性检查判 NOT_ROBUST；子代改分裂精度操作数掉到 4.26×→4.17× 谷底，此后重建，最终 15.20×（谷底的 2.65 倍），86% 节点继承自修复节点。
- **L2/043（落后支线供零件）**：一个只有领先者一半速度的新根（15.10× vs 32.08×），其单一融合 persistent 张量核 kernel 在一个形状类上更快；child 把它嫁接到现任链上，32.15× 创新高，路线终达 42.86×，97% 后续节点出自该线。
- **L1/065（同型）**：落后张量核支线被按形状路由嫁接，2.10× 一路爬到 5.63×，96% 后续节点出自该线。
- **Quant/029（本地快的假象）**：与前四个案例相反的教训——本地 14.55× 的最优三次过不了站点构建限制，最终上榜的解（SOL 0.931935）靠的是"删掉永远走不到的 56/68 个配置、把翻译单元压到 4 个文件"，即**变小而非变快**。

前四个案例是"本地慢但谱系价值高"，第五个是"本地快但部署价值低"——两个方向一起说明：本地分数是关于自家 pod 与自家构建环境的断言，不是关于站点的，更不是关于谱系潜力的。

共性：**节点的本地速度是它作为父节点价值的糟糕预测器**——下探与落后支线各自供养了 86–97% 的后续节点。这要求两个制度前提：档案库必须保留所有正确 kernel（而非只留最优），且扩展权必须交给能读全谱系的控制器。这正是 AlphaEvolve/OpenEvolve 一系"强解源于弱中间体"直觉的逐题量化版。

值得强调这套机制与普通"重启/多样性"策略的区别：树搜索也会保留次优节点（UCB 的探索项就在干这个），但 UCB 的选择只看节点自身的分数与访问数；而 LLM 控制器读的是节点附带的笔记（瓶颈记录、下一步计划）、子树统计与方向历史，能识别"慢但结构新"与"慢且死路"的差异。Quant/030 里 1.52× 节点被连续押注三次（下探→修溢出→嫁接），第三次才兑现——纯分数驱动的选择器在第二次失败后大概率放弃它。档案库的 edge 只记录"种子"血统，child 还可以从其他节点抄代码（三个案例正是靠这种 graft），所以谱系树实际低估了重组的丰富度。

**测量速率瓶颈**。三个独立证据钉死同一条：

- warm restart 的 3.6× 吞吐跃升（锁等待归零）；
- 控制器对树搜索 2.4× 正确尝试的优势；
- 早期诊断："GPU 只忙 13% 时每个 GPU 已有约 5 个调用在等锁"。

诊断细节值得复述：早期每把锁罩住整个远程调用——包括 CPU 侧 build 和 12–15 秒的 shell 启动——GPU 本体只在锁内占一小段。干预是把 build 移进缓存、shell 启动压到毫秒、profile 转可选、新最优的验证交给基础设施；匹配时段对比下每候选锁时间降 71%、吞吐 3.6×、正确率不动。第二次重启把锁移到 host 侧并加倍 host 数，小时中位数再次翻倍以上（但混入了两个变更，论文如实标注未拆分）。

论文将其上升为本文的 scaling 论断：agent 数量度量的是需求，限制规模的是可靠测量速率。这与 DuoDiscover 把"评估成本"立为自主发现的第一瓶颈互为印证——一个从提吞吐、一个从降保真两头攻击同一面墙。

**慢发现的自愈**。收益曲线前陡后缓，但尾部小 SOL 差异决定了大量单题排名——board 第一是广度（89 个单题第一、193 个前十）堆出来的，不是少数明星题。前 2% 候选之外的 98% 只拿走 19% 收益，却换来了榜位。注意力类问题占了总差距的最大份额（34%），纯 GEMM/MLP 与全层问题离光速最远（SOL 0.77 左右）——剩下的硬骨头恰好是库 kernel 最成熟的地带，这预示着下一轮提升的最小收益区。

**"98.4% 正确"的机制注脚**。这个数字（截至 11-02 的候选正确率）不是模型多聪明，而是结构使然：child 继承的父代已经全 workload 正确，单点改动破坏正确性的概率低；编译-修复循环（Algorithm C1 的内层 repeat）先在单一 workload 上修到对才进入完整评测；同代码重复测量直接复用旧结果不新计。高正确率降低了每次测量的废品率，本质上还是"提高可靠测量速率"这条主线的一部分。

**外部交叉验证**：

- "垫脚石"与 FunSearch/AlphaEvolve 系的进化档案库思想同源，且被 OpenEvolve 的质量-多样性设计（MAP-Elites 保每次优解）间接支持；
- "评估是瓶颈"有 DuoDiscover 的整篇论文背书；
- "goal-only 即强基线"与 JustGoal 的发现一致；
- "更强搜索必然找到检查器缝隙"在 Sakana 事件、SOL-ExecBench 自家 14.5% 拒收率、Recursive 的迭代 hack 检测器三处独立复现。

论文的核心论断没有一条只靠自家榜单自证。

## 七、必要知识反推

要做出（或真读懂）这个系统，需要四层知识，缺一层就塌一角：

**Blackwell 微架构的具体性**。得知道 tcgen05 是什么——第五代张量核 MMA，累加器驻 TMEM、单线程发射、支持 CTA-pair 协作 2-SM MMA，吞吐为 Hopper wgmma 的 2–4 倍；还有 TMA 张量拷贝引擎、mbarrier 异步栅栏、cta_group::2、setmaxnreg 的 warp 特化寄存器分配、PDL（programmatic dependent launch）。这些不仅为了写 kernel，更为了看懂"94% 内联 PTX、77% 命名 tcgen05、80% 线程块簇、0% wgmma"这句统计在说什么：模型群自己迁移到了新指令集上，旧代的快速路径被整体放弃。PTXBench 一类的评测佐证了这块的稀缺性：架构特定 PTX 能力在前沿模型间分布极不均匀，B200 上普遍更弱（Gemini 3.1 Pro 在 B200 GEMM turn-0 只有 8.3% 目标指令达成率）——这解释了为什么搜索（而非单次生成）是必经之路。

**进化搜索与程序合成谱系**。archive 采样、MAP-Elites、质量-多样性、stepping stones（Lehman & Stanley 的 novelty search 血统）、Darwin Gödel Machine 的父代采样、Hyperagents 的 LLM 元 agent——本文的三条吸收线各有出处，不知道源头就看不出哪些是设计决策、哪些是继承。

**分布式系统工程**。GPU 锁的粒度设计（锁内只留 GPU 阶段、build 进缓存）、append-only ledger + 单 builder 原子换库的读写分离、每 run 数据库隔离、per-GPU 锁下的吞吐诊断（锁时间/候选 降 71% 的测量本身就是工程活）、23 条无状态规则 + 三级告警的监控、container 集群上的 pod 级凭证管理。第 5 节四个 lesson 全是这类知识，没有一个和 LLM 有关。其中"验证放在决策处"的算术很典型：child 自跑鲁棒性检查时占掉约四分之一锁时间；改为只自动查每个新最优 + 发送行全查，每候选检查数从 0.66 降到 0.27，94.9% 的新最优仍被覆盖（其中 95.9% 判 ROBUST）——用覆盖率数字换检查预算，是典型的工程折中而非原则声明。另一条：大父代以文件而非文本传入 prompt，首 prompt 上下文缩减 88–96%，吞吐持平——千级并发下上下文总量本身就是 fleet 级成本。

**评测方法论与对抗思维**。四口径计时的纪律、as-of 日期、配对符号检验、pre-registration 式的校准规则（每条校准先写下再看站点结果）、12 道发送检查的设计（每道对应一类已知攻击面）、以及"把操纵检查失败的实验如实报 null"的克制。防作弊部分需要 KernelBench 作弊图鉴的完整知识：内存重用、隐藏流、降精度、shape hardcode、运行时计时选路——本系统封堵的每条路都有前车之鉴。精度规则也自加码：基准论文允许 dtype 匹配且过容差时降精度，运行中团队改采更严规则（保留声明 dtype、fp32 用快单元模拟可以、bf16/fp16 降到声明类型之下算违规、Quant 板豁免）——在"能过"与"该过"之间主动选择后者。

还有一个容易被忽略的知识点：论文对 formal verification 的排除有据可查——调研过的形式化与 SMT 工具都不建模 Blackwell 异步张量核操作，最好的候选只覆盖 16% 的问题，于是退而求"模型外测试 + 声明局限"。知道形式化验证的能力边界，本身就是必要知识。

反推门槛：这是一个"模型不动、其余全动"的工程重项目——千级并发会话、专有 GPU 机队、SQL 档案库、监控面板、校准流水线。学术小组难以复制其规模，但可以复制其结构（档案库 + 控制器 + 模型外检查都是小团队可实现的），论文也承诺放出搜索循环、SOL-ExecBench 接口、检查器与示例配置（不含 agent prompt）。安全设计同样成体系可学：GPU pod 无云凭证、metadata 服务被屏蔽、agent 只能到达自己 run 的指名 GPU pod、pod 级短时模型凭证、每日 shell 命令审计——"不信任自家 agent"是一等设计约束，而非事后补丁。

## 八、通用性灵感

**测量瓶颈论的推广**。把"可靠测量速率是 scaling 上限"当普适假设去审视其他搜索式自改进领域：数学定理证明（一次 lean 验证 vs 千次脑内推演）、agent 自我改写（一次真实任务评估 vs 千次自我打分）、芯片设计（一次流片 vs 千次仿真）。多数"test-time compute 不奏效"的报告，重检后可能发现是测量通道堵塞而非计算无用——本文的 GPU 锁诊断（GPU 13% 忙、每卡 5 个等待者）就是现成的排查模板：**先测利用率与队列深度，再谈加机器**。对做 agent 量化的团队，这是把算力预算从"加 agent"改押"提评测吞吐"的实证依据。

**慢解生态作为资产管理**。32% 这个数字对任何维护"当前最优"的系统都是一记提醒：greedy 只留最优等于系统性丢弃期权。可迁移的制度设计是三条：

1. 保留全部正确解及其谱系（存储便宜，丢弃昂贵）；
2. 扩展权交给看得见全谱系的决策者（LLM 或人）；
3. 把"下探后再反弹"当作正常搜索行为而非故障。

SWE agent 的方案库、prompt 优化器的指令池、推荐系统的召回层，同构问题比比皆是。嫁接操作（Quant/030 的第三个 child 把新 attention 接到现任最优上）提示档案库的价值不止"回溯"，还有**跨谱系的零件重组**——这是普通 tree search 没有的算子。迁移时注意两个前提：档案库必须带"可判读的节点注记"（瓶颈记录与下一步计划），否则控制器无法识别哪些慢节点值得押注；且"正确才入档"的门槛要稳，否则档案库会被错误解污染成负资产。

**官方分数隔离**。"学习信号只用自产测量，外部计分板只给人看"是一个可迁移的防污染架构：它同时防了分布过拟合（对榜优化）、防了 reward hacking 的最短路径（骗过官方评测即得分）、也让"何时提交"成为纯粹的人类战略决策。任何有公开榜的自动搜索系统（Kaggle 自动化、SAT 求解竞赛、code golf）都适用。副作用同样值得设计：因为 agent 看不到榜，人会通过"child 槽分配 + 少量批准过的 prompt 注记（设计方向、Triton 指引、时钟说明）"来传导战略意图——不含分数与排名的窄通道。这是"人机分工"的一个干净范本：机器负责在既定规则内搜索，人负责规则外的资源调度与时机判断，两者的信息面刻意不对称。

**warm restart 作为 harness 迭代协议**。"记忆全在模型外"的直接红利是方法论本身可以热更新而不丢进度——论文原话："方法于是变成一个有序的版本序列，所以我们发布这个序列。"这对长周期 agent 运行是范式性的：把 prompt、工具、评测当作可独立迭代的 harness 层，用档案库锚定连续性，一次重启只上一个可门控的变更。对照当下常见的"改一版 prompt 就冷启动重跑"，这是长跑系统的基本纪律。

**冷边界**。三个未解问题值得挂着：

- 其一，"测量速率是瓶颈"尚未被 agent 数量的直接实验证实（作者自认）；
- 其二，前 2% 候选拿 81% 收益的曲线意味着**边际收益急剧衰减**——若目标是再登一榜，复利故事的尾部支撑主要在榜位而非绝对性能，长期经济性存疑；
- 其三，单一模型依赖——控制器与子代理都是 Opus 5.5，"换更强模型是否让 harness 的精心设计贬值"没有答案（E.2 的引擎对比只在 pre-final 上做过且混淆交错）。

还有一类论文没有明说但数据里透出来的限制：两个慢于基线的题里，L2/037（0.30×）是代码评审主动否决了一个过全部自动检查的库回退方案的结果——防作弊纪律与榜单分数在这里直接冲突，团队选择了前者。这类"自律成本"在 21 个低于 1.5× 的题上（全部在 L1/L2，多为纯 GEMM/MLP 与全层问题，均值 SOL 0.61 vs 其余 0.86）可能都被支付过：最规整的计算恰恰是库 kernel 最强、搜索最难做出增量的地带。

更远处，作者自己划出的下一步更诚实：更便宜的验证（让更多尝试可被可靠测量）、跨硬件迁移、以及把 kernel 装进真实 serving 栈——最后一项的收益会小于单 kernel 加速比，因为 serving 栈已经在用调优过的库 kernel。

从零到第一的故事之所以可信，不在榜首数字，而在论文把"为什么赢"拆成了可复算的账：2.4 倍尝试率、3.6 倍吞吐、32% 垫脚石、81% 早期收益——每笔账都标注了口径与日期。对信奉"bitter lesson"的读者，这篇论文给的是半句补语：**算力规模赢，但前提是每一次尝试都能可靠地踩在下一次的测量上。**

而对我们这些旁观者，最有用的也许是一个朴素的对照：同一时期、同一榜单、同样"固定模型 + 搜索"的信条下，ForgeKernel 押跨 run 知识积累、DuoDiscover 押代理评估器、Recursive 押长程研究线程、本文押测量吞吐与谱系生态——四条路线各自登顶过不同的板。这与其说是路线之争的分晓，不如说明这个范式的瓶颈是多元的：知识、评估、上下文长度、测量速率，各有各的墙。本文的贡献是把其中一面墙（测量速率）第一次量到了小数点后，并给出了一套"怎么拆墙"的可复算工程叙事。下一代系统大概率会同时带几把锤子。
