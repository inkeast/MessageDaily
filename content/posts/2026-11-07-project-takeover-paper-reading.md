# Take It From Here: Evaluating Coding Agents On Project Takeover —— 精读

> **论文链接**：[https://arxiv.org/abs/2611.07307](https://arxiv.org/abs/2611.07307)
> **发表时间**：2026年11月
> **机构**：Upwork Inc、University of Technology Sydney（悉尼科技大学）、Scale AI、The Education University of Hong Kong（香港教育大学）
> **领域标签**：cs.SE / 编码智能体评测 / 长期记忆

**机构合作说明**：这是一篇典型的"企业出数据、学界出方法"的合作论文。第一作者团队来自 Upwork——全球最大的自由职业平台之一，44 个真实项目、7,983 条交互消息的数据正是来源于此；悉尼科技大学（UTS）团队负责需求状态图的形式化与诊断框架设计；Scale AI 与港教大参与实验与评审。通讯作者为 UTS 的 Huan Huo。

## 一、论文背景

### 1.1 编码智能体的下一步：从"写函数"到"接手项目"

过去几年，编码智能体（Coding Agent）的能力边界经历了三次扩张：

1. **单点代码生成**：HumanEval、MBPP 时代，模型根据一段规格说明生成一个独立函数；
2. **仓库级任务**：SWE-bench、SWE-Lancer 时代，智能体可以在真实代码库里浏览文件、修改实现、跑测试，解决一个具体的 GitHub issue 或自由职业任务；
3. **长期项目协作**：智能体作为助手参与数月之久的项目，需要理解新请求、在已有工作基础上推进项目。

这篇论文瞄准的正是第三阶段的一个关键场景——**项目接管（Project Takeover）**：一个新智能体（或新会话）在中途加入项目，收到一条新请求。此时它手里的信息是：

- 一大段**交互历史**（客户和此前开发者的多轮沟通，可能长达上千条消息）；
- **当前请求**；
- **请求发生前的项目环境**（代码、文档或 PCB 设计文件的快照）。

它要做的事情远比"改个 bug"复杂：**从冗长的历史中恢复出"目前仍然有效的需求"，判断新请求如何改变这些需求，然后在既有项目里实施变更**。

### 1.2 为什么这件事很难：需求信息是"演化"的

用一个类比：项目接管就像你中途接手一位同事的活儿。同事留给你不是一份整洁的规格说明书，而是几百页微信群聊天记录。客户在消息 30 里说"用 PostgreSQL"，消息 150 里改口"换成 MySQL"，消息 400 里又说"预算不够，先用 SQLite 吧"。你接到的最新请求是"加一个导出功能"——你不仅要知道导出功能本身，还要知道导出的数据该从哪个数据库读、历史上哪些约束（比如"必须支持 CSV 格式"）仍然生效。

这里的核心困难在于：**需求的当前状态是历史事件的折叠结果**。每条消息可能是引入、修改、推迟、撤销某个需求，或者报告实现成败。要回答"现在该做什么"，必须把这条演化链完整重放一遍。这正是软件工程领域经典的**需求追踪（Requirements Traceability）**问题——论文直接引用了 1994 年 Gotel & Finkelstein 与 2000 年 Nuseibeh & Easterbrook 的需求工程经典文献作为方法论根基。

### 1.3 现有评测的盲区

论文指出，现有基准没有覆盖这个完整过程：

- **代码生成/补全基准**（HumanEval、MBPP、CrossCodeEval、RepoBench）：没有交互历史；
- **项目级基准**（SWE-bench、SWE-Lancer、SWE-EVO、ProjDevBench）：任务从给定的 issue 描述和代码环境出发，不需要从历史里"考古"出需求；
- **长期记忆基准**（LongMemEval、MemoryAgentBench、LongMemEval-V2）：测的是对话历史中的检索、更新、弃用，但不要求把信息落地为"交付物"；
- **交互式/多轮编码基准**（ConvCodeWorld、SR-Eval、LoCoEval 等）：覆盖了多轮反馈或需求细化，但没有在"指定接管点"上把**需求重建 → 更新 → 交付**整条链路串起来评测。

一句话：**要么有历史没交付，要么有交付没历史**。这篇论文要补的就是这个缺口——并且用诊断实验回答"到底卡在哪一环"。

## 二、论文定位和关联工作

按研究谱系，本文的相关工作可以分为四条线：

### 2.1 谱系一：编码能力基准（从函数到项目）

| 工作 | 核心思想 | 与本文的关键区别 |
|---|---|---|
| HumanEval / MBPP（2021） | 规格说明 → 单函数 | 无历史、无既有项目 |
| SWE-bench（2024） | 真实 GitHub issue + 仓库 | 任务描述给定，无需从历史恢复需求 |
| SWE-Lancer（2025） | 真实自由职业任务、按金额计酬 | 同上，且不覆盖多轮需求演化 |
| SWE-EVO（2025） | 软件持续演化场景 | 演化序列给定，非"从沟通历史考古" |
| ProjDevBench（2026） | 端到端项目开发 | 从零开始，不处理接管时的历史包袱 |

本文与其的差异：接管任务的"任务描述"本身是**隐含的**——必须从交互历史中重建，而且历史里混着大量已失效的旧版本需求。

### 2.2 谱系二：长期记忆评测

| 工作 | 核心思想 | 与本文的关键区别 |
|---|---|---|
| LongMemEval（2025） | 多会话问答测时序推理、知识更新、弃答 | 只测"答"，不测"做" |
| MemoryAgentBench（2025） | 增量信息下的检索/学习/理解/丢弃 | 无项目交付环节 |
| LongMemEval-V2（2026） | 从历史 web 交互推断环境变化与工作流 | 输出是文本推断而非项目修改 |

本文与其的差异：把"记忆"从问答正确率推进到**交付验证**——需求状态理解错误会直接体现为 build/回归/目标测试失败。

### 2.3 谱系三：多轮/交互式编码

ConvCodeWorld（可复现反馈环境中的会话式代码生成）、SR-Eval（步进式需求细化下的代码生成）、SWE-Bench-CL（持续学习）、SWE Context Bench（编码中的上下文学习）、SlopCodeBench（长程迭代任务中智能体的退化）等工作各自覆盖了多轮反馈或演化任务。LoCoEval（2026）最接近——它在长对话中引入冲突与更新，分别评测主题识别、信息抽取和函数生成；但它的评估对象仍是"对话结束后生成函数"，而非在指定接管点交付完整项目变更。

### 2.4 谱系四：过程诊断类基准

SWE-RPG 对照参考答案诊断需求与规划错误，RigorBench 评测执行轨迹中的规划/验证/恢复纪律。本文的 RQ1–RQ3 诊断设计与之一脉相承，但创新在于**把诊断与交付验证链接到同一批目标上**，从而可以回答"需求理解错误是否是交付失败的充分解释"（答案竟然是否定的——这是本文最反直觉的发现之一）。

### 2.5 本文定位总结

| 维度 | 之前的路线 | 本文的突破 |
|---|---|---|
| 任务输入 | 给定 issue 描述 | 交互历史（18–1,075 轮）+ 当前请求 + 项目环境 |
| 评测对象 | 代码 diff 或答案文本 | 需求状态诊断 + 可执行交付验证的双轨 |
| 诊断能力 | 无 / 仅整体通过率 | 需求原子五维状态，逐字段评分 |
| 失败归因 | 不能区分"没理解"和"没改对" | Oracle 实验：喂正确状态仍只有 9.01% 目标测试通过 |
| 数据来源 | GitHub / 合成 | 真实自由职业项目（软件、文档、PCB） |

## 三、问题定义

### 3.1 从具体场景到抽象问题

具体场景：智能体在项目中途接管，从历史 + 当前请求 + 项目环境中产出修改后的项目。

核心洞察：**"项目接管"的本质是"需求状态机的重放与外推"**。历史上的每条消息都是对某个需求原子状态机的一次事件操作；接管任务 = 把状态机重放到请求前一刻（得到 pre-state G⁻），应用当前请求的事件（得到 target state G⁺），再把 G⁺ 实施到项目工件上。

论文用一个精妙的结构来承载这个抽象——**需求原子（Requirement Atom）**：语义完备、可独立演化的最小需求单元。类比来说：

- 一条消息 ≈ 一次 git commit（可能同时触及多个需求）
- 一个需求原子 ≈ 一个文件（有自己的生命周期）
- 需求状态 ≈ 文件在某个 commit 的内容快照
- 接管 ≈ checkout 到某个历史 commit，再 cherry-pick 一条新提交

### 3.2 需求原子的五维状态

每个需求原子在任意时刻的状态由五个维度构成（论文 Table 5）：

| 状态维度 | 含义 | 类比 |
|---|---|---|
| **Attributes（属性）** | 当前确立的参数、行为、约束 | 文件内容 |
| **Lifecycle status（生命周期）** | ACTIVE / DEFERRED / REMOVED / null（历史不足） | 分支状态 |
| **Scope（范围）** | 持续时间、适用组件、适用上下文 | 作用域声明 |
| **Ambiguity（歧义）** | 未解决的 VALUE/SCOPE/LIFECYCLE 问题及其来源 | TODO 注释 |
| **Implementation evidence（实现证据）** | CLAIMED WORKING / FAILED / VERIFIED WORKING | CI 状态 |

注意生命周期与实现证据是**独立**的：一个 ACTIVE 的需求可以带着 FAILED 的实现证据——"客户要求的"和"已经做出来的"是两回事。

事件系统支持九种操作：INTRODUCE、MODIFY、DEFER、RESUME、REMOVE、AMBIGUOUS、IMPLEMENTATION CLAIM、RUNTIME FAILURE、RUNTIME VERIFICATION。确定性重放（deterministic replay）为每个原子构建独立的状态图，节点是五维快照，边记录事件与来源消息。

### 3.3 形式化的问题定义

- **给定**：历史消息序列 H、当前请求 q、请求前项目环境 E；
- **求解**：
  1. **需求诊断**：识别相关需求与证据（RQ1）、重建 G⁻（RQ2）、对 q 做出 ACT/CLARIFY 决策并给出 G⁺ 或澄清问题（RQ3）；
  2. **项目交付**：修改 E 得到 E′，使得三重检查通过——Build（可构建/文件有效）、Target test（请求的变更被实现）、Regression（历史有效约束被保留）；
- **约束**：G⁻/G⁺ 均不得使用请求之后的实现或运行时反馈信息（防止"偷看答案"）。

### 3.4 这个抽象的精妙之处

把"需求理解"从模糊的自然语言理解问题变成**可逐字段比对的结构化对象**，是整个评测的支点。它带来两个好处：

1. 诊断可以**部分给分**（Post-State Score 用类似 F1 的软评分），从而区分"完全不会"和"差一点全对"；
2. 可以构造 **Oracle 实验**——直接把正确的 G⁻ 或 G⁺ 喂给智能体，把"需求理解"这一变量从交付链路中剥离，单独测量"实施"能力。没有这个结构化表示，Oracle 实验无从谈起。

## 四、问题解法

论文的"解法"不是训练一个新模型，而是构建一套**评测与归因框架**，由三个实验加一个基准组成。所有实验共享六种配置：Codex CLI 搭载 GPT-6 Astra、GPT-6 Sol、GPT-5.6 Sol、GPT-5.6 Terra，Claude Code 搭载 Opus 5.5、Sonnet 5，全部使用高推理档位。

### 4.1 实验一：直接交付（主实验）

类比：直接让学生看全部聊天记录后交作业。

- **输入**：历史（两种条件）+ 当前请求 + 请求前项目环境；
- **历史条件**：
  - **C1（Full History）**：接管点之前的全部合格消息，交付目标上平均 186.9 轮；
  - **C2（Relevant History）**：用需求标注过滤，仅保留与当前请求涉及需求相关的消息及其演化轨迹，平均 8.7 轮（不足 C1 的 1/20）；
- **输出**：修改后的项目，接受三重检查：Build / Target test / Regression 三项全过才算**完整交付**；
- **运行控制**：每个"配置 × 目标 × 条件"独立新进程跑一次，编码限时 1,800 秒；未完成、未提交、编码失败一律记 0 分且保留在分母里（防止"挑简单题做"美化数字）。

设置 C2 的动机来自长上下文评测（LongBench、RULER）的发现——上下文越长性能越差。如果"缩短上下文"就能救回交付率，说明瓶颈在检索；如果不能，说明瓶颈更深。

### 4.2 实验二：需求理解诊断（RQ1–RQ3）

类比：不让学生交作业了，改为口头答辩，逐环考察"你找对资料了吗、还原对了吗、更新对了吗"。

诊断在 349 个目标上进行，**只给历史与当前请求，不给项目环境**，模型输出单个结构化 JSON 响应后冻结。三个诊断逐级递进：

| 诊断 | 考察内容 | 核心指标 |
|---|---|---|
| **RQ1** 相关信息识别 | 哪些历史需求/证据与当前任务相关 | 需求与证据各自的 Precision / Recall / F1 |
| **RQ2** 请求前状态重建 | 相关需求的 G⁻ | 匹配需求的属性重建分 + 需求覆盖率 |
| **RQ3** 请求更新或澄清 | ACT/CLARIFY 决策 + G⁺ 或澄清问题 | 决策准确率、Exact Post-State Accuracy、Post-State Score、Blocking-Issue F1、Question Validity |

几个关键设计细节：

- **语义判定官（semantic judge）**：预测与 Gold 措辞可能不同，先由 LLM 判定语义关系（SAME ATOM / MERGED ATOMS / SUBPART / RELATED DIFFERENT / UNRELATED / UNCERTAIN），再由程序做一对一最大匹配和字段比对——LLM 只负责"判关系"，分数计算完全程序化，避免了"LLM 打分不可复现"的老问题；
- **Post-State Score**（式 2）：对匹配需求取状态维度均分，再用 2·Σsᵣ / (|R̂|+|R|) 的 F1 式聚合，部分正确有部分分，漏掉或多余的需求都会被罚；
- **Exact Post-State Accuracy**：全对才算——ACT 决策正确、无漏无多的需求集、所有适用字段值正确、无多余状态维度、待删属性名列表与 Gold 一致；
- **ACT/CLARIFY 双分支**：信息不足时应该选择 CLARIFY 并提出能获取关键信息的问题——这本身就是真实接管的必备能力（349 个目标中 37 个的 Gold 是 CLARIFY）。

### 4.3 实验三：Oracle 状态对照

这是全文归因设计的点睛之笔——用"喂答案"来定位瓶颈：

| 条件 | 需求处理阶段输入 | 编码阶段输入 | 回答的问题 |
|---|---|---|---|
| **Oracle Pre-State** | 正确的 G⁻ + 当前请求（历史为空） | 预测的 G⁺（冻结）+ 初始环境 | 绕过"历史重建"后，更新与实施还剩多少问题？ |
| **Oracle Post-State** | 直接供给正确的 G⁺ | Gold G⁺ 投影 + 初始环境 | 需求理解满分时，实施能力的天花板在哪？ |

编码阶段只接收状态投影（需求引用、摘要、最终状态字段），剥离原始请求与历史，确保测的是"把明确目标落进既有项目"的纯粹能力。

### 4.4 数据构造：44 个项目怎么变成 349 个目标

数据构造流水线（论文 Figure 3）值得细看，因为它决定了评测的生态效度：

1. **来源**：44 个真实进行中的协作项目，覆盖软件、Word 模板/报告、PCB 设计三类交付物；完整历史 18–1,075 轮（均值 181.4，中位数 110），共 7,983 条消息；
2. **标注**：LLM 辅助标注需求原子、变更事件与来源消息 → 程序校验消息引用、事件顺序、状态转移、历史边界 → 确定性重放生成每个原子的状态轨迹；
3. **选点**：筛选"依赖历史、需求变化可评估"的请求作为接管点，得到 349 个诊断目标（312 个 Gold-ACT + 37 个 Gold-CLARIFY）；
4. **人工复核**：4 名人类评审分两对覆盖全部 44 个项目，每项目双人独立评审，一致则通过、分歧则复议；共复核 733 项需求边界、2,108 个必需证据组、733 项请求前状态、763 项请求后状态、43 个阻塞问题；
5. **可执行子集**：在 123 个候选中筛选"环境可复现、初始状态满足 Build 过/Target 败/Regression 过"的目标，最终 37 个（22 个软件/网站 + 9 个 ESP32 PCB + 4 个 Word 模板 + 2 个安全报告，来自 7 个项目）。

### 4.5 ReqMemBench：两阶段协议

诊断与交付通过"冻结"机制链接：Phase A 在 349 个目标上做需求诊断、冻结响应；只有有效响应且选了 ACT 的运行才进入 Phase B——带着冻结的需求响应去改项目、接受三重检查。这样同一次接管的能力被拆成可分别归因的两段。

### 4.6 全景对比

| 实验 | 目标数 | 输入 | 独立变量 | 测量 |
|---|---|---|---|---|
| 直接交付 C1/C2 | 37 | 历史+请求+环境 | 历史长度与构成 | 完整交付率及三检查分量 |
| 诊断 RQ1–RQ3 | 349 | 历史+请求（无环境） | 无环境隔离理解 | 状态级软/严指标 |
| Oracle Pre | 37 | G⁻+请求 → 编码 | 历史重建被绕过 | 同交付检查 |
| Oracle Post | 37 | G⁺ → 编码 | 需求理解被置满 | 同交付检查 |

## 五、评估指标与实验证据

### 5.1 主结果一：直接交付几乎全军覆没

37 个可执行目标上的完整交付率（论文 Table 2）：

| 配置 | Full History (C1) | Relevant History (C2) |
|---|---|---|
| GPT-6 Astra (Codex) | 10.81% | 5.41% |
| GPT-6 Sol (Codex) | 5.41% | 2.70% |
| GPT-5.6 Sol (Codex) | 2.70% | 5.41% |
| GPT-5.6 Terra (Codex) | 5.41% | 0.00% |
| Opus 5.5 (Claude Code) | 5.41% | 2.70% |
| Sonnet 5 (Claude Code) | 0.00% | 0.00% |
| **六配置均值** | **4.95%** | **2.70%** |

三个关键读数：

1. **4.95% 意味着 37 题平均只能完整交付不到 2 题**——前沿模型 + 成熟 harness 的组合在最接近真实工作的场景里几乎不可用；
2. **C2 比 C1 更差**（2.70% vs 4.95%）：把历史从 187 轮砍到 8.7 轮，交付率反而下降。短上下文并没有换来性能提升——当前的历史过滤方案会丢掉对交付有用的信息，"上下文太长"不是唯一的问题；
3. **没有任何配置显著领先**：最强的 GPT-6 Astra 也只有 10.81%，说明这是系统性能力缺口而非某个模型的短板。

### 5.2 主结果二：需求状态没有配置能做全对

诊断实验（349 目标）的三层发现：

**第一层：找得到，但找不精（RQ1）。** 以 GPT-6 Astra 为例（C1 条件）：证据 Recall 高达 0.9211，Precision 却只有 0.2254——Gold 证据几乎都被它捞进来了，但同时捞进来大量无关消息。需求识别层面六个配置的 Precision 在 0.26–0.44、Recall 在 0.52–0.68 之间，无一既准又全。

**第二层：认得出需求，还原不出状态（RQ2）。** GPT-6 Sol 的需求覆盖率达 0.6777（约 2/3 的 Gold 需求能匹配上），但匹配上的需求其属性重建分只有 0.2671——"知道有这么个需求"和"知道这个需求的具体参数"之间隔着巨大鸿沟。全部配置的属性重建分都在 0.24–0.28。

**第三层：更新后全对为零（RQ3）。** 在两种历史条件下，**六个配置的 Exact Post-State Accuracy 全部为 0/312**。软指标上，最好的 Opus 5.5 在全部 Gold-ACT 目标上 Post-State Score 为 0.1670；即便只看它选对 ACT 的 256 个目标，也只有 0.2036；再看其中需求集与 Gold 完全匹配的 79 个目标，仍然只有 0.3656。

论文的失败分解（Table 28）进一步显示：312 个 Gold-ACT 目标按"第一处未满足条件"归类后，即使需求集完全匹配的 589 个（跨条件）保存分数也全部栽在状态字段严格正确性上，没有任何目标只输在最后的删除列表环节——**卡点在状态内容本身，不是边角格式**。

决策层面也有信号：全选 ACT 的"无脑基线"准确率就有 0.8940（因为 312:37 的类别不平衡），而 Opus 5.5 的决策准确率 C1 为 0.7880、平衡准确率 0.7335——只有 Opus 5.5 明显跑赢基线，其余配置连"该不该问"都分不太清。

### 5.3 主结果三：喂对答案也改不对项目（Oracle）

这是全文最有冲击力的结果（Table 4，六配置均值）：

| 指标 | C1 直接交付 | Oracle Pre-State | Oracle Post-State |
|---|---|---|---|
| Build 通过率 | 58.56% | 60.36% | **96.40%** |
| Target test 通过率 | 6.31% | 4.95% | **9.01%** |
| Regression 通过率 | 51.35% | 54.05% | **90.99%** |
| 完整交付率 | 4.95% | 4.50% | **8.11%** |

读数：

1. **喂入正确目标状态后，build 和 regression 几乎满分**（96.40% / 90.99%）：智能体完全有能力知道"哪些东西不该动"并维护一个可用的项目环境——正确的需求信息有效消除了"误伤历史功能"的问题；
2. **但目标测试只从 6.31% 涨到 9.01%**：知道"要改什么"之后，"把它改出来"依然几乎不会。Post-State 的 222 个"配置×目标"评估中 219 个提交了工件，其中 184 个（84.02%）通过 build 与 regression 却倒在目标测试上——**不是环境坏了、不是回归了，就是请求的变更本身没实现**；
3. **Pre-State 完整交付率 4.50%**：给了正确的请求前状态、只要求自己做一次更新+实施，结果与从零考古的 C1（4.95%）相当——更新环节同样不是省油的灯。

### 5.4 失败案例：两段式归因的教科书演示

论文的 PCB 案例（目标 43214420_T004）把两重瓶颈串成了一条因果链：

- **诊断侧**：客户要求把电池连接器移到板背面、与 USB-C 口相对。Opus 5.5 的 RQ1/RQ2 完美——需求 Precision = Recall = 1、证据 Recall = 1、覆盖 = 1，请求前状态里明确记有"8 个角上安装孔、M2.5 规格"等机械布局约束。**但更新后的目标状态里，整条机械布局需求消失了**（当前请求并未撤销它），Post-State Score 只有 0.3259；
- **交付侧**：GPT-5.6 Sol 的 Oracle Post-State 运行中，结构化描述文件（设计摘要、artifact model）都正确更新了连接器位置，**但交付的 PCB 文件与初始归档逐字节相同**——目标测试报告"连接器边缘法线不相对"（dot=1.000000，即方向完全没变）。

前一半说明"更新时丢失仍然有效的约束"，后一半说明"改文档不代表改工件"——论文也诚实标注：单案例证明的是三种现象的共存，不构成严格因果证明。

### 5.5 指标体系如何支撑核心主张

核心主张是"存在两重独立瓶颈"。支撑链条：

- 若只有理解瓶颈：Post-State 应接近 100% → 实际 9.01% 目标测试通过，证伪；
- 若只有实施瓶颈：诊断分数应与交付强相关且 Post-State 无改善 → 实际 build/regression 大幅改善（说明需求信息确实有用），证伪"信息无用"；
- C2 < C1 排除了"纯上下文长度问题"——过滤后的相关历史更短却更差，说明交付需要的历史信息超出了当前过滤器的表达能力。

## 六、效果优势的根源解释

本文是评测论文，"优势"指的是其归因结论的可靠性：为什么它能断言"两重瓶颈"而不被混杂因素误导？

### 6.1 根源机制与证据链

**结论一：需求目标状态形成是第一重瓶颈。**

- 因果链：长历史中需求多版本叠加 → 模型检索以"宁多勿漏"策略运行（证据 Recall 0.92 / Precision 0.23）→ 更新时无法在封闭世界假设下精确折叠状态（Exact 0/312）→ 且会丢弃已恢复的约束（PCB 案例）→ 交付时目标测试失败。【论文实验已支持】
- 机制解释（论文引用外部证据）：Laban et al. 2026（LLMs Get Lost in Multi-Turn Conversation）发现多轮对话中模型过度依赖先前答案、新信息到来时不修正早期假设；本文的"更新丢约束"现象与该机制一致——模型把"当前请求"当作增量补丁而非状态机迁移。【论文引用支持 + 阅读者推测的连接】

**结论二：既有项目修改是第二重独立瓶颈。**

- 因果链：Post-State 条件下需求变量被控制为 Gold → build/regression 达 96.40%/90.99%（说明模型能维护环境）→ 但目标测试仅 9.01% → 说明失败的自由度集中在"把指定变更实施进既有工件"这一步。【论文实验已支持，控制变量设计】
- 机制假设（论文自述为 hypothesis）：即使有明确目标，智能体仍可能保留早期假设或只做局部编辑，留下与更新需求不一致的实现——论文引用 SlopCodeBench（Orlanski et al. 2026）"迭代扩展导致结构复杂度与冗余代码累积"的发现作为旁证。【论文引用旁证 + 明确标注为假设】Oracle PCB 案例中"描述文件改了、工件字节未动"是该假设的具体呈现：修改停留在与验证器脱钩的表征层。

**反事实检验：**
- 去掉 Oracle 设计（即只有主实验）：4.95% 的失败无法分解，可能被全盘归咎于"上下文太长"——而 C2 更差（2.70%）已经提示这不是长度问题；
- 去掉诊断（只有交付）：无法发现 Exact 0/312 与"覆盖 1.0 但更新丢约束"的分离现象。

### 6.3 综合判断与未决问题

- **多项证据共同支持**：(a) 需求状态形成是真实瓶颈（0/312 + 软分数断层 + 案例）；(b) 实施是独立瓶颈（Oracle 控制变量下 9.01%）。

- **可能失效条件**：若未来模型具备真正的状态跟踪能力（而非上下文模式匹配），第一重瓶颈可能先于第二重消失；针对"工件-描述脱钩"的验证器反馈训练可能直接压缩第二重瓶颈。

## 七、必要知识反推

假设让一个完全没有背景的人从零完成这项工作，他至少需要掌握：

### 7.1 领域知识层

- **软件工程的需求管理实践**：为什么需求有生命周期（提出/推迟/撤销）、为什么需求追踪要链接到来源消息——不理解这些就无法设计出"需求原子"这个表示。论文的根基是 1994/2000 年的需求工程文献，这是一个"30 年前的领域知识在 LLM 时代复活"的典型案例；
- **自由职业平台的真实工作流**：客户-开发者多轮沟通、交付验收的实操形态——这决定了数据长什么样（Upwork 的独特贡献）；
- **PCB / 文档 / 软件三类交付物的验证方式**：PCB 怎么检查"连接器在背面"（边缘法线几何检查）、Word 模板怎么测（OOXML 结构）——没有这些知识设计不出 37 个可执行验证器。

### 7.2 方法论知识层

- **基准评测的设计原理**：控制变量（C1/C2 只变历史）、Oracle 对照（隔离理解与实施）、固定分母（防幸存者偏差）——这是实验科学方法在评测中的直接应用；
- **LLM-as-judge 的工程化**：让 LLM 只判语义关系标签、程序负责匹配与计分，加上跨诊断一致性检查与人工仲裁——需要同时理解 LLM 的能力边界与图匹配算法（最大基数一对一匹配、增广路径）；
- **长期记忆评测的既有谱系**：LongMemEval 等工作的指标设计经验，避免重新发明轮子。

### 7.3 工程知识层

- **Agent harness 的运行控制**：每目标独立进程、时间预算（诊断 900 秒 / 编码 1,800 秒）、工具权限隔离（禁网络、禁跨运行窥视）、响应冻结与契约校验；
- **可复现环境工程**：37 个初始环境必须满足"Build 过 / Target 败 / Regression 过"的初始验证——这本身就是一个不小的数据工程；
- **确定性重放系统**：事件操作语义（如"REMOVE 后不许复活但允许后续实现声明"）与状态图构建的程序化实现。

### 7.4 知识融合的关键节点

最有价值的融合发生在两处：

1. **需求工程 × 状态机 × LLM 评测**：把 30 年前的需求追踪理论转化为"需求原子状态图"，再转化为可逐字段评分的 benchmark 对象——三个领域的化学反应；
2. **Oracle 对照 × 交付验证**：把心理学/医学的"干预实验"思想引入编码评测——不观察现象（分数低），而是干预系统（喂正确状态）并观察哪个环节的失败消失。没有这个融合，"两重瓶颈"的结论无从谈起。

## 八、论文中可以提取的通用性灵感

### 灵感 1：用"状态机重放"评测一切历史依赖任务

- **核心思想**：凡是答案 = 历史事件折叠结果的任务，都可以用"原子化 + 事件重放 + 快照比对"来构造可部分给分的诊断。
- **论文证据**：需求原子五维状态 + 确定性重放 + Post-State Score 软评分，使"差多少"变得可量化（0/312 严指标与 0.17–0.37 软指标的分离）。
- **推广场景**①：法务合同审阅（条款原子的生效/变更/终止重放）；②：产品需求管理工具自动生成 PRD 当前版；③：客服工单系统判断"用户此刻到底要什么"；④：科研代码库的配置漂移溯源；⑤：多轮谈判代理的中期状态审计。

### 灵感 2：Oracle 干预是归因的王牌

- **核心思想**：想知道链路哪一环拖后腿，就把该环的输出替换为金标准再测全程——改善幅度即该环的边际贡献。
- **论文证据**：Post-State 把 build/regression 拉到 96.40%/90.99% 而目标测试仅 9.01%，一击定位"实施瓶颈"。
- **推广场景**①：RAG 系统分别喂金标准检索结果/金标准重写，定位检索 vs 生成瓶颈；②：多模态管线做金标准感知注入；③：agent 工作流逐节点 golden-pass-through；④：数据标注流水线定位人工/自动环节质量；⑤：自动驾驶模块化栈的逐模块回放测试。

### 灵感 3：删上下文 ≠ 提性能，信息构成比长度更关键

- **核心思想**：先验地"帮模型省上下文"（过滤、摘要）可能删掉交付所需的隐性信息；相关性的定义必须以任务输出为准，而非以话题相似度为准。
- **论文证据**：C2 平均历史仅 8.7 轮（C1 的 1/21），完整交付率反而从 4.95% 掉到 2.70%。
- **推广场景**①：企业知识库的 RAG 预过滤策略评估；②：长对话助手的记忆压缩阈值设计；③：代码仓库的上下文裁剪工具；④：多文档摘要保留策略；⑤：agent 记忆系统的"遗忘"机制设计——忘错比不忘更贵。

### 灵感 4：描述层更新 ≠ 工件层更新，验证必须锚定工件

- **核心思想**：智能体可能更新了所有"关于工件的结构化描述"而工件本身一字未动——评估与训练信号必须直接锚定最终工件。
- **论文证据**：Oracle PCB 案例中设计摘要/artifact model 均已更新，交付的 PCB 文件却与初始归档逐字节相同。
- **推广场景**①：设计工具代理（Figma/CAD）的验收测试；②：数据库 schema 迁移代理的最终状态断言；③：基础设施即代码的 drift 检测；④：自动化报告生成的事实-底稿一致性核验；⑤：游戏资产生成管线的产物级（而非日志级）验收。

### 灵感 5：封闭世界假设是对抗"宁多勿漏"的解药

- **核心思想**：模型的默认策略是高召回低精度（证据 Recall 0.92 / Precision 0.23），在需要精确状态的任务上，评测和训练都应显式引入封闭世界假设——多余即错误。
- **论文证据**：Exact Post-State Accuracy 要求"无漏无多 + 全字段正确 + 删除列表一致"，全部配置 0/312；失败分解显示需求集全匹配的样本仍全部败于状态字段。
- **推广场景**①：结构化信息抽取的严格模式；②：医疗处方的禁忌项完整性检查；③：配置管理的漂移审计；④：法规合规清单的逐项核对；⑤：agent 记忆写入的"精确性"奖励设计。

### 灵感 6：把"该不该问"作为一等公民评测对象

- **核心思想**：知道何时信息不足并问出"能解锁决策的问题"，与知道答案同等重要；类别不平衡下的决策评测必须对照无脑基线。
- **论文证据**：349 目标里 37 个 Gold-CLARIFY；always-ACT 基线准确率即达 0.8940，多数配置的决策质量未能显著超越它；Question Validity 单独评测"问题能否换来关键信息"。
- **推广场景**①：医疗问诊 AI 的追问策略；②：需求访谈机器人；③：安全审计的澄清式扫描；④：科研复现代理的缺信息处理；⑤：客服升级人工的触发决策。
