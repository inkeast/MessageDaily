## 一、论文背景

### 1.1 编码 Agent 的"视觉"问题

LLM Agent 正越来越多地被用于**仓库级（repository-level）软件工程任务**：故障定位、issue 修复、测试生成、安全补丁。这些任务有个共同的前置环节——Agent 必须先**找到正确的代码上下文**：哪个文件、哪个函数与任务相关、该看什么证据，然后才能推理和编辑。

但当前主流编码 Agent（Claude Code、SWE-agent、Agentless、OpenHands）访问仓库的方式出奇地"原始"：**裸文件 + 词法搜索 + shell 命令**。也就是说，Agent 把代码当成纯文本来对待。要知道某个符号在哪定义、谁调用了它、哪些模块依赖它，Agent 只能反复 grep、读文件、试错——这些操作本质上是在**手工重建**程序的结构信息。

### 1.2 程序本身有现成的"地图"

程序分析领域几十年积累告诉我们，代码天然有多种结构化视图：

- **抽象语法树（AST）**：暴露定义与嵌套包含关系——"代码住在哪里、怎么分组"
- **调用图（Call Graph）**：暴露过程间控制流——"谁调用谁"
- **依赖图（Dependency Graph）**：暴露模块级耦合——"哪个文件 import 哪个文件"
- **文档（Docs）**：连接自然语言与代码意图——"这段代码想干什么"

这些视图在代码智能研究（TBCNN、GraphCodeBERT、DocPrompting 等）中早已是标准工具，但它们在 **LLM Agent 工作流**中扮演什么角色，一直缺乏系统理解。

### 1.3 核心痛点：表示与脚手架"捆绑销售"

此前的研究有个方法论缺陷：**代码表示总是和 Agent 脚手架、检索方法、修复循环捆绑在一起**。比如 AutoCodeRover 强调结构化实体搜索，ARISE 暴露仓库图工具——它们都是完整系统。当一个系统比 baseline 好时，你无法区分提升来自模型、prompt、Agent 策略，还是那个代码视图本身。

这就像评测"导航仪是否有用"，但每辆装导航仪的车同时换了发动机和轮胎。论文要做的，就是**只换导航仪，其他全部冻结**的受控实验。这填补了一个明确空白：我们缺少"哪种表示、对哪类任务、以什么代价有帮助"的系统比较。

## 二、论文定位和关联工作

论文 Related Work 梳理出三条研究脉络，本论文站在三条脉络的交叉点上。

### 2.1 仓库级 Agent 软件工程

| 工作 | 核心思想 | 与本论文的关键区别 |
|---|---|---|
| SWE-bench (ICLR'24) | 确立了真实 GitHub issue 的仓库级修任务设置 | 只提供基准，不研究表示 |
| SWE-agent (NeurIPS'24) | 证明"Agent-计算机接口"塑造 Agent 行为 | 接口与 Agent 绑定，非受控变量 |
| AutoCodeRover (ISSTA'24) | 定位先于修复，结构感知的代码实体搜索 | 完整系统评估，表示效果无法分离 |
| Agentless (FSE'25) | 分解为定位-修复-验证的简单脚手架 | 上下文选择策略固定 |
| OrcaLoca (ICML'25) | 动作调度+分解+上下文剪枝改进定位 | 评估完整系统 |
| ARISE (arXiv'26) | 暴露仓库图与切片工具 | 特定表示设计，非横向比较 |

**共同局限**：评估的是完整系统或单一表示设计。本论文**冻结 Agent 脚手架，把代码视图本身作为实验变量**。

### 2.2 面向结构与意图的代码表示

| 工作 | 核心思想 | 与本论文的关键区别 |
|---|---|---|
| TBCNN (AAAI'16) | 用 AST 建模语法结构的树卷积网络 | 表示嵌入模型内部 |
| Allamanis et al. (ICLR'18) | 程序的语义关系图表示 | 同上 |
| GraphCodeBERT (ICLR'21) | 数据流融入预训练 | 同上 |
| DocPrompting (ICLR'23) | 检索文档辅助代码生成 | 用于生成而非 Agent 导航 |
| RepoRepair (arXiv'26) | 层次化文档辅助仓库级修复 | 特定系统 |

**区别**：这些工作把表示嵌进模型/检索器/修复系统内部；本论文把 AST/CG/Deps/Docs/Hybrid 作为 **MCP 工具在 Agent 轨迹中动态暴露**。

### 2.3 仓库级上下文检索

RepoBench、CrossCodeEval 评估跨文件补全；RepoCoder 用迭代检索生成；Repoformer 证明"更多上下文不总是更好"；图路线的 GraphCoder、RepoGraph、LocAgent、CodeGraph 暴露仓库图或图引导搜索。**共同点：每个系统承诺一种图设计和检索策略**；本论文则固定 Agent，把代码视图作为受控变量横向比较五种。

### 2.4 定位结论

**之前的路线**：表示 = 系统组件（与脚手架捆绑，无法归因）
**本论文的突破**：表示 = 独立实验变量（MCP 工具服务器 + 固定 Agent 栈 + 同任务 ID 网格）

这是第一篇在**同一 Agent 栈、四个仓库级任务**上受控比较五种代码表示的工作。

## 三、问题定义

### 3.1 从具体到抽象

**具体问题**：编码 Agent 该通过什么表示访问代码库？AST 好还是调用图好？

这个问题难以直接回答，因为"好"取决于任务。论文的核心洞察是把问题抽象为**瓶颈匹配问题**：

> 每个仓库级任务都有一个当前瓶颈（定位代码 / 写补丁 / 写断言 / 安全推理）。代码表示的价值 = 它暴露的关系是否命中任务瓶颈。

### 3.2 类比

代码表示之于编码 Agent，就像**索引结构之于数据库查询**：

| 数据库世界 | 本论文世界 |
|---|---|
| B+ 树索引 | AST（按结构组织） |
| 外键连接 | Call Graph（调用关系） |
| 分区表 | Deps（模块依赖） |
| 全文倒排索引 | Docs（BM25 文档检索） |
| 物化视图 | Hybrid（多关系融合地图） |
| 查询类型 | 任务瓶颈（定位/修复/测试/安全） |
| 没有索引的全表扫描 | baseline 的 grep+read 浏览 |

索引不会让写 SQL 更快，只让查找更快——这正是论文发现的类比。

### 3.3 形式化定义

一次 Agent 运行被参数化为元组：

```
⟨agent, model, representation, benchmark task⟩
```

- **给定**：固定 agent 框架（Claude Code）、固定模型（claude-haiku-4-5-20251001, effort=low）、固定基准任务集（同任务 ID）
- **求**：representation ∈ {无MCP baseline, AST, Callgraph, Deps, Docs, Hybrid} 对以下度量的因果影响：任务成功率、token 用量、墙钟时间、工具调用行为
- **约束**：MCP 服务器设计需 agent 无关（agent-agnostic）、检索由 Agent 主动执行（agent-executed retrieval，不预计算塞 prompt）

### 3.4 抽象的精妙之处

这个设计的价值在于**归因能力**：任何行为差异（成功率、token、工具使用）只能来自表示变量，因为其他全部冻结。同时"按需查询的地图"（on-demand repository map）保留了 Agent 的自主性——它不是被动接收上下文，而是主动决定何时查询哪种视图。

## 四、问题解法

### 4.1 五种代码表示：五张不同的"仓库地图"

每种表示是一个**图地图**：节点是代码单元，边是该表示编码的关系。

| 表示 | 节点 | 边 | 回答的问题 | 类比 |
|---|---|---|---|---|
| AST | 函数/方法/类/变量等定义 | 语法包含（文件→顶层定义→嵌套定义） | "代码住在哪里、怎么分组" | 图书馆的书架目录 |
| Callgraph | 函数/方法 | 解析后的调用边（caller→callee） | "控制流怎么走、症状如何沿调用链溯源" | 地铁线路图 |
| Deps | 文件（附带定义） | import 边（file→imported file） | "模块怎么组织、改一处波及哪里" | 城市行政区划图 |
| Docs | 有文档的符号 | 无边（纯 BM25 全文检索） | "用人类语言描述的意图对应哪段代码" | 百科全书索引 |
| Hybrid | 函数+文件 | calls+imports+contains 三合一 | 以上全部，外加变更影响半径 | 综合地图 App |

**关键细节**：
- Docs 没有图结构可走，因此跳过图扩展，直接按 BM25 对文档化符号排序——这使它天然适合"自然语言提问"
- Hybrid 不是新结构，而是融合：contains 边承载 AST 骨架，一张图同时持有包含、调用、依赖三种关系

### 4.2 实现架构：表示 = MCP 工具服务器

每种表示实现为一个 **Model Context Protocol (MCP) 工具服务器**，运行前对目标仓库建索引、存为可搜索的仓库地图。

**解析技术栈**（工程知识层的亮点）：
- 所有语言统一用 **tree-sitter** 解析（带各语言语法）
- Python：调用关系用 **jedi** 解析、import 依赖从 import/from 语句提取、docstring 用 **griffe** 加载
- C/C++（jedi/griffe 不适用）：调用通过"调用名匹配仓库级定义"解析、依赖从 #include 提取、文档取定义前紧邻的注释块

**统一查询流程**（所有服务器共享）：
1. **种子节点**：SQLite FTS5 全文索引 + BM25 排序（符号名匹配权重 > 签名 > 文档 > 代码体）
2. **图扩展**：结构化服务器沿各自关系扩展（AST 沿包含、CG 沿调用、Deps 沿 import、Hybrid 沿全部合并边）
3. **邻域排序**：random-walk-with-restart 中心性（从种子节点出发），最高分的源码片段按文件分组返回
4. Docs 例外：跳过图扩展，直接返回 BM25 排序的文档化符号

### 4.3 每个服务器暴露的 MCP 工具

| 服务器 | 工具数 | 代表性工具 |
|---|---|---|
| AST | 8 | ast_explore, ast_node, ast_search, file_skeleton, ts_query, parse_file |
| Callgraph | 9 | callgraph_explore, callers_of, callees_of, call_path, function_info |
| Deps | 8 | deps_explore, module_deps, dependency_path, layer_summary, cycles |
| Docs | 6 | docs_explore, docs_node, module_overview, repo_map |
| Hybrid | 6 | hybrid_explore, impact_of（变更影响半径）, repo_map |

设计保证所有服务器共享 `<rep>_explore` / `<rep>_node` 导航对，给 Agent 可比的入口，同时允许关系特定操作。

### 4.4 实验网格

```
(1 baseline + 5 表示工作流) × 4 基准 = 24 组受控配置
```

- **Agent 栈**：Claude Code CLI，claude-haiku-4.5（解析为 20251001 快照），effort=low，内置工具通过 `--tools` 钉死为 Read/Edit/Write/Bash/Grep/Glob
- **表示工作流**：通过 `--mcp-config` 挂载对应 stdio MCP 服务器；baseline 不挂载
- **MCP 设计两性质**：Agent 无关（同一服务器可无修改地跑在 Codex 等任何 MCP 兼容宿主上）；Agent 执行检索（不预计算塞 prompt，Agent 自己发查询并整合进轨迹）
- **采样**：95% 置信水平、5% 误差边际的样本量估计，随机种子确定、所有工作流用**相同任务 ID**

### 4.5 四个基准：四种瓶颈

| 基准 | 任务 | Agent 输出 | 成功度量 | 样本量 |
|---|---|---|---|---|
| LinuxFLBench | Linux 内核 bug 报告故障定位 | 最多 10 个可疑文件排序列表 | 文件级 recall@k (k∈{1,10}) | 152 |
| SWE-bench Pro | 真实 GitHub issue 程序修复 | unified-diff 补丁 | 解决率（通过全部 fail-to-pass 且保持 pass-to-pass） | 253 |
| SWT-bench | 从 issue 生成测试 | 复现 bug 的单元测试 | 复现测试率（bug 版失败且修复后通过） | 161 |
| SecBench | 漏洞自动安全补丁 | 安全补丁 | 补丁接受率 | 166 |

这四个任务的精心选择构成**瓶颈谱系**：纯定位（LinuxFLBench）→ 定位+编辑（SWE-bench Pro）→ 定位+安全推理（SecBench）→ 定位+断言写作（SWT-bench）。

**行为/成本度量**：每任务平均 token、墙钟秒、MCP 调用数、原生工具调用数（细分 read/grep/glob/bash）。

## 五、评估指标与实验证据

### 5.1 RQ1 主结果：成功率与成本的全景

#### LinuxFLBench（故障定位）——表示的"主场"

| 工作流 | recall@1 | recall@10 | avg tokens | 墙钟(s) | MCP | 原生 | read | grep | bash |
|---|---|---|---|---|---|---|---|---|---|
| Baseline | 0.572 | 0.717 | 1,008,163 | 66.7 | 0 | 25.4 | 8.4 | 6.0 | 9.5 |
| AST | 0.526 | 0.757 | 754,768 | 104.6 | 13.1 | 0.9 | 0.5 | 0.0 | 0.3 |
| Callgraph | 0.572 | 0.770 | 683,227 | 105.1 | 11.0 | 2.2 | 1.1 | 0.0 | 1.1 |
| Deps | 0.572 | 0.757 | 628,244 | 87.6 | 8.5 | 0.7 | 0.4 | 0.0 | 0.3 |
| Docs | 0.586 | 0.770 | 662,834 | 105.6 | 11.1 | 2.4 | 0.6 | 0.0 | 1.7 |
| **Hybrid** | 0.526 | **0.829** | **610,910** | 82.2 | 9.5 | 0.5 | 0.3 | 0.0 | 0.3 |

**解读**：
- 五种表示 recall@10 全部超过 baseline（0.757–0.829 vs 0.717），Hybrid 最高
- token 全降 25–39%（Hybrid 最省，-39%）
- recall@1 差异小且有涨有跌——收益主要在**改善 top-10 候选集**，不是稳定产出第一名
- 机制可见于工具列：baseline 靠 8 次 read + 6 次 grep + 10 次 shell 拼答案；表示工作流用 9–13 次地图调用替换几乎全部浏览，read 降到 ≤1.1，grep/glob 归零
- **代价**：墙钟时间上升（66.7s → 82–106s）

#### SWE-bench Pro（程序修复）——效率收益保留，准确收益消失

| 工作流 | 解决率 | avg tokens | 墙钟(s) | MCP | 原生 | read |
|---|---|---|---|---|---|---|
| Baseline | 49.0% | 3,116,193 | 268.8 | 0 | 44.5 | 12.7 |
| AST | 50.6% | 2,450,752 | 209.1 | 5.2 | 37.7 | 8.4 |
| Callgraph | 46.2% | 2,310,653 | 193.7 | 4.2 | 38.1 | 8.7 |
| Deps | 49.4% | 2,406,690 | 205.3 | 3.4 | 39.1 | 8.6 |
| Docs | 44.3% | 2,532,738 | 205.8 | 4.9 | 39.0 | 7.6 |
| Hybrid | 50.6% | 2,590,046 | 204.3 | 4.3 | 39.2 | 8.6 |

**解读**：
- 每种表示 token 降 17–26%（Callgraph 最省 2.31M，-26%）
- 解决率贴近 baseline：AST/Hybrid 50.6%、Deps 49.4%（噪声内），Callgraph 46.2%、Docs 44.3% 略降
- 墙钟反而下降（268.8s → 194–209s），因为浏览轮次减少
- **结论**：地图主要替换仓库浏览，不直接提升补丁质量

#### SWT-bench（测试生成）——瓶颈在断言写作

| 工作流 | 复现率 | avg tokens | 墙钟(s) |
|---|---|---|---|
| Baseline | 44.7% | 1,671,772 | 161.4 |
| AST | 45.3% | 1,772,180 | 170.1 |
| Callgraph | 37.9% | 1,687,094 | 201.1 |
| Deps | 42.9% | 1,771,300 | 184.2 |
| Docs | 47.2% | 1,823,938 | 185.1 |
| **Hybrid** | **47.8%** | 1,871,848 | 192.5 |

**解读**：
- Hybrid（47.8%）与 Docs（47.2%）小幅领先（+3.1 / +2.5 pp），Callgraph 明显掉队（37.9%，-6.8pp）
- **所有表示 token 与时间全涨**——地图上下文叠加在原生浏览之上
- 决定性步骤是写出有区分力的断言，不是找到代码

#### SecBench（安全补丁）——调用图的高光时刻

| 工作流 | 解决率 | avg tokens | 墙钟(s) |
|---|---|---|---|
| Baseline | 28.9% | 683,774 | 66.4 |
| AST | 25.3% | 656,332 | 166.6 |
| **Callgraph** | **34.3%** | 614,360 | 184.2 |
| Deps | 31.9% | 651,116 | 144.4 |
| Docs | 31.3% | 697,763 | 290.4 |
| Hybrid | 29.5% | 658,069 | 136.4 |

**解读**：
- Callgraph 最高（34.3%，+5.4pp），Deps/Docs 也涨，AST 反而掉（25.3%）
- 原因：SecBench 输入是**栈中心**的（crash stack frame），成功需要沿调用链从崩溃帧走到拥有不变量的调用方/被调用方上下文——这正是调用图的关系
- 所有表示墙钟大涨（66.4s → 136–290s）

### 5.2 指标体系如何支撑核心主张

- **主指标**（任务成功）：recall@10 / 解决率 / 复现率——证明"收益任务依赖"
- **辅助指标**（token/时间/工具行为）：证明机制——地图**置换**浏览（read 下降、MCP 调用上升），而非魔法提升
- **消融**（五种表示横向对比 + Hybrid 合并）：证明"关系类型要匹配瓶颈"
- **RQ2 轨迹分析**（下文详述）：实例级 win/loss 归因，把"表示有用"落到"什么条件下有用"

**这套设计的证明力**：如果表示普遍提升 Agent 能力，四个基准的成功率应全面上涨——实际只有定位类全涨，修复类持平，测试类混合，安全类仅调用图突出。**这个模式本身就是"瓶颈匹配假说"的证据**。

### 5.3 RQ2：实例级分歧全景

Table VII 统计每个表示相对 baseline 的实例级 win（baseline 败我胜）/loss（反之）与 token 更少/更多：

| 基准 | 表示 | Win | Loss | Net | Token少 | Token多 |
|---|---|---|---|---|---|---|
| LinuxFLBench | AST | 17 | 11 | +6 | 111 | 41 |

### 5.4 轨迹编码：为什么赢、为什么输

两位作者端到端阅读每对分歧轨迹（查询内容、返回地图、读写文件、最终产物），写自由文本归因，迭代归类到稳定。每格报告 n/N（该类占该结果总数的比例）。

#### 性能轴的根因类别

**LinuxFLBench（定位类输赢完全由"关系是否命中 bug 形态"决定）**：

| 表示 | 主导 win 类别 | 主导 loss 类别 |
|---|---|---|
| AST | 报告点名文件内故障（17/17） | 症状≠根因文件，结构上远距（7/11） |
| Callgraph | 调用可达的跨文件故障（17/17） | 邻居漂移（5/9）、排序稀释 |
| Deps | 报告点名函数/API（13/17） | 架构文件在 import 簇之外（9/11） |
| Docs | 术语命中注释（17/17） | 仅崩溃症状无术语（7/9） |
| Hybrid | 单目标文件直落（11/17）+跨子系统症状到故障（6/17） | **零败绩** |

论文给出两个经过验证的 Callgraph 案例：
- **Win（LinuxFLBench 14053）**：NFS 挂载 rsync 时内核冻结，故障在症状两层之下的 RPC 客户端 net/sunrpc/clnt.c。调用图沿 RPC 调用链把 clnt.c 拉进地图排 #9；AST/Deps 的关系困在 fs/nfs/* 症状目录内，baseline 42 个动作后仍错过。**只有调用关系跨越 NFS→RPC 层**。
- **Loss（LinuxFLBench 5093）**：WiFi 卡挂起，故障在 atmel.c 驱动。调用图跟着固件/resume 调用链漂到 PCMCIA 胶水层，从未到达 atmel.c（驱动加载固件的路径不是直接调用边，图中不存在）；baseline 的关键词搜索反而把 atmel.c 排 #1。**症状不调用到的"兄弟"文件，调用图漂向错误邻居**。

**SWE-bench Pro（主导 loss 高度一致："定位对了，补丁写错"）**：

所有表示的主要失败类别都是 correct localization, wrong patch（16–23 个 loss）：地图找到了 gold-patch 文件、Agent 也编辑了，但修复逻辑错误。例如 Deps 案例（ansible-942424e1）：deps_explore 两三次调用就到达确切故障文件，但 k=1 单次补丁尝试逻辑错误；baseline 到达同一文件恰好一次通过。**这是修复方差，不是定位失败**。

还有一类**所有地图都无力的任务形态**：全树查找替换（索引给出定义但非全部引用点）、新建文件（无现有文件可检索）、非 Python 修复点（YAML、docker-compose）。

**SecBench（Callgraph 赢在"执行关系的显著性"）**：

Callgraph 主导 win 是 flow localization（9/18）：查询或选中节点与崩溃栈函数或最终编辑文件重叠。最有说服力的对照：Callgraph 解决而 Hybrid 未解决的 18 个实例中，**Hybrid 在 14 个案例里编辑了与 Callgraph 相同的文件但仍未产出成功补丁**——说明到达文件不够，Hybrid 的额外上下文可能稀释了执行流信息的显著性。Win 案例（gpac CVE-2023-4682）：AVI 解复用溢出，调用图把崩溃栈 avi_read/AVI_read_frame 链接到解复用路径，一行状态修复落在 dmx_avi.c 通过；baseline 在 avilib.c 加 size cap，sanitizer 仍触发。Loss 案例（faad2 CVE-2021-32278）：调用图编辑崩溃点 lt_predict.c 钳制索引，sanitizer 仍触发；baseline 修 syntax.c 在预测前拒绝无效元数据——**崩溃点太显著时，调用中心视图反而掩盖真正该修的调用方格式不变量**。

**SWT-bench（输赢同一类别：测试方差）**：

所有表示的主导 win 和主导 loss 类别相同：写出与 baseline 相同或相邻测试目标的测试，k=1 的生成恰好复现/不复现。Test-variance win 占各表示 win 的 15–25/18–28。**瓶颈在断言写作，不在找代码**。

#### Token 轴的根因类别

**省 token 的主导机制——read displacement（读取置换）**：地图返回的源码体被 Agent 视为"已读"，免去大量源文件读取。LinuxFLBench 上 AST 79/111、Callgraph 109/109、Deps 72/115、Docs 93/115、Hybrid 85/117 的更少 token 运行由此解释；SWE-bench Pro 上同样占绝对主导（115–188 / 181–197）。

**超支的三种模式**：
1. **Map overhead（地图开销）**：简单任务 baseline 便宜解决，地图调用纯属多余（AST 在 LinuxFLBench 的 30/41 超支运行）
2. **Over-exploration（过度探索）**：文件已找到仍反复精化查询（Docs 常见，SWT-bench 上 102/102）
3. **Verbatim-source explosion（原文爆炸）**：单次合并图查询返回巨大原文载荷（Hybrid 常见，SWT-bench 上 94/94）

论文的 Docs 对照案例：fewer-token 运行（LinuxFLBench 16043）中 docs_explore 直接返回故障文件原文，零源码读取得分，token 为 baseline 的 0.15×；more-token 运行（11391）中报告直接点名文件，baseline 几步搞定，Docs 的廉价查询反而诱发冗余精化，token 膨胀到 baseline 的 27.7×。**同一表示、同一基准，效果天差地别——取决于任务与关系的匹配**。

### 5.5 效度威胁（论文自陈）

- **内部**：Agent 运行非完全确定；处理组实际结合了表示内容、可用性与"地图优先"工作流（含强制一次地图查询的 pre-tool-use hook），行为变化不能全归于数据结构本身
- **外部**：单一 Agent 栈（Claude Code）、四基准，其他模型/语言/仓库可能不同
- **构建**：基准成功不完全等于补丁质量；token/工具计数省略了建图、克隆、Docker 等一次性成本
- **统计**：每实例每工作流只跑一次（k=1）而非 pass@k 多样本协议，小差异（尤其 SWT/SecBench）可能是一次性方差——因此论文强调大而一致的效应与轨迹证据，把接近的解决率作描述性处理

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**核心问题**：为什么表示工作流在定位类任务上同时升 recall 降 token，在编辑类任务上却收益消失？

**因果链 1：read displacement → token 下降（论文实验已支持）**

```
地图把相关源码体内联返回
→ Agent 将其视为"已读"，跳过大量 Read 调用
  （LinuxFLBench：read 8.4→≤1.1，grep 6.0→0，bash 9.5→≤1.7）
→ 每任务的浏览轮次坍缩
→ token 下降 25–39%
```

RQ2 的实例级归因直接支持：更少 token 的运行绝大多数由 read displacement 解释（Callgraph 在 LinuxFLBench 上 109/109）。

**因果链 2：关系命中 → recall 上升（论文实验已支持）**

```
bug 报告的"信号形态"决定哪种关系能到达根因：
- 报告点名符号 → AST 包含边直达文件
- 症状与根因跨文件有调用链 → Callgraph 穿越
- 报告点名 API → Deps import 簇召回
- 报告用领域术语 → Docs 全文命中注释
四种单一关系各覆盖一种 bug 形态（各 17/17 win）
→ Hybrid 合并全部线索 → 零 loss、recall@10 0.829
```

**因果链 3：瓶颈迁移 → 收益消失（论文实验已支持，本文认为是全文最重要发现）**

```
任务瓶颈 = 定位（LinuxFLBench）→ 表示命中瓶颈 → 成本收益双正
任务瓶颈 = 补丁不变量/测试断言（SWE-bench Pro / SWT-bench）
→ 地图只能改变"去哪"，不能改变"怎么改"
→ 成功率贴近 baseline（44.3–50.6% vs 49.0%）
→ 主导失败变成 "correct localization, wrong patch"（16–23 loss）
→ 地图上下文叠加在仍需的读写之上 → token 反升（SWT-bench 全线）
```

**因果链 4：信息显著性 > 信息量（SecBench 的 Callgraph 之谜，论文实验已支持）**

Hybrid 含调用边却不如纯 Callgraph（29.5% vs 34.3%）。论文的关键证据：Callgraph 解决而 Hybrid 失败的 18 例中 Hybrid 有 14 例编辑了同一文件。解释：Hybrid 的额外上下文稀释了执行流关系的显著性——**起作用的不是"有调用信息"，而是"调用信息是最显性的导航信号"**。这类似注意力稀释：选项越多，关键线索的相对突出度越低。

**因果链 5：超支的机制（论文实验已支持）**

三种模式（map overhead / over-exploration / verbatim-source explosion）共同说明：地图查询太便宜时，Agent 会"顺手多查"——廉价查询诱发冗余精化（Docs 案例 token 膨胀到 27.7×）。

### 6.3 综合判断与未决问题

**多研究共同支持的机制**：
1. read displacement 省 token（本文 RQ1/RQ2 双重证据）
2. 关系-瓶颈匹配决定收益（四基准模式 + RQ2 类别分析）
3. 信息显著性可胜过信息量（SecBench Callgraph vs Hybrid 的 14/18 同文件证据）

**仍属推测的机制**：
- "注意力稀释"式的显著性解释是作者基于 14/18 证据的合理推断，未经直接注意力检验
- 超支三模式的边界（何种任务分布下地图开销占主导）未量化

**优势成立条件**：任务瓶颈在定位、报告信号与某种关系形态匹配、任务本身非平凡（否则 map overhead）。
**可能失效条件**：全树查找替换、新建文件、非代码产物（YAML/配置）、k=1 方差主导的近平衡场景、其他模型/Agent 栈（论文只测了 Haiku 4.5 + Claude Code）。

## 七、必要知识反推

假设一个没有任何背景的人要完成这项研究，他最少需要知道什么？

### 7.1 领域知识层

- **仓库级 SE 任务的作业流程**：真实 issue → 定位 → 编辑 → 验证的链条，以及每一步 Agent 需要什么信息。不理解这个就无法设计"瓶颈谱系"四基准。
- **四种代码表示各自"看到"什么**：AST=包含、CG=调用、Deps=import、Docs=意图。这是把"代码视图"拆成可控变量的前提。
- **四个基准的评测协议**：recall@k、fail-to-pass/pass-to-pass、复现测试的判定。否则无法解释"解决率"背后的语义。

### 7.2 方法论知识层

- **受控变量实验设计**：为何必须冻结 ⟨agent, model, task IDs⟩、为何捆绑归因是此前工作的缺陷——这是全文方法论贡献的根基。
- **MCP 协议与工具服务器模式**：知道 MCP 是什么、stdio 挂载怎么做，才能实现"表示 = 可插拔服务器"。
- **检索技术栈**：BM25/FTS5 全文检索、random-walk-with-restart 中心性——统一查询流程的两大支柱。
- **采样理论**：95% 置信 + 5% 误差的样本量估计（Cochran 抽样技术），保证 152–253 的样本量有统计代表性。
- **轨迹编码（qualitative coding）方法**：两人独立阅读、自由文本归因、迭代稳定归类——RQ2 的质性分析规范。

### 7.3 工程知识层

- **多语言解析工具链**：tree-sitter（通用语法）、jedi（Python 调用解析）、griffe（docstring），以及 C/C++ 下降级方案（名称匹配 + #include + 前置注释）。
- **Claude Code CLI 的配置面**：`--tools` 钉内置工具、`--mcp-config` 挂服务器、effort 参数——实验基础设施。
- **成本与行为的度量管线**：token 计数、墙钟、工具调用分类统计的实现。

### 7.4 知识融合的关键节点

1. **"受控实验" × "代码表示"**：把 SE 实验方法论的因果推断需求，落到"表示做成 MCP 服务器"的工程实现上——这是论文设计的化学反应点。
2. **"瓶颈谱系" × "基准选择"**：意识到四个现成基准恰好张成"定位→编辑→断言"的瓶颈维度，使任务依赖性结论可以被**结构化地**读出，而非事后讲故事。
3. **"量化网格" × "质性轨迹"**：RQ1 的聚合数字定位"哪里有差异"，RQ2 的轨迹编码解释"为什么有差异"——混合方法在归因上的融合。
4. **"显著性"洞察**：SecBench 中 Callgraph vs Hybrid 的同文件对照，把"信息多≠信息好"从直觉变成可检验的机制命题。

## 八、论文中可以提取的通用性灵感

### 灵感 1：瓶颈诊断先于工具选型（范式迁移类）

**核心思想**：任何辅助工具（表示、索引、上下文）的价值由"任务的当前瓶颈是否被它命中"决定，而非由工具本身的先进性决定。
**论文证据**：同一 Hybrid 表示，LinuxFLBench recall@10 +15.6% 且 token -39%，SWT-bench token +11.9% 且复现率仅 +3.1pp；SWE-bench Pro 全部表示解决率贴近 49.0% baseline。
**推广场景**：
- RAG 系统选型：先诊断错误来自检索还是生成，再决定优化检索器还是提示工程
- 数据库性能调优：先看慢查询是缺索引还是算力瓶颈
- 教育科技：学习困难来自概念缺失还是练习不足，决定推送讲解还是习题
- 团队管理：交付慢是沟通瓶颈还是工程瓶颈，决定加会议还是加工具

### 灵感 2：信息显著性可以胜过信息量（机制类）

**核心思想**：给决策者（人或模型）更多信息而稀释关键线索的显著性，可能不如只给最相关的少量信息。
**论文证据**：SecBench 上纯 Callgraph 34.3% vs 含调用边的 Hybrid 29.5%；Callgraph 赢 Hybrid 的 18 例中 14 例 Hybrid 编辑了同一文件仍失败。
**推广场景**：
- LLM 上下文工程：长上下文塞满不如精准截选，避免"大海捞针"退化
- 仪表盘设计：核心 KPI 突出显示优于全量指标平铺
- 医疗诊断界面：鉴别诊断线索置顶，而非全病历平铺
- 提示词设计：少而准的示例往往优于多而杂的示例堆砌

### 灵感 3：读取置换——用"结构化答案"消灭"探索成本"（机制类）

**核心思想**：若辅助工具能内联返回目标内容本身，用户会跳过整个探索阶段，成本收益远超"辅助探索"。
**论文证据**：read displacement 解释了绝大多数 token 节省（Callgraph 在 LinuxFLBench 109/109）；地图返回源码体后 read 从 8.4 降到 ≤1.1。
**推广场景**：
- 搜索引擎：直接答案卡片 vs 链接列表的效率差异
- API 设计：返回完整对象 vs 返回 ID 再查一次
- 客服系统：一次给出完整解决方案 vs 多轮引导自助
- 编译器：中间结果缓存复用 vs 每次重算

### 灵感 4：廉价操作诱发过度使用（信号利用类）

**核心思想**：当某操作边际成本极低时，即使不必要也会被频繁执行，形成"便宜但累积昂贵"的浪费模式。
**论文证据**：Docs 的廉价查询诱发冗余精化，单实例 token 膨胀到 baseline 的 27.7×；map overhead 是简单任务超支主因（AST 30/41）。
**推广场景**：
- 云服务：按调计费的廉价 API 导致轮询滥用
- 社交媒体：无限下滑的"廉价"内容消费累积成时间黑洞
- 代码评审：轻量评论按钮导致碎片化讨论取代深度评审
- 缓存设计：TTL 过短的廉价缓存查询导致穿透

### 灵感 5：把"系统组件"提升为"实验变量"（方法论类）

**核心思想**：一个领域里长期与整体捆绑销售的组件，把它抽出来做成可插拔变量做受控比较，往往能回答此前无法归因的问题。
**论文证据**：此前表示与脚手架捆绑（AutoCodeRover/ARISE 等），本文用 MCP 服务器 + 固定 Agent 栈首次分离出表示的净效应。
**推广场景**：
- 模型评估：把 tokenizer、解码策略从"模型"中拆出做受控比较
- 营销归因：把渠道从整合营销中拆出做增量实验
- 药物研发：把辅剂成分从复方中拆出做单变量试验
- 教育评估：把教材、教学法、班级规模拆开测量各自效应

### 灵感 6：混合视图是安全的默认，但不是免费的午餐（机制类）

**核心思想**：合并多种信息源的"全息视图"能覆盖最多场景（鲁棒性），但在任一单一场景未必最优（峰值）。
**论文证据**：Hybrid 在 LinuxFLBench 零 loss、净 +17 最稳；但在 SecBench（34.3% vs 29.5%）和 SWT-bench token 上输给单一视图；verbatom-source explosion 是其特有超支模式（SWT-bench 94/94）。
**推广场景**：
- 模型选型：通用大模型 vs 微调小模型——鲁棒与峰值的权衡
- 投资组合：分散组合抗风险，单一重仓搏超额
- 产品策略：全功能平台 vs 单点爆款工具
- 检索系统：混合检索（向量+关键词）稳健但单一方法在某些 query 上更快更准
