## 一、论文背景

### 1.1 什么是 SWE-bench？为什么它成了编码智能体的"高考"

2023 年底，普林斯顿团队提出 SWE-bench：从 12 个知名 Python 项目的 GitHub 历史中，挑出"某个 issue（问题报告）后来被某个 PR（拉取请求，即代码修复提交）关闭"的真实案例，让 AI 智能体只读 issue 文本、在仓库里自己改代码，再用开发者写进 PR 的测试来判断改对没有。这套"issue 进、补丁出、测试判卷"的范式，比"给一道题写一段代码"的传统评测难得多——智能体必须理解整个代码库、定位故障、协调多文件修改。发布时最强模型只能解决 1.96% 的问题，而到 2026 年，榜单领先者已冲到 80% 以上，接近饱和。

随之而来的是一系列"续集"：OpenAI 联合原作者推出经人工核验 500 题的 **SWE-bench Verified**（93 名开发者逐题检查"issue 描述是否清晰、测试是否过严、任务是否可解"）；字节跳动 Seed 团队的 **Multi-SWE-bench** 把语言扩到 Java/Go/Rust/C++ 等七种；微软的 **SWE-bench-Live** 用自动化流水线持续收录 2024 年后的新 issue 对抗数据污染（固定基准的问题在于模型训练时可能已经"背过"答案——2026 年 OpenAI 审计发现所有前沿模型都能逐字复现部分 Verified 题目的标准补丁）；SWE-rebench 则把采集全流程自动化。但它们有一个共同盲区：**全部是通用软件仓库，没有一家针对机器人软件及其构建系统**。而机器人恰恰是软件工程里最难啃的骨头之一。

顺带预习两个后文反复出现的术语：**F2P（fail-to-pass）测试**指修复前失败、修复后通过的测试——它验证"bug 真的被修了"；**P2P（pass-to-pass）测试**指修复前后都应通过的测试——它验证"修复没有顺手弄坏别的东西"。一个补丁必须让全部 F2P 通过且不破坏任何 P2P 才算解决任务，这是 SWE-bench 谱系通行的判卷规则。

### 1.2 什么是 ROS 2？机器人软件难在哪

ROS（Robot Operating System，机器人操作系统）并不是真正的操作系统，而是"机器人界的 Linux 生态"——一套开源的、模块化的软件框架，把导航、控制、感知、驱动等能力做成可复用的包（package）。一台基于 ROS 2 的移动操作机器人，可能同时跑着几十个 C++ 和 Python 包，靠分布式中间件互相收发消息。几个关键概念：

| 概念 | 是什么 | 类比 |
|------|------|------|
| ROS 2 包 | 带 package.xml 清单的软件单元，声明依赖 | 乐高积木块 |
| colcon | 元构建工具，按依赖拓扑排序批量构建整个工作区 | 小区总包工头 |
| ament/CMake | 单个包内部怎么编译的规范（C++ 包用 ament_cmake） | 单栋楼的施工规范 |
| rosdep | 按包声明自动安装系统依赖 | 装修材料采购员 |

机器人软件的难点在于：**正确性跨越包和进程的边界**。一个补丁可能编译通过，却违反了 ROS 消息契约或节点生命周期约定，改变了 launch 启动行为，或者只在特定仿真器、特定时序、特定硬件配置下才失败。行为依赖时序、并发与硬件，从业者至今高度依赖现场测试。这意味着：复现一个机器人软件任务，远不止"检出代码跑单测"那么简单——评价必须保留领域工具链与执行环境，处理并发与非确定性，并把基础设施故障与错误修复区分开，否则测出来的分数反映的是环境失配，而不是智能体的修复能力。

### 1.3 缺口：两边的基准都答不了"智能体能维护机器人代码库吗"

一方面，SWE-bench 系不碰机器人；另一方面，机器人领域的现有评测考察的是"从零写新程序"（如 Code as Policies、RLE-Bench）、补全单个函数（ROSDevEval），或在一个导航栈上修少量精选缺陷（RoboBugBench 的 33 个任务）。没有基准能回答机器人团队最关心的问题：**我现有的代码库，智能体能维护哪些部分？** 这就是 Robo-SWE 的出发点。

## 二、论文定位和关联工作

### 2.1 研究谱系一：issue 解决与可复现缺陷数据集

| 工作 | 核心思想 | 与 Robo-SWE 的关键区别 |
|------|---------|----------------------|
| SWE-bench（ICLR 2024） | 定义 issue-to-patch 任务范式 | 仅 12 个 Python 仓库；Robo-SWE 扩展到机器人四域 |
| SWE-bench Verified（2024） | 93 名开发者人工核验 500 题 | Robo-SWE 的两评审员人工核验列为未来工作，目前自认"临时"分数 |
| Multi-SWE-bench（NeurIPS 2025） | 扩展到七种语言、68 名专家标注 | 语言扩了、领域没扩；无机器人构建系统 |
| SWE-bench-Live / SWE-rebench（NeurIPS 2025） | 自动化采集 + 持续更新抗污染 | Robo-SWE 借鉴了其自动化思路，但保留领域准入规则 |
| Defects4J / BugSwarm / GitBug-Java | 打包可复现缺陷供测试研究 | 面向 APR/测试，非智能体 issue 解决 |
| ROBUST（EMSE 2024） | 221 个 ROS 1 bug 的 Docker 复现 + 扎实理论分析 | ROS 1（非 ROS 2）、系统级 bug 缺测试 oracle、无 agent 横评 |

值得注意：ROBUST 论文自己发现，156 个运行时 bug 里只有 15 个附带能触发 bug 的测试——这正是 Robo-SWE 坚持"必须有开发者测试做 oracle"的原因（下文详述）。

### 2.2 研究谱系二：机器人编码评测

| 工作 | 评测对象 | 与 Robo-SWE 的区别 |
|------|---------|------------------|
| Code as Policies（ICRA 2023）/ CaP-X（ICML 2026） | 从零写控制/学习程序 | 不涉及既有代码库维护 |
| EmbodiedSWE / RLE-Bench（2026） | 长时程操作 / 机器人学习工程 | 写新代码而非修真实 issue |
| ROSDevEval（EMSE 2027） | ROS 代码函数生成 | 粒度是函数，非整库 issue |
| RoboBugBench（arXiv 2610.16369） | ROS 2 导航栈 33 个缺陷，仿真行为 oracle | 单一栈；Robo-SWE 覆盖 28 仓库、继承开发者测试 |
| HWE-Bench（2026） | 硬件描述代码的 F2P 任务 | 域是芯片不是机器人 |

**定位结论**：Robo-SWE 是第一个跨机器人软件四域（ROS 2 系统 / 仿真与物理引擎 / 机器人算法库 / 机器人学习框架）、以"挖掘的 issue + 隐藏开发者测试 + 可执行环境"三位一体为特征的可执行 issue 解决数据集，填掉了 SWE-bench 谱系与机器人评测之间的空白地带。

## 三、问题定义

论文要解决的核心问题可以抽象为：**如何在行为依赖时序、并发与硬件的领域里，构造"可执行、可复现、oracle 可信"的 issue 解决任务？**

形式化拆解：一个任务是一个五元组（issue 文本 I，基线提交的工作区 W，开发者修复 F，开发者测试 T，容器环境 E），需满足四条约束——

1. **可执行性**：在 E 中离线运行 T，无需网络；
2. **oracle 有效性（F2P）**：在 W 上跑 T 必须失败，在 W+F 上跑 T 必须通过——即 fail-to-pass 测试确实"卡"在这个 bug 上；
3. **无回归（P2P）**：F 加入后原本通过的测试不能挂；
4. **稳定性**：上述判定在重复运行中一致，flaky（不稳定）判决一票否决。

这个定义的精妙之处在于**用开发者自己的测试当 oracle**：开发者修 bug 时写的测试天然编码了"什么行为才算修好"，无需基准作者自己发明判卷标准。它的代价是"必须同时存在关闭的 issue、修复 PR 与测试"，把大量真实 bug 挡在门外——这是用可信度换覆盖面的设计取舍。

## 四、问题解法：挖掘流水线

整条流水线像一套层层筛选的"漏斗"，从 61,878 个候选仓库一路筛到 236 个任务。先看全景，再拆关键环节。

| 阶段 | ROS 2 | 仿真/物理 | 算法库 | 机器人学习 | 合计 |
|------|-------|----------|--------|-----------|------|
| 候选 PR | 640 | 709 | 140 | 78 | 1,567 |
| 进入构建队列 | 325 | 458 | 93 | 52 | 928 |
| 环境构建成功 | 291 | 104 | 50 | 44 | 489 |
| 执行准入通过 | 124 | 66 | 34 | 38 | 262 |
| 最终评测任务 | 103 | 63 | 32 | 38 | 236 |
| 有候选的仓库 | 39 | 11 | 11 | 2 | 63 |
| 有任务的仓库 | 17 | 4 | 5 | 2 | 28 |

### 4.1 仓库从哪来：一次 ROS 生态普查的"重跑"

ROS 2 域的仓库不是拍脑袋选的。作者重实现了 Malavolta 等人 2019 年 ROS 普查的挖掘方法（GitHub GraphQL API + rosdistro 索引 + 社区列表，2026 年 9 月采集），从 61,878 个候选仓库中筛出 2,114 个含 ROS 2 代码的仓库，再按"活跃 + 至少 100 个合并 PR"筛到 197 个，用 GPT-5 mini 分类出 171 个机器人系统，最后保留满足"至少 5 名人类作者且无人占比超 80%"的 80 个最大仓库作为挖掘框架。其余三域用人工筛选的 42 个仓库，按活跃度与开源协议筛到 25 个。

### 4.2 候选怎么定：任务定义与 LLM 筛选

一个合格的候选 PR 必须满足：合并、关闭了更早的 issue、同时改动了生产代码和测试、作者是人类、不是 backport（向后移植）。挖掘窗口为截至 2026 年 10 月的四年间，共 61,655 个合并 PR 产出 1,567 个候选。生产/测试代码靠内容区分而非文件名，并限制改动规模保证任务可审阅。

随后 LLM 筛选（ROS 2 用 GPT-5，其余用 GPT-5 mini）评估两件事：issue 是否足够清晰、开发者测试是否合理对应 issue 且不需要"只在修复里才有的 API"。注意分工：**LLM 只决定谁能进构建队列，能不能进数据集由执行说了算**——这避免了大模型筛选直接决定数据集质量。

### 4.3 环境怎么建：digest 固定的容器复现

每个候选任务在 PR 基线提交处构建容器，测试全程断网。ROS 2 镜像从 digest 固定的官方 ROS 镜像出发，用 rosdep 装依赖、colcon 构建受影响的包，发行版跟随 PR 目标分支。其余三域每仓库一份审阅过的固定配方。这套设计直面机器人软件"环境即评分一部分"的现实：不固定环境，测出来的分就是环境失配的噪声。

### 4.4 准入怎么判：三态 × 重复的执行式验证

这是全文最硬核的设计。每个候选在三个状态下跑测试，每态重复 2-3 次：

- **状态 A**：基线提交 + 自带测试（仅非 ROS 2 域）——确认基线本身是健康的；
- **状态 B**：基线提交 + PR 测试——F2P 测试必须**失败**（证明测试确实卡在 bug 上）；
- **状态 C**：状态 B + 开发者修复——F2P 测试必须**通过**，且任何 P2P 测试不得破坏。

任何不稳定判决直接否决：ROS 2 域丢弃 flaky 测试、没有稳定 F2P 就整题拒绝；其余域任何 flaky 拒绝整题。还有一条针对编译型语言的细则：**修复前编译不过的新测试不算"失败"**——因为新测试经常调用修复才引入的 API，这条规则一刀拒掉了 96 个 ROS 2 候选。任务从不被编辑以通过验证（"Tasks are never edited to pass"）。

### 4.5 发布前最后一关：Release 检查

262 个通过执行准入的任务导出为 Harbor 任务格式后再过一遍 harness 校验：开发者修复必须得 1 分、空补丁必须得 0 分。26 个任务因各具原因被撤下（issue 里泄露修复、F2P 无改动即通过、环境漂移等），另有 1 个因上游依赖退役被统一排除，最终 236 题。顺带发现一个工程细节：部分 ROS 2 测试套对宿主机负载敏感——12 核机器并发跑 14 个任务时，15 个 ROS 2 任务上连开发者自己的修复都会失败。这直接促成了"同时最多评 3 个 ROS 2 任务"的作业规范。

每个任务是一个 Harbor 目录：`instruction.md`（原 issue + 工作区路径与构建命令）、`environment/`（Dockerfile）、`solution/`（开发者修复，对智能体隐藏）、`tests/`（隐藏 oracle：F2P/P2P 测试标识符与评分脚本）、`task.toml`（时限/资源限制/网络模式/溯源信息）。一条命令即可评测：`harbor run -p <task> -a <agent> -m <model>`。

## 五、评估指标与实验证据

### 5.1 数据集本身的画像

- **规模与分布**：236 题、28 仓库、四域；ROS 2 域内导航与移动机器人 45 题、控制与驱动 26 题、中间件 22 题为主；
- **语言构成**：ROS 2 域 103 题中 80 题修 C++，其余三域全部纯 Python；
- **修复规模**：开发者修复中位数 30 行 / 2 文件，78 题不超过 15 行，24 题超过 150 行——补丁小但跨包约束重，正是机器人软件的典型形态；
- **新鲜度**：PR 合并时间从 2022 年 11 月到 2026 年 10 月，65% 是 2026 年合并的，且每题记录合并日期供用户按模型训练截止时间过滤——直接支持污染研究。

### 5.2 主指标：解决率（resolve rate）

主实验跑了两类配置：五个主力配置（Claude Opus 5.5 与 Claude Sonnet 5.5 跑 Claude Code 2.1.302，GPT-6.1 Sol 中/最高努力与 GPT-6 Astra 跑 Codex 0.163.0）每配置 3 次完整运行，外加 GLM-5.3（1 次）与 Kimi K3.1 Pro（2 次）跑 OpenCode，共 3,540 次评分尝试、3,529 条可用轨迹。每次尝试 1 小时预算、仅可访问模型 API，Claude 配置另设每尝试 20 美元成本上限。注意一个方法论细节：服务商容量中断的尝试被替换重跑而非记为零分（14 次被替换，含 4 次原始奖励为通过的中断），普通失败则保留原分——作者区分"基础设施故障"与"模型失败"的意识贯穿始终。

判卷规则即第三部分的形式化定义：全部 F2P 通过且无 P2P 破坏 = 解决。95% 区间用 2,000 次任务级 bootstrap 重采样计算。

**核心结果表（2026 年 11 月 10 日）**：

| 配置（运行次数） | 总解决率 | 95% 区间 | ROS 2 | 仿真 | 算法 | 学习 | Any | Every |
|-----------------|---------|---------|-------|------|------|------|-----|-------|
| Opus 5.5（3） | **56.5** | 50.7-62.4 | 48.5 | 59.8 | 69.8 | 61.4 | 60.2 | 51.7 |
| Sol max（3） | 54.1 | 47.9-60.3 | 50.8 | 55.6 | 64.6 | 51.8 | 57.2 | 50.0 |
| Sol medium（3） | 52.5 | 46.5-58.6 | 49.5 | 55.0 | 61.5 | 49.1 | 56.4 | 47.9 |
| Astra（3） | 51.4 | 45.1-57.9 | 46.3 | 56.1 | 59.4 | 50.9 | 54.2 | 47.9 |
| GLM-5.3（1） | 46.2 | 39.9-52.6 | 42.7 | 52.4 | 53.1 | 39.5 | – | – |
| Sonnet 5.5（3） | 45.8 | 39.8-51.7 | 39.8 | 55.6 | 49.0 | 43.0 | 51.3 | 39.4 |
| Kimi K3.1 Pro（2） | 43.9 | 37.5-50.0 | 39.3 | 54.0 | 46.9 | 36.8 | 47.0 | 40.7 |

Any/Every 列分别是"至少一次运行解出"和"每次运行都解出"的任务比例，均值成本 0.10-1.24 美元/次。

### 5.4 数据集存储与使用方式

复制包以四张表组织全部元数据（CSV + JSON Lines 导出）：

| 表 | 内容 |
|----|------|
| tasks | 每任务一记录：仓库、PR/issue 链接、基线与修复提交、合并日期、域与子类、构建系统、测试框架、补丁规模、F2P/P2P 标识符、许可、内容哈希、审计标记 |
| candidates | 全部 1,567 个候选 PR：各自到达的最后阶段与被拒原因 |
| admission | 状态 A-C 每次重复中每个测试的判定 |
| attempts | 每次 agent 尝试：配置、运行、结果、逐测试判定、token 用量、时长、补丁与轨迹路径 |

使用上一条命令即可评测：`harbor run -p <task> -a <agent> -m <model>`。因为开发者修复是公开的，智能体应离线运行（否则可能搜到答案）；因为负载敏感，ROS 2 任务建议 12 核主机上同时最多评 3 个。

### 5.3 指标说明了什么

三个层次的解读：

1. **头部差距真实存在但区间重叠**：Opus 5.5 比 Sonnet 5.5 高 10.7 个百分点，但论文明确提示这是"模型-harness 组合"的比较而非孤立模型比较，主力配置的置信区间互相重叠，不宜过度排名；
2. **稳定性差异是隐藏信号**：Opus 的 Any-Every 差距 8.5 个百分点，说明不少任务"时灵时不灵"——单次运行的分数会高估能力；
3. **15 次主力运行聚合后**：83 题每次都解出、81 题从未解出、72 题随配置或运行波动——**约三分之一任务处于"能力边界区"**，这批任务是未来研究 agent 行为最富信息量的样本。

## 六、效果优势的根源解释

本部分回答：为什么 Robo-SWE 能测出"通用基准测不出"的领域差距？它的分数为什么可信（又在哪些方面仍不可信）？

### 6.1 根源机制与证据链

**因果链一：领域工具链保留 → 环境失配噪声被消除 → 域间差异显形**

- SWE-bench 系假设"检出代码跑单测"即可复现任务；机器人软件的正确性跨包/跨进程（消息契约、launch 行为、仿真器与时序依赖），该假设不成立【论文论证，实验佐证】；
- Robo-SWE 用 digest 固定 ROS 镜像 + rosdep + colcon 按 PR 基线提交复现环境【论文设计】；
- 结果：C++ 为主的 ROS 2 域解决率（39.8%-50.8%）显著低于纯 Python 的仿真域（52.4%-59.8%），七个配置一致——若环境是噪声源，域间差异不可能如此整齐【论文实验已支持】。

**因果链二：三态重复执行准入 → 不稳定 oracle 被挡在数据集外 → 分数反映修复能力而非运气**

- flaky 测试会让"开发者修复得 1 分、空补丁得 0 分"的双检失效——重复运行中判决翻转的任务会让分数不可复现【机制推理】；
- 三态 × 2-3 次重复 + flaky 一票否决 + "修前不编译不算失败"细则（单条规则拒 96 个 ROS 2 候选），把 oracle 的时序稳定性前置到准入阶段【论文设计，有具体淘汰数字支撑】；
- 附加证据：发布后 Release 检查又抓出 26 个"执行通过但导出后翻车"的任务，说明即便严格准入仍需最后一道 harness 校验【论文实验已支持】。

**因果链三（诚实标注：仍属论文自认的未决项）：执行式验证 ≠ 公平性**

执行验证保证的是"可复现"，不保证"issue 与测试对齐"。论文自动审计标记了 26 个"测试用到 issue 里从未提到的标识符"的任务——一个正确回应了 issue 的补丁可能挂在这类测试上，因此论文自己把所有解决率标注为"临时的"（provisional），两评审员人工核验（对标 SWE-bench Verified 的 93 人核验协议）尚未开始。这是本工作罕见的自我克制，也是使用该基准分数时必须牢记的边界。

### 6.2 相关工作检索与对照

围绕"可执行 oracle 的可信度"这一根源问题，外部检索结果如下：

| 研究（可核验链接） | 相似尝试 | 相关结论 | 与本文的差异与适用边界 | 对根源解释的影响 |
|------|----------|---------|----------------------|------------------|
| ROBUST（EMSE 2024，[arxiv.org/abs/2404.03629](https://arxiv.org/abs/2404.03629)） | 221 个 ROS 1 bug 的 Docker 复现 | 156 个运行时 bug 仅 15 个附带可触发测试；失败常跨组件而修复局限于单文件少数行 | ROS 1、无 agent 评测；其"缺测试"发现反向支撑 Robo-SWE 坚持 oracle 准入的必要性 | 支持 |
| RoboBugBench（arXiv 2610.16369，[arxiv.org/abs/2610.16369](https://arxiv.org/abs/2610.16369)） | ROS 2 导航栈 33 缺陷，仿真行为 oracle | 继承测试型 oracle 会接受错误补丁；其审计发现 11/11 "假补丁"（压制故障信号而非修复）被规则接受；观测通道丢弃的信息无法靠更严判据找回 | 单栈深挖 vs Robo-SWE 多仓库广覆盖；互补关系（论文也如此定位） | 限定：说明 Robo-SWE 的开发者测试 oracle 同样可能接受错误补丁，解决率可能偏高 |
| SWE-bench Verified（OpenAI 2024，[openai.com/index/introducing-swe-bench-verified](https://openai.com/index/introducing-swe-bench-verified/)） | 93 名开发者人工核验 500 题 | 人工核验能剔除"测试过严/issue 欠约束"的问题任务 | 核验协议被 Robo-SWE 列为未来工作模板 | 支持：证明 Robo-SWE 自认的"临时性"是必要补课而非过度谦虚 |
| Multi-SWE-bench（NeurIPS 2025，[arxiv.org/abs/2504.02635](https://arxiv.org/abs/2504.02635)） | 七语言 issue 解决基准 | 语言覆盖扩展可行且有价值 | 未覆盖机器人构建系统；与 Robo-SWE 是"语言轴 vs 领域轴"的正交互补 | 补充：说明 Robo-SWE 填的是领域轴空白 |
| SWE-bench-Live（NeurIPS 2025，[arxiv.org/abs/2505.23419](https://arxiv.org/abs/2505.23419)） | 自动化采集 + 持续更新 | 人工策展不可扩展，自动化流水线是方向 | Robo-SWE 的流水线已是自动化 + 记录式（账本），但尚非持续更新 | 支持 |

交叉验证的关键外部证据是 RoboBugBench：它从完全不同的路线（构造仿真行为 oracle + 对抗审计）得出与 Robo-SWE 自陈局限一致的结论——**测试型 oracle 的强度是这类基准的共同软肋**。两条独立研究线在同一问题上相遇，这是"分数应视为上界/下界而非真值"这一判断获得的多源支持。

### 6.3 综合判断与未决问题

- **多源共同支持**：领域工具链必须进评测环境（SWE-bench 谱系自身演进与 Robo-SWE 域间差异数据共同支持）；执行式准入 + 双检（修复=1、空补丁=0）是可复现性的必要条件（Harbor/Terminal-Bench 2.0 的 oracle/nop 双 agent 校验采用同一设计）；
- **仍属合理猜测**：ROS 2 域更难究竟归因于 C++ 编译链、跨包契约还是任务本身性质，论文未做分解（三变量混杂，本次检索范围内未发现后续消融工作）；
- **失效条件**：若模型训练数据已含相关 PR（污染），或 LLM 筛选系统性偏好某类任务，域间比较可能失真；78 题来自单一机器人学习仓库（mjlab）、五仓库占 56% 任务的集中度也意味着域级结论反映的是少数项目。

## 七、必要知识反推

假设让一个零背景的人重做这项工作，最少需要哪些知识？

**领域知识层**：机器人软件栈的运作机制——ROS 2 的包/消息/生命周期概念、colcon-ament-CMake 构建链、rosdep 依赖体系、仿真器与物理引擎在开发中的角色。不理解"正确性跨包跨进程"，就无法设计出保留工具链的环境方案，甚至会误以为 Docker 装个 Python 就够了。也需要知道领域内的代表项目长什么样（Navigation2 是导航栈、ros2_control 是控制器框架、MuJoCo Warp 是 GPU 物理引擎、LeRobot 是机器人学习框架），才能设计出覆盖四域的仓库清单。

**方法论知识层**：SWE-bench 范式及其谱系（Verified/Multi/Live/rebench 各自解决什么、留下什么）、F2P/P2P 测试语义与 flaky 判决的危害、挖掘软件仓库（MSR）的实证方法——包括 Malavolta ROS 普查的阈值设计。不知道"修前必挂、修后必过、P2P 不破坏"这套 oracle 语义，准入规则就无从谈起。

**工程知识层**：容器化与依赖固定（digest 固定、离线运行）、GitHub GraphQL API 大规模挖掘、LLM 筛选流水线的 prompt 设计与确定性门控、Harbor 任务格式与 harness 校验（oracle=1 / nop=0）、以及一个容易被忽视的点——**宿主机负载对测试稳定性的影响**（12 核并发 14 任务时开发者修复都会翻车），这需要真实的运维敏感度才能发现并转化为作业规范。

**知识融合的关键节点**：最有创造性的融合在"准入规则"处——把 MSR 的实证挖掘方法（仓库普查）、软件测试的 oracle 理论（F2P/P2P/flaky）与机器人领域的特殊性（colcon 构建、编译期依赖新 API 的测试）三者拧在一起，才诞生了"修前不编译不算失败"这类只有同时懂三边的人才写得出的细则。另一个融合节点是"来源账本"：把数据集构建从"只发布成品"升级为"发布全部 1,567 个候选的每一步记录"，这是把 MSR 的可审计传统带进基准发布。

## 八、论文中可以提取的通用性灵感

**灵感一：oracle 有效性靠"三态双向验证"保证，而非靠 oracle 本身高级**
- 核心思想：一个判卷标准是否可信，不取决于它多复杂，而取决于它是否在"有修复"和"无修复"两种状态下给出方向相反的稳定判定。
- 论文证据：状态 B（修前 F2P 必挂）× 状态 C（修后 F2P 必过）× 重复运行，配合 release 期"修复=1、空补丁=0"双检，淘汰了 96+26+1 个不合格候选。
- 推广场景：① 教育 automated grading（判分脚本需先在满分/零分卷上校准）；② RAG 系统的评估集构建（问题须在"有检索结果"与"无检索结果"下区分模型表现）；③ 安全审计的 PoC 验证（exploit 在补丁前后必须一成一败）；④ 任何"用执行判卷"的 agent 基准。

**灵感二：发布"账本"而不只发布"成品"，让数据集的取舍可审计**
- 核心思想：数据集的每一个入选与落选决定都应可追溯，这比事后声明"我们做了严格筛选"更有科学价值。
- 论文证据：1,567 个候选 PR 每个都记录了到达的阶段与被拒原因，连同 3,540 次尝试的逐测试判定全部公开。
- 推广场景：① 人工标注数据集（公开标注分歧与仲裁记录）；② 基准评测报告（公开全部尝试而非只报最好成绩）；③ 政策/评审类决策（公布完整候选池与淘汰理由）；④ 模型训练数据配比研究。

**灵感三：评测环境的"负载敏感"是隐形混杂变量，须显式管理**
- 核心思想：并发执行会改变被测对象的行为，评测协议必须为环境敏感性让步（限制并发），而不是让分数默默吸收噪声。
- 论文证据：12 核并发 14 任务时 15 个 ROS 2 任务上开发者修复失败，静息主机上 11 个恢复通过——不控制并发，"标准答案"都会被判错。
- 推广场景：① CI 流水线的 flaky 测试治理（限流/隔离）；② 大模型推理评测（吞吐压力下的延迟测量）；③ 性能基准测试（内核版本、温度、邻居负载）；④ 任何涉及时序敏感系统的实验设计。

**灵感四：用"合并日期元数据"把污染控制权交给下游用户**
- 核心思想：基准无法预知所有模型的训练截止时间，但可以把每题的时间戳带上，让用户自行切分"训练前/训练后"子集。
- 论文证据：每任务记录 PR 合并日期（2022-2026，65% 在 2026 年），明确建议用户据此排除早于模型训练截止的任务。
- 推广场景：① 持续学习基准的时间切分评估；② 竞赛出题的防作弊分层；③ 任何静态评测集对抗训练数据泄漏的通用做法。

以真实任务 `ros2__rosbag2-1812` 为例（rosbag2 是 ROS 2 的数据记录工具，PR #1812 修复"`ros2 bag convert` 忽略未知消息类型的文件"）：

```
ros2__rosbag2-1812/
├── instruction.md     # 原 issue 全文（234 词）+ 工作区路径 + 构建命令
├── environment/       # Dockerfile：digest 固定 ROS 2 镜像 + rosdep + colcon
├── solution/          # 开发者修复（2 文件 11 行：给 get_package_share_directory
│                      #   加 try-catch，找不到包时抛 DefinitionNotFoundError）
└── tests/             # 隐藏 oracle：1 个 F2P + 7 个 P2P 测试 + 评分脚本
                       #   F2P: throw_definition_not_found_for_unknown_msg
```

智能体只看到 `instruction.md` 与构建好的工作区；`solution/` 与 `tests/` 在评分时才注入。解题 = 让全部 F2P 通过且无 P2P 破坏。这个小任务也展示了机器人软件修复的典型形态：改动极小（11 行），但要理解 ament 包索引的异常语义——"编译通过"与"行为正确"之间的鸿沟，正是这个基准存在的意义。
