## 一、论文背景

先讲清楚两个前置概念，这篇论文的动机才立得住。

**KV-cache 是什么**：LLM 处理 prompt（这一步叫 prefill，预填充）时，注意力层会为每个 token 算出 key/value 状态存起来，后续生成时反复读取。当后来的 prompt 与之前的 prompt 开头一段完全相同时（**共享前缀**，shared prefix），这段的 KV 可以直接复用，跳过重算——这就是前缀缓存。prefill 是 Agent 场景的大头：一个 agent 任务动辄几十次 LLM 调用，每次都带着累积增长的上下文。

**问题的来源**：Agent 应用通过一连串相互依赖的 LLM 调用解题——指令、输入文档、中间结果在调用间反复出现。但"内容重复"不自动等于"缓存命中"：前缀匹配要求 token 从第一个开始严格一致，一旦共享值前面出现一个不同的 token，它的 KV 就再也匹配不上了。GPU 显存又有限，为一个调用保留缓存可能挤掉另一个调用需要的缓存——KV-cache 抖动下，单请求 prefill 时间可涨 6.8 倍、生成吞吐最多掉 66%（论文引用的 agentic 负载特征研究）。

打个比方：前缀缓存像图书馆的复印服务——只有当你的文件**从第一页起**与之前复印过的某份文件完全相同，才能直接拿现成复印件；哪怕中间一页插了张新纸，后面全部重印。Agent 的 prompt 恰恰爱在中间插纸。

现有系统怎么应对？SGLang 的 RadixAttention 复用最长匹配前缀并优先调度长匹配请求；KVFlow/Helium/PBKV/CacheScout 等 workflow-aware 系统用工作流结构或观测到的执行模式预测下次调用、指导缓存管理。但它们有一个共同的盲区：**把 prompt 划分为"可复用前缀 + 不透明后缀"，在后缀这个粒度上不再区分内部组件**。KVFlow 的做法很典型：按预测的执行顺序优先保留固定前缀，把变化的后缀整体赋予最高驱逐优先级——它看不见后缀里"持久共享值"与"一次性临时内容"的区别。

论文的观察是：**动态后缀有内部结构**。会话级输入（一整个 session 不变的 claim）、累积历史（只增不改的 evidences）、临时结果（每次迭代被替换的 query）可能同处一个 prompt，但复用潜力天差地别——这个性质被命名为 **intra-prompt heterogeneity（prompt 内异质性）**。作者实测：四个评测 agent 中 **51–92% 的共享 token 因前面出现不同 token 而错过前缀缓存**；**约 20% 的服务 prompt token 在一个会话内只用一次**却占着内存。两个数字合起来画出了一幅完整的浪费图景：一边是大头共享被布局挡在缓存门外，另一边是小头垃圾被无差别供养在缓存里。

再看一个贯穿全文的例子（事实核查 agent）：输入 claim → A 生成检索 query → B 搜索证据 → C 结合已收集证据评估 → 循环 B/C 直到 D 出结论。claim 流向全部四个调用点且全程不变；evidences 被 C 和 D 共享、只增不改；query 和单次搜索结果每次迭代都被换掉。原始 prompt 布局里，每个调用点的专属指令排在共享上下文前面——四条 prompt 各自的"Decompose/Search/Assess/Verdict 指令"互不相同，导致前缀在跨调用点处全部断掉，claim 明明四个站点都在用，缓存却认不出来。

用一句话预览解法：把 claim 挪到 system prompt 之后、四站共享的 "system+claim" 前缀就成立了；把 evidences 排在临时值前面、它 append-only 的旧前缀天然可复用；把每个站点的指令沉底、不再切断公共头部——这三步"搬家"不需要改任何引擎代码，radix 树自己就会命中。而"哪些值该搬去哪、搬家后谁还活着"，由编译器分析代劳。

## 二、论文定位和关联工作

论文定位在 LLM serving 系统，核心标签是**编译器-serving 协同设计**（compiler-serving co-design）。它站在四条研究线的交汇处，但与每条都有本质区别：

| 相关线 | 代表工作 | 与 MORTIS 的关系 |
|---|---|---|
| 前缀缓存与分层 KV | SGLang RadixAttention/HiCache、vLLM PagedAttention、CachedAttention、Mooncake | 提供 radix 树/主机分层等基础设施，但只按"前缀+后缀"粒度管理；MORTIS 建在其上（SGLang fork）并下沉到组件粒度 |
| workflow-aware 缓存管理 | KVFlow、Helium、Learned Prefix Caching、PBKV、CacheScout、KVTether、Pythia | 用 Agent 步数图/在线学习/生命周期信号预测调用，操作对象仍是"已识别的前缀"；MORTIS 证明（同布局对照实验）这些策略无法利用 prompt 内异质性 |
| 应用信息供服务端优化 | Parrot（语义变量）、Teola（细粒度算子） | Parrot 用语义变量暴露请求间 DAG 做调度与共享放置，是"程序信息进 serving"的先驱；但它不做组件级生命周期分析，也不改 prompt 布局 |
| prompt 构造优化 | DSPy adapter、NOOA 标签、SGLang 前端常量前移、Liu et al. 关系分析排序、Prompt Cache、CacheBlend | DSPy/NOOA 靠约定或人工标签定组件顺序——标签"复述了程序里已有的性质"，代码一改就过期；Prompt Cache/CacheBlend 允许非前缀复用（预计算模块/选择性重算跨注意力），MORTIS 则选择"重排使前缀匹配成立"，复用引擎现有机制 |


一个精妙的立足点：在 byLLM/DSPy/NOOA 这类**类型化 LLM 函数调用框架**中，prompt 组件天然对应程序变量——框架 lowering 时总是产出五类组件（框架脚手架、任务指令、参数描述、参数值、输出 schema），只是顺序不同（论文 Figure 3 对比了三个框架的同一次调用）。**变量怎么共享、何时被覆盖，本来就在程序里写着**——这正是编译器分析能插手的地方。与 NOOA 的人工标签对比尤其点题：手动标注复述了程序已有性质且易过期，分析程序本身则精确且免维护。

值得一提的还有"跨工具间隙调度"这条线（InterCept/Continuum/TokenCake）：它们瞄准 ReAct agent 在工具调用空档的 KV 换入换出决策，与 MORTIS 的调度目标相通，但信息来源是运行时间隙统计而非程序结构——可以看作同一问题在"无类型化框架"前提下的替代解。

总结定位：MORTIS 的新颖性不在单个组件（reaching definitions 是 1970 年代的技术、Witten-Bell 是 1991 年的、Tarjan SCC 是教科书内容），而在**"prompt 组件 ↔ 程序变量"这个对应关系 + 用它把两套机制串成闭环**——识别 intra-prompt heterogeneity 这一新概念并用 51–92% 错失率的动机数据支撑，是典型的系统类顶会（OSDI/SOSP/EuroSys/MLSys）口味。

## 三、问题定义

先明确"损失"的两种形态，问题才算定义完整：

- **共享错失（missed sharing）**：值被多个调用点使用，但因为在 prompt 里排在调用点专属内容之后，前缀匹配在差异 token 处断掉，KV 无法复用——51–92% 的共享 token 栽在这里。
- **保留失准（imprecise retention）**：系统只见到"匹配上的前缀"和"其余部分"，无法按各组件的真实复用前景分别管理——单次使用的临时内容与会话级共享值享受同等的 LRU 待遇，约 20% 只用一次的 token 白占内存，还可能在争用中挤掉真正会被再用的缓存。

两种损失分别对应两个正交的优化方向：前者要**改表示**（把共享搬进前缀的位置），后者要**改策略**（按未来有用性分配内存）。MORTIS 的贡献正在于同时做这两件事、且都建立在同一份编译期信息之上。

形式化地说，agent serving 系统的 KV-cache 管理要同时回答两个问题：

1. **怎么排**：prompt 内组件以什么顺序布局，决定了哪些内容能形成引擎可命中的物理前缀。给定各调用点的组件集合与组件间的值传递关系，求每个调用点的布局，使跨调用点的可复用前缀总量最大。
2. **怎么留**：显存有限，哪些缓存条目值得保留、哪些应该立刻释放、哪些要提前取回。每个缓存条目的"未来有用性"取决于其对应值的生命周期（何时被覆盖而变死）与下次使用的时机。

三个难点让这两个问题不能单靠静态分析解决：

- **程序结构不决定实际复用**：静态分析揭示可能的共享/更新/未来消费者，但执行路径、组件大小、调用间隔都在运行时才确定（循环跑几圈、哪条分支被走）。
- **暴露前缀需要跨调用点协调**：各调用点独立排序组件，可能把同一个值放在不同的前置上下文后面，缓存照样无法共享——A 站把 claim 放在位置 2、B 站放在位置 3，前缀各断各的。
- **潜在复用要与当前内存压力权衡**：为未来调用保留/预取前缀消耗着其他请求能用的内存，过早驱逐又迫使重算。

一个通俗类比可以串起整个问题空间：把 KV-cache 想成一间储物间，每个 prompt 组件是一件行李。现有系统只认"进门时排在最前面的那串行李"（前缀），其余的统统当作"不明物品"堆在一起按"最近摸过"的规则清退（LRU）。MORTIS 做的事相当于给每件行李贴上三种标签——"几个人共用"（共享模式）、"什么时候过期"（生命周期）、"下次谁会来取"（下次调用预测）——然后按标签决定谁放门口（前缀位置）、谁先扔（驱逐）、要不要提前从仓库搬回来（预取）。

论文没有给出单一的形式化目标函数，而是把解拆成"编译期产物（Agent Descriptor）+ 运行时细化 + 两个优化机制"的工程体系——这是系统类论文的常规做法，评估以 JCT/吞吐/命中率来闭环。

## 四、问题解法

MORTIS = **编译器产出 Agent Descriptor** + **服务端两大机制**（自适应 prompt 重排 + 主动 KV-cache 调度）。架构：编译器把分析结果交给 Mortis Server，Server 结合运行时观测做重排与调度，底层还是 SGLang 引擎的 device/host 两级 KV 池。先给一张组件分工表：

| 部件 | 时机 | 输出 | 解决什么 |
|---|---|---|---|
| Call-site Template | 编译期 | Ic/Bc/Hc（演化五分类+生命周期） | 每个组件"是什么性质" |
| Workflow Automaton | 编译期骨架+运行时填充 | 转移概率/终止概率/间隔分布 | "接下来谁会被调、隔多久" |
| Adaptive Re-layout | 编译期决策+运行时观测长度 | 每调用点布局 | 共享错失 |
| Proactive Scheduling | 运行时 | 四档带驱逐/PLANNED 保留/预取 | 保留失准 |

### 4.1 Agent Descriptor：编译期产物

**(1) Call-site Template Tc=⟨Ic, Bc, Hc⟩**——每个 LLM 调用点一份：

- **Ic（不变规格）**：编译期就固定的 prompt 部分（system prompt、schema、指令）。获取方法很实在：编译器**用符号占位符提前跑一遍框架的 lowering pass**，产出运行时 prompt 的静态骨架 + 每个参数一个带标签的占位符——这一步本质是"符号化执行"，用抽象值代替真实输入走完渲染流程。
- **Bc（动态绑定）**：运行时才确定的参数值，即那些占位符被填充后的产物。
- **Hc（异质性标注）**：每个绑定两维信息——演化类 E（值怎么变）和生命周期 S（何时死）。

**演化五分类**（按可复用性降序）是论文最核心的分析产物，靠 **reaching definitions 数据流分析**获得。这个经典编译器概念值得从"是什么"讲起：程序里一个变量会被多次赋值（每个赋值点叫一个"定义"），编译器想知道的是——在程序的某个点上，**当前生效的是哪次赋值**。"到达定值分析"沿控制流图传播：一个定义从赋值点出发，沿所有可能路径向前流动，直到被同变量的新定义"杀死"（遮蔽）。含循环的程序有环，分析要沿回边迭代到不动点。MORTIS 对每个动态绑定的底层变量做这个分析（含回边、局部定义遮蔽更早定义），然后按每条到达定义的右侧形态分类：

| 类别 | 值关系 | 事实核查例子 | 缓存含义 |
|---|---|---|---|
| CONST | 代码里的字面量/模块级常量 | — | 所有会话共享，稳稳放前缀 |
| COPY | 未修改地传自另一个调用点 | claim 传给 A/B/C/D | 跨调用点共享，最值得暴露 |
| RESP | 来自另一个调用点的返回值 | query←decompose_claim(claim) | 单向流，下次调用值会变 |
| EXTEND | append-only，旧值是新值的前缀 | evidences←evidences+Δ | 旧前缀可复用，只需增量 prefill |
| VOLATILE | 每次新产生或分析边界外 | 外部输入兜底；冲突路径保守降级 | 用完即弃，驱逐第一优先 |

保守性处理很讲究：不同 CFG 路径给出冲突类别时降级为 VOLATILE（宁可不优化，不可错优化——把 EXTEND 误判会让缓存拼出错误前缀），但编译器在每条转移边 (q,q′) 上附加"这条边上变量怎么变"的元数据——运行时一旦知道实际走了哪条边，就能把 VOLATILE 精确还原（比如该边赋的是字面量，就是 CONST）。

这五类的排序还有一层深层含义：**它们正好构成"缓存价值梯度"**。CONST/COPY 是跨调用点甚至跨会话共享的（最值得放进公共前缀）；EXTEND 的价值在"旧前缀免重算"（增量 prefill）；RESP 的值下次调用就换（不值得保留但排列上仍可稳定）；VOLATILE 是纯噪声（用完即弃）。布局算法与调度算法的所有排序键，本质上都是这个梯度的不同投影。

**生命周期 S(b)**：记录覆盖（overwrite）该变量的过程/循环体集合。执行一旦进入 S(b) 中的过程，旧值的缓存字节即"变死"（dead）——这个概念直接对应编译器里的活性分析（liveness）：一个值从最后一次使用起就死了，死值的缓存无需保留。变量只赋一次全程有效则 S=∅（claim 全会话有效就是这种情况）。

**(2) Workflow Automaton A=(Q,P,q0,F,Dgap)**——程序级的带时间标注概率有限状态自动机：状态集 Q 每个状态对应一个 LLM 调用点；q0 是入口调用点；P 是状态间转移概率；F 是各状态的终止概率；Dgap(q,q′) 是"调用 q 完成到 q′ 发起"的间隔分布。构造方法：编译器从 typed AST 识别 LLM 调用点、构建**过程间 CFG 再投影**（非 LLM 调用收缩掉，只留 LLM 调用点之间的可达关系；调用目标静态不可解析时保守地连到所有候选目标）；**Bourdoncle 弱拓扑排序**（1993 年为程序验证的高效混沌迭代提出的技术）从投影图的环结构里恢复循环嵌套——因为投影后循环的显式语法结构已经丢了，只剩图上的环。P/F/Dgap 留空，由运行时观测填充。

一个自动机怎么"用文字想象"：事实核查 agent 投影后是 A→B→C 的小环（B/C 循环若干圈）加 C→D 的出口，运行时每次转移被计数后，A→B 边的概率趋于 1、C→B 与 C→D 的概率随任务统计收敛，B→C 间隔分布则刻画了"搜索工具耗时+代码间隙"的真实节奏。

为什么用自动机而不直接用 CFG：CFG 是"可能的结构"，自动机是带概率与时间的"结构+统计"——调度需要的是后者（下一步最可能是谁、还有多久来），而结构部分恰好又能从 CFG 投影免费得到。编译器给骨架、运行时给血肉，这句话在 MORTIS 里到处成立。

### 4.2 自适应 Prompt 重排

**可动的东西**：动态绑定 Bc 可任意排列——框架只是按参数声明顺序放置，重排完全合法（每个参数被 lowering 成参数名标记的自包含块，顺序信息不参与语义）；Ic 中的指令规格可前可后（system prompt 恒在最前，schema 交给受限解码引擎）。

**为什么需要"协调"而不是各排各的**：假设 A 站把 claim 排在 query 后、B 站把 claim 排在 search_result 后，即使两站都带了 claim，它前面的上下文不同，前缀照样断——所以布局必须在调用点之间联合决策，这正是 Algorithm 1 以转移边为单位收集分组信息的原因。

**布局决策算法**（论文 Algorithm 1）按三步走：

1. **共享绑定排优先图**：对每条转移边 (q,q′) 把共享绑定（被多个调用点携带的绑定）分三组——unchanged（两站都带且值不变）> append（两站都带且只追加）> rewritten/one-sided（被改写或只有一站带）——组建优先图（低组别指向高组别的边），**Tarjan 强连通分量（SCC）缩凝成 DAG 后拓扑排序**（SCC 内部则按键排序，因为环上不存在全序）。SCC 以 (−length, depth) 为键（token 越长的共享值越靠前，length 由服务器运行时观测——这是"静态分析+运行时血肉"模式的又一处体现；depth 是从入口到首个携带该值的调用点的转移数）。
2. **私有绑定排序**：按 (scoped, ρ, depth, −length) 字典序升序——生命周期长（S=∅ 记 0）在前、稳定性等级高（CONST=1…VOLATILE=5）在前。
3. **指令规格后置**：含共享绑定的调用点把指令规格放 prompt 末尾（开关可保留在前）。这是关键一招：不同调用点的指令各不相同，放在前面就把公共前缀切断了；放后面，"system prompt + claim"就成为四站共享的物理前缀。

效果对照论文 Figure 1→Figure 2：重排后四条 prompt 都以 "system prompt + claim" 开头，evidences 紧随其后（其 append 性质使旧 token 前缀天然可复用），指令沉底。**重排本身不改任何内容，只动顺序**，引擎现有的 radix 前缀缓存机制自动就能命中——不需要改内核。与 Static-Adapter 的区别在此显形：固定布局只会"不变组件一律前移"，没有转移边上的共享性分析，也学不会"该后置的指令要后置"这种非单调策略。

用搬家类比串起来：unchanged 的值是"全家都在用的锅"（放厨房最顺手的位置=前缀最前），append 的值是"只往外添东西的储藏柜"（旧东西不动，新东西放后面，旧前缀照样匹配），rewritten/one-sided 的是"各人自己的私物"（放后面，谁也别挡公共通道），指令规格是"每家不同的门牌"（干脆贴门上=prompt 末尾，不占公共走廊）。

### 4.3 主动 KV-cache 调度

**可复用头部与易变尾部**：重排后的 prompt 自然分成 reusable head（静态前缀 Ic+CONST + 会话共享扩展 COPY/EXTEND）与 volatile tail（VOLATILE 绑定）。这个切分是调度一切动作的分界线：头部是候选的保留/预取对象，尾部是驱逐的第一目标。

**下次调用预测**（三个子问题：来不来 / 何时来 / 来的时候前缀长什么样）：

- **到达概率**：每个调用点用包裹它的循环链标记上下文 ζ=(i₁,…,iₘ)（各层循环当前迭代号——"外层第 2 圈、内层第 5 次"这样的元组），维护频率表 P(q′|q,ζ)/F(q,ζ)。为什么需要循环上下文：同一个调用点在"循环第 1 次"和"第 8 次"之后走向不同分布的情况很常见（比如评估调用在前面几轮大概率继续搜索、接近收敛时大概率收尾出结论），裸转移概率把这些平均掉了。
- **估计方法用 Witten-Bell 插值**从空上下文逐级平滑到全上下文——这是 1991 年为自适应文本压缩的零频率问题提出的经典解法：权重 λₖ=nₖ/(nₖ+dₖ) 随观察数增长，常见上下文主导预测，罕见上下文退让给更短的上下文；无观察的上下文直接跳过。每次观测同时计入所有后缀子上下文行（(i₁,…,iₘ) 的观测同时记进 (iₘ)、(iₘ₋₁,iₘ) 等行），数据稀疏时也能用。选它而非训练模型，与整体设计哲学一致：**轻量统计+程序结构先验，好过黑盒学习**——agent 会话往往只有几十次转移，深度模型根本喂不饱。
- **到达时间**：按转移边记录的间隔样本，取 ĝ = max{t₅₀ − ½(t₉₀−t₅₀), 0}——中位数再按分布离散度收紧（t₉₀−t₅₀ 越大说明该转移的间隔越不可预测，估计越往早收，避免错过预取窗口）。
- **前缀重构**：利用 Hc 的值关系，用当前会话已观测的参数值按 q′ 的布局拼出其 prompt 前缀，**停在第一个未知值处**——预测的前缀是"确定会出现的部分"，不含臆测内容。

**四档生命周期带驱逐**（从先驱逐到最后驱逐）：

| 带 | 内容 | 处置 | 直觉 |
|---|---|---|---|
| RETIRED | 已完成会话的易变尾部 | 最先清；host 层也优先清它 | "人已退房，行李直接扔" |
| TRANSIENT | 活跃会话的易变尾部 | 次之；**不许进入 host 层**（反正不会复用，搬下去纯浪费带宽） | "本晚就走的过客，别腾柜子" |
| UNCLASSIFIED | 分析无法归类 | 保持引擎默认（recency） | "不知道，按老规矩" |
| PLANNED | 被预测调用将复用的前缀 | 最后驱逐 | "明天还要来的常客，留座" |

带的流转绑定会话生命周期（三个赋带时机）：prompt 入缓存时按 reusable head 切分、尾部与生成的回复记 TRANSIENT；后续调用改写了某绑定，对应头部截到幸存前缀、之后的字节降级 TRANSIENT（"截断降级"——EXTEND 类值被改写成 VOLATILE 时其旧前缀仍旧幸存，这正是重排把可复用值放前面的又一红利）；会话结束，全部易变尾部落 RETIRED，头部留 UNCLASSIFIED 靠 recency 老化（同程序其他会话可能还共享它）。radix 树驱逐堆以 band 为主键、recency 为次键。

一个容易忽略的细节：TRANSIENT **不许进入 host 层**——分层缓存的常规逻辑是"设备放不下的往 host 搬"，但 MORTIS 知道这些字节永远不会再被用，搬下去只浪费 PCIe 带宽和 host 内存。这是"语义信息改变分层策略"的小而美的例子。

**保留与预取**：把预测总结为三元组 (πq′, P(q′|q,ζ), treply+ĝ)，按收益密度排序准入：

```
D(q′) = P(q′|q,ζ) · |πq′|cached / max(treply + ĝ − tnow, τmin)
```

直觉：概率越高、已缓存 token 越多、越早到来，越值得留——分子是"期望省下的 prefill 量"，分母是"还要等多久"，比值即单位时间收益；τmin=0.5s 防止即将到来的调用获得无界 D 挤掉别人。PLANNED 准入到固定比例（0.6）设备容量为止；radix 树节点累积所有覆盖它的预测的 D，共享头部天然排在私有头部前（一个节点被多条预测覆盖，其 D 累加——结构化的"多数票"）。预取处理已被降到 host 的部分：释放截止 trelease = treply+ĝ − host 拷贝时间 − 未缓存部分 prefill 时间，截止最早者优先，只用空闲设备内存（先回收 RETIRED/TRANSIENT），空间不足则暂停但持续刷新这些条目的 recency 防止老化。

预测本身有丢弃机制：每次调用刷新预测，预测的调用真的到来或其预计到达时刻已过即丢弃——预测是短命的滚动窗口，不是长期积累的模型，这与 CacheScout 的在线学习模型形成轻量化对照。

## 五、评估指标与实验证据


**设置**：单块 A40 GPU，Qwen3-32B-AWQ，SGLang v0.5.10.post1 之上实现，15GB GPU + 25GB CPU KV 池，retention fraction 0.6，τmin=0.5s。四个 agent 负载（Jac byLLM 移植）：HoVer 事实核查、HumanEval 编码、BFCL 工具调用、FinanceBench 金融分析；另加四类混合负载。五个基线在同一 fork 上重实现：SGLang（RadixAttention+HiCache+LRU）、CacheScout、Continuum、KVFlow、Static-Adapter（模仿 DSPy adapter 的固定布局）。指标为平均 JCT（job completion time，任务完成时间）与吞吐（每分钟服务的 prompt token 数）——注意吞吐按 token 计而非请求数，这更公平地反映 prefill 节省。所有基线在同一代码基上重实现而非引用原论文数字，避免了实现差异带来的口径问题。

**主要数值**：

| 实验 | 结果 |
|---|---|
| 四负载 vs SGLang | JCT 加速 1.08–**1.99×**（几何均值 **1.45×**）；吞吐提升 1.04–**1.97×**（几何均值 **1.49×**） |
| 混合负载（3 lanes/agent） | 吞吐最高 **1.86×**、JCT 最高 **1.83×**；六档 lanes 几何均值吞吐 **1.56×**、JCT **1.53×** |
| TP=4（4×A40，prefill 1292→2252 tokens/s） | 几何均值吞吐 **1.60×**、JCT **1.58×**（最高 1.92×/1.87×）——缓存 miss 变便宜后优势仍在 |
| RTX 3090 + Qwen3-14B-AWQ（5.2GB GPU/10GB CPU） | 保持同样改善模式（小显存小模型也成立） |
| 2×2 消融（几何均值） | 仅 re-layout：JCT/吞吐 1.03×/1.02×；仅 scheduling：1.30×/1.36×；全开：1.45×/1.49×——**超可加** |
| 预取消融 | 关闭预取吞吐最多降 2.6%（该测试台上收益主要来自保留） |
| 缓存命中率（Figure 7） | Fact-check 上 MORTIS 从最低并发就高于 Relayout-only（其循环重入使 TRANSIENT 尾部很快失效）；Coding 上 MORTIS 命中率随并发几乎不降；Continuum/CacheScout 各并发下贴着 SGLang；KVFlow 在四负载上 vs SGLang 无显著改善（它操作的前缀太短） |
| 同布局对照（基线喂 MORTIS 布局） | 基线最多再获 1.11× JCT（CacheScout on Coding、KVFlow on Fact-check），MORTIS 仍全面胜出 |
| 任务质量（Table 2） | MORTIS 布局下 Fact-check 21.9%（原始 byLLM 16.3%）、Coding 54.8%（55.3%）、Financial 37.2%（34.9%）、BFCL 18.7%（14.1%）；三种布局的 LLM 调用次数差 ≤3%、输出 token 差 ≤6%——加速不是靠少干活 |

几个值得单独指出的实验设计：**同布局对照实验**（把 MORTIS 重排后的 prompt 喂给基线、以 Relayout-only 为 1×）干净地剥离了"布局收益"与"调度收益"，证明基线调度策略在前缀/后缀粒度上确实无法利用 prompt 内异质性；**任务质量对照**回应了"改 prompt 顺序会不会伤模型"的自然疑问（见第六部分交叉验证，这个问题比想象中严重）；**金融 agent 上调度几乎不加收益**的诚实报告——该 agent 是简单管线、消化大块文档，只有最高压力下主动驱逐陈旧缓存才见效。

负载规律也讲得清楚：低并发时内存充裕，re-layout 贡献几乎全部收益（把隐藏共享暴露出来即可）；并发升高缓存开始争用，调度才登场（保住可复用头部）；最高压力下引擎完全饱和、无空闲内存可供调度腾挪，各配置收敛回基线。这条"压力-收益曲线"本身也是论文的可信度来源——它在正确的物理约束处（显存耗尽）承认优化空间消失，而不是宣称全负载段优势。

消融 2×2 的详细读法（论文 Table 3）：

| | 调度 Off | 调度 On |
|---|---|---|
| **重排 Off**（JCT/吞吐） | 1.00× / 1.00× | 1.30× / 1.36× |
| **重排 On**（JCT/吞吐） | 1.03× / 1.02× | 1.45× / 1.49× |

四格读出三个信息：单独重排几乎不动几何均值（但注意它在低并发段的单点收益大，被高并发拉平）；单独调度反而比重排单独更强（内存争用是主要瓶颈的信号）；全开超过乘积——超可加。

四类 agent 的收益形态也各有面孔，对照论文 Figure 5：Fact-check（多站点共享 claim+循环累积 evidences）收益最大，JCT 最高接近 2×——它是"intra-prompt heterogeneity"的教科书负载；Finance（管线型、大文档）收益最小但混合负载下错峰价值高；Coding/BFCL 居中，分别对应"迭代改代码"与"多轮工具调用"两种典型模式。**收益大小与"prompt 内异质程度"正相关**这一观察本身就是对论文核心论点的间接验证。

## 六、效果优势的根源解释

因果链：**方法差异 → 机制变化 → 指标提升**，逐环拆解。

**环 1：编译器数据流分析 → prompt 组件还原为程序变量 → "谁会被再用、何时变死"成为可知信息**

- 方法差异：现有系统只见"前缀+不透明后缀"；NOOA 式人工标签复述程序性质且易过期。MORTIS 用 reaching definitions 分析 + CFG 投影 + 弱拓扑排序，自动算出演化五分类与生命周期作用域。
- 机制变化：缓存管理所需的共享/生命周期信息从"猜测或人工维护"变为"编译期免费副产物"，且静态保守性（VOLATILE 兜底）可被运行时按实际转移边精确化。
- 指标提升：这是所有后续收益的信息基础——没有组件级信息，重排不知排什么、调度不知保什么。它也解释了为什么 KVFlow 在四负载上 vs SGLang 无显著改善：不是预测不努力，而是预测所依附的操作对象（原始布局下的可识别前缀）太短。

**环 2：共享性/稳定性排序 + 指令后置 → 隐藏共享变为物理前缀 → 低并发命中率即近饱和**

- 方法差异：原始布局把调用点专属指令放在共享上下文前，前缀在跨调用点处全断；Static-Adapter 只会机械地把不变组件前移（程序无关的固定布局）。
- 机制变化：claim 前移到 system prompt 后，四站共享 "system+claim" 前缀；evidences 的 EXTEND 性质让旧 token 前缀天然可复用；指令沉底不再切断公共前缀。引擎现有 radix 缓存零改动即可命中——51–92% 错失的共享 token 大部分被找回。
- 指标提升：低并发下 re-layout 几乎贡献全部收益；消融中仅 re-layout 也有 1.03×/1.02×（几何均值），且在 Coding/BFCL 上低并发命中率即追平完整 MORTIS。注意环 2 的收益"上限锁定"于布局自由度：若框架 lowering 不允许重排（组件被模板语法粘死），这条环就断了——这也是方法适用性的前提条件。

**环 3：重排创造"可放弃尾部+可保留头部"结构 → 四档带驱逐+PLANNED 保留 → 高并发下守住命中率**

- 方法差异：LRU 不区分可复用头部与易变尾部；KVFlow 等虽预测调用但操作的前缀太短（原始布局下可识别前缀确实短——这正是环 2 未做的结果）；同布局对照实验证明基线调度即使拿到好布局也最多再赚 1.11×。
- 机制变化：约 20% 只用一次的 token 所在的 TRANSIENT 尾部被优先驱逐、禁止下沉 host；PLANNED 带按收益密度 D 准入，内存争用时"该保的保住、该放的放掉"。
- 指标提升：仅调度也有 1.30×/1.36×；BFCL 高并发命中率约 65% vs Relayout-only 的 40% 以下；混合负载中异质 agent 内存需求错峰 + 及时让出陈旧缓存，收益进一步放大到 1.56×/1.53×。

**环 4：两机制超可加 → 1.45×/1.49× 总收益**

消融的 2×2 表给出最有说服力的一格：仅 re-layout 1.03×、仅 scheduling 1.30×、全开 1.45×——超过两者乘积（约 1.34×）。机理很清晰：**重排创造的"可复用头部+可放弃尾部"结构正是调度所需的操作对象**——没有重排，调度想保的前缀太短（MORTIS-No-Relayout 在原始布局下命中率上不去）；没有调度，重排暴露的头部在高并发下会被 LRU 误驱逐。两个机制是"造出可管理的结构"与"管理它"的关系。

值得注意这个超可加性只在"几何均值"口径下显著——金融 agent 上调度加成近零、Fact-check 上调度加成很大，**超可加的程度与负载的异质程度同步**。这不是放之四海皆准的魔法叠加，而是"结构-策略匹配"在合适负载上的兑现。

**环 5：任务质量不降的来源**

重排只动顺序不改内容，且组件自带标签（参数名标记的自包含块），模型看到的信息集合不变。实测三种布局下 LLM 调用次数差 ≤3%、输出 token 差 ≤6%，Fact-check/BFCL 准确率反而上升（16.3%→21.9%、14.1%→18.7%）。注意"调用次数差 ≤3%"这半句很关键——它排除了"加速是因为模型少跑了几轮循环"的替代解释。准确率上升的一个可信解释是"指令后置"恰与提示工程 known-good 实践（任务描述贴近生成位置）暗合——性能优化与质量优化在这里意外同向（详见交叉验证第 3 条的边界讨论）。

**环 6：混合负载放大效应的来源**

四类 agent 的内存需求时间上错峰（编码 agent 的 prefill 高峰与工具调用 agent 的等待期不重叠），MORTIS 的"语义化驱逐"能在别人需要时立即让出已死的缓存——LRU 做不到这点因为它不知道哪些已死。这解释了混合负载几何均值（1.56×/1.53×）高于单负载均值的现象：细粒度让渡能力在资源争用频繁的环境里溢价。

**总因果链**：编译器分析（组件=变量）→ 两条机制线（重排暴露共享 / 调度保住共享）→ 分层收益（低并发靠重排、高并发靠调度、混合负载靠错峰让渡）→ JCT/吞吐几何均值 1.45×/1.49×，且任务精度不降、调用量不变。两个机制以"造结构+管结构"的关系超可加咬合，是全部收益的结构性来源。

### 外部检索交叉验证

我做了外部检索，验证论文核心论点在更大语境下的成立性：

1. **"程序信息暴露给 serving 层"的路线有 OSDI 级先例**。Parrot（OSDI 2024，[https://arxiv.org/abs/2405.19888](https://arxiv.org/abs/2405.19888)，[微软研究院页面](https://www.microsoft.com/en-us/research/articles/parrot/)）用语义变量把请求间 DAG 传给服务端，端到端延迟最高降 11.7×、共享 system prompt 场景请求数撑 12×。这印证了 MORTIS 的前提：**请求级 API 丢失应用级信息是真实且昂贵的**。但 Parrot 的语义变量止步于"占位符级"的生产者-消费者关系；MORTIS 更进一步用经典数据流分析（reaching definitions）提取变量的**演化模式与生命周期**，并据此改写 prompt 物理布局——分析深度上是代际差。
2. **"前缀之外还有大量可复用 KV"被独立工作反复证实**。CacheBlend（EuroSys 2025，[https://research.rudrite.com/cacheblend](https://research.rudrite.com/cacheblend)）面对 RAG 场景同一痛点：非前缀位置的缓存块复用率近零，其解法是"全部复用+选择性重算约 15% 的跨块注意力关键 token"，TTFT 降 2.2–3.3×。这佐证了 MORTIS 的动机数据（51–92% 共享 token 错过缓存）不是个例。两条路线形成有趣对照：CacheBlend **改内核**让非前缀 KV 可拼接（付重算代价），MORTIS **改布局**让复用退化为合法前缀（复用现有引擎、零内核改动）——后者代价更低，但前提是组件可重排（类型化框架给了这个自由度）。
3. **"prompt 顺序影响任务质量"是真实风险，论文的处理偏乐观**。外部证据：多项研究报告示例块位置变化可使准确率波动数个百分点到极端情况数十个百分点（如 Llama-3 3B 在 GSM8K 上把 demonstration 从开头移到末尾，42.0%→11%；综述见 [https://www.promptot.com/blog/block-order-matters-prompts](https://www.promptot.com/blog/block-order-matters-prompts)）；UCSD 2025 研究发现示例顺序敏感度（0.01970）与示例选择敏感度（0.02251）几乎同量级（[https://alphaxiv.org/audio/2511.09700](https://alphaxiv.org/audio/2511.09700)）。MORTIS 的 Table 2 只测了 4 个负载、Qwen3 单一模型族、且多数指标变化在噪声量级（Coding 54.8% vs 55.3%）——**方向上可信（组件自带标签、信息集合不变），但"重排无损"的一般性在强顺序敏感任务/模型上未被充分验证**，这是审稿人应追问的点。值得注意的是 Fact-check/BFCL 的提升可能恰来自"指令后置"带来的 recency 效应，与提示工程的 known-good 实践（任务放末尾）暗合。
4. **相反/边界结论的检索**：我尝试检索"prompt 布局重排总是无害"或"编译器分析对 agent serving 无益"的相反证据，本次检索范围内未发现直接反驳；检索到的相邻工作（KVTether 捕获运行时生命周期信号、TokenCake 估计工具调用时长做换入换出）反而都确认"组件级生命周期信息有价值"这一前提，只是获取手段不同（运行时信号 vs 静态分析+运行时细化）。论文自报的局限也属诚实：单卡 A40 为主、四个偏小负载、模型单一（Qwen3-32B/14B AWQ）、预取贡献 ≤2.6%——在更快互联/更大显存的生产配置下收益幅度待验。
5. **与 Flide 等单 pass 引擎路线的张力（边界讨论）**：检索中注意到另一条技术路线——为 agent 决策/多问场景构建专用单 pass 引擎（如 arXiv 2610.42148 的状态分叉）。若未来引擎能在一次前向内完成"共享状态+全部分支"，重排暴露前缀的收益部分被内化。但两条路线并不互斥：MORTIS 的组件级生命周期信息对任何缓存型引擎都是有效输入，且通用 serving 的存量生态（SGLang/vLLM）在可见未来仍是主流载体。本次检索范围内未发现对编译器-guided 缓存管理路线的否定性结论。

## 七、必要知识反推

读懂本文需要（或能反向学到）的知识栈，按依赖顺序（1–3 是领域背景，4–6 是方法工具，7–9 是评估与工程视角）：

1. **LLM serving 基础**：prefill vs decode 两阶段、KV-cache 的作用与显存代价、radix 树前缀缓存（SGLang RadixAttention——用 radix 树组织已缓存前缀、新 prompt 沿树匹配最长路径）、LRU 驱逐、device/host 分层（HiCache/Mooncake 式两级池）。
2. **Agent 负载特征**：多轮循环调用、累积上下文、工具间隙（InterCept/Continuum/TokenCake 处理的 ReAct 工具调用空档）、KV 抖动的代价（prefill 涨 6.8×）。
3. **类型化 LLM 函数调用框架**：DSPy Signature/Module、byLLM 的 meaning-typed programming、NVIDIA NOOA——理解"prompt 组件 ↔ 程序变量"的对应从何而来，以及框架 lowering 总是产出五类组件这一关键事实。这条知识也划定了方法边界：对 LangChain 式自由拼接字符串的框架，此路不通。
4. **经典编译器分析**（本文的工具箱）：reaching definitions（到达定值分析——每个程序点上可能生效的定义集合）、过程间 CFG 与投影、Bourdoncle 弱拓扑排序（从图环结构恢复循环嵌套，1993 年形式验证领域成果）、Tarjan SCC（强连通分量缩凝 DAG）。
5. **图算法**：优先图建模偏序、SCC 缩凝+拓扑排序得到全序——布局算法的骨架。
6. **统计估计**：Witten-Bell 插值（1991 年零频率问题：未见事件的概率估计与上下文加权平滑）、分位数（t₅₀/t₉₀）做保守到达时间估计。
7. **缓存调度理论**：收益密度排序（D 公式的结构 = 价值/时间，与最短作业优先/价值密度贪心同族）、带优先级的分档驱逐（band 而非单一 recency）、预取的截止时间计算（trelease = 预计到达 − 传输时间 − 重算时间）。
8. **提示工程的位置效应（可选但重要）**：lost-in-the-middle、首因/近因偏差——评估"重排是否影响质量"时需要的背景视角。
9. **多智能体/MAP-Reduce 式请求拓扑（可选）**：Parrot 论文里总结的链式摘要、map-reduce、多代理编码等工作流形态——理解"为什么请求间结构信息值钱"的背景。

## 八、通用性灵感

先总一句：MORTIS 的深层主题是**把"隐藏在程序结构里的运行时事实"变成系统可消费的元数据**。以下各条都是这个主题在不同方向上的展开。

1. **"LLM 程序也是程序"**。Agent 应用的 prompt 不是散文而是编译产物——有语法树、有数据流、有生命周期。一旦把 prompt 组件看作程序变量，七十年的编译器分析积累（到达定值、活性分析、CFG 投影）全部可以直接出租给 serving 系统。这个对应关系可以推广：agent 框架的中间表示（无论 byLLM/DSPy/NOOA）都是现成的分析入口，任何"运行时才知道值的结构"都能用"符号化执行 lowering"提取静态骨架。
2. **信息的所有权决定信息的价格**。NOOA 要开发者手工标注参数性质，MORTIS 证明这些性质**本来就写在代码里**。设计系统时先问：我要的元数据是不是某个上游已经拥有的信息的重复表达？如果是，就去上游挖（编译器/类型系统/运行时），别让人手抄——手抄的元数据必然过期。
3. **先造结构，再谈策略**。消融的超可加性（1.03×+1.30×→1.45×）是本文最美的结果：调度策略再好，没有 re-layout 造出的"干净头部+可弃尾部"就没有操作对象。系统设计常犯的错误是拿着聪明策略去操作混乱结构——先重构表示（这里 literally 是 re-layout），策略的杠杆才搭得上去。
4. **预测不确定时的分层保守设计**。静态分析冲突就降级 VOLATILE、运行时按实际边精确化；概率估计用 Witten-Bell 从粗上下文平滑到细上下文；到达时间按分布离散度收紧。每一层都有"保守兜底+观测细化"的双轨——处理不可完全预测的系统（agent 执行路径）时，这种"静态骨架+运行时血肉"的架构比纯学习式（CacheScout）或纯启发式（LRU）都稳。
5. **改布局是零侵入的优化载体**。MORTIS 的重排不需要改任何 GPU 内核、复用引擎现成 radix 缓存——对比 CacheBlend 要改注意力计算。当你的优化能被"翻译"成下游系统已有机制（前缀匹配）的输入时，落地成本骤降。设计时优先寻找这类"语义保持的表示变换"。
6. **驱逐策略需要语义，不只是时间**。LRU 的隐含假设是"最近用过的将来还会用"——agent 负载下这是错的（20% token 只用一次）。生命周期带（RETIRED/TRANSIENT/UNCLASSIFIED/PLANNED）的思路适用于任何缓存系统：从应用语义里提取"死期"和"下次使用"信息，都比纯时间局部性强。数据库缓冲池、CDN、前端资源缓存同理。
7. **对"prompt 是接口"的意识**。重排 prompt 组件 = 改变了模型看到的接口呈现，这个操作有性能收益（缓存命中）也有质量风险（位置敏感）。工程上应该把"prompt 布局"当作可调参数管理：默认给缓存友好布局，保留 per-call-site 开关（论文的 pin 开关就是雏形），关键任务上 A/B 验证。这与 API 设计里"字段顺序不影响语义、但影响序列化兼容性"的权衡同构。
8. **混合负载是异质性的放大器**。四类 agent 混跑时收益（1.56×/1.53×）高于单独均值，因为不同 agent 的内存需求错峰、MORTIS 能及时让出陈旧缓存。部署启示：**异质负载共置时，细粒度的"该放就放"能力比单负载下的峰值优化更值钱**——这也是云上多租户 serving 的普遍规律。
9. **诚实的负结果帮助定位机制**。金融 agent 上调度几乎无效、预取贡献 ≤2.6%、最高压力下收敛回基线——这些"不 work 的格子"划出了方法的适用边界（管线型单流的 agent、预取在快显存配置下无利可图），反而让主结论更可信。写系统论文和读系统论文时，负结果都是定位因果的锚点。
10. **编译器与 ML 系统的"再合流"**。过去十年 ML 编译器（XLA/TVM/MLIR）把编译技术用于加速张量计算；MORTIS 代表另一条路——用编译分析为**运行时资源管理**（缓存、内存、调度）提供语义信息。随着 LLM 应用越长越像传统软件（类型、模块、控制流），预计更多经典分析（指针分析→别名分析查共享、副作用分析→查工具调用污染）会被重新包装进 serving 栈。"AI 应用的性能工程"正在变成一个编译器问题。

**一句话收束**：MORTIS 告诉我们，agent 时代最大的免费午餐埋在程序本身的结构里——编译器只是那把挖它的铲子。
