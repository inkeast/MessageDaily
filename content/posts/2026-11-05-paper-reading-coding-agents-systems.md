# 编码代理五连读：从压缩模型到修复模糊构建的系统级工作

## 〇、总览：当编码代理开始「经营系统」

过去两年，编码代理（coding agent）的评测重心经历了三次迁移：从函数级代码生成（HumanEval），到仓库级 issue 修复（SWE-bench），再到终端环境里的多步骤任务（Terminal-Bench）。而这五篇论文共同标记了第四次迁移的方向：**让代理接管那些传统上由系统工程师、SRE、平台团队承担的「系统级工作」**——压缩一个模型、设计一个推理服务系统、端到端解决一次云事故、迁移整个企业的代码舰队、修复持续模糊测试的基础设施故障。

五篇论文分布在这条光谱的两个端点上，恰好互补：

- **评测端（论文一、二、三）**：三个新基准分别把 LLM 压缩、推理服务设计、云 incident 解决形式化为「终端任务」（terminal task）——代理在固定预算内自由探索，最终由独立验证器裁决。这是 Terminal-Bench「以结果论英雄」范式向 AI 系统工程与 DevOps 领域的系统性扩张。
- **落地端（论文四、五）**：两篇系统报告展示了同一类工作在真实世界里的形态。Bloomberg 的 Automated Uplift 在约 8,600 个仓库上跑了两个迁移战役；FuzzMedic 则在 OSS-Fuzz 上修复真实构建失败并拿到 29 个维护者合并。

| 维度 | CompressionBench | ServerBench | SWEOps-Bench | Bloomberg Uplift | FuzzMedic |
|---|---|---|---|---|---|
| 任务 | 压缩 LLM | 设计推理服务 | 解决云 incident | 舰队级代码迁移 | 修复模糊构建 |
| 核心指标 | PPL 比 + 准确率门 | dollars per dollar | 分级恢复率 + 惩罚时延 | PR 合并率 | check_build 通过率 |
| 顶级数字 | 29/36 通过验证 | 4.87× 最强基线 | 52.7% 端到端恢复 | 2,333 PR / 729 合并 | 48.44% 修复率 |
| 最深洞察 | 似然≠能力保持 | 验证须匹配部署负载 | 检测≠恢复 | 生成≠吸收 | 症状≠根因 |

合读之后能看到一条贯穿五篇的暗线：**系统级工作中，「可见信号」与「真实目标」之间的裂缝无处不在**——压缩后的 PPL 几乎不变但答案变了（论文一）；开发环境的评分到最终重放暴跌（论文二）；症状清除但修复语义错误（论文三）；PR 生成了却没人合并（论文四）；编译错误在 A 工作区而根因在 B 工作区（论文五）。五篇论文的解法殊途同归：把验证做成独立、执行、贴近部署条件的闭环。下面逐篇精读。

## 一、CompressionBench：让编码代理自主压缩 LLM

### 1.1 背景与定位

LLM 推理正日益受限于内存带宽而非算力：自回归解码中每个 token 都要把权重从显存读一遍，而一次片外访存的能耗远高于它喂给的乘加运算。压缩——在更小存储预算内保持模型行为——因此同时降低部署显存占用与每 token 能耗。构造一个高质量压缩模型从来不是「选个位宽」那么简单，而是涉及量化格式、混合精度分配、剪枝、低秩分解、蒸馏以及配套推理代码的耦合决策。这项工作恰好是编码代理日益擅长的那类「实验加系统」劳动，而且自带递归自我改进（RSI）意涵：会压缩模型的代理，能改进后续系统所依赖的模型效率。

论文的定位是提出**第一个评测代理自主压缩 LLM 能力的终端任务基准**。与 KernelBench（评测单个 kernel）、MLE-bench（评测 ML 实验）不同，CompressionBench 的独特性在于「数值近似的选择权」：代理必须自己选择、实现并验证一种表示，使生成的答案仍然有用。作者来自 CMU InfiniAI Lab（该校研究团队，曾出品 Hotline 等推理系统工作），是 Terminal-Bench/Harbor 生态的深度参与者。

### 1.2 问题定义

任务四元组：源检查点（含 tokenizer）、存储上限 C、GPU 与固定运行时、墙钟预算 T。代理在离线容器中工作，可读论文、校准数据与恢复数据，自由产出候选 a = (W, I)——压缩权重加推理实现。优化目标形式化为：

**minimize Δ̂(a) = Ĥ(q_a) − Ĥ(p)**，约束为包存储 S_pkg(a) ≤ C 且驻留存储 S_res(a) ≤ C。

奖励函数是源模型采样续写上的 PPL 比值 F = PPL(p)/PPL(q_a)（其期望恰等于平均 next-token KL 散度），乘以十倍作为反馈；执行失败或超存储则记零。关键设计有三：**双存储口径**——包体积与服务时驻留权重（含 scale、codebook、持久化反量化副本）分别检查，防止「小包大跑」的作弊（试点实验发现 QTIP 包仅 6.96 GiB 但执行时保留 BF16 权重，正是这条规则的由来）；**预算共享**——评估调用与构建消耗同一个 T，代理必须判断「再跑一次完整模型实验值不值」；**独立终审**——冻结产物在全新容器里用不相交的数据复测，答案准确率门（GSM8K/HumanEval/TriviaQA 各 50 题，均值 ≥ BF16 参考的 80%）在搜索期不存在且阈值对代理保密。

### 1.3 解法：任务设计与六个代理的搜索

实验设置：三个源模型——两个 MoE（Nemotron-3.5 Super VL 120B-A12B、Qwen3.5 122B-A10B，各配 32/48 GiB 双档）与一个 dense（Qwen3.8 27B，配 8/12 GiB 双档），共 6 个任务。六个代理：Claude Sonnet 5.5、Claude Opus 5.5、GLM 5.3、Kimi K3.1 Pro、MiniMax M3.1 Flash、DeepSeek V4.1 Flash 1017，统一用 Claude Code 挂最大推理力度、单张 H200 NVL、vLLM 0.32.0、8 小时预算，每对代理-任务只跑一次。基线包括均匀 GPTQ（组 128、128 条校准序列）与三个已发布量化（Unsloth Dynamic、GSQ-RCO）。

两个完整案例展示了高分代理的实际策略。**Sonnet 压 dense Qwen3.8 到 12 GiB**：用 Hadamard 旋转加格码（trellis codes）替换标量 GPTQ，配误差补偿与 Viterbi 搜索；KL 消融拟合出损失模型指导位宽分配，token 频率指导嵌入与输出头精度；实验否决了 KL 变差的 Fisher 加权方案与大格码。最终 PPL 3.253、三基准均值 76.67%，对比 BF16 的 3.221/74.00%。**Opus 压 MoE Qwen3.5 到 48 GiB**：旋转 GPTQ 加专家间差异化位宽，修订本地验证方法（改评模型生成续写）后把精度配额转向后层；最终 PPL 2.818、准确率 82.67% vs BF16 2.755/84.67%。

### 1.4 评测数值与优势根源

主结果：36 份提交 29 份通过验证（宽松档 18/18 全过；紧张档 6 个倒在准确率门、1 个超时）。每任务取最低 PPL 代理产物，平均比 BF16 PPL 高 3.4%，下游准确率 77.33% vs BF16 79.56%。

**基线对比**：均匀 GPTQ 在 6 个设置中 4 个过不了答案门——最惨的 Nemotron 32 GiB 档 PPL 4.680、准确率 5.33%，同任务 Sonnet 做到 1.801/76.67%；而最强代理产物在全部 5 个可测发布量化参考上 PPL 更优（Qwen3.8 8 GiB：Sonnet 3.363 vs GSQ-RCO 3.764）。但准确率维度上紧档 Qwen3.5 发布版反超最低 PPL 代理产物，且 Sonnet 的 12 GiB 产物解码速度只有 16.7 tokens/s、远低于 GSQ-RCO 的 74.6——存储-质量收益不自动兑现成速度，表示与 kernel 必须一起考虑。

**优势根源的因果链**（基于记录的 301 次评估与全部修订轨迹）：(1) 存储预算把表示、精度分配与参数保留耦合成一个整体——位宽定死码本数量，clipping 与 rounding 决定这些码如何逼近权重，24 次等存储修订里 21 次降低 PPL，Kimi 在紧张 Qwen3.5 上只改 clipping 与 GPTQ damping 就把反馈 PPL 从 3.738 压到 3.132。表示设计在固定存储下「创造空间」，这是与只选位宽的固定配方拉开数量级差距的根源。(2) 完整模型反馈逆转 79 次局部排序中的 17 次——权重 MSE、层输出误差与整体 PPL 会偏爱不同候选（k-means 码本权重 MSE 更优但 PPL 更差，GPTQ 取舍相反），实验判断力（何时信局部证据、何时花预算跑完整模型）因此成为关键能力。(3) 似然不验证模型：Opus 的分配加蒸馏把 PPL 增量从 6.17% 一路压到 4.64%，GSM8K 却从 88% 掉到 72%；Sonnet 三个版本 PPL 3.2572/3.2531/3.2525 几乎相同，150 题里答对 111/104/115 题——生成与推理一致性测试暴露 PPL 看不见的失败，独立验证因而是必要的而非装饰。

### 1.5 知识反推

让一个零基础的人重做这项工作，最少需要：**量化与压缩理论**（GPTQ/AWQ/QuaRot/QuIP#/QTIP 一族方法的取舍、Hessian 加权误差补偿、格码与 Viterbi 解码、剪枝后蒸馏恢复）；**存储与推理系统知识**（包体积 vs 驻留存储的口径、反量化副本、kernel 实现对内存流量的影响）；**实验方法论**（KL 散度与 PPL 比值的等价性推导、局部指标与全局指标的分歧来源、预算 constrained 实验设计）；**终端任务评测工程**（Harbor 容器化、冻结终审、防作弊的存储核算）。最难的融合点在于把「压缩算法研究」翻译成「代理可探索的决策空间」——论文不规定流程，只固定目标、预算与验证，这要求设计者对哪些自由度真正影响质量有深刻直觉。

### 1.6 通用灵感

**灵感一：奖励只测一个量，验证必须测另一个正交的量**。PPL 度量分布保真，答案门度量能力保持，二者在轨迹上明确分离——任何「单一指标上线」的自动化系统（代码生成用通过率、翻译用 BLEU）都值得问一句：我的指标与真实目标之间有多大的可操纵缝隙？**灵感二：把「预算共享」作为评测设计原则**。评估调用消耗同一个时间池，逼出「实验判断力」这一通常被隐藏的能力——推广到人类组织：审批资源与执行资源同池，才能看出谁真的会做实验。**灵感三：规则要堵住「小包大跑」式的口径套利**。双存储核算的教训是：任何资源约束都要覆盖「持久占用」而不仅是「申报体积」，从云成本核算到碳排放核算同理。

## 二、ServerBench：让编码代理设计专用推理服务系统

### 2.1 背景与定位

编码代理的工作流本身跑在 LLM 服务系统上，这带来一个自指的机会：代理能否设计支撑自己运行的服务系统？现有推理评测基准有三个被论文明确点名的缺口：**工作负载过度简化**——独立请求或固定 prefill/decode 场景下，静态批处理几乎和生产引擎一样好，连续批处理与 paged attention 的价值测不出来；**目标只有加速比**——忽略时延要求与 GPU 成本，而服务提供方真正要决定的是「在满足 TTFT/TPOT 的前提下接多少负载」；**验证只查正确性**——短促孤立的测试根本覆盖不了投机解码、状态复用、自定义调度引入的新执行路径。ServerBench（CMU + USC，InfiniAI Lab 的姊妹工作）同时补上这三个缺口，是第一个评测「代理设计完整服务系统」的基准。

### 2.2 问题定义

任务固定模型检查点、GPU 配置、编码会话工作负载与服务要求。代理从最小 Transformers 服务器 S₀ 出发，在开发预算 B（8 小时）内产出实现 S_B 与会话并发 c_B——既造引擎又选负载，这是与「固定负载测加速比」的根本区别。目标函数 **dollars per dollar**：把每个完成请求的输入输出 token 按固定 API 价格计价，只有 TTFT 与 TPOT 都达标的请求计入分子，除以测量窗口的 GPU 成本。例如 3.65 美元合格 token 价值除以 0.83 美元 GPU 成本得 4.40。时延目标取 SGLang 参考配置多次重放 p90 的最大值，在开发开始前冻结。工作负载用 AgentX harness 有状态闭环重放真实编码代理会话：保留请求长度分布、共享前缀、并行子代理分支与轮间依赖——后继请求要等它依赖的响应，服务时延因此决定窗口内能推进多少工作，这是开环基准无法模拟的。验证在全新部署上用不相交种子重放：查完整提示、规定输出长度、流式一致性、对检查点的生成保真（疑似续写用 teacher forcing 查每 token 后悔上界 4.0）、held-out 20 题答案准确率（较朴素实现最多降 0.1），再加运行后代码与行为审查。

### 2.3 解法：评测协议与实验设置

三个部署：Qwen3.5 9B（2×L40）、Gemma-4-E4B-it（1×L40）、Qwen3.8 27B INT4（2×L40）。十一个代理模型（Claude Opus 5.5/Sonnet 5.5/Opus 5、GPT 6 Astra/6.1 Sol/6 Sol、Kimi K3、Qwen3.8-Max-0902、MiMo V2.6 Pro、GLM 5.3、DeepSeek V4.1 Flash），GPT 系挂 Codex、其余挂 Claude Code，全部最大推理力度；每对代理-部署一次 8 小时开发加 1,800 秒终评重放。基线 SGLang v0.5.19 与 vLLM v0.28.0（Qwen3.5 9B 上 1.62/1.49，Gemma 上最强基线是 vLLM 的 0.61，27B INT4 上 1.47）。发布版本与实现分离、与性能测试分离；代理自选诊断尺度——小实验隔离疑似瓶颈，完整重放测交互请求。

### 2.4 评测数值与优势根源

**主结果**：33 个运行 22 个产出通过验证的系统、13 个超过最强基线。Claude Sonnet 5.5 在 Gemma E4B 达 2.97 dollars-per-dollar（vLLM 基线 0.61 的 4.87 倍）；Claude Opus 5.5 在 Qwen3.5 9B 达 4.40（SGLang 1.62 的 2.71 倍）、在 Qwen3.8 27B INT4 达 2.64（vLLM 1.47 的 1.80 倍）。但成绩分布很不均匀：六个模型三个部署全部通过验证，只有三个在全部部署上超过最强基线；GPT 6.1 Sol 在 9B 上拿 2.84、在 27B INT4 上却只有 0.98——低于 1.47 的基线。API 花费与成绩也不对齐：Opus 5.5 单次运行花约 100 美元，GPT 6.1 Sol 只花约 13 美元却能在 9B 上拿到 2.84。

**优势根源的因果链**：(1) **高价值设计先升能力再逐步加载**。并发轨迹分类显示 raise-and-hold 组 10/10 通过验证、10 个里 9 个超过最强参考，never-tuned 组 0/6 超过参考；超基线两倍以上的组里 17 次负载决策有 7 次带来后续价值提升，低于基线组 23 次里只有 2 次。成功组在median 0.90 小时就跑通首个可用端到端重放（失败组 2.96 小时），早测量留下更多时间做能力开发。最高分系统普遍组合更多优化——投机解码、延迟感知调度、主机内存状态存储；跨轮复用则人人都有。(2) **反馈要放在工作负载语境里解释**。超基线两倍组 49% 的保留决策有工作负载相关的验证支撑，验证失败组只有 25%、未验证决策占 40%。最漂亮的对照是 prompt-lookup 投机解码：Opus 5 用随机文本合成探针得到 null 结果就放弃了；Opus 5.5 用 60 条重放回复追查，修好模拟器测得每步接受 2.09–2.34 个 token 才采用。从同一检查点恢复 Opus 5 各跑两小时，有重放反馈的那条臂重新采纳了投机解码，新鲜种子上合格价值高 1.13–1.31 倍；工作负载选出的草稿长度 K=7 比合成文本选出的 K=3 高 3.0%–3.9%。(3) **验证必须匹配部署工作负载**。33 个提交里只有 5 个记录过负载或长上下文下的自然停止检查。Kimi 的前缀缓存在孤立长提示测试里通过，同一前缀第二次插入即崩溃——孤立测试漏掉跨请求复用；Qwen3.8-Max 收紧准入策略后只测了短提示，提交的政策让一段 315K token 输入永久排队，终评停摆。反例是 Opus 5.5 在 Gemma 上主动收缩缓存容量逼出抢占路径，暴露未初始化缓存的 NaN 缺陷，修复后 3/3 通过压力测试、回退版本 0/3——把「设计引入的执行路径」变成必测项，是可靠交付的核心。

### 2.5 知识反推

重做这项工作需要：**推理服务系统全景**（vLLM/SGLang 的调度与内存管理、前缀复用、prefill-decode 干扰、投机解码的接受率经济学）；**服务质量与定价知识**（p90 分位数目标、SLO 满足率、token 计价、GPU 小时成本）；**负载建模**（会话依赖、闭环重放、种子间变异、观察窗效应——300 秒窗口的分数平均是 1,800 秒的 1.42–1.70 倍）；**实验设计与代理评测工程**（Harbor 沙箱、冻结终审、行为检查加人工复核的双层验证）。最微妙的融合点是「让代理自选并发」这一设计：它把运筹学里的准入控制变成代理的决策空间，于是评测同时考了实现能力与经营判断。

### 2.6 通用灵感

**灵感一：把「单位成本的价值」而不是「峰值性能」定为优化目标**。dollars per dollar 天然惩罚超载（时延超标即收入清零），推广到任何资源换产出的系统：推荐服务的 QPS 不如「合格 QPS/机器成本」，销售团队的线索量不如「成交线索/人力成本」。**灵感二：验证的覆盖面要跟着设计走**。每引入一个新机制（抢占、缓存复用、准入），就生成一条只在特定条件下才走的执行路径——验证清单应该是设计的函数，而不是一份静态核对表。**灵感三：便宜的工作负载画像可以防止昂贵的误判**。对 128 个种子做 CPU 扫描只要 7.71 秒，就能发现开发抽签处于第 4 百分位的异常轻载——在大规模评测或 A/B 决策前先花几秒钟看分布，是性价比极高的习惯。

## 三、SWEOps-Bench：评测代理端到端解决软件引发的云事故

### 3.1 背景与定位

云上 incident 一旦源于软件缺陷，解决它就要同时动用运维调查（看集群、看日志）与代码修改（改控制器源码、重新部署）——这正是开发与运维边界消融的地带。现有基准各覆盖一角：云运维基准（AIOpsLab、ITBench、SREGym 等）靠微服务 demo 里注入合成故障，不要求修复真实历史缺陷；软件工程基准（SWE-bench）从静态 issue 描述出发修仓库，没有运行时发现与部署验证。SWEOps-Bench（中山大学 + 香港中文大学）填补的正是「运行时检测 → 根因定位 → 源码修复 → 部署 → 恢复验证」全生命周期的空白，且全部任务来自确认过的真实历史缺陷。

### 3.2 问题定义

基准构建走两阶段筛选：先从 Sieve/Acto/Oat 等控制器可靠性研究及 2026 年 1–8 月合并的 bug 修复 PR 里收集候选，按「无可验证上游修复」「非 operator 实现缺陷」「重复或不可复现」三准则排除；再对每个候选重建隔离环境（钉住源码版本、K8s 发行版、镜像与依赖），配对执行 buggy 与 fixed 版本——只有 buggy 复现目标故障且 fixed 消除故障并通过回归检查才保留。最终得到 55 个任务、16 个 Kubernetes operator 项目（含 CNPG、Rook、PromOp、RedisOp、MongoOp 等），28 个来自既往研究、27 个来自 2026 年新收集；缺陷机制分布为 Construction 15、Defensive Handling 13、Input Validation 10、Control Logic 9、Lifecycle/Ownership 5、Admission Policy 3；运行时表现分布为 Workload degraded 19、Operator crash 17、Resource rejected 9、Operator-reported 5、Storage blocked 5。

评测协议：会话先在健康基线上运行（60 分钟预算，阴性对照检验误报），随后触发工作负载制造故障，故障态阶段（独立 60 分钟预算）里代理通过 bash 终端与 kubectl 及本地仓库交互，提交修复后 harness 编译、重建镜像、部署并回传执行反馈。指标覆盖三段：检测（Healthy/Faulty/Paired——Paired 要求同一任务两次判断都对，惩罚「永远报警」与「永远正常」的平凡启发式）；RCA（文件级/函数级/联合）；补救七项（Build/Deploy/Patch Check/Fault Cleared/Regression Tests/Fix-Specific Tests/Agent-Declared Recovery），整体恢复要求在预算内明确声明恢复且通过除 Patch Check 外全部适用检查。时延用惩罚式计量：未达成的检测、识别、补救里程碑分别罚 B、3B、6B 分钟（B=60），三项全缺罚满 10B。

### 3.3 解法：任务定义与评测设计的关键取舍

三个设计决定值得注意。**其一，恢复判据绑定行为而非补丁文本**：Fix-Specific Tests 在触发条件下检验受影响能力（改造自上游 PR 回归测试），接受与参考补丁不同的等价修复——这直接回应了「症状消失不等于语义正确」。**其二，检测与诊断结果独立于最终恢复上报**，使得「错误 RCA 却恢复成功」「正确 RCA 却恢复失败」这类错位可被量化。**其三，时间作为内生目标**：对 SRE 而言时延就是伤害，惩罚式指标把完成率与时延压进同一个可比数字。

实验跑 6 个代理-模型配置：Codex 与 Claude Code 两个终端 harness × GPT-5.6 Luna、Claude-Sonnet-5、DeepSeek-V4.1-Flash、GLM-5.3-Flash 四个模型（各 harness 覆盖两到三个），全部官方默认参数、一线 API 端点，Harbor 编排、每任务独立 k3s 集群。

### 3.4 评测数值与优势根源

**主结果（55 任务均值）**：故障态检测 72.7%–90.9%，配对检测 38.2%–85.5%，联合 RCA 5.5%–50.9%，而整体恢复只有 14.5%–52.7%——识别事故与端到端解决事故之间存在巨大鸿沟。最高配置 Claude Code + Claude-Sonnet-5：配对检测 85.5%、联合 RCA 38.2%、恢复 52.7%；其补救分项为 Build 100%、Deploy 81.8%、Fault Cleared 61.8%、Regression Tests 97.9%、Fix-Specific Tests 58.8%、声明恢复 72.7%。惩罚式 TTR 从 263.7 分钟（最佳配置）到 477.4 分钟（Claude Code + GLM）。

**对比与错位**：Codex 下 DeepSeek-V4.1-Flash 恢复 45.5% 高于 GPT-5.6 Luna 的 30.9%，而 Luna 的配对检测 72.7% 反而是 Codex 系最高——检测强不等于恢复强。Claude Code 的 token 消耗是 Codex 的 4.1–4.5 倍（输入）与 6.6–9.6 倍（输出），但 GLM 配 Claude Code 恢复率反而从 34.5% 跌到 14.5%、DeepSeek 只微升 45.5%→47.3%——多花钱不多办事。轨迹级分析揭示两个错位：14.5%（Codex+Luna）至 21.8%（Claude Code+Sonnet-5）的任务在报告了错误联合 RCA 的情况下仍达成验证恢复（案例 B：RCA 指错文件但修复沿证据走对了路）；反向地，症状清除率 61.8%–72.7% 远高于 Fix-Specific Tests 通过率 29.4%–58.8%（案例 C：删掉 selector override 让集群 Ready 了，却违背了「保留合法 override、拒绝非法 override」的语义要求）。

**优势根源的因果链**：(1) 生命周期成本后置——惩罚时延 TTD 一致低于 TTI 与 TTRem，瓶颈在识别与修复而非发现；未解决轨迹即便拉长执行、增加调用也不收敛。(2) Input Validation 是共同软肋（恢复 40.0%/10.0%），因为归一化或回退处理能消除报错却被算作成功——「消除验证错误」与「正确处理非法输入」在症状层面不可区分，只有 fix-specific 检查能分辨。(3) 失败模式集中在 Action Realization Error（Codex 50.0%/Claude 38.5% 的失败轨迹）与 Insufficient Confirmation（28.9%/46.2%）：前者是「 plausible 干预只改了一半位置」，后者是「观察到残余异常却用不充分证据排除出解决目标」——问题不在有没有看到异常，而在把异常排除出目标时有没有正当理由。修复尝试的边际收益早期集中：Claude Code 一次尝试恢复 47.3%、两次 54.5%、之后不再增加。

### 3.5 知识反推

重做需要：**Kubernetes 与 operator 模式**（CRD、调和循环、PodSecurity、RBAC 清单的生成链路）；**SRE 方法论**（TTD/TTI/TTR 生命周期计量、阴性对照、惩罚式评分的构造）；**基准工程**（历史缺陷复现的版本钉住、配对执行验证、防污染的资料隔离——issue 讨论与参考修复对代理不可见）；**轨迹分析**（失败模式分类学标注与多人一致性校准）。融合难点在于「真实感」与「可控性」的平衡：任务必须真实到保留原始失败模式与触发条件，又必须可控到 60 分钟能跑完一个生命周期——两阶段筛选的每一关都在做这个交换。

### 3.6 通用灵感

**灵感一：诊断是假设，不是阶段**。论文最实用的建议是把 RCA 当作可在补救全程修订的假设、把部署结果当作更新假设的证据——任何「先诊断后执行」的线性流程（医疗、维修、调试）都受益于这种贝叶斯化。**灵感二：维护显式的恢复契约**。修复前先写下「这个修复应该恢复什么行为」（从 API 定义、schema、既有测试导出），症状消失只是契约的一部分——推广到任何「指标代理目标」的场景：降级指标达标不等于用户体验恢复。**灵感三：机制要对着失败模式打**。Step Repetition 高的代理需要状态跟踪，Insufficient Confirmation 高的需要证据链接式验证——泛化加推理或工具不如对症下药，这一原则适用于所有 agent 工作流设计。

## 四、Bloomberg 的混合管线：企业规模代码迁移的工业经验

### 4.1 背景与定位

每个大组织都背着一长列「值得做但永远不够紧急」的基础设施迁移：旧构建工具还能跑、旧打包模型还有人在用，单仓库迁移成本高到排不进路线图。Bloomberg 把这类工作称为 uplift，并把问题改写为：如果自动化把生成迁移的成本打到极低，组织能否把以前「不值得做」的迁移做掉？Automated Uplift 是一个多个月的工业项目，论文报告其中成长起来的两个战役：异构的 Python 打包迁移（PyPackaging，约 1,900 个候选仓库）与均质的 C++ 构建系统迁移（CppBuild-to-CMake，约 6,700 个候选仓库），合计约 8,600 个仓库。这是典型的工业经验报告（Bloomberg + UCL），价值不在 novelty 而在真实约束下的完整数据。

### 4.2 问题定义

三个研究问题：RQ1 确定性工具与 LLM 步骤之间怎么分工？RQ2 运行时生产数据对迁移准确度有什么影响？RQ3 舰队规模迁移战役的主导瓶颈是什么？背后的核心约束是：仓库级迁移需要源码里不存在的信息（生产跑的是哪个解释器版本、哪个集群部署了哪个依赖版本、哪些脚本真的被调用），而直接套用开箱 LLM 在复杂仓库上崩溃（引用的 RepoMod-Bench 数据：1 万行以下仓库 pass 率 91.3%，5 万行以上掉到 15.3%）。

### 4.3 解法：五阶段混合管线

两个战役共享同一骨架：**(1) 分类收集（确定性）**——按原型（archetype）分类并组装迁移上下文；**(2) 提示渲染（确定性）**——同一上下文恒定渲染出同一提示；**(3) 执行（LLM）**——PyPackaging 里 LLM 直接改仓库，CMake 里 LLM 只抽取 JSON、模板写 CMakeLists.txt；**(4) 验证（确定性，永不委托 LLM）**——按历史失败提炼的规则检查，失败则带错误重调 LLM 至多三次；**(5) 描述（LLM，只读）**——从迁移证据写 PR 描述。原则一句话：凡需跨舰队可复现、可审计的都确定性，LLM 只做仓与仓之间会变的那部分变换。代码量结构佐证这一定位：PyPackaging 工具约 4,300 行确定性 Python 对 230 行 LLM 接口，外加约 3,600 行提示模板与参考文档。

两个战役在两个维度上构成自然对照。**反馈环深度**：CMake 是浅环——抽取错误被 schema 拦、模板错误被编译拦、行为改变被单测拦，全部发生在开 PR 之前；PyPackaging 是深环——打包与 --help 冒烟能过，错误的依赖选择要到 owning team 部署运行才暴露。**人群均质性**：CMake 项目落入少数相似原型、一个仓库的修复可复制到下个仓库；PyPackaging 候选散布 18 类原型、大量一次性案例。运行时遥测是 PyPackaging 的关键输入：12 个数据源（解释器启动日志、模块使用轨迹、集群依赖版本等）与 AST 导入交叉验证——两边都见的依赖按部署环境可用版本钉死；只在源码出现的可能是条件性或死依赖，交给 LLM 不钉版本；只在运行时出现的通常是传递依赖，排除。模型从 Claude Sonnet 4.5 升到 Opus 4.6 后，分工边界双向移动：放松了为旧模型不可靠导入分析而设的 AST 预处理，收紧了分类（早期试过 LLM 分类，因同包不同跑落进不同原型而废弃）——工作准则沉淀为「扩大 LLM 在生成中的角色，绝不扩大它在验证中的角色」。

### 4.4 评测数值与优势根源

截至 2026 年 4 月 30 日的 PR、6 月 30 日观察结局：两战役共 2,333 个 PR、729 次成功迁移。CMake：2,039 个 PR 中合并 698（34.2%）、拒绝 165（8.1%）、无决策 1,176（57.7%）；PyPackaging：294 个 PR 中合并 31（10.5%）、拒绝 64（21.8%）、无决策 199（67.7%）。按团队估计（每个 CMake 任务约 2 人日、每个 PyPackaging 任务 1–2 人日），仅已合并变更就折合超千人日手动工作量。PR 生成率按原型分层：PyPackaging 三个专属模板原型分别达 80.2%（96 任务出 77 PR）、56.5%、54.5%，多数失败是故意拒绝（数据收集发现不可安全迁移就不开 PR）；CMake 三个原型中公司定义构建配置走全自动确定性工具（1,877 任务），团队定义与代码生成原型分别 44.4% 与 63.0%。

**优势根源的因果链**：(1) CMake 合并率是 PyPackaging 的三倍多、拒绝率不到一半，主因是浅反馈环——管线内编译加单测给了评审者「已知能工作」的强证据，而 PyPackaging 的接收团队要自己承担部署风险。均匀人群使修复可跨仓复用进一步摊薄信任成本。(2) 瓶颈从生成转到吸收：最常见的结局是「无决策」（57.7%–67.7%），生成速度远超团队消化速度；继续提升生成质量对这两个数字影响甚微。(3) 合并率系统性低估影响：51 个被拒的 PyPackaging 仓库里 34 个后来由团队自己完成迁移、14 个复用了管线的大部分改动——PR 作为「起点草稿」的价值不计入合并统计。开发者反馈直指两个改进点：让团队能直接 push 到机器人的分支（有人因为推不进去只好另开 PR 合并自己的版本）、开 PR 前先跑项目自己的测试。

### 4.5 知识反推

重做需要：**大规模代码改造的前 LLM 谱系**（ClangMR、T2R、PolyglotPiranha 的规则式路线及其在异构场景的极限）；**构建与打包系统知识**（CMake 语义、Python 打包模型、import 与包名的映射难题——PIL 来自 pillow 这类错位靠全舰队级映射表一次性解决）；**生产遥测工程**（启动日志、模块使用轨迹、集群版本差异如何变成提示上下文）；**组织与流程设计**（中心团队把指令写给管线而非写给人群、原型分层运营、批量评审）。最深的融合点是「Environment-in-the-Loop」主张的工业化：把可执行环境状态与运行时反馈直接纳入迁移过程——学术版本是让代理跑测试，工业版本是喂给它全舰队观测数据。

### 4.6 通用灵感

**灵感一：自动化降的是生产成本，不是吸收成本**。任何向他人交付产出的自动化（报表、补丁、决策建议）都要问：接收方的审阅、验证、部署成本降了吗？没降的话，瓶颈只是换了位置。**灵感二：反馈环深度决定自动化上限**。开战前先评估「错误能在离产生多远的地方被发现」——能在管线内编译验证的可以高歌猛进，需要部署后运行时验证的要克制设计。这个单变量比任何模型选型都更预测成败。**灵感三：给长尾留「起点 PR」而非全自动**。约 20 个仓库以下的原型不值得专属自动化，承认阈值、把工程精力转向采纳问题，是反过度工程的组织智慧。**灵感四：验证权与生成权分离，且验证权永不外包给模型**——舰队规模下一个漏检错误伤害几百个仓库，这个不对称性决定了安全边界。

## 五、FuzzMedic：修复持续模糊测试的构建失败

### 5.1 背景与定位

OSS-Fuzz 为开源项目提供持续模糊测试，但约 20% 的集成项目处于构建失败状态——fuzzer 实际「下岗」。修复横跨两个工作区：项目仓库与模糊基础设施工件（构建脚本、工具链、sanitizer 设置），平台维护者缺项目上下文、项目维护者缺模糊专长，形成维护真空。现有构建修复系统（BuildMedic 修 Maven 依赖、CXXCrafter 修通用 C/C++ 构建、CompileAgent 做仓库级编译）都不处理这种跨工件、需要容器与插桩约束意识的修复。FuzzMedic（天津大学 + 南洋理工 + Google）用多代理系统补位，并有 29 个补丁被上游或 OSS-Fuzz 主分支合并的真实落地证据。

### 5.2 问题定义

任务定义有三个实际约束：编译器或链接器报错只是症状，可操作的修复可能在另一个工作区或依赖里；故障发生在可运行 target 存在之前，只有构建反馈没有崩溃输入；补丁尝试会改动工作区——清掉早期错误可能暴露后期错误，失败的编辑可能破坏之前正常的阶段，无差别的补丁采样在昂贵的完整构建面前不可行。基准构建相应地强调历史保真：从 OSS-Fuzz 公开门户收集 2022 年 12 月至 2026 年 6 月的 1,820 份构建失败日志，经事件去重（余 744）、元数据检查（余 488）、历史重放（钉住双仓库 commit、基础镜像 digest、依赖标识，在 Docker 里复现且诊断与阶段吻合）收敛到 113 个项目的 128 个可复现失败；三位作者按 Nourry 等人的根因分类学标注，校准集 Fleiss' κ=0.76。语言分布 C++ 45、JVM 21、C 19、Python 18、Rust 12、Go 11、Swift 2；编译（RC1，83 例）与依赖（RC2，29 例）合计占 87.5%。

### 5.3 解法：四组件协作的修复循环

FuzzMedic 用 Google ADK 实现、DeepSeek-V4-Flash 驱动全部代理（定位与执行类代理温度 0.0，反思类 0.2），每案 8 轮、1.5 小时预算。

**ECRCL（证据约束根因定位）**：把构建日志抽象成主故障区（最早致命诊断、滤掉级联），用空间相关（改过故障相关文件/构建配置/依赖声明的 commit）、时间邻近（故障前后一天内）与修复范围判定（上游源码还是下游配置工作区）构造候选集；在异构证据图上做 PageRank 式有界消息传播（阻尼 0.85、3 轮迭代，时间权重随 Δt 半衰），再用环境门控系数（与 sanitizer/架构/编译器/工具链的兼容性，二值）打分；取 top-1 做**反事实验证**——父版本能构建、重放候选复现同签名失败才算确认，全部失败则返回 UNKNOWN。**FGRK（失败引导修复知识）**：从 1,940 份候选记录经严格排除（评测项目全部 253 条、相关仓库与同源事件、来源审查）得到 110 个项目 188 次历史失败，LLM 辅助抽取加双人复核固化成 56 条模板（43 条错误模式 ERR + 13 条可复用准则 GL）——例如「Dockerfile 多源 COPY 缺目标路径末尾斜杠」这类跨项目复现的通用约束；检索按失败区域正则匹配，每提示最多注入四条。**RSMC（反思摘要与记忆固化）**：把每轮验证前后状态差分成「已解决症状/持续问题/下轮优先级」的结构化进展评估，压缩冗长日志为决策相关记忆，避免失败策略重复。**HSR（分层状态回滚）**：核心创新。修复过程在活工作区上进行且非单调，HSR 把每个已验证工作区状态记为修复状态图（RSG）节点——状态 = 六阶段（环境引导→依赖解析→插桩编译→fuzzer 链接→工件验证→运行时 fuzz 执行）中的阶段 L 加三项检查（list_fuzzers/check_build/run_fuzzer）的通过数 V；阶段推进或验证提升则接受，连续两轮中性（θ=2）或回退则物理回滚到支配祖先并重新定位根因。

### 5.4 评测数值与优势根源

**主结果**：128 案修复 62 例（48.44%），三次独立运行的均值、标准差 1.56 个百分点、95% 置信区间 [44.56%, 52.32%]。三个基线在同一 Docker 后端与 check_build 判据下：CompileAgent 27 例（21.09%）、SWE-Search 17 例（13.28%）、Agentless 10 例（7.81%）——与最强基线差 27.35 个百分点，且有 31 例是 FuzzMedic 独自修好、三基线全漏。等预算补充对照：统一 8M token/90 分钟上限下 FuzzMedic 59 例 vs CompileAgent 25 例（最低预算 1M/15 分钟则 CompileAgent 16 vs 11 反超——预算充足时结构化搜索优势才显现）；同模型同验证器同轮次预算的裸迭代代理在 64 案子集只修 4 例、FuzzMedic 35 例。成功案例成本：中位 1,874,876 tokens、22.96 分钟、平均 $0.3257，中位补丁只改 1 个文件 5 行。

**优势根源的因果链**：(1) **症状与根因的空间分离**是基线失败的主因——jimfs 的 Java 类版本不匹配日志像是 JDK 问题，真因是上游 errorprone 2.42.0→2.43.0 引入了不兼容该 JDK profile 的注解处理器；ECRCL 的反事实验证（父版本可建 + 重放复现同签名）把「看起来像」升级成「确认是」，补丁因此不盲改。(2) **工作区非单调性**是长程调试的杀手——toml_edit 案例要先修 Docker WORKDIR 冲突才能暴露 Rust 链接器对 __sancov_gen_* 符号的未解析，基线在两个失败间来回震荡、不保留已解决子问题；RSMC 记住已验证状态、HSR 在退化时物理回滚到支配祖先，保住了 checkout 进度。消融佐证：去 HSR 修复数 62→42（掉 20 例，最大单一组件），去 ECRCL 46、去 RSMC 51、去 FGRK 52，且任一组件移除都使成功案例中位 token 涨 1.24–1.48 倍——四个组件不是堆料而是互补分工。(3) **领域知识提供模糊特定的约束**而非通用构建编辑常识——FGRK 的 WORKDIR 规则、插桩符号约束在通用基线的知识范围之外。(4) 边界同样清晰：进入修复循环的失败尝试里 58.2% 连根因定位都没有；修复案例中根因定位成功率仅 38.71%——相当一部分成功靠验证反馈驱动的方法性修复而非精确诊断；50.0% 的成功案例发生过回滚。

**真实世界验证**：通过 oss-fuzz-gen 的 PR 实验机制集成，人类核验加维护者评审后合并 29 个补丁（28 个项目）：10 个修上游缺陷（34.48%）、19 个修 OSS-Fuzz 集成问题（65.52%）；含 3 个滞留一年以上的顽固失败（airflow 510 天、toml_edit 449 天、mdbook-i18n-helpers 470 天）与 2 个从未构建成功的案例（bc-gh、bazel-rules-fuzzing-test）。

### 5.5 知识反推

重做需要：**模糊测试基础设施**（OSS-Fuzz 工作流、sanitizer 插桩、引擎与架构配置、ClusterFuzz 生态）；**软件工程经验知识**（Sliwerski-Zimmermann-Zeller 的 change-inducing-fix 分析——ECRCL 两级定位策略的直接源头、git blame、git bisect 式反事实推理）；**图算法**（PageRank 式消息传播做证据一致性排序）；**长程 agent 工程**（状态图设计、支配关系与回滚策略、反思记忆的压缩、知识库的防泄漏隔离——FGRK 与评测集的项目级排除是评测有效性的生命线）。融合点在「把调试过程本身建成数据结构」：RSG 让「试过什么、哪条路死了」从对话历史变成可回退的图——这是把经典搜索思想（分支定界、回溯）移植到 agent 工作流的一次干净示范。

### 5.6 通用灵感

**灵感一：先确认因果再动手改**。反事实验证（回退到父版本能过、重放候选复现失败）是任何诊断类任务的黄金标准——从性能回归排查（这个 commit 真的是元凶吗）到营销归因（这个渠道真的带来了转化吗）。**灵感二：为非单调过程建显式状态图**。凡「修改会破坏之前进展」的场景（谈判、代码重构、实验科学），保存已验证状态的快照、定义支配关系、允许物理回滚，都远优于「在污染状态上继续修补」。**灵感三：领域知识蒸馏成小而严的模板库**。56 条人工复核的 ERR/GL 模板胜过泛泛的 RAG——关键在严格的适用条件标注与来源隔离（不许评测项目混入知识库），质量与纪律比规模重要。**灵感四：按阶段量化进展**。六阶段加三检查的 L/V 二元组把「修到哪了」变成可比状态，使「中性容忍 θ=2」这类精确的回滚触发成为可能——模糊的进度感是长程任务的大敌。

## 六、合读结论：系统级编码代理的五条公理

把五篇并置，可以提炼出关于「编码代理做系统级工作」的五条跨论文公理，每条都有至少两篇的独立证据：

**公理一：可见信号与真实目标的裂缝必须用执行来弥合**。CompressionBench 里 PPL 几乎不变的版本答案数在变（3.2572→3.2525 对应 111→115 题）；SWEOps-Bench 里 Fault Cleared 61.8%–72.7% 而 Fix-Specific Tests 只有 29.4%–58.8%；FuzzMedic 里可见编译错误的根因在另一个工作区。三篇的答案一致：验证必须执行、必须贴近部署条件、必须检查目标行为本身而非其代理指标。

**公理二：检测（或生成）不等于解决（或采纳）**。SWEOps 的检测 90.9% 对恢复 52.7%；Bloomberg 的 PR 生成远快于吸收（57.7%–67.7% 无决策）；ServerBench 的 33 运行 22 个通过验证但只有 13 个超最强基线。系统级工作的评测与运营都要为「最后一公里」单独建模——那往往才是瓶颈所在。

**公理三：反馈的类型与语境决定其价值**。ServerBench 用受控恢复实验证明工作负载语境的反馈翻转设计决策（1.13–1.31 倍价值差）；CompressionBench 证明完整模型反馈逆转 17/79 局部排序；Bloomberg 证明管线内验证深度预测合并率（34.2% vs 10.5%）；FuzzMedic 证明构建反馈加状态保持是修复的前提（裸迭代 4 例 vs 完整系统 35 例）。便宜的信号要先问「它到底测了什么条件」再决定信不信。

**公理四：努力与资源不线性兑换效果**。SWEOps 里 4–9 倍的 token 消耗换不来恢复率提升；CompressionBench 里最高 API 花费不对应最佳 PPL 排名；ServerBench 里 GPT 6.1 Sol 低价拿高分却在另一个部署翻车。系统级工作的回报由判断力（何时实验、信哪个信号、何时回滚）而非蛮力决定——这也是为什么五篇的作者都选择分析轨迹与决策而非只报分数。

**公理五：确定性边界是规模化与安全性的护栏**。Bloomberg 的准则「扩大 LLM 的生成角色、绝不扩大验证角色」在 8,600 仓库上验证；FuzzMedic 把验证交给 check_build 而非 LLM 判断；CompressionBench 与 ServerBench 的终审全部由独立验证器与人工复核执行。当错误能在舰队规模上复制时，验证权的外包成本不再是概率问题而是期望损失问题。

**知识反推的总纲**（跨五篇）：这一代系统级编码代理研究站在三块基石上——终端任务评测范式（Terminal-Bench/Harbor 的结果导向与容器化）、经典系统与软件工程智慧（SRE 生命周期计量、change-inducing-fix 分析、规则式大规模重构的经验与极限）、以及受控实验方法论（配对执行、惩罚式指标、等预算对照）。真正的新知识发生在三者的交叉处：把「实验判断力」「验证设计」「状态管理」这些原本属于人类工程师的隐性能力，变成可评测、可消融、可优化的显式机制。

**通用灵感的总纲**：如果只带走一句话，那应该是 ServerBench 与 SWEOps 共同示范、Bloomberg 与 FuzzMedic 在生产中付过学费的那条——**为你的自动化系统设计一个它骗不过的验证器，并让验证的成本结构与执行的部署条件同构**。做到了，代理的自主性就可以放心放大；做不到，再高的生成质量也只是把风险从生产侧挪到了接收侧。
