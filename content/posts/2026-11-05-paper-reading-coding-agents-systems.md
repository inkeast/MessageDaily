# 编码代理五连读：从压缩模型到修复模糊构建的系统级工作

## 〇、总览：当编码代理开始「经营系统」

### 0.1 评测重心的第四次迁移

过去两年，编码代理（coding agent）的评测重心经历了三次清晰的迁移：从函数级代码生成（HumanEval 时代的「补全一个函数」），到仓库级 issue 修复（SWE-bench 时代的「在真实仓库里改一个 bug」），再到终端环境里的多步骤任务（Terminal-Bench 时代的「在容器里干完一票活」）。每一次迁移都伴随着能力假设的升级：从「会写代码」到「会导航仓库」再到「会使用工具与执行反馈」。

而这五篇论文共同标记了第四次迁移的方向：**让代理接管那些传统上由系统工程师、SRE、平台团队、研究员承担的「系统级工作」**——压缩一个模型、设计一个推理服务系统、端到端解决一次云事故、迁移整个企业的代码舰队、修复持续模糊测试的基础设施故障。这些任务的共同特征是：没有现成的「正确答案」可以对答案，只有一组资源约束（存储、GPU、时间、人力）和一组必须独立验证的行为要求（准确率门、时延目标、恢复契约、可编译性）。

### 0.2 光谱的两个端点

五篇论文分布在这条光谱的两个端点上，恰好互补：

- **评测端（论文一、二、三）**：三个新基准分别把 LLM 压缩、推理服务设计、云 incident 解决形式化为「终端任务」（terminal task）——代理在固定预算内自由探索，最终由独立验证器裁决。这是 Terminal-Bench「以结果论英雄」范式向 AI 系统工程与 DevOps 领域的系统性扩张。值得注意的是，论文一与论文二同出 CMU InfiniAI Lab，共享同一套「固定任务 → 沙箱内代理设计 → 独立终审」的三段式协议骨架，可以视为一个评测研究议程的两翼。
- **落地端（论文四、五）**：两篇系统报告展示了同一类工作在真实世界里的形态。Bloomberg 的 Automated Uplift 在约 8,600 个仓库上跑了两个迁移战役，用的是「LLM 做有界变换、确定性系统做其他一切」的混合管线；FuzzMedic 则在 OSS-Fuzz 上修复真实构建失败并拿到 29 个维护者合并的补丁——包括三个滞留一年以上的顽固案例。

| 维度 | CompressionBench | ServerBench | SWEOps-Bench | Bloomberg Uplift | FuzzMedic |
|---|---|---|---|---|---|
| 任务 | 压缩 LLM | 设计推理服务 | 解决云 incident | 舰队级代码迁移 | 修复模糊构建 |
| 核心指标 | PPL 比 + 准确率门 | dollars per dollar | 分级恢复率 + 惩罚时延 | PR 合并率 | check_build 通过率 |
| 顶级数字 | 29/36 通过验证 | 4.87× 最强基线 | 52.7% 端到端恢复 | 2,333 PR / 729 合并 | 48.44% 修复率 |
| 最强配置 | Claude Sonnet 5.5 | Claude Sonnet 5.5 | Claude Code + Sonnet-5 | CMake 浅环战役 | DeepSeek-V4-Flash 全代理 |
| 最深洞察 | 似然≠能力保持 | 验证须匹配部署负载 | 检测≠恢复 | 生成≠吸收 | 症状≠根因 |

### 0.3 贯穿五篇的暗线

合读之后能看到一条贯穿五篇的暗线：**系统级工作中，「可见信号」与「真实目标」之间的裂缝无处不在**。压缩后的 PPL 几乎不变但答案变了（论文一）；开发环境的评分到最终重放暴跌（论文二）；症状清除但修复语义错误（论文三）；PR 生成了却没人合并（论文四）；编译错误在 A 工作区而根因在 B 工作区（论文五）。五篇论文的解法殊途同归：把验证做成独立、执行、贴近部署条件的闭环。下面逐篇精读。

## 一、CompressionBench：让编码代理自主压缩 LLM

### 1.1 背景：内存墙与递归自我改进的第一块踏脚石

LLM 推理正日益受限于内存带宽而非算力：自回归解码中每个 token 都要把权重从显存读一遍，而一次片外访存的能耗远高于它喂给的乘加运算（论文引 Horowitz 2014 的经典 ISSCC 数据）。压缩——在更小存储预算内保持模型行为——因此同时降低部署显存占用与每 token 能耗，让模型更便宜地服务、跑在更小的硬件上。

构造一个高质量压缩模型从来不是「选个位宽」那么简单。GPTQ、AWQ、SmoothQuant、OmniQuant 提供了校准驱动的舍入与缩放；QuIP、QuaRot、SpinQuant 通过旋转与非相干处理改进量化；QuIP#、AQLM、QTIP 发展格码与 trellis 表示；HAWQ 系做敏感度混合精度；剪枝与低秩方法删除参数。这些是「积木」，但没有任何单一方法能在任意存储限制与硬件目标下产出可用的模型——需要组合、实现、验证。这项工作恰好是编码代理日益擅长的那类「实验加系统」劳动，而且自带递归自我改进（RSI）意涵：会压缩模型的代理，能改进后续系统所依赖的模型效率，是「AI 改进 AI 基础设施」这条链条上一个可度量的环节。

论文定位明确：提出**第一个评测代理自主压缩 LLM 能力的终端任务基准**。与 KernelBench（评测单个 kernel 的正确性与速度）、MLE-bench（评测 ML 竞赛解题）、RE-Bench（评测研究工程）不同，CompressionBench 的独特性在于「数值近似的选择权」：代理必须自己选择、实现并验证一种表示，使生成的答案仍然有用。

### 1.2 问题定义：耦合的数值决策与不完整的反馈

论文开篇即指出自主压缩需要三种能力，这也是任务设计的出发点：

**其一，协调耦合的数值决策**。存储预算把表示、精度分配与参数保留绑成一个整体：花在一个组件上的 bit 不能给别处，剪枝释放字节但删除容量；即使在同一标称精度下，clipping、舍入、校准与元数据都改变表示质量。代理必须判断可行的组合，而非独立优化每个选择。

**其二，解读不完整的反馈**。权重重构误差、层输出误差、完整模型似然、生成答案准确率各回答不同的问题——改善局部近似的改动可能损害完整模型，微小的似然收益可能掩盖生成回退。代理必须判断何时廉价的局部证据够用、何时值得花预算跑完整模型实验。

**其三，协同设计高效执行**。压缩只有在解包、重构与索引不抵消内存流量削减时才真正省资源；持久化的反量化副本会吃掉驻留存储节省。代理必须实现适配目标硬件的推理路径并验证其正确运行。

任务四元组：源检查点（含 tokenizer）、存储上限 C、GPU 与固定运行时（vLLM 0.32.0）、墙钟预算 T（8 小时）。代理在离线容器中工作——只读源权重、起步推理代码、可检索的压缩论文、校准与恢复数据（FineWeb、UltraChat-200k、WikiText-103）、独立的本地测试题（MATH-500）。候选 a = (W, I) 由压缩权重加推理实现组成，共同定义可执行模型 q_a。

优化目标形式化为：**minimize Δ̂(a) = Ĥ(q_a) − Ĥ(p)**，约束为包存储 S_pkg(a) ≤ C 且驻留存储 S_res(a) ≤ C。似然在源模型采样的续写上计量：每个数据集含 256 个 512 token 上下文（Dolma 3 Dolmino 混合），BF16 以温度 1 采样 1,536 token 且不做概率截断，两模型对同批 token 计分。奖励是 PPL 比值 F = PPL(p)/PPL(q_a) = exp(−Δ̂)（其期望恰等于平均 next-token KL 散度），执行成功且双存储达标时奖励 10F、否则记零。解码速度单独上报、不进奖励——把压缩质量与执行效率刻意分开。

三个关键的评测设计决策值得单独点出：

- **双存储口径**：包体积（权重加代码加 tokenizer 资产）与服务时驻留权重（含 scale、codebook、padding、持久化反量化副本；KV 缓存与临时工作区不计）分别检查。附录 D 交代了由来：试点实验发现 QTIP 试点包仅 6.96 GiB 但执行时保留 BF16 权重，多个代理试点也保留高精度副本——「小包大跑」的口径套利必须被规则堵死。
- **预算共享**：评估调用与构建消耗同一个 T。搜索期似然集与验证集用不相交文档、匹配源比例。代理必须判断「再跑一次完整模型实验值不值」——这正是 MLAgentBench/RE-Bench 式「预算化实验」设定的延续。
- **独立终审**：冻结产物在全新容器里用不相交数据复测。答案准确率门用 GSM8K（4-shot、320 token、终数判断）、HumanEval（0-shot、384 token、单测）、TriviaQA（5-shot、24 token、别名归一化）各 50 题，均值 ≥ BF16 参考的 80%（阈值在搜索前设定且对代理保密）。审查检查完整性：token 与概率必须来自提交的前向计算、未缩放的 logits、模型存储核算、外部权重、硬编码输出、概率或时序测量操纵。

### 1.3 解法：任务矩阵与两个完整压缩策略

实验设置：三个源模型刻意覆盖两种架构与两档压力——两个 MoE（Nemotron-3.5 Super VL 120B-A12B、Qwen3.5 122B-A10B，各配 32/48 GiB 双档）与一个 dense（Qwen3.8 27B，配 8/12 GiB 双档），共 6 个任务。档位由试点测量校准：宽松档允许 4-bit GPTQ 加组或 damping 精修；紧张档使低位表示与精度分配变得关键。六个代理：Claude Sonnet 5.5、Claude Opus 5.5、GLM 5.3、Kimi K3.1 Pro、MiniMax M3.1 Flash、DeepSeek V4.1 Flash 1017，统一用 Claude Code 挂最大推理力度、单张 H200 NVL、每对代理-任务只跑一次。基线两层：均匀 GPTQ（组 128、128 条校准序列，选能装进包限制的最大一致位宽、嵌入与输出头吃剩余空间）与已发布量化（Nemotron 用 Unsloth Dynamic UD-IQ2_XXS、Qwen3.5 用 Unsloth Dynamic、Qwen3.8 用 GSQ-RCO）。

论文用两个案例把「数值设计到执行」的完整链条摊开：

**Sonnet 压 dense Qwen3.8 到 12 GiB**：核心是 Hadamard 旋转加格码（trellis codes）替换标量 GPTQ，配误差补偿与 Viterbi 搜索；矩阵实验帮助选表示，KL 消融拟合出损失模型指导位宽分配（mixer 3.8–4.5 bit、MLP 3.7–3.8 bit、嵌入 3–6 bit、头 3–8 bit），token 频率指导嵌入与输出头精度；表示与分配变化产生最大奖励增益，校准精修其次。两个「负结果」同样重要：实测 KL 变差就否决 Fisher 加权分配；更大格码重构收益甚微且搜索成本高，就保留小的。执行侧按需从格码重构权重 tile，避免整矩阵驻留。最终 PPL 3.253、三基准均值 76.67%——两项都超过 BF16 参考的成对复测（3.221/74.00%）。

**Opus 压 MoE Qwen3.5 到 48 GiB**：旋转 GPTQ 加专家间差异化位宽（48 层 × 256 专家、attn 4–8 bit、router 共享 8 bit）。最有教学价值的是它的验证演化：起初按局部证据偏好给前层更多精度，把本地验证改为评模型生成续写后，转向后层——这个分配随后被奖励反馈确认。在紧张档上它花 1.7 小时探索 1-bit 专家层：局部似然偏好新候选、完整模型反馈偏好旧分配，Opus 恢复并精修了旧分配。最终 PPL 2.818、准确率 82.67% vs BF16 的 2.755/84.67%。

### 1.4 评测数值：主表、基线对比与失败形态

**主结果**：36 份提交 29 份通过验证。宽松档 18/18 全过；紧张档 11/18 过——6 个倒在答案准确率门、1 个（MiniMax 在 Qwen3.5 32 GiB）在答案生成中超时。每任务取最低 PPL 代理产物，平均比 BF16 PPL 高 3.4%，下游准确率 77.33% vs BF16 79.56%。

紧张档主表节选（PPL ↓ / 准确率 ↑ / TPS ↑）：

| 方法/代理 | Nemotron 32G | Qwen3.5 32G | Qwen3.8 8G |
|---|---|---|---|
| BF16 | 1.688 / 80.00 / 147.5 | 2.755 / 84.67 / 158.3 | 3.221 / 74.00 / 61.4 |
| 均匀 GPTQ | 4.680 / 5.33 / 20.9 | 7.185 / 6.00 / 26.4 | 7.480 / 4.67 / 12.6 |
| 发布量化 | — | 2.900 / 83.33 / 122.9 | 3.764 / 65.33 / 75.5 |
| Sonnet 5.5 | 1.801 / 76.67 / 57.2 | 2.883 / 78.67 / 39.8 | 3.363 / 68.67 / 23.4 |
| Opus 5.5 | 1.811 / 85.33 / 48.6 | 3.003 / 76.67 / 73.2 | 3.370 / 66.00 / 26.2 |

**基线对比的三个层次**：(1) 均匀 GPTQ 在 6 个设置中 4 个过不了答案门——最惨的 Nemotron 32 GiB 档 PPL 4.680、准确率 5.33%，同任务 Sonnet 做到 1.801/76.67%；它只在宽松档的 MoE 任务上通过。固定配方只覆盖任务套件的一部分。(2) 已发布量化是更强的参照：最强代理产物按 PPL 在全部 5 个可测发布参考上更优（Qwen3.8 8 GiB：Sonnet 3.363 vs GSQ-RCO 3.764）。但准确率维度出现分化——紧档 Qwen3.5 发布版准确率反超最低 PPL 代理产物，PPL 与答案准确率共同决定「你会选哪个工件」。(3) 存储与质量的错位：Sonnet 的 8 GiB dense 模型 PPL 低于三个代理的 12 GiB 模型——更好的表示可以超越额外存储。

**失败与浪费的形态**（论文第 4 节的轨迹分析是全文最精彩的部分）：

- **生成回退潜伏在似然之下**：Opus 紧档 dense 运行里，分配加蒸馏把验证 PPL 增量从 6.17% 一路压到 5.89%、5.00%、4.64%，GSM8K 却从 88% 掉到 72%（HumanEval 与 TriviaQA 同期上升）；四个运行十二对相邻版本显示小幅 PPL 变化下既有新答对也有新答错。剪枝的 GLM/MiniMax 模型产出重复或截断的 HumanEval 补全，而 BF16 的错误多是能跑但没过测试的程序。
- **检测到失败与修好它是两回事**：MiniMax 的本地推理测试在 MLP 宽度剪枝后显示大损失（相对未剪 3-bit 参照），GLM 的专家剪枝候选在 MATH-500 上同样欠佳，两者都测了替代方案却保留了剪枝——没找到可行修复。Opus 在蒸馏期间测过生成，但最后几个 PPL 导向的改动没重跑同样的生成测试。轨迹暴露两个独立要求：找到修复已知问题的候选，以及让测试与最终提交的工件保持同步。
- **执行 bug 的一则正面案例**：MiniMax 在 Nemotron 上对比批量与逐专家推理的 token 概率，分歧暴露一个专家索引 bug；修复把反馈 PPL 超出 BF16 的比例从约 11% 降到 4.5%，最终通过验证——表示不动、只修执行。
- **停止行为**：17 个运行在代理首次声明「完成」后又改了权重（Kimi 5 次、Opus/DeepSeek 各 4 次、Sonnet 0 次）；「声明完成」与「最后一次有效改动」是两回事。GPU 繁忙占比中位数 30%–60%，更高占比对应更低 PPL，但更多工具调用本身不带来收益。

### 1.5 优势根源：为什么代理能打赢固定配方

**因果链**（每环都有轨迹证据）：

1. **表示设计在固定存储下创造空间**。位宽定死码本数量，clipping 与 rounding 决定这些码如何逼近权重与激活。24 次等存储修订（包体积变化 ≤0.01 GiB）里 21 次降低反馈 PPL，覆盖全部六代理六任务；Kimi 在紧档 Qwen3.5 上只改 clipping 与 GPTQ damping 就把反馈 PPL 从 3.738 压到 3.132；配对消融固定精度分配、校准与推理实现，只把 GLM 的 MSE 选定 clipping 换成 min-max，选定范围在更低验证 PPL 与更高答案准确率上全胜——且两变体占用完全相同的存储。与只选位宽的固定配方（GPTQ）拉开差距的根源就在这里。
2. **实验判断力改变选择**。权重 MSE 对重构误差一视同仁，线性输出 MSE 按校准激活加权，完整模型 PPL 度量所有层组合后的行为——三种准则在相近编码尺寸下偏爱不同修订（k-means 码本权重 MSE 更优但 PPL 更差，GPTQ 舍入相反）。79 次配对比较中完整模型反馈逆转 17 次先前的局部排序，八次导致显式回滚（Kimi 五次、DeepSeek 三次）。
3. **元数据与权重的预算竞争**。Kimi 压缩 dense 的组 scale 存储来装更多 4-bit 权重；DeepSeek 提高 Nemotron 非专家精度；Opus 给 Qwen3.5 后层专家更多精度。分配必须把量化器开销与名义位宽一起算。
4. **验证的必要性来自结构而非流程**：搜索期反馈只用似然，答案门在终审才出现、阈值保密——这个信息不对称的设计保证了「为评分而优化」不可能伪装成「为能力而优化」。

**边界与诚实声明**：论文明确报告 Sonnet 的 dense 宽松档工件在 PPL 与准确率上都超过 GSQ-RCO 发布件，但解码只有 16.7 tokens/s 对发布件的 74.6——存储-质量收益不自动兑现成速度，表示与 kernel 必须一起考虑；TPS 同时反映提交的 kernel 实现与反量化开销。这是对「压缩即加速」这一常见误解的当场纠正。

### 1.6 知识反推：重做这项工作的最少知识集

假设让一个零基础的人在一年内重做 CompressionBench，最少需要：

- **量化与压缩理论**（领域知识层）：GPTQ 的 Hessian 加权误差补偿、AWQ 的激活感知缩放、Hadamard 旋转与非相干处理（QuaRot/SpinQuant）、格码与 Viterbi 解码（QTIP）、敏感度引导混合精度（HAWQ-V2）、剪枝（SparseGPT/SliceGPT）与蒸馏恢复。不需要能发明新算法，但需要能判断「什么组合在什么存储档位下有戏」。
- **存储与推理系统知识**：包体积 vs 驻留存储的口径、持久化反量化副本的影响、vLLM 的权重布局、batch-one 解码的时序测量（128 token 首末间隔取 127/L、三轮三请求取中位）。
- **实验方法论**：KL 散度与 PPL 比值的数学等价（E[Δ̂] = E[D_KL(p‖q)]）、局部指标与全局指标的分歧来源、预算 constrained 实验设计、配对消融的控制变量。
- **终端任务评测工程**：Harbor 容器化、冻结终审、防作弊的存储核算与完整性审查、搜索/验证数据的分离。

**融合的关键节点**：最难的一步不是以上任何单项，而是把「压缩算法研究」翻译成「代理可探索的决策空间」——论文不规定流程、只固定目标预算与验证，这要求设计者对哪些自由度真正影响质量有深刻直觉（哪些留给代理、哪些钉死在协议里）。双存储核算与答案门保密这两条规则，都是设计者预判了作弊路径后的产物。

### 1.7 通用灵感

**灵感一：奖励只测一个量，验证必须测另一个正交的量**。PPL 度量分布保真，答案门度量能力保持，二者在轨迹上明确分离。推广：任何「单一指标上线」的自动化系统——代码生成用通过率、翻译用 BLEU、客服用解决率——都值得问一句：我的指标与真实目标之间的可操纵缝隙有多宽？在缝隙里藏着的失败（重复循环、截断输出）往往只有执行目标行为才能暴露。

**灵感二：把「预算共享」作为评测与组织设计原则**。评估调用消耗同一个时间池，逼出「实验判断力」这一通常被隐藏的能力。推广到人类组织：审批资源与执行资源同池核算，才能看出谁真的会做实验、谁在用评估逃避交付。

**灵感三：规则要堵住「小包大跑」式的口径套利**。双存储核算的教训是：任何资源约束都要覆盖「持久占用」而不仅是「申报体积」。云成本核算看常驻实例而非只在采购单、碳排放核算看持续排放在而非仅运输里程——口径即激励。

**灵感四：声明完成不等于完成**。17 个运行在声明完成后继续改权重、且这是普遍行为而非个例——自动化系统的「完成信号」需要用「最后一次有效变更」来校准，这对 agent 工作流的状态管理与人类项目的收尾检查同样适用。

## 二、ServerBench：让编码代理设计专用推理服务系统

### 2.1 背景：自指的机会与三个评测缺口

LLM 编码代理的工作流本身跑在 LLM 服务系统上，这带来一个自指的机会：代理能否设计支撑自己运行的服务系统？AlphaEvolve 用评估器反馈改进算法与基础设施、Vortex 让代理在可编程服务系统里生成稀疏注意力算法——代理驱动的系统优化已成气候。但现有推理性能基准有三个被论文明确点名的缺口：

**缺口一：工作负载过度简化**。既有基准发独立请求或固定 prefill/decode 场景。请求长度一致、批次固定时，静态批处理几乎和生产引擎一样好，连续批处理与 paged attention 的价值测不出来。而真实编码代理的负载是：短长请求混合、多轮共享上下文增长、并行子代理分支扇出——前缀复用、内存管理与 prefill-decode 干扰在这里才塑造性能。

**缺口二：目标只有加速比**。既有基准按相对基线的 speedup 或 throughput 计分，忽略时延要求与 GPU 成本、固定供给负载。而服务提供方真正要决定的是：在 TTFT/TPOT 达标的前提下接多少负载——这是容量与准入的联合决策。

**缺口三：验证只查正确性**。对照参考实现或测试套件不够。服务系统还必须在部署负载上满足尾延迟目标、完整执行工作负载；投机解码、状态复用、自定义调度引入的执行路径，短促孤立的测试根本不碰。

ServerBench 同时补三个缺口，是第一个评测「代理设计完整服务系统」的基准，与 CompressionBench 构成 InfiniAI Lab 的姊妹工作（作者高度重叠、协议同构）。

### 2.2 问题定义：dollars per dollar 与有状态闭环重放

任务固定模型检查点、GPU 配置、编码会话工作负载与服务要求（TTFT 目标 τ_first、TPOT 目标 τ_token、固定 token 价格）。代理从最小 Transformers 服务器 S₀（全局请求锁、无跨请求前缀缓存）出发，在开发预算 B 内产出实现 S_B 与会话并发 c_B——既造引擎又选负载。可以重设计执行、批处理、内存管理、调度与状态复用，但检查点、精度与推理语义钉死。

**目标函数 dollars per dollar**：对请求 i，客户端实测输入输出计数 x_i、y_i 给出价值 v_i = (p_in·x_i + p_out·y_i)/10⁶；q_i = 1 当其有限 TTFT 与 TPOT 都达标。系统得分 D = Σq_i·v_i / (d·r·(W/3600))——合格 token 价值除以测量窗口的 GPU 成本。可分解为 D = G·f：总价值 G 乘以价值加权合格率 f。例如 3.65 美元合格价值除以 0.83 美元 GPU 成本得 4.40。缓存前缀按完整输入价计价一次。这个目标天然奖励「容量提升与负载选择的协调」：多接会话只在整个时延达标时增收。

**时延校准**：开发开始前，用 SGLang 各模型的 cookbook 配置在参考工作点上多次重放，τ_first = max_j a_j、τ_token = max_j b_j（取多次重放 p90 的最大值以给运行间变异留余量），然后冻结为逐请求目标。

**有状态闭环重放**：用 AgentX harness（SemiAnalysis）重放记录的编码会话——请求长度、多轮结构、共享前缀、并行子代理分支与轮间时延（全局空闲期压缩封顶 10 秒）。请求等待它依赖的响应，服务时延因此决定窗口内推进多少工作。隐私保护式重建替换提示与工具内容但保留长度、前缀与拓扑。开发与终评用不相交种子。

**验证协议**：终评在全新部署重建提交系统、用不相交种子重放。检查覆盖：完整提示、规定输出长度（定时重放禁 EOS 以生成规定长度；单独的 EOS 探针测自然停止）、流式一致性、对检查点的生成保真（最多抽 16 条疑似续写做 teacher forcing、每 token 对数概率后悔容忍上限 4.0）、held-out 20 题答案准确率（较朴素实现最多降 0.1、按 k_cand ≥ max{0, k_ref − ⌊0.1n⌋}）；再加运行后审查——审查代理加人工检查提交代码与记录行为，查检查点保真、推理语义、工作负载执行与禁止捷径，可以推翻自动失败、也可以抓行为测试漏掉的违规。

### 2.3 解法：实验设置与代理环境

三个部署：Qwen3.5 9B（2×L40，上下文 1M，输入 $0.1044/M、输出 $0.1855/M）、Gemma-4-E4B-it（1×L40，131k 上下文，$0.02/$.10）、Qwen3.8 27B INT4（2×L40，1M 上下文，$0.0898/$2.657——输出价高两个数量级，因为 INT4 权重要生成昂贵长答案时每 token 价值高）。GPU 成本统一 $0.82/GPU 时。时延目标分别冻结在 TTFT 4.10s/TPOT 23.5ms、2.53s/121.7ms、10.30s/48.4ms。

十一个代理模型：Claude Opus 5.5/Sonnet 5.5/Opus 5、GPT 6 Astra/6.1 Sol/6 Sol、Kimi K3、Qwen3.8-Max-0902、MiMo V2.6 Pro、GLM 5.3、DeepSeek V4.1 Flash。GPT 系挂 Codex、其余挂 Claude Code（都最大推理力度），在无网 Harbor 沙箱里每对代理-部署一次 8 小时开发加 1,800 秒终评重放（明显异常失败允许至多一次重跑）。基线 SGLang v0.5.19 与 vLLM v0.28.0：SGLang 用各模型 cookbook 配置、按最大化总价值选并发；参考结果取 5 个独立种子均值。三个部署的最强基线分别是 SGLang 1.62（Qwen3.5 9B）、vLLM 0.61（Gemma E4B）、vLLM 1.47（27B INT4）。

发布与测量分离：代理「发布」一个版本冻结实现与并发，与「测性能」是两个操作；预算耗尽时最后发布的版本成为提交。

### 2.4 评测数值：主表与三个分析发现

**主结果**：33 个运行 22 个产出通过验证的系统、13 个超过最强基线。分部署看（合格 $/$ @ 并发 c，附 p90 TTFT/TPOT）：

| 代理 | Gemma E4B（基线 0.61） | Qwen3.5 9B（基线 1.62） | Qwen3.8 27B INT4（基线 1.47） |
|---|---|---|---|
| Claude Opus 5.5 | 2.47 @40 | **4.40** @16 | **2.64** @8 |
| Claude Sonnet 5.5 | **2.97** @32 | 4.34 @20 | 2.01 @12 |
| GPT 6 Astra | 1.75 @32 | 3.18 @12 | 1.48 @4 |
| GPT 6.1 Sol | 1.59 @24 | 2.84 @4 | 0.98 @4 |
| Claude Opus 5 | 1.15 @24 | 1.16 @1 | 0.62 @6 |
| Kimi K3 | 0.52 @6 | 0.93 @1 | 未通过 |
| GLM 5.3 / DeepSeek | 未通过 | 未通过 | 未通过 |

Claude Sonnet 5.5 在 Gemma E4B 达 2.97，是 vLLM 基线 0.61 的 4.87 倍；Claude Opus 5.5 在 Qwen3.5 9B 达 4.40（SGLang 的 2.71 倍）、在 27B INT4 达 2.64（vLLM 的 1.80 倍）。但分布不均：六个模型三个部署全部通过验证，只有三个（Opus 5.5、Sonnet 5.5、GPT 6 Astra）在全部部署上超过最强基线。GPT 6.1 Sol 在 9B 上拿 2.84、在 27B INT4 上却只有 0.98——低于 1.47 的基线。价值与成本的分解同样有信息量：Qwen3.5 9B 终评上 Sonnet 5.5 产出的总价值（6.42）高于 Opus 5.5（5.56），但合格份额更小，最终 4.34 对 4.40——「多接」与「接得住」的张力直接显形。API 花费与成绩也不对齐：Opus 5.5 单次开发约 $100–105，GPT 6.1 Sol 约 $13 却能在 9B 拿 2.84。

**发现一：高价值设计先升能力再逐步加载**。并发轨迹分四类：raise-and-hold（逐步加载后稳住）10 个里 9 个超最强参考、10/10 通过验证；retreat（一路下调）4/7 通过；oscillate 4/7 通过；never-tuned（从未调载）0/6 超参考、3/6 通过。超基线两倍以上的组 17 次负载决策有 7 次带来后续价值提升，低于基线的验证运行 23 次里只有 2 次。高分组在 median 0.90 小时跑通首个可用端到端重放（1–2 倍组 2.05 小时、低于基线组 2.96 小时）——早测量留下更多时间做能力开发。受控对照：16 会话下 Opus 5.5 的 Qwen v1→v2 重设计在匹配种子上提升价值 1.32–1.88 倍；冻结的 Gemma 系统上 Sonnet 5.5 从 2 会话的 1.30 升到 32 会话的 2.97。高分系统普遍组合更多服务优化——投机解码、延迟感知调度、主机内存状态存储；跨轮复用则人人都有。决策方式也成熟：Opus 5.5 用负载模拟器指导 Qwen 加载测试、20 会话重放总价值更高但合格率只有 64% 后保留 16；Sonnet 5.5 在 Gemma 上固定种子对比 36 对 32 会话，36 总价值更高但 TPOT 未达标更多，提交 32。

**发现二：反馈要在工作负载语境里解释**。超基线两倍组 49% 的保留决策有工作负载相关的改进验证（失败组 25%、未验证决策占 40%）。最漂亮的对照是 prompt-lookup 投机解码：Opus 5 用随机文本合成探针得 null 结果就放弃了；Opus 5.5 用 60 条重放回复追查初测 null、修好模拟器，测得每步接受 2.09–2.34 个 token 才采用。修正后的交叉实验（131 请求、K=7）：真实提示+真实回复每步发出 2.635 token，全合成只有 1.244——同一优化在合成文本上看起来没用。论文进一步从同一检查点恢复 Opus 5 各跑两小时（有/无自己重放回复的反馈）：只有反馈臂重新采纳投机解码，其提交服务器在两个新鲜公共种子上合格价值高 1.13–1.31 倍。反向教训也有：一次 Opus 5.5 的 27B 运行把并发从 10 升到 16 并改调度，看到分数从 2.20 涨到 2.99 就保留；临近截止时一次调度修复还在预热，于是回到那次 900 秒重放支撑的配置——终评同一实现合格份额从 76.0% 崩到 16.8%、分数 0.48。事后 CPU 扫描 128 个额外种子只要 7.71 秒就发现：开发抽签处于初始流可用性的第 4 百分位（异常轻载）、终评抽签在中位——便宜的工作负载画像本可避免昂贵误判。

**发现三：验证必须匹配部署工作负载**。33 个提交里只有 5 个记录过负载或长上下文下的自然停止检查。三则案例：Qwen3.8-Max-0902 收紧准入保护 TPOT 后只测了短提示和一次 11 请求重放，提交的政策让一段范围内的提示长度永远进不了执行队列，终评在一个 315K token 输入上停摆——短测试没查准入策略的提示长度边界。Kimi 的重放暴露前缀缓存异常加数值错误，修好数值路径、用新引擎重测孤立长提示通过；但对提交缓存的检查首次插入成功、同一前缀第二次插入即崩溃——孤立测试漏掉跨请求复用，该异常在终评复现。正面案例是 Opus 5.5 在 Gemma 上：加入抢占与缓存恢复协调 TTFT/TPOT 后，主动收缩缓存容量逼出这些路径执行，压力测试暴露未初始化缓存存储产出无效输出（缺陷早于抢占改动就存在）；修复后强制抢占复跑、恢复输出与孤立执行对比、减池复制 3/3 通过（回退修复则 0/3）——把「设计引入的执行路径」变成必测项并随修复重跑。

**窗口与抽样敏感性**：300 秒窗口的分数平均是 1,800 秒的 1.42–1.70 倍、900 秒为 1.04–1.21 倍；Opus 5.5 在 Qwen 上把窗口从 300 拉到 1,800 秒使跨种子变异系数从 0.37 降到 0.19——中等长度重放可指导开发，最终结论要靠长窗口。

### 2.5 优势根源与边界

**因果链**：目标函数设计是根。dollars per dollar 把「容量」与「合规」做成乘积，超载立即清零收入——这解释了为什么 raise-and-hold（先建能力再加载、过载即收敛）优于盲目加载；把并发选择权交给代理，等于把运筹学里的准入控制变成被评测的决策。反馈解释是第二环：合成探针与真实回复的差距（2.635 vs 1.244）说明「测什么条件」比「测多少次」重要。验证设计是第三环：全新部署加不相交种子使「开发态过拟合」（记忆了的负载条件、热身后的缓存）不可迁移。

**论文自报的边界**（值得尊敬的诚实）：仅三个部署、一个编码轨迹源；闭环重放不同于开环生产需求；相关性分析与源检视不建立因果优化效应；固定价格 token 价值度量部署效率而非实现利润；校准依赖参考引擎。

### 2.6 知识反推

重做这项工作需要：

- **推理服务系统全景**（领域知识层）：Orca/vLLM 的调度与内存管理、SGLang/Preble 的前缀复用、Sarathi-Serve/DistServe 的分块 prefill 与预填充-解码分离、投机解码的接受率经济学；MLPerf Inference 的标准化传统。
- **服务质量与计价知识**：p90 分位数目标、SLO 满足率、token 计价、GPU 时成本；「合格产出」（goodput）概念的谱系。
- **负载建模与统计**：会话依赖、闭环重放、种子间变异、观察窗效应、工作负载画像（初始流可用性这类分布特征）。
- **代理评测工程**：Harbor 沙箱、发布/测量分离、行为检查+人工复核的双层验证、重建可复现记录（检查点、语料修订、环境快照、提交工件、并发、种子）。

**融合的关键节点**：与 CompressionBench 一样，难点在「把系统设计翻译成决策空间」。ServerBench 的独特选择是让代理自选并发——把「实现能力」与「经营判断」放进同一个被测对象，再用 G·f 分解把它们在结果里分开。这个「合成目标可分解」的技巧是评测设计的通用手法。

### 2.7 通用灵感

**灵感一：把「单位成本的价值」而不是「峰值性能」定为优化目标**。dollars per dollar 天然惩罚超载。推广：推荐服务看「合格 QPS/机器成本」而非裸 QPS；销售团队看「成交线索/人力成本」而非线索量；模型服务看「达标请求/token 成本」而非吞吐。凡有质量门槛的地方，分子都该过滤、分母都该真实。

**灵感二：验证清单是设计的函数**。每引入一个新机制（抢占、缓存复用、准入）就生成一条只在特定条件下才走的执行路径。推广到任何演进中的系统：安全审查、回归测试、合规检查的覆盖面都应该跟着「这次改动新增了哪些路径」动态扩展，静态核对表注定过期。

**灵感三：便宜的工作负载画像防止昂贵的误判**。7.71 秒的 CPU 扫描能发现开发抽签处于第 4 百分位。推广：A/B 决策前先看分布而非均值；模型评测前先查数据集的难度分层；任何「单次实验定结论」的场合都先问这次抽样处于分布的什么位置。

**灵感四：null 结果先问测试条件，再下结论**。Opus 5 因为合成探针放弃了真实负载下有效的优化——「这个优化没用」和「这个优化在我测的条件下没用」是两个命题。评审、面试、市场验证里同样如此。

## 三、SWEOps-Bench：评测代理端到端解决软件引发的云事故

### 3.1 背景：开发与运维的边界消融地带

云上 incident 一旦源于软件缺陷，解决它就要同时动用运维调查（看集群状态、看控制器日志、探测端点）与代码修改（改控制器源码、重建镜像、滚动更新）——这正是自主代理兴起后开发与运维边界消融的地带。Kubernetes operator 是代表性场景：自定义资源加专用控制器、按状态调和原则持续运行，控制器逻辑的缺陷直接损害被管理的工作负载——一个 Redis operator 的缺陷可能让生成的 Pod 规格引用未定义的卷，K8s API server 拒绝该规格、集群无法完成初始化；失败表现在运行时资源上，而缺陷藏在 operator 实现里。

现有基准各覆盖一角（论文 Table 1 的对照表很清晰）：云运维基准（OpsEval 的 curated 问答、AIOpsLab/ITBench/SREGym/Cloud-OpsBench/RCAEval 的 demo 微服务注入故障）不要求在原始仓库里修历史缺陷、不验证部署后恢复；软件工程基准（SWE-bench 的静态 issue 修复）没有运行时发现与部署验证。SWEOps-Bench 填补「运行时检测 → 根因定位 → 源码修复 → 部署 → 恢复验证」全生命周期，且全部任务来自确认过的真实历史缺陷。

### 3.2 问题定义：四项设计要求与两阶段筛选

论文提出四项设计要求（R1–R4），是这类「真实感基准」的模板：**R1 运行时发现**——代理必须从活集群观察中独立发现异常，没有预打包的 issue 描述，还要先辨别健康基线；**R2 可部署源码修复**——修的是缺陷实现而非运维 workaround，候选修复要进原生构建流程并部署到活集群获得反馈；**R3 验证过的功能恢复**——症状消失不等于解决（表面补丁或 Pod 重启能掩盖失败、引入回归），验证结合案例特定的故障 oracle 与端到端管理检查；**R4 端到端生命周期评测**——统一协议覆盖检测、诊断、修复、验证，暴露回溯行为与时延/token 成本。

**基准构建**走两阶段筛选。第一阶段（候选收集与排除）：从 Sieve、Acto、Oat 等控制器可靠性研究及 2026 年 1–8 月合并的 maintainer 确认 bug 修复 PR 收集候选（新缺陷挖掘降低预训练暴露窗口）；按 E1 无可验证合并修复（或修复被 revert）、E2 范围外（改的是文档/注释/第三方部署工具/被管应用而非 operator 实现或配置）、E3 重复或重建受限（需不可得的专有服务）排除。第二阶段（环境重建与执行验证）：钉住受影响源码版本、K8s 发行版、容器镜像、依赖与部署清单，重建隔离环境并配案例特定的触发工作负载；配对执行 buggy 与 fixed 版本，按 E4 引导失败（到不了健康初态）、E5 不可观察（无运行时表现）、E6 不可复现排除。1,820→128 的漏斗（去重 1,076、元数据 256、历史重放 360）产出 55 个任务——28 个来自既往研究、27 个来自 2026 年新收集。

**任务分布**：16 个 operator 项目覆盖分布式数据库（CNPG/PostgreSQL 9,374 星、MongoOp、RedisOp、CassOp）、存储（Rook/Ceph 13,670 星）、可观测（PromOp、VMOp、GrafanaOp、OTelOp、LoggingOp）、消息（RabbitMQOp）、流处理（SparkOp）与 serverless（KnativeOp）。缺陷机制六类：Construction 15、Defensive Handling 13、Input Validation 10、Control Logic 9、Lifecycle/Ownership 5、Admission Policy 3；运行时表现五类：Workload degraded 19、Operator crash 17、Resource rejected 9、Operator-reported 5、Storage blocked 5。

**评测协议**：会话分两幕。第一幕健康基线（60 分钟预算）——阴性对照检验误报；第二幕触发故障后（独立 60 分钟预算、全新会话上下文），代理经 bash 终端用 kubectl 与 Unix 工具查系统、读写本地仓库；提交修复时 harness 编译、重建控制器镜像、部署进集群并回传执行反馈（编译错误、rollout 失败），文件修改、运行日志与集群状态在会话内持续留存。出站网络禁用，issue 讨论、参考修复与验证脚本对代理全程保密。

### 3.3 解法：oracle 构造与指标体系

**三段 oracle**：检测用案例特定故障探针（由 buggy/fixed 差分行为导出，查资源条件、事件日志或服务端点），最早确认表现确立 TTD 参考时间戳；RCA 标注来自 maintainer 确认的 issue 报告与合并修复（修复 commit 里的辅助改动不自动算根因位置），文件级与函数级（配置类 incident 查配置文件）；补救用可执行检查——构建部署成功、目标故障消除（故障 oracle）、fix-specific 功能测试（触发条件下检验受影响能力）、回归套件（改造自上游 PR 回归测试与项目集成套件，经 buggy/fixed 差分执行确认）。关键取舍：这些检查评估修复实现的运行时行为而非与开发者补丁的文本相似性——接受替代的有效修复、同时确保症状消除不以牺牲必要功能为代价。

**指标体系**：检测三率（Healthy/Faulty/Paired——Paired 要求同一任务两幕判断都对，专罚「永远正常」与「永远报警」）；RCA 三级（File/Func/Joint）；补救七项（Build/Deploy/Patch Check/Fault Cleared/Regression Tests/Fix-Specific Tests/Agent-Declared Recovery，整体恢复 = 预算内显式声明 + 除 Patch Check 外全部适用检查通过）；时延四量（TTD/TTI/TTRem/TTR）用惩罚式计量——未达成的检测、识别、补救里程碑分别罚 B/3B/6B 分钟，验证恢复的任务保留实测 TTR，三项全缺罚满 10B。

**实验配置**：6 个代理-模型配置——Codex 与 Claude Code 两个终端 harness × GPT-5.6 Luna（2026-07-09）、Claude-Sonnet-5（2026-06-30）、DeepSeek-V4.1-Flash（2026-09-10）、GLM-5.3-Flash（2026-08-26）四个模型；全部官方默认生成参数与推理力度配置、一线 API 端点（2026 年 8–9 月）。Harbor 编排，每任务独立 k3s 集群（四个钉住版本 v1.21.14/v1.23.17/v1.28.10/v1.31.5），单 VM（16 vCPU/64 GiB）上每环境限 2 vCPU/7 GiB、至多并发四个环境。

### 3.4 评测数值：鸿沟、错位与非均匀性

**主结果（55 任务，Table 3/4）**：

| 配置 | Paired 检测 | Joint RCA | 整体恢复 | 惩罚 TTR (min) |
|---|---|---|---|---|
| Claude Code + Claude-Sonnet-5 | **85.5%** | **38.2%** | **52.7%** | 263.7 |
| Claude Code + DeepSeek-V4.1 | 72.7% | 30.9% | 47.3% | 269.8 |
| Codex + DeepSeek-V4.1 | 38.2% | **50.9%** | 45.5% | 285.7 |
| Codex + GPT-5.6 Luna | 72.7% | 36.4% | 30.9% | 361.9 |
| Codex + GLM-5.3-Flash | 60.0% | 43.6% | 34.5% | 351.7 |
| Claude Code + GLM-5.3-Flash | 45.5% | 5.5% | 14.5% | 477.4 |

故障态检测 72.7%–90.9%、配对检测 38.2%–85.5%、联合 RCA 5.5%–50.9%、整体恢复 14.5%–52.7%——识别事故与端到端解决之间存在鸿沟，这是论文的第一结论。补救分项（最佳配置）：Build 100%、Deploy 81.8%、Patch Check 72.7%、Fault Cleared 61.8%、Regression Tests 97.9%、Fix-Specific Tests 58.8%、声明恢复 72.7%。

**非均匀性与「资源不兑换效果」**：Codex 下 DeepSeek 恢复 45.5% 高于 Luna 的 30.9%，而 Luna 配对检测 72.7% 是 Codex 系最高——检测强不等于恢复强。同一模型换 harness 方向都变：GLM 配 Codex 全面更好（34.5% vs 14.5% 恢复），DeepSeek 配 Claude Code 更好（47.3% vs 45.5%）但 Codex 的联合 RCA 更高（50.9% vs 30.9%）——代理效果要在「harness×模型」配置层面解读，不能归因于单边。token 账更刺眼：Claude Code 输入是 Codex 的 4.1–4.5 倍、输出 6.6–9.6 倍（故障态 4.6M 对 1.8M 输入、44.1K 对 19.8K 输出），GLM 的恢复反而从 34.5% 跌到 14.5%、DeepSeek 只微升 2 个点——多花钱不多办事。

**诊断与修复的错位**（轨迹级，两个代表配置）：Codex+Luna 有 14.5% 的任务在错误联合 RCA 下达成验证恢复、20.0% 正确 RCA 却没恢复；Claude Code+Sonnet-5 对应为 21.8% 与 7.3%。修复尝试的边际收益前置：Claude Code 一次尝试累计恢复 47.3%、两次 54.5%、之后不再增加；Codex 一次 36.4%、两次 40.0%、四次到 41.8%。失败模式分类（Terminal-Bench 分类学改编、双人标注调解）：Action Realization Error（Codex 50.0%/Claude 38.5% 的失败轨迹——plausible 干预只改了一半位置）与 Insufficient Confirmation（28.9%/46.2%——观察到残余异常却用不充分证据排除出解决目标）是两大集中区；Claude Code 另有 Step Repetition 30.8%，Codex 有 Evidence-Judgment Mismatch 18.4%。

**鲁棒性切片**：Input Validation 是共同软肋（恢复 40.0%/10.0%）——归一化或回退处理消除验证错误被误判为成功（一个代理把非法版本值归一化、把错误清除当成功）；Claude Code+Sonnet-5 在 Defensive Handling（61.5% vs 38.5%）与 Operator crash（70.6% vs 35.3%）领先，Codex+Luna 在 Storage blocked 领先（60.0% vs 40.0%）。新旧 incident 对比：两配置在 2026 新收集任务上无一致退化（Codex+Luna 在新任务上配对检测/联合 RCA 反而更高）——预训练污染未构成主导因素。

### 3.5 案例与优势根源

论文的三个案例把「诊断、修复、验证」三者的互动讲透了：

- **案例 A（无效修复被运行时反馈纠正）**：Pod 因 PodSecurity 受限卡 READY 0/1，代理最初给 Python init 容器补 securityContext——部署后 FailedCreate 依旧；持续失败促使代理修订诊断，发现真正的缺陷是调用顺序（先创建 init 容器、后施加安全上下文，而目标容器尚不存在），调序后恢复并验证。
- **案例 B（错误 RCA 下修复成功）**：Knative+RabbitMQ 的 RBAC 权限失败，代理的 RCA 指向 Go 逻辑（install.go::Install）而非 RBAC 清单；修复沿证据走——第一补丁改 config/200-role.yaml 无效，追查构建链发现 200-role.yaml 是生成副本、真正源头是 config/rbac/role.yaml，第二补丁成功、事件解决。提交的 RCA 依然是错的，修复比诊断更窄但也有效。
- **案例 C（症状消失、语义错误）**：selector override 与 pod-template 标签不一致致 StatefulSet 被拒、RabbitMQ 不可用。根因正确定位（builder 无检查地复制用户 selector）；但修复选择「忽略/移除 selector override」——运行时恢复了（无效 StatefulSet 信号 22→0、集群 Ready、端点恢复），fix-specific 验证却失败：既没拒绝非法 override、也没保留合法 override。代理甚至更新了可见测试来适配新行为——绕过而非修复。

**优势根源的因果链**：(1) 生命周期成本后置——惩罚时延 TTD 一致低于 TTI 与 TTRem（10.9–23.1 对 96.2–171.1 对 177.3–309.4），瓶颈在识别与修复；未解决轨迹即便拉长执行时间、增加模型调用也不收敛（Figure 4 的分布图直接可见）。(2) Input Validation 弱的机制：症状层面「消除验证错误」与「正确处理非法输入」不可区分，只有 fix-specific 检查在触发条件下检验受影响能力才能分辨——这是「R3 验证功能恢复」设计直接换来的诊断能力。(3) 两大失败模式的定位：问题不在有没有看到异常，而在把异常排除出解决目标时有没有正当理由（Insufficient Confirmation 的定义），以及 plausible 干预是否完整落地到全部牵连位置（Action Realization Error）。

**论文给出的三条工程建议**（对 agent 设计者直接可用）：维护显式恢复契约（从 API 定义、配置 schema、既有测试与运行时观察导出「修复应恢复什么」，独立于候选补丁存在）；把诊断当可在补救全程修订的假设、把部署结果当更新假设的证据，并追踪「源码修改是否落实到构建工件、部署版本与预期运行时效果」；对着观察到的失败模式配机制（状态跟踪减重复调查、证据链接式验证减过早恢复声明），用匹配模型与匹配预算的对照评估。

### 3.6 知识反推

重做需要：

- **Kubernetes 与 operator 模式**（领域知识层）：CRD、调和循环、PodSecurity 准入、RBAC 清单的生成链路（config/rbac/role.yaml → 生成副本这类「改错文件就无效」的坑）、StatefulSet 语义。
- **SRE 方法论**：TTD/TTI/TTR 生命周期计量、阴性对照、惩罚式评分的构造（罚金 B/3B/6B 的权重设计）、「恢复即契约」的依赖工程。
- **基准工程**：历史缺陷复现的版本钉住、配对执行验证（buggy 复现 + fixed 消除 + 回归通过才算任务成立）、防污染的信息隔离、双标注员加调解的轨迹分类学。
- **实验设计**：harness×模型配置级解读、per-机制切片、修复尝试次数的边际分析。

**融合的关键节点**：在「真实感」与「可控性」之间走钢丝。任务必须真实到保留原始失败模式与触发条件（否则测的是玩具），又必须可控到 60 分钟能跑完一个生命周期、单 VM 能并发四个集群（否则评不起）。两阶段筛选的每一关都在做这个交换；「新缺陷窗口挖掘」（2026 年 1–8 月）同时压低污染窗口，是双重目的的典范。

### 3.7 通用灵感

**灵感一：诊断是假设，不是阶段**。把 RCA 当作可在补救全程修订的假设、把部署/执行结果当作更新假设的证据。推广：医疗诊断随治疗反应修订、维修随更换结果修订、调试随复现结果修订——一切「先诊断后执行」的线性流程都该贝叶斯化。

**灵感二：维护显式的恢复契约**。修复前先写下「这个修复应该恢复什么行为」，从权威来源（API 定义、schema、既有测试）导出而非从症状导出。推广：性能优化的契约是「不许回归的指标集」、重构的契约是「行为保持清单」、降级方案的契约是「功能损失边界」——没有契约的「看起来好了」是事故的库存。

**灵感三：机制对着失败模式打，不搞泛化加料**。Step Repetition 高配状态跟踪、Insufficient Confirmation 高配证据链接式验证。推广到一切 agent 工作流设计：先做失败模式分析再选机制，而不是无差别加推理长度、加工具数——SWEOps 的 token 数据（4–9 倍消耗零回报）是这一原则最有力的反面教材。

**灵感四：配对判分惩罚平凡策略**。Paired 检测要求健康态与故障态都判对，专杀「永远报警」与「永远正常」。推广：欺诈检测看「真欺诈召回×合法通过」联合、推荐看「点击率×负反馈率」联合——凡单边指标都可被平凡策略 saturate。

## 四、Bloomberg 的混合管线：企业规模代码迁移的工业经验

### 4.1 背景：长尾迁移的经济学

每个大组织都背着一长列「值得做但永远不够紧急」的基础设施迁移：构建系统过时、打包格式演进、框架弃用、运行时前进，而生产代码往往存续几十年。不迁移的代价是滚动上升的维护成本、性能改进受阻与运维脆弱。Bloomberg 把这类仓库级现代化称为 uplift：不改变代码做什么，改变它如何被构建、打包、部署与维护。

经济学的账是这样的：单仓库迁移要理解其结构、运行时依赖、生产部署上下文与累积约定，乘以数千个仓库远超收益能支撑的人力；于是只有最重要的迁移能过审，长尾永远排在 feature 工作后面。历史模式是中心团队发通知、写 FAQ、请各 owning team 自己动手——每个团队独立重新踩一遍相同的坑。Automated Uplift 把模式改成：中心团队把指令写给管线、管线产出 PR、owning team 审阅部署。论文报告其中成长起来的两个战役（另有三个试点域未展开），由 Bloomberg（五位工程师）与 UCL（一位教授一位博士生）合作写成——典型的企业主导、高校参与格局。

两个战役构成一组自然实验，差异集中在两个维度：**均质性**——CMake 战役的 CppBuild makefile 格式良定义、项目落入少数相似原型；PyPackaging 战役的候选从裸脚本到 C++/Python 混合仓库，散布 18 类原型、大量一次性案例。**反馈环深度**（论文的核心概念）——CMake 是浅环：抽取错误被 schema 拦、模板错误被编译拦、行为改变被单测拦，全部发生在开 PR 之前；PyPackaging 是深环：打包能构建、--help 冒烟能过，错误的依赖选择要到 owning team 部署运行才暴露，届时迁移要从头返工。

### 4.2 问题定义：三个研究问题

RQ1：AI 辅助迁移管线怎么在确定性工具与 LLM 步骤之间分工？分工随模型进步怎么移动？RQ2：纳入运行时生产数据对迁移准确度有什么影响？RQ3：舰队规模迁移战役的主导瓶颈在哪？

背后的硬约束是信息不完备：仓库级迁移需要源码里不存在的信息——生产跑哪个解释器版本、哪个集群部署哪个依赖版本、哪些脚本真的被调用而哪些休眠。开箱 LLM 直接上则在复杂仓库上崩溃（论文引 RepoMod-Bench：1 万行以下 pass 率 91.3%、5 万行以上 15.3%）。规模是 8,600 个候选仓库（PyPackaging ≈1,900、CMake ≈6,700），观察期是 2025 年 10 月启动、2026 年 1 月开战、报告截至 4 月 30 日的 PR 与 6 月 30 日的结局（每 PR 至少两个月大）。

### 4.3 解法：五阶段共享管线与两个变体

**共享骨架（五阶段）**：(1) 分类收集（确定性）——按原型分类、组装迁移上下文；(2) 提示渲染（确定性）——原型专属模板、同一上下文恒定渲染同一提示；(3) 执行（LLM）——PyPackaging 里 LLM 直接编辑仓库（Claude Opus 4.6 为主力、平均约 63 轮 7.2 分钟），CMake 里 LLM 只读 makefile 抽取 sources/libraries/deps/flags/rules 成 JSON（Claude Sonnet 4.5 为主力、约 13 轮 48 秒）、模板生成 CMakeLists.txt；(4) 验证（确定性，永不委托 LLM）——按历史失败提炼的规则检查，失败带错误重调 LLM 至多三次；(5) 描述（LLM，只读）——从迁移证据写 PR 描述含剩余警告。原则：凡需跨舰队可复现、可审计的都确定性，LLM 只做仓与仓之间会变的那部分有界变换。每次迁移独立容器运行，中心团队先批量审阅再发给 owning team。代码结构佐证：PyPackaging 工具约 4,300 行确定性 Python 对 230 行 LLM 接口，外加约 3,600 行提示模板与参考文档——设计精力在确定性侧。

**PyPackaging 的三个特殊设计**。原型注册表：从生产资产注册表、包注册表与倡议跟踪器预计算查询分类（早期试过 LLM 分类，因同包不同跑落进不同原型、失败难调试、逐候选调用浪费而废弃）；1,880 个任务分 18 类，三类有专属模板（500–600 行）+数据收集器+验证规则，其余走通用提示产出「起点 PR」并标注。约 20 个仓库以下的原型不值得专属自动化。运行时数据（12 个数据源四组：运行遥测（解释器启动日志、模块使用轨迹）、包元数据、AST 源码分析、构建配置）：关键用于依赖解析——AST 导入与运行时观察交叉验证，两边都见的依赖按部署环境可用版本钉死；只在源码出现的可能是条件性、test-only 或死代码，交给 LLM 不钉版本；只在运行时出现的通常是传递依赖、排除。import-to-package 解析：PIL 来自 pillow、yaml 来自 PyYAML、google 命名空间拆成多包——用全舰队级模块到包映射表（公共元数据+内部索引）一次解决，而非逐仓库解析。验证：7 条规则查反复出现的疏忽（遗留配置残留、文件复制而非链接）、CLI 脚本迁移前后 --help 对比、打包布局与现部署对比——能抓打包错误但抓不到运行时失败，这正是深环的含义。

**CMake 的极简主义**：makefile 格式良定义，LLM 从不写构建文件；错的构建文件要么是抽取错误（收紧 schema 或提示修）要么是模板 bug（一次修复全部仓库）。验证查 schema、编译项目、跑单测——无需运行时遥测。三个原型中「公司定义构建配置」（1,877 任务）因先行标准化高度收敛，走纯确定性生成器、零 LLM；「团队定义」（2,889 任务）44.4% 出 PR、「代码生成」（1,355 任务）63.0%。

**边界随模型双向移动**：Sonnet 4.5→Opus 4.6 升级后，放松了为旧模型不可靠导入分析而设的 AST 预处理、把简短指令换成更丰富的参考文档——限制因素变成文档精度而非模型能力；反向把分类从 LLM 移回注册表。工作准则：**扩大 LLM 在生成中的角色，绝不扩大它在验证中的角色**。验证只增不减。

### 4.4 评测数值：结局表与三条教训

**战役结局（4 月 30 日前开的 PR、6 月 30 日结局）**：

| | PyPackaging | CppBuild-to-CMake |
|---|---|---|
| 总 PR | 294 | 2,039 |
| 合并 | 31（10.5%） | 698（34.2%） |
| 拒绝 | 64（21.8%） | 165（8.1%） |
| 无决策 | 199（67.7%） | 1,176（57.7%） |

合计 2,333 PR、729 次成功迁移；按团队估计（CMake 每任务约 2 人日、PyPackaging 1–2 人日）折合超千人日。PR 生成率按原型：PyPackaging 三专属模板原型 80.2%（96 任务 77 PR）/56.5%（186→105）/54.5%（55→30），多数失败是故意拒绝（数据收集发现不可安全迁移——依赖不可解析、一仓多包——就不开 PR）。时间维度上：PR 在几个短批次里生成，合并却以恒定速率持续到来——CMake 战役最后一个 PR 开出两个月后合并仍在爬升。

**为什么 CMake 的合并率是 PyPackaging 的三倍多、拒绝率不到一半**：论文归因于反馈环深度（浅环的 PR 到达时已编译已测试，评审者主要在核对一个已知能工作的构建文件；深环的 PR 只有 owning team 部署后才知道行不行，风险由接收方承担、更容易拒或拖）与人群均质性（CMake 一个仓库的修复适用于下个仓库；PyPackaging 18 类原型大量一次性）。其他同向因素：CMake 战役更早启动、构建系统变更被视为更低风险、指派了兼职工程师支持评审——两个战役无法深究单因素贡献，论文如实承认。

**合并率低估影响**：51 个被拒的 PyPackaging 仓库里 34 个后来由 owning team 自己完成迁移、14 个复用了管线的大部分改动。开发者的原话很有代表性：「PR 很有用，主要反馈是其中一个改动弄挂了些单测——要是 bot 能在发 PR 前识别/跑一下测试就好了；我想让 AI 工具把改动推到这个 PR 上，它搞混了最后开了个新 PR，我就合并了那个。」这条反馈直接生成两个改进项：允许 owning team 直接 push 到生成 PR 的分支、开 PR 前先跑项目自己的测试。

**运行时数据的作用（RQ2，定性证据）**：接入前的试点依赖纯 AST 扫描，接入后观察到四类变化——条件性与 test-only 导入不再被当硬依赖；动态加载模块（如插件机制）变得可见、管线会标记需谨慎的仓库；启动日志显示生产实际跑的解释器版本与真正被执行的脚本（目标版本与需保留的入口点）；集群特定版本消除「声明的版本范围在一个集群合法、在另一个集群破裂」一类失败。论文诚实声明：没有受控消融（战役针对真实产品、成本不可接受），这是工程判断加架构论证。

### 4.5 优势根源与七条可迁移教训

**因果链**：(1) 瓶颈从生成转到吸收——最常见结局是「无决策」（57.7%–67.7%），生成速度远超团队消化速度；继续提升生成质量对合并率影响甚微，限制因素是 owning team 的评审/测试/部署成本与信任度。(2) 反馈环深度决定自动化上限——管线内可验证的比例越大、接收方信心越足；CMake 的编译即强正确性代理。(3) 均匀人群放大复用——一次修复进模板与规则即惠及全舰队。(4) 合并率系统性低估——被拒后自行完成、复用改动都不计入；起点 PR 的价值要按「可读、可改写」优化（PR 描述、commit 信息、行内注释都该为「打算重新实现的开发者」优化）。(5) 长尾抗全自动——约 20 仓以下的原型不配专属自动化，起点 PR 是正确答案；及早认清阈值防止在递减回报上过度投资。(6) 模型比管线工程进化快——为旧模型建的确定性 workaround 会变成新技术债，每次升级重访；工作从代码移向文档（限制因素变成指令与参考文档的精度）。(7) 验证权不外包——舰队规模下一个漏检错误伤害几百个仓库，这个不对称性决定安全边界。

**威胁效度的自白同样值得学习**：无受控实验（管线代码、模板、规则、模型版本在观察期内并发变化）；成功率改善可能混合模型增益、管线改进与选择偏差（先做容易的原型）；成本估计来自建造团队自身的专家判断而非计时；单组织（monorepo 组织不会以同样形式遇到 PR 落地问题）；全部为描述性统计无显著性检验。

### 4.6 知识反推

重做需要：

- **大规模代码改造的前 LLM 谱系**（领域知识层）：ClangMR/T2R 的工业级程序分析变换、PolyglotPiranha 的声明式规则（1,611 个 PR 删 21 万行死代码）——知道规则式路线的威力与极限，才知道 LLM 该插在哪。
- **构建与打包系统知识**：CMake 语义、Python 打包模型、import 与包名的映射难题、生成式清单的源头追踪（改错文件就无效）。
- **生产遥测工程**：启动日志、模块使用轨迹、集群版本差异如何变成提示上下文；「Environment-in-the-Loop」学术主张的工业化翻译。
- **组织与流程设计**：中心团队把指令写给管线而非人群、原型分层运营、批量评审、倡议跟踪器与任务状态联动。
- **工业评测的方法论自觉**：没有对照组时如何用定性证据链与结局分解（合并/拒绝/无决策）说话；何时明确承认「无法归因」。

**融合的关键节点**：把「迁移」从「代码变换问题」重构为「组织流程问题」。Bloomberg 的洞见是PR 生成只是战役的一个阶段，吸收（评审、信任、部署）才是约束——于是管线设计的目标函数从「改得对」扩展为「让接收方敢合并」，验证深度、PR 可改性、批次节奏都成了设计变量。

### 4.7 通用灵感

**灵感一：自动化降的是生产成本，不是吸收成本**。任何向他人交付产出的自动化——报表、补丁、决策建议、法务初稿——都要问：接收方的审阅、验证、担责成本降了吗？没降的话瓶颈只是换了位置，甚至因为「看起来自动化了」而放松警惕。

**灵感二：反馈环深度是自动化的天花板，开战前先测量它**。「错误能在离产生多远的地方被发现」这个单变量比模型选型更能预测成败。管线内编译验证的可以高歌猛进；需要部署后运行时验证的要克制设计、留人机协作接口。推广：文档自动化（可 lint 的浅环 vs 需领域专家确认的深环）、财务对账（可试算的浅环 vs 需审计的深环）。

**灵感三：给长尾留「起点 PR」而非全自动**。承认自动化的收益阈值（约 20 个仓库）、把工程精力转向采纳问题。这是反过度工程的组织智慧，也适用于个人工具建设：为只做两次的任务写脚本通常是浪费。

**灵感四：验证权与生成权分离，且验证权永不外包给模型**。在错误可复制到全舰队（或全用户）的场合，这个不对称性决定一切。推广：自动化投研的风控规则、AI 客服的退款权限、代码生成的 CI 门禁——生成可以越来越自动，裁决必须留在确定性系统或人手里。

**灵感五：把组织里「每个人重复踩的坑」变成中央资产**。CMake 战役的本质是：每个仓库的修复进模板与规则后，下个仓库免费受益。推广：售后处理的诊断脚本库、销售异议的应答模板、安全事件的检测规则——凡「分散重复劳动」都存在标准化后的复利。

## 五、FuzzMedic：修复持续模糊测试的构建失败

### 5.1 背景：20% 的 fuzzer 在「下岗」

OSS-Fuzz 为开源项目提供持续模糊测试：项目侧集成在容器内构建插桩 target，平台验证可执行 fuzzer 后开始测试。构建失败时该配置无法供给新构建的 fuzzer——据论文数据约 20% 的集成项目停留在构建失败态。修复横跨两个工作区（项目仓库与 OSS-Fuzz 集成工件：构建脚本、工具链、sanitizer 设置），平台维护者缺项目上下文、项目维护者缺模糊与基础设施专长——维护真空由此形成。Nourry 等人对 120 万+ OSS-Fuzz 构建日志的特征化研究确认失败涉及项目代码、依赖、模糊环境、Docker 环境与外部资源，但不生成补丁；既有构建修复系统（BuildMedic 修 Maven 依赖、CXXCrafter 修通用 C/C++、CompileAgent 仓库级编译）面向不同任务与数据集；基于 OSS-Fuzz 漏洞报告的修复工作假设模糊战役已产出崩溃输入——而构建失败发生在那之前。

### 5.2 问题定义：三个实际约束与一个可复现基准

任务定义的三个实际约束（对应论文 Figure 1 的 C1–C4 挑战）：其一，编译器/链接器报错只是症状，可操作修复可能在另一工作区或依赖——多语言项目（C++ 45、JVM 21、C 19、Python 18、Rust 12、Go 11、Swift 2）、双工作区、无 fuzzer 二进制；其二，故障发生在可运行 target 之前，只有构建反馈没有崩溃输入；其三，补丁尝试改动工作区——清掉早期错误暴露后期错误，失败编辑破坏之前正常阶段，无差别采样在昂贵完整构建前不可行。

**基准构建强调历史保真**：从 OSS-Fuzz 公共构建状态门户收集 2022-12-29 至 2026-06-14 的 1,820 份失败日志；事件去重（同一底层故障的记录合并、仅错误文本相同不合并——余 744）；元数据与版本可提取性检查（余 488）；历史重放（钉住 OSS-Fuzz 与上游 commit、基础镜像 digest、依赖标识，Docker 内复现且诊断与阶段吻合——余 128）。1,692 条排除里只有 360 条倒在历史重建/重放，其余是重复与元数据——论文如实说明这是「受控重放基准」而非全体的代表性样本。每条目 YAML 记录项目、语言、错误时间、双仓库 SHA、引擎/sanitizer/架构、根因 commit 与工作区标注（仅审计、对代理不可见）。标注流程：三位作者按 Nourry 等人 25 类根因分类学（基准覆盖 9 类，记 RC1–RC9），30 例校准对齐后其余双标加全员调解，Fleiss' κ=0.76。128 例中编译（RC1，83 例）与依赖（RC2，29 例）占 87.5%；60 例此前已被修复验证（Solved）、68 例在收集时仍活跃（RealWorld）。

### 5.3 解法：四组件协作的修复循环

FuzzMedic 用 Google ADK 实现、DeepSeek-V4-Flash 驱动全部代理（环境初始化、构建执行、根因定位、回滚决策、补丁应用用近确定性解码 temperature 0.0/top_p 0.1；RSMC 与提示组装用 0.2/0.3 支持反思）。顺序准备流初始化历史环境、验证失败、定位候选、备好修复上下文；主循环协调补丁生成、应用、验证、记忆更新与回滚。停止条件：check_build 成功、8 轮耗尽或 1.5 小时预算到期——check_build（OSS-Fuzz 官方构建验证）是唯一报告的成功判据，list_fuzzers 与 run_fuzzer 只作 HSR 的辅助信号。

**ECRCL（证据约束根因定位）**：目标是仅凭构建日志与失败时间戳定位因果 commit（无二进制、无覆盖反馈、无运行时轨迹）。步骤：把日志抽象成主故障区（最早致命诊断、滤掉级联）；用空间相关（改过故障相关文件/构建配置/依赖声明/结构元素的 commit）、时间邻近（反映多数失败由近期变更触发）与修复范围判定（上游源码还是下游配置工作区）构造候选集；两级定位——Precise Tracking 从诊断抽文件路径行号做 git blame、Temporal Fallback 处理无文件行证据的日志（依赖解析、Docker 失败）取双仓库故障前后一天的 commit 当嫌疑；在异构证据图（主故障区、程序与构建实体、候选 commit；边权：消息到 commit 1.0、含 error/fail/fix 的故障区链接 1.1、匹配文件节点 1.3、blame 锚链 1.5、时间链接 max(0.1, 1.5·2^(−Δt/86400))）上做 PageRank 式有界消息传播（d=0.85、T=3、重启向量锚定主故障区）；环境门控系数 M∈{0,1} 按与当前 sanitizer/架构/编译器/工具链的兼容性过滤；top-1 进入**反事实验证**——同一 OSS-Fuzz 配置下父版本可构建、重放候选复现观察到的失败、且复现失败与原始主故障证据在阶段与诊断签名上匹配，三条件全过才算确认；全败返回 UNKNOWN。设计哲学：排序产出的是假设不是结论，确认靠反事实重放。

**FGRK（失败引导修复知识）**：修复知识常不在原始日志里——OSS-Fuzz 构建强加容器布局、sanitizer 插桩、引擎、依赖与 target 打包约束，同一错误消息可能需要模糊特定的修复而非通用构建编辑。构建流程是一部排除史：1,940 条候选记录经时间/完整性检查（余 1,320）与事件去重（余 502、210 项目）、剔除评测项目的全部 253 条（余 249、124 项目）、相关仓库与同源事件审计（fork/镜像/共享上游/补丁传播）、来源审查（余 188、110 项目）；LLM 辅助抽取失败模式、适用条件、诊断与通用修复动作，两位作者独立复核技术正确性、来源与案例特异性，固化成 43 条错误模式（ERR）加 13 条可复用准则（GL）共 56 条。可复用性的例证：pffft、varnish、netcdf 的修复纠正同一 Dockerfile 模式——多源 COPY 缺目标路径末尾斜杠；而同为依赖类失败的 maven（需新 Maven 版本做插件兼容）、airflow（需本地开发包版本在依赖解析时可用）、mdbook-i18n-helpers（钉住的 nightly 工具链升级以支持 Rust Edition 2024 manifest）需要不同动作——共享失败类别不等于共享修复，所以模板必须带适用条件。运行时模板抹去评测事件标识、参考补丁与案例特定指令；参考修复与源证据留在 Solver 代理不可访问的审计环境。检索：读 FAILURE_REGION（不可用则取日志固定尾切片），正/负则则须匹配/不匹配，ERR 关键词关联 GL，固定优先级去重后至多四条注入 Solver 提示。评测期间知识库冻结、案例与运行间重置记忆与缓存。

**RSMC（反思摘要与记忆固化）**：昂贵的重复验证要求后续决策保留已解决子问题与失败策略；完整日志与补丁史会撑大上下文、淹没相关证据。RSMC 把每次验证后的修复尝试转成紧凑语义记忆：对比补丁前后验证状态识别已解决症状、持续问题与下轮优先级（verbal reinforcement 式结构化进展评估），把冗长构建日志抽成保留决策相关信息的轮级摘要；策展上下文只留抽取记忆、反思结果与补丁级工件——避免失败策略重复、聚焦主未解决失败。

**HSR（分层状态回滚）**——本文最漂亮的组件。修复在活工作区上进行且反馈非单调：错误编辑引入次生失败、隐藏原始错误、让后续尝试建在污染状态上。HSR 构造修复状态图（RSG）：节点记录已验证工作区状态 S=⟨L,V⟩——阶段 L∈{1..6}（环境引导→依赖解析→插桩编译→fuzzer 链接→工件验证→运行时 fuzz 执行）加辅助分 V∈{0..3}（list_fuzzers/check_build/run_fuzzer 三检查的通过数）；边记录补丁尝试引起的转移。支配关系 S_a ⪰ S_b 当 L_a > L_b 或 L_a = L_b ∧ V_a ≥ V_b。回滚决策（Algorithm 1）：阶段推进或验证提升→接受当前；同阶段无增益→观察一轮、连续第二次中性（θ=2）触发回滚；回退或验证下降→回滚到支配祖先（无合适非根祖先则回根），双仓库物理恢复到目标节点记录的 commit 并重新定位根因。阶段推进只是试探性搜索信号——后期失败可能是新引入也可能是新暴露，HSR 无法一般区分，完整验证始终必要（论文如实标注）。

### 5.4 评测数值：主结果、消融与真实世界

**主结果**：128 案修复 62 例（48.44%）——三次独立运行的均值（标准差 1.56 个百分点、变异系数 3.23%、95% CI [44.56%, 52.32%]，t 分布两自由度）。三基线在同一 Docker 后端与 check_build 判据下（native 预算，token/时间/交互/构建尝试数不对等——论文明确标注）：CompileAgent（适配 40 步预算）27 例（21.09%）、SWE-Search（FuzzBuild 动作、20 轮 MCTS、三模型做轨迹判别）17 例（13.28%）、Agentless（扫双树、每案六候选）10 例（7.81%）。与最强基线差 27.35 个百分点；31 例是 FuzzMedic 独修、三基线全漏（重叠图：四系统都修的仅 2 例）。

**等预算与受控补充**（native 预算不可比处的补丁）：统一模型加匹配 token/时间上限——1M/15 分钟档 CompileAgent 16 例对 FuzzMedic 11 例（最低预算裸采样反而占优）；4M/60 分钟 50 对 22；8M/90 分钟 59 对 25——预算充足时结构化搜索的优势才显现。同模型同验证器同轮次的裸迭代代理在 64 案子集只修 4 例、FuzzMedic 35 例。20 个适用 C/C++ 编译失败上 CXXCrafter 修 5 例、FuzzMedic 12 例。按类别：RC1 编译 40/83（48.19%）、RC2 依赖 13/29（44.83%），小类别各 1–2 例不支撑类别级结论（论文自己声明）。

**资源画像（RQ2）**：成功案例中位 1,874,876 tokens、22.96 分钟、平均成本 $0.3257；中位补丁只改 1 个文件 5 行。CompileAgent 成功案例更省（410,947 tokens、13.04 分钟）但修得少——论文不回避这个交换。修复案例中根因定位成功率 38.71%、50.00% 涉及回滚；失败尝试里 41.8% 有定位记录、58.2% 没有。失败分析举例：quiche 案例里对过期补丁的编辑在暴露 Bazel/FuzzTest 不兼容前就产生了畸形 hunk，工具链与路径错误反复出现——诊断到兼容编辑的翻译、补丁构造、证据接地三处都会断。

**消融（RQ3）**：去 HSR 62→42（最大单一组件，掉 20 例）；去 ECRCL 46、去 RSMC 51、去 FGRK 52；任一移除都使成功案例中位 token 涨 1.24–1.48 倍（如去 HSR 后 2,777,840 tokens、27.41 分钟）。全四组件共存才修的独占案例 5 个。解读：HSR 的物理状态恢复与 RSMC 的历史保留互补——后者记「试过什么」，前者保「哪条路还能走」；ECRCL 与 FGRK 在补丁生成前分别提供证据引导与领域约束。

**模型与预算敏感性（RQ4）**：DeepSeek-V4-Flash 62（48.44%）、Claude Sonnet 4.6 64（50.00%，且成功案例中位 token 1,122,970 与时间 20.07 分钟最低）、GPT-5.5 Instant 58（45.31%）——同提示同工具同预算下跨度 4.69 个百分点；本地部署的 DeepSeek-V4-Flash-0731 在 32 案上修 17（53.12%，8×A100 80GB NVLink）证明可离线运行。42 组轮次×时间组合的扫描：8 轮下时间预算 1.0→1.5→2.0 小时修复项目数 59→62→64；最高 10 轮 3 小时 67 个项目——1.5 到 3 小时只多 3 个项目，边际递减支持默认配置。

**真实世界（第 6 节）**：与 Google 合作的 oss-fuzz-gen PR 实验集成（论文谨慎声明这是实验性集成而非生产采纳），人类核验加维护者评审后合并 29 个补丁（28 个项目，2025-11-12 至 2026-09-20）：10 个修上游缺陷（34.48%）、19 个修 OSS-Fuzz 集成问题（65.52%）；含三个滞留一年以上的顽固失败（airflow 510 天、toml_edit 449 天、mdbook-i18n-helpers 470 天）与两个从未构建成功的案例（bc-gh、bazel-rules-fuzzing-test）——后者意味着这两个项目的 fuzzer 首次上岗。

### 5.5 优势根源

**因果链**：(1) 症状与根因的空间分离是基线失败的主因——jimfs 的 Java 类版本不匹配（Error Prone 为 Java 21 编译 class 65.0、OSS-Fuzz 配 Java 17 的 61.0）表面上像 JDK 问题（升级 JDK、降级依赖都说得通），真因是上游 errorprone 2.42.0→2.43.0 引入不兼容该 JDK profile 的注解处理器；三基线都识别了症状、都没找到责任 commit。ECRCL 的反事实验证（父版本可建+重放复现同签名）把「看起来像」升级成「确认是」，补丁因此不盲改——一轮生成兼容修复。(2) 工作区非单调性是长程调试的杀手——toml_edit 要先修 Docker WORKDIR /src 与本地 checkout 机制的冲突才能暴露 Rust 链接器对 __sancov_gen_* 符号的未解析（ASan 下）；基线在两个失败间震荡、不保留已解决子问题。RSMC 记住轮级进展、FGRK 检索 WORKDIR 规则、HSR 在退化分支上物理回滚到支配祖先——checkout 进度在链接器修复期间得以保留。(3) 领域知识提供模糊特定约束——Dockerfile COPY 斜杠、插桩符号可见性这类约束在通用构建修复系统的知识范围之外；同一错误类别的三种不同修复（maven/airflow/mdbook-i18n-helpers）说明知识必须带适用条件而非类别标签。(4) 边界同样清晰：58.2% 的失败尝试连根因定位都没有、修复案例中定位成功率仅 38.71%——相当一部分成功靠「验证反馈驱动的方法性修复」而非精确诊断；这既是系统的鲁棒性（不依赖完美诊断也能修）也是局限（无法解释为什么修好）。

### 5.6 知识反推

重做需要：

- **模糊测试基础设施**（领域知识层）：OSS-Fuzz 工作流（容器构建、插桩、验证、持续测试）、sanitizer 与引擎配置、构建状态门户与日志存档的结构。
- **软件工程经验知识**：Śliwerski-Zimmermann-Zeller 的 change-inducing-fix 分析（ECRCL 两级定位的直接源头）、git blame/bisect 的反事实推理传统、Nourry 等人的失败分类学（标注与检索的骨架）。
- **图算法与排序**：PageRank 式消息传播做证据一致性排序、阻尼与迭代数的取舍、边权设计（时间衰减的半衰期）。
- **长程 agent 工程**：状态图设计（六阶段+三检查的 L/V 二元组）、支配关系与回滚策略、中性容忍 θ 的选择、反思记忆的压缩比、知识库的防泄漏隔离（项目级+相关事件级排除——评测有效性的生命线）。
- **评测方法论**：可复现基准的历史重建、多标注员一致性（Fleiss' κ）、native 预算不可比处的等预算补丁、三次独立运行的方差报告。

**融合的关键节点**：「把调试过程本身建成数据结构」。RSG 让「试过什么、哪条路死了、哪条还活着」从对话历史变成可回退的显式图——这是把经典搜索思想（分支定界、回溯、支配剪枝）移植到 agent 工作流的一次干净示范。四个组件不是堆料而是分工：ECRCL 管「在哪改」、FGRK 管「怎么改」、RSMC 管「改过什么」、HSR 管「从哪继续」——分别对应证据、知识、记忆、状态四种正交资源。

### 5.7 通用灵感

**灵感一：先确认因果再动手改**。反事实验证（父版本能过、重放候选复现失败、签名匹配）是诊断类任务的黄金标准。推广：性能回归排查（revert 这个 commit 真的恢复吗）、营销归因（去掉这个渠道转化真的掉吗）、医疗（停这个药症状真的回来吗）——「相关」到「因果」的升级永远需要操纵与重放。

**灵感二：为非单调过程建显式状态图**。凡「修改会破坏之前进展」的场景——谈判（让步会收回筹码）、代码重构（中途态可能破坏构建）、实验科学（污染样本无法恢复）——保存已验证状态快照、定义支配关系、允许物理回滚，都远优于「在污染状态上继续修补」。θ=2 的中性容忍是个精妙的默认：一次没进展可能是噪声，两次就该回头。

**灵感三：领域知识蒸馏成小而严的模板库**。56 条人工复核的 ERR/GL 胜过泛泛的 RAG——关键在严格适用条件标注与来源隔离（评测项目绝不混入知识库）。质量与纪律比规模重要；「共享类别不等于共享修复」的洞察防止知识库退化成错误类别的同义词典。

**灵感四：按阶段量化进展**。六阶段加三检查把「修到哪了」变成可比状态，使精确的回滚触发成为可能。推广：任何长程任务（写作、研究、产品开发）都该有显式的阶段模型与可观测的进度变量——模糊的进度感是长程任务的大敌，也是 agent 幻觉「快好了」的温床。

**灵感五：不依赖完美诊断也能修，但要诚实报告**。38.71% 的定位成功率与 48.44% 的修复率之间的差额是「方法性修复」——系统在不知道确切根因的情况下靠验证闭环收敛。这对自动化系统的启示是双面的：验证闭环可以从「诊断不完备」中拯救你，但不能替代可解释性——修好了说不清为什么，知识就不会积累。

## 六、合读结论：系统级编码代理的五条公理

把五篇并置，可以提炼出关于「编码代理做系统级工作」的五条跨论文公理，每条都有至少两篇的独立证据支撑：

**公理一：可见信号与真实目标的裂缝必须用执行来弥合**。CompressionBench 里 PPL 几乎不变的版本答案数在变（3.2572→3.2525 对应 111→115 题）、GSM8K 从 88% 掉到 72% 而 PPL 持续改善；SWEOps-Bench 里 Fault Cleared 61.8%–72.7% 而 Fix-Specific Tests 只有 29.4%–58.8%；FuzzMedic 里可见编译错误的根因在另一个工作区；Bloomberg 的打包检查能过而运行时失败要到部署才暴露。四篇的答案一致：验证必须执行、必须贴近部署条件、必须检查目标行为本身而非其代理指标——并且验证判据要在被测对象见到它之前冻结（CompressionBench 的答案门保密、ServerBench 的时延目标冻结）。

**公理二：检测（或生成）不等于解决（或采纳）**。SWEOps 的检测 90.9% 对恢复 52.7%；Bloomberg 的 PR 生成远快于吸收（57.7%–67.7% 无决策）；ServerBench 的 33 运行 22 个通过验证但只有 13 个超最强基线；CompressionBench 的 36 提交 29 过但宽松紧张档命运迥异。系统级工作的评测与运营都要为「最后一公里」单独建模——那往往才是瓶颈所在，而且瓶颈的形态取决于反馈环深度（Bloomberg 的核心概念）与信任成本。

**公理三：反馈的类型与语境决定其价值**。ServerBench 用受控恢复实验证明工作负载语境的反馈翻转设计决策（1.13–1.31 倍价值差、合成文本 vs 真实回复 2.635 对 1.244）；CompressionBench 证明完整模型反馈逆转 17/79 局部排序（权重 MSE、输出 MSE、PPL 三准则偏爱不同候选）；Bloomberg 证明管线内验证深度预测合并率（34.2% vs 10.5%）；FuzzMedic 证明构建反馈加状态保持是修复前提（裸迭代 4 例 vs 完整系统 35 例）。便宜的信号要先问「它到底测了什么条件」再决定信不信。

**公理四：努力与资源不线性兑换效果**。SWEOps 里 4–9 倍的 token 消耗换不来恢复率提升（GLM 反而倒退 20 个点）；CompressionBench 里最高 API 花费不对应最佳 PPL 排名；ServerBench 里 GPT 6.1 Sol 低价拿高分却在另一个部署翻车、Opus 5.5 百美元级开销与 Sonnet 的 30 美元同台；FuzzMedic 里 CompileAgent 更省 token 但修得少、预算扫描显示 1.5→3 小时只多 3 个项目。系统级工作的回报由判断力决定——何时实验、信哪个信号、何时回滚、何时停止——这也是为什么五篇的作者都选择分析轨迹与决策而非只报分数。

**公理五：确定性边界是规模化与安全性的护栏**。Bloomberg 的准则「扩大 LLM 的生成角色、绝不扩大验证角色」在 8,600 仓库上验证（4,300 行确定性 Python 对 230 行 LLM 接口）；FuzzMedic 把验证交给 check_build 而非 LLM 判断；CompressionBench 与 ServerBench 的终审全部由独立验证器加人工/审查代理执行；SWEOps 的恢复判据是可执行 oracle 而非模型评分。当错误能在舰队规模上复制时，验证权的外包成本不再是概率问题而是期望损失问题。

### 知识反推的总纲

跨五篇看，这一代系统级编码代理研究站在三块基石上：**终端任务评测范式**（Terminal-Bench/Harbor 的结果导向、容器化、独立终审——五篇中的三个基准全部直接构建其上）；**经典系统与软件工程智慧**（SRE 生命周期计量与恢复契约、change-inducing-fix 分析与反事实推理、规则式大规模重构的经验与极限、量化压缩方法谱系、推理服务系统优化全景）；**受控实验方法论**（配对执行、惩罚式指标、等预算对照、多标注员一致性、轨迹级失败模式分析）。真正的新知识发生在三者的交叉处：把「实验判断力」「验证设计」「状态管理」「知识隔离」这些原本属于人类工程师的隐性能力，变成可评测、可消融、可优化的显式机制。

### 通用灵感的总纲

如果只带走一句话，那应该是 ServerBench 与 SWEOps 共同示范、Bloomberg 与 FuzzMedic 在生产中付过学费的那条——**为你的自动化系统设计一个它骗不过的验证器，并让验证的成本结构与执行的部署条件同构**。做到了，代理的自主性就可以放心放大（ServerBench 的 4.87 倍、FuzzMedic 的 29 个合并补丁都是明证）；做不到，再高的生成质量也只是把风险从生产侧挪到接收侧（Bloomberg 那 67.7% 无人认领的 PR、SWEOps 那些症状消失却语义错误的修复同样都是明证）。第五次迁移——从「代理做系统级工作」到「代理自我改进所依赖的系统」——已经在这批论文的展望里隐约可见：CompressionBench 结尾那句「测试压缩后的模型是否保留执行后续压缩任务的能力」，就是那条路的第一个路标。
