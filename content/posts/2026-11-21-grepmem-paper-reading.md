## 一、论文背景

### 1.1 长程 agent 的"工作台太小"困境

LLM agent 的上下文窗口就像一张固定大小的办公桌：深度研究 agent 可能连续翻看几十份文档（每集 1M–5M token），桌面迟早放不下。更麻烦的是，**信息的需求是延迟揭晓的**——第 3 步瞥到的一个标识符，可能到第 30 步组合答案时才变得关键；而在第 3 步那一刻，你根本不知道它将来重要。把全部历史留在桌面上既昂贵又终究放不下；即便放得下，模型也不能可靠地利用超长上下文中的所有信息（Lost in the Middle 现象，Liu et al., 2024）。

所以挑战其实是两件事，而过去的工作常常把它们混为一谈：

1. **管理工作上下文**：桌面（上下文窗口）必须腾出地方放新信息；
2. **保住取回过去的能力**：被挪走的信息必须还能按需找回。

这两件事的时间尺度不同：前者以"轮"为单位反复发生，后者以"整个任务生涯"为单位持续累积。把两者塞进同一个机制（压缩即销毁），是后续一切麻烦的根源。

### 1.2 现有解法都在"提前下注"

| 路线 | 代表做法 | 核心赌注 |
| --- | --- | --- |
| 全量保留 | ReAct：一直留着，窗口满就停 | 赌窗口够大（显然不够） |
| 遮蔽 | Observation Masking：旧工具输出换成占位符 | 赌被遮的内容不再需要 |
| 摘要压缩 | ReSum / SUPO：定期把历史摘要成一段话重启 | 赌摘要写作者猜对了未来需要什么 |
| 结构化记忆 | MemGPT/Letta：工作记忆 + 归档记忆 + 检索 | 赌记忆组织与抽取决策做对了 |

这些方法的共同问题：**都必须在需求已知之前做不可逆决定**。摘要是有损压缩——一个精确的哈希值、一条 ERROR 日志、某次搜索里顺带发现的候选答案，恰恰是摘要最容易"顺手扔掉"的细节；而它们一旦被扔掉就永远找不回来。MemGPT 这类结构化记忆虽然保留可检索的历史，但要引入嵌入模型、检索索引、记忆抽取与归档等一整套基础设施——每一步都是额外的决策点与故障点。

### 1.3 论文的反问：既然数字存储几乎免费，为什么要提前扔？

与人类记忆不同，数字存储允许 agent 以极低代价保留**完整**交互历史。近期研究还提示：对原始历史做简单词法搜索，性能可以媲美结构化记忆系统（ReFind，Li et al. 2026；Sen et al. 2026）。本文把这个想法推到逻辑极致，重新审视短期上下文管理与长期记忆的边界：**一份完整的数字记录 + 一个简单的搜索工具，能不能在不要结构化存储、不要检索索引的前提下，构成有效的 agent 记忆？**

## 二、论文定位和关联工作

### 2.1 三条研究谱系

**谱系一：压缩工作上下文。** ReAct（Yao et al., 2023）全量保留直到窗口满；Observation Masking（Lindenbauer et al., 2025）用占位符遮蔽旧观察；ReSum（Wu et al., 2026）与 SUPO（Lu et al., 2026）用摘要重启上下文；MemAgent、MEM1、Context Folding、AgentFold 等学习方法更新有界记忆状态或折叠子轨迹。这些机制决定"哪些细节还能留在桌上"。GrepMem 直接构建在 SUPO 的摘要循环之上——这是它的直接前驱。

**谱系二：组织外部记忆。** MemGPT（Packer et al., 2024，商业化后为 Letta）把 LLM 上下文当操作系统主存，外部存储当磁盘，用分层记忆（核心/召回/归档）与换页工具管理；Generative Agents 按新近性/重要性/相关性检索；A-MEM 组织链接笔记，Mem0 抽取事实，Zep 与 HippoRAG 建知识图谱。这些方法在"解题"之外引入了记忆组织与检索的额外决策。GrepMem 的区别：直接用单个无索引搜索工具从纯文本日志取回信息。

**谱系三：搜索历史与学习召回。** 递归语言模型（RLM）让长输入可被程序化检视；Sen et al.（2026）对比 grep 与向量检索在聊天档案上的表现；ReFind 用 agent 主导的词法搜索遍历原始对话，不建图不摘要即胜过 HippoRAG 2 等结构化系统。但这些工作**没有训练 agent 搜索自己不断增长的工作轨迹**——GrepMem 补上了这一环：用 RL 把"何时搜、怎么写查询"与任务动作、摘要写作联合训练。

### 2.2 定位对比表

| 维度 | 之前的路线 | 本文的突破 |
| --- | --- | --- |
| 保留什么 | 需求揭晓前决定（遮蔽/摘要/抽取） | 什么都不扔：追加式无损日志 |
| 怎么取回 | 嵌入索引 / 记忆抽取 / 图谱 | 单个正则搜索工具，无索引 |
| 基础设施 | 嵌入模型、向量库、记忆管理器 | 纯文本日志 + grep，零额外组件 |
| 训练方式 | 多数不训练检索行为 | RL 联合训练任务动作+摘要+检索 |
| 评测方式 | 单一策略或零星对比 | 同一模型同一配方训练五种策略、RL 前后双测 |

### 2.3 与同期 CompAct-Bench 的对照

同日发布的 CompAct-Bench（arXiv 2611.25673，复旦×清华×腾讯混元）从**度量端**揭示问题：即便是 Claude/GPT 级前沿模型，激进压缩下任务精度仍大幅退化，失败不只来自信息遗漏，更来自任务状态被扭曲（未解决的问题被压成"看似已结论"）。GrepMem 则从**方案端**给出回应：既然压缩必然有损，就把"压缩"与"访问过去"解耦——摘要只服务当前推理，细节交给无损日志。两者一问一答，构成同一天上下文管理研究的镜像叙事（本博客今日另有 CompAct-Bench 精读）。

## 三、问题定义

### 3.1 从具体场景到抽象结构

具体场景：agent 在 32K 窗口内做需要数百万 token 交互的研究任务，中途被反复压缩，最后还要回答"第 5 步那个 docid 的确切值是什么"。

核心洞察：上下文管理其实是**两个正交问题的耦合**——

- **工作上下文管理**是个"桌面空间"问题：桌面上放什么，只影响**当前推理**的效率；
- **访问过去**是个"仓库检索"问题：历史里有什么能找回，决定**未来需求**能否满足。

过去的方法把两者绑死：压缩桌面的同时就永久销毁了仓库里的对应原件。摘要再好，也回答不了"那个哈希值第三位是什么"——原件没了就是没了。抽象问题因此可以写成：

> 给定有界上下文窗口 $W$、不断增长的交互历史 $h_1, h_2, \dots$、以及一组延迟揭晓的信息需求 $q_1, q_2, \dots$，设计机制使得：(1) 任意时刻工作上下文不超过 $W$；(2) 对任意 $q_i$，agent 能取回满足它所需的原始信息；(3) 额外基础设施（索引、嵌入、辅助模型）最少。

### 3.2 类比：工作台、仓库与检索员

| 论文组件 | 仓库类比 | 作用 |
| --- | --- | --- |
| 工作上下文（摘要后） | 桌上便签 | 支撑当前推理，小而够用 |
| 追加式纯文本日志 | 隔壁仓库的全部原件 | 什么都不销毁 |
| grep_history 工具 | 检索员按编号精确翻找 | 用正则词面锚点回取细节 |
| 压缩摘要也入日志 | 便签复印一份存档 | 摘要本身可再被搜到 |

关键在于：**不需要靠便签回忆细节，也不需要给仓库建复杂索引**——因为日志是逐字保留的，细节的"词面"（名字、数字、ID、日期）就是最可靠的锚点，正则表达式足以命中。

### 3.3 形式化要点

一个研究回合中：上下文 $c$ 接近窗口上限 $\tau$ 时触发压缩——生成摘要 $s \sim \pi_\theta(\cdot \mid c, \text{summarize})$，把 $s$ 追加进日志，将 $c$ 重置为"系统提示 + 任务 + $s$"，并启用 grep_history。此后 agent 每步采样动作 $a \sim \pi_\theta(\cdot \mid c)$，消息、工具调用、工具输出全部同步追加进日志。约束是交互预算（回合数、grep 调用免计回合上限 10 次）。

## 四、问题解法

### 4.1 组件一：有界上下文 + 无损日志（解耦的存储层）

GrepMem 建立在 SUPO 的摘要循环上，但加了一条铁律：**工作上下文可以压缩，日志永不丢弃**。系统每产生一条消息、一次工具调用、一个工具输出、一段摘要，harness 自动把它追加到持久化纯文本日志——agent 无需任何显式"存记忆"动作，也就没有"忘了存"的失败模式。日志格式很朴素：每条记录一个头行（如 `[turn 4 tool get_document(...)]`）加正文，逐行可匹配。

类比：桌面定期清空换成便签，但隔壁仓库自动收下每一张被清走的原件——不需要员工动手归档，归档是自动的、逐字的。

两种表示各司其职：工作上下文经摘要保持紧凑、支持 ongoing 推理；无损日志保证压缩省略的细节随时可恢复。

### 4.2 组件二：grep_history 按需召回（解耦的访问层）

首次压缩之后，grep_history 工具解锁。它对完整未压缩日志做**大小写不敏感的正则表达式搜索**，默认按时间顺序返回匹配行、带上下文行与原始出处标注（哪一轮、哪个工具调用），并支持：

- **分页**：默认每页 10 条（至多 30），响应上限 6K 字符，给出续页 offset；
- **上下文行**：默认 1 行（至多 3 行），行内匹配点前后裁剪至 300 字符；
- **count 模式**：只报匹配总数不返回内容——专为"数一下有多少条 ERROR"类问题设计。

一个微妙设计：早前 grep_history 自身的输出不再进日志索引（跳过匹配），避免搜索结果自我膨胀。因为检索靠正则而非语义相似度，agent 必须构造能命中历史词面的模式——简单关键词（名字、数字、日期、ID）或复杂正则皆可；无效模式会返回编译器错误，超时 10 秒的搜索会被中止。

### 4.3 组件三：GRPO 强化学习联合训练（学会"何时搜、搜什么"）

有了无损日志，效果取决于 agent 会不会用。本文用与 SUPO 同源的 GRPO 式 RL（std 归一化优势、裁剪目标、KL 惩罚 β=0.01、80 步、动态采样丢弃全同奖励组、token 级 TIS 离策略校正）**联合优化任务动作、摘要写作、记忆检索**三件事——三者共享回合级奖励，摘要与 grep 调用**没有单独监督信号**，全靠最终答对与否反传信用。训练集 4000 个回合：70% 单问题 OpenResearcher 深研任务、15% 三问题会话、15% 合成 ContextBench 式长流。

公平性设计是本文实验的骨架：五种策略（ReAct / Masking / SUPO / MemGPT / GrepMem）各自用**同一个 Qwen3.5-9B（thinking 模式）、同一 RL 配方、同一训练数据、同一任务工具、同 32,768 token 窗口**分别训练，RL 前后双测。窗口 W=32,768、生成上限 G=4,096、压缩阈值 τ=28,672；每问 30 回合；grep/记忆工具回复免计回合（每回合至多 10 次）。基线还原非常细致：Masking 按 token 预算遮蔽并在不够时逐层退化（先遮观察、再删推理、最后丢整轮）；MemGPT 配齐 working_context_append/replace、archival_memory_insert/search（BM25 版）、conversation_search 三套工具与 70% 内存压力预警。

### 4.4 五策略机制全景

| 策略 | 工作方式 | 能否超窗口 | 保真 | 可召回 | 无索引 |
| --- | --- | --- | --- | --- | --- |
| ReAct | 全量保留，满了就停 | ✗ | ✓ | ✗ | ✓ |
| Masking | 旧工具输出换占位符 | ✓ | ✗ | ✗ | ✓ |
| SUPO | 摘要后重启上下文 | ✓ | ✗ | ✗ | ✓ |
| MemGPT | 摘要 + 三层记忆管理 | ✓ | ✓ | ✓ | ✗（嵌入/BM25 索引） |
| **GrepMem** | **摘要 + grep 原始日志** | ✓ | ✓ | ✓ | ✓ |

（表据论文 Table 1；GrepMem 是唯一四项全满足的策略——MemGPT 虽可召回但依赖检索索引与记忆抽取。）

## 五、评估指标与实验证据

### 5.1 三大评测、五项任务的设计逻辑

评测按"问题何时揭晓"分两组，这正是因果链的实验骨架：

| 任务 | 问题数 | 问题揭晓时机 | 考察什么 |
| --- | --- | --- | --- |
| BCP-Multi（276 集×3 问，源自 BrowseComp-Plus） | 828 | 输入**前**已知 | 多问题间保留早前搜索发现 |
| AMA-Bench file（208 条轨迹×12 问） | 2,496 | 输入**前**已知 | 搜索外部固定轨迹（人人有 grep_trajectory） |
| AMA-Bench stream（189 条轨迹×12 问） | 2,268 | 输入**后**揭晓 | 流式吃入轨迹后独立答题 |
| ContextBench KV Store（6 档长度×4 种子） | 576 | 输入**后**揭晓 | 精确键值回取 |
| ContextBench Log Triage（5 档长度×4 种子） | 480 | 输入**后**揭晓 | 日志条目查找与计数 |

KV Store 输入流 33K–968K token（最高约 30 倍窗口），Log Triage 最高 20 倍窗口；答案由官方程序化评分器判分（KV 值尾带哈希，杜绝蒙混），BCP-Multi 与 AMA-Bench 由 gpt-5.6-sol 依参考判分；报告 95% 置信区间（10,000 次配对 bootstrap）。

### 5.2 主结果：五任务成绩表（RL 后）

| 策略 | BCP-Multi | AMA file | AMA stream | CB KV | CB Log | 平均 |
| --- | --- | --- | --- | --- | --- | --- |
| ReAct | 0.2 | 38.3 | 26.6 | 0.0 | 0.0 | 13.0 |
| SUPO | 38.1 | 45.5 | 45.2 | 13.9 | 6.6 | 29.8 |
| Masking | 34.8 | 44.5 | 44.9 | 20.7 | 6.6 | 30.3 |
| MemGPT | 39.9 | **46.4** | **45.4** | **99.9** | 50.0 | 56.3 |
| **GrepMem** | **46.9** | 46.3 | 46.1 | 97.4 | **95.3** | **66.4** |

（单位 %，据论文 Table 3；加粗为列内最佳。）

三个层次的读法：

1. **对有损基线的碾压发生在"需要词面细节"处**：KV Store 97.4% vs SUPO 13.9%/Masking 20.7%/ReAct 0%；Log Triage 95.3% vs SUPO 6.6%/MemGPT 50.0%。
2. **对结构化记忆的胜利在"平均"与"成本"**：五任务平均 66.4% vs MemGPT 56.3%；且 GrepMem 只用 MemGPT 29% 的 token（ContextBench 2.51M vs 8.60M/流）。
3. **增益并非处处存在**：AMA file 46.3% vs MemGPT 46.4% 持平；AMA stream 46.1% vs SUPO 45.2%，+0.9pp 不显著——这非但不是失败，恰是论文论点的关键证据（见第六部分）。

### 5.3 token 成本 Pareto 分析

GrepMem 在全部五项任务上落在"精度–token 成本"Pareto 前沿（不存在既更便宜又更准的策略）：BCP-Multi 比 SUPO 仅多 6% token（1.22M vs 1.15M/集）换 +8.8pp；AMA file 反而省 5%（560K vs 590K）；ContextBench 多花 19% token 换 KV +83.5pp/Log +88.7pp，同时只有 MemGPT 的 29% 成本。最贵的一站是 AMA stream：2.3× SUPO token（869K vs 377K）只换 0.9pp，每条轨迹 grep 约 19 次——论文诚实承认这是召回开销不划算的场景。墙钟时间上 GrepMem 同样在前沿：ContextBench KV 每流 38 分钟 vs SUPO 61 分钟（摘要更短反而更快），Log 56 vs 84 分钟。

### 5.4 RL 前后对比：增益从哪来

| 任务 | RL 前 | RL 后 | Δ | 论文归因 |
| --- | --- | --- | --- | --- |
| CB Log Triage | 75.0 | 95.3 | **+20.3** | 查询构造与证据聚合改善（查找+计数） |
| BCP-Multi | 40.9 | 46.9 | +6.0 | 搜索时机、查询构造、证据复用 |
| CB KV Store | 93.9 | 97.4 | +3.5 | 精确值检索的查询更准 |
| AMA file | 46.9 | 46.3 | −0.6 | 状态转移/因果推理非检索优化所能及 |
| AMA stream | 45.8 | 46.1 | +0.3 | 同上 |
| **五任务平均** | **60.5** | **66.4** | **+5.9** | RL 前即已领先（基线 MemGPT RL 后 54.1→56.3） |

值得注意的是：RL 前 GrepMem 平均 60.5% 已高于所有基线 RL 后的值——机制本身的价值先于训练；RL 的作用是**放大**（尤其把"会写查询"练出来，Log +20.3pp），而非制造差距。

### 5.5 缩放实验

ContextBench 流长从 1×拉到 30×（KV）/20×（Log）窗口：SUPO 与 Masking 随长度增长精度趋零，GrepMem 全程保持高位（KV 恒高，Log 经 RL 后长流上进一步提升）；MemGPT 在 Log 上稳定但停在约 50%。差距随输入变长而拉大——历史越长，可搜索的完整历史越值钱。

## 六、效果优势的根源解释

### 6.1 因果链：为什么赢、为什么有时不赢

**第一环（约束分析）：摘要压缩必须在需求已知前决定保留什么。** 摘要本质是"未来需求的预判"，而 BCP-Multi 一个会话压缩 25–27 次、ContextBench 问题在输入结束后才揭晓——预判不可能总对。〔论文实验支持：SUPO/Masking 在 CB 上 6.6–20.7%〕

**第二环（内容分析）：精确值、日志条目、早前搜索发现恰是摘要易丢的。** 它们的特征是"词面细节"——哈希尾、时间戳、docid、候选答案的分数——对当前推理无关紧要所以被摘要略去，但提问恰恰问它们。〔论文实验支持：KV/Log 题型设计与 SUPO 崩溃点吻合；CompAct-Bench 外部佐证：压缩失败常因状态扭曲而非泛泛的"信息丢失"〕

**第三环（机制解耦）：把"压缩工作上下文"与"访问过去"拆开——无损日志 + grep 正则词面锚点回取。** 因为原件逐字保留，细节的词面就是检索锚点，正则可精确命中，无需嵌入/索引/抽取。SUPO 摘要循环原样保留（当前推理仍靠便签），只是不再销毁仓库。〔机制设计〕

**第四环（可证伪预言）：需要词面细节的任务大幅提升；问题可由摘要承载的任务增益消失。** 若机制价值真来自"找回被摘要省略的细节"，则：KV Store 97.4% vs SUPO 13.9%（+83.5pp）应当发生；AMA stream 的问题多为因果/状态变化——摘要本来就能保住——则增益应当消失。实测 stream 仅 +0.9pp 不显著、长于窗口的轨迹上 +2.3pp [−0.2, 4.9] 亦不显著。AMA file 更妙：所有策略都拿到 grep_trajectory（人人有检索），差距即消失（46.3 vs 46.4/45.5）——排除了"GrepMem 的模型更会搜索"这一混淆解释，坐实"价值来自对自身历史的无损访问权"。〔论文实验支持〕

**第五环（训练放大）：RL 改进查询构造，把检索收益兑现。** Log Triage +20.3pp 最大，正因它同时考查找与计数——最依赖查询质量；AMA 两任务 RL 前后几乎不动（−0.6/+0.3pp），因为其瓶颈在因果推理而非检索。〔论文实验支持〕

**第六环（对结构化记忆的赢法）：MemGPT 的失败不在"没保留"而在"基础设施税"。** MemGPT 同样保留可检索历史（CB KV 99.9% 甚至更高），但结构化记忆卡三重税：token 成本 3.4×（8.60M vs 2.51M/流）、每流数百次 LLM 调用（391 vs 154）、Log Triage 计数类操作下 archival/BM25 检索语义拖累（50.0% vs 95.3%）。〔论文实验支持〕

### 6.3 综合判断与未决问题

**多研究共同支持的机制**：(1) 有损压缩系统性丢失词面细节（本文 + CompAct-Bench + CLM 的 ContextBench 试点研究三方一致）；(2) agent 控制的迭代词法检索可替代预建结构（本文 + ReFind + Sen et al.）。**仍属推测的部分**：RL 增益的具体来源（查询构造 vs 搜索时机 vs 证据复用）论文只有归因分析、无消融分离；MemGPT 在 Log Triage 卡在 50% 的确切原因（检索语义 vs 记忆卡编辑负担）亦未拆解。**优势成立条件**：问题的证据存在于 agent 自身历史、且可由词面锚点命中。**可能失效条件**：语义鸿沟大的问题（同义改写、跨语言）、需要全局抽象综合的问题（ReFind 作者也承认摘要在此不可替代）、隐私敏感部署（完整日志本身就是敏感面——论文 Ethics Statement 自认）。

## 七、必要知识反推

假设一个零基础的人要复现这项工作，最少需要知道什么？

### 7.1 领域知识层

- **agent 交互循环与上下文窗口机制**：不懂"消息/工具调用/工具输出如何拼进 prompt、窗口满会怎样"，就无法定位压缩触发点；
- **摘要压缩循环（SUPO）**：本文直接在其上扩展，必须理解"摘要→重启→继续"的循环与它的策略梯度分解；
- **正则表达式与日志检索实践**：grep_history 的分页/上下文行/count 模式设计，来自对"程序员怎么在日志里找东西"的深刻模仿——`doc_8812|born in 19\d\d` 这样的示例查询是工程师直觉的产物。

### 7.2 方法论知识层

- **GRPO 系 RL 训练**：std 归一化组内优势、裁剪、KL 惩罚、动态采样、离策略校正——以及关键的"回合级共享优势"设计（摘要与 grep 无单独奖励，信用跨压缩边界反传）；
- **五类上下文管理策略的原论文细节**：Masking 的退化顺序、MemGPT 的三层记忆与预警协议——基线还原失真会让对比失效；
- **评测方法论**：bootstrap 置信区间、配对比较、"问题揭晓时机"作为控制变量——这是因果链可证伪性的来源。

### 7.3 工程知识层

- **RL 训练基础设施**：rLLM on verl + vLLM rollouts，24×H100 的训练/推理 GPU 配比（8 FSDP + 16 rollout），约 6K H100 小时的预算规划；
- **日志工程的边界处理**：压缩调用如何塞进窗口（按字符估 token、丢最老轮次、截最新输出）、grep 输出防自我膨胀、10 秒超时——魔鬼全在细节里；
- **评测 harness 的一致性**：论文甚至发现并修复了自己评测 harness 丢弃摘要的 bug 并重测——没有这种严谨，RL 前后对比不可信。

### 7.4 知识融合的关键节点

真正的创造性火花在于三处融合：(1) 把"程序员 grep 日志"的日常实践升格为 agent 记忆的完整访问层；(2) 认识到 agent **自己的历史**天然满足词法检索的前提（词面都见过），从而规避外部语料的词汇鸿沟难题；(3) 把"问题揭晓时机"从评测细节提升为因果诊断工具，让增益与不增益同样成为证据。

## 八、论文中可以提取的通用性灵感

**灵感一：把"管理空间"与"访问历史"解耦。** 存储便宜时，销毁是设计选择而非必然。论文证据：日志无损保留 + 桌面摘要的解耦，使 KV Store 从 13.9% 到 97.4%。推广场景：数据库临时表 vs 归档表分离；IDE 内存索引 vs 全量 git 历史；浏览器标签页管理（活跃标签精简、完整会话可搜索）；个人笔记（便签 + 全文检索仓库）。

**灵感二：在需求揭晓前，避免任何不可逆决定。** 压缩、抽取、摘要都是"提前下注"。论文证据：问题后揭晓的任务上，有损基线趋零而本文保持。推广场景：特征工程中的过早特征选择；ETL 中的早期降采样；缓存淘汰策略（LRU 不可逆驱逐 vs 可找回层）；法务/医疗记录留存策略。

**灵感三：词面锚点是 agent 自身历史的天然检索键。** agent 见过的字符串就是最可靠的键，不需要语义索引。论文证据：正则 grep 无索引即达 97.4%，MemGPT 带索引反在计数任务上 50%。推广场景：聊天记录回溯（ReFind 已证）；自动化测试的日志断言；代码考古（git log + grep）；审计追踪。

**灵感四：机制的收益要用"它应该失效的地方"来检验。** 增益消失处（AMA stream +0.9pp 不显著）与增益爆发处同样 informative。推广场景：任何消融设计——预测方法在哪类问题上不该赢，再去验证；A/B 测试中寻找"无差异子群"以定位真实作用路径。

**灵感五：RL 的价值在于兑现机制红利，而非创造机制。** RL 前 GrepMem 已 60.5% 领先全部基线；RL 只是放大（Log +20.3pp）。推广场景：先设计对的无监督机制骨架，再用学习放大；检索增强、工具使用类系统的训练优先级排序。

**灵感六：简单基线是复杂系统的照妖镜。** "纯文本日志 + grep"这个近乎玩笑的方案把结构化记忆系统拉下马，说明领域存在"架构增生"惯性。推广场景：任何新系统立项前先跑最 naive 的基线；评估一个领域的成熟度，可看其最简可行方案与 SOTA 的差距。
