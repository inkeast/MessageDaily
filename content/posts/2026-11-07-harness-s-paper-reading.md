## 一、论文背景

### 1.1 什么是 Harness：模型之外的"半个大脑"

一个 agent 的表现 = 模型策略（policy）× 执行系统（harness）。Harness 指的是提示词、工具接口、上下文与记忆机制、以及约束策略与环境交互的执行规则的总和。即使模型权重完全不动，换一个 harness，agent 接收到的信息和决策变成动作的方式也会彻底改变：

- **ReAct**（论文引用 Yao et al., 2023b）证明了"推理与行动交错"这一表示方式的价值；
- **SWE-agent**（Yang et al., 2024b）证明了 agent-计算机接口（ACI）的设计直接决定软件工程任务的成败；
- 近期的 **Meta-Harness、HarnessX、Life-Harness** 等工作（Lee et al., 2026; Chen et al., 2026b; Xu et al., 2026）进一步把 harness 本身当作可自动优化的对象。

可以把 harness 类比为"新员工的入职手册 + 工位配置"：同一个毕业生（模型），配不同的手册、工具栏、审批流程（harness），产出可能天差地别。

### 1.2 Harness 优化路线的两大痛点

现有工作大多沿两条路线优化 harness：

1. **寻找"普遍更优"的 harness**：把各种局部修复累积进一个设计。问题是不同修复可能要求互相冲突的执行方式，即使兼容的编辑也会彼此干扰——单一大而全的 harness 会丢掉各变体的长处。
2. **Harness 与策略交替共同演化**（如 Co-Harness、WHALE）：每轮策略更新后，此前的修复对新策略可能失效，需要反复生成和验证变体，演化成本高；而且"策略+配套 harness"这对组合的收益，在策略回到基础 harness H0 时可能无法保留。

### 1.3 本文观察到的三性质（动机核心）

论文在"从公共基础 harness H0 出发做 harness 演化"这一设定下（实验场景为 Qwen3.5-4B + AppWorld），系统识别出三个性质（Figure 1）：

- **局部性（Locality）**：harness 编辑往往只修复一部分失败任务，同时在原本已解决的任务上引入回退。Figure 1a 中四个变体的"修复数 − 回退数"（ΔSolved）分别为 +15、+8、+10、+3——修复的同时总伴随回退。
- **互补性（Complementarity）**：兄弟 harness 之间可以互相补救。对 H1–H4 各执行一次的 oracle 并集覆盖率达 65.65%，而同样 rollout 预算下 H0 pass@4 只有 44.66%（个体成功率 32.82%–37.40%）。多样执行行为带来覆盖面净增益。
- **非平稳性（Nonstationarity）**：harness 的效用随策略学习而变化。某个变体相对 H0 的优势会变成劣势，变体间的排序会随策略检查点翻转（Figure 1c 中 ΔSolved 随训练步在 +15、−1、−4、+6、+4、+1 间波动）。

这三条性质合起来指向一个结论：**不要找"最好"的 harness，而要维护一个"互补"的 harness 池，并且路由必须随策略更新而刷新**。这就是 Harness-S 的出发点：用兄弟 harness 选择性救援基础系统的失败，再把获得的能力沉淀进单一策略，使其回到 H0 时依然有效。

## 二、论文定位和关联工作

按论文 Related Work（第 2 节）与扩展相关工作（附录 H）梳理，相关研究可分四条谱系：

### 2.1 谱系一：Harness / 执行设计演化

| 工作 | 核心思想 | 与 Harness-S 的关键区别 |
|---|---|---|
| ADAS / Darwin Gödel Machine（Hu et al., 2025; Zhang et al., 2026a） | 用代码演化自动设计 agent 结构，维护可执行 agent 档案库 | Harness-S 不递归重设计 agent，而是保留互补的局部修复变体 |
| Meta-Harness（Lee et al., 2026） | 端到端优化模型 harness，提出者可读历史实现/分数/轨迹 | Meta-Harness 产出单一 Hbest；Harness-S 证明保留整个兄弟池 + 按任务路由更优（HE-only 对比见主表） |
| Harness-R1 / RRSI / SpecForge（Shao et al., 2026; Xia et al., 2026; Cheng et al., 2026） | 让编辑策略自身可学习 / 正则化 harness 编辑促迁移 / 从执行反馈精炼行为规约 | 这些方法优化"如何产生 harness 编辑"；Harness-S 优化"如何用固定 harness 池训练策略" |
| HarnessX / Life-Harness / EvoHarness-RL（Chen et al., 2026b; Xu et al., 2026; Ning et al., 2026） | 可组合/自适应/可演化的 harness 铸造厂，或运行时协调 | 同上，属于"harness 侧"演化；Harness-S 关注能力向策略参数的转移 |

### 2.2 谱系二：Harness 与策略联合优化（最直接的竞品）

- **HarnessBandit**（Wei et al., 2026）：用可学习性与跨 harness 可迁移性信号，在每个优化器步调度一个 harness。Harness-S 的分配单位不同——是"H0 下全失败的任务"，只有全失败组才触发救援。
- **HarnessX**（Chen et al., 2026b）：把 harness 演化与跨 harness GRPO 耦合在共享回放缓冲上，按任务跨 harness/策略版本分组。Harness-S 不做耦合演化：池在训练期固定，只用行为画像刷新路由证据。
- **WHALE**（Kim et al., 2026）：交替 Meta-Harness 式搜索与拒绝采样微调（实验中的最强联合基线之一）。
- **HarnessForge / Co-Harness**（Chen et al., 2026a,c）：演化配对的 harness-策略分支 / 交替 harness 与模型权重更新。
- **关键差异**：这些联合方法的收益绑定在"演化出的配对"上；Harness-S 的评价协议是**回到 H0 测试**，专门检验收益是否在撤掉辅助执行支持后仍然保留。

### 2.3 谱系三：Agent RL 训练

GRPO（Shao et al., 2024）是本文共享优化器的基线；DAPO（Yu et al., 2025）用动态采样过滤全对/全错组；RAGEN 研究 rollout 多样性与反馈；LOOP、AgentGym-RL、Agent Lightning 在有状态环境（含 AppWorld）训练长程 agent。这些工作都在"如何从环境结果中学习"上发力，但都不改变产生经验的执行系统本身——Harness-S 的切入点恰恰是：在放弃一个任务之前，先换执行支持再试一次。

### 2.4 谱系四：知识迁移

经典蒸馏（Hinton 2015；Kim & Rush 2016）、Policy Distillation（Rusu et al., 2016）、Kickstarting（Schmitt et al., 2018）、STaR/Expert Iteration（Zelikman 2022; Anthony 2017）、特权信息学习（Lopez-Paz 2016; Learning by Cheating, Chen 2019）。Harness-S 与它们同构的地方是"训练期获得部署期没有的支持，再把能力留下"；独特之处在于"教师"不是一个更强的模型，而是**同一策略在不同执行上下文中的自己**。

### 2.5 定位总结

| 维度 | 之前的路线 | 本论文的突破 |
|---|---|---|
| Harness 优化目标 | 找单一最优 harness（Hbest） | 保留互补变体池，按任务定向使用 |
| 与策略的关系 | 交替共同演化 / 配对绑定 | 池固定，策略单向从救援经验中学习 |
| 评价协议 | 用演化出的 harness 评测 | 强制回到 H0 评测，检验能力内化 |
| 路由证据 | 静态分数 / 每步调度 | 行为画像 + 多 LLM 投票 + 随策略再锚定 |
| 训练触发 | 全任务混合 harness | 仅 H0 全失败任务触发救援 |

一句话定位：**Harness-S 是首个把"harness 互补性"当作可训练资源、以"全失败任务定向救援"为分配单位、并以"撤掉辅助后仍有效"为检验标准的 agent 训练框架。**

## 三、问题定义

### 3.1 从具体场景到抽象问题

具体问题：策略在基础 harness H0 下对任务 x 的 K 次采样全部失败，GRPO 对该任务没有任何组内奖励对比（全 0 奖励组梯度为零），这个任务在本次更新中被浪费。

核心洞察：**失败的根源常常不在策略"不会"，而在"harness 提供的执行支持与该任务不匹配"**。换一个互补的执行上下文，同一策略可能就走通了。走通之后产生的"成功-失败"对比，恰恰是 GRPO 最缺的学习信号。

这可以类比为一个深度学习中的经典结构（论文附录 H.2 给出了对应谱系）：

| 深度学习/经典 RL 概念 | Harness-S 中的对应物 |
|---|---|
| 教师/特权信息（Learning by Cheating） | 兄弟 harness 提供的辅助执行支持 |
| 知识蒸馏（学生最终独立工作） | 训练后策略回到 H0 独立执行 |
| 数据增强 | 同一任务在不同 harness 上下文中的重采样 |
| 课程/探索（Go-Explore 先回到前沿状态再探索） | 全失败任务先换 harness 再生成新 rollout |
| 非平稳环境下的再校准 | 策略检查点处的行为画像再锚定 |

### 3.2 形式化定义

- 策略 πθ 在 harness H 下生成轨迹 τ ~ p_{θ,H}(·|x)，验证器给出 R_x(τ) ∈ {0,1}。
- harness 效用定义为其期望成功率：u_θ(H,x) = E_{τ~p_{θ,H}}[R_x(τ)]。注意效用显式依赖 θ——这就是非平稳性的形式化来源。
- **给定**：兄弟池 H = {H0, H1, …, HM}（同源、共享执行基础/环境接口/验证器、同一策略参数）、训练任务分布、共享 GRPO 优化器。
- **求**：策略参数 θ*，使得在 H0 下的期望成功率最大化（而不是在某个演化 harness 下）。
- **约束**：救援 rollout 预算有限（每个全失败任务 K 个救援 rollout）；池的实现训练期间不可变；测试时不得额外更新。

### 3.3 这个抽象的精妙之处

把优化目标定在"撤掉辅助后仍有效"，等价于把 harness 从"部署组件"重新定义为"训练脚手架"。评价协议本身（回 H0 测试）就杜绝了"靠外挂拿分"的捷径——这是论文实验设计里最关键的一步棋。

## 四、问题解法

Harness-S 全流程分三个阶段（Figure 2）：离线定向演化 → 救援训练 →（推理期）Rank-1 路由。

### 4.1 阶段一：Directional Harness Evolution（构建兄弟池）

类比：**遗传算法中的"分支保留"而非"精英收敛"**——不把所有好基因挤进一个个体，而是保留多个特长个体。

流程（AppWorld 实际配置，附录 F）：

1. **失败归因**：在 P1={H0} 上执行新鲜训练任务（Qwen3.5-4B Base、贪心解码、每任务 1 rollout、seed 42），分析 prompt 要求把每个失败归到根因组或标记未解决。
2. **定向编辑**：编辑器（GLM-5.3，温度 0.6，high reasoning effort）针对"2–3 个相关根因、每个根因至少 2 个不同失败任务"生成子 harness；可编辑六类组件：Prompt、Skill、Context、Memory、Hooks、Tool View（明确禁止默认只改 prompt）。
3. **本地验证**：每个候选最多在 30 个任务上测试（含最多 10 个成功对照），可提交一版修订。
4. **父代选择**：按联合验证覆盖最大化选至多 B=4 个父代（每个任务只计一次，偏向互补的父代组合）。
5. **池累积**：所有可执行、协议合规的子代都进池（不只是被选为父代的）。AppWorld 搜索共 3 轮，提案预算 7/8/8。

论文给出三个具体兄弟编辑的例子（附录 D，Table 7），直观展示"局部修复"长什么样：

| 兄弟 | 编辑内容 | 对应行为画像（prefer 条目） |
|---|---|---|
| S6 | after_tool 钩子：检测到分页元数据时提醒"翻页直到空页/权威总数" | 跨 inbox/spam/archive 聚合信息时完整分页并去重（H0 只查第一页） |
| S7 | action_guidance 规则：组合条件要求"分别检索后取交集" | 查"本月退回的办公桌"时按产品名∩时间联合过滤（H0 泛化了条件） |
| S8 | 低预算钩子：剩余步数 ≤3 时提醒"完成必要验证并留一步提交" | 验证完成后用 complete_task 提交（H0 得出结论却没提交） |

最终池：H0 + 19 个辅助 harness = 20 个，训练期间实现完全固定。

### 4.2 阶段二：Complementary Harness Rescue Training（核心训练循环）

类比：**DAPO 的动态采样解决"全对/全错组无信号"，Harness-S 用"换执行上下文重采样"解决同一问题**——但不是丢弃，而是换 harness 重新生成。

Algorithm 1 的每批处理：

1. 任务 x 在 H0 下采样 K=8 个 rollout，得 G0(x)。
2. 若有成功 → 保留 G0(x) 正常 GRPO。
3. 若**全部失败** → 路由器选出 Top-K=8 个辅助 harness（S_K^{(s)}(x)），**同一策略**在每个选中 harness 下从任务初始状态各生成 1 个新 rollout，得 GR(x)。
4. 保留组 G(x) = GR(x)（**替换**失败的 G0(x)）。
5. 在保留组上做 GRPO 更新：组内中心化+标准化优势 a_{x,j} = (R − r̄_x)/max(σ_x, ε)，ε=10⁻⁶；PPO 式裁剪目标，裁剪宽度 η⁻=0.20、η⁺=0.28，无参考模型 KL 项。

两个关键实现细节（附录 B）：

- **只有策略 token 进损失**：harness 注入的指令与工具观测被排除在 token 损失之外——模型不为"外挂说的"负责，只为"自己做的"负责。
- **生成上下文保留**：救援轨迹计算概率比时保留其生成时的 harness 上下文 c_H；对 rollout 后端与训练后端概率不一致的 token，用截断重要性权重 w=clip(π_old/q, 0, 2) 修正。

为什么"替换"而不是"混合"？救援组内若同时含成功与失败，就制造了原本不存在的组内奖励对比——这正是 GRPO 的燃料。

### 4.3 阶段三：Adaptive Harness Router（会学习的选择器）

路由器要回答："对这个失败任务、对当前策略，哪些兄弟 harness 最可能救回来？"它综合三类证据：

1. **Harness Behavior Profiles（行为画像）**：P_i^{(s)} = (prefer 列表, avoid 列表)，每个条目形如 {When: 任务条件, Behavior: 相对 H0 的行为差异}。由 LLM 从**配对验证轨迹**（同任务、同初始状态、同执行限制下 H_i vs H0）中归纳。例（论文插图）："查办公桌是否本月退回时——[prefer] 行为层联合过滤名字与日期；[avoid] 下单时——行为会加未请求的商品"。
2. **验证成功率**与**相似验证任务上的结局**。
3. **多 LLM 投票**：V 个投票者独立对候选排名，每张票给前 4 名权重 1、3/4、1/2、1/4，未列名 0 分；总分 q(H|x) 排序取 Top-K。

**Policy-aware 再锚定（应对非平稳性）**：每 10 次更新（AppWorld 4B 设置）冻结当前策略，在每个 H_i 与 H0 上重新跑配对验证执行，刷新画像与统计量（Eq. 11）。测试结果被排除在外。这保证路由证据始终匹配"当前"策略——论文 Table 2 证明这一步值 4.71 个 Avg@3 点。

### 4.4 推理期复用：Rank-1 路由

训练完成后做最后一次画像再锚定，推理时对每个任务从**含 H0 的全池 20 个**中选 Top-1：

Ĥ(x) = argmax_H q*(H|x)

选择发生在执行之前、rollout 数不变——即"不加推理成本的任务级 harness 个性化"。

### 4.5 全景对比表

| 组件 | 输入 | 输出 | 类比 |
|---|---|---|---|
| 定向演化 | H0 + 失败轨迹根因 | 固定兄弟池（20 个） | 遗传算法分支保留 |
| 救援训练 | 全失败组 + Top-8 兄弟 | 替换组（含成功/失败对比） | 特权信息蒸馏 + 动态采样 |
| 自适应路由器 | 画像 + 验证证据 + 投票 | 每任务 Top-K harness | 非平稳环境下的上下文 bandit |
| Rank-1 推理 | 最终画像 | 每任务 1 个 harness | 模型路由（RouteLLM 思想） |

## 五、评估指标与实验证据

### 5.1 实验设置

- **模型**：Qwen3.5-4B / Qwen3.5-9B（同一策略，训练与救援共用）。
- **基准**（附录 A，任务数 Train/Val/Test）：
  - AppWorld（应用 API 编排）：320/150/262，共 732；
  - DBBench（数据库操作）：1600/200/300，共 2100；
  - SWE-Gym（软件工程）：240/100/160，共 500。
- **指标**：Pass@3（3 次 rollout 至少 1 次成功的任务比例）、Avg@3（3 次成功率均值）。主表为 3 次独立随机实验的均值（Harness-S 报告跨 run 标准差）。
- **算力**：8 张 NVIDIA H800；外部模型（编辑器/投票器）用量按 API token 单独报告。
- **前沿参照**（非对比对象，仅作参照）：GPT-6-Sol、DeepSeek-v4-Flash、GLM-5.3-Flash 在 H0 下的成绩。

### 5.2 主结果（RQ1，Table 1）：全面超越三类基线

4B 关键数字（Pass@3 / Avg@3）：

## 六、效果优势的根源解释

*（按本次精读执行约束，本节外部交叉验证基于论文自述的相关工作谱系与实验证据展开，未做独立外部检索；推测性内容已明确标注。）*

### 6.1 根源机制与证据链

**因果链 1：全失败组 → 零梯度问题 → 换上下文恢复对比信号**

- GRPO 的优势是组内相对量（Eq. 6）：全失败组 R 全 0 → σ=0、优势全 0 → 该任务对更新无贡献。全失败组越多，有效样本越少。【论文实验支持：GRPO EG 率仅 64.69%，两个混合基线同样停滞】
- Harness-S 不丢弃全失败任务，而是换 8 个互补执行上下文重新采样——互补性（oracle 并集 65.65% vs H0 pass@4 44.66%）保证其中一部分能被救回。【论文实验支持：EG 率升至 79.38%，终点验证 63.33% vs 48.00%】
- 救回的组天然含成功/失败对比，GRPO 拿到非零梯度。【机制上成立，论文 Figure 3 直接展示】

为什么"换 harness 重采样"优于"同 harness 重采样"（H0 rescue 只到 70.94%）？因为 H0 下 8 连败的任务在 H0 下第 9–16 次尝试的成功率先验很低（失败相关），而兄弟 harness 修复的恰是不同根因——S6 补分页、S7 补交集、S8 补提交，各管一段。这是**信息来源的多样化**，不是采样次数的堆叠。

**因果链 2：只对策略 token 计损失 + 保留生成上下文 → 能力留在策略而非外挂**

- 若把 harness 注入的指令也算进损失，模型会学到"依赖外挂提醒"；排除这些 token 后，梯度只强化"策略自己在该上下文中的决策"。【论文机制设计，附录 B】
- 行为学验证：训练后 H0 下查 schema 67.6%（GRPO 38.2%）、阻断后改断言 48.5%（GRPO 13.3%）、Rank-1 对 H0 优势缩到 0.76 分、H0 被路由器排第一的比例升至 22.52%。【论文实验支持】

**因果链 3：再锚定对抗非平稳性 → 路由持续命中**

- 非平稳性（Figure 1c）意味着旧画像会误导新策略下的路由。每 10 步用冻结策略重跑配对验证刷新画像，使选择依据始终"与时俱进"。【论文实验支持：自适应 vs 固定画像 Avg@3 56.87 vs 52.16，救援成功率四个阶段全面领先】

**因果链 4：为什么固定混合失败（57.63/58.78 < 60.31）而定向救援成功**

- 固定混合把兄弟 harness 的 rollout 摊到**所有**任务上：对 H0 已能解决的任务，多样化上下文反而稀释了"本可以强化的成功经验"，甚至引入无关失败；只有全失败任务才需要多样化。【论文实验支持：两混合基线 EG 率与最终分均低于纯 GRPO；此解释的"稀释"机制为阅读者推测，论文未单独消融】

### 6.2 相关工作对照（基于论文 Related Work/附录 H 的谱系）

| 研究（论文内引用） | 相似尝试 | 相关结论 | 与本文的差异 | 对根源解释的影响 |
|---|---|---|---|---|
| DAPO（Yu et al., 2025） | 动态采样过滤全对/全错组 | 同样认识到均匀奖励组限制组相对更新 | DAPO 直接丢弃，Harness-S 换上下文再生 | **支持**因果链 1 的问题诊断 |
| Learning by Cheating（Chen et al., 2019）/广义蒸馏（Lopez-Paz et al., 2016） | 训练期特权信息→部署期无特权策略 | 训练期额外支持可内化为部署期能力 | 特权是环境状态，Harness-S 的特权是执行上下文 | **支持**因果链 2 的迁移假设 |

| DAgger（Ross et al., 2011） | 学习者分布下的专家反馈 | 训练分布匹配是独立设计选择 | 分布偏移视角解释再锚定必要性 | **支持**因果链 3 |

### 6.3 综合判断与未决问题

**多证据共同支持的机制**：(1) 全失败组是 GRPO 训练的结构性浪费，恢复组内对比是提升的近因（DAPO + 本文 Figure 3 双重印证）；(2) 训练期辅助支持可以内化为部署期能力（Learning by Cheating 谱系 + 本文 RQ4/RQ5 行为与路由证据）。

**仍属推测或单源支持的机制**：(1) "固定混合稀释成功经验"的具体机制（本文仅有效果证据，无机制消融）；(2) 多 LLM 投票优于单一 LLM 路由的程度未单独报告；(3) 行为画像的 prefer/avoid 条目质量对最终增益的敏感度未知。

**适用条件**：需要可验证的任务结果（R∈{0,1}）与可配对执行的验证集——开放端任务需先解决验证器问题；兄弟池的互补性上限受 H0 失败结构约束（若失败全因模型能力不足而非执行支持，救援率会塌缩）。

**可能失效条件**：池过小或兄弟高度重叠（附录 E 显示重叠均值 62.47% 已不算低）；策略更新极快而再锚定频率跟不上；任务分布漂移导致画像失配。

## 七、必要知识反推

假设让一个零背景的人重做这项工作，他至少需要：

### 7.1 领域知识层

- **Agent = 策略 × harness 的解耦观**：不知道 ReAct/SWE-agent 建立的"执行设计决定行为"共识，就不会想到把 harness 当训练资源。
- **长程 agent 任务的失败结构**：AppWorld/SWE-Gym 式任务里失败高度模式化（分页遗漏、条件泛化、忘记提交、验证通道被阻断）——这是根因归组可行的前提。
- **验证器与任务结果语义**：R_x ∈ {0,1} 的确定性验证是整个救援-强化闭环的地基。

### 7.2 方法论知识层

- **GRPO 组相对优势的数学**：必须精确知道全失败组梯度为零，才能定位"恢复组内对比"这一杠杆点（并联系 DAPO 的先例）。
- **蒸馏/特权学习理论**：判断"训练有外挂、部署无外挂"的能力转移是否可信，以及该用什么证据（行为频率、held-out 案例、依赖度下降）检验。
- **非平稳环境下的路由/再校准**：理解 u_θ(H,x) 依赖 θ，才会设计画像再锚定而非静态路由表。
- **进化搜索的档案保留思想**：来自 ADAS/DGM 谱系——保留互补分支而非精英收敛。

### 7.3 工程知识层

- **可配置 harness 系统**：六类可编辑组件（Prompt/Skill/Context/Memory/Hooks/Tool View）与协议合规校验，让"编辑 harness"成为可执行操作。
- **RL 训练基础设施细节**：token 级损失掩码（策略 token vs 注入 token）、生成上下文保留、rollout/训练后端概率失配的重要性修正（w=clip(π_old/q,0,2)）——任何一处做错，迁移都会被污染。
- **成本核算**：搜索 rollouts、训练 rollouts、GPU·h、API tokens 的分项记账能力，才能与 WHALE/HarnessForge 公平对比。

### 7.4 知识融合的关键节点

1. **洞察节点**：把"harness 演化的三性质"（领域观察）翻译成"池固定 + 路由刷新"的系统约束（方法论）——局部性⇒保留分支；互补性⇒救援有收益；非平稳性⇒必须再锚定。三性质不是罗列，每条直接对应一个设计决策。
2. **算法节点**：把 DAPO 式的"无效组问题"与蒸馏式"特权支持"两个不相邻文献谱系焊接成"救援组替换 + 仅策略 token 损失"。
3. **验证节点**：发明"回 H0 测试 + Rank-1 依赖度变化"的评价协议，使"能力内化"从口号变成可测量。

## 八、论文中可以提取的通用性灵感

### 灵感 1：不要合并专家，要维护专家池 + 按例路由（范式迁移类）

- **核心思想**：当多个"修复"互相冲突时，放弃"集成成一个万能方案"，改为保留互补变体、按输入实例定向调用。
- **论文证据**：单变体修复 11–15 个失败而并集 29 个（附录 E）；Meta-Harness 单一 Hbest 仅 48.09（AppWorld 4B）vs Harness-S HE-only 56.87。
- **推广场景**：① 推理引擎配置调优（不同 workload 路由不同 kernel 变体）；② 数据清洗规则库（冲突规则共存，按行特征路由）；③ 编译器 pass 调度；④ 临床诊疗方案选择；⑤ 代码 review 规则集。

### 灵感 2：全失败信号是"换条件重试"的触发器，不是丢弃的理由（信号利用类）

- **核心思想**：一组全失败的样本在组相对方法（GRPO/A2C 类）里零梯度，但它携带的信息是"当前条件不匹配"——改变生成条件（上下文/工具/约束）再试，比同一条件下加倍采样更有效。
- **论文证据**：EG 率 79.38% vs H0 rescue 70.94%（同样的额外预算、不同分布）；两个固定混合基线低于纯 GRPO。
- **推广场景**：① 数学推理 RL 中对全错题换提示模板/工具重采样；② 自动超参搜索中失败 trial 换骨架；③ 多臂 bandit 的 context 扩充；④ LLM 评测中失败项的 harness 诊断；⑤ 机器人任务的控制器切换。

### 灵感 3：训练期特权必须在损失层面与部署对齐（关注点分离类）

- **核心思想**：想让"训练时有辅助、部署时无辅助"的能力转移成功，必须把辅助产生的内容从学习目标中剥离（只学自己的决策，不学依赖外挂）。
- **论文证据**：harness 注入指令与工具观测不计损失；训练后 H0 下行为频率全面改善、Rank-1 依赖从 14.21 分缩至 0.76 分。
- **推广场景**：① 知识蒸馏中的 hint 屏蔽；② 教学中的脚手架撤离（scaffolding fading）设计；③ 辅助驾驶→手动驾驶的能力交接训练；④ 带 coach 的模拟训练→无 coach 实战；⑤ IDE 辅助编程下的人才培养评估。

### 灵感 4：非平稳系统中的选择器必须周期性再锚定（机制类）

- **核心思想**：任何"为当前模型/系统挑选最优配置"的组件，其证据都有保质期；主系统每变化一轮，选择器的校准数据就应刷新一轮。
- **论文证据**：自适应画像 vs 固定画像 Avg@3 56.87 vs 52.16（+4.71）；Figure 1c 中变体优势随训练翻转。
- **推广场景**：① MoE 路由器的定期重校准；② 推荐 system 中 feature 漂移下的召回池刷新；③ 编译器 heuristic 随芯片微架构更新；④ 招聘测评工具的常模更新；⑤ 风控规则库随攻击手法演化。

### 灵感 5：评价协议本身可以成为方法论贡献（评测类）

- **核心思想**："回到最差/最简配置下测试"这一协议设计，能把"真内化"与"靠外挂"在指标上强制分离，倒逼方法做真正的能力转移。
- **论文证据**：所有对比均在 H0 下评测（联合基线被迫也交出 H0 成绩），Rank-1 增益与 H0 依赖度共同构成内化证据。
- **推广场景**：① 工具增强模型的"无工具模式"评测；② Copilot 产品的"关掉补全"留存测试；③ 教育评估中的闭卷复测；④ RAG 系统的"检索关闭"鲁棒性项；⑤ 团队对顾问依赖度的"顾问离场"检验。

### 灵感 6：小模型 + 定向执行编排可以越级挑战大模型（跨域迁移类）

- **核心思想**：当任务失败可归因、执行支持可配置时，把算力投在"为每个失败实例找到合适的执行上下文"上，性价比可能高于投在模型规模上。
- **论文证据**：路由版 4B 全面超过 9B GRPO(H0 rescue)；9B Rank-1 DBBench 78.00 超过 GPT-6-Sol 参照 71.33。
- **推广场景**：① 边缘设备的任务级引擎切换；② 客服系统的难例升级路由；② 搜索系统的 query 改写器池；④ 量化交易的多策略切换；⑤ 医学影像的多读者协议（multi-reader）诊断。
