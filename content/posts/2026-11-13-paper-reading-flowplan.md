## 一、论文背景

### 1.1 LLM 编码 agent 很强，但账单很吓人

LLM 编码 agent（Claude Code、SWE-agent、OpenHands、AutoCodeRover 等）已经能实际处理仓库级软件工程任务：拿到一个 issue，自己去搜仓库、读源码、改代码、跑测试，最后交出一个 patch。但这个"迭代交互循环"的推理成本极高。论文基线测量：**Claude Haiku 4.5 + SWE-bench Pro 上，原生 Claude Code 平均每个 issue 消耗 370 万 token，其中 98% 是缓存读（cache reads）**。

贵在哪？在于 agent 循环的结构本身：每次模型调用都要把之前积累的整个对话重放一遍，每个工具观测结果都会让对话更长。所以修复成本有两个乘数因子——**模型调用次数 × 每次调用重放的上下文大小**。

外部研究印证了这个量级：一项对 SWE-bench Verified 上八个前沿模型的大规模测量（arXiv:2604.22750）发现，agentic coding 平均每任务消耗约 417 万 token（约 $1.86/任务），是单轮代码推理的约 3500 倍；输入输出比高达 154:1——钱主要花在"重读积累的上下文"而不是"写新代码"上。同一任务不同运行之间 token 消耗可以相差 30 倍。这些都是 2026 年编码 agent 落地的核心痛点。

### 1.2 现有降本思路：都在做"减法"

近期工作从几个方向削减成本，但共同模式是**限制、压缩或选择性跳过修复过程中的信息与动作**：

- **AgentDiet**（FSE 2026）：用第二个 LLM 周期性改写压缩积累的轨迹；
- **EET**（ACL 2026 Findings）：检索先验修复经验，用置信度估计鼓励提前终止；
- **SHERLOC**（EMNLP 2026）：在修复前跑一个专门的定位 agent，先定位再修；
- **To Run or Not to Run**（ISSTA 2026）：干脆禁止 agent 执行程序；
- **SeeRepo**（ASE 2026）：把文本仓库探索部分替换为可视化仓库图。

这些方法针对不同的开销来源，但都停留在源码文本层面：做完减法后，agent 依然要反复读源码来决定"改哪里、怎么改、改完没有"。

### 1.3 被忽视的老朋友：程序抽象

论文回到了软件工程的一条基本原理：**程序抽象**。软件工程历来用抽象来暴露任务相关的程序性质、屏蔽无关细节。控制流图（CFG，Allen 1970）展示执行如何在基本块之间移动；数据流图（DFG）展示值如何从定义传播到使用。这些是编译器和程序分析几十年的基石抽象，也已被代码属性图（CPG）、GraphCoder、Devign 等现代系统用于漏洞分析和代码检索。

作者的追问很自然：**在改源码之前，先在程序抽象层面推理，能不能降低编码 agent 的 token 消耗？** 毕竟 agent 即使已定位到相关代码，仍会继续读文件、看 diff、跑测试来决定怎么修、什么时候修完——这些动作每一轮都在膨胀上下文。

## 二、论文定位和关联工作

### 2.1 研究谱系一：agentic 软件工程中的 token 缩减

论文对 2026 年十二个 SE/ML 顶会（ICSE/FSE/ASE/TSE/TOSEM/NeurIPS/ICLR/ICML/AAAI/EMNLP/ISSTA/ACL）做了系统调研，确认 171 篇论文中 27 篇以降低 SE agent 的 token/上下文/成本/交互长度为核心贡献，18 篇有官方实现，最终选出五个可在 Claude Code 中复现的方法（见 1.2 节）作为受控对比对象。此外还有更广的相邻方向：上下文管理方法（ACON、Context-Folding、SWE-AGILE 等）压缩或选择性保留轨迹历史；提示压缩技术（LLMLingua-2）缩减单个 prompt；定位方法（FuseSearch、BLAgent 等）缩短仓库探索；资源分配类工作（turn 预算控制、budget-aware agent、测试时按需分配算力）则从外部限制交互量。

### 2.2 研究谱系二：代码表示与程序图用于 LLM

AST、调用图、依赖图、仓库级图表示（RepoGraph、LocAgent、ARISE 等）已被广泛用于支持代码导航、检索和定位。GraphCoder 用语句级控制流/依赖关系检索补全上下文；代码属性图（Yamaguchi 2014）结合语法与控制/数据流做漏洞分析。但论文指出一个关键区分：**现有仓库级表示通常只服务于"找到代码"——找到之后，修复推理就回到源码文本了**。作者团队自己此前的姊妹工作（arXiv:2611.07286，How Should Agents See Code?）系统研究了代码表示对 agentic SE 的作用，FlowPlan 是这条线在"修复成本"维度的深挖。

### 2.3 研究谱系三：程序分析驱动的自动修复

把程序分析接入修复并非全新想法：PathFix 用 CFG 上的期望路径约束引导 LLM 修复；MENTOR 用 MaxSAT 故障定位给学生程序生成 sketch 让 LLM 填空。但这些工作的目标是提高修复正确率，而 FlowPlan 借用同样的经典抽象，目标是**降低交互成本**——并首次把"编辑前的意图声明 + 编辑后的结构验证"做成显式终止条件。

### 2.4 定位对比

| 维度 | 之前的路线 | FlowPlan 的突破 |
|------|-----------|----------------|
| 干预阶段 | 修复前定位（SHERLOC）/每步后压缩（AgentDiet）/探索期替换（SeeRepo）/测试期禁跑（No-execution） | 定位、规划、验证三阶段全流程 |
| 程序视角 | 文本或仓库级图（找到即弃） | 函数级 CFG/DFG 作为持续工作层 |
| 抽象计划 | 无（意图隐式） | 编辑前显式表达为类型化图增量 |
| 完成判据 | 无或依赖自我报告置信度（EET） | 图增量匹配 = 机器可检查的终止条件 |
| 额外 LLM 调用 | 有的需要（SHERLOC/AgentDiet） | 不需要（图引擎无模型调用） |

**定位结论**：FlowPlan 是首个把函数级流图同时用于 agent 修复的"事前规划载体"和"事后验证判据"的工作，与既有 token 缩减方法正交（它不减信息，而是换一层推理表示）。

## 三、问题定义

### 3.1 从具体场景到抽象本质

具体问题：编码 agent 修一个 issue 太贵。表面做法是压缩上下文、减少动作。但论文看穿了更深层的结构：**agent 的昂贵源于它缺少一个"我改完了"的客观判据，只能用反复读代码、看 diff、跑测试这种信息密集型动作来逼近确信**。

抽象问题：把"修复"从源码文本操作提升为**抽象结构空间中的变换**——

- **状态空间**：函数的规范化图指纹（CFG 的块/边集，DFG 的定义-使用多重集）
- **操作算子**：类型化图增量（如 add_guard、remove_branch、change_condition、rewire_edge）
- **目标**：找到一个算子序列，使初始状态变换到目标状态

| 深度学习/经典概念 | FlowPlan 对应物 |
|------------------|-----------------|
| 模型参数 | 函数图指纹（结构的规范化摘要） |
| 优化方向（梯度） | 类型化图增量（显式修复意图） |
| 训练收敛判据（loss 不再下降） | 观察到的图变化 == 计划的图增量 |
| 过拟合检测（验证集） | flow_verify 审计未计划内的修改 |

### 3.2 形式化定义

**给定**：(1) 仓库级 issue 或崩溃报告；(2) 一个能读写代码、执行命令的编码 agent；**求**：一个修复策略，使得 (1) 解决率不显著下降；(2) 总 token 消耗（input+output+cache-read+cache-write）最小化。**约束**：不替换、不限制 agent 的原生工具（保留回退自由度）；不引入额外模型调用（辅助 LLM 本身也烧钱）。

### 3.3 精妙之处

这个抽象的妙处在于把"何时停止"从**认知问题**（agent 自己觉得改好了吗？）变成了**计算问题**（重建的图和计划的增量匹配吗？）。EET 靠 agent 自报告置信度终止，No-execution 靠干脆不做验证；FlowPlan 则证明：只要验证能在低维结构空间里机械化执行，验证本身可以既便宜又可靠——它用的是差分对比（指纹差异），不需要完整重读源码。

## 四、问题解法

FlowPlan 的核心设计：**关键修复决策在抽象程序层做，而不是直接在源码文本上做**。整体分四个阶段，配合五个 MCP 工具和一个 `/flowfix` skill。

### 4.1 函数级程序抽象（工作层）

类比：与其给模型看整本小说（仓库源码），不如给它看这一章的人物关系图（当前函数的 CFG/DFG）。

- **按需构建**：不为整个仓库建图，只为当前调查的函数构建视图，屏蔽无关内容；
- **CFG 视图**：基本块 + 源码位置 + 控制流边（标注 true/false/loop/return/raise 角色）；Python 从 AST 派生，C/C++ 用 Joern 构建代码属性图后按崩溃栈裁剪；
- **DFG 视图**：变量定义及每个定义到达的使用；
- **规范化指纹**：每个视图诱导一个 canonical fingerprint（CFG 为规范化的块/边集合，DFG 为定义-使用关系多重集）。编辑前记录 HEAD 状态指纹，编辑后重算——两者之差就是"观察到的图增量"。因为计划用同一套图词汇表达，观察增量可以直接和计划增量对比；
- **符号索引**：会话前用 tree-sitter 预建仓库级符号索引（SQLite，含名称/限定名/种类/文件/行号范围），每仓库一次、零模型调用。

### 4.2 五个流图工具（MCP 接入）

| 工具 | 角色 |
|------|------|
| `flow_of` | 按函数名解析符号索引，返回带源码位置的 CFG/DFG |
| `flow_locate` | 把候选缺陷锚定到被验证的图元素上；引用无效时返回最近三个合法候选 |
| `flow_plan` | 把修复意图记录为类型化图增量，并从 HEAD 快照图指纹 |
| `flow_check` | 编辑后重建图，对比观察增量与计划增量 |
| `flow_verify` | 终止前验证完整修复计划，并审计计划外修改的函数 |

关键设计细节：

- **定位是可观测决策而非硬约束**：引用错两次后保留但标记"未验证"，不人为终止修复——定位错误因此可度量；
- **计划从 HEAD 快照**：防止 agent 先改文件再调 flow_plan 导致对比基准被污染；
- **计划累积而非破坏性覆盖**：多次 flow_plan 按函数合并并追加历史，完整保留意图演化轨迹；
- **两级通用算子**：`no_flow_change`（修源码但不改流图，如纯重命名）和 `add_function`（引入新函数，此时从当前文件提取新函数构造指纹做验证）；
- **分级比对**：`exact`（计划操作直接出现在观察增量中）/`same_family`（相关操作实现了预期结构效果，如边重连达成条件变更的效果）/`mismatch`。分级避免把结构等价实现误判为失败。

### 4.3 四阶段修复策略（`/flowfix` skill）

类比：外科手术流程——先看片子定位病灶（locate），术前签字确认手术方案（plan），动刀后核对病灶是否切除（edit-and-check），出院前全面复查（verify）。

1. **Locate**：先用 issue/崩溃报告中的证据直接调 `flow_of` 查看候选函数的图；图没暴露缺陷就回退普通搜索/读文件工具换个候选；
2. **Plan**：编辑前调 `flow_plan`，用图增量表达修复意图，计划必须覆盖所有预期修改的函数；
3. **Edit and check**：做最小源码编辑后调 `flow_check`；mismatch 允许再编辑一次，仍不匹配可修改计划一次；
4. **Verify**：终止前调 `flow_verify` 覆盖整个计划和工作区；失败允许一次纠正编辑 + 一次最终验证。**验证通过 + patch 非空 = 完成判据**。

两个刻意的克制设计：(1) 策略是建议性的，没有 runtime hook 强制调工具或禁用原生工具——保留底层 agent 行为；(2) 重试上限有界（一次重编辑、一次重规划），让验证引入的额外交互可控，不会退化成开放式循环。

### 4.4 与基线 agent 的关系

FlowPlan **不替换不限制** Claude Code 的 Read/Edit/Write/Bash/Grep/Glob 工具。图抽象提供工作层，源码交互保留为回退路径。MCP 工具描述会常驻 prompt 前缀（即使不调用也占 token），这是方法自带的固定开销，也是 SecBench 上收益被摊薄的原因之一。

## 五、评估指标与实验证据

### 5.1 实验设计

- **Agent/模型**：Claude Code v2.1.220（headless，低推理档），Claude Haiku 4.5 和 Claude Sonnet 5 两个模型；每实例每配置全新会话，跑一次；
- **基准**（按 95% 置信度、5% 误差边际采样）：SWE-bench Pro（Python 修复，n=158，来自 ansible/openlibrary/qute-browser）、SWE-bench Verified（Python 修复，n=218，django/sympy 等十一仓库）、SecBench（C/C++ 安全补丁，n=169，OSS-Fuzz sanitizer 报告 + PoC 输入）；
- **预算上限**：SWE-bench 80 turns/$2/25min，SecBench 40 turns/$1.50/25min（远高于基线典型用量，仅作保险）；
- **统计**：任务成功用 McNemar 精确检验；token 用配对置换检验（20 万次置换）+ Holm-Bonferroni 校正（40 个比较）。判据严格。

### 5.2 指标体系

- **主指标**：相对基线的 token 比率（总均值 / 匹配实例的基线均值），四类 token（input/output/cache-read/cache-write）全部计入，包括辅助调用；
- **约束指标**：解决率（官方 harness：fail-to-pass 全过且 pass-to-pass 不挂；SecBench 为 PoC 不再触发 sanitizer）；
- **机制指标（RQ3）**：协议五步各步对照参考 patch 的正确率；轨迹分阶段 token 分解。

### 5.3 核心结果一：RQ1——降本不伤效果

十二个 FlowPlan 配置（2 图视图 × 6 设置）token 全降，十个显著（Holm 后 p<0.001；仅 Sonnet 5 SecBench 两项不显著）：

| 设置 | Haiku 4.5 (CFG/DFG) | Sonnet 5 (CFG/DFG) |
|------|---------------------|--------------------|
| SWE-bench Pro | **0.47× / 0.46×** | **0.72× / 0.76×** |
| SWE-bench Verified | **0.32× / 0.35×** | **0.73× / 0.74×** |
| SecBench | **0.68× / 0.74×** | 0.94× / 0.92×（不显著） |

解决率变化 -4.6~+4.5 个百分点，方向不一致，McNemar 检验无一显著。**降本没有以牺牲任务成功为代价**。token 结构上：节省主要来自 cache-read 下降（基线 96-98% token 是缓存读）；cache-write 反而增加（skill + MCP 描述 + 图视图都是新上下文），但只抵消 Pro/Verified 上节省的 ≤1.3-1.5%（SecBench 上达 9-16%，且输出 token 也增加，因为要显式陈述计划）。

### 5.4 核心结果二：RQ2——同场竞技赢了大部分

五方法同实例、同模型、同 agent、同记账复现：

| 方法 | token 范围（6 设置） | 特点 |
|------|---------------------|------|
| **FlowPlan** | 0.32-0.94× | 3 个设置降幅最大，1 个并列最大 |
| No-execution | 0.56-0.81× | 全部显著；Sonnet 5 两设置胜过 FlowPlan |
| SHERLOC | 0.85-1.33× | 定位阶段自身引入调用与缓存写，常抵消收益 |
| AgentDiet | 0.79-1.13× | 反思改写步骤带来额外开销 |
| EET | 0.90-1.10× | 仅 Haiku 两设置显著；Sonnet Pro 上解决率反而 +10.8pp（唯一显著效果差异） |
| SeeRepo | 0.96-1.13× | 从未低于基线 |

**规律**：靠消除重复交互的方法（FlowPlan、No-execution）比"加预处理/压缩机制"的方法省得多——后者的机器开销会吃掉它们省下的上下文。

### 5.5 核心结果三：RQ3——协议正确性与节省来源

对照参考 patch 的五步协议分解（Haiku 4.5 全轨迹，n=1090）：

| 协议步骤 | 池化正确率 | 瓶颈所在 |
|----------|-----------|----------|
| 函数定位 | 77% | SecBench 难：崩溃栈指向症状处，修复常在调用者 |
| 图构建忠实 | 84% | SecBench 的 DFG 视图较低（64%） |
| 图元素定位 | 47% | **最弱环节**：定位失败症状 ≠ 定位需修改的成因代码 |
| 修复规划 | 59%（含部分正确） | Verified/SecBench 上 40-59% 计划描述了不同变化（部分是有效替代修法） |
| 计划实现 | **91%** | **一旦意图显式化，落地高度可靠** |

全步骤正确占 8-37%，这些轨迹解决率 53-81%，其余仅 28-46%——中间决策确实是修复走向的有效信号。示例轨迹（django-13089）：10 次调用 0.19M token 全步正确，基线 45 次调用 2.32M。

**token 归因**（按轨迹阶段分解）：基线约三分之二 token 消耗在首次编辑之后（Pro 2.42M、Verified 2.19M，各约 31 次调用反复重读/diff/测试）。CFG 把该阶段压到 18/12 次调用、0.96M/0.48M——**编辑后阶段贡献了 Pro 上 75%、Verified 上 73-74% 的总节省**。规划+验证本身只花 2.8-3.7 次调用、0.08-0.17M token，不到其节省额的十分之一。编辑前探索也减半（1.20M→0.55M）。SecBench 基线仅 15 次调用、无长尾可砍，节省主要来自单次调用上下文变小（31K vs 51K tokens/call）。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**对比对象**：原生 Claude Code。它有效是因为交互自由——任何信息都能通过工具获得。但自由度的代价是**终止判据缺失**：agent 没有"改完了"的客观证据，只能用昂贵的源码级动作（重读、diff、跑测试）逼近确信，而这些动作发生在轨迹最深处、每次重放最贵上下文的时刻。

**因果链**（每步标注证据等级）：

1. 显式类型化图增量计划 → 修复意图从隐式分布状态变为机器可检查的外部承诺【论文实验支持：flow_check 以 86-95% 会话率确认编辑匹配计划】；
2. 意图可检查 → flow_check/flow_verify 用指纹差分取代编辑后的反复重读与测试 → 后编辑调用从 31 次降到 12-18 次【论文实验支持：图 5 阶段分解，75%/73-74% 节省来自编辑后】；
3. 函数级图视图比源文件/shell 观测紧凑 → 单次调用积累上下文变小 → cache-read 下降【论文实验支持：SecBench 31K vs 51K per-call；cache-read 占基线 96-98%】；
4. 砍掉的是轨迹最深处（最贵）的调用 → 节省被杠杆放大【论文实验支持：编辑后调用每次重放完整积累上下文，是"验证长尾"】；
5. 外部研究交叉印证：agentic coding 输入输出比 154:1、cache-read 是所有阶段最大成本项（arXiv:2604.22750），印证"减少重放"是正确杠杆【外部证据】。

**反事实推理**：如果只有图抽象（工作层）而没有显式计划/验证判据，agent 仍需自行判断完成时机——SecBench 上无长尾可砍时 FlowPlan 增益随即缩水（Sonnet 5 上不显著），恰说明其优势主要依赖"砍长尾"机制而非图视图本身的紧凑性【阅读者推测，基于 SecBench 反例的机制推断】。

### 6.3 综合判断与未决问题

**多项证据共同支持的机制**：(1) "终止判据缺失是编码 agent 成本的核心来源"——EET、Fail-Fast、StopLoss、No-execution 从不同角度一致支持；(2) "消除重复交互 > 压缩上下文"——本文五方法受控对比 + AgentDiet 的开销反例。

**仍属推测的部分**：图视图（CFG vs DFG）哪个更优——论文实验显示两者无稳定差异，选择可能任务相关；"计划实现 91% 可靠"是否部分因为计划本身宽松（same_family 分级）——论文未做分级敏感度消融。

**适用条件与失效条件**：优势在长轨迹（基线有深验证长尾）时最大；短轨迹任务（如 SecBench+强模型）上 MCP 固定开销占比升高、增益可能不显著；修复涉及跨函数上下文、流图无法表达的语义、或全新代码时，抽象层信息不足，需回退源码交互；结论限于 Claude Code + 两同厂模型 + 三基准，其他 agent/模型/语言未验证。

## 七、必要知识反推

假设让一个毫无背景的人完成这项工作，最少需要掌握什么？

### 7.1 领域知识层

- **编码 agent 的循环结构与成本模型**：必须理解"每次调用重放全部历史 + 工具观测膨胀上下文"这一结构性成本来源，否则无法定位"调用次数 × 上下文"双因子；必须知道 cache-read/cache-write 的记账区别（98% 是缓存读这一观察直接决定了优化杠杆的位置）；
- **Claude Code 的扩展机制**：MCP 工具协议（工具描述常驻前缀、观测作为普通工具结果返回）和 skill 机制（指令注入首条用户消息）——不理解这两个挂载点，方法就没有宿主；
- **SWE-bench 系评测的运作方式**：fail-to-pass/pass-to-pass 判据、headless 执行、官方 harness 评分——这是效果约束指标的地面。

### 7.2 方法论知识层

- **程序分析基础**：CFG/DFG 的定义、构建（AST 派生、tree-sitter 解析、Joern 代码属性图）、规范化指纹的设计（为什么用块/边集合、定义-使用多重集而不是图同构——差分可判定性）；PDG/CPG 等相邻表示及其适用边界；
- **2026 token 缩减研究版图**：171 篇调研筛出五方法的流程、各方法干预点（定位前/每步后/探索期/测试期）——没有这张地图就没有公平复现对比的设计；
- **实证方法论**：置信度驱动的样本量计算（95%/5%）、McNemar 精确检验（配对二元结果）、配对置换检验 + Holm 校正（多重比较）——判据不严，"不显著地不伤解决率"这一结论就不成立。

### 7.3 工程知识层

- **符号索引与会话隔离**：tree-sitter 预建 SQLite 索引（每 commit 一次、零模型调用）；从 HEAD 而非工作区快照指纹（防基准污染）——这些细节决定验证的正确性；
- **图增量词汇表设计**：类型化算子集（add_guard/remove_branch/change_condition/rewire_edge + no_flow_change/add_function）如何覆盖真实修复空间、分级比对（exact/same_family/mismatch）如何容忍等价实现；
- **有界重试的协议设计**：为什么是"一次重编辑 + 一次重规划 + 一次纠正验证"——既要可恢复又不能让验证自身退化成新长尾。

### 7.4 知识融合的关键节点

- **节点一：程序分析 × agent 经济学**。把"指纹差分"这一编译器/程序分析的经典技术，从正确性验证语境迁移到"agent 终止判据"语境——两个领域各自成熟，连接点是"完成判据可计算化"；
- **节点二：MCP/skill 机制 × 修复策略**。四阶段策略不是论文算法而是写给 agent 的指令（skill），工程上必须理解"建议性协议 + 可观测决策记录"比"强制 hook"更符合评测公平性；
- **节点三：受控对比方法论 × 复现工程**。五个对比方法保留原始实现/prompt/阈值，只统一实例、模型、记账——这是"复现可能偏离原研究，但同场内对比有效"这一效度论证的基础。

## 八、论文中可以提取的通用性灵感

### 灵感一：把"完成"从认知问题变成计算问题

- **核心思想**：任何开放式迭代系统（agent、优化循环、人工流程）中，若"何时算完成"靠主观判断，成本就会失控；给终止一个机器可检查的客观判据，是最高杠杆的效率干预；
- **论文证据**：flow_check/flow_verify 取代编辑后 31 次调用的验证长尾，贡献 73-75% 的 token 节省；而 EET 用自报告置信度只有 0.90-1.10×；
- **推广场景**：(1) 数据分析 agent——用"查询计划全部执行且结果 schema 匹配"作终止判据；(2) 文档撰写 agent——编辑前声明大纲变更，编辑后 diff 比对；(3) 自动化运维——声明期望的系统状态增量，验证收敛后停止；(4) 科学实验循环——预注册假设与判据，证据匹配即结束。

### 灵感二：意图先行的外部化承诺改变执行质量

- **核心思想**：让系统在行动前把意图显式写为结构化、可审计的承诺，行动后的偏差即可机械检测——这比事后解释"我做了什么"强得多；
- **论文证据**：一旦计划记录在案，编辑实现计划的可靠性达 91%（五基准池化）；且 flow_verify 能审计计划外的未声明修改；
- **推广场景**：(1) 数据库迁移——迁移前声明 schema 增量，执行后 diff 验证；(2) AI 辅助医疗/法律文书——先声明修改要点再动笔；(3) 团队协作协议——设计文档作为对代码评审的"计划增量"；(4) 安全面——对自动改动系统声明允许修改的资产白名单。

### 灵感三：换一层表示，比在原表示上做减法更省

- **核心思想**：与其在原始高维载体（源码文本、完整对话）上压缩/裁剪（有损且自身有开销），不如换到任务本质相关的低维抽象层上推理——减法方法的机器开销常吃掉其收益；
- **论文证据**：压缩类（AgentDiet 0.79-1.13×）和替换类（SeeRepo 0.96-1.13×）常不省钱，而换层推理的 FlowPlan 达 0.32×；其规划+验证自身开销不到节省额的十分之一；
- **推广场景**：(1) 长文档 QA——在论点图谱上推理而非全文反复重读；(2) 多轮谈判/博弈 agent——在让步空间表示上规划；(3) 视频理解——在事件时间线上推理而非逐帧重看；(4) 日志排障——在因果依赖图上定位而非全量重放日志。

### 灵感四：帮最强的模型省不如帮最弱的模型省？——成本干预的杠杆分布

- **核心思想**：效率机制的收益不是均匀分布的，它与"被消除行为的基线规模"成正比（长尾定律）：基线轨迹越长、冗余越多，干预收益越大；
- **论文证据**：Haiku 4.5（基线 3.4-3.7M token）降到 0.32-0.47×，Sonnet 5（基线 0.7-1.2M）只降到 0.72-0.94×；SecBench 短轨迹上增益最小甚至不显著；
- **推广场景**：(1) 云成本优化——先审计最大浪费源再选工具；(2) 推荐降本方案前先做基线行为画像（有没有长尾可砍）；(3) 评测新效率方法时应报告"基线轨迹长度 × 节省率"二维结果而非单点；(4) 个人生产力——识别自己工作流中的"验证长尾"（反复检查、返工）优先消除。

### 灵感五：定位症状 ≠ 定位病因，跨层定位是通用难点

- **核心思想**：任何诊断型任务（修 bug、看病、排障）中，可观测的失败点（崩溃栈、症状）与需要干预的成因点（调用者、上游）系统性错位——表面线索的"可及性"会诱导诊断者锚定错误位置；
- **论文证据**：图元素定位仅 47% 正确；SecBench 上 agent 频繁锚定 sanitizer 报告的崩溃语句，而修复常在调用链上游（定位正确率跌至 25-28%）；函数定位 77% vs 元素定位 47% 的落差也说明粒度越细错位越重；
- **推广场景**：(1) 可观测性/On-call——告警点与根因的系统错位需因果图谱补偿；(2) 医学诊断——症状部位与病因分离；(3) 组织管理——绩效问题的表现部门与制度成因；(4) LLM 排障——输出错误的直接 token 位置与 prompt/训练数据成因。

### 灵感六：可观测性优先的协议评估——把过程决策作为科学对象

- **核心思想**：评估一个多步协议时，不只看端到端结果，而是把每步中间决策对照"参考答案"分级打分——既定位瓶颈步骤，又验证中间信号与最终结果的相关性；
- **论文证据**：五步协议分解发现规划实现 91% vs 图元素定位 47% 的巨大落差，精确指出改进方向；全步骤正确的轨迹解决率 53-81% vs 其余 28-46%，证明中间决策有预测力；
- **推广场景**:(1) 多 agent 系统评测——逐步审计各角色决策质量；(2) 复杂工具链 A/B——分阶段归因而非只看末端指标；(3) 教育评估——解题过程分步打分；(4) 自动驾驶接管分析——还原感知/规划/控制各环节决策。
