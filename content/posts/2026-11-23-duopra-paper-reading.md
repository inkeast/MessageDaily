> **论文链接**：[Duopra: From Full-Duplex Conversation to Full-Duplex Agency](https://arxiv.org/abs/2611.25773)
> **发表时间**：2026年11月
> **机构**：上海交通大学、腾讯、上海大学、布里斯托大学（企业+高校合作，第一作者 Chiyu Chen 在腾讯实习期间完成工作，共同一作 Pengzhou Cheng 来自上海大学）
> **领域标签**：cs.AI / 全双工语音交互 / 语音 Agent / 工具调用

## 一、论文背景

**全双工语音模型是什么。**传统语音助手是"对讲机"式的半双工：用户说完、系统静音检测结束、再开始生成回复。全双工（full-duplex）交互模型则像人一样边听边说：用户话音未落就能开始回应，能被打断、能在停顿处保持沉默、能发出"嗯嗯"之类的backchannel（附和语）表示在听。Moshi、SyncLLM、dGSLM 等工作把这套"对话控制能力"（conversational agency）——何时说、何时停、何时让、何时续——做进了模型本身，延迟从数秒降到 200ms 量级。

**缺的那一半：任务能力。**只会聊天不够。真实助手还要"办事"：查航班、下单、改订单——也就是在语音流里**及时发起工具调用**，并在用户口头纠正（"等等，买一台就行"）后**用被纠正的值修订参数**。论文把这称为任务能力（task agency）：决定何时行动、保留用户最新意图、完成所请求的步骤。

**主流方案：前端-后端架构及其隐藏瓶颈。**当前业界普遍把两件事拆开：一个全双工"前端"负责对话，把任务以自然语言请求委派（delegate）给一个工具型"后端" LLM 异步执行（Realtime-Venus、DuplexOmni、SALMONN-duo 等均属此类）。这个架构的前提假设是：执行可以外包，但前端必须先把一个**还在演化中的请求**（用户随时改口）固化成可执行任务——判断信息是否足够、吸收纠正、写出保留所需值和步骤的请求。论文在 Full-Duplex-Bench v3（FDB v3）上测了一个残酷的事实：RV-Audio + Harness 这套基线只在 **11.0%** 的会话里把请求交给后端（hand-off），Pass@1 只有 **4.7%**——无论后端多强，没发出的请求永远不会被执行。这个 11.0% 构成了"hand-off 上限"。

**还有一层工程暗坑。**前端的语言模型（thinker）更新后，其隐状态会漂移，而语音生成器（talker）恰恰以这些隐状态为条件——训完任务，话可能说得含混不清了。

这就是论文要回答的问题：是什么限制了前端-后端 agent 的任务成功率？一个全双工交互模型如何获得可靠的任务能力，同时不丢对话控制、不毁语音质量？

## 二、论文定位和关联工作

### 谱系一：全双工交互模型（对话能力线）

- **dGSLM**（[Nguyen et al., TACL 2023](https://arxiv.org/abs/2203.16502)）：首个"无文本"双塔模型，从 2000 小时双通道原始音频学出含笑声、副语言信号的双流对话，证明文本不是对话建模的必需中介。
- **Moshi**（[Défossez et al., 2024](https://arxiv.org/abs/2410.00037)）：把自身语音与用户语音建模为并行流，用"内心独白"（inner monologue，时间对齐的文本前缀）约束音频 token，理论延迟 160ms，是首个实时全双工语音 LLM。
- **SyncLLM**（[Veluri et al., EMNLP 2024](https://arxiv.org/abs/2409.15594)）：把时间信息直接注入 Llama3-8b，让模型与真实时钟同步生成，用 21.2 万小时合成语音对话训练。

这些工作确立了"一个因果策略同时决定说与听"的范式，但都不做工具调用。Duopra 的底座 RV-Audio（9B）正属于这一谱系的后续。

### 谱系二：前端-后端委派架构（任务能力外包线）

- **Realtime-Venus**（[Venus Team, 2026](https://arxiv.org/abs/2609.13814)）：双循环运行时，前端维持对话，Harness 异步执行委派任务并回注结果。Duopra 直接以它的 RV-Audio 为基座——本文基线 RV-Audio + Harness 即此系统。
- **DuplexOmni**（[Huang et al., 2026](https://arxiv.org/abs/2606.09186)）：交互层+思考层异步并行。其消融显示换弱思考层，交互指标几乎不变（ToR 72.6→72.1）而推理指标大跌（77.2→50.3）——旁证了"交互质量由前端决定"。
- **SALMONN-duo**（[Yu et al., 2026](https://arxiv.org/abs/2609.34247)）：双系统+成本感知 RL，教系统 1 何时直答、何时委派系统 2。与 Duopra 的关键区别：它优化的是**要不要委派**的决策，Duopra 进一步优化**发起出的请求是否忠实完整**。

### 谱系三：前端直呼工具（任务能力内化线）

GPT-Realtime 支持异步函数调用；**Qwen-Audio-3.1-Realtime**（[Bao et al., 2026](https://arxiv.org/abs/2609.25176)）用 GRPO 训工具使用与说话时机协同；SHANKS 在用户说话中就发起调用。Duopra 的差异化在于：**直呼与委派共享同一动作接口**（后端被表示成一个工具 query(task)），且用执行结果驱动的全双工 RL 统一训练两条路径。

### 定位总结

| 维度 | 之前两条路线 | Duopra 的突破 |
|------|------------|--------------|
| 任务能力位置 | 外包给后端（委派线）或前端直呼（内化线），二者割裂 | 统一动作接口：query(task) 也是一个工具，直呼/委派同标准 |
| 优化目标 | 委派率、路由准确率等代理指标 | 执行结果（及时、完整、有据）直接作为 RL 奖励 |
| 失败诊断 | 归因笼统 | 把 Pass@1 分解为 Call × Pass\|call，定位"发起瓶颈" |
| 训练副作用 | 甚少讨论任务训练对语音的影响 | 三阶段含投影器修复，量化 CER/WER 与条件余弦 |

**基准**：FDB v3（[Lin et al., 2026](https://arxiv.org/abs/2604.04847)）是本文主战场——100 条真实含糊（disfluent）英语录音 × 12 个模拟 API，本身就是为暴露"真实语音下的工具使用"而生的基准。

## 三、问题定义

论文的核心洞察是一个**抽象统一**：与其把"前端"和"后端"当成两种角色，不如把整个系统看成一个流式策略，委派和直呼只是这个策略**可见工具集不同**的两种配置。

**一个策略同时管说与做。**用户音频以 Δ（1 秒）为单位流入。在第 t 单元，前端读入音频 x_t 与注入的观察 e_t（含工具 schema 与历史调用结果），输出三元组：

- y_t = (m_t, w_t, a_t)
- m_t ∈ {listen, speak}：轮次状态（对话能力）
- w_t：被发声的文本
- a_t：**私有动作**，从不发声（任务能力）——调哪个工具、带什么参数

策略是因果的：π_θ(y_t | x_≤t, e_≤t, y_<t)。全双工 agency 就是**在一个因果策略里同时把两类决策做好**。

**工具暴露的三种配置。**域工具集 F 中每个工具有 JSON schema；后端代理 B 被表示为**多出来的一个工具 query(task)**，其参数是自包含自然语言任务描述。前端可调集 T 决定配置：

| 配置 | T 的内容 | 对应现实系统 |
|------|---------|------------|
| Backend | {query}，域工具在后端手里 | 请求式委派（Realtime-Venus 原样） |
| Direct | F，无后端 | 前端直呼 |
| Both | F ∪ {query} | 模型自己选路由，无独立调度器 |

**信息充分性准则（对两条路径同一标准）。**一次调用正当，当且仅当每个必填参数都有来源：用户语音（**最后的纠正值才是终值**）、先前调用结果、或会话上下文默认值。缺必填值就只问缺的；可选参数取默认。委派的任务描述必须保留最新值、必需步骤与前置依赖。

**成功判据与 hand-off 上限。**任务成功要求 (i) 调用集合与 gold 调用完全一致（参数全对、不多不漏——执行被纠正前的过期调用也算失败）；(ii) 口头回答有据（只基于返回观察）；(iii) 及时（信息充分则在请求结束后 k_act=3 单位内行动）。在请求式委派下，Pass@1 可分解为：

> Pass@1 = Call（有域工具执行的会话占比，由前端单独决定）× Pass|call（这些会话的条件通过率，取决于前端写的任务+后端执行）

**无论后端多强，Pass@1 不可能超过 hand-off 占比**——没发出的请求没法执行。这就是论文诊断基线的钥匙。

这个抽象的精妙之处：它把"前端-后端架构怎么了"这个工程问题，化归为"一个策略的发起行为怎么了"这个可测量的问题，且判据与谁执行无关。

## 四、问题解法

Duopra = RV-Audio 9B 底座 + 统一动作空间 + 三阶段训练。基础组件：thinker（LLM，hidden 4096）控制双工流并产出公开文本与私有 JSON 动作（写在 `<delegate>` 区间内，永不被发声）；talker（20 层、768 维）经投影器 P_φ（MLP，4096→768→768，**3,737,088 参数**）以 thinker 隐状态为条件，用 s3tokenizer 音频 token + Token2wav 声码器出 24kHz 语音。

### 阶段一：协议 SFT——先教会"格式"

类比：新员工入职先学工单系统怎么填。在 12,800 条合成会话（70% 中文、60% 任务导向、40% 能力保留）上微调 thinker 全部 transformer 层（冻结 embedding、LM head、音频编码器与 talker），损失只覆盖参考输出位置（公开文本+私有动作+双工控制 token），400 步、峰值学习率 2×10⁻⁶。示范内容覆盖：听、问缺失必填值、select 检索 schema、发结构化调用、播报结果。产出 Duopra-SFT。

### 阶段二：全双工 RL——再用结果教会"时机与忠实"

类比：SFT 学的是"照着模板填"，RL 学的是"填对了才有奖金"。在沙盒里对每个任务以 G=8 个 rollout 采样（同一预录用户音频与工具目录），runtime 执行私有动作（直呼打到模拟工具、委派发给冻结的 Qwen3.8-27B 后端），结果在下一个单元边界注入流中。

**奖励设计（时间锚定、结果分层）**，全部以 1 秒音频单元计时：

| 行为 | 奖励 |
|------|------|
| 完整执行+有据回答：请求结束后 3 单位内行动 | +1.2（3–8 单位 +1.1，更晚 +0.9） |
| 诚实播报部分完成 | 0.1 + 0.15c（c 为正确执行步骤占比） |
| 使用被用户纠正过的值 | −0.6 / 每个值 |
| 编造结果（观察未到就播报） | −0.95 |
| 该调用却没调用 | 说了话 −0.85；沉默 −0.90 |
| 打断后 2 单位内停下 / 停顿中不抢话 | 控制类奖惩 |

评分员 = 运行时规则 + Qwen3.8-27B judge，judge 需给出结构化证据（目标索引、观察索引、逐字引用），评分员再验证引用真实存在且支持该目标——防 judge 幻觉。意外后端故障在委派忠实充分时被过滤，不惩罚前端。

**课程**：2a 阶段（7,908 任务）练直呼/纠正/澄清/打断/backchannel → Duopra-RL1；2b 阶段加入 5 个新任务族（D1 单步、D2 多步依赖、D3 纠正、D4 充分性四变体、D5 后端出错恢复），84 个随机命名空间的工具目录共 2,688 个 schema 变体（沿 SGD-X 思路防背 schema），并按 45:55 回放 2a 任务 → Duopra-RL。

**优化器**：Dr. GRPO（[Liu et al., COLM 2025](https://arxiv.org/abs/2503.20783)）+ thinker LoRA（r=32, α=32），优势 A_i = r_i − 组均值，clip 0.2，KL 锚定 Duopra-SFT（β=0.01，k3 估计器）。Dr. GRPO 去掉了 GRPO 的响应长度归一与组内标准差归一两个偏差源——对一个输出长度差异极大（说话多 vs 少、调用多 vs 无）的语音策略，长度偏差尤其致命。

### 阶段三：仅投影器修复——thinker 动了，把 talker 的"输入插头"对回去

类比：换了新主机（thinker），显示器（talker）的线还是旧接口——不换显示器，只转接。thinker 训练后隐状态漂移，talker 条件方向走样，语音可懂度下降。修复方案极度克制：冻结 Duopra-RL thinker 与整个 talker，**只训 3.7M 参数的投影器**。缓存两套 thinker 在相同流前缀上的隐状态 h_orig 与 h_RL，目标是对齐方向：

> L = 1 − cos(L2norm(P_φ(h_RL)), L2norm(P_φ0(h_orig))) + λ‖φ−φ0‖²（L2-SP 正则，λ=0.01）

450 步、931 会话的 35,154 个口语 token 位置。产出最终 Duopra。

## 五、评估指标与实验证据

### 指标体系

- **主指标 Pass@1**（FDB v3）：会话通过率——执行日志含全部 gold 调用、参数全对、无多余调用（含后端执行的），执行过期调用即失败。可分解为 Call × Pass|call。
- **辅助指标**：Tool F1（工具名，免 judge）、Arg.（judge 评参数准确率）、Resp.（回答质量）、事实回答时延；FDB v1.0 三项接管率 TOR（Turn 用户说完后接管↑ / Pause 真实停顿中抢话↓ / Intr. 被打断后回应↑）。
- **消融指标**：各 checkpoint（SFT/RL1/RL）对比、结果类分布（pass/no-call/wrong-arg/missing/extra）、多调用（2–3 call）通过率、CER/WER、条件余弦。

### 主结果（FDB v3，300 会话/配置，3 解码种子）

| 系统 | 后端 | Call | Pass\|call | Pass@1 |
|------|------|------|----------|--------|
| RV-Audio + Harness | Qwen3-8B | 10.3 | 45.2 | **4.7** |
| DuplexOmni | Qwen3-8B | – | – | 17.0 |
| Duopra-SFT (Direct) | 无 | 44.7 | 58.2 | 26.0 |
| Duopra-RL1 (Direct) | 无 | 56.3 | 47.3 | 26.7 |
| **Duopra (Direct)** | 无 | 81.3 | 58.6 | **47.7** (+43.0) |
| **Duopra (Backend)** | Qwen3-8B | 86.7 | 51.5 | **44.7** (+40.0) |
| **Duopra (Backend)** | DeepSeek-V4.1-Flash | 77.0 | 64.1 | **49.3** (+44.7) |

外部参考点（不同评测协议，非同台排名）：GPT-Realtime 60.0、Gemini Live 3.1 54.0、Gemini Live 2.5 49.0——Duopra 与 Gemini Live 2.5 相当。

**这些数字如何支撑主张**：(1) 换掉同一后端前的对话前端，Pass@1 十倍级提升，配对 95% 置信区间 [31.3, 48.7] 不含零——任务能力可以学进前端；(2) 无后端直呼 47.7% 与委派 44.7% 相当——学到的能力是"原生的"，不依赖外部执行器；(3) Both 配置下几乎从不委派、133 次成功至少 132 次来自自己的直呼——工具可见时任务能力就在前端。

### 发起 vs 执行（RQ2 的证据）

- 基线失败主因是**发起不足**：hand-off 仅 11.0% 会话（33 会话 34 次 hand-off 中仅 31 次真正触发域工具），Pass@1 上限被锁死。
- **匹配会话分析**：在基线执行了调用的 31 个会话上，Duopra 通过 12 次 vs 基线 14 次——**并不更强**；净增益来自其余 269 个基线从不执行的会话（通过 122 个）。增益全部来自"把没发起的请求发起出来"。
- 换更强后端（DeepSeek）：Pass|call +12.5（显著），但 Call 下降，Pass@1 净变化 +4.7 不显著——**后端再强也补不出发起**。

### 训练如何把发起变成完成（RQ3）

- RL1 阶段：Call 大涨（44.7→56.3），Pass@1 几乎不动（26.0→26.7）——"多打电话≠办成事"。
- 2b 阶段后：no-call 从 89.7%（基线）压到 18.7%；多调用任务（2 call/3 call）从 RL1 的 **0%/0%** 升到 **24.1%/31.3**；Pass@1 Direct 达 47.7（对 RL1 +21.0，CI [15.3, 27.0]）。
- 残余错误转移：no-call 退场后，"工具对但参数错"成为最大失败类（300 会话中 58 个）——选对工具与保留用户值是两种独立能力（案例：订单号里字母 O 被写成数字 0）。

### 对话与语音不塌（RQ4）

- FDB v1.0 三项接管率全部超过底座 RV-Audio：Turn 59.1→75.6，Pause 18.1→5.4（降为好），Intr. 79.5→91.3。
- 代价：自发 backchannel 全丢（三后训 checkpoint 在 55 个测试项上为 0），打断响应从 RL1 到最终版略降。
- 投影器修复：同一 Duopra-RL thinker，换 Stage-3 投影器后中文 CER 6.01→2.58（减半以上）、英文 WER 9.74→7.66（选择集证据），条件余弦 0.930→0.973，音色相似度基本不变。这是"任务训练后还能听懂它在说什么"的关键。

## 六、效果优势的根源解释

### 根源机制与证据链

**因果链 1：发起瓶颈的消除靠"把后端变成工具+执行结果奖励"。**

- 基线机制局限（论文实验已支持）：请求式委派下前端只见过 query 一个接口、看不到域工具 schema，发起意愿与请求质量都无从优化；hand-off 11.0% 封顶。
- 本文改变（论文实验已支持）：schema 对前端可见 + 直呼/委派共享接口 → 信息从"前端猜后端要什么"变成"前端直接读参数要求"；RL 奖励直接锚定执行结果（及时 +1.2、过期值 −0.6、编造 −0.95）→ 优化信号从代理指标变成最终指标。
- 机制变化：发起行为从"未被优化的自由文本习惯"变成"被结果奖励塑形的结构化动作"→ no-call 89.7%→18.7% → Call 86.7%（Backend 配置）。

**因果链 2：先提发起率、再把发起转化为完整执行，靠课程两段式。**

- Stage 2a 学会"该出手时就出手"（Call↑），但 Pass@1 不动——说明发起质量问题（缺步骤、丢依赖）未被解决。
- Stage 2b 加入 D2 多步依赖/D4 充分性/D5 恢复任务族后，多调用 0%→24.1/31.3——奖励分层的 0.1+0.15c 部分完成项给了梯度细粒度信号（论文实验已支持；"部分完成奖励塑造了中间行为"这一机制细节属阅读者推测）。

**因果链 3：投影器修复有效，因为漂移是低维接口问题。**

- 机制：thinker 权重变化→h_RL 与 h_orig 方向偏差（余弦 0.929）→talker 条件失配→CER 升高；只对齐投影器输出方向（cos 损失）即把余弦拉回 0.974、CER 减半（论文实验已支持）。深层含义：任务知识主要存在 thinker 权重里，talker 接口是窄瓶颈——3.7M 参数足够修。反事实：不修复则 CER 6.01，修复仅动 0.04% 参数。

### 综合判断与未决问题

- **多研究共同支持**：结果驱动 RL 可训练语音 agent 的行动时机（Qwen-Audio-3.1、Duopra 双证）；发起/委派率是可学习且值得单独优化的量（SALMONN-duo、Duopra）；纠正处理是行业级瓶颈（FDB v3、Duopra）。
- **仍属推测**：Dr. GRPO 的无偏性在语音流式域的迁移有效性（论文未做 GRPO 对照消融）；部分完成奖励 0.1+0.15c 塑造中间行为的细粒度机制。
- **适用条件**：优势在"工具 schema 可对前端暴露"的前提下成立；Backend 配置下参数错误率与时延上升（wrong-arg +10.7，时延 14.85s vs Both 10.42s），说明自然语言转述有损——域工具不可见时 query(task) 的忠实性是软肋。
- **可能失效条件**：工具目录巨大（schema 注入成本）、真实多轮动态目标（论文自限：预录用户请求+模拟 API，无后续追问）、非中文英文口音（训练语音合成自有限音色库）。

## 七、必要知识反推

假设一个零知识的人要复现这项工作，最少需要知道什么？

### 领域知识层

- **全双工交互的运行机制**：1 秒单元流式循环、listen/speak 控制 token、thinker-talker 分工与条件关系——不知道这些就无法理解动作要塞进哪个流、为何私有动作不能被发声。
- **对话行为学**：turn-taking、backchannel、打断的界线——否则无法设计 FDB v1.0 的三类 TOR 评估，也无法发现 backchannel 丢失这一代价。
- **工具调用协议**：JSON schema、必填/可选参数、SGD-X 式 schema 变体——统一接口 query(task) 的设计建立在对"什么让一个调用合法"的理解上。

### 方法论知识层

- **策略梯度与 GRPO 家族**：必须知道 GRPO 的长度/标准差归一偏差，才会为长度高度可变的语音 rollout 选 Dr. GRPO。
- **奖励设计的证据学**：judge 需结构化证据+引用校验才能防 judge 幻觉；数值归一化（"三九五"=395）需口语数字化经验。
- **迁移学习正则**：L2-SP（Li et al., 2018）不是常识——知道它才能想到用参数距离正则锚住投影器。
- **诊断方法**：Pass@1 = Call × Pass|call 的分解、匹配会话分析、hand-off 上限推理——这是从流式系统日志做归因的测量学。

### 工程知识层

- **流式沙盒与结果注入**：G=8 rollout 共享预录音频、单元边界注入观察、时间锚定计分——RL 能跑起来全靠这套 runtime。
- **双工评测管线**：FDB v1.0 要求输出音频与输入时钟对齐录制，否则停顿/轮次指标全错。
- **成本意识**：阶段三只训 3.7M 参数（全模型的 0.04%）——知道"最小修复面"的工程判断。

### 知识融合的关键节点

1. **接口统一**（对话工具 + agent 接口 → query(task)）：把两个领域的"调用"抽象成同一动作，需要同时深谙 function calling 与委派架构。
2. **奖励=执行结果+时间锚**（RL + 对话时序 → 分层奖励）：把对话学的时序概念（打断后 2 单位停）与 RL 的结果奖励融在一个标量里。
3. **最小修复面**（表示学习 + 工程成本 → 投影器修复）：意识到 talker 条件漂移是低维接口问题而非表征问题，是全文最省钱的一步棋。

## 八、论文中可以提取的通用性灵感

### 灵感 1：外包执行，不可外包发起

**核心思想**：任何"前端-后端"协作系统里，后端能力再强也无法执行未被发出的请求；系统上限由发起方的忠实性决定。
**论文证据**：hand-off 11.0% 构成 Pass@1 上限；匹配会话上 Duopra 并不比基线强（12 vs 14），增益全部来自原本未发起的会话；换 DeepSeek 后端 Pass|call +12.5 但 Pass@1 不显著提升。
**推广场景**：(1) 代码 agent 中规划器与执行器的分工——执行器再强也救不了不敢提 PR 的规划器；(2) RAG 系统——检索器上限由 query 重写质量决定；(3) 人机协作——下属执行力无法弥补上级不敢授权；(4) 多智能体系统——委派消息的完整性是系统性瓶颈；(5) API 网关——上游服务的调用覆盖率先于延迟优化。

### 灵感 2：把被委派者表示为一个工具，统一优化界面

**核心思想**：当两条执行路径（自己做 vs 委派做）共享同一动作接口与成功标准时，一条 RL 信号可以同时优化两者，且无需独立路由器。
**论文证据**：query(task) 与域工具同接口，Both 配置下模型自己学会几乎全部直呼（133 成功中至少 132 无委派）且成绩与专门配置相当。
**推广场景**：(1) LLM 路由——大小模型路由统一为"模型即工具"；(2) 微服务编排——同步调用与异步任务同一 API 面；(3) 数据库优化器——远程查询与本地计算统一算子接口；(4) 机器人技能——原生技能与云端技能同一动作空间。

### 灵感 3：分清"发起率"与"完成率"两个阶段指标

**核心思想**：复合成功率应分解为覆盖率 × 条件成功率，两者病因与药方完全不同；只看总数会把"不敢做"误诊为"做不好"。
**论文证据**：RL1 阶段 Call 大涨而 Pass@1 不动（26.0→26.7），2b 阶段才转化为完成；错误类别从 no-call 主导迁移到 wrong-argument 主导。
**推广场景**:(1) 销售 funnel——触达率与转化率分治；(2) 搜索引擎——召回覆盖率与排序精度分治；(3) 自动驾驶接管——请求接管率与接管质量分治；(4) 医疗诊断——送检率与检出率分治；(5) CI 系统——触发率与通过率分治。

### 灵感 4：主模型更新后，用最小参数面修复下游接口

**核心思想**：级联系统中上游微调导致的下游失配，常可用一个窄投影层（对齐表示方向）修复，无需重训下游或全模型。
**论文证据**：仅训 3.7M 投影器（cos+L2-SP）使 CER 从 6.01 降至 2.58、条件余弦 0.930→0.973，thinker/talker/声码器全冻结。
**推广场景**：(1) LLM 升级后修复下游 embedding 依赖（重训适配器而非下游）；(2) 推荐系统特征上游换 encoder 后对齐特征空间；(3) 语音识别换声学模型后修复语言模型接口；(4) 迁移学习中的 adapter 思路在"修复"而非"适配新任务"场景的应用。

### 灵感 5：时间锚定的分层奖励优于二值成功奖励

**核心思想**：对时序敏感的系统，奖励应同时编码"做多快"（时间锚）与"做多对"（结果分层，含部分完成），而非只有最终 0/1。
**论文证据**：3 单位内 +1.2 / 3–8 单位 +1.1 / 更晚 +0.9 的及时性分层，加 0.1+0.15c 的部分完成奖励，与 −0.6 过期值、−0.95 编造构成完整梯度场；no-call 从 89.7% 压至 18.7% 的同时多调用从 0% 起步增长。
**推广场景**：(1) 机器人操作的实时性奖励；(2) 自动交易的执行时延与滑点；(3) 应急响应系统的分级时效；(4) 流式推荐的首屏时间与质量权衡；(5) 人机对话系统的插话时机训练。

## 结语

Duopra 的价值不只是把一个数字从 4.7 提到 44.7，而是给"语音 agent 为什么办不成事"提供了一个可复用的诊断框架（发起瓶颈）与一套可复制的训练配方（统一接口 + 结果驱动 RL + 最小修复面）。它也诚实地图绘了代价：backchannel 丢了、Backend 配置下转述有损、评测还停留在预录请求与模拟 API。从"会聊天"到"会办事"再到"边聊边办事"，全双工 agency 这条路刚被打通第一段。
