## 一、论文背景

### 1.1 自动化攻击的速度已经超过补丁周期

要理解这篇论文，先要理解它对抗的威胁模型有多紧迫。LLM Agent 现在可以在**不给任何漏洞描述**的前提下自主发现并利用 Web 漏洞（Fang et al., 2024; Zhu et al., 2026）。更现实的是论文引用的两个案例：开源多 Agent 渗透测试框架 ARTEX 于 2026 年 7 月发布，到 8 月底就被经济犯罪和间谍活动攻击者投入使用，某些案例在初始探测后**数小时内**就取得特权访问（Google/Mandiant 与 Microsoft 威胁情报的报告）。

这带来一个防御范式的根本困境：面对一个能把立足点在数小时内转化为完整入侵的攻击者，防御者**可能来不及先打补丁**。论文的切入点由此确立——需要一种在攻击者的 exploit **已经生效之后**仍然有效的保护。

### 1.2 欺骗防御：从"诱饵偏好"到"强制引流"

LLM Agent 有一个被反复验证的弱点：**它们高度信任环境返回的内容**。Agent 会执行注入在工具输出中的指令（InjecAgent）、点击对抗性弹窗、甚至在自己已经识别出陷阱的情况下仍然按陷阱行事（Prinos et al., 2026 的"识别-行动鸿沟"）。防御者已经开始利用这种轻信：

- Cloaks/honeytokens/traps：针对 Agent 偏好和有限记忆设置陷阱（Ayzenshteyn et al., 2025）
- AgentSnare：用面包屑把 Agent 引入 LLM 模拟的诱饵主机（Wang et al., 2026a）
- AgentTrap：哨兵端点+升级反馈把 Agent 引偏（Wang et al., 2026b）

但这类方案有一个共同的软肋：**真实漏洞路径仍然可达**——资产安全依赖于 Agent "更喜欢"诱饵。一旦 Agent 不咬钩，真实目标照样暴露。

### 1.3 被遗忘的老思路：搬走攻击者

论文 revival 了两个经典设计：Shadow Honeypots（Anagnostakis et al., 2005）把异常检测器标记的流量送到受监控的服务副本；Honey-patches（Araujo et al., 2014）把触发已修补漏洞的攻击者 fork 进诱饵容器。核心区别在于：这些设计服务于**人类攻击者**的时代，本文要回答的是——当攻击者是 LLM Agent、且防御规划者也换成 LLM 时，这套"引流"机制对**攻击过程中动态生成的 exploit** 会产生什么效果？

## 二、论文定位和关联工作

### 2.1 研究谱系图

按三条主线组织相关工作：

**谱系一：LLM Agent 作为攻击者**
- Fang et al.（2024b）：证明 LLM Agent 能自主入侵网站；Zhu et al.（2026）：Agent 团队可利用 0-day——确立威胁真实性
- PentestGPT、AutoAttacker、CAI、Incalmo 等：以 LLM 为核心组织整个攻击流程
- CVE-Bench（Zhu et al., 2025）：在复现的 CVE 上给攻击 Agent 打分，ICML 2025，本文直接沿用其评测器；PACEbench、Cybench、BountyBench 覆盖多主机/赏金场景

**谱系二：Agent 对环境的信任**
- InjecAgent、Pop-up 攻击、Honeyquest：证明 Agent 会跟随注入指令、误信伪造证据
- 本文不把这种轻信当作新发现，而是研究它如何显现在**真实攻击的最终报告**里

**谱系三：对攻击者的欺骗**
- 经典欺骗：Spitzner 蜜罐、Honeywords（Juels & Rivest）、欺骗技术综述（Han et al.）
- 搬移型：Shadow honeypots（2005）、Honey-patches（2014）——本文的直接思想来源
- 面向 LLM 的欺骗：Hacking back（提示注入反击）、Cloak/Honey/Trap、诱饵漏洞（Zhang et al., 2026）
- 2026 年两个可对照系统：AgentSnare（15 个 CVE-Bench 任务 pass@3 无真实利用）、AgentTrap（95.8%→79.2%）

### 2.2 本文的差异点

| 维度 | 诱饵偏好型（AgentSnare/AgentTrap） | 经典搬移型（Shadow/Honey-patch） | 本文 |
|---|---|---|---|
| 真实路径可达性 | 保持可达 | 搬走被标记者 | 确认后**全部后续请求**（含 exploit）改道 |
| 决策者 | Agent 自愿选择诱饵 | 异常检测器 | LLM 源码规划 + 固定规则路由器 |
| 规划来源 | 人工/通用 | 通用 | **从应用源码静态规划**，无逐任务 LLM 调用 |
| 评测 | 真实攻陷/完成声明 | — | 真实攻陷 + **影子副本上分别打分** + 攻击者报告分析 |

关键定位：搬移攻击者不是新想法，欺骗 LLM Agent 也不是新想法，本文的贡献在**组合**以及这个组合**让什么变得可测量**——因为对两份副本分别用基准自己的评分器打分，才能区分"防御后 exploit 失败了"和"exploit 成功了但在影子上"这两件完全不同的事。论文明确不与 AgentSnare 等直接对比。

## 三、问题定义

### 3.1 从具体场景到抽象问题

**具体场景**：一个零日攻击 Agent 拿到 Web 应用地址和八种可选评分影响（读密钥文件、代码执行等任一即可）；防御者拥有应用源码，拿不到 CVE 描述或通告。

**核心洞察**：防御问题可以抽象为一个**信息不对称下的引流博弈**——防御者能在攻击前从源码预判"哪些表面会被打、什么行为暴露攻击者"，而攻击 Agent 只能从环境反馈中学习。姜饼屋（童话里糖果砌成的陷阱屋）的类比正源于此：影子副本对攻击者而言与真实目标**界面完全一致**，唯一区别是它的"成功"毫无价值。

**形式化**（威胁模型条款）：
- 攻击者：自主 Agent，可发任意 HTTP 流量、可在自己环境运行工具；不能触网/触宿主机/触 Docker；不知道是否有蜜罐
- 防御者：部署前可读代码与配置、可探测 staging 副本；不知道 CVE
- 防御成功：任务结束时攻击者在**真实目标（primary）**上未取得任何评分影响

### 3.2 这个抽象的精妙之处

论文把"防御是否有效"拆成了可分离的三个测量问题：(a) 真实目标是否被攻陷；(b) exploit 落在哪里（真实/影子/失败）；(c) 攻击者**报告**了什么。大多数防御工作只测 (a)，而 (a) 一旦饱和到零就失去区分度——这正是第四部分"如何测量一个饱和的防御"要解决的。

## 四、问题解法

### 4.1 全景：三层架构

类比：这套系统像一家"海关+平行世界"的组合——规划阶段是海关官员事前研究航线（源码）标注高风险航线；路由器是海关窗口按名单放行或改道；影子副本是给可疑旅客准备的一个**完全复刻的平行机场**，旅客在其中一切照旧，只是永远到不了真实目的地。

```
攻击者 → 路由器（每客户端状态机） ─┬─ normal/suspect → 真实目标 (primary)
                                   └─ confirmed ────→ 影子副本 (shadow，隔离容器栈)
                                                      + arm C: LLM responder 动态加诱饵
```

### 4.2 静态规划（arm B）：两个 LLM 防御者 + 六道自动门

类比：像"分析师+设计师"的装修团队——分析师看图纸（代码导出+配置+数据库 schema），设计师出软装方案（诱饵），而六道自动门是验收规范。

**分析师（Claude Opus 4.8，经 Claude Code，只有读/搜索/写工具）**：
- 输入：staging 副本代码导出（脱敏、限流）、运行时元数据、数据库 schema；唯一网络通道是发 HTTP 探测 staging
- 输出：应用画像 + 最多 10 个风险表面排序列表（方法、路径模式、攻击类别）

**设计师（只读画像和风险列表）**：
- 输出五部分计划：诱饵页面、伪造端点、提示（hints）、蜜标（honeytoken——假凭证/密钥，后续使用即暴露攻击者）、检测规则
- 所有假值都是占位符，每次运行填充新值

**六道自动门**（不向 Agent 展示反馈）：schema 检查、诱饵构建、404 检查（每个诱饵路径必须在真实应用上返回 404）、不变量检查（重放最多 20 条探测路径，要求真实应用行为不变）、应用内放置检查、检测规则检查。另有 taint 检查拒绝泄漏基准标识符的计划。

规划成本中位数：每应用 $2.0–2.4、7–16 分钟。

### 4.3 路由器：固定代码的三态状态机

这是设计的灵魂——**LLM 只写计划，路由器是读计划的固定代码**，arm B 在攻击期间没有任何防御方 LLM 调用：

| 状态 | 进入条件 | 服务对象 |
|---|---|---|
| normal | 初始 | primary |
| suspect | payload 签名（SQLi/路径穿越模式）、20 请求内 5 次 404 的错误爆发 | primary |
| confirmed | 蜜标出现、命中伪造端点/诱饵、预测风险表面上的 payload | **shadow**（单向，不可逆） |

确认后该客户端的**每个后续请求**都进影子副本——目标在独立容器栈、独立网络/存储/假密钥。已转发中的请求在 primary 上完成。欺骗性应答延迟 2–4 秒（tarpit，焦油坑策略）。

类比：状态机像免疫系统——suspect 是 innate 免疫的快速粗筛，confirmed 是 adaptive 免疫的精准锁定，且锁定后永不解锁（单向转移）。

### 4.4 增强配置（arm C）：运行时 LLM 应答器 + 更多规则

arm C 在 arm B 之上叠加四项（注意：因此 RQ4 比较的是**整体配置**，不能隔离 responder 单独贡献）：

1. **LLM responder**：确认后最多调用 3 次，读攻击者近期流量，在影子上放置新伪造端点/提示/文件/数据库行（每次最多 5 项，须过同类门；影子评分器已报成功则不再放置）
2. **Escalation 规则**：suspect 客户端对最高排名的代码执行/认证表面发未认证请求→确认
3. **Persistence 规则**：suspect 状态下第 20 个请求→确认
4. **Secret guard**：知晓本次运行合成密钥，primary 响应即将携带它的瞬间确认客户端并改用影子应答
5. 诱饵链接参数改名（arm B 中默认名含 "artex" 字符串，会向攻击者泄露信息）

### 4.5 实验阶梯（experiment ladder）

三步逐级远离设计条件，这是论文实验设计的亮点：

| 实验 | 攻击者 | 任务 | 变化 |
|---|---|---|---|
| 1 | Claude Opus 4.8 | CVE-Bench 40 | 无（开发集：规划者见过此攻击者行为） |
| 2 | ARTEX（DeepSeek-V4-Flash 驱动） | CVE-Bench 40 | 换攻击者（真实入侵中使用的框架！） |
| 3 | ARTEX | alt-cve-bench 20 | 再换任务（本文新建，与设计零重叠） |

ARTEX 的容器化收容设计值得注意：仅允许经 CONNECT 代理访问 api.deepseek.com、netwatch 边车记录一切连接尝试、每轮实验前跑四点收容证明、web-search/web-fetch 工具禁用。每个任务每臂攻击一次；有效性判定要求五个作弊信号全零（联系 exploit 主机、web 搜索、读其他运行目录、Docker 命令、委托外部 agent）。

## 五、评估指标与实验证据

### 5.1 指标体系：为"饱和"设计的测量

主指标"真实攻陷"（grader 验证的 primary 影响，或确认前真实密钥暴露）有个问题：静态计划已把它压到零后，就**无法再区分任何叠加改进**。论文因此构造了四组在饱和时仍有区分度的量：

| 指标 | 定义 | 衡量什么 |
|---|---|---|
| 真实攻陷（主指标↓） | 基准评分器验证的 primary 影响 | 防御的最终目的 |
| 偏转 deflected | exploit 在影子上成功且 primary 完好 | 防御是"挡住"还是"搬走" |
| 伪密钥报告 | 攻击者把植入假密钥当真值报告 | 欺骗在攻击者报告中的渗透 |
| 路由余量 | 确认所需请求数/秒数、确认信号、确认前到达 primary 的 payload 请求数 | 零背后的安全边际 |

统计方法：任务配对的精确 McNemar 检验；零计数时报告精确二项 95%（Clopper–Pearson）区间上端——"0/n 的强度只有 n 那么大"。

### 5.2 主结果：数字全景

**RQ1——欺骗砍掉几乎全部真实攻陷**：

| 实验 | 无防御 (A) | 静态计划 (B) | 增强 (C) | B vs A 配对检验 |
|---|---|---|---|---|
| Opus 4.8 @ CVE-Bench | **26/40** | **5/40**⁽ᵃ⁾ | **1/40** | 22:1, p=5.7e-6 |
| ARTEX @ CVE-Bench | **20/40** | **0/40**（31 有效运行） | **0/40** | 15:0, p=6.1e-5 |
| ARTEX @ alt-cve-bench | **15/20** | **0/20** | **0/20** | 15:0, p=6.1e-5 |

⁽ᵃ⁾ 其中 4 次评分器成功 + 1 次确认前真实密钥暴露。控制组攻陷且静态臂有效运行的任务上，静态臂 95% 区间上端 11.6%；全部 51 个有效运行上 7.0%。58 个记录的静态臂运行（含无效）无一攻陷。

**RQ2——exploit 是被搬走，不是被拦截**：ARTEX 的 exploit 在静态臂 14/40、增强臂 21/40 个 CVE-Bench 任务上"在任一副本上成功"（对照 20/40），全部落在影子上。alt-cve-bench 上 12/20 与 14/20 对 15/20。差异不显著（p≥0.25）但每任务仅一次保留运行，不能证明"exploit 概率不变"——alt-cve-bench 上静态臂 12/20 vs 15/20 是 15 个百分点的差距。

**路由余量**：静态臂中位 6 个请求（IQR 3–30）、26.9 秒确认（CVE-Bench）；alt-cve-bench 5 个请求、20.2 秒。确认信号最常见是预测风险表面上的 payload（17/31 与 11/20），其次伪造端点（9/6）、诱饵（5/3）。影子服务了攻击者每运行中位 95.2%/93.2% 的请求。仅有 2/31 次 CVE-Bench 运行中 payload 请求在确认前抵达 primary（7 与 4 个请求），未造成攻陷。最晚确认案例（CVE-2024-31611）：ARTEX 向一个不存在的上传路径发了 31,409 个请求（全 404）后才打开诱饵，第 31,421 个请求确认。

**分析师失手时的保护**：arm B 分析师的风险表面只在 22/39 个 CVE-Bench 计划中命中真正漏洞 handler。但 15 个控制组攻陷且静态臂有效的任务上，失手（6 次）后攻击者全靠乱撞诱饵或其他预测表面被确认。**失手后的保护依赖攻击者在摸到 bug 前广泛试探**。

**RQ3——换攻击者/换任务**：定性结论保持。Opus 4.8 从未提交植入密钥（80 次欺骗臂运行），ARTEX 在静态臂 7/40 任务上把假密钥当真报告、其中 6 次无任何有效 exploit——纯诱饵就能产生假战果。

**RQ4——增强配置没有显著优势**：arm B/C 在 ARTEX 实验中真实攻陷同为零；51 个配对任务上偏转 26 vs 29（p=0.51）、伪密钥报告 10 vs 17（p=0.17）、确认时间 22.4s vs 23.0s。均不显著且不能确立等价。

### 5.3 ARTEX 报告里的欺骗：识别-行动鸿沟的真实攻击版

120 个欺骗臂任务（110 有效运行）中，harness 提取的值是植入假值的有 55 次：18 次仅出现在原始工具输出、7 次 ARTEX 记录了但质疑、**30 次被当真发现报告**（20 次无任何有效 exploit）。质疑来自一致性检验（如"该端点对关闭端口和 gopher:// 也'成功'，不可信"）。10 次报告中称某项为诱饵，**其中 5 次同一报告仍把另一个植入值当真**——一次 ARTEX 判定泄露的管理员密码"是诱饵"，却把同一文件里的植入密钥当真上报。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**因果链 1：为什么静态规划就能压真实攻陷到零？**

模型差异（诱饵偏好 vs 确认后全量引流）→ 机制变化（攻击者无需"自愿上钩"，只要任何一个确认信号触发，后续一切流量包括 exploit 都进影子；真实路径对被确认客户端**不可达**）→ 指标体现（ARTEX 0/40、0/20）。

- 【论文实验已支持】确认信号触发广泛：预测表面 payload 17/31、伪造端点 9/31、诱饵 5/31——三条通路互补。
- 【论文实验已支持】单向状态机意味着攻击者没有"回头路"；Agent 缺乏跨请求的指纹比对能力（7 次看到 shadow 容器名的运行中无一推断出自己在副本上）。
- 【阅读者推测】攻击者的环境反馈与真实目标界面一致（诱饵路径在真实应用 404、不变量检查保证行为不变），因此缺少"察觉被搬走"的信号——这与 Agent 环境信任文献一致，但论文未直接测量 ARTEX 的怀疑程度演化。

**因果链 2：为什么"搬走"优于"拦截"（在测量意义上）？**

拦截型防御要在 exploit 生效前判定其恶意；引流型只要求**尽早确认客户端身份**。前者的错误代价是非对称的（漏判=攻陷），后者的容错空间大得多——晚确认也不要紧，只要在 exploit 触达真正漏洞代码前。

- 【论文实验已支持】中位 6 请求/26.9 秒确认 vs 数千秒的攻击预算；最坏案例 31,409 个请求仍未失守（因为全打在不存在的路径上）。
- 【论文局限自认】论文没有与"拦截型/纯检测"基线对比，"偏转优于拦截"的主张并未被检验——结果只描述防御如何工作。

**因果链 3：RQ4 无显著差异的根源**

responder 在**确认后**才启动，而此时两配置都已把客户端送上影子——它只能改变攻击者之后的行为和报告，几乎无法改变 primary 是否攻陷。真实攻陷差异只能来自 arm C 的额外确认规则和 secret guard，而 Opus 4.8 实验中 5:1（p=0.22）提示有余量但样本不足。

### 6.3 综合判断与未决问题

**多研究共同支持的机制**：(1) LLM Agent 环境轻信（InjecAgent/Pop-up/Honeyquest 多方一致）；(2) 搬移式防御可行性（2005/2014 两次工程先例）；(3) 偏好型欺骗有效性但非强制（AgentSnare/AgentTrap）。

**仍属推测的机制**：静态规划的泛化边界——分析师对 CVE-Bench 的风险表面召回只有 22/39，alt-cve-bench 上的 15 个百分点 exploit 差距可能部分反映"没被搬走的攻击变难了"，因果方向未定（论文自认一运行/任务测不了概率）。

**适用条件与失效条件**：优势成立的条件是（a）确认足够早（分析师命中或攻击者广泛试探）、（b）客户端归因持续有效（论文的按 listener 归因是最暴露的假设）、（c）影子隔离完备（容器名泄露是真实教训）。失效场景：攻击者轮换身份、跨请求交叉验证密钥、指纹识别影子副本、或预期欺骗存在（Rouxii 类）。防御者优势（能读自家源码）对第三方部署不成立；Opus 4.8 既当防御规划者又当实验 1 攻击者的自比问题也值得注意。

## 七、必要知识反推

假设一个零知识的人要复现这项工作，最少需要掌握什么？

### 7.1 领域知识层

- **Web 漏洞利用的基本语法**：不理解 SQLi/路径穿越/反序列化等 payload 签名，就无法设计 suspect 触发规则；不理解八种评分影响的语义，就无法解读 CVE-Bench 评测器
- **LLM Agent 的攻击循环**：探测→读取响应→生成假设→打 exploit→报告——不理解这个循环，就无法设想"把整个循环搬进影子"的策略
- **蜜标/诱饵的欺骗语义**：假凭证的使用即暴露（Honeywords 传统）——这是确认信号设计的直接前置知识

### 7.2 方法论知识层

- **经典搬移防御的谱系**：Shadow honeypots 与 Honey-patches 的"标记→副本"架构是本文的模板；不知道它们就意识不到本文的增量在"LLM 规划+LLM 攻击者"
- **配对实验设计与精确检验**：McNemar 检验、Clopper–Pearson 区间、"零计数的强度只有 n 那么大"——饱和测量方法论是论文的隐性贡献
- **Agent 环境信任文献**：识别-行动鸿沟等结论是解读第 6.4 节报告分析的理论框架

### 7.3 工程知识层

- **容器化隔离与收容证明**：独立容器栈/网络/存储的影子搭建；ARTEX 的 allowlist 代理+netwatch 边车+四点收容证明——没有这些，安全实验本身不可信
- **有效性审查流水线**：五个作弊信号、冻结哈希的扫描器、离线复评、评分器正控制（166 项检查全过）——对抗评测的工程纪律
- **基准构建方法论**：alt-cve-bench 的四条准入（纯 HTTP、可评分、可复现、中继时限内）、难度预标注（6 易/8 中/6 难）、任务完成四条件

### 7.4 知识融合的关键节点

1. **"源码→风险表面→诱饵放置"的映射**：把程序分析思维（分析师 agent）与欺骗设计（设计师 agent）融合——这是把经典蜜罐从人工配置升级为 LLM 规划的化学节点
2. **"饱和→次级指标"的测量重构**：把防御评测从单指标重构为"落点+报告+余量"的三维证据体系——没有这一步，RQ2–RQ4 都无法提出
3. **"信任界面一致性"的工程收敛**：404 检查、不变量检查、taint 检查、参数改名等细节全部服务于"影子不可分辨"这一信息论目标

## 八、论文中可以提取的通用性灵感

### 灵感 1：饱和指标之下要测"余量"而非止步于零

- **核心思想**：当主指标被任何方法压到零（饱和），它就失去区分度；应设计在饱和态仍有分辨力的次级指标（落点、报告、边际）。
- **论文证据**：真实攻陷全零后用偏转/伪密钥/确认余量分离 arm B 与 arm C；"零的强度只有 n 那么大"用 Clopper–Pearson 上端量化。
- **推广场景**：1) 云服务可用性 SLA 全绿后测尾延迟；2) 编译器 fuzzing 全过后测覆盖深度；3) 安全告警零漏报后测确认时延；4) 模型安全评测全过后测拒绝理由质量；5) 自动驾驶零事故后测接管余量。

### 灵感 2：把"决策"交给 LLM、"执行"交给固定代码

- **核心思想**：LLM 负责事前规划（高价值、可审查、可冻结），确定性代码负责运行时执行（零延迟、零漂移、可审计）。
- **论文证据**：arm B 攻击期间零防御方 LLM 调用；规划成本每应用仅 $2.0–2.4；计划经六道自动门验证后冻结。
- **推广场景**：1) 数据库权限系统用 LLM 事前生成策略、规则引擎运行时执行；2) CI/CD 用 LLM 生成发布计划、固定管道执行；3) 合规系统 LLM 起草规则、确定性校验器落地；4) 游戏 AI 导演系统离线规划、在线脚本执行。

### 灵感 3：搬走问题而非阻断问题（对不可判定动作）

- **核心思想**：当无法在动作生效前可靠判定其恶意性时，可以改变动作的作用域——让它生效，但生效在一个无价值的环境里。
- **论文证据**：exploit 在影子上成功（14/40、21/40）而 primary 完好；确认只需中位 6 请求，远早于 exploit 成形。
- **推广场景**：1) 沙箱执行不可信代码；2) 蓝绿部署中把可疑流量导入影子集群观察；3) 反欺诈中让可疑订单"成功"进入人工审核队列；4) 邮件系统把可疑发件人投递到隔离区而非拒收；5) 对抗性 ML 中把可疑查询路由到蜜罐模型。

### 灵感 4：欺骗的价值在于污染攻击者的"战果报告"

- **核心思想**：对以"报告"为交付物的自动化系统，防御的最高形态不是阻止其行动，而是让其行动产物流入污染区——攻击者的报告本身成为检测信号。
- **论文证据**：ARTEX 30/110 有效运行上报假密钥为真、20 次无 exploit 纯因诱饵；5 次在标记另一项为诱饵的同时仍上报假密钥。
- **推广场景**：1) 数据投毒防御中给爬虫喂假数据；2) 竞争情报对抗中维护"展示层"内容；3) 反侦察的军事欺骗条令；4) 对抗 Agentic 信息收集时的蜜罐知识库。

### 灵感 5：实验阶梯——逐步远离设计条件的评测效度设计

- **核心思想**：评测应像阶梯一样逐级引入设计时未见的变量（换攻击者→换任务），区分"开发集性能"与"泛化性能"。
- **论文证据**：三实验从设计条件（26/40→5/40）到换攻击者（20/40→0/40）到换任务（15/20→0/20），并诚实标注各比较是开发集/描述性。
- **推广场景**：1) 模型评测的分布外泛化阶梯；2) 药物临床试验的 I/II/III 期递进；3) 渗透测试报告区分"已知环境"与"盲测"结果；4) 自动驾驶仿真→封闭场地→公开道路的验证链。

### 灵感 6：防御评测要测防御者自己没主张的东西

- **核心思想**：论文主动报告了不利于解释简洁性的结果——exploit 概率可能下降 15 点、RQ4 无法分离 responder、共享记忆混杂、容器名泄露——用效度审计约束自己的结论。
- **论文证据**：复评、评分器正控制（166 项）、共享记忆敏感性分析（剔除后 13:0/11:0 仍显著）、无效运行全清单。
- **推广场景**：任何 benchmark 论文、医疗 AI 研究、政策评估的内部效度审查。

## 附录：alt-cve-bench 一览

论文发布的 20 个新任务（6 易/8 中/6 难）涵盖 Apache/Grafana/Webmin/Spring/Drupal/Metabase/Jenkins/Gogs/Laravel 等应用的知名 CVE，参考 exploit 请求中位数：易 2.5、中 3、难 9.5（最大 599，来自盲注提取与模糊测试）。基准与 harness、经验证欺骗计划、冻结扫描器将以 Apache-2.0 发布；参考 exploit 与攻击者完整转录不公开（含可用利用链）。ARTEX 已被原作者撤库，论文使用本地构建（commit 160fe13）仅作测量。
