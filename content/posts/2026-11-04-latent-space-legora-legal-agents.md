## 先说结论

这场访谈的真正主题不是「AI 颠覆法律」，而是一个工程悖论：法律是最依赖保密数据的行业，而 Legora 作为这个行业的 Agent 平台，从头到尾看不到任何一条真实用户 trace——嘉宾原话，这是「这生意一个超级烦人的怪癖」，因为律所的数据「甚至不是律所的，是律所客户的」。他们的答案是绕开数据本身：合成「评测世界」（一万份文件的数据室尽调）、把失败归类成十几种模式分桶、用超廉价 LLM 跑在线评测，用这套替代体系去逼近看不见的真实用法。产品端最重要的界面决策是「表格」：Tabular Review 单表最高做到百万格，把 fan-out 检索变成律师本来就懂的二维审阅动作，而 Lists 这个「Notion database 式原语」让「agent 造列表、列表造 agent」成为组织一切工作的粘合剂。商业模式端，嘉宾认为计时收费已在低端出现裂缝（项目费、甚至免费做关系活），钱向并购、诉讼和客户关系集中；更结构性的判断是合伙人制的深层矛盾——人力资本无法沉淀为公司资产，他想让律所把「本所做法」codify 成可积累的 IP。对做垂直 Agent 的团队，本场最可迁移的三件事：按业务领域×任务追踪模型热力图（回退比想象常见）、fan-out 前先跑前十行迭代、以及在 DPA 供应商极简的约束下做模型套利。

## 一、从「ChatGPT + 瑞典法条」到 Agent 操作系统

Legora 的起点被嘉宾一句话概括：「带瑞典法条搜索工具的 ChatGPT，字面意义上这就是全部」。2024 年这家公司还叫 Leya（嘉宾当年帮 CEO Max Junestrand 改 YC 申请——两家随后先后进了 YC：嘉宾自己的公司是 23 届，Legora 是 24 届），产品从法律研究（律师花大量时间找「长得像本案的先例」）起家，逐步长成两层：一层是**做工作**——起草、改 Word 文件、整理归档、跑复杂分析；另一层是**编排工作**——lists（他自己的类比是「我们的 Linear」）、intake（与客户协作）、portal（律师↔律师、客户↔律师、律师↔agent、agent↔agent）。产品叙事里一个值得注意的细节：Tabular View 这个由 Legora 推广的术语已经溢出成行业通用词，嘉宾明确表示乐见 Anthropic 的 Claude for Legal「用我们的术语」——命名权即品类定义权，这是垂直 Agent 公司少被讨论的一种护城河形态。

从 assistant 到 agent 的切换发生在约一年前，嘉宾将其归因于推理模型「改变了一切」。今天的形态是「真的很好用的律师版 ChatGPT」，加上侧栏里一组定制工具。规模感（节目页官方口径 + 嘉宾口述交叉）：100 名工程师（他曾在入职半年的幻灯片里放《300 勇士》宣称「永远 20 个工程师打天下」，现在自嘲 100 人还嫌小）、纽约 100 人并在继续扩张、工程招聘集中在纽约/斯德哥尔摩/伦敦。文化上他承认作为斯德哥尔摩地下室里的 underdog，「谦逊是底色」，进美国后不得不学会 bold。

## 二、看不见 trace 的评测学：合成世界、失败分桶与热力图

本场信息密度最高的部分是评测体系，因为它直接回应标题里的矛盾——「造 Agent 却看不见数据」。约束是三重的：律所数据高度保密；很多数据所有权根本在律所的客户手里；Legora 与客户之间也不存在「可以看数据」的协议（主持人猜「你们总签了什么协议吧」，嘉宾答「我倒希望」）。于是连「匿名化改写」都要划一条苛刻的线：改写到只剩三个候选值再任选其一，可以；仅仅去掉人名，「那可能不行」——他们的原则是主动把自己限制到最安全的一侧。能做的是结构化信号：已知失败模式大概十到二十种，把线上案例分桶归类，再叠加任务类型与业务领域分类，就得到了一个不需要看内容也能优化的坐标系。

在这个约束下，评测团队（三位工程师 + 三位律师混编成一个小队，另有约百人的 legal engineer 池——「大所干过三四年、通常有 CS 学位的律师」，他称之为最难招但力量倍增率最高的人）设计了「世界」：一万个文件的模拟数据室，目标是产出一份包含全部红旗、措辞得当的尽调报告，任务再拆成「起草」与「找红旗」两层。所有模型按业务领域×任务跑出一张大热力图——嘉宾给出的反直觉观察是：**模型发布的「部分回退」远比外界想象的常见**，经常是这几项涨了那几项跌了。这也解释了评测团队的历史时机问题：直到不久前做复杂评测都不划算，因为模型本身在狂飙——他曾有一个引用格式问题，什么都没做，下一次模型发布把指标从 70% 干到 99%。真正持续的工作是三件事：harness、治理（审计日志、数据保留），以及在线评测——用「超廉价 LLM 消息」判断每次会话是否解决了问题，配合 feature flag 对比新功能的「改善还是灾难性下滑」。常规产品指标则漂亮得反常：对一款企业软件，DAU/WAU/MAU 与每月使用小时数都「极高」。

与「看不见数据」配对的是幻觉对策。Legora 有一套引用系统：agent 产出的每句话都带可点击链接，定位到源文档 PDF 里的 bounding box 高亮，而且可以多层下钻——agent 基于 Tabular Review 写出的结论能一路引到那张表的具体单元格，「从底往上全部可验证」。律师的使用行为则像 code review 的两极：有人根本不点（嘉宾复述主持人圈的观察：有人对幻觉出的最高法院链接毫不在意），有人逐个逗号地读；专业人士真正的行为模式是「知道哪几处必须查」，如同审一个初级律师的产出。

## 三、界面即护城河：百万格表格、Lists 原语与 agent 群

Tabular Review 的交互是本场的具体锚点：一万份雇佣合同做尽调，每一行是一份合同，每一列是一个问题（终止通知期多长？有没有 IP 转让条款？解约赔偿多少？），整表自动填充、全部带溯源引用、可标记「已审/有旗」、可评论协作。更关键的是 agent 可以自行编排它：往 agent 里丢一万个文件说「做尽调」，它会自己拉起 Tabular Review、跑完、分析结果、标出红旗（「CEO 薪酬高得离谱」「这个奖金结构很怪」），再据此给客户起草备忘录。单表规模最高到过百万格。工程上的安全阀同样朴素：Tabular Review 默认**先跑前十行**，让用户确认「显示的是不是我们以为会显示的东西」，快速迭代到结果对了「再放开跑」——这是对所有做 fan-out 检索的团队都成立的渐进式放量原则。

为什么是表格？嘉宾的答案毫不玄学：总览最快、天然带引用、最好审阅，「比我们试过的任何其他形态都好用」，用户甚至不愿意导出到 Excel（前端用的是做了十几年表格的 AG Grid）。主持人补充了形态学的观察：表格形态在 GTM（Clay）证明过拉力，但奇怪地没有扩散——V7 试过，金融领域也没有头部玩家。写作者推断：fan-out + 同构抽取 + 人工复核的场景，二维表格可能是最短路径，这个形态在更多垂直行业仍有空位。

Lists 则是编排层原语：像 Notion database 一样可配置、带触发器和自动化，是「粘合一切」的胶水——列表可以触发 agent，agent 回写列表字段，「agent 造列表、列表造 agent、agent 读列表，agent 群就活了起来」（他用「用 Linear 协调一群 coding agent」作类比）。intake 是它的店面化应用：一个法律专用 Slack bot，把请求变成列表工单，法务团队坐在 Legora 里管理 agent，办完自动回 Slack——「没人需要换工具」。对内，这套原语还兼职低代码平台：legal engineer 能基于 lists 加生成式 UI 快速搭出定制产品（他举了基金管理仪表盘），「你要自己的？很简单」——主持人概括为「Legora 里的 Lovable」。年内第五笔收购 Wexler（英国，fact intelligence）也挂在这条思路上：百万份诉讼文件抽取成带实体和日期的事实，再互相比对出「佐证 vs 矛盾」——转写一场庭审后，「他说他不在场，但这封邮件说明他在」当场对质。嘉宾把公司级战略说得很直白：客户要感觉你建了很多东西，实际上你只建了很少的原语。

组织上与产品咬合的是双层交付：第一线 legal engineer 以超级用户身份配置产品、不写代码、驻场教律所把工作流结构化；第二线 forward deployed engineer（FDE）写进生产代码、做集成——纽约的第一名员工就是一名 FDE（前 YC 创始人，嘉宾以「两届 YC、做过 Meta 搜索」的高门槛标准招的她）。FDE 同样不碰客户数据，只建系统；API 面则刻意收紧：他们曾长期拒绝开放 API，因为产品迭代太快、不想维护旧版本对已变数据模型的兼容——20 个工程师时「做不到」，100 人时才付得起这个税。嘉宾最后抛出的开放问题也值得记录：「agent 能不能本身就是 API」——用触发 agent 干活替代确定性的 API 调用，代价是效率与确定性（他的估计：约百分之一二的概率干出计划外的事）。

## 四、模型策略：Pareto 前沿套利与 harness 里的低垂果实

模型选择器的存在本身就是一段妥协史。主持人（以 Cognition 顾问身份）给出 agent lab 论述：垂直 Agent 公司本质是「领域专用 GPT wrapper」，职责是替用户守住模型 Pareto 前沿——「你去问律师：这合同该用 Sonnet-high 还是 Opus-mid？他不知道。我们的时薪是一千美元，让它能跑就行」。嘉宾完全同意这个论点，但现实是用户要尝鲜：他们抗拒了很久，最终还是给了五档模型选择器（含 Fable、Opus、Astra），明知多数法律工作用不上 Mythos 级智能、明知尝鲜者积分烧得快十倍。能力分布上他给出一个粗刻度：约六成工作现有模型已经做得很好，剩下的博弈是成本与延迟；真正需要更强智能的是复杂分析，而且法律工作总量本身会随智能扩张。

选型逻辑被主持人称作 model arbitrage：在能力、延迟、成本、治理、区域可用性构成的空间里逐任务优化——某些开源权重模型适合特定任务就部署，某些任务后训练（直到最近开源变强才开始做，且有严格边界：只做「有界任务」，比如法律研究这种 fan-out 检索，可训出快、便宜、低延迟的专用模型；「训练自己的 Fable 当主 agent？对 Anthropic 没胜算」），其余用前沿模型。约束侧的故事很能说明问题：全栈在 Azure，不是技术选型而是信任继承——三年前律所对 AWS 和 Google 说「绝无可能」，却因 365 已通过安全审查而接受 Microsoft；on-prem 的讨论三年内彻底消失。DPA（数据处理协议）上的供应商清单「非常少」：不用 ElevenLabs，一站式厂商（OpenAI/Google/Microsoft）「不必样样最强、样样够用加治理」就有真实溢价。转写链条上的细节也值得抄：先用 LLM 层抽取关键词、再带着关键词重跑转写模型，对抗领域专名（他举的翻车例子：澳大利亚法庭某称谓被稳定转写成「condom」；主持人的例子：Whisper 和 ElevenLabs 至今把 Claude Code 转成 Cloud Code）。

在 harness 一侧，他排出的优先级是 search、analysis、drafting 三件定制：大合同起草本质是判例检索（「similar」是多维的：同行业、同类型公司、同交易结构），从多份先例文档决定「哪段取自哪份」仍是搜索问题。起草模型的质量评价很具体：Fable 和 Open「极啰嗦」，Astra 简洁、写得好——「实验室都有 Slack 通道，这些不是新闻」。长文档推理仍是模型缺口：百万 token 合同的跨文编辑、记住上方改过的定义与顺序，他们的做法是分块加编排式编辑，且「scaffolding 随模型代际重写」（Word 编辑的 map-reduce 方案改过好几轮）；主持人对应给出自己新闻工作的迁移：从 map-reduce 转向全塞进上下文。嘉宾补了一个更细的坑：分块摘要会丢「块间」信息——某件事跨两页展开，单块与检索词都不相关、合起来才是关键，这需要步骤间推理。最后是主持人抛出、嘉宾背书的一条实用建议：RAG 重的场景别只看 MTEB 榜首，「embeddings 上还有大量 alpha」，看 Voyage 或定制嵌入——唯一前提是多语言能力（「欧洲是多语言之王」）。

## 五、计时收费的裂缝：合伙人制、初级律师与「谁的数据」

商业模式部分的起点是一个好故事：嘉宾当年帮 Max 改 Leya 的 YC 申请，给出的唯一反馈是「这事别人试过一百万次都没成——计时收费下，效率等于减收，律师凭什么买单」。他现在认为驱动反转的是竞争压力：律师们「知其严重性」，明白商业模式在承压、不变不行。变化已经在美国发生：低端工作（小型 review 之类）转向项目费计价，一部分干脆免费做——律所历史上就愿意为维护客户关系白干活，现在可以不亏本地做。钱则向并购（「最容易举的例子」）、诉讼和客户关系时间集中。这与 Eve 一场（见[旧文](https://inkeast.github.io/MessageDaily/posts/2026-10-31-a16z-eve-plaintiff-law-ai/)）从原告端看到的「结果定价外溢」互为印证：两端 squeezing 的是同一条计时收费曲线。

更结构性的判断关于合伙人制。嘉宾的解释框架：律所唯一资本是人力资本，「你不能拥有人，但可以租」——合伙制就是让人力资本当股东从而留下来的结构。他想帮律所建的是**无形资本**：一个学习「本所做法」的系统、自改进的知识图谱加判例库，让方法论 codify 成可积累的 IP。但激励是错配的：「eat what you kill」奖励拉客户，不奖励沉淀方法论；合伙人离职，建过的资产带不走一分分红——「整个商业模型都在被重新审视」。至于主持人反复挑逗的「paralegals 没了、初级律师没了」，嘉宾的回应是「我们实际看到的不是这样」：如同工程界，好的初级更值钱了（产出翻了几倍），市场在两极化而非一刀切消失；那个「一百万文件、paralegal 锁屋里干到凌晨四点」的场景确实消失了，但角色在升维成 legal engineer——这个词也从 Legora 内部叫成了行业词（主持人补了个梗：CSJD）。

数据获取的讨论直接衔接上周的行业新闻（详见[旧文](https://inkeast.github.io/MessageDaily/posts/2026-11-01-ai-daily-brief-spawn-ai-pilled-playbook/)里 Crosby 意向收购 Weil 与 Google 约 1000 万美元买 Spirit Airlines 运营数据的部分；嘉宾本场回忆的数字是「一千万、七百万，反正差不多」）。他披露 Legora 的常规做法：请愿意配合的客户匿名化文档加问题描述，「能复现就能修」。至于「买一家律所拿数据」这个版本，他指出两个未解问题：数据到底属律所还是属客户（「客户都走了也许就行——我真的不知道」），以及输入好拿、输出难用——只买到终稿，得逆向工程「他们怎么走到的」；真正的金矿是真实用户的 trace，「极高价值」。呼应他看不见 trace 的日常约束，这个闭环颇为讽刺：最缺的数据恰好是最买不到的形态。

结尾的格局判断：主持人问实验室会不会像截胡编码公司那样（「已经发生两次」）对法律动手，嘉宾认为不会——实验室要通吃整个企业知识工作（数据分析、销售、营销、财务都得做），法律只是其中一块，且「永远不会做得像我们这么深」；Claude 接一些小客户的法律需求「很好，没关系」，但「四亿美元的并购交易，你还是会要 Legora」。两年预测：大企业可能用 Claude co-work 调用 Legora（如他本人通过 Claude 用 Linear、但还是会打开 Linear），律所直接住在 Legora 里。主持人收尾的两个断言值得原样保留：「每个行业——医生、律师、码农——最后都会有两三家 agent lab 统治」；嘉宾的回应则是「现代社会某种程度上就跑在法律上」。另外两个组织侧信号：Legora 在推动法学院教学使用（嘉宾坦承「不知道进展到哪」），主持人则现场出主意——直接资助 CS 背景的人读 JD（JD-MBA 常见，JD-CS 罕见）。

## 机制、二阶影响与读者启发

**链条一：数据不可见 → 评测体系重构。** 变化：无 trace、无数据协议、匿名化受限；原因：数据的终极所有权在律所的客户；得失：失去数据飞轮，换来「零风险」的合规位与被迫建起的失败模式本体；二阶影响：Agent 公司的 QA 职能从「看日志」变成「设计合成世界 + 归类失败」的环境工程师，评测能力本身成为垂直壁垒；观察指标：合成评测与真实客诉的命中率、失败分桶覆盖率；启发：做不了数据飞轮的行业，先把「失败模式本体论」建起来——它是数据飞轮的替代资产。

**链条二：表格成为 agent 的原生界面。** 变化：fan-out 检索被装进百万格表格且用户不导出；原因：二维审阅匹配律师（及一切专业审阅者）的既有肌肉记忆与逐格溯源需求；得失：牺牲对话式炫技，换来审阅效率与信任；二阶影响：每个「同构任务 × 海量对象 × 人工复核」的垂直行业都可能长出自己的 Clay（表格 Agent 层），AG Grid 类基础设施与百万格稳定性成为隐性需求；观察指标：其他垂直 SaaS 是否出现「表格+溯源+agent 编排」三件套；启发：选界面形态等于选用户的肌肉记忆，不是选技术最优解；fan-out 必配「前十行迭代」安全阀。

**链条三：计费模式反转采纳激励。** 变化：低端转项目费/免费、高端向并购与诉讼集中；原因：计时收费下效率自伤收入，竞争压力强制反转；得失：律所从效率抵制者变成采纳者，软件商的 TAM 从「省下的工时」变成「承接的工作」；二阶影响：合伙人制的资产结构被追问——人力资本若能 codify 成系统 IP，「离开无分红」的激励必须重设计，律所资产负债表可能首次出现「方法论资产」科目；观察指标：美国低端业务平价计费比例、大所初级招聘结构、法学院 AI 课程渗透率；启发：向专业服务卖效率，先问「谁的 KPI 被效率伤害」，计费模式不变则效率卖不动。

**链条四：合规约束重塑模型排序。** 变化：DPA 供应商极简、全栈 Azure、转写弃 ElevenLabs；原因：信任继承（Microsoft 365 已过安全审查）与数据出境治理；得失：单一云绑定 vs 拿下保守行业；二阶影响：「够用 + 治理 + 一站式」的厂商获得合规溢价，榜单名次不等于可用性排序，开源/自托管组件在合规敏感链路价值上升；观察指标：DPA 名单长度、开源模型在敏感任务中的部署比例；启发：受监管行业选型的第一张表不是模型榜单，而是「我的 DPA 允许谁」。

主持人问早期客户是瑞典律所——瑞典所和美国所（甚至亚洲所）有什么差异？你们主要服务大所吧？嘉宾：起家时合作的确实是非常大的律所，但五十人规模的律所也能获得很多价值。欧洲客户整体动作偏慢，美国的推进非常快，而且 AI 在美国公司的议程优先级明显更高。美国的公司（企业法务和律所都是）自建胃口也大得多：他们想「跟你们一起搞个大动作」——自建 CRM、自建文档管理系统等等，然后做触发器：在 Salesforce 里做完一次 review 自动派给某个人、处理完流进 Legora、再回流出去。这是简单端；还有极其野心的——想直接和我们一起造一个全新产品，「我们真做不了这个」。欧洲客户则更偏向「拿现成的」，给产品建议。主持人问：是欧洲客户不觉得生存威胁、美国客户觉得？嘉宾：两边都知道这事关律所/公司的成败，都极其重视，只是实现路径不同。

**[1560s - 1680s]**
主持人转入产品指标：怎么知道自己做的东西是好的？嘉宾：常规的企业软件指标我们都很在乎——用户在产品里花的时间、有没有获得价值、续不续约、回不回头；对企业软件来说，我们的 DAU/WAU/MAU 和「每月在产品里的小时数」都高得惊人。另外我们做在线评测：用超便宜的 LLM 消息判断「这次会话到底解决用户问题没有」，形成一个在线指标；上新功能时用 feature flag 对比——「是改善了，还是灾难性下滑？」然后是嘉宾认为最有意思、也最难的一点：**我们基本看不到任何 trace，看不到任何数据**——全部高度保密，这对工程来说是极其憋屈的工作状态：你给用户一个什么都能干的 agent，而你完全不知道用户实际在拿它干什么。主持人：我以为你们总跟律所签了什么数据协议。嘉宾：「我倒希望。」问题是律所手里很多数据连律所自己都无权给——那是他们客户的。所以我们只能靠评测团队「逼近」大家的真实用法，把它做进评测集。「这是这生意一个超级烦人的怪癖。」

**[1680s - 1800s]**
主持人：能不能做改写（paraphrase）？比如 ChatGPT 有个 /feedback 直接上传完整轨迹，你们显然不行，但可以用 LLM 把真实内容改写成「改掉所有名字和细节、但结构足够像」的合成版？嘉宾：做不了。这里有个区间问题：如果你把内容抽象到只剩三个候选值、随机取一个，那没问题；如果只是去掉人名，那「可能不行」。我们一贯选最安全的路线，把自己限制到最狠，目标是「零风险」。但有些事可以做：我们知道失败模式大概就这十种二十种，可以在线上把会话归类到某个桶里，这就是有用信号；还可以按任务类型、业务领域分类，就有概念了。这是我们一直在想怎么做聪明的事。接着谈隐私史：两年前要让律所接受「数据发给 Anthropic」这种事有多难？嘉宾：我们全部基础设施都在 Azure 上，主要就是为此——起步时律所说「AWS？绝无可能」，Amazon、Google 都「不能把数据交给他们」，我们只能全线架在 Microsoft 上，因为律所已经用着 365：Microsoft 在他们心里是「已通过安全审查的认可供应商」。这几年风向变了：大家明白必须上云，on-prem（本地部署）的讨论也彻底消失了——「云上是安全的，甚至比你现在自己搞的更安全」。嘉宾感慨：这不过是三年内发生的转变。主持人：法律行业此前把这事晾了十年。嘉宾：「我们需要 AI 来踹所有人一脚。」

**[1800s - 1920s]**
主持人：开源模型现在很强，你们怎么考虑？嘉宾：就像你说的——把客户始终带着沿 Pareto 前沿走。在一张「所有模型 × 擅长什么 × 延迟 × 成本 × 治理 × 区域可用性」的大地图上做优化：某些开源权重模型在特定任务上很好，就用在那里；有些我们会后训练；有些直接用前沿模型。主持人：「你把这叫 model arbitrage（模型套利）。你们年初还是坚定的 Anthropic 阵营。」（另提到 Grok 进步很大。）主持人请嘉宾举一个「总体排名不高但意外地好」的模型。嘉宾：早期某个 Gemini 版本在特定类型的转写和说话人归因上极好，我们就用它做转写。主持人：你们要做会议记录类产品（类似 Granola）吗？嘉宾：我们其实可能会做一个 meeting 功能；这里说的转写还包括用户上传听证会录音等文件，我们转成文本后就能在上面跑全套分析。不用 ElevenLabs——DPA（数据处理协议）原因；我们的 DPA 名单上供应商非常少，因为必须把数据流向锁得极紧。嘉宾由此说到一站式厂商的好处：Gemini、OpenAI 这类「来我这，你要的大多都有」的供应商其实非常值钱——不必样样最强，只要每样都够好，还带治理、可扩展，那就够了。

**[1920s - 2040s]**
嘉宾：还得夸一下 Microsoft 的转写模型（转写作「my transcribe」，存疑）——他们做的这个比旧的 Gemini 还好，arena 排名通常都在前二到前四，「这就够了」：治理齐全、可扩展。主持人：语音转文本是不是已经好到「错一两个词无所谓」？嘉宾：不不。我在这上面踩坑很多，法律领域尤其：某个国家（好像是澳大利亚）法庭里对某类人的特定称谓，会被一致地转写成「condom（安全套）」——这种错误你绝不想要。所以我目前的 workflow 是：在上面再跑一层 LLM 抽取关键词，然后带着关键词重跑转写模型。只要规模化做过转写就会知道：任何偏离日常对话的领域都会堆出海量转写错误。主持人：有行话就完蛋。对，就像 Whisper 和 ElevenLabs 至今仍把 Claude Code 转成 Cloud Code——（笑声）——「这就是为什么我们知道还有很大改进空间」。随后转向 agent 产品盘点：Tabular Review、intake 已经提过；嘉宾确认大家必须知道的「大件」清单：agent、Tabular Review、projects，另外 Word 加载项很重要——很多人就在 Word 里干活——还有 Outlook 加载项。

**[2040s - 2160s]**
主持人请嘉宾把 Tabular Review 的用户体验从头走一遍（先律师视角，再谈工程难点）。嘉宾：典型场景就是尽调——要审全部雇佣合同、全部供货合同等。放一万份雇佣合同进去，每一行是一份合同；然后按「列」提问：第一列问「终止通知期是多久」，全部自动填出来（三十天之类的）；下一列问「有没有 IP 转让条款」；再下一列「如果要裁掉他我们要赔多少」「他的薪酬是多少」——整张表全部填满。你也可以直接把一万个文件丢给 agent 说「做尽调」，它会自己拉起一个 Tabular Review 跑完全部，等结果出来后做分析、标出红旗——「这个 CEO 的薪酬高得离谱」「这个奖金结构很怪」——需要重点看的它替你挑出来；然后 agent 可以据此给客户起草备忘录，或者把红旗清单交给律师人工复核。它还是协作式的：可以评论、给其他人看。主持人：一百万格确实吓人；先说说为什么选表格这个形态？

**[2160s - 2280s]**
嘉宾：表格就是好用——工作的入手门槛极低、对全局的总览极快、审阅极容易。我们产出的所有内容都带回到源文档的引用，你可以很轻松地核验；想确保全对的话，可以把单元格标成「已审」，把有旗的标出来，加评论协作。「这比我们试过的任何其他形态都好用。」主持人：有意思的是表格形态在某些领域拉力很强（GTM 那边的 Clay 就以表格著称），但不知为何没有扩散开——V7 试过，金融领域我想不出一个做「大表格+AI」的头部名字。嘉宾：确实没有。我也觉得奇怪——只要你是 fan-out、每份文档做完全相同的抽取，表格就是理解全局最好的形态。主持人：用户会想导出到 Excel 吗，还是愿意住在你们的表里？嘉宾：愿意住在里面。主持人：你们用 AG Grid 还是自研？嘉宾：用 AG Grid，它应该是这个领域领跑的，人家做了十五年表格，懂行。表格这条线聊完，主持人转向工程侧：fan-out 最有意思——工程师都懂「往一百万份文档上扇出去之前，先在两份上试试」，你们会这么做吗？嘉宾：我们真的会这样：Tabular Review 会先跑前十行，让你检查「它显示的是不是我们以为会显示的东西」。而且对自建这类功能的用户来说这也是最佳实践：在前十行上快速迭代，直到拿到想要的结果，「再放开跑（go ham）」。下一个大件：intake，你们的 Slack bot——主持人打趣「人人都说自己有个 Slack bot，你们的有什么不同」？

**[2280s - 2400s]**
嘉宾：我们的是法律专用的。它其实不只是「跟 agent 对话的界面」——它专门用来「发起一个 agent」，agent 把任务加进列表。我们有 lists 这个东西（最接近的类比是 Linear）：请求进入专门的 intake 列表，律师和 agent 在 Legora 里看到「这是律所/企业法务收到的请求」，可以为它们发起 agent、协作处理，标记完成后自动回到 Slack。所以它更像一个「店面」：提一张工单、说清要审什么，东西办好了自动送回来，「没人需要换任何工具」，法务团队就坐在 Legora 里管理所有 agent。主持人：这类东西的数据结构很有意思——本质上是个 inbox，所有查询进来再转化成别的形态；跟其他功能做集成难吗？嘉宾：不难，我们有一些真正好用的原语：lists 是个极好的原语——极其灵活，像 Notion database，想配成什么样都行，我们在「让它超级可扩展」上投了很多；还能配触发器和自动化，是把一切粘在一起的胶水：列表上发生什么就发起 agent run，结果回来填进字段、加进文档。就像你可能用 Linear 或任务管理工具协调一堆 coding agent，我们用 lists 做同样的事——「agent 可以建列表，列表可以建 agent，agent 还能读列表」，于是「agent 群就活起来了」。主持人：用户是兴奋还是被吓到？这基本就是终端用户编程了。

**[2400s - 2520s]**
嘉宾（接「终端用户编程」）：可以让人搭出疯狂的自动化，有些人会超级上头——像 Clay 有自己的网红用户生态，「有 influencers 挺酷的」。值不值要看怎么用——我们需要这种灵活性，哪怕完全不暴露给终端用户：假设它只对内，这也是让 legal engineer 快速量产产品的最快方式——基金管理仪表盘这类东西可以直接用 lists 加生成式 UI 搭出来，等于一个新产品；我们可以做一个「专门产品市场」，legal engineer 出去见客户，「你想要自己的定制版？容易，马上给你配一个」——有点像「Legora 里面的 Lovable」（转写作「inside the door」，存疑）。即便不暴露给用户，我们自己的定制功能也这么建。我们在英国还做了另一笔收购叫 Wexler，做 fact intelligence（事实智能），主要服务诉讼：给一场官司上传一百万份文件，从中抽取带命名实体和日期的「事实」，然后把所有事实互相比对，看哪些互相佐证、哪些互相矛盾——这威力巨大：你可以转写一场庭审，然后「他在庭上说了这个，但那边那封邮件说明他当时不在场」。现场看它跑起来「真的酷到不行」。我们同样能在这个原语上搭很多产品。规模化公司的思路就是：必须解决太多问题，所以要不断想「怎么建一个能延展到很多终端产品的核心原语、支撑高度可定制的体验」。

**[2520s - 2640s]**
主持人请嘉宾把原语清单重述一遍。嘉宾：lists（超级可配置）、projects（本质是文件容器/文件系统）、agent（可以很多种配置跑起来）。主持人：agent 有名字吗？给它起个名？嘉宾：没有。（旧名 Leya 时代人们曾把它当命名实体谈，后来停了，「也许会捡回来，也许会混乱，不知道」。）Tabular Review 算是这些原语的一个「实例化」——你可以想走多深走多深。那些就是大件。主持人转入 FDE（forward deployed engineer，前置部署工程师）话题：Max 谈过——新客户要尽快拿到价值才能留住。你们的 forward deploy 团队怎么演化的？嘉宾：第一个 forward deploy 招在纽约，也是我们在纽约的第一名员工，YC 创始人背景，大概九个月前（记不太准）。主持人：算 legal engineer 吗？嘉宾：不算，纯工程师。我一直在想怎么规模化地做这件事，核心是：怎么赋能 legal engineer、赋能超级用户去深度定制产品；然后我们仍会保留 forward deploy 工程师做定制集成、做 scoping（界定可行性），并把这一切反馈回核心产品——像「第一道防线、第二道防线」：legal engineer 能搞定大部分定制和体验，搞不定的、需要动核心产品或做集成的，FDE 跟进；FDE 有时做产品、有时跟客户。

**[2640s - 2760s]**
主持人：走一个例子——刚签下一个大客户，第一步是什么？是「给你们派一个 FDE、帮你建产品」那样吗？嘉宾：客户和客户差别很大，但如果是大客户、特别投入、有一堆想法——通常他们已经自己试过造什么并且失败了，「这是想解决的问题」——我们会配 legal engineer、必要时加一名 FDE：「这几位会过来，陪你们所有律师上手，把你们现在的工作流梳理出来、搬进 Legora。」主持人：legal engineer 和 FDE 的分界到底是什么？嘉宾：legal engineer 以超级用户的方式配置产品，不写代码；FDE 写进生产代码，这就是分界。FDE 什么背景？创始人、普通工程师、「他们都老了」（笑）。D 是我们的第一位——做过两家 YC 公司、在 Meta 做搜索，「她非常强」。主持人：「这门槛可不低。」嘉宾：对，她是我们在美国的第一双靴子。FDE 都给客户建什么？差别很大：有些是人人都要的核心工作流，直接建进 Legora——「我们这么处理 NDA」之类，激活就行，更像「技能构建」；多数 FDE 案例是「我们还做不到的事」——原语需要更多灵活性，或者客户有个极复杂的系统要集成，FDE 就过去对着我们的 API 建，必要时扩我们的 API。

**[2760s - 2880s]**
主持人：法务结构上怎么处理？毕竟你们自己都不能碰交易数据——FDE 怎么在客户项目上工作？嘉宾：他们仍然不碰数据，只建系统。不过他们有时会像「员工」一样入驻客户：发一台电脑什么的（主持人惊讶：给到律所层面？）——对，但很少发生，通常建个集成就搞定了；只有需要时才这样，而且要看客户规模是否值得——因为 FDE 同时也能做核心产品，这是个持续的优先级权衡。主持人：有没有 Palantir 那种「四天驻场一天回总部写产品」的固定规则？嘉宾：没有，老实说这都还在早期。明年我预计会有一个更大的、持续轮转的 FDE 池：驻场两个月把一件事建完，再去下一家；带着 legal engineer 和 FDE 滚动进驻特定项目。主持人转到 API：你现在是「Legora 平台的 CTO 兼维护者」——你们会把 web app 里的全部能力都开成 API 吗？嘉宾：现在不做这个承诺。我们有可用的 API，但不是产品全部表面。有意思的问题是：这是不是战略？有人会喜欢——「我不用学新工具，在现有工具里装个 Legora 就行」（比如 Word 加载项）——但那样你就得维护它。

**[2880s - 3000s]**
嘉宾（续 API 话题）：这正是我们一直不做 API 的原因：API 是六个月前才开始的，之前抗拒了很久，因为产品迭代太快，我不想被「维护旧版 API 去适配已经改掉的数据模型」拖慢。现在公司大了，付得起这个成本了；二十个工程师的时候真做不到。主持人（Swyx）：我琢磨过这个问题——所有公司都该有平台团队和产品团队：产品团队你有一个，只要平台别跟产品绑死，第二个就很容易拉起来；最简单的例子是 web app、mobile app、RPC（转写作 RCP，已校正）以及其他集成，然后你的 FDE 就只是平台的「又一个客户端」。嘉宾：对，甚至 agent 也可以这么看：有一个跑 agent 的 harness 团队，你可以在它周围建产品——配上规模化和自动化等等。主持人：这就是著名的 AWS 教令（Bezos：不许再走后门，团队之间只准通过 API 交互，给客户的 API 就是你内部的 API，没有就去建），客户因此得到了一切。嘉宾：这个思路现在也在微调。我们在玩的一个想法是：「agent 能不能就是 API？」听起来很怪，但有些场景客户真正想要的只是「触发某些事发生」——不是说我们在做这个，但我在脑子里推演：你触发 agent、让它去做那件事，显然比直接打一个固定 API 低效得多——可这就是我在琢磨的问题：我们产品里有多少可以只是 agent，而不是其他所有东西。

**[3000s - 3120s]**
主持人：无界执行、成本和延迟——这是仅有的顾虑吗？嘉宾：还有确定性：大概每一百次里有两次，它会干出我们不想让它干的怪事。主持人转问产品克制：你是「对大多数事说不、只做少数事」，还是「做更多事、再雇一百人」？嘉宾：我曾是非常坚定的第一种。入职半年时我放过一张《300 勇士》电影的幻灯片说「我们这辈子就保持二十个工程师，打赢所有比我们大得多的对手」；现在一百个工程师了，反而觉得太小。现实是惨烈的竞争、用户要的东西太多——我可以当清教徒说「我们就二十人、只建这点东西」，但那样我们只会输、用户会去别家，所以必须建更多。我现在的工作定义是：设计一个系统，让客户感觉我们建了非常多东西，而我们实际只建了很少的东西。主持人：「原语化，对喽。」嘉宾：测试新产品、看有没有拉力？我们没怎么做过——只下过几个有高度信心的战略赌注，主要因为需求堆积如山：大家喊着要的东西都做不完，没必要去试「这个也许行」。

**[3120s - 3240s]**
嘉宾（续）：有时我们会跟客户说「不，我们认为另外那个东西对你更战略」，然后坚持做那个。这种战略赌注的例子：agent 本身——没有任何人要求过「我希望我的助手有更多 agency、不问我就自己干」，但我们判断行业必然走向那里、它会让大家做很多很酷的事；协作是另一个——行业会走向「在你工作的地方（Legora 里）协作」，而不是邮件和短信里。主持人：那律所内部学会用 agent，是靠 FDE 进去教吗？嘉宾：主要靠 legal engineer——也可以叫「前置部署的法律工程师」——他们进驻律所，帮律师把工作流围绕 agent 的能力重新组织。主持人转题：你们说过（Max 提过）早期不做微调，现在还是吗？嘉宾：到目前为止没微调过任何模型。过去几个月开源权重模型变得极强，所以我们会针对特定任务做——前提是「前沿模型在该任务上的成本/延迟表现」与「后训练模型的潜力」之间存在巨大落差。法律研究是绝佳例子：本质是 fan-out 检索问题，可以训出一个执行这类查询极快、极便宜、低延迟的专用模型。主持人：所以是「把模型后训练得更擅长非常具体的有界任务」。嘉宾：对，我们可不想训一个自己的 Fable 当主 agent——那场仗对 Anthropic 打不赢。

**[3240s - 3360s]**
主持人补充：搜索/检索（RAG）上仍有大量研究可做，不那么光鲜，甚至不是训练模型，而是架构和管道——你们跟 turbopuffer 合作过案例，late interaction（晚期交互）你们做吗？嘉宾：实际上还没做，但你说得对，这正是方向。我们团队有个哥们（转写作 son，存疑，疑为人名）特别痴迷搜索，老来找我说「该上这个了、有新的 embedding 模型、可以搞 late interaction」——他还真去推动 turbopuffer 团队做了 multi-vector 支持，好让我们能做这类事。但在模型之前、甚至在 harness 之前，都有大量低垂果实：想给客户更好的产出，有一堆立刻见效的事可做，轮不到先训模型。什么才是法律行业的好 harness？文件怎么改、分析怎么做、法律研究怎么跑——全烤进去：出现一个问题，它知道怎么去做研究、找先例找答案，这些都非常关键，再加上周边的治理。主持人：那最重要的定制工具是不是检索——引不到对的信息就全完了？嘉宾：是检索、分析、起草三件——起草大 Word 合同其实一点也不简单。从零起草一份大合同，你得先找先例：我们以前怎么写的？这条款需不需要？这家律所以前怎么处理的？NDA 简单，但复杂合同必须先找对先例。

**[3360s - 3480s]**
嘉宾（续）：律师从不坐下就开敲，他们先琢磨「类似交易里我们用过哪些条款」，而「类似」是多维的：同行业、同类公司、同结构；然后从多份文档里决定「哪一段取自哪一份」——这本身就是个检索问题。主持人：哪个模型起草最好？嘉宾：我昨天刚说过这个——Fable 和 Open（转写如此，疑指 OpenAI 模型）话都极多、极啰嗦，你们肯定也知道，啰嗦一般不是好事；Astra 写作相当好、简洁得多。主持人：你们会跑一百个 prompt 来约束吗？嘉宾：能做一些，但「话痨体质」对我们挺难治。下一代 Anthropic 模型大概率会好很多——Astra 其实就非常简洁。主持人：你们肯定跟实验室都有 Slack 通道直说这些吧？嘉宾：当然，这不是新闻，他们都知道。另一个我在乎的是幻觉：它们会不会编东西？我们有一套引用系统：写出来的东西必须带链接，用户点开，PDF 上一个 bounding box 高亮「这条信息取自这里」，我们确保它说的每句话都可引用——而且多层下钻：agent 基于 Tabular Review 写的结论，可以一路引到那张表的单元格/行，从底往上全部可验证。主持人：律师真的会去核对这些引用吗？嘉宾：一开始有些会，现在嘛——跟代码圈一模一样：有的工程师对 agent 输出满不在乎（有人对幻觉出的最高法院链接都不点），有的人每个逗号都读。

**[3480s - 3600s]**
嘉宾（续）：但话说回来，一个人怎么可能逐条看完那么多东西？他们其实知道「哪里是必须查的关键」，就像 code review 知道看什么系统；其他「听着合理的，大概没问题」——跟收到初级律师的产出一样：这几处我要核一下，那些应该没事。主持人：那下一代模型之前，法律推理还有什么缺口是你想要的？嘉宾：一时想不出具体的，但长文档推理仍然难：百万 token 的巨大合同，你要在全文各处做编辑，还得记得「上面这些地方你都改过、这个定义变了、这个顺序变了」。最简单的做法是一把梭——全部塞进去、一次性输出——我们不这么做，我们分块、然后「编排式」地做编辑。嘉宾感慨：身处这个行业有趣就有趣在这些地方：我们的 Word 编辑方案做过 map-reduce、又改掉，来来回回——「模型一变，我们搭的脚手架就得跟着重搭」。主持人深有同感：我因为工作做大量新闻整合，最近刚从 map-reduce 切换到「全塞进上下文」，因为现在这样效果更好。嘉宾：是，但也不完全一样。我们在搜索上遇到过一个坑：在一份巨大合同里找某个东西，可以 map-reduce，但只要涉及摘要，就可能丢掉「块与块之间」的重要细节——逐块摘要再拼起来，nuance 就没了。所以我们是两套搜索并用，其中一套需要在中间步骤里做推理。我正想找个好例子。

**[3600s - 3720s]**
嘉宾（例子）：有些文件用整整两页讲一件事，单独每一块跟你的检索词都不相关，但合在一起却极度相关——这就是难做的地方，而且（呼应前面）想让模型在这种事上变好很难，因为我们根本看不到真实合同。主持人：那你们会不会请客户做「类似真实合同」的示例？嘉宾：我们有反馈机制，客户愿意配合的话：他们说「这个对我们特别重要但现在做得不好」，我们就说「太好了，能不能把文档和问题匿名化给我们，能复现我们就能修」。主持人：这事还有个更激进的版本——买一家律所。嘉宾：确实有人在考虑。但这里有讲究：那些数据到底属于律所还是属于客户？「如果客户都走光了，那也许就没问题了——我是真不知道。」不过这确实是搞到大量数据的一条路。主持人：就像 Google 买 Spirit（航空）那样——他们花了大概一千万、七百万还是多少来着；一家倒闭的公司还留着 Slack，Slack 都能卖；好像还有家 YC 公司专门收购倒闭公司——大家要的就是「真人在真工作里留下的东西」。嘉宾：买律所数据的真正问题是：输入好拿——真实输入很棒；但输出难用——你只拿到最终结果，得逆向工程「他们是怎么走到的」。在我们的产品里，拿到真实用户的真实 trace 价值极高；只有产出、不知道好坏和过程，就很难用。（主持人：我们快到时间了。）主持人最后指路一个方向——embedding 上还剩很多 alpha：如果你的负载很吃 RAG，只看 MTEB 榜拿第一名的模型用，你是在把大量收益留在桌上。
