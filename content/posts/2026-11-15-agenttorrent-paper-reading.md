## 一、论文背景

### 1.1 Agentic coding 工具：从"写提示词"到"管资产"

Claude Code、OpenAI Codex、Cursor、GitHub Copilot 这类 **agentic coding 工具**（也叫编码智能体），已经能在仓库里自主完成多步骤的软件修改任务：读代码、改文件、跑测试、提交 commit。它们与早期"补全代码"的助手不同——自主性高，能自己决定读什么、改什么、执行什么命令。

高自主性带来一个新问题：**开发者如何"管教"这些工具？** 过去几年的答案是写更精细的提示词（prompt engineering），而现在的实践重心已经转移：开发者不再只打磨一句话的提示，而是**工程化地配置工具读到的上下文和它运行所依赖的"缰绳"**——把这些配置作为文件提交进仓库，像管理源代码一样管理它们。

### 1.2 两个关键概念：上下文工程与 harness 工程

**上下文工程（context engineering）** 是提示词工程的延伸。Anthropic 在其技术文章中给出的定义是：为模型的有限上下文窗口策展"最优 token 集合"的系统性方法——不只写好指令，还要管理检索文档、对话历史、工具输出、记忆等所有进入模型视野的信息（见 [Anthropic: Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)）。落到仓库层面，就是编写 `CLAUDE.md`、`AGENTS.md` 这类**上下文文件（context file）**：告诉工具本项目怎么构建、怎么测试、什么不能碰。可以把上下文文件理解为"写给 AI 的新员工入职手册"。

**Harness 工程（harness engineering）** 中的 harness（缰绳/马具）指包裹在模型外部的执行框架：工具调用接口、权限约束、错误处理、检查点等。配置 harness 就是配置工具**能做什么、不能做什么**——例如 MCP（Model Context Protocol）配置决定工具可以连接哪些外部服务器，hooks 决定工具执行命令前后自动触发什么检查，settings 决定哪些命令需要人工批准。

论文标题中的 **context and harness engineering artifacts** 就是指这两类制品在仓库中的落盘形式。作者将每种配置机制的一个实例（如一个 `CLAUDE.md` 文件或一个 skill 文件夹）称为一个**配置工件（configuration artifact）**，共覆盖十类机制。用"新员工入职"做类比，这十类机制各管一摊：

| 机制 | 典型样貌 | 类比 | 管什么 |
|---|---|---|---|
| 上下文文件 | `CLAUDE.md`、`AGENTS.md` | 入职手册 | 工具启动时必读的项目规范 |
| 技能（skills） | 含 `SKILL.md` 的文件夹 | 岗位操作手册 | 按需加载的专项流程知识 |
| 规则（rules） | `.cursor/rules/*.mdc` | 岗位红线 | 匹配特定文件/场景的约束 |
| 设置（settings） | settings.json | 门禁权限表 | 哪些命令要人工批准 |
| 子代理（subagents） | 子代理定义文件 | 外包专家名单 | 把子任务委派给专职 agent |
| 自定义命令 | 斜杠命令定义 | 快捷键宏 | 一键启动常用工作流 |
| MCP 配置 | `.mcp.json` 等 | 外部供应商名录 | 可连接的外部工具服务器 |
| 插件（plugins） | 插件清单 | 装机软件清单 | 功能扩展包 |
| 钩子（hooks） | 钩子配置 | 考勤打卡规则 | 命令执行前后自动触发的检查 |
| LSP 配置 | 语言服务器配置 | 翻译对接人 | 代码理解后端的接入方式 |

### 1.3 AGENTS.md 生态与 spec-driven 开发：制品正在爆发

两个外部事实说明这些制品已成为规模化的真实生态：

- **AGENTS.md** 是一个开放格式，自称为"给 agent 看的 README"，由 OpenAI Codex、Google Jules、Cursor、Amp 等生态多方发起，现由 Linux 基金会下的 Agentic AI Foundation 托管，已有超过 6 万个开源项目采用（见 [agents.md](https://agents.md/)）。同一仓库里常常同时存在 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules/*.mdc` 等多个重叠的指令文件。
- **Spec-driven 开发框架**（如 GitHub 官方的 [Spec Kit](https://github.com/github/spec-kit)）在实现之前先让 agent 产出规格说明、计划和任务列表等**agentic 规划文档（planning document）**（Spec Kit 的 `/specify → /plan → /tasks → /implement` 工作流）。这些文档同样被提交进仓库，成为上下文的重要来源。

### 1.4 为什么要研究它们：研究碎片化，数据无法合并

论文开篇用 nornir-automation/nornir 仓库给了一个直观的动机示例（图 1）：一个 commit 同时加入了 `CLAUDE.md` 与 `AGENTS.md` 两个上下文文件，commit 消息致谢了 Claude Code；另一个 commit 安装了 Spec Kit，其 AGENTS.md 又引用了 `.specify/memory/constitution.md` 这份规划文档——文件引入文件、commit 致谢工具、指令引用规划，这些**横跨四类制品的关系**只有把它们链接起来才能看见。

这些制品记录了人类如何指挥 AI 工具，是研究"人机协作软件工程"的第一手材料。但现有研究各自为政：有的只研究 `SKILL.md`，有的只研究 specs 文件，采样方式（多按文件名搜索）和采集时间各不相同。SpecMine 的作者就承认，按文件名搜索会把"严肃项目和教程、模板克隆、一次性实验"混在一起。**研究者无法把已有数据集合并起来，跨仓库、跨工件类型地回答"agentic 软件工程被采用到什么程度"这类基本问题。** 这就是 AgentTorrent 的动机。

## 二、论文定位和关联工作

### 2.1 前作：AgentConfigs

AgentTorrent 是团队前作 **AgentConfigs**（2026 年 3 月发布，AIware 2026 Datasets & Benchmarks track，[DOI: 10.1145/3805760.3814922](https://doi.org/10.1145/3805760.3814922)）的直接升级：前作覆盖 5 个工具、4,738 个仓库、15,591 个配置工件和 148,519 条 AI 共同署名的 commit。AgentTorrent 把配置工件扩到约四倍（62,374 个），新增 OpenCode（数据显示它是当时 GitHub 上最流行而尚未覆盖的工具）、plugins 与 LSP 两类机制、导入链解析、规划文档，以及对六个目标工具之外 AI 工具的致谢 commit。分类器也从闭源模型（GPT-5.2）换成了开源权重模型并补充人工核验。

### 2.2 相关数据集谱系

按研究对象可分四条线：

| 谱系 | 代表工作 | 内容与采样 | 与 AgentTorrent 的关键区别 |
|---|---|---|---|
| 单一制品数据集 | GitSkills（[arXiv:2608.10906](https://arxiv.org/abs/2608.10906)）：379 万个 SKILL.md；SpecMine（[arXiv:2608.25202](https://arxiv.org/abs/2608.25202)）：47 万 specs 文件 | 按文件名代码搜索采样，无分母 | 无工程性筛选，混入教程/模板；无同仓链接 |
| 指令文件普查 | Zarzycki（[arXiv:2610.31715](https://arxiv.org/abs/2610.31715)）：22,854 个高星仓库中 26.3% 有 AGENTS.md/CLAUDE.md | 1,000+ 星、近 90 天有推送、13 种语言 | 只看根目录两类文件，偏向头部项目 |
| 采用率普查 | Robbes et al.（TOSEM 2026）；Khosravani & Mockus（[arXiv:2606.24429](https://arxiv.org/abs/2606.24429)，1.8 亿仓库） | 按配置文件/commit 痕迹/机器人账户等多层检测 | 覆盖面极广但工件内容不落地；Khosravani 明言"绝对召回未知" |
| 工件历史 | GHAgentFiles（ICSME 2026）：14.2 万文件历史；MCP-Eco：MCP 声明；AIDev（MSR '26）：93 万 PR | 各自独立采样 | 单一维度，不能跨制品类型链接 |

### 2.3 定位结论

AgentTorrent 的差异化主张有两点：**（1）同仓链接**——它是表中唯一同时记录配置工件、导入文件、规划文档和致谢 commit 并在仓库层面互相链接的数据集；（2）**有分母**——仓库抽样独立于"是否含配置"这个预测目标（先按工程性筛出 40,901 个工程项目，再看其中多少含配置），因此能给出"10,944/40,901 ≈ 26.8% 的工程软件项目含配置工件"这样的普及率估计，而按文件名搜索的数据集天然没有分母。

## 三、问题定义

论文要解决的本质问题可以抽象为：**如何把散落在 GitHub 上的、控制 agentic coding 工具的"暗数据"变成一个可链接、可复核、可持续更新的关系型证据基础？**

拆成形式化的四个子问题：

1. **给定** GitHub 仓库总体（数亿级），**求**一个有代表性且与配置无关的工程软件项目样本（分母），**约束**是排除个人玩具项目、教程、模板（Kalliamvakou et al. 2014 指出的 GitHub 挖矿经典陷阱）；
2. **给定**样本仓库的文件树，**求**配置工件的完备检测规则，**约束**是每条规则必须锚定厂商文档或真实仓库示例（可审计、可随文档漂移更新）；
3. **给定**检测到的工件，**求**它们之间的语义链接（导入链、规划文档引用、commit 归因），**约束**是链接必须遵循各工具真实的加载规则（如 Claude Code 每链最多四次连续导入）;
4. **给定**整套检测结果，**求**精度与召回的双侧量化，**约束**是不依赖单一模型自证。

这个抽象的精妙之处在于：它把"研究采用率"从一个检索问题（搜文件名）改造成了**测量问题**——有抽样框、有分母、有检出误差区间的测量。用流行病学做类比：

| 流行病学概念 | AgentTorrent 对应物 |
|---|---|
| 目标总体 | GitHub 上活跃、有许可证的工程软件项目 |
| 队列抽样（先定总体） | GHS 抽样框 46,503 → 工程项目 40,901 |
| 暴露（exposure） | 仓库含配置工件/有致谢 commit |
| 患病率 | 10,944/40,901 ≈ 26.8% 的普及率 |
| 检测试剂灵敏度/特异度 | 启发式的召回/精度（双侧评估） |
| 病例对照（先选病例） | 按文件名搜索式采样（无分母，本文摒弃） |

这是"先定总体、再测暴露"的思路在软件仓库挖掘上的移植。

## 四、问题解法

论文的核心交付物是一条**五阶段自动化流水线**（重跑只需 GitHub token 和 OpenRouter API key）：

```
1 抽样(Sampling)      → 2 分类(Classification) → 3 收集(Collection)
                                                      ↓
5 分析(Analysis)      ← 4 打包(Packaging)
```

### 4.1 阶段一：抽样——先圈定"像样"的仓库

查询 [SEART GitHub Search（GHS）](https://seart-ghs.si.usi.ch/)（MSR 社区标准抽样工具，Dabic et al. MSR 2021，只索引 ≥10 星仓库）得到非 fork、有许可证、≥2 贡献者、≥1 PR、创建满 18 个月、近 6 个月有 commit 的仓库；再经 GitHub API 元数据过滤（剔除私有/归档/锁定，保留 OSI 开源许可证与十种最常见主语言，剔除教育仓库，commit 数与 watcher 数不低于样本中位数 358/5），最终得到 **46,503 个仓库的抽样框**。贡献者与活跃度门槛针对的正是"个人项目与僵尸项目"两类噪声。

### 4.2 阶段二：用开源权重模型识别"工程软件项目"

不是每个仓库都是认真工程出来的软件项目（有的只是课件或 demo）。流水线用 **DeepSeek V4.1 Flash**（开源权重）读取仓库名、描述、README、issue/PR 活动、元数据和文件清单，通过自研 MCP 服务器最多抓取 5 个链接页补充信息，按排除标准（教学材料、模板等）+ 至少两条工程实践证据（测试、贡献者文档等）输出 true/false/unclear 三值标签。三值逻辑的判定规则值得注意：命中任一排除标准即 false；标准或证据不确定即 unclear；**true 要求"无一排除标准命中 + 至少两条工程实践有证据"**——把不确定排除在样本外而不是硬猜，是宁缺毋滥的保守设计。去除头提交相同的副本后保留 **40,901 个工程项目**（另标 4,222 false、25 unclear、1,355 主要因 README 非英语而未出标签）。

验证设计是本阶段亮点：**GLM-5.3 作为第二个模型**独立盲标 1,039 个样本，两模型一致率 98.0%（95% CI [96.9%, 98.7%]，Cohen's κ = 0.87）；第一作者仲裁 21 个分歧（同意 DeepSeek 11 个、GLM 8 个、都不同意 2 个）。标签连同原始模型响应一起存档，可在不重跑模型的情况下复现。

### 4.3 阶段三：收集——2,343 条可审计启发式

判定"什么算配置"的标准是**厂商自己怎么说的**：文件必须被工具厂商文档记载为仓库级配置才算。落地为：

- **358 条路径启发式**覆盖十类配置机制，每条强制引用厂商文档或源码并记录核验日期，自动化测试保证"无来源不入库"；连"长得像配置但工具不读"的路径（如 `.claude/memory`）也带注释记录，防止误报；
- **导入解析**：识别 `@docs/style.md` 这类文件导入，按工具加载规则追踪链式导入，解析器与厂商实现在 74/66 个测试文本上对过答案；
- **523 条启发式**收集 Spec Kit、OpenSpec 等 73 个框架产出的规划文档（specs/plans/tasks）；
- **431+402 条启发式**识别致谢 commit（通过作者/提交者身份、消息文本、co-author trailer），并区分四类信用：工具身份、被采纳的评审建议、工具插入的致谢、用户惯例。

一个说明启发式必要性的数字：本版数据中 **312,453 条致谢 commit（占 24.4%）只有靠仓库衍生启发式才能检出**，纯文档模式会漏掉它们。

### 4.4 阶段四/五：持续更新与自动核查

计划**季度发布**；**每周监控 438 个厂商文档页面**，页面变更即自动开 issue（用 Claude Code 辅助复核受影响启发式）——论文强调没有任何相关数据集做了这种文档漂移监控。未知路径与未知致谢格式的回扫曾发现 `.claude/workflows` 等新配置位置。发布前自动核查：工具标志与配置记录一致、commit 数一致、消息致谢与启发式吻合；每个分析脚本跑两遍验证可复现性。

### 4.5 数据组织

数据以 CSV 按"工件类型 × 仓库"组织，可按仓库名 join：

| 文件 | 内容 | 数量 | 涉及仓库 |

| repos.csv | 元数据+工程性标签 | 46,503 | 46,503 |
| context_files.csv | 上下文文件（如 CLAUDE.md） | 25,353 | 10,026 |

## 五、评估指标与实验证据

数据集论文的"实验"是对**检测质量**的量化。作者同时评估精度（检出的对不对）与召回（该检出的漏没漏），这在同类工作中少见——GHAgentFiles 只估了精度，Khosravani & Mockus 明言"绝对召回未知"。

### 5.1 精度评估（用 Claude Opus 5.5 的 agent 标注，分层抽样）

| 检测对象 | 精度（加权） | 95% CI | 样本量 |
|---|---|---|---|
| 配置工件 | 99.87% | [94.4%, 100%] | 806 |
| 六工具致谢 commit | 99.96% | [96.6%, 100%] | 360 |
| 文件导入 | 99.98% | [90.5%, 100%] | 157 |
| 规划文档 | 99.8% | [93.3%, 100%] | 366 |

标注协议：独立 agent 盲重标每层 20%（650 项中仅 7 项分歧），第三方 agent 依启发式的证据说明仲裁。信用类型判定 574 次中 571 次正确。

### 5.2 召回核查（反向翻文件清单与完整 commit 日志）

- 在 100 个有检出仓库中人工翻文件清单，发现 386 个配置文件/目录，启发式命中 383（漏 3）；
- 在 200 个无检出仓库中发现仅 1 个漏检；外推到全部 29,955 个无检出仓库，95% CI 上界为 833 个（≈2.8%）；
- 从完整 commit 日志均匀抽 1,000 条：19 条致谢六工具，检出 18——漏检存在但样本太小，作者如实报告"检出比例无法精确估计"而非粉饰。

### 5.3 数据本身揭示的研究线索（论文给出的示例发现）

这些数字展示了"同仓链接"设计能回答什么问题：

- **工具在给自己写指令**：23.8% 的上下文文件、36.1% 的规划文档，其引入 commit 致谢了某个 AI 工具——即 agent 参与编写了指挥后续 agent 的文件；
- **指令依赖网络**：1,551 条导入把 176 个仓库的文件连成链，可研究指令间的依赖与**相互矛盾**；
- **致谢要拆开看**：Gemini 的 6,360 条致谢 commit 中 5,261 条（82.4%）只是"采纳了它的评审建议"，Copilot 该比例为 39,047/184,386——不区分信用类型会高估"agent 写码"的规模；
- **共现强度**：4,124 个配置仓库（37.7%）使用 ≥2 类机制；417 个含规划文档的仓库中 93.0% 同时有致谢 commit，三类制品在 388 个仓库中齐聚。

## 六、效果优势的根源解释

### 6.1 与 baseline 路线的机制对比

为什么 AgentTorrent 能支持别人支持不了的研究？根源不在"规模更大"，而在**三个结构性设计**：

**（1）分母独立于预测目标。** 按文件名搜索的数据集（GitSkills、SpecMine）把"是否被检索到"与"是否含配置"绑死，永远无法回答普及率。AgentTorrent 先按工程性筛仓库再看配置，等于把混杂变量切开。这是测量学上"先定总体再测暴露"的正确姿势——论文实验已支持（10,944/40,901 的比率可直接计算）。

**（2）启发式锚定厂商文档。** 文件名搜索的隐含假设是"文件名稳定"，但配置生态漂移极快（论文的周度监控就是为此设计）。每条启发式引用文档+记录核验日期，使规则库变成**可审计、可追踪漂移**的活文档，而不是一次性快照——论文实验已支持（312,453 条 commit 依赖仓库衍生启发式检出，说明纯文档规则也不够，两者互补）。

**（3）链接而非罗列。** 把工件、导入、规划文档、commit 关在同一仓库名下，使"agent 是否参与编写自己的指令"这类因果性问题第一次可查——论文实验已支持（23.8%/36.1% 的共现数据）。

### 6.2 外部检索交叉验证

以下为本次检索范围内找到的相关研究对照（检索关键词：GitSkills dataset、AGENTS.md census、detecting AI coding agents census、AgentConfigs 等）：

| 研究（可核验链接） | 相似尝试 | 相关结论 | 与本文的差异与边界 | 对根源解释的影响 |
|---|---|---|---|---|
| Zarzycki, AGENTS.md/CLAUDE.md 普查（[arXiv:2610.31715](https://arxiv.org/abs/2610.31715)） | 22,854 个高星仓库的指令文件内容分析 | 26.3%（最高星层 59.6%）有指令文件；1/3 指令集带生成器签名；4/5 创建后被编辑 | 只看根目录两文件、限 1,000+ 星；与本文 26.8% 的普及率量级互相印证 | **支持**：普及率量级一致；其"生成器签名"独立佐证"工具写指令"现象 |
| Khosravani & Mockus 180M 仓库普查（[arXiv:2606.24429](https://arxiv.org/abs/2606.24429)） | 四层检测框架（bot 账户/消息签名/作者名/配置文件） | 单一 bot 账户通道只覆盖 3.3% 的 Claude Code commit；commit 与 PR 两通道分别对 Claude Code/Codex 几乎全盲 | 覆盖 1.8 亿仓库但工件内容不落地；自认召回未知 | **支持**：证明单一检测通道系统性偏倚——本文 833 条启发式+双侧评估正是对该问题的回应 |

| Anthropic 上下文工程（[官方文章](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)） | — | context rot：token 越多注意力越稀释，上下文是稀缺资源 | 厂商观点文章，非实证研究 | **背景支持**：说明上下文文件为何值得作为研究对象（它们直接决定有限上下文的利用率） |
| Spec Kit（[github/spec-kit](https://github.com/github/spec-kit)） | spec-driven 开发框架 | `/specify→/plan→/tasks→/implement` 各阶段落盘 Markdown 工件 | 框架本身，非研究 | **背景支持**：解释规划文档这一新制品类别的来源 |

**本次检索范围内未发现**：对"配置工件+致谢 commit 同仓链接有效性"这一具体设计进行独立复现的第三方研究（该数据集 2026 年 11 月刚发布，属合理结果）；亦未发现否定"文档锚定启发式优于文件名搜索"的直接反例。

### 6.3 综合判断与未决问题

**多研究共同支持的机制**：配置文件的普及率量级（~26%）已被两条独立采样路径（Zarzycki 高星普查与 AgentTorrent 工程项目样本）交叉印证；单一检测通道的系统性偏倚已被 Khosravani & Mockus 定量证明。**仍属推测的部分**：精度评估的标注与启发式开发共用 Claude 家族模型（论文在局限中自认标签非独立），99.87% 等数字可能偏乐观——但人工召回核查（386 中命中 383）提供了非模型依赖的旁证。**适用边界**：结论限于默认分支、活跃、有许可证、十种语言的工程项目；commit 致谢 ≠ 实际贡献量，未致谢的使用完全不可见；采样或检测规则跨版本变化时，总量变化不能直接解读为采用率变化。

## 七、必要知识反推

假设一个零基础的人要复现这项工作，最少需要掌握：

**领域知识层**

- 六个工具各自的配置机制全景：哪个工具读哪些路径、忽略哪些（如 Cursor 只读 `.cursor/rules` 下的 `.mdc` 而忽略那里的 README.md）——不懂这个，358 条路径启发式一条也写不出来；
- spec-driven 开发生态：73 个框架各自把规划文档放在什么路径——这是 523 条规划文档启发式的原料；
- commit 归因惯例：co-author trailer、工具自动插入的致谢与用户手写惯例的差别——不懂会把"采纳评审建议"误算成"agent 写码"。

**方法论知识层**

- MSR 社区的抽样方法论：为什么用 GHS、为什么设贡献者/活跃度门槛（Kalliamvakou 2014 的 GitHub 挖矿陷阱清单）、什么是"工程软件项目"分类传统（Munaiah et al. 2017）——这是分母设计的理论依据；
- LLM 标注的验证方法学：双模型独立盲标+人工仲裁+κ 系数+置信区间——否则无法证明 40,901 个标签可信；
- 测量学思维：精度/召回双侧评估、分层加权、CI 外推——区别于"搜到多少算多少"的检索式思维。

**工程知识层**

- 大规模 GitHub 数据工程：API 限流处理、clone 默认分支、跟随文件改名读历史、保留 commit 日志以支持免重克隆的规则重放；
- FAIR 数据管理：DOI、开源许可证、逐列文档、来源记录；
- **知识融合的关键节点**：把"厂商文档作为真理来源"这个软件工程直觉，与"先定总体再测暴露"这个测量学原则，在"启发式必须引用文档"与"抽样独立于配置"两个具体设计上焊接起来——这是整篇论文的创造性核心；再用"链接数据库"的形态把两者固化，使下游研究者无需重复这两步。

## 八、论文中可以提取的通用性灵感

**灵感一：分母必须独立于预测目标。**
核心思想：要测量某现象的普及率，样本选择标准不能包含该现象本身。
论文证据：AgentTorrent 先筛工程项目再看配置（10,944/40,901），而文件名搜索类数据集（GitSkills 379 万文件、>50% 重复）无分母且混入教程模板。
推广场景：① 测量企业内某安全实践的采用率时，不能只调查已注册该实践的团队；② 问卷调查中避免筛选题与目标行为相关；③ 量化"某 API 的使用比例"时应从全部代码库抽样而非从该 API 的搜索结果抽样；④ 病例对照研究 vs 队列研究的设计选择。

**灵感二：规则库要锚定权威来源并监控其漂移。**
核心思想：面向快速演化的生态建检测规则时，每条规则绑定可审计出处并持续监控来源变化，规则库才能长期活着。
论文证据：358 条路径启发式逐条引用厂商文档并记核验日期；周度监控 438 个厂商页面自动报警；未知路径回扫发现 `.claude/workflows` 等新位置。
推广场景：① 合规检查规则引用法规条文并跟踪修订；② 爬虫选择器绑定页面结构并在改版时告警；③ 知识库条目附引用链接并定期验证存活；④ 依赖库 API 兼容性矩阵跟踪上游 changelog。

**灵感三：链接数据 > 单表数据。**
核心思想：在同一实体（这里是仓库）下链接多类证据，能催生单表数据无法回答的问题。
论文证据：因为 commit 与工件同仓链接，才能发现"23.8% 的指令文件由被致谢的工具参与引入"——工具在自己写缰绳。
推广场景：① 学习分析中把课程资源、论坛发帖、成绩链接到同一学生；② 把代码漏洞报告与修复 commit、测试用例链接；③ 用户行为日志与客服工单按账号链接；④ 医疗中把处方、检验、诊断按患者链接。

**灵感四：拆解"信用类型"再统计贡献。**
核心思想：聚合指标前先问"这个信号的语义同质吗"，不同产生机制的信号混在一起会系统性误导。
论文证据：Gemini 82.4% 的致谢只是评审建议被采纳，Copilot 39,047/184,386 同理——不拆分会把"建议被采纳"算成"代码由 AI 写"。
推广场景：① 引用计数区分自引/强引/弱引；② 销售归因区分首触/末触；③ 开源贡献统计区分 bot/CI/真人；④ 社交媒体影响力区分转发与原创。

**灵感五：LLM 标注的"双模型盲标+人工仲裁"协议。**
核心思想：用 LLM 做大规模标注时，独立性要用第二个不同家族的模型来构造，分歧用人工仲裁，全部原始响应存档备查。
论文证据：DeepSeek 标注、GLM-5.3 盲标 1,039 样本（一致率 98.0%、κ=0.87）、第一作者仲裁 21 例并反馈改进 prompt。
推广场景：① 内容审核的自动化初审；② 任何用 LLM 生成评测集/训练标签的生产流程；③ 多模型交叉验证的文献筛选；④ 数据清洗中的异常判定。
