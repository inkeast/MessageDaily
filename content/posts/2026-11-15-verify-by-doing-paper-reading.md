## 一、论文背景

### 1.1 从" Agent 会做题"到"Agent 会自我改进"

LLM Agent 的能力近年来突飞猛进，但一个根本问题始终存在：**Agent 做完一件事后，怎么知道自己做得对不对？** 这个问题看似简单，实则是所有自我改进系统的命门。所谓 Agent 自我改进（self-improvement），指的是 Agent 在完成任务的过程中或之后，修改自己的"做事程序"，让下一次尝试做得更好。改进可以发生在两个层面：

- **改权重**：通过强化学习等方式更新模型参数，代价高昂且测试时通常不可行；
- **改程序**：在模型权重冻结的前提下，更新 Agent 的工作流或 harness（指令、技能、检查清单等外围程序）。

所谓 **harness**，可以类比为给模型套上的"岗位操作手册"——它规定了 Agent 拿到任务后先做什么、后做什么、调用哪些工具、执行完如何自检。模型本身是"大脑"，harness 是"工作流程与规章"。近年来一系列工作（GEPA、RHI、TTHE 等）证明：不动权重、只演化 harness，就能显著提升测试时表现。

### 1.2 测试时的根本困境：没有外部反馈

但"改程序"这条路有个隐藏前提——你得知道改了之后是变好还是变坏。在标准化基准上，这不难：跑一遍基准，拿分数当反馈。然而一旦走出基准，进入真实部署场景，**参考答案和任务完成信号往往是不可用的**。用户不会告诉你"你这个 CRM 更新做对了，打 95 分"；环境本身也不会弹出"任务成功"的提示。此时 Agent 只能依靠两样东西判断成败：任务请求文本本身，以及与环境交互过程中产生的观察。

这就产生了两个相互纠缠的挑战：

1. **从不完整的观察推断任务成败**：只看表面的执行记录很容易误判。论文开篇的预算表格例子很典型——任务要求正确分派每笔费用的付款方、保证费用总计一致、算好税后净收入。如果检查只停留在"表格里有 Manager/Production/Total 这些标签、表头存在"，那么数字加起来对不对、付款方分派对不对，全都无从知晓。**找到了期望的标签，不等于任务完成。**
2. **反馈本身可能不完整时，如何改进**：更隐蔽的问题是，如果你用来判断成败的"检查程序"本身有盲区，那么基于它的自我改进就会被误导——你会在错误的方向上越走越远，而且每次改进都"通过"了自己的检查，盲区永远暴露不出来。生成再多候选，用同一套有盲区的检查去筛选，**盲区会被原样保留**。

### 1.3 现有方法各补一角，唯独不补"验证本身"

论文梳理了三类现有方案，指出它们都只解决了一部分问题：

- **工具增强的批评**（CRITIC 等）：让模型用工具获取额外观察来批评自己的输出，能补充证据，但检查程序本身是固定的，发现了盲区也无法把它固化成以后的检查；
- **回顾式诊断与偏好历史**（RHO、RHI、TTHE 等）：用历史执行记录指导执行程序更新，但评估端不动，验证盲区随改进累积；
- **红皇后哥德尔机 RQGM**：首次让 Agent 和 Evaluator 联合演化，但其 Evaluator 替换依赖留出集（held-out）上的真值标签引导——而这恰恰是测试时拿不到的外部反馈。

一句话总结动机：**验证程序本身应该成为测试时改进的对象，而且在没有外部反馈的条件下也要能被改进。** 这就是本文要解的题。

## 二、论文定位和关联工作

### 2.1 研究谱系一：执行端程序优化

| 工作 | 更新对象 | 反馈来源 | 与 VbD 的关键区别 |
|---|---|---|---|
| DSPy / AFlow | LM 流水线 / 代码化工作流 | 验证集指标 | 离线优化，需要标注数据 |
| Voyager | 可执行技能库 | 环境反馈 | 跨任务积累，不做任务内验证演化 |
| Self-Refine / Reflexion | 输出 / 后续行为 | 自我反馈 | 单轮改进，无持久的验证程序更新 |
| GEPA（ICLR 2026 Oral） | 提示词 | 验证指标 + 自然语言反思 | 用 1/35 的 rollout 超越 RL，但仍需验证指标 |
| HGM / RHO / RHI / TTHE | Agent 程序 / harness | 基准分 / 自偏好 / 轨迹代理信号 | 只改执行端，评估端固定 |

GEPA 值得多说一句：它证明了"用自然语言反思替代标量奖励"可以极其样本高效（678 次 rollout 打败 GRPO 的 24000 次），这为"语言空间的程序演化"提供了强证据。VbD 继承了这一思想，但把演化对象从提示词扩展到了"执行 + 验证"两套程序。

### 2.2 研究谱系二：为判断获取证据

ReAct 让推理与行动交织；CRITIC 用工具批评输出；Self-RAG 学习检索与批评决策；Agent-as-a-Judge 用 Agent 检查工件是否满足需求；VAGEN 主动探测图形界面状态。这条线的共识是：**判断任务完成需要超出 Actor 执行轨迹的额外观察**。VbD 的推进在于：把检查发现（findings）带进后续轮次，变成对执行与验证两个程序的持久修改。另一面，Huang 等人的经典工作证明 LLM 在无外部反馈时内在自我纠错会失效甚至变差——这为 VbD"验证必须主动获取证据而非凭空自省"的设计提供了反面警示。

### 2.3 研究谱系三：执行与评估共演化

| 工作 | 共演化机制 | 外部依赖 | 与 VbD 的差异 |
|---|---|---|---|
| 过程监督 / 自奖励 LM / EvoRubrics / 证明者-验证者 | 训练阶段耦合生成与奖励 | 人工反馈 / 训练 | 改权重，非测试时 |
| RQGM（arXiv 2606.26294） | 纪元内评估固定、边界处替换 Evaluator | 留出集真值标签引导替换 | VbD 无标签，每轮内审查验证变更 |
| Double Ratchet | 指标演化 + 锚定参考集 | 锚定参考集 | VbD 无参考集 |

**定位结论**：VbD 是首个在**无外部反馈的单任务内**让验证程序与执行程序共演化的框架。与最接近的 RQGM 相比，本质区别有二：其一，RQGM 的 Evaluator 替换靠留出集真值打分，VbD 靠同一批候选上的双向比较审查；其二，RQGM 在纪元内评估完全固定，VbD 每轮都测试 Evaluator 提案。

## 三、问题定义

### 3.1 从具体场景到抽象结构

具体场景：Agent 在一个任务内反复尝试，每次尝试产生一个候选（执行记录 + 结果状态 + 回复/交付物）。没有基准分、没有参考答案。要产出尽可能好的最终输出。

论文的核心洞察是一个深层结构相似性：**验证程序的演化 ≈ 评估器的在线学习，但它所需的训练信号不必来自外部真值，而可以来自"证据支撑度的横向比较"**。就像法律体系不需要"绝对真理"也能进步——两份判决书摆在一起，看哪份的证据链更扎实、法条适用更准确，就能选出更好的裁判者。

### 3.2 形式化定义

给定任务 x（含请求、材料、许可工具），定义：

- **Actor harness H**：指令 + 工作准则（rubric）+ 技能 + 持久检查计划；
- **Evaluator harness Φ**：同样由指令、rubric、技能构成，但用于评估；
- **保留状态**：现任候选 z、候选集 G、历史 D；
- **固定不变**：模型权重、任务需求、工具权限、选择器 Π、审查者、接受规则。

**求解目标**：在预算内（3 轮 × 2 次执行）最大化最终选定输出的离线得分，约束是演化全程不得接触官方评分与参考答案。

这个抽象的精妙之处在于"冻结与可演化的精确切分"：任务需求冻结（防止目标漂移）、底层模型冻结（公平且现实），但**生产信号的方式**（验证程序）与**消费信号的方式**（执行程序）都可演化。验证程序的更新改变了内部信号如何产生，而需求本身不变——这就在"无外部反馈"和"目标不漂移"之间架起了桥梁。

## 四、问题解法

VbD 的每一轮循环分四步，下面逐步拆解。整体类比：Actor 像"运动员"，Evaluator 像"裁判"，Editor 像"教练组"，审查者像"仲裁委员会"——运动员和裁判都在被教练组训练，而裁判的晋升要过仲裁委员会这一关。

### 4.1 第一步：Actor 试验（Actor Trials）

当前 Actor（H）和提案 Actor（H̃）各自执行一次任务，产出新候选 a、b。两者接收**相同的临时检查**，只有提案方带持久编辑——这样既让双方都暴露于当前的验证关注点，又测试了提案的执行程序。临时检查本轮过后过期，除非被重新审议。

每个候选完整保存执行记录、结果状态与交付物，并记录其生成 harness。**这个链接至关重要**：后面改进后的 Evaluator 可能会从候选池里选中一个早先的输出——选中旧输出不构成采纳新 Actor 的试验证据，所以必须留痕，让"输出选择"与"Actor 采纳"可以分别判定。

### 4.2 第二步：主动评估（Agentic Evaluation）

这是论文标题"Verify by Doing"的直接体现。Evaluator 不是坐在那里看执行记录打分，而是**动手检查**：用工具读取工件与环境状态，执行针对性检查。比如预算表格任务中，Evaluator 会实际读取费用与收入的单元格，重算总计是否一致。

发现（findings）采用结构化形式：

$$F_{\Phi}(B) = \{(c_i, q_i, o_i, f_i)\}_{i=1}^{m}$$

每条发现记录四个要素：候选 $c_i$、命题 $q_i$（要检查什么）、观察与来源 $o_i$（实际读到了什么）、带不确定性的范围化评估 $f_i$。评估按 Field（字段）、Relation（关系）、Aggregate（聚合）、Task（任务）四层范围组织。

一个固定的选择器 Π 把发现解读为对任务的判断：$d = \Pi(x, B, F_{\Phi}(B))$，区分"支持的偏好 / 平局 / 未决判断 / 回退"。这个偏好就是**内部信号**——替代外部基准分，驱动后续一切决策。

### 4.3 第三步：比较选择（Comparative Selection）——三重门

这是 VbD 机制设计上最精细的部分，三件事分开决定：

| 决策 | 机制 | 通过条件 |
|---|---|---|
| **Evaluator 采纳** | 固定审查者在同一批候选上对比新旧 Evaluator 的报告，比较证据支撑度与准则适用性 | 双向顺序审查都支持提案（$V_E \wedge v_1 = v_2$），否则保留原版 |
| **输出选择** | 保留版 Evaluator 在合格候选集 C 上产生支持的选择 | 按内部信号选出 $z^+$，可以是早先的候选 |
| **Actor 采纳** | 提案 Actor 的新鲜输出必须自己证明自己 | 有效试验 $\wedge$ 选中的恰是提案自己的输出（$z^+ = b$）$\wedge$ 初始比较与现任比较都有严格支持（$s_1 \wedge s_2$） |

为什么三重门缺一不可？

- **双向顺序审查**（两个 presentation order 都须支持）抑制位置偏差——LLM 评审对先呈现的内容有系统性偏好；
- **输出选择与 Actor 采纳分离**：防止"选了一个好输出，却固化了一个坏 harness"。案例 Sales047 展示了这一点——提案的输出被选中（它确实更好），但最终比较只判定"等价"而非"严格更优"，于是 Actor 更新被搁置，好输出照用，坏 harness 不固化；
- **Actor 采纳要求自家新输出获严格支持**：直接堵死了"提案 Actor 恰好赶上一个旧候选出彩"这类张冠李戴的证据。

### 4.4 第四步：Harness 共演化（Harness Co-evolution）

Editor（固定指令 $L_{edit}$）把验证发现翻译成对执行、验证或两者的修改提案，每项修改必须声明**预期效果**与**对应的检验方式**。同一条观察可以同时变成两样东西：

> Evaluator 发现"宣称不可用的联系表其实读得出来"→ Actor 获得一条检索指令（下次换个 API 端点再试），Evaluator 获得一条可用性检查（以后凡有候选宣称资源不可用，先实际读一遍）。

历史 D 保留被拒绝的试验与观察来源，供后续提案参考。任务结束后 harness 与历史全部重置——VbD 研究的是**单任务内**的自适应。

### 4.5 全景机制对照表

| 组件 | 输入 | 输出 | 类比 |
|---|---|---|---|
| Actor (H) | 任务 + harness | 候选（记录/状态/交付物） | 运动员 |
| Evaluator (Φ) | 候选池 + 工具 | 结构化发现 + 内部信号 | 主动取证的裁判 |
| 审查者（固定） | 新旧 Evaluator 报告 × 2 顺序 | Evaluator 采纳决定 | 仲裁委员会 |
| 选择器 Π（固定） | 任务 + 候选 + 发现 | 输出偏好 | 记分规则 |
| Editor（固定） | 发现 + 历史 | 下一轮双 harness 提案 | 教练组 |

## 五、评估指标与实验证据

### 5.1 实验设置

- **主骨干**：DeepSeek-V4-Flash-0731（284B 参数 / 13B 激活），全部角色同一模型、权重冻结；离线评分用 GPT-5.6-sol（xhigh 推理强度）；第二骨干 Qwen3.8-Flash-Next（125B / 6B）验证泛化。
- **协议**：所有迭代方法 3 轮 × 每轮 2 次执行 = 每任务 6 次尝试；3 次运行取均值 ± 标准差。
- **基准**：AutomationBench（600 任务，工作流执行，验证保存的应用状态）、τ3 Banking（97 任务，对话 + 操作的政策合规）、GDPval（选 133 个支持文档工具的任务，专业交付物按官方 rubric 评分）。三个基准要求的"完成证据"各不相同，正好检验方法的通用性。

### 5.2 主结果：三基准全面第一（无外部反馈方法中）

| 方法 | AutomationBench (%) | τ3 Banking (%) | GDPval (%) |
|---|---|---|---|
| Base (Pass@1) | 22.3 | 35.1 | 70.8 |
| BoN (6 选 1) | 31.2 | 40.5 | 76.8 |
| HGM | 31.8 | 41.2 | 78.0 |
| RHO | 30.9 | 38.8 | 76.4 |
| RHI | 31.7 | 45.4 | 78.4 |
| RQGM | 33.7 | 41.2 | 80.1 |
| **VbD** | **37.0 ± 1.9** | **49.5 ± 2.1** | **82.4 ± 1.4** |
| 外部反馈参照†（不参与排名） | 42.6 | 56.4 | 83.6 |

VbD 相对三个基准上各自的最强基线分别领先 **+3.3 / +4.1 / +2.3 个百分点**。作为参照，带基准分演化的外部反馈方法（HGM+基准分）为 42.6%——VbD 距这个"作弊上限"还有 5.6pp，量化了无外部反馈设定的真实难度。Qwen 骨干上 VbD 同样三项全部第一（48.4 / 57.4 / 84.7），证明增益不是特定模型的巧合。

轮次轨迹（AutomationBench）：30.0% → 34.3% → 37.0%，且第二轮均值就已超过 RQGM 的最终成绩、token 成本更低。partial credit（每任务满足的断言比例）从 66.35% 升至 70.26%，说明改进是"满足更多具体需求"而非碰巧过线。

### 5.3 关键诊断实验

**RQ2a：Actor 更新门控质量**。用离线 partial credit 标注每次提案是改进还是回归，统计门控的拒绝能力：

- VbD 的**回归拒绝率（TNR）89.3%**，RQGM 仅 71.2%（**+18.1pp**）；精度 77.6% vs 77.0%（持平），接受率与 HGM/RQGM 相当。
- 门控计数（表 11）：VbD 提案 1,104 次、接受 207 次，其中 FP（接受的回归）仅 45 次、TN（拒绝的回归）374 次。三重门没有因严格而扼杀改进，只是精准过滤了退步。

**RQ2b：固定候选池上的选择质量**。把 BoN 的 6 个候选固定住，只换选择器：VbD 演化后的 Evaluator 选出 35.8% 通过率，BoN 初始 Evaluator 31.2%，RQGM 33.4%。**输出一个不换，仅靠改进验证就多捞回 4.6pp**——直接证明"更好的验证能从同样的池子里发现已有成功"。

**RQ3：消融**。去掉主动验证（只评既有轨迹、不做新检查）：AutomationBench 掉 2.7pp；冻结 Evaluator（只让 Actor 演化）：掉 1.6pp。两个消融在三个任务集上全部同向为正，说明"获取证据"与"保留验证教训"贡献各自独立、不可互相替代——Actor 演化补不上验证的缺口。

**行为学证据**：技能加载率从 0%（第 1 轮无技能可用）升至 23.1%；含状态验证的尝试从 20.4% 升至 25.3%；Search 调用降 28.3%、总调用从 63.8 降至 54.6——Actor 从"到处搜"转向"做完就验"，与设计意图一致。

### 5.4 案例研究：机制如何落地

- **Sales063（双 harness 协同）**：初始尝试漏掉客户记录更新、回复里点名了被排除的参会者，且未验证就宣称服务不可用。第 2 轮：Actor 加载"回复范围"技能、Evaluator 加对应 rubric——记录更新完成、回复合规，离线判过。对照组 HGM 与 RQGM 完成了主操作，但回复里始终保留着被排除者的名字。
- **Support091（仅靠验证翻盘）**：Actor 全程未变，第 3 轮改进的 Evaluator 重检早先候选对，发现初始输出的回复违规叙述了未处理项，于是把第 2 轮就已存在的通过候选选了出来——**新鲜尝试全失败，最终成功完全来自选择**。
- **Finance024（诚实的失败案例）**：Evaluator 把文件写入时间戳当成业务日期，选了失败输出。论文不回避：主动验证不能消除证据误读。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**对比对象**：RQGM 是此前最强的共演化方法，为什么它在本设定下输给 VbD？RQGM 的 Evaluator 替换发生在纪元边界、靠留出集真值引导；移到无标签的单任务设定后，其替换依据退化为任务观察上的效用估计，且纪元内评估完全固定。于是它的根本局限是：**验证盲区在整个纪元内持续误导 Actor 更新，而替换时机到来时又缺乏可靠的比较证据**。

VbD 的因果链（每步标注证据等级）：

1. **不完整验证误导自适应**（论文实验支持：消融去掉主动验证 -2.7pp；预算案例中表头检查看不到数值关系）→ 这是所有方法的共同瓶颈；
2. **主动验证扩展当前判断的证据基础**（论文实验支持：表格探针、消息重读等具体检查在案例中暴露了标签检查看不到的数值与内容关系）→ 缓解"推断成败"挑战；
3. **Evaluator 演化把漏检需求固化为持久检查**（论文实验支持：消融冻结 Evaluator -1.6pp；Support091/Marketing088 中改进的 rubric 改变了选择结果）→ 缓解"反馈不完整"挑战，盲区一旦暴露即成为永久检查；
4. **同一发现双路复用**（论文实验支持：Sales063 同一发现同时变成 Actor 技能与 Evaluator rubric；行为学上技能加载率 0→23.1%）→ 执行与验证的改进互相喂养，而非各自为战；
5. **三重门阻断回归式更新**（论文实验支持：TNR 89.3% vs 71.2%，+18.1pp；Sales047 展示输出选择与 Actor 采纳分离）→ 自我改进不至于被自我欺骗劫持；
6. **推论（阅读者推测）**：VbD 相对 RQGM 的领先中，有一部分可能来自"每轮审查验证变更"与"每轮测试 Actor 提案"带来的更高更新频率——论文的 6 次执行预算限制了 RQGM 的树搜索，此因素未被单独消融，应视为待验证假设。

### 6.2 相关工作检索与对照

围绕"无外部反馈的自我改进"这一核心设定，检索结果如下：

| 研究（可核验链接） | 相似尝试 | 相关结论 | 与本文的差异与边界 | 对根源解释的影响 |
|---|---|---|---|---|
| [TTHE, arXiv 2607.08124](https://arxiv.org/abs/2607.08124) | 测试时用无标签轨迹演化可执行 harness，冻结权重 | 执行程序可在无标签下测试时改进；但其自认核心挑战是"执行派生代理信号可靠性" | 只演化执行端，跨批次适应；代理信号不可靠的问题恰是 VbD 用"演化验证"回应的问题 | 支持：无标签程序演化可行；补充：验证端不演化则代理信号瓶颈仍在 |
| [Huang et al., arXiv 2310.01798](https://arxiv.org/abs/2310.01798), ICLR 2024 | 系统检验"内在自我纠错"：无外部反馈时让模型自评自改 | GPT-3.5/GPT-4 无 oracle 标签时自我纠错持平或变差 | 静态 QA 推理任务，非工具环境；测的是"凭空自省"，非"主动取证" | 支持：印证"凭空自省不可靠"，反衬 VbD 让验证主动获取环境证据的必要性；提示边界：若环境无可读状态，VbD 机制退化 |
| [RQGM, arXiv 2606.26294](https://arxiv.org/abs/2606.26294) | 纪元化 Agent-Evaluator 共演化，留出集真值引导替换 | 共演化评审器可降低自偏好偏差、以 1/3 搜索成本提升证明评分 | 需要 held-out 标签与跨任务搜索预算；VbD 是其无标签、单任务设定的直接对照 | 支持：执行-评估共演化优于固定评估（跨两项研究、两种设定一致）；限定：RQGM 的结论不能直接证明无标签设定下仍成立——这正是 VbD 补的空 |
| [GEPA, arXiv 2507.19457](https://arxiv.org/abs/2507.19457), ICLR 2026 Oral | 自然语言反思演化提示词，1/35 rollout 超越 GRPO | 语言空间反思是样本高效的学习媒介 | 需要验证指标作为反思信号；跨任务离线优化 | 支持：语言空间程序演化的高样本效率解释了 VbD 为何在 6 次执行内见效；限定：GEPA 的指标依赖在 VbD 中被内部信号替代，替代品的可靠性由本文自己的固定池实验背书 |

在本次检索范围内，未发现除 RQGM 与 VbD 外其他"无外部反馈且同时演化验证程序"的同期工作；亦未发现得出"演化验证在同类设定下无效或有害"结论的研究。最接近的反向证据是 Huang 等人对内在自我纠错的否定，但其任务设定（无工具的静态推理）与 VbD（可检查环境的工具型 Agent）存在本质差异，不构成直接反驳。

### 6.3 综合判断与未决问题

**多研究共同支持的机制**：(a) 冻结权重下的测试时程序演化有效（TTHE、GEPA、本文）；(b) 执行-评估共演化优于只演化执行（RQGM 原设定、本文消融）。**仍属推测的部分**：VbD 领先中"更新频率"与"三重门"各自的贡献份额未被分解；发现双路复用是否在更长轮次中持续增益也未验证。**适用条件**：环境状态可隔离、可重读（论文自述不可逆动作与不可重置环境限制直接应用）；验证发现需可转译为可执行检查。**可能的失效条件**：Actor、Evaluator 与审查者共用同一模型，可能共享同一种证据误读（Finance024 已现一例）；延迟生效的副作用与不可访问的状态会逃逸验证；与外部反馈参照 5.6pp 的差距提示内部信号仍系统性弱于真值。

## 七、必要知识反推

假设一个零知识的人要完成这项工作，最少必须掌握什么？

**领域知识层**：
- Agent harness 的构成（指令/技能/rubric/检查计划）与其对行为的决定性作用——不理解这个，就不知道"演化什么"；
- 测试时自适应与训练时自适应的区别——不知道权重冻结的约束，就不会想到在程序空间做文章；
- 基准评分、参考答案、内部信号三种反馈的可得性分层——这是问题定义的出发点。

**方法论知识层**：
- 程序/prompt 演化谱系（DSPy→GEPA→HGM→RQGM）——知道前人止步于何处，才能定位"验证程序本身未被演化"这一空缺；
- LLM-as-a-judge 的位置偏差与比较评审技巧（双向顺序）——没有这知识，三重门设计不出来；
- 奖励模型的过优化/奖励博弈理论（Skalse、Gao 等）——理解"不完整检查会偏爱漏检需求的输出"，才有动机让检查进化；
- 内在自我纠错的失败模式（Huang 等）——知道凭空自省不可靠，才会坚持"验证必须动手取证"。

**工程知识层**：
- 三类基准（工作流状态检查/政策对话合规/专业交付物 rubric 评分）的评估管线搭建，含离线评分与在线选择的严格隔离——隔离不严，实验就自我污染；
- 结构化发现（候选/命题/观察/评估四元组）与证据引用协议的设计——让"证据支撑度可比较"成为可实现的操作；
- 固定候选池、消融、门控计数（TP/FP/TN）等归因实验设计——把"共演化有效"拆成可分别验证的机制主张。

**知识融合的关键节点**：
1. 把"验证"从 noun 变成 verb——发现 RQGM 的留出集依赖可以被"同候选双向比较审查"替代，是全文最关键的洞察，它把共演化从"需要真值"的设定解放出来；
2. 把"发现"设计为一等公民——同一条发现三路分发（内部信号、Actor 更新、Evaluator 更新），使执行与验证的改进天然耦合；
3. 把"选择好输出"与"固化好程序"在机制上拆开——防止自我改进系统最危险的自证循环。

## 八、论文中可以提取的通用性灵感

**灵感一：改进生产信号的方式，而不只是消费信号的方式**。
核心思想：当反馈不可靠时，优化"反馈如何产生"往往比优化"如何根据反馈行动"更根本。
论文证据：冻结 Evaluator 消融掉 1.6pp，固定池上仅换选择器即 +4.6pp。
推广场景：推荐系统中除了调排序模型也演化离线评估器；教育中除了改进教学方法也迭代考试的设计质量；代码团队除了改代码也持续演化 CI 检查集；个人复盘时先问"我的衡量标准对吗"再问"我努力对吗"。

**灵感二：证据要主动获取，判断要保留不确定性**。
核心思想：凭空自省不可靠，动手检查才能产生真证据；检查后仍无法确定的，如实标注"未决"而非强行二选一。
论文证据：预算案例中表头检查与单元格重算的信息量差异；发现四元组中显式的"带不确定性的范围化评估"；Finance024 失败案例反向印证。
推广场景：法务尽调中的实地核查优于书面自述；科研中区分"数据支持"与"推测"；运维中区分"监控覆盖到的"与"未覆盖的"。

**灵感三：同一证据，多处复用**。
核心思想：一次发现的价值可以通过"变成做法 + 变成检查"双重固化而翻倍。
论文证据：Sales063 同一发现产出 Actor 技能与 Evaluator rubric；Marketing015 联系表检索既成执行指令又成可用性检查。
推广场景：事故复盘同时产出"操作规程修订"与"审计检查项"；安全研究同时产出补丁与入侵检测规则；考试错题同时修正解题习惯与出题人认知。

**灵感四：采纳变更的证据门槛要与其固化程度匹配**。
核心思想：临时使用的改动可以宽松，要固化的改动必须自证——且证据必须来自其自身的新鲜表现。
论文证据：三重门（双向审查 + 自家输出被选中 + 双阶段严格支持）；TNR +18.1pp 而 precision 不掉。
推广场景：组织变革先试点再推广（试点证据绑定在变革本身）；A/B 测试的新策略须在自己的流量上赢；宪法修正的门槛高于普通立法。

**灵感五：分离"这次做对了"与"以后都会对"**。
核心思想：单次成功与程序性进步是两个命题，需要两套判定。
论文证据：Sales047 选中提案输出却拒绝 Actor 更新；Support091 Actor 不变仅靠更好选择翻盘。
推广场景：投资中区分一次盈利与可持续策略；面试中区分候选人碰巧答对与真实能力；软件中区分测试通过与设计正确。

## 附录：方法一页速览

一轮 VbD 循环的浓缩版：① 当前/提案 Actor 各跑一次 → 两个新候选入池；② 两个 Evaluator 主动检查同一候选池 → 结构化发现 + 内部信号；③ 三重门：双向审查定 Evaluator 去留、保留 Evaluator 选输出、提案 Actor 靠自家新鲜输出获严格支持才转正；④ Editor 把发现翻译成双 harness 修改提案并声明检验方式，进入下一轮。全程不接触基准分与参考答案；任务结束，harness 与历史重置。

> 值得注意的边界：VbD 的自我改进是任务内的、不跨任务迁移的；三轮预算内的结论，更长演化周期下是否持续增益尚属开放问题。与外部反馈参照 5.6pp 的差距既是内部信号的天花板暗示，也是"验证还能进化到什么程度"的悬念。
