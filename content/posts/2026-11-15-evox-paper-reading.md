## 一、论文背景

### 1.1 什么是 Agent Harness？

一个常见误解是「Agent = 大语言模型」。模型本身只会输入文本、输出文本——它不能执行 `ls`，不能记住上一轮发生了什么，也不知道自己的上下文已经用了 18 万 token。真正把「会描述工具调用的模型」变成「修好了失败测试的 Agent」的，是包裹在模型外围的一整套软件层——**Agent Harness（操作套件）**。

用类比来说：如果模型是一位能力出众的厨师，Harness 就是整个后厨——灶台、刀具、传菜流程、防火规程的总和。同一 位厨师换一个后厨，出品可能天差地别。

一个典型 Harness 通常包含六件事：

| 组件 | 作用 | 举例 |
|------|------|------|
| Agent 循环 | 调用模型→执行工具→回填结果→再调用，直到任务完成 | while 循环 + 终止条件 |
| 工具集 | 模型的「双手」 | bash、文件读写、搜索、浏览器、MCP 服务 |
| 上下文管理 | 决定模型每轮看到什么，窗口满了如何压缩 | 系统提示词、compaction 摘要 |
| 权限与沙箱 | 哪些动作需要人批准、爆炸半径多大 | 白名单命令、Docker 容器 |
| 状态与记忆 | 跨轮次、跨会话保存状态 | 计划文件、CLAUDE.md/AGENTS.md |
| 停止条件与预算 | 最大轮数、最大 token、最大花费 | 防止整夜烧钱的死循环 |

Claude Code、OpenAI Codex CLI、OpenHands、SWE-agent、Aider 都是知名 harness。业界已经公认：**同一个模型，搭配不同的 harness，表现可以截然不同**——模型能力不等于 Agent 能力，中间隔着一整个执行层。

### 1.2 「决策合理」为何还会失败？

EvoX 论文的出发点是观察到三类普遍的执行失败：

1. **工具调用失配**：模型选对了工具，但调用格式畸形，或者把工具调用「泄漏」成了一段普通文本，执行接口根本无法处理；
2. **可恢复失败中断流程**：路径写错、依赖缺失、命令失败——这些本不意味着任务不可行，但 Agent 可能就此停手；
3. **虚报完成**：模型声称「任务已完成」，但实际操作从未成功执行——「说完成了」不等于「真完成了」。

这三类失败有个共同点：**模型的语义决策本身没有错，错发生在决策与执行之间的缝隙里**。现有 harness 各自零散地处理这些问题（比如有的内置重试、有的做强 schema 校验），但没有一个统一的视角说清楚：harness 到底在整个系统里扮演什么角色？

### 1.3 评测的困境

要证明「harness 设计影响成功率」，就得做横向对比，而这本身是个方法论难题：

- 把各家的提示词、工具、控制循环**全部统一**？那就把被研究的对象抹掉了——测的不再是 harness 本身；
- 完全**放任不管**？各家模型请求参数、运行时条件、失败归因都不同，比较就失真了。

**核心矛盾**：模型的能力已被充分研究，但模型决策如何被翻译成可靠执行，缺乏一个显式的概念框架与可控的评测方法。这正是 EvoX（运行时设计）与 Contrast（评测框架）分别要解决的两个问题。

## 二、论文定位和关联工作

### 2.1 Harness 与运行时控制谱系

- **SWE-agent**（Princeton，NeurIPS 2024）：提出 Agent-Computer Interface（ACI）概念，为仓库导航、代码编辑、测试专门设计了「为模型而设的接口」，证明了接口设计的巨大影响。链接：[arxiv.org/abs/2405.15793](https://arxiv.org/abs/2405.15793)
- **CodeAct**（ICML 2024）：用可执行代码作为组合式动作空间，比固定工具集表达力更强。链接：[arxiv.org/abs/2402.01030](https://arxiv.org/abs/2402.01030)
- **OpenHands**（ICLR 2025）：通用开源开发环境，事件流架构 + Docker 沙箱 + 多 Agent 协调。链接：[arxiv.org/abs/2407.16741](https://arxiv.org/abs/2407.16741)
- **Claude Code / Codex**：厂商将工具编排与执行控制集成进开发工作流的商业 harness；
- **Pi / Hermes / Prime Agent**：分别代表极简可扩展循环（Pi）、持久记忆与可复用技能（Hermes）、持久执行环境与递归子 Agent（Prime Agent）。

**可靠性与结构化工作流方向**：Reflexion 用语言反馈做下一轮尝试、CRITIC 做工具辅助自纠错、Agentless 把软件修复结构化为定位→补丁→验证三段。这些工作证明「执行设计超越模型推理」的重要性，但各自只解决单点问题。

**EvoX 的差异**：不是再造一个单点修复机制，而是提出「The Second Policy」统一视角，把散落的执行控制组织成 harness 层的系统性职责。

### 2.2 Harness 效应评测谱系

- **SWE-bench / SWE-bench Live / AgentBoard**：分别解决仓库级 issue 修复评测、基准时效性与污染、细粒度进度测量；
- **Harness-Bench**（arXiv:2605.27922）：系统测量 harness 效应，发现 GLM-5.3 在不同 harness 下满分率相差 13.5 个百分点，无一家 harness 在所有模型上领先；
- **The Scaffold Effect**（arXiv:2607.22585）：同一模型换 harness，每解一题的 token 消耗可差 40 倍；
- **Same Model, Different Harness**（arXiv:2608.26218）：固定模型权重下研究上下文管理与停滞执行处理的影响；
- **Harbor**（[harborframework.com](http://harborframework.com)）：Terminal-Bench 背后的统一评测框架，为异构 Agent 提供容器化任务规范。Contrast 的公平合约设计直接受其启发。

**EvoX/Contrast 的差异**：上述工作指出「同名配置不等于同等执行」——但 nominal 相同的参数，各家 harness 发给 provider 的实际请求仍可能不同。Contrast 用 Model Bridge 在 provider 侧审计真实请求，并用证据裁决区分「Agent 失败」与「基础设施失败」。

### 2.3 定位总结

| 维度 | 之前的路线 | EvoX/Contrast 的推进 |
|------|-----------|---------------------|
| 概念 | harness = 隐式的工程制品 | harness = 显式的「操作策略」，与模型「语义策略」对偶 |
| 机制 | 单点修复（重试/校验/反思各自为战） | 三机制覆盖执行环三个点位，形式化为 H=(Γ,Δ) |
| 评测 | 对齐声明配置即认为可比 | locked/shared/native 三分 + provider 侧请求审计 + 证据裁决 |
| 结论 | harness 影响性能（现象） | 操作策略与语义策略的匹配度决定增益（机制解释） |

## 三、问题定义

### 3.1 从具体到抽象

**具体问题**：Agent 的失败常常不是模型「想错了」，而是「合理的决策没有被可靠执行」。这三类缝隙（接口失配、中断、虚报）散落在执行环各处，该如何系统性接管？

**深层洞察**：一个 Agent 系统里其实存在**两个决策者**。论文发现的最本质结构是把二者显式分离：

- **语义策略 πθ**（模型）：决定「做什么」——理解任务、规划动作、根据反馈修正决策；
- **操作策略 H = (Γ, Δ)**（harness）：决定「怎么做」——提议如何被解释、执行、并汇入后续交互。其中 Γ 是面向模型的引导（注入上下文），Δ 是确定性运行时控制（处置输出）。

这个对偶类似于经济学中「决策权与执行权分离」的组织设计：董事会做战略决策（语义），CEO 与规章制度负责执行落地（操作）——两个策略互补而非替代。

**形式化**：每步交互中两个策略按如下方式协作：

```
g_t = Γ(h_t, s_t)                  # harness 注入运行时引导
c_t = Ctx(x, h_t, g_t, T_t)        # 组装模型上下文
u_t ~ πθ(· | c_t)                  # 模型输出提议
(â_t, d_t) = Δ(u_t, s_t, T_t)      # 运行时控制产出可执行动作与处置
```

其中 h_t 是交互历史、s_t 是运行时状态、T_t 是可用工具集。处置 d_t 可以放行执行、返回诊断或终止交互；工具反馈 o_t 更新 h_{t+1}、s_{t+1}。**注意：这里没有任何新增训练的 policy 网络**——操作策略是规则与引导的组合。

### 3.2 这个抽象的精妙之处

- **不引入第二个模型**：操作策略靠「引导 + 确定性规则」实现，不改模型参数，因此可跨 provider 复用——这是后文跨模型增益实验的前提；
- **覆盖全环而非单点**：三机制分别在「动作产生前」「执行受阻时」「收尾报告时」三个点位接入，对应公式里的不同环节；
- **评测问题同样被形式化**：任务 τ_i × 模型 m_k × harness a_j 的执行 r_ijk = Run(τ_i, m_k, a_j; φ_ik, ν_ijk)，其中 φ_ik 是受控外部条件、ν_ijk 是 harness 原生行为——给定这个结构，求在保留 ν 的前提下让比较公平，这引出 Contrast。

## 四、问题解法

### 4.1 三大操作机制：执行环上的三个关卡

EvoX 用 Rust 实现（内存安全 + 高并发，适合长期运行时），三个机制各守一个点位：

**机制一：Action Realization（动作实现）——「海关安检」**

模型输出 u_t 后、真正执行前，先过三道检查：工具调用检测（识别畸形结构化调用或以非标准文本形式表达的工具意图）→ schema 校验 → **有界**参数归一化。能恢复兼容表示就归一化为可执行动作 â_t；不能恢复则拒绝或退回模型修正，**绝不随意重新解释**。「有界」是关键词——只做保守兼容转换，防止 harness 自作主张曲解模型意图。

**机制二：Execution Continuity（执行连续性)——「陪跑教练 + 熔断器」」

工具反馈 o_t 返回后，Γ 引导模型诊断失败、修订后续动作而不是提前放弃；同时 Δ 监控重复错误模式，必要时启用熔断器终止无效循环；上下文管理器在接近窗口上限时自动压缩，支持长程交互。这是「软引导」与「硬控制」的混搭：能修就修，修不动就停。

**机制三：Outcome Grounding（结果接地）——「验收审计员」**

收尾阶段引导模型区分「打算做的动作」与「已完成的操作」，要求汇报基于 h_t 中记录的观察证据，而非想当然的成功假设。注意这个机制主要靠模型面指令实现，不做独立的正确性验证——目标是报告与观察一致，而非证明任务完成。

| 机制 | 执行环位置 | 主要组件 | 控制类型 |
|------|-----------|---------|---------|
| Action Realization | 模型输出之后、执行之前 | 调用检测、schema 校验、有界归一化 | 确定性 Δ 为主 |
| Execution Continuity | 工具反馈之后 | 恢复引导、重复错误检测、熔断、压缩 | Γ 引导 + Δ 控制 |
| Outcome Grounding | 最终报告时 | 接地式汇报引导 | Γ 引导为主 |

### 4.2 Contrast：既统一赛场又保留打法

Contrast 的核心是**公平合约**，把评测条件分三类：

- **Locked（锁定）**：按预定义规则锁定，如模型兼容的推理配置、输出上限、网络访问策略；
- **Shared（共享）**：在同一场比较内保持一致，如模型身份、provider 路由、执行预算；
- **Native（原生）**：保留 harness 特有属性——系统提示词、工具接口、上下文管理、恢复策略，**记录而非同质化**。

用足球做类比：锁定球场尺寸、用球规格、比赛时长（locked/shared），但不禁止任何一支球队用自己的战术打法（native）——因为战术正是你想测的东西。

四阶段流程：

1. **任务资格与完整性**：异构基准统一为带版本工件与内容身份的任务规范；**Oracle 对照**（用参考解法确认「做对了会被识别」）与 **No-op 对照**（什么都不做不该得分）正负双向检验 verifier 可靠性；检查环境与缓存是否泄漏答案；
2. **受控原生执行 + 请求审计**：Cove 执行基底为每个任务提供容器化环境；**Model Bridge** 统一适配各 harness 的 API 协议，并在请求发往 provider 途中检查受控参数是否真实生效——区分「声明的配置」与「实际发生的调用」；
3. **证据裁决**：每次运行收集 Agent 轨迹、模型请求、verifier 结果、运行时诊断与资源消耗。裁决规则 (y_ijk, q_ijk) = Adjudicate(r_ijk, e_ijk; ρ) 决定该记录是被计分、排除还是隔离——**基础设施故障不被算到 Agent 头上，正当的任务失败保留在评估中**；
4. **配对比较**：只在全部六个 harness 都有有效计分的公共任务-模型集合 I_common 上做统计比较，用任务级重采样估计置信区间。

## 五、评估指标与实验证据

### 5.1 实验设置

- **参赛方**：六家 harness——EvoX、Claude Code、Codex、Hermes、Pi、Prime Agent；
- **模型**：六个——Opus 5、Sonnet 5、GPT-6 Astra、GLM-5.3、Kimi K3、DeepSeek V4 Flash；
- **基准**：五个——Aider Polyglot（多语言编程，28 题）、GAIA（网络辅助推理，21 题）、Harbor Index（算法问题，28 题）、SWE-Live（仓库级修复，27 题）、Terminal-Bench 2.1（终端工程，28 题），共 132 任务、4752 个计划组合；
- **主指标**：二值任务成功率（基准各自 verifier 判定）；主比较集为 691 个公共任务-模型对；
- **EvoX 配置**：非交互模式 v1.1.0-pre.93，**关闭记忆、演化与扩展**——只测基线操作设计。

### 5.2 主结果：整体与分层

**整体（691 对）**：EvoX 56.2% > Pi 55.9% > Claude Code 55.3% > Hermes 54.4% > Prime 50.4% > Codex 49.6%；其余五家均值 53.1%，EvoX 领先约 +3.0pp。

**按模型分层（关键发现）**：

| 模型 | EvoX | 该模型最优 harness | EvoX vs 其余五家均值 |
|------|------|------------------|---------------------|
| GLM-5.3 | 57.8% | EvoX | **+10.7pp** |
| Kimi K3 | 61.3% | EvoX | **+7.9pp** |
| GPT-6 Astra | 78.5% | Codex (80.2%) | +0.5pp |
| Opus 5 | 68.2% | Claude Code (74.8%) | +0.4pp |
| Sonnet 5 | 45.4% | EvoX | −1.3pp |
| DeepSeek V4 Flash | 22.1% | EvoX | −0.6pp |

第一方 harness 在自家模型上领先（Claude Code-Opus、Codex-Astra），EvoX 在 GLM-5.3 与 Kimi K3 这两个「缺第一方 harness 调优」的模型上增益最大——**harness 效应是模型依赖的**。

**按基准分层**：EvoX 对五家均值在全部五个基准上为正：Aider +4.0（64.7% 第一）、GAIA +3.0（86.7% 第一）、SWE-Live +5.4（48.4%，但 Pi/Claude Code 以 49.2% 略高）、Harbor +0.8（Claude Code 31.5% 第一）、TB 2.1 +1.5（Pi 60.7% 第一）——**没有 universally dominant harness**，但 EvoX 跨任务族最均衡。

### 5.3 行为证据：增益从哪来？

执行结果画像显示：EvoX 正常完成率 73.4%，与对手均值 73.3% 几乎持平；但**正常完成内的 verifier 通过率 73.6% vs 对手均值 68.3%**——优势不来自「更常跑完」，而来自「跑完的质量更高」。这与 Outcome Grounding 的设计意图一致。

22 条成功轨迹复盘：15 个「至少四家对手失败、唯 EvoX 成功」的案例中，8 个包含更彻底的执行接地验证——例如用真实 SIGINT 信号复现异步任务取消、用 GDB 定位越界错误后对约 23 万个编码做差分验证修正。

**敏感性分析**：剔除任一模型 EvoX 优势仍为正（稳健），但剔除 GLM-5.3 降 1.5pp、剔除 Kimi K3 降 1.1pp——两家模型贡献了聚合优势的相当部分。同时 Codex 剔除 GPT-6 Astra 后降 1.5pp，印证第一方依赖。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**对比对象**：其余五家 harness 不是稻草人——Pi 极简循环、Claude Code/Codex 厂商深度调优、Hermes 带持久记忆、Prime 带递归子 Agent。它们有效是因为各自在接口设计/上下文工程上确有积累。

**baseline 的根本局限**（机制层面）：这些 harness 的执行控制是**隐式且碎片化**的——校验、重试、终止规则散落在各组件里，没有针对「决策-执行缝隙」的系统性覆盖。具体瓶颈：接口级失败在到达执行层前无人接管；可恢复失败与预算耗尽的区分不明；收尾汇报与执行证据脱钩。

**因果链**（标注证据等级）：

1. 三类失败（失配/中断/虚报）源于决策与执行的缝隙，而非模型语义错误【论文动机，现象层面已支持】；
2. 三机制分别接管缝隙的三个点位：有界归一化消灭接口级失败、引导+熔断平衡恢复与止损、接地约束对齐汇报与证据【论文设计主张】；
3. 正常完成率持平但完成内通过率 +5.3pp → 增益来自「完成质量」而非「完成频率」，指向 Outcome Grounding 与更彻底的验证行为【论文实验已支持】；
4. 增益集中于 GLM-5.3/Kimi K3 → 操作策略在缺乏第一方调优的模型上边际价值最大，因为第一方 harness 已用隐式调优填补了同样的缝隙【论文数据支持前半句；「填补机制相同」是阅读者推测】；
5. 关闭记忆/演化/扩展仍有增益 → 增益来自基线操作控制本身【论文消融已支持】。

### 6.2 相关工作检索与对照

| 研究（可核验链接） | 相似尝试 | 相关结论 | 与本文的差异 | 对根源解释的影响 |
|---|---|---|---|---|
| Harness-Bench（[arXiv:2605.27922](https://arxiv.org/abs/2605.27922)） | 固定外部条件、保留原生行为的受控 harness 横评 | harness 间存在大幅、模型依赖的性能差异；无一家全模型领先；建议按「模型-harness 配置级」报告 | 只测现象，未提出操作策略概念；未做 provider 侧请求审计 | **支持**：模型依赖效应与 EvoX 发现一致，强化「效应真实存在」 |
| The Scaffold Effect（[arXiv:2607.22585](https://arxiv.org/abs/2607.22585)） | 三 harness × 两模型的配对比较 | harness 选择致 token 效率差 40 倍；通过率差 0-8pp 且置信区间多含零；失败模式跨模型复现（harness 级偏差） | 规模较小；聚焦效率而非操作控制机制 | **支持＋限定**：证明 harness 级偏差模型无关地存在，但也提示通过率差距通常不大——EvoX 的 +3.0pp 处于该范围上沿 |
| Same Model, Different Harness（[arXiv:2608.26218](https://arxiv.org/abs/2608.26218)） | 同 harness 两配置（完整历史 vs 压缩旧工具结果）对照 | 上下文管理策略改变任务结果 | 单一机制（上下文管理）研究 | **补充**：证实执行连续性组件（上下文管理）的独立效应 |
| SWE-agent（[arxiv.org/abs/2405.15793](https://arxiv.org/abs/2405.15793)） | ACI——为模型定制接口 | 接口设计显著影响成功率 | 接口层单点；无操作策略全环视角 | **支持**：接口规范化（Action Realization 的前身）的价值早有证据 |
| Harbor（[harborframework.com](http://harborframework.com)） | 统一容器化评测框架 | 统一任务规范+沙箱可支撑大规模横评 | 评测基础设施而非操作策略 | **方法学支持**：Contrast 公平合约在其启发上扩展出三分条件与请求审计 |

在本次检索范围内未发现针对「第二策略」这一对偶概念本身（语义/操作策略分离）的直接先行工作；最接近的是 Harness-Bench 提出的「按配置级报告」主张，但其停留在测量层面，未上升为运行时设计原则。

### 6.3 综合判断与未决问题

**多研究共同支持**：harness 效应真实、显著且模型依赖（Harness-Bench、Scaffold Effect、本文三方一致）；接口规范化与上下文管理有独立价值（SWE-agent、SMDH）。

**仍属推测**：三机制各自贡献的精确分解——论文只做了「全开 vs 全关记忆/演化/扩展」的消融，**没有逐机制拆解**，+3.0pp 中 Action Realization、Execution Continuity、Outcome Grounding 各占多少未知；「第一方 harness 用隐式调优填补同样缝隙」是对 Claude Code/Codex 闭源实现的推测，无法直接核验。

**适用条件与失效风险**：优势已在强模型+第一方 harness 组合（Opus+Claude Code、Astra+Codex）上趋近于零甚至为负（Sonnet 5 上 −1.3pp）——对已被深度调优的模型-配对，通用操作策略可能无增益；+3.0pp 总体差距不大，且在 Scaffold Effect 观察的 0-8pp harness 差异范围内，不能排除部分来自工程细节而非概念框架本身；691 对的公共集排除了大量无效运行，可能引入有利于稳健 harness 的选择偏倚。

## 七、必要知识反推

假设一个零知识背景的人要复现这项工作，他最少需要知道什么？

**领域知识层**：

- LLM API 调用机制（结构化输出、工具调用 schema、推理配置参数）——不理解就无法设计 Model Bridge 的请求审计，也无法识别「畸形调用」长什么样；
- Agent 执行环的完整生命周期——三机制必须精确对位于执行环的三个点位，点位错位（比如把熔断放执行前）就失效；
- 各家 harness 的架构差异（Pi 的极简循环、Hermes 的记忆、Prime 的递归子 Agent）——否则无法设计 adapter 让六家在统一基底上运行。

**方法论知识层**：

- 受控实验设计——locked/shared/native 三分本质上是「控制无关变量、暴露自变量」的实验设计原则在 Agent 评测上的移植；
- 正负对照思想——Oracle/No-op 双向检验 verifier，直接借鉴自实验科学；
- 配对统计与重采样——公共任务-模型集上的 paired comparison 需要统计推断基础；
- harness 效应研究脉络（Harness-Bench 等）——知道前人已经证明现象存在，才能把问题从「有没有效应」推进到「效应从哪来」。

**工程知识层**：

- Rust 运行时开发——内存安全与并发是长期运行时的硬需求；
- 容器化与沙箱编排——Cove 执行基底要为 4752 个组合提供一致环境；
- provider API 差异——六家模型供应商的协议适配。

**知识融合的关键节点**：最有价值的化学反应在于**把实验科学的对照思想移植到 Agent 评测**（Oracle/No-op、provider 侧审计、证据裁决），以及**把组织管理学的权责分离思想移植到 Agent 架构**（语义/操作策略对偶）。单独任何一层知识都不足以产生这两个设计——它们是跨域嫁接的产物。

## 八、论文中可以提取的通用性灵感

**灵感一：给「第二决策者」正名**
核心思想：复杂系统中「决策」与「执行」是两个独立的策略源，显式分离并各自优化，优于混为一谈。
论文证据：harness 被形式化为操作策略 H=(Γ,Δ) 后，三机制的职责边界清晰、可独立评测。
推广场景：机器人 stack 中的规划器/控制器分离、组织流程中的战略/执行分权、数据库的查询优化器/执行引擎分工、DevOps 中策略引擎与执行器（如 OPA）、自动驾驶的决策层与规控层。

**灵感二：有界修正优于无限重写**
核心思想：自动纠错要设保守边界——能归一化就归一化，不能恢复就退回上游，绝不擅自重新解释。
论文证据：Action Realization 的「有界归一化」明确拒绝任意重解释，宁可退回模型修正。
推广场景：数据清洗的可恢复转换、编译器错误恢复（跳过 vs 猜测）、API 网关的请求改写规则、人机交互中的智能默认值设计、法务合同审核中的自动标注 vs 自动改写。

**灵感三：验收要与证据对齐，而非与主张对齐**
核心思想：汇报系统应基于观察到的证据生成结论，而不是复述意图；「说做了」不等于「做了」。
论文证据：Outcome Grounding 使 EvoX 正常完成内通过率 73.6% vs 68.3%，优势恰恰来自完成质量的提升。
推广场景：CI/CD 的部署成功必须以健康检查为准（而非脚本退出码）、科研的可重复性声明、销售漏斗的「成交」以回款为准、审计中的实质测试、Agent 系统的 done-condition 设计。

**灵感四：公平比较要三分条件——锁定的、共享的、原生的**
核心思想：比较异构系统时，把条件分为锁定（硬规则）、共享（组内一致）、原生（保留差异并记录），既能控制无关变量又不抹杀被测对象。
论文证据：Contrast 用此三分让六家 harness 在保留原生提示词与工具接口的前提下可比。
推广场景：云服务性能横评（锁定负载、保留各家调优）、教育测评的标准化考题与自由教学法、车型对比测试的统一路况与各自调校、大模型评测的统一解码配置与各自系统提示词。

**灵感五：把失败归因做成证据裁决**
核心思想：评估体系必须区分「被试失败」与「基础设施失败」，否则测量噪声会系统性污染结论。
论文证据：Contrast 的 Adjudicate 机制把基础设施故障从 Agent 失败中剥离，隔离而非武断计分的记录保留审计线索。
推广场景：A/B 测试中的样本污染剔除、临床试验中的盲态数据审核、在线服务的错误预算归因、体育比赛的 VAR 复核流程。

## 附录：速查卡

- **一句话总结**：EvoX = 把 harness 从「隐式工程制品」升格为「显式操作策略」，用三机制接管决策-执行缝隙，在保留各家原生打法的公平赛场上拿下六家 harness 最高成功率。
- **数字锚点**：691 公共任务-模型对 / 整体 56.2%（+3.0pp）/ GLM-5.3 +10.7pp、Kimi K3 +7.9pp / 完成内通过率 73.6% vs 68.3%。
- **三机制口诀**：出海关（Action Realization 有界安检）→ 陪跑教练带熔断（Execution Continuity）→ 验收审计员（Outcome Grounding）。
- **值得追踪的后续**：逐机制消融分解、GEP 经验演化开启后的增益叠加、Contrast 框架的开源复用。
