## 一、论文背景

### 1.1 根信任（RoT）：整个系统安全的"地基"

想象一栋大楼的地基——楼上所有楼层的安全性都建立在它之上。**根信任（Root of Trust, RoT）**就是计算机系统的地基：它是一颗独立芯片或 SoC 内的一个硬件块，负责两件最基础的事：

- **安全启动（Secure Boot）**：不可变的 ROM 代码用固化在 ROM/熔丝/OTP 里的公钥，逐级验证下一级固件的签名，确保设备只运行合法软件；
- **远程证明（Attestation）**：RoT 用 DICE 体系派生的设备密钥（UDS→CDI）对固件度量值签名，让远程验证者确认设备未被篡改。

开源 RoT 已经跑在生产设备里：**Caliptra** 是 CHIPS Alliance 开发的数据中心 SoC 根信任块（用于 CPU/GPU/DPU/TPU），**OpenTitan** 是 lowRISC 维护的开源硅根信任（已量产用于 Google Chromebook），**OpenPRoT** 是平台级 RoT 固件栈。它们分别用 Rust/C 写固件、用 SystemVerilog 写 RTL 硬件。

关键在于：RoT 里的 bug 后果极端——攻击者可以绕过安全启动、提取密钥、伪造证明；而且**boot ROM 和 RTL 的缺陷在流片后无法修补**（任天堂 Switch 的漏洞就是 deployed silicon 永久沦陷的例子）。所以 RoT bug 必须在发布前找到。

### 1.2 LLM agent 找漏洞：已有能力与两个失效点

LLM agent（如 Big Sleep、DARPA AIxCC 的参赛系统、OpenAnt、Co-RedTeam）已经能在通用软件里找到真实漏洞。但论文指出这套范式在 RoT 上撞到两个硬约束：

**失效点一：漏洞判定依赖项目专属上下文，通用漏洞模式编码不了。**
看一个真实例子（CVE-2026-7328）：Caliptra runtime 固件接受某些 mailbox 命令时，既不检查调用者特权级、也不检查其提供的总线地址，导致未特权调用者可以发起 DoS 或任意 DMA。这个 bug **没有内存损坏、不会崩溃**——它违反的是 Caliptra 自己定义的信任边界（『哪些调用者可以发哪些命令』）。论文研究的 34 个已知 bug 里，15 个属于缺失授权/认证不当/签名验证不当/TOCTOU 这类 CWE，全都是"逻辑违规"而非"内存出错"。

更麻烦的是反方向：RoT 代码里**故意的冗余长得像 bug**。OpenTitan 第一个可变启动阶段会在匹配后立即重新检查值、把布尔编码成 0x739/0x1d4 而不是 1/0——这些"冗余"是防故障注入（glitch 攻击翻转单个分支/比特）的故意对策。不知道项目设计意图的 agent 会犯两种错：把故意对策标记为冗余代码（假阳性），或漏掉威胁模型要求但缺失的对策（假阴性）。

**失效点二：没有 RoT 硬件，输入只能靠项目自己的测试基建驱动。**
AIxCC 系统靠崩溃和 sanitizer 报告确认 bug；OpenAnt/Co-RedTeam 在自己的容器里跑 PoC。但 RoT 的对手输入是 mailbox 命令、固件镜像、MCTP/PLDM 消息——通用 HTTP/命令行/文件 harness 根本喂不进去。PoC 必须驱动 Caliptra 的硬件模型、OpenTitan 的 Bazel 测试或 Verilator RTL testbench；而且逻辑缺陷不一定崩溃，PoC 必须**检查安全性质**而非等待 crash。维护者本来就要花大量精力分诊未验证报告（论文引用了关于 AI 报告淹没维护者的研究），所以有用的 PoC 必须能在项目自己的 harness 里作为测试被维护者复跑。

这就是本文的出发点：**把漏洞发现、评审、复现的每个阶段都"接地"（ground）到 RoT 项目自己的工件上。**

## 二、论文定位和关联工作

### 2.1 谱系一：LLM agent 漏洞发现（通用软件）

| 工作 | 核心思想 | 与 MJOLNIR 的关键区别 |
|------|---------|---------------------|
| Big Sleep（Google Project Zero, 2024） | LLM 辅助变体分析，找到 SQLite 真实栈下溢 | 单点发现，无管线化验证 |
| DARPA AIxCC 系统 | 网络推理系统发现漏洞+漏洞证明+补丁 | 靠崩溃/sanitizer 确认，RoT 逻辑漏洞不崩溃 |
| IRIS / LLMSAN / Vulnhuntr / Chai | LLM+程序分析（污标注、数据流验证、调用链追踪、密码误用差分测试）降假阳性 | 静态/半动态，无项目原生执行环境 |
| **OpenAnt**（arXiv 2606.19149） | 代码分解为外部入口可达单元（攻击面降 97%）+ 对抗式验证 + 自建 Docker 容器内动态验证 | **MJOLNIR 直接继承其管线形态**；但 OpenAnt 只覆盖 HTTP/WebSocket/命令行/文件输入可达代码，RoT 目标一个都不暴露这些入口 |
| **Co-RedTeam**（ICML 2026, arXiv 2602.02164） | 发现+利用两阶段编排、执行接地迭代推理、跨任务长期记忆；消融证明执行反馈关键 | 只在基准上评估；MJOLNIR 把执行接地到项目自身工具链而非自建环境 |

论文明确说：管线形状承自 OpenAnt/Co-RedTeam，**不主张管线本身是贡献**；新意在于每一阶段使用的证据——项目威胁模型与原生测试基建。

### 2.2 谱系二：固件与硬件安全中的 LLM

- **IoT 固件**：FirmAgent（fuzzing 找污点源+LLM 分析路径）、LIVA（多 agent 二进制污点分析）、FirmHive（运行时 agent 树）——都分析 IoT 固件二进制的输入处理 bug；MJOLNIR 分析 RoT 固件**源码**，bug 依赖启动阶段状态与信任边界。
- **RTL/SoC**：MARVEL（多 agent 找 Hack@DATE 竞赛 SoC 的 RTL 漏洞）、BugWhisperer（微调 LLM 检测 SoC 漏洞）、SV-LLM（从威胁建模到仿真验证的 SoC 安全验证）、BugGen（合成 RTL bug）、HWE-Bench（用项目自身仿真流验证修复）、RTL fuzzer（差分测试/黄金参考模型/形式辅助）。这些都在注入 bug 的基准或单点上工作；MJOLNIR 面对生产 RoT 项目的真实未知漏洞。
- **PoC 生成与基准**：PAGENT（静态分析+动态反馈引导 PoC agent）、PoC-Gym（发现 PoC 到达漏洞点才算成功，仅凭成功标记不可靠）、CyberGym/SEC-bench（最佳 agent 在已知漏洞复现任务上成功率仅约 20%）——这些从已知漏洞出发；MJOLNIR 要先发现 bug。

### 2.3 定位总结

| 维度 | 之前的路线 | 本论文的突破 |
|------|-----------|-------------|
| 判定依据 | 通用漏洞模式（CWE/内存安全/崩溃） | 项目威胁模型+设计约定（哪些冗余是故意的、哪些检查必须存在） |
| PoC 执行环境 | agent 自建容器/sanitizer | 项目自身 harness（Cargo/Bazel/Verilator，Nix 开发壳），PoC 是 test-only 的 |
| 目标 | 通用开源软件、IoT 固件、注入 bug 的基准 | 生产开源 RoT（Caliptra/OpenTitan/OpenPRoT）固件+RTL 真实未知漏洞 |
| 证据标准 | PoC 跑通即可 | 必须经**未修改生产代码**触发+diff 检查+终审拒绝 mock/空洞断言 |

论文自称（经本次检索核对属实）：**首个把漏洞发现与评审接地到项目专属 RoT 安全需求、并通过原生固件/RTL 测试基建复现漏洞的 agentic 系统**，且有 64 个真实确认漏洞与生产 CI 部署背书。

## 三、问题定义

### 3.1 从具体场景到抽象问题

**具体问题**：让 LLM agent 在 RoT 固件与 RTL 中发现并复现安全相关漏洞。

**核心洞察**：这个问题的本质不是"找一个漏洞模式匹配器"，而是**证据与裁决标准的迁移**——通用漏洞发现的裁决标准（崩溃、sanitizer、通用 CWE）在 RoT 域全部失效，必须换成项目自己的裁决标准（信任边界+威胁模型要求的对策）。同理，复现的证据标准（自建环境跑通）也要换成项目自己的证据标准（原生 harness 里作为测试跑通且不改生产代码）。

**类比**：这就像把一个只懂"体检指标异常即病"的实习医生，换成一个掌握病人专属病史的专科医生——同一段代码，在 Caliptra 是漏洞，在另一个项目可能是文档写明的正常行为；反过来，缺少一个"看起来多余"的对策在 RoT 里就是漏洞。

### 3.2 形式化定义

论文给出的问题设定（§2.3 威胁模型）：

- **给定**：
  - 项目源码（固件/RTL）、项目自己的威胁模型（资产：安全启动与防回滚完整性、设备密钥保密性、跨信任边界的特权分离、跨复位的服务可用性）；
  - 对手模型：控制 RoT 外部接口的一切输入（mailbox 命令、固件镜像、熔丝值、MCTP/PLDM/SPDM 消息、boot-services 请求），**但不能修改 RoT 代码**；物理攻击（故障注入/侧信道）在项目威胁模型范围内，MJOLNIR 不实际实施但报告缺失对策；
  - 项目自身的测试基建（硬件模型、mocks、testbench、构建工具链）。
- **求**：发现并复现**安全相关 bug**——定义为"对手可控输入违反项目某安全目标"或"遗漏威胁模型要求的对策"（含 defense-in-depth 类：对策保护了部分路径但没保护全部路径）。
- **约束**：PoC 只有在"通过对手可控输入、经未修改生产代码触发所报缺陷"时才算有效证据；agent 无 web 访问；PoC 只在开发机上跑。

### 3.3 这个抽象的精妙之处

- **"安全相关"是项目相关量而非绝对量**：这直接解释了为什么通用方案在此必然产生系统性假阳/假阴——它们优化的是数据集上的平均判别力，而这里需要的是逐项目判别力。
- **"对手不改代码"与"PoC 不改生产代码"对齐**：把威胁模型的假设翻译成了对 PoC 证据的形式约束——一个 mock 掉目标逻辑的 PoC 证明的是 stub 的行为，不是项目的缺陷。这是本文最干净的一个形式化对应。

## 四、问题解法

MJOLNIR 基于 Google ADK 构建，共 **6 个 agent + 12 个工具**（2,837 行 Python 编排 + 1,705 行 agent + 1,699 行工具 + 245 行提示词 + 697 行 Nix），模型无关（Gemini/Claude/OpenAI/Ollama 本地模型），同一次运行内所有 agent 用同一模型。整体是一条**多级漏斗**：发现 → 去重 → 初审 → PoC → 终审。

### 4.1 Project Expert：把项目语境变成可注入的知识

类比：审计组进场前先读的"项目尽调报告"。

- 扫描前用只读代码搜索工具巡视项目（目录布局、README、架构文档、构建文件），写出摘要：执行阶段、**信任边界与安全不变量**、寄存器映射与 MMIO 约定、构建/测试目标，以及**可能被误认为 bug 的故意设计模式**（如 OpenTitan 的 hardened check）。摘要按 commit+威胁模型缓存。
- 每个 agent 还收到一份 **≤90 行的 per-project 威胁模型**（Markdown，实际 59-84 行）：信任边界、资产、关键威胁类别。
- 其他 agent 通过工具**随时提问**：每次提问启动一个新实例，以威胁模型+摘要+历史问答为种子；重复问题直接从历史回答。这保证 Project Expert 上下文有界，即使被大量并行提问。

### 4.2 Source File Auditor：按文件并行发现

类比：专科医生逐份病历检查，但随时可以调阅全院档案。

- 每个在范围内的文件一个 Auditor 实例并行跑，拿到文件全文；不预计算跨文件上下文，而是用代码搜索工具（Universal Ctags 查符号定义、ast-grep 在 Tree-sitter 语法树上做结构化模式匹配、ripgrep 搜内容）按需检索调用者/被调用者/类型定义，并向 Project Expert 提问项目约定。
- 指令编码 **RoT 专属审计指南**：整数运算、外设与主机命令的不可信输入、并发、密码代码的时序/功耗侧信道、密钥零化、必须抗故障注入的安全决策。语言专属指南按文件类型选择：C/Rust 覆盖内存安全/unsafe/错误处理/panic；SystemVerilog 覆盖位宽与符号危害、寄存器锁绕过（REGWEN）、时钟与复位域交叉、状态机完整性。
- **假阳性约束**显式写入指令：目标是无推测无 D-cache 的顺序核、崩溃有看门狗复位——因此只有导致持久控制流劫持或腐蚀跨复位状态的崩溃才报告；内部 helper 缺检查只有不可信输入可达才报告。
- 扫 PR 时只审计改动文件并附 diff，指示不报告未触碰函数里的既有 bug。

另有一个 **Report Ingestor** agent 支持第二输入模式（Re-Analysis）：读外部漏洞报告（Markdown/表格/日志），以 Auditor 相同的 schema 进入同一条下游管线——外部报告同样要过怀疑式评审与 PoC 关卡。

### 4.3 Deduplicator 与 Adversarial Reviewer：两级怀疑式过滤

**Deduplicator**（类比：把"同一个根因的多个症状"合并成一份病历）：把同一根失败机制（如一个未加固 helper 的多个调用点）折叠为一个规范 finding；跨运行时与历史 open finding 匹配，重复扫描不重复报告。放在评审前，让重复项不浪费评审与 PoC 的钱和 token。

**Adversarial Reviewer**（类比：会诊里专门唱反调的医生），评审两轮：

- **初审**：只看 finding 与源码+威胁模型。指令使其默认怀疑——不能因上下文缺失就评"可利用"，任何未定位到的定义必须假设其实现安全；要评 exploitable 或高/严重级，必须从真实源码构造逐步论证。它还重校准严重度/CVSS/CWE（MJOLNIR 对照 MITRE 目录校验 CWE、从向量重算 CVSS，不信任模型自报分数）。
- **终审**：额外看 PoC 的 diff、harness 输出，拒绝：mock 掉被测目标的 PoC、空洞断言（无论缺陷在不在都能过的断言）、直接调用内部 helper 而公共入口已消毒输入的 PoC、只依赖 debug 构建行为（如算术溢出 trap）的 finding。

每个 finding 是一条记录（文件/位置/严重度/CWE/CVSS 向量/判决/状态/PoC），每阶段合并输出并追加历史快照，每个判决可追溯到做出它的阶段。

### 4.4 PoC Exploit Generator：在项目自己的工具链里复现

类比：不自己搭实验台，直接用项目实验室的现成设备做验证。

- 在项目的 **scratch Git worktree** 里工作，PoC 写成项目自己测试基建里的测试：Caliptra 固件用 Cargo（含硬件模型上的全固件 mailbox 测试）、OpenTitan ROM_EXT 与 OpenPRoT 用 Bazel、RTL 写独立 C++/SystemVerilog testbench 用 Verilator 编译运行。指示其优先复用项目现成的集成模型、测试 helper 与 mock。
- 构建与测试命令通过**单一 harness 命令**在项目自己的 **Nix 开发壳**里执行——所以接入新项目=添加新开发壳，不是新工具（这是可移植性目标 D3 的实现）。命令先校验：拒绝引用 worktree/工作区/项目检出/Nix store//dev 之外的路径，拒绝以 find/grep/cat 等文件探索程序开头的命令，净化环境变量，900 秒超时。
- **diff 检查门**（只能降级 agent 的自报、不能升级）：PoC 未验证，除非 diff 非空、至少跑过一条 harness 命令、且 diff 只改测试代码（路径含 test/mock/fuzz/harness 等测试 token 或构建文件；项目可自加 token，OpenTitan 加了 dv/tb；Rust 单元测试在源文件内，规则放宽为"不删行且含 #[cfg(test)] 内联测试标记"）。门不检查测试退出码（测试可能以触发 bug 或断言良性两种方式通过），是否真的演示了缺陷交给终审。
- **失败不等于证伪**：PoC 失败本身不关闭 finding——如果 harness 无法驱动该缺陷（依赖硬件寄存器或物理故障注入），标记为 harness limitation，finding 保持 open-unverified；只有 PoC 尝试揭示存在阻止利用的 guard 才关闭。
- 每个 PoC 存档：diff、每条 harness 命令及输出的日志、以及一个可脱离 MJOLNIR 复跑的独立脚本——维护者可以直接检验。

### 4.5 全景：漏斗与部署

| 阶段 | Agent | 输入 | 输出 | 关键接地点 |
|------|-------|------|------|-----------|
| 预调研 | Project Expert | 项目源码+文档 | 架构/信任边界/对策摘要（缓存） | 项目工件本身 |
| 发现 | Source File Auditor（每文件并行） | 文件全文+威胁模型+摘要 | 候选 finding | 语言专属指南+可提问 |
| 去重 | Deduplicator | 候选 findings | 按根因合并 | 跨运行历史 |
| 初审 | Adversarial Reviewer | finding+源码+威胁模型 | 保留/关闭+重校准 | 逐源码论证 |
| 复现 | PoC Exploit Generator | 幸存 finding | test-only PoC+运行日志 | 项目原生 harness |
| 终审 | Adversarial Reviewer | PoC+diff+输出 | verified/unverified/关闭 | 拒绝 mock/空洞断言 |

**部署形态**：项目从自己的 CI 触发（PR/定时/手动），PR 模式只扫改动文件、findings 直接作为 review 评论发到 PR 上；运行结果同步云存储，Deduplicator 读历史 open findings 防重复报告；静态 web 仪表盘展示每个 finding 的判决、CVSS、历史与复现脚本。**接入一个项目只需 4 个配置文件**（Nix 项目定义、带项目工具链的开发壳、威胁模型、scan job），无需改 MJOLNIR——Caliptra 的项目定义 12 行 Nix，三仓库共享一个 28 行开发壳；最大的 OpenTitan 也只有 55 行定义+177 行壳+7 个共 29 行的 scan job。

## 五、评估指标与实验证据

### 5.1 指标体系与实验设计

**主指标：precision**（TP/(TP+FP)）——因为未知 bug 无 ground truth，recall 只在已知 bug 集上测。评估组合了三个互补证据源：

1. **盲标 precision**（RQ1）：Caliptra 维护者（3 人、2 个组织）对 Caliptra runtime 固件上的 open findings 盲标（对配置/阶段/模型盲）；
2. **已知 bug 召回**（RQ4）：34 个全部在模型训练截止（2026 年 3 月）**之后**才修复的已知安全 bug——规避训练数据污染；
3. **维护者确认数**（RQ5）：此前未知且被维护者确认的安全 bug 总数。

**辅助/消融指标**：漏斗各阶段关闭数（RQ2）、跨重复与跨模型稳定性（RQ3）、每 run 成本。

**基线**：4 个单 agent 配置（per-file/whole-dir × 有无威胁模型，同模型、无管线无 RoT 指南）——与 MJOLNIR 共享模型，因此差异只反映提示词与管线。**消融**：去威胁模型、去 Project Expert。

**目标规模**：6 个评估目标共 344 文件/72.2k 行（Rust/C/SystemVerilog），覆盖 Caliptra（runtime 固件、MCU ROM+协议、DPE）、OpenTitan（ROM_EXT 固件、Earl Grey RTL 顶层）、OpenPRoT（平台服务）；已知 bug 研究扫 Caliptra 核心固件 fw-2.1.0（201 文件/37k 行，含 ROM/FMC/runtime/共享驱动）。**隔离**：固定 commit、无 git 历史的新工作区、试验间互不可见、无 web 工具。模型：Gemini 3.8 Flash / Gemini 4 Argon（2026-03 截止）、Claude Sonnet 5.5（2026-06 截止）。

### 5.2 RQ1：Caliptra runtime 固件上的 precision

| 配置（3 runs） | Open/run | TP | FP | Precision | PoC/run | 成本/run |
|---|---|---|---|---|---|---|
| **MJOLNIR（Flash）** | 8 (±1.7) | 24 | 0 | **100%** | 7 (±2) | $180.03 |
| MJOLNIR w/o 威胁模型 | 7 (±3) | 16 | 5 | 76.2% | 7 (±3) | $162.02 |
| MJOLNIR w/o Project Expert | 8.3 (±1.5) | 20 | 5 | 80% | 6.7 (±1.1) | $214.57 |

| 单 agent Whole-Dir w/o TM | 5 (±1.7) | 10 | 5 | 66.7% | – | $3.79 |
| **MJOLNIR（Argon）**（采样†） | 22.7 (±4.9) | 10 | 2 | 83.3% | 15 (±1.7) | $31.16 |

### 5.3 RQ2/RQ3：漏斗与稳定性

- **初审是唯一大量关闭 findings 的阶段**：关闭进入量的 71.4%（Flash）/46.9%（Argon）/97%（Sonnet）。去重关闭很少（每 run 从空历史开始）；PoC 与终审主要附着证据而非过滤。未获 verified PoC 的 open findings 大多是 Argon 的 harness limitation（7.7 个未验证中 6.7 个）。
- **单 run 只覆盖部分**：Flash 5 次重复共 25 个位置匹配 issue，16 个只出现 1 次（平均 67% 的 issue 会重现于另一 run）；三模型合计 44 个 issue 中 36 个只被一个模型报告。**重复扫描/多模型扫描能显著增收**——这也解释了为什么生产部署用 CI 常驻扫描。

### 5.4 RQ4：34 个已知 bug 的召回

| 层级 | bug 数 | Flash: MJOLNIR vs 基线 | Argon: MJOLNIR vs 基线 |
|------|-------|----------------------|----------------------|
| A：已发布 CVE | 5 | 4 vs 3 | 5 vs 4 |
| B：维护者修复（无 CVE） | 22 | 6 vs 4 | 12 vs 8 |
| C：加固类（零化/证明/侧信道） | 7 | 0 vs 0 | 0 vs 0 |
| **合计** | **34** | **10 vs 7（29.4% vs 20.6%）** | **17 vs 12（50% vs 35.3%）** |

分层揭示的信息：Argon 的评审保留了全部发现的 A/B 层 bug、只关掉 2 个 C 层栈零化项（单地址空间 M-mode 固件无独立栈读取原语）；**Flash 的评审却错关了已发现的 18 个已知 bug 中的 8 个**（初审 7+终审 1，含 CVE-2026-11835）——precision 的代价是 recall。两模型共同漏掉的 10 个 B 层 bug 多为外部规范检查或跨复位硬件不变量（FIPS 140-3 XTS 密钥半不等性、ML-DSA-87 填充、Key Vault 跨复位写锁）。附注：CVE-2026-7328 由早期 MJOLNIR 原型发现，本文管线未用其任何信息。训练污染控制：34 个修复均在 2026 年 4 月后合并、5 个 CVE 在 6-8 月披露，均晚于 Gemini 双模型 3 月截止；且对比在同模型基线上进行，残余暴露被同持。

| Caliptra DPE | 0 | 0 | – | – | $39.36 |

OpenTitan+OpenPRoT 全部 **15 个 PoC 验证 finding 均为 TP**；唯一 FP 来自无 PoC 的 open finding。MCU 固件上尝试 PoC 还揭出一个静态评审漏看的 guard，使终审关掉 1 个假警报——PoC 阶段反向修正静态分析。**合计 64 个维护者确认的此前未知安全漏洞**（runtime 固件三模型 37 + 其余五目标 27）。RTL 结果证明同一套 agent/工具/管线不改代码即从 Rust/C 固件迁移到 SystemVerilog。

### 5.6 成本结构（附录 B）

- 每 run $7.62（Sonnet）—$180.03（Flash）；基线 $3.50-4.60（但无评审无 PoC）。
- **每 token 牌价是 run 成本的糟糕预测器**：Argon 牌价高于 Flash（$2.00 vs $0.75/M 未缓存输入），但 Flash 调用更多 LLM（6,424 vs 1,656 次）与工具（5,814 次调用）、读 5.4 倍输入 token、缓存命中率更低（36.6% vs 84.9%），反而更贵。Sonnet 工具调用最少（293 次），5.9 分钟跑完，最便宜。
- **去 Project Expert 反而更贵**（$180→$214.57）：Auditor/Reviewer 各自重复探索仓库、缓存复用崩塌（缓存命中 36.6%→10.7%）——项目知识注入是省钱的，不是花钱的。
- 发现阶段占成本大头（Flash 的 68.3%）。安全拒绝极罕见：34 runs 共 11 次（集中在全管线运行的 PoC/评审 agent 与去 Project Expert 消融的 Auditor）。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**对比对象**：4 个单 agent 基线。它们曾经有效的原因：单 agent+通用审计提示在通用软件上足以发现模式化漏洞（内存安全、注入），因为那类漏洞的判定标准是普适的。

**baseline 的根本局限**（不是"它没做 X"，而是结构性障碍）：通用审计提示优化的是**无项目上下文时的平均判别力**。而 RoT 的"安全相关"是逐项目定义的——同一模式在不同项目里真伪相反。缺少项目语境的 agent 无法区分"故意的冗余对策"与"遗漏的对策"，于是 per-file 模式向多报侧失效（1/4 FP：看不到调用者处的检查）、whole-dir 模式向少报侧失效（上下文过载后只报最有把握的，4.7/run）。**这不是提示词能修的——缺的是信息，不是推理。**

**因果链**（每步标注证据等级）：

1. RoT 漏洞判定取决于项目特定信任边界与对策 →【论文实验已支持：34 个已知 bug 中 15 个属授权/认证/签名验证/TOCTOU 类；CVE-2026-7328 无内存损坏、纯信任边界违规】
2. Project Expert 综述 + ≤90 行威胁模型注入，使审计与评审具备"哪些冗余是故意的、哪些检查必须存在"的判别依据 → precision 66.7-78.6% 升至 100% →【论文实验已支持：主表对比 + 双消融（去 TM 100%→76.2%、去 PE →80%）】
3. 消融中回潮的 FP **正是**评审 agent 有项目上下文时会拒绝的信任边界类问题（如把文档化的信任边界约定报成认证绕过）→【论文实验已支持：§5.2.1 明确陈述】机制上闭环：去掉的组件恰好是提供该判别依据的唯一来源，回潮的 FP 类型与组件功能一一对应。
4. PoC 限定项目自身 harness、只改测试文件、必须经未修改生产代码触发 → 证据可被维护者原样复跑 → 确认率极高 →【论文实验已支持：15/15 PoC 验证 finding 全 TP；MCU 上 PoC 还揭出静态评审漏看的 guard（PoC 阶段具有独立的纠错价值）】
5. 评审是双刃剑：precision 以 recall 为代价 →【论文实验已支持：Flash 初审+终审错关 8/18 个已发现已知 bug】这是机制的内生权衡，不是实现瑕疵——怀疑式过滤对边界 case 必然有误杀率。
6. 单 run 覆盖不完整是模型随机性的函数 →【论文实验已支持：16/25 issue 仅出现一次】所以生产部署形态是 CI 常驻+跨 run 去重，而非一次性审计。

**反事实推理**：若去掉威胁模型（保持管线其余不变），precision 退化到 76.2%——与最佳基线几乎重合。这说明 MJOLNIR 的优势**不是多 agent 编排本身**带来的，而是项目知识注入带来的；管线只是让这些知识在每个决策点（审计/评审/PoC）都能被使用。去 Project Expert 的退化（80%）更温和但成本上升 19%，因为 agent 用重复探索部分替代了缺失的综述（且替代不完全）。

### 6.3 综合判断与未决问题

- **多研究共同支持的机制**：①威胁建模/项目意图先于检测（MJOLNIR 消融 + GitHub Security Lab 实践 + Co-RedTeam 领域知识注入）；②执行接地优于纯静态判断（MJOLNIR PoC 纠错 + Co-RedTeam 消融）。
- **仍属合理推断的机制**：①"项目**原生** harness（相对自建沙箱）是高确认率主因"——OpenAnt/Co-RedTeam 在自建环境也降了 FP，本文没有原生 vs 自建的受控对比，此归因部分依赖 PoC-Gym/CyberGym 的间接证据；②≤90 行的人工威胁模型优于 LLM 现场推导的威胁模型——论文未做此对比，GitHub Security Lab 用的是现场推导且也有效。
- **优势成立条件**：项目有清晰的书面威胁模型与可运行的测试基建（三个开源 RoT 恰好都有）；维护者愿意盲标与分诊。**可能失效条件**：闭源/文档贫乏项目（威胁模型需人工撰写）；物理故障注入类缺陷永远拿不到 verified PoC（harness 天花板）；跨文件 bug（每文件一个 Auditor 的结构性弱点）；Flash 这类评审过严的模型上 recall 损失显著。

## 七、必要知识反推

假设找一个没有任何知识的人重做这项工作，最少必须知道什么？

### 7.1 领域知识层

- **RoT 体系结构**：安全启动/度量启动/DICE 派生链（UDS→CDI→证明）、三阶段启动（ROM→FMC→Runtime）、mailbox 命令模型、MCU/MCTP/PLDM/SPDM 协议栈——不知道这些就写不出威胁模型，也看不懂 CVE-2026-7328 为什么是漏洞。
- **故障注入与对策**：glitch 攻击原理、hardened comparison、常量时间编码、密钥零化——否则无法理解"故意的冗余"这一 FP/FN 的双向陷阱（这是论文最核心的领域洞察）。
- **三个项目的具体工程**：Caliptra 的 Rust/Cargo 生态、OpenTitan 的 Bazel/OTP/ROM_EXT 流程与 SystemVerilog RTL、OpenPRoT 的 Pigweed 微内核——PoC 生成器必须能在这些真实工具链里写测试。
- **CWE/CVSS 体系**：finding 记录的规范化语言，且需要知道模型自报分数不可信（要对照 MITRE 目录重算）。

### 7.2 方法论知识层

- **LLM agent 工程全景**：ADK 类编排框架、ReAct 式工具循环、结构化输出 schema、提示缓存、检查点容错——2,837 行编排代码的每一项设计（并行批处理、错峰启动、指数退避）都依赖这些经验。
- **既有 agentic 安全系统**：OpenAnt 的分解/对抗验证/动态验证三段式、Co-RedTeam 的执行接地与长期记忆——MJOLNIR 的管线形态直接站在它们肩上。
- **安全评审的认识论**：怀疑式评审的构造（"未定位的定义假设安全"是贝叶斯先验的工程化）、"失败 PoC≠证伪 finding"的证据不对称性。
- **评估方法学**：盲标、Krippendorff α、裁决流程、训练截止后的已知 bug 集设计（防污染）、同模型基线控制变量——论文评估之所以可信靠这些。

### 7.3 工程知识层

- **Nix 可复现环境**：把项目工具链打包进开发壳，使 PoC 构建跨主机可复现，也是"接入=加开发壳"的可移植性来源。
- **代码搜索工具链**：Universal Ctags/ast-grep(Tree-sitter)/ripgrep 的能力边界与组合方式（跨文件一步一链地追定义）。
- **Verilator/Cargo/Bazel 的测试机制**：RTL testbench 怎么写、内联 Rust 单元测试的 diff 规则为什么要特判。
- **CI 集成与负责任披露**：PR 评论式报告、云存储+仪表盘、披露窗口期内隐去漏洞细节。

### 7.4 知识融合的关键节点

1. **"威胁模型是对手的约束，也必须是分析器的约束"**：把威胁模型从安全文档变成每个 agent 的提示词注入 + PoC 的证据标准（不改生产代码）——领域知识（对手不改代码）与 agent 工程（提示注入）在同一处融合，这是全文最关键的化学反应。
2. **"故意对策=系统性 FP 源"的识别**：需要同时懂故障注入对策（领域）和 LLM 的模式匹配失败模式（方法论）才能预先想到，并由此设计 Project Expert 摘要里"列出可能被误认为 bug 的设计模式"这一具体条目。
3. **"维护者是最终评审者"**：把 PoC 写成项目测试+独立复跑脚本，是安全研究规范（负责任披露）与 DevOps 工程（CI/PR 流程）的融合——这也是 64 个确认与 800+ PR 部署得以发生的组织性前提。

## 八、论文中可以提取的通用性灵感

### 灵感一：领域判定标准注入优于通用能力堆叠

**核心思想**：当"什么算对/错"是项目专属的时候，把判定标准做成紧凑工件（≤90 行）注入每个决策点，比换更强的模型更有效。
**论文证据**：同模型下 precision 66.7-78.6%→100%；去掉威胁模型退化到 76.2%（与基线重合）；GitHub Security Lab 在 Web 域独立复现同结论。
**推广场景**：①代码评审 agent 注入团队编码规范与"故意的设计决定"清单；②医疗/法律文档审核 agent 注入机构合规边界；③数据分析 agent 注入企业的指标口径定义；④测试生成 agent 注入项目的 invariant 文档。

### 灵感二：把"预调研"做成可查询的有界缓存服务

**核心思想**：与其让每个 worker 自行探索全局上下文（重复劳动+缓存崩塌+成本上升），不如预先由一个专家 agent 生成综述并对外提供问答服务。
**论文证据**：去 Project Expert 后 precision 降至 80% 且成本反升 19%（$180→$214.57，缓存命中 36.6%→10.7%）。
**推广场景**：①多 agent 并行处理长文档时设"文档专家"中继；②微服务代码迁移项目中的架构 FAQ 服务；③大规模数据清洗中的 schema 词典服务；④任何"并行 worker+共享全局知识"的编排。

### 灵感三：证据必须在被审对象自己的环境里产生

**核心思想**：自建验证环境证明的是验证环境，不是被审对象；把验证接到对象的原生工具链，证据才对真正负责的人（维护者）可复用。
**论文证据**：15/15 PoC 验证 finding 全为 TP；PoC 复用项目 mock/硬件模型/Verilator testbench；附带独立复跑脚本。
**推广场景**：①合规审计直接在被审计系统的监控栈里跑；②第三方 SDK 质量验证用其官方测试框架；④学术复现要求用作者原始环境（容器化）而非重写；⑤ SRE 混沌工程在生产拓扑副本上演练。

### 灵感四：自动门槛只降级不升级 + 怀疑式终审的组合防作弊

**核心思想**：对 agent 自报结果的自动检查（diff 门）应设计成"只能把声称降级为未验证"，把需要判断力的最终裁决留给有完整上下文的怀疑式评审；二者职责分离。
**论文证据**：diff 门不检查退出码（测试通过≠演示了缺陷），终审专门拒 mock 目标/空洞断言/直调内部 helper；MCU 上 PoC 揭出 guard 反向关闭 1 个假警报。
**推广场景**：①AI 生成代码的 CI 门禁（编译过≠正确）+人工评审；②agent 产出的研究报告附可点验证链接（点击门）+编辑核查；③自动化科学实验的"仪器原始数据"与"结论解释"分层验证。

### 灵感五：失败不证伪——证据不对称性的显式建模

**核心思想**：复现失败有两种不可区分的原因（缺陷不存在 vs 环境 drove 不出），系统应把失败保持为"未验证"而非"否定"，只有失败揭示反证（guard）才关闭。
**论文证据**："A failed PoC does not itself refute a finding"；harness limitation 保持 open-unverified；同一原则用于外部报告的 Re-Analysis。
**推广场景**：①fuzzing/测试中"未复现≠误报"的 bug 分类学；②告警分诊中"证据不足"与"确认良性"分离（威胁检测实践已有同构呼声）；③科学实验阴性结果与推翻性证据的区分。

### 灵感六：随机性之下，部署形态决定有效覆盖

**核心思想**：当单次运行输出不稳定（16/25 issue 仅出现一次）时，把系统做成常驻 CI+跨运行去重，比追求单次完美更划算。
**论文证据**：五次重复的稳定性研究；跨运行 Deduplicator 读云存储历史防重复报告；4 个月 800+ PR 部署。
**推广场景**：①不稳定的生成式系统一律考虑"多采样+合并去重"而非单次调优；②安全扫描/依赖审计的常驻化；③多模型并扫取并集（论文显示 36/44 issue 仅单模型报告）。

## 附录：数字速查

- 管线：6 agent / 12 工具 / ~7,200 行代码（含 Nix）；威胁模型 59-84 行；接入 4 个配置文件。
- Precision：Flash 24/24=100%，Argon 10/12=83.3%（采样），Sonnet 3/3=100%；基线 66.7-78.6%。
- 召回（34 已知 bug）：Flash 10（29.4%）vs 基线 7（20.6%）；Argon 17（50%）vs 基线 12（35.3%）。
- 确认新漏洞：64（37 runtime 固件三模型 + 27 其余五目标单扫）。
- 成本：$7.62-180.03/run（同模型基线 $3.50-4.60 但无评审/PoC）；发现阶段占 Flash 成本 68.3%。
- 部署：3 个生产仓库、4 个月、800+ PR。
- 局限：Flash 评审错关 8/18 已发现已知 bug；16/25 issue 单 run 仅现一次；故障注入类缺陷无法获 verified PoC；diff 门对"内联测试旁的生产改动"有已知的粗规则漏洞（终审兜底）。
