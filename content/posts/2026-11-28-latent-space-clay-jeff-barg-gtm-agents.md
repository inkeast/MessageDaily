## 先说结论

Clay 的 head of AI Jeff Barg 在这期访谈里给出的最反常识的立场是：Clay 明确**不希望自家 agent 明显好于「直接用 Clay + Claude Code」**，而两者用量已「接近 50/50」。背后的判断是，coding agent 范式（Claude Code 2025 年 2 月出现）让专业工具的首触界面不再是护城河，Clay 要争的是「被所有 agent 调用的 GTM 基础设施」——所以它把精力投在数据上下文层、原语和即将上线的自动模型路由上，而不是死守界面。另一条线索是成本：Jeff 算了一笔账，拿 4000 万家公司全库各问一遍「适不适合我的产品」约 1500 美元；而资格审查类任务的 eval 已饱和约一年，前沿模型的价值上移到编排层。对读者来说，这期节目的价值不在于 Clay 做了什么产品，而在于它示范了一家 SaaS 公司在 agent 时代如何重新决定「什么该自己拥有、什么该放手」——以及一家 600 人的公司为什么还在谈「制度性勇气」。

## 一张表格造出的岗位：Clay 如何把「GTM engineer」变成自己的客户画像

Clay 对自己的定义是「增长用的创意工具」（creative tool for growth）：帮人建公司和联系人列表，再用 agent 与数据商补上营收、融资、CEO、办公地点等字段，筛出最值得追的客户（[0s–120s]）。Jeff 说 Clay 七年前起步时只是表格里的低代码工具，这个表格形态沿用至今——swyx 补充，他和其他 AI builder 聊「表格形态」时，大家举的成功例子就是 Clay（[0s–120s]）。

品牌上的「创意」不是装饰。Jeff 认为 GTM 本身就是创造性工作，而「没有一个竞品真的这么相信或尝试去做」，这帮助 Clay 聚起了一群「用很酷的方式增长公司」的社区（[120s–240s]）。更关键的是聚焦：Jeff 入职前约三年，公司在「做招聘还是做 GTM」之间选了 GTM 并加倍投入；此前公司非常横向，收窄到单一画像之后才做出让 Clay 成功的产品（[120s–240s]）。swyx 把这条路径和自己提出「AI engineer」、服务这个群体来增长 Latent Space 与 AIE 的做法类比，认为 Clay 已经是「GTM engineer」的同义词（[120s–240s]）。

Jeff 解释这个被 Clay 「品牌化」的岗位：2010 年代公司靠往 pipeline 里堆人来增长，而现在很多问题可以被工程化——用系统去找客户。这与 LLM、ChatGPT 之后的时代重合：agent 可以爬网、资格审查、在规模上施加判断。他拆解这门学科的三块能力：agent 工程（怎样写提示词才能真正资格审查、理解 LLM 系统）、数据工程（建列表、转换、enrichment、过滤、在上面建不同视图）、以及传统软件工程（编排：有人填了「联系我们」表单，就去研究这家公司，再转给销售或外呼 campaign）（[240s–360s]）。主持人补充这个岗位的旧名字可能是 marketing engineer 或 growth engineer，Jeff 回答它过去大概落在 revenue operations（RevOps）这个篮子里，「今天我们仍然卖给 RevOps 团队」，但作为独立学科还是相当新的；从业背景很杂，很多传统软件工程师转进来做，也有雄心勃勃的 RevOps 人员长成这个角色（[360s–480s]）。

## 数据层是壁垒，通用性是代价

主持人提醒没做过这行的人低估了背后的数据工作：大量数据挖掘、实体解析和一点知识图谱。Jeff 接过话说「几百亿美元的公司就是作为给 Clay 供数的数据库被造出来的」——他举 ZoomInfo、RocketReach 为例：你手里只有一个邮箱，要查出对方在哪家公司、公司多大、是不是买家、有没有刚跳槽。Clay 的位置是与大量数据商合作，数量「数以百计」（他不知道最新数字）（[360s–480s]）。

与过去很多销售工具做「点方案」不同，Jeff 说 Clay 刻意做得很通用，什么列表型的事都能建，客户在上面造出疯狂的东西。但这带来明确的权衡：「非常灵活，意味着有很多种犯错方式」，可以建出一堆不如预期的系统（[480s–600s]）。这一点在后文 Signals 产品的「信息过载」里会再次出现。

## 五个人加入五十人的公司：Avenue 并购与「十倍业务」的起点

Jeff 是通过 Clay 收购他上一家公司 Avenue 加入的。Avenue 是他和高中朋友在 2020 年初创办的，两人从中学起就一起写 app，做过 App Store 最早的 500 个 iPad 应用之一；联合创始人来自 Uber，Jeff 毕业后在 Amazon。他们的洞察是：市场运营团队其实需要和工程团队一样的可观测性方案（[480s–600s]）。公司做了约四年半，客户包括 Ramp、AngelList、DoorDash 等（转写中另一处客户名「Valen/Valiant」前后不一，疑似同一公司，未能核实）；至于「went through IC / raised from Excel」（疑似 YC 与某基金，未核实），保留原文不改（[480s–600s]）。

2024 年末，他们经共同朋友认识了 Clay 的 Kareem 与 Varun。当时已有一些数据工程公司想收购 Avenue，团队也在考虑融 A 轮——业务增长不错，但不确定能不能做到出发时想要的「十亿美元级结果」，于是决定加入一家已有更多牵引力的大公司（[480s–720s]）。条件上的悬殊被主持人追问出来：Clay 当时 50 人，Avenue 5 人，「一天之内进来公司 10% 的人」，Jeff 说他们当时低估了对方下的注（[600s–720s]）。

Avenue 带来的是什么？Jeff 讲了一个对比：加入时 Clay 营收约 1500 万到 2000 万美元，PLG（产品驱动增长）做得非常好，但最大的合同也很小——大量公司自助注册、用得很开心，却还没有进入中端市场和企业销售。Avenue 在 DoorDash、AngelList 这类规模化公司上卖过东西，知道怎么做（[600s–720s]）。他从 Avenue 带来的最大教训反过来说更刺眼：Avenue 有商业牵引，却「从未真正搞清核心客户是谁」，而 Clay 对单一客户画像的专注是他觉得最惊人的地方（[720s–840s]）。

## Signals 与 Claygent：「AI 前锋公司」里只有一个人在做 AI

加入后的头几个月，团队做的是 Signals。Jeff 解释当时的缺口：Clay 在「静态列表」上生意很好——办一场晚宴，想知道来的人里谁是好客户，可以做到；但要做「在线的营收系统」，比如有人换工作了、他在上一家公司买过 Clay、下一家也可能买，没有好用的系统。Signals 就是监控新入职、晋升这类市场里的事件，让客户据此建 play。技术与 Avenue 高度重叠：从「运营可观测性」变成「市场可观测性」（[720s–840s]）。最难的部分是客户多样性——GTM engineer 们太有创意，有人追踪所有谈过的客户、职业轨迹、新闻、社交提及、产品评论、Gong 通话、网站访客，「很容易第一天想着我什么都能响应，然后就被淹没了」（[840s–960s]）。Jeff 坦言这是 Clay「既美又吓人」的地方：能做的太多，也可能让人不知所措（[840s–960s]）。

Signals 本身几乎不是 AI，只是管道，以前大家用 Zapier 做这类事——Jeff 评价 Zapier「礼貌地说没跟上时代」，它更像 A 到 B 的数据搬运；而 Clay 把所有数据汇到同一处，就有了状态，可以做「同一家公司三个人跳去同一家」这类判断（[840s–1080s]）。

从工程负责人到 head of AI 的转折点是一个尴尬的事实：加入时公司 50 人、工程约 20 人，用 agent 做资格审查和 enrichment 已经是业务的重要部分，却只有一个人在做——大概 24 岁、刚毕业，后来离职创业去了。「我们是一家非常 AI 前锋的公司，却零个人在做 AI，挺吓人的」（[960s–1080s]）。此前 Clay 并非没有 agent：2023 年 11 月、ChatGPT 一年后就有会搜网、做结构化抽取、把「谁是 CEO」写进单元格的产品，但它只是工作流里的一步，不是「用 agent 构建工作流」（[960s–1080s]）。Jeff 转向补团队、路线图和策略。催化剂是他自己用 Cursor 的体验：Claude Code 2025 年 2 月出现后，他判断「这显然是工程的方向，GTM 也会有同样的转变」，路线图主体就是让 agent 构建并持续改进 GTM play（[1080s–1200s]）。

这里要分清两个产品。Claygents（转写作 Claygens）是工作流里已有的东西：agent 爬网、结构化数据、填进表格，「大多数人想到 Clay 就想到 Claygents」，Jeff 团队把整个 Claygent 技术栈重建了一遍以支撑规模；业务自加入以来涨了 10 倍，Claygent 用量「比业务增长还多」（[1080s–1200s]）。Clay agents 被他描述为「销售 rep 几年前做的事」：对每条线索做分类、研究、核对员工规模，只不过原生长在表格里、也能上网，数据主要来自公开网络而非 ZoomInfo（[1200s–1320s]）。

## Sculptor 的两次生命：从「加一列」到「写代码」的编排者

Signals 之后第一个真正的爆款是 Sculptor。Jeff 的分层比喻很清楚：Clay agents 做工作流里的每一个任务（资格审查、打分、enrichment、文案），Sculptor 则是「构建这些工作流、协调这些 Clay agents」的那一层——「Sculptor 建表结构，Clay agents 填单元格」（[1200s–1320s]）。它在 2025 年 9 月上线，整个夏天在做，那时还是 Sonnet 3.5 的时代，「人们对怎么正确构建 agent 知道得少得多」。做法是把一堆读写 Clay 平台的工具接口交给模型跑循环，再花大量时间做系统提示和工具定义优化（[1200s–1440s]）。

结果「做得不错」，但表达力远不及当时的 Claude Code，更不用说现在大家做的 agent。Jeff 的分界线很具体：Sculptor 擅长「帮我加一列做这件事」，不擅长「帮我建一个能带来十个合格会议的外呼 campaign」——后者需要的不只是工具，还有销售 rep 脑子里的上下文，而它恰恰缺这些（[1320s–1440s]）。eval 也没量对东西：他们在写、在跑，但上线后立刻看到大量用户拿它做表格上的分析——「我们没规划这个」；一批 eval 在小公司数据上表现好，到了企业客户几百万行的表就崩了。Jeff 说这些都是「事先可能预见、但我们在生产里才观察到」的问题（[1320s–1440s]）。

当时的 eval 是什么样？「很标准」：看输出、判断建议是否正确，本质是 LLM-as-judge，衡量的是实际调用的工具——提示是「建一个表做这些事」，就看有没有真的加上这些列。至于真正的目标（建外呼 campaign 拿到客户），主持人指出这类数据很难拿；Jeff 承认现在也「还没到能测下游效果的地步」，但在「测实际质量」上好了很多（[1440s–1560s]）。

主持人问了一个直接的问题：既然在做 harness，为什么不直接拿现成的？Jeff 的回答是三条教训。第一，「coding agents 真的很好」——模型非常擅长操作 coding agent、用 Bash 或 Python 写脚本做事。第二，他们给 agent 的工具表达力太小，需要能把工具链起来、一次建五列。第三，原语太受限：没有 CRM 数据，发 campaign 也拿不到结果。于是这变成一次全平台重建——现在 Clay 有一个叫 audiences 的「核心数据上下文层」，导入 CRM 数据、Gong 数据，全部实体解析在一起，「可以把它想成客户与联系人的权威总表」（[1440s–1560s]）。

主持人紧接着问了一个「 cheeky」的问题：这层数据是跨客户共享多租户，还是有单租户保证？Jeff 回答是单租户，对所有人都是。主持人算了一笔账：共享可以省很多成本——抓一次 OpenAI 的资料，不用每个客户各抓一遍。Jeff 承认「单租户有一大堆缺点」，但它更简单，而且「重复工作比你想的少」，因为客户做的事非常定制——有人要员工规模，有人要电话号码，有人要「长子的名字」，到那一步就「退化」了。Clay 确实有自己开箱即用的公司和联系人数据集，但没有专门的品牌，硬要叫就叫「search」；对外的口径是「我们有这些集成」，而不是「Clay 自己有数据」（[1560s–1680s]）。主持人把 Clay 概括为「GTM 口味的基础设施商」：你自建会做的事，它替你做了（[1560s–1680s]）。

## 1500 美元给全球每家公司打一次分：模型分层的经济账

谈到开源模型与后训练，Jeff 说 Clay 入职以来一直「 flirt」过训练自己模型的想法，但在他加入后的前 18 个月里「现实上不可行」，最近几个月才在某些领域变得可能——而且主要是为了省钱：推理量到了一定级别，可以「降一个模型档」拿到不错的表现；如果针对自家工具集和输入分布做后训练，效果相当好。他们「很早」，但「很快」会发布这方面的东西，目标是「能力不变、降成本、提速」（[1680s–1800s]）。

主持人问其他 head of AI 该定什么目标——50%？75%？Jeff 给了两条路：一是现成的开源权重模型已经不错，他提到「K3」（转写疑似，未能核实）价格尚可、仍然偏贵，但比 Opus 便宜不少；二是用更小权重档的模型通过后训练做到 Opus 水平——「两跳降本」。他也点了两个坑：训练前沿模型「真的很难」，想在某领域达到或超过他口中的「Fable」（转写疑似）水平不易；更常见的是公司在推理支出基数还不够大时就跳进去，省下的钱对业务没有意义（[1680s–1920s]）。主持人追问门槛是一千万还是一亿美元，Jeff 答「十到一百（百万美元）」这个区间才开始「有分量」，并说这与他的预期一致（[1800s–1920s]）。

swyx 把话题引到一周前做的一期播客——嘉宾是「Jev」（转写疑似，未核实），「现在满城都在谈」——并问 Clay 本来就在做分类，Jev 是不是叠加。Jeff 说两者目标有很多重叠，但 Clay 生产环境里还没用 Jev；他觉得这个名字很准，「可以想象人们会用 Jev 多得多」：现在客户用 Claygent 做资格审查，却仍习惯把列表限制在一万家公司左右（[1800s–1920s]）。然后他给出本期被引用最多的思想实验：Clay 有 4000 万家公司的数据集，每家的 LinkedIn 大约 1000 token，你公司的理想客户画像（ICP）大约 500 token，合计 1500 token；对每家公司问一句「这家客户适合我的产品或服务吗」，跑遍全球所有公司，「大概 1500 美元」——你会得到一张「每家公司是不是我好客户」的概率表，「这是一个很酷的起点」（[1860s–2040s]）。需要说明的是，嘉宾口述的算式（「1500 token 乘 420 亿、每十亿 42 美元」）与 1500 美元的总额并不严格吻合，这里按节目口径记录。

主持人问 enrichment 的预算是多少。Jeff 说差异很大，但「每条合格线索 1 到 10 美元」是个不错的区间；如果约到了一次通话，「10 到 100 美元不夸张」，取决于业务类型和每个客户的期望价值（[1920s–2040s]）。

哪些环节仍需要前沿智能？Jeff 的判断是「GTM 工程的编排方式差异巨大」：像 Sculptor 这样端到端建 play 的事，「最好和平均在产出上差 10 倍到 100 倍」，抽取层级越高越需要前沿；而任务型 agent、资格审查这一步，「我们的 eval 大概已经饱和一年了」，新模型只在更难的任务上更好（[1920s–2040s]）。这就是模型路由有用的地方：深度研究类任务用前沿（「Fable」）远好于「GLM 5.3 flash」（转写疑似），但查一家公司最近的融资公告，「过去一年出的任何模型都能做好」（[1920s–2160s]）。

## 用户讨厌模型选择器：把选模型的责任收回厂商

Clay「很快」会发布模型路由器。swyx 提出他的「agent apps」论：客户不会整天在产品里切模型，大约 5% 的人想切，其余人只想把活干完，「他们信任你作为技术供应商替他们选」。Jeff 的回应比主持人更激烈：「我们的用户讨厌我们的模型选择器……大多数客户不想看到它，看到就烦」，而且收到了很多抱怨（[2040s–2160s]）。他的类比是特斯拉自动驾驶：多数时候你想自动驾驶，有人想自己打方向盘、开手动挡，「祝他们好运」，但大多数人就是自动驾驶（[2040s–2160s]）。

但这不等于取消选择器。客户不可能「为每个新模型在自己用例上跑 eval」，所以不想折腾的人用 auto；想折腾的「我们保留模型选择器」。swyx 提到 Cognition 给自动模式起了「Devin Fusion」之类的品牌名，问 Clay 会不会叫「Clay Fusion」或「Clay One」——Jeff 说「我们就叫 auto mode，不想搞花哨」。他也指出这个模式的一个隐患：用户会怀疑「我怎么知道你是怎么花我的 token 的」，本质上是一个「trust us」模式，需要提供分析数据、建立信任（[2040s–2160s]）。自动模式理论上应优于自选，因为它可以按任务路由——「找 Apple 的 CEO 和找一家不知名本地公司的 CEO 是非常不同的任务」（[2160s–2280s]）。

主持人质疑：Clay 的用户不都是 power user 吗——GTM engineer、大量 agency？Jeff 同意 agency 所有者不会停止自选模型，auto 面向的是「其他所有人」，而这一群人「非常多」：很多客户带着一些 GTM 工程的想法来，但对很多事还是新手，靠品牌和营销「自己找到 Clay」（[2160s–2280s]）。

## 重建成 coding agent 之后，eval 量的是轨迹而非结果

Sculptor 上线后，Clay 把整个 agent 架构重建了一遍：「它不再是一个工具循环模型，而是一个真正的 coding agent」。Clay 公开了 CLI，新版 agent 直接在云端沙箱里用 CLI，表达力强得多，能用 Clay 平台的所有部分（[2160s–2280s]）。eval 的分类现在「主要还是按用例」：描述客户用 agent 做的事，以及「我们认为应该走到的轨迹」——比如问的是一方数据，就应该查数据上下文层——再加上回复质量和实际发生的事：用户要建工作流，有没有真的建出来、工作流是否具备这些属性（[2160s–2280s]）。

往后六个月想做到什么？Jeff 说很难预测，但他真正想要的是「合成式的产出生成」——测量二阶效果：用户要建一个触达某份名单的外呼 campaign，能不能测到「这些人真的回复了」。他承认这很难全部拥有，主持人的反驳更直接：「有些是我的 skill issue——我冷邮件写得不够好」，这也是「真金白银才是真正的 eval」这类说法的麻烦所在。Jeff 说他一直想把某种 eval 平台做进产品，让客户能在产品里建测试、建立确信；主持人说这几乎拖住了公司——「你永远无法拥有结果，因为你是个让人做大批量的工具」，Sierra 那种公司会说「你直接为结果付钱」。Jeff 回应 Clay 不做完全按结果的类型，「但即便是 Sierra，也内建了 eval 平台」——如果某样东西在内部 eval 里表达不出来，「它多半就是一个要做的产品功能」（[2280s–2400s]）。

## 团队全是「软件工程师」，最难招的是做过生产 agent 的人

AI 团队的构成是「非常平均的三分」：传统机器学习背景的人、应用 AI 工程师（建过 eval、喜欢做这类事的人）、以及标准软件工程画像——「这是个工程系统，可以在上面建很多东西」。头衔上大家都叫软件工程师，主持人补一句「现在叫 AI engineer 了」（[2400s–2520s]）。最难招的能力，Jeff 说得很干脆：有「实际构建生产级 agent」经验的人。Clay 在纽约，这类人比湾区少。swyx 不太服气，说自己的第二大会议就是 AIE New York、「我们在把这些人聚起来」，又承认纽约人总跟他说「这里没有 AI 场景」，数来数去就是 Runway 和 Ramp 这几家；Jeff 说自己在纽约长大、爱纽约，但事实如此。他把人才池小的原因归于时间：「ChatGPT 才四岁」，在 agent 工程上花过一年的人本来就不多（[2400s–2640s]）。

## 没有 Temporal、没有 LangGraph：BullMQ 上的手写编排

swyx 自述有 Temporal 背景，于是问 Clay 用什么做后端编排。答案让两位主持人都笑了：没有 Temporal、没有 LangGraph（转写作 blank graph），「手写的」。Jeff 说 agent 持久性大部分至今仍建在 BullMQ——一个 JavaScript 队列库——之上，「大部分还好」，但「我不知道我们在 BullMQ 上还能不能撑过下一个 10 倍」（[2520s–2640s]）。

数据栈同样是手写为主：ClickHouse 在产品和内部都用，Snowflake 用于分析，产品里大部分东西建在 Postgres 之上；内部数据集用过 Dagster，正在改造（[2640s–2760s]）。swyx 感叹「现代数据栈完蛋了」——Clay 体内嵌着一整个数据仓库和 ETL/反向 ETL 管道，把这些公司都吞并了，他自述曾供职于其中之一（Airbyte），「他们基本都死了」；Avenue 当时也和 Metaplane 这类数据监控公司相邻，Jeff 说他和那些人很熟（[2520s–2640s]）。Jeff 的回应更克制：前数据人们「被吞进了 AI 工程、被吞进了应用、被默认就该能跑」，但上下文层、知识图谱、管道都还是要建的，「有时候会坏，不会魔法般地自己工作」（[2640s–2760s]）。

swyx 又问连接器维护——这曾经是个大生意，现在是不是大家都有 MCP 了就不用维护了？Jeff 说 Clay 维护和构建这些的人「比你想的少很多」，但仍然很多；最近刚上线了 25 到 30 个新集成，瓶颈不是工程，「而是合同和周围的事」，主持人补上「还有质检——基础集成容易，但你真的测过吗」（[2640s–2760s]）。

## agent 规模化时先坏的是可观测性和限流

主持人问 agent 规模化过程中什么坏了。Jeff 说加入 Clay 后立刻在做的是 Claygent，「坏的东西太多了」。第一是没有可观测性，于是接入了 LangSmith，才看得清 agent 在做什么、调了什么工具、有没有在工作（[2760s–2880s]）。第二是负载形态：因为人们在表格里跑东西，推理负载非常尖峰——一张五万家公司的表，就等于同时给每家公司跑一个 agent，短时间内向推理供应商发出海量请求。大量工作围绕限流：供应商宕机或限速时能暂停执行、再恢复（[2760s–2880s]）。

主持人问是否有双源推理策略。Jeff 说没有，「因为各种原因」，但「现在可能会做」；Clay 更在意的是公平——「noisy neighbor」问题：一个大企业客户跑一百万条 enrichment，不应该把刚注册、只想跑十人工作流的用户挤出去（[2760s–2880s]）。swyx 顺带推荐了 Jeff 在 LangSmith 大会上的讲座，说这里不展开（[2760s–2880s]）。

swyx 接着归纳他在各公司 head of AI 身上看到的共同模式，像在编一本「head of AI 手册」：小团队也能做很多；要路由器但不撤选择器；最终什么都双源；从闭源转向开源模型。他追问还有什么—— Clay 的 agent 看起来更「管道式」、自主度有限，而有人在直接发「完整的 ChatGPT/Codex/Claude Code 克隆」。Jeff 说 Clay「实际上也会这么做」：产品里会有一个带沙箱、约束很少、能用全部 Clay 原语的 agent（[2880s–3000s]）。但他紧接着给出了本期最核心的立场：「我们的 ethos 是让 Clay 平台对所有 agent 都好用——不管是我们的还是外部的 agent。所以我们明确不希望自家 agent 明显好于直接用 Clay + Claude Code。」（[2880s–3000s]）

形态上，Clay CLI 和 MCP 都有，做 MCP 的团队把重心转去做了 CLI；Jeff 把它们统称为「API、SDK、CLI、MCP——四种形态」，主持人感慨大家对这些「很宗教化」，Jeff 认为「检验偏见」是好事（[2880s–3120s]）。

## 50/50：当一半用量来自 Claude Code，为什么还做自家 harness

主持人问 Clay 在 Claude Code 等外部 harness 里的用量与自家 harness 相比是多少。Jeff 说具体比例记不清，「但比我想的接近 50/50 得多」。主持人用私人例子回应：他约会的 GTM 从业者酷爱「Grokbot」（转写疑似，未核实），「你永远别想从她手里掰走」。Jeff 说「我们也不想」，团队花了很多时间想「是否需要拥有这块界面面积」，结论是「真的没关系」——人们可以在 Grokbot 里做 GTM，「我们希望他们拥有所有的」（能力）（[3000s–3120s]）。

主持人提出一个反方框架：这像 Salesforce 的「Mark Vanier」（转写疑似，未核实）也信奉的宗教——作为真相之源或 SaaS 提供商，你可以要求所有人付月费用你的东西，而把自己暴露为 API 就失去了首触界面，「但你可以把 API 做得非常好」。Jeff 回答，团队确实在自家 harness 上花了很多时间、也希望人们用它，「但那不是重点」，「我们只是想让 Clay 成为这个 agentic GTM 基础设施，它会在很多不同的地方有价值」（[3000s–3120s]）。主持人再问：所以你们是在试图自动化 GTM？Jeff 说框架不同——Clay 想做的是把 Claude Code 带给工程的转变搬到 GTM：GTM engineer 仍然存在，只是产出多得多。他拿 Clay 自己举例：公司有一个很好的 GTM 团队，「但有一大堆我们没在做的事」，他能随口想出十个现在没在跑的 GTM 想法，「Clay 的目标就是把这些都做了」（[3000s–3240s]）。

内部需求反过来推动产品的一个例子是 CLI：Jeff 说 CLI 很大程度上来自内部 GTM 团队——他们和 Grokbot 用户一样，坐在 Cursor 里不肯出来，说「我们不能不用」；Clay 的销售团队在 Codex 里做交易准备；而 GTM ops 团队「大概就是我们所说的 GTM 工程团队」——前工程师在做 GTM 工作，在 Clay 上建一堆内部工具（[3120s–3240s]）。主持人仍然不放过 50/50 这个数字：「如果 Clay harness 的意义不是打败 Claude Code harness，那为什么要做？为什么不全力做最好的 CLI/MCP？」Jeff 的回答朴素：「人们想要在 Clay 里有东西」——客户已经在 Clay 界面里建东西，自然想在那里用 agent，「某种程度上只是跟随客户需求」。他也不神化自家 harness：「你可以把 Claude Code 装进容器——比如 Pi 或者 OpenCode」——「很多这类 agent 实际上就是这么做的」。主持人的结论是「harness 构建里没有太多 alpha」；Jeff 透露 Clay 的 agent harness 建在开源的 Pi 之上做定制，技术栈是 JavaScript，用 Vercel AI SDK（[3120s–3240s]）。

## 上线前两天被「无限期推迟」：制度性勇气与创始人模式

swyx 把话题转向他常问的「勇气」与「情绪代谢」（emotional metabolism）：当某件事没成，那是什么样子？Jeff 说他「非常强烈地」认为制度性勇气是当下公司里最重要的东西，而且很难——他加入时 Clay 50 人，现在大约 600 人，「势头就是让一切固化，做一件事需要的勇气越来越多」（[3240s–3360s]）。

他的案例是 ChatGPT Apps。Clay 是首批商业应用的 launch partner 之一，之前与 OpenAI 团队松散合作，然后「在季度中间重排了大约 25% 的工程团队、持续一个月」做集成——「ChatGPT 有巨大的需求」，动机很强。但对方始终不给「这事会不会成」的信号，只说「如果够酷也许会上」，于是 Clay 把公司四分之一的工程力量押上去。上线前两天，OpenAI 说「我们要取消，无限期推迟，如果再做会通知你们」（[3240s–3480s]）。主持人的反应是「TLDR：大动作」，追问 OpenAI 为何改主意。Jeff 说自己不确切知道发生了什么，「他们肯定不是轻易做的决定，有别的要平衡的优先级」，但团队当时的判断是「这个赌注仍然成立，我们只需要做」，于是继续做，假设「他们很可能会改主意」——三四天后，OpenAI 改了主意（[3360s–3480s]）。主持人问是否有假设，Jeff 说很难推测，「现在一切都很动态，围绕这些的决策流程也很动态」；主持人的总结是「任何和实验室打过交道的人都知道，他们内部很混乱，我们同情他们」（[3360s–3480s]）。

swyx 进一步质疑优先级：录制时是第四届 DevDay 前夜，OpenAI 每年都想推某种市场类产品，「每次都 flop」，为什么把它当头等优先级？Jeff 解释，那正是 Clay 开始想「界面面积」问题的时期——是否要在 Clay 里做一个完整的 ChatGPT 克隆，还是借用已有的东西；另外有博弈论的考量：「如果有一个竞争对手做了，而这次它真成了」；「感觉像是对的赌注」（[3360s–3600s]）。swyx 也承认「每年都更好、更精致，虽然不会席卷世界，但出现在首页非常有价值」。Jeff 把它比作自己的 iPad 早期开发经历：「AI 显然是某种平台转移，但人们还没搞清楚平台那部分」——每家公司都有自己想成为平台的「单窗玻璃」（[3480s–3600s]）。swyx 反过来提醒：Clay 自己已经是很多人的平台——合作伙伴会在 Clay 的活动上发布集成，「别对他们取消」；他把这一切归纳为「情绪代谢：打击来了就接着」（[3480s–3600s]）。

swyx 还把并购解读为「创始人模式」的一种形式：50 人的公司买下 5 人的团队，就是在注入创始人能量——「我不是来做普通员工的，我被雇来就是为了搅动局面」。他说 Clay 应该还做过其他并购，Jeff 默认了（[3480s–3600s]）。谈到「信念的勇气」，Jeff 用 Clay 自身的历史回答：Kareem 建了这家公司五年，「基本没什么灵」，所以他「灵魂深处相信只要推得够久事情就会成」。产品上也有例子：刚发布的 Workflows 产品，agency 所有者「非常喜欢」、有自发的热度，但第一次拿给人看时，「人们不理解、困惑，有些甚至生气」——「为什么要做这个？给我列表就好，我们喜欢表格」「这不就是 Zapier 吗」（[3600s–3720s]）。Jeff 回应，如果是今天造 Zapier，大概会吸收这些东西——它「agent 优先、CLI 优先」，大多数工作流是用 CLI 或 agent 建的（[3600s–3720s]）。

## 「多少 YC 公司在用 Clay」：一分钟问出来的答案与它没回答的问题

主持人把 Clay 的理想概括为「让所有人都能编程」——包括那些「不是 Python 之神」、不该在 Cursor 里碰基础设施的 GTM engineer，给他们一个「受祝福的地方」，所有工具和数据都在一处。Jeff 说这也在改变 Clay 内部的工作方式：团队想分析「多少 YC 公司在用 Clay」，直接问了 agent，「大概 60 秒」就找到了答案。主持人猜数字很高，Jeff 不肯给确切数字，只说「是个健康的数字」，并拿 Supabase 作类比——「每一批大约 70% 用 Supabase」（[3600s–3720s]）。他的感慨是时间账：一年前要把 YC 批次抓进电脑里的 CSV、想办法拿到 Snowflake 权限、再去 Salesforce 对照，「现在这些都不需要了，直接问 Clay」（[3720s–3840s]）。主持人指出 Clay 所在领域的特权——数据大多是「准公开」的，不像别的公司对 Snowflake 权限那么敏感。Jeff 同意「大部分如此」，但也有公司要更细粒度的权限；有数据上下文层的好处之一，就是只带 GTM 相关的信息，不必什么都进来（[3720s–3840s]）。

Workflows 是「今年夏天早些时候」上线的，属于「12 周 12 次发布」中的一次——Jeff 自己也说不知道为什么选在夏天。表现「非常好」；他们盯的指标之一是「人们在 workflows 里做的事占 tables 的比例」：大家把 Clay 想成表格工具，那也确实是产品核心，「但我们看到很多人直接切换到 workflows 作为主要模式」，无论按客户还是按比例，「增长很快」。主持人问这是否可能成为主界面，Jeff 说「肯定有这个潜力」（[3720s–3840s]）。

接下来最让他兴奋的是重架构的 Sculptor：已经在产品里以有限形式上线，将「很快」对所有人、在 Clay 的每个界面发布——这是 Clay 的第一方 agent，回答 YC 问题的就是它。为什么要重架构？「就是为了围绕 coding agent 重建它」——更强大、表达力强得多、更可扩展；主持人插话「更高的 NRR」（净收入留存）（[3840s–3960s]）。swyx 提出他最感兴趣的分析角度：它会改变人们问的问题类型——他最大的遗憾之一是没早期投 Perplexity，当时想「我坚持用 Google，不需要每次搜索都调一次 LLM」，但当你真的每次搜索都调 LLM，「你会问不一样的问题」（[3840s–3960s]）。Jeff 说他最期待的是人们开始建的「奇怪的 GTM 想法」：做完 YC 分析后他想到，对那些还不是 Clay 客户的公司，「现在没有人系统性地去问为什么」，应该让 agent 每周去查一遍（[3840s–3960s]）。

主持人问 Clay 有没有「用 Clay 与不用 Clay 的 YC 公司」的成长数据——Stripe 和 Cognition 都做这类事。Jeff 说「我们应该做」，主持人却提醒这一定是自选择的：更技术原生、长得更快的公司才会采用，「混淆了相关与因果」。Jeff 同意「采用 Clay 不等于成为模范客户，但这是一步」，也承认「大概有什么原因让我们没有真正聚焦 YC，但我也说不上来为什么」（[3960s–4080s]）。

## 模型仍「有点笨」，agent 还不会调试 agent

主持人问：假设下一代模型来了，有什么是因为能力不够而还没做的？Jeff 的回答从「看过太多 agent trace」出发：「模型还是有点笨。」例子是基础的——用同样的输入反复试同一条 CLI 命令、不纠正，「不是火箭科学，但还有空间」（[3960s–4080s]）。主持人问 Clay 是否有实验室合作——「你们和这些人都共享 Slack」，能不能像实验室要反馈那样，给一个 LangSmith 线程 ID 说「看这个」。Jeff 说「我们大概可以」，这确实是个有意思的关系（[3960s–4080s]）。swyx 加码：agent 构建者需要自己的一套反馈机制，更有力的版本是「把所有 bug 报告打包叫它 benchmark」——「你们在这个上面很差」。Jeff 认为方向对，但要花些功夫（[3960s–4200s]）。swyx 建议「找个研究生一起做」：把过去 500 条 bug 报告分类、归组、去 PII，就是一篇论文和一个 benchmark，Sierra 很早就这么做了——按垂直行业做 tau-bench（航空、零售、电信），本质是「请为我的业务优化」。Jeff 说 Clay 想过「销售优化模型」长什么样，但「很早」，还没考虑公开 benchmark；swyx 说这是「win-win-win」，还能把纽约的工程师「从洞里引出来」。Jeff 补充，内部有真正的 GTM engineer 做「飞轮」——怎么找客户群、怎么给客户打分——「但这个飞轮我们大概连接得不够」（[4080s–4200s]）。

具体到 coding agent，Jeff 最想要的改进是：看着一条很长的 agent trace，指出「它在哪一步糊涂了」。「现在 agent 还不擅长这个，它们的直觉是错的」——它们会说「这步花的时间长」，而实际上那步花时间是对的、错的是别处，「大部分时候都是这样」。所以「下载坏 trace、让 agent 看、自动改进」这件事「就是不工作」，让 agent 写自己的提示也只在某种意义上可行；Clay「仍然手写大量 skills」，他认为这是个可解的问题（[4200s–4320s]）。预告方面，Clay 即将举行活动（转写作「Sculpt」），会上会发布「一整套面向 GTM engineer 的新功能，给他们工具箱里加新工具」（[4200s–4320s]）。主持人的收尾是「你一直很坦诚」，承认自己「概念上懂 Clay，但没懂它的深度」，现在已经有两个业务上的用例；对工程师朋友，Jeff 的建议是：「直接试着让 Clay agent 建你想做的那个 GTM 事，看看会发生什么。」（[4320s–4343s]）

## 机制链与读者启发

**链条一：分类成本塌方——从「抽样审查」到「全量打分」**

- 变化/信号：Jeff 给出一道算式——Clay 的 4000 万家公司数据集，每家按「LinkedIn 约 1000 token + 理想客户画像约 500 token」各问一遍「这家公司适合我的产品吗」，全场跑完约 1500 美元（[1800s–2040s]，嘉宾口述、算式口径不严）。主持人补刀：现在客户用 Claygent 做资格审查，仍习惯把列表压到一万家左右再跑（[1800s–1920s]）。
- 直接原因：单位推理价格持续下滑（嘉宾顺口给出「每十亿 token 几十美元」量级的单价），加上开源权重模型「比 Opus 便宜不少」（[1680s–1800s]）。
- 谁获得/失去：获得方是数据集持有者与小团队——以前只有买得起 ZoomInfo 的公司才能「对全世界先筛一遍」；失去方是靠「数据访问权」收费的中间层，因为筛选本身不再稀缺。
- 二阶影响：当「全量打分」比「人工挑样本」更便宜，GTM 的问题提法会从「我该查哪些公司」变成「全库里谁最像我最好客户」；同时噪声也等比放大——打分便宜不等于线索干净，后段的触达成本（嘉宾口径：每条合格线索 1–10 美元、约到一个电话 10–100 美元，[1920s–2040s]）成为新的瓶颈。
- 未来观察指标：单次全库扫描价格；客户平均运行规模（从一万到全库的比例）；合格线索的后续转化率是否被稀释。
- 对读者的启发：任何依赖「人工先筛一遍」的流程（招聘、采购、投资标的扫描）都可以套这道算式——先算全量成本，再决定要不要保留人工筛选这一步。

**链条二：模型能力分层——「任务层已饱和，价值上移到编排层」**

- 变化/信号：Jeff 说资格审查类任务的内部 eval「大概已经饱和一年」，新模型只在更难的任务上更好；而像 Sculptor 那样端到端建 play 的编排任务，「最好和平均差 10 倍到 100 倍」（[1920s–2040s]）。
- 直接原因：简单任务上各家模型早已越过「够用」线，继续堆前沿模型只多花钱；复杂任务则仍受表达力与上下文制约（Sculptor v1 擅长「加一列」、不擅长「给我带来十个合格会议的外呼 campaign」，[1320s–1440s]）。
- 谁获得/失去：获得方是把前沿预算集中到编排层、在任务层降档的公司（Jeff 的「两跳降本」：换开源权重 + 用更小模型后训练到 Opus 水平，[1680s–1800s]）；失去方是按「每次调用都卖前沿模型」计价的供应商，以及把 eval 只做在小公司数据上的团队（企业百万行表会崩，[1320s–1440s]）。
- 二阶影响：模型选择器从「产品卖点」变成「用户怨气来源」——Clay 用户讨厌模型选择器，约 5% 的人想自己切，其余希望厂商代选，Clay 即将推出自动路由并保留手动模式（[2040s–2280s]）。选模型的责任从用户转移到厂商，信任问题随之转移（「你怎么花我的 token」）。
- 未来观察指标：Clay 路由器上线后的自动模式采用率与抱怨量；后训练/开源模型在实际负载中的占比（Jeff 称会「很快」发布）；Jeff 给出的后训练门槛——年推理支出「十到一百万美元」量级才开始有分量（[1800s–1920s]，转写为 ten to hundred，按上下文理解为百万美元）。
- 对读者的启发：先用 eval 确认哪一层已经饱和，再决定预算放哪一层；不要为「 saturated」的任务多付钱，也不要为「未饱和」的任务省前沿模型。

**链条三：SaaS 的界面护城河松动——「不比 Clay + Claude Code 更好」**

- 变化/信号：Clay 明确表示「不希望自家 agent 明显好于直接用 Clay + Claude Code」，自家 harness 与外部 harness 的用量「比我想的更接近 50/50」（[2880s–3000s]、[3000s–3120s]）。
- 直接原因：coding agent 范式（Claude Code 2025 年 2 月出现）让「在通用 harness 里操作专业工具」成为可能；Clay 把能力开放成 API、SDK、CLI、MCP 四种形态，内部 MCP 团队转向 CLI（[2880s–3000s]）；自家 harness 建在开源 Pi 之上定制，Jeff 坦言 harness 层「没有太多 alpha」（[3120s–3240s]）。
- 谁获得/失去：获得方是拥有数据与原语的基础设施商（被更多 agent 调用）和偏好自己工具的专业用户（主持人提到约会对象「掰不走」的 Grokbot，转写疑似）；失去方是把首触界面当作护城河的应用商——主持人以 Salesforce 式「暴露 API 就失去首触界面」的顾虑作对照（[3000s–3120s]）。
- 二阶影响：竞争焦点从「谁拥有窗口」转向「谁拥有上下文层与原语」——Clay 为此全平台重建了名为 audiences 的数据上下文层（CRM、Gong 数据实体解析成一张总表，[1440s–1560s]）。Clay 仍做自家 harness，但理由只是「客户想在 Clay 界面里用 agent」（[3120s–3240s]）。
- 未来观察指标：外部 harness 占比是否继续上升；Clay 是否把更多能力做进原语而非界面；路由器、CLI、MCP 的发布节奏。
- 对读者的启发：如果你卖的是「工作台」，问自己被 Claude Code/Codex 直接调用后还剩什么；如果剩下的是数据、权限与可观测性，那就该把它们产品化，而不是死守界面。

**链条四：工具型公司的结果归属——「eval 表达不了的东西，就是要做的产品功能」**

- 变化/信号：Jeff 想量 Sculptor 产出的二阶效果（外呼 campaign 对方是否真回复），但承认做不到；主持人反驳：你是大量工具，无法拥有全部结果，Sierra 直接按结果收费（[2280s–2400s]）。
- 直接原因：GTM 结果受客户自身能力影响（主持人的「skill issue」论），工具方拿不到完整因果链；Clay 目前的 eval 主要是按用例检查轨迹与产出属性（[2160s–2280s]）。
- 谁获得/失去：获得方是坚持工具定位、不承诺结果的公司（风险小、可规模化）；失去方是期待「按结果付费」的客户，他们要自己承担使用质量。
- 二阶影响：Clay 选择把 eval 能力做进产品、甚至连 Sierra 也内建 eval 平台（[2280s–2400s]），「可评估」正在成为 GTM 工具的标配功能。
- 未来观察指标：Clay 是否发布面向客户的 eval 功能；「工作流 vs 表格」使用占比（Jeff 称很多客户已把工作流当主模式，[3720s–3840s]）。
- 对读者的启发：做工具不必羡慕按结果收费——把「客户怎么判断好不好用」产品化，是另一种拥有结果的方式。

**链条五：平台依赖下的制度性勇气——ChatGPT Apps 上线前两天被「无限期推迟」**

- 变化/信号：Clay 投入约 25% 工程团队一个月做 ChatGPT Apps 首批商业应用，上线前两天被 OpenAI 告知无限期推迟，3–4 天后对方改主意（[3240s–3480s]）。
- 直接原因：Jeff 称 OpenAI 内部「很动态」、决策流程同样动态；swyx 补充 DevDay 历年推市场类产品多不成功，质疑为何当头等优先级（[3360s–3480s]）。
- 谁获得/失去：获得方是保持选项的合作方——Jeff 团队按「这个赌注是否仍成立」决定继续做，等来了反转；失去方是把季度计划押在单一大平台发布节奏上的团队。
- 二阶影响：Jeff 把这件事归入「制度性勇气」——公司从 50 人到约 600 人，固化惯性越来越强，做事需要的勇气越来越多（[3240s–3360s]）；swyx 把并购小团队解读为注入「创始人模式」（[3480s–3600s]）。
- 未来观察指标：Clay 在 ChatGPT Apps 正式上线后的位置与用量；Clay 自己的活动（转写「Sculpt」）上发布的新功能是否按期。
- 对读者的启发：与平台方合作时把「被取消」纳入计划——决策标准不是情绪而是赌注是否仍成立；组织变大后，把「继续做」的权力留给离一线最近的人。

**行业意味着什么**

这场访谈里真正被反复确认的，是 GTM Agent 的竞争重心已经从「能不能跑」转向「在哪里跑、由谁选模型、谁拥有上下文」。Clay 的选择是把数据层与原语做厚、把界面做薄、把模型选择内部化；这些选择让它在 agent 时代仍是「被调用的基础设施」，但也意味着它主动放弃了界面独占带来的溢价与结果归属带来的想象空间。

**我该如何观察**

- 看 Clay 的路由器、CLI、MCP 与重架构 Sculptor 的发布节奏与采用率，尤其是外部 harness 占比是否继续向 50/50 以上漂移。
- 看「全库扫描」类用例的真实成本与线索质量，判断分类成本塌方是否带来转化稀释。
- 看按结果收费的对手（如 Sierra 类）是否反过来内建 eval 与工具能力——两个方向的收敛速度，决定 GTM Agent 最终是工具生意还是结果生意。
