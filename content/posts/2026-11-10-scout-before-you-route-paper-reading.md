## 一、论文背景

### 1.1 什么是模型路由（Model Routing）？

现在的 LLM 生态像一个庞大的劳务市场：有便宜但能力一般的小模型，有昂贵但强大的推理模型，还有同一模型在不同"思考努力程度"（reasoning effort）下的多个版本。**模型路由器（router）** 就是这个市场的调度员——每来一个用户请求（query），它在生成任何内容之前决定把这个请求发给哪个模型，目标是在"答对的概率"和"要花的钱"之间取得最优权衡。

形式化地写，对请求 x 和候选模型 m，路由器要估计两件事：

- **p_m(x)**：模型 m 答对 x 的概率（质量）
- **c_m(x)**：模型 m 处理 x 的成本（价格）

然后选使得 `V·p̂_m(x) − ĉ_m(x)` 最大的模型，其中 V 是"答对一道题值多少钱"，扫过不同的 V 就能扫出一条成本-精度权衡曲线。

### 1.2 被忽视的另一半：成本其实是"因题而异"的

绝大多数路由器对 c_m(x) 的处理简单粗暴：**给每个模型定一个固定均价**，仿佛每个请求消耗的 token 数都一样。这在非推理模型时代勉强成立，但推理模型（reasoning model，会先写长篇思维链再给答案的模型）彻底改变了局面：

- 论文实测，在 LiveCodeBench 上，**同一个模型的输出长度在不同问题之间相差 11–121 倍**（第 10 百分位 vs 第 90 百分位）；
- 一个"平均便宜"的模型，在某个特定难题上可能生成超长推理链而变得昂贵；
- 反过来，"平均昂贵"的强模型在简单题上可能几百 token 就收工。

这就像汽车保险：如果保险公司对每位司机收同样的保费，好司机在补贴坏司机。论文用了一个精妙的类比——他们的方法是一个"**精算师式侦察兵（actuarial scout）**"：像精算师根据投保人个人情况定价而非收取平均保费一样，侦察兵在任何一个模型被调用之前，就对每个请求单独定价。

### 1.3 三个研究问题

论文把这个被忽视的问题拆成三问：

1. **何时值得预测逐 query 成本？**（per-query cost worth predicting when?）
2. **是什么因素驱动了给定输入的成本？**
3. **这种预测能做多便宜？**——需要多少标注样本？需要多大的 LLM 做一次 prefill？

值得注意的是，此前唯一把成本预测从路由系统里孤立出来研究的工作（CARROT）得出的结论是"逐 query 成本没什么用"——但它测试的模型池里几乎没有推理模型。本文正是抓住这个盲区：**推理模型时代，这个结论需要重写**。

### 2.2 本文的三点独特性

1. **把成本预测孤立出来系统评测**：此前的工作要么在完整系统内部顺带预测成本（无法归因），要么像 CARROT 一样孤立测试但模型池里没有推理模型。本文在推理模型候选池上，让所有成本估计器共享同一套成功预测，正面对比。
2. **同时对照两个锚点**：向下对照"固定均价"（中位数定价），向上对照"完美成本知识"（上帝视角知道每个请求的真实长度）——这让"值不值得做"有了上下界。
3. **机制分析**：不只比数字，还回答"长度到底由什么决定"——这是理解所有结果的一把钥匙。

### 2.3 与"激活探针"研究线的关系

另一条相关研究线发现：LLM 在生成第一个 token 之前，其内部激活就"编码"了它自己会不会失败（Lugoloobi et al., 2026, arXiv:2602.09924——用生成前激活上的线性探针预测成功，并据此路由可在 MATH 上省 70% 推理成本）。Varshney 等人的 prefill 路由器（arXiv:2603.20895）也用 prefill 激活预测正确性。**本文站在这些工作肩膀上，把"激活探针能预测什么"从成功概率扩展到了输出成本**，而且只用一份共享激活。

## 三、问题定义

### 3.1 形式化

给定请求 x 和候选模型池 {m}（每个候选是一个"模型 × 推理努力档位"的组合，由某个 API 端点提供服务），路由器在生成前选定一个候选：

```
m*(x; V) = argmax_m { V·p̂_m(x) − ĉ_m(x) }
```

其中 V 是正确答案的价值。每个请求只回答一次，没有验证器、没有回退链。成本按 token 计价：

```
ĉ_m(x) = r_in·n_in(x) + r_out·ℓ̂_m(x)
```

输入 token 数 n_in(x) 是已知的，输入单价 r_in、输出单价 r_out 是模型属性——**唯一需要预测的是输出长度 ℓ̂_m(x)**。这就是整篇论文的核心未知量。

### 3.2 评测协议的三个关键设计

**（1）匹配精度下比成本（matched accuracy）**。不能直接比"谁便宜"，因为便宜的策略精度也低。做法：扫 V 得到每个估计器的成本-精度前沿（上凸包），在两条前沿共同达到的 12 个精度点上逐一比较成本，报告几何平均节省比例。

**（2）Headroom 与 Capture**。两个本文反复使用的概念：

- **Headroom（节省上限/头寸空间）**：假设一个"完美成本预言家"（知道每个请求的真实输出长度）做路由，相对中位数定价能省多少。这是任何实际估计器的实用上界。
- **Capture（捕获比例）**：本方法实际节省 ÷ headroom。衡量"上帝视角的蛋糕，你吃到了几成"。

**（3）十套训练集平均 + 配对 bootstrap 区间**。每份结果都是对 10 个随机重划的训练集求均值（每次重训所有探针），置信区间是测试问题上的配对 bootstrap——两个估计器在同一批重采样上对比，控制了题目难度波动。

### 3.3 候选池与基准

- **5 个主候选**（经 OpenRouter 调用）：gpt-oss-20b（low/medium 档）、deepseek-v4-flash、gpt-oss-120b（medium/high 档）。deepseek-v4-flash 被钉死在单一 provider，因为不同 provider 的输出长度差异显著。
- **9 个基准**：LiveCodeBench、Omni-MATH、MMLU-Pro、AIME 1983–2024、APPS、BigCodeBench、CodeContests、SuperGPQA、BIG-Bench Extra Hard——覆盖代码、数学、知识、混合推理四类。
- 候选间成本相差 11–49 倍，且**精度与价格不单调**：deepseek-v4-flash 在 5 个数据集上最准，其余也只差 1.6 点以内，成本却只有 gpt-oss-120b-high 的 17–37%。

## 四、问题解法

### 4.1 核心思路：一个共享的"侦察兵"

先用一个类比建立直觉：想象你是一家翻译公司的调度台，手下的译员（候选模型）按产出字数收费。糟糕的调度台只看"每位译员平均每单多少字"；聪明的调度台拿到稿件先扫一眼（**scout 预检**），判断"这份法律合同对译员 A 大概是 3000 字的活、对译员 B 是 8000 字的活"，再结合每位译员的可靠度派单。

技术上，scout 是一个**冻结的（frozen，权重不更新）小 LLM**——Qwen3-4B-Instruct-2507。它对 prompt 只做 **prefill**（预填充）：

> **Prefill 是什么？** LLM 处理一个请求分两阶段：prefill 阶段一次性并行读入整个输入 prompt，为每个 token 位置计算隐藏状态向量（激活），并构建 KV 缓存；decode 阶段才逐个生成输出 token。scout 只做第一步——**读题，不答题**。

从这次前向传播中提取特征：**8 个层的 mean-token 激活和 last-token 激活拼接**。直觉上，中间层的激活编码了模型对问题的深层理解（难度、类型、需要多长的推理），而 last-token 激活浓缩了"读完题后的整体印象"。

### 4.2 双探针：成功探针 + 成本探针

> **线性探针（linear probe）是什么？** 在冻结模型的激活向量上训练一个简单线性分类/回归器来预测某个属性，是可解释性研究的经典工具（Alain & Bengio, 2016）。它的价值在于：如果线性探针能预测某个属性，说明模型内部表征"线性可读地"编码了该属性。

在同一份激活特征上，为**每个候选模型**各训练两个探针：

| 探针 | 任务 | 模型 | 关键细节 |
|---|---|---|---|
| 成功探针 | 预测 p̂_m(x) | L2 正则逻辑回归 | **Platt 缩放校准**：用校准集把原始 logits 映射为良好校准的概率（路由公式里 V·p̂ 需要真实的概率尺度，不只是排序） |
| 成本探针 | 预测 log 平均输出长度 | 岭回归（ridge） | **Duan smearing 修正**：先回归 log 长度再指数化回去会引入系统性偏差（Jensen 不等式），Duan (1983) 的非参数 smear 估计用训练残差修正这一偏差，再重缩放到候选的训练均值 |

预测长度乘以该候选的 token 单价，得到期望成本。**成本探针对一个已经部署 prefill 路由器的系统是"零增量"的**——激活已经算好了，只是多训一个线性头。

### 4.3 为什么一份激活能预测所有候选模型的长度？

这是方法成立的机制前提，论文用实际输出做了方差分解（详见第六部分）：**输出长度主要取决于问题本身，而非模型或采样随机性**。问题间方差占 log 长度方差的 .71–.99，且各候选模型在同一问题上的长度互相解释 .42–.96——"同一道题对所有模型都是长题"。因此，一个读题的 scout 的激活里包含足够的共享信号，每个候选只需要一个小小的线性变换来"翻译"成自己的长度尺度。

### 4.4 一个重要的反直觉边界条件

一个看似省事的替代方案：既然"难题更长"，直接用成功探针的概率反推长度不就行了（消融项 "length from predicted success"）？论文发现这**在数学/代码类上可行，在知识/混合格式上会失败**：

- 数学/代码（LCB、AIME、CodeContests 等）：经验难度单独解释约一半的 log 长度方差（R² .45–.57）——难题确实更长；
- 知识/混合格式（MMLU-Pro、SuperGPQA、BBEH）：经验难度解释不到五分之一——**一道多选题长得长，是因为它的选项长，不是因为难题**。

所以在 MMLU-Pro 上，专门训练的长度探针比"从成功概率反推长度"多省 18.4 个百分点。这个发现本身就是对"长度≈难度"这一行业默认假设的一次有力修正。

### 4.5 工程细节摘要

- 特征标准化（零均值单位方差，按训练集统计）；
- 正则强度在校准集上从 9 个候选值中选择（成功探针按 AUC）或训练集内部交叉验证选择（成本探针）；
- 价格用最小二乘拟合各模型实际账单费用得到（区分输入/输出单价）；
- Scout 前向开销：单卡 H100 上 **19–28 毫秒**，成本探针零额外开销。

## 五、评估指标与实验证据

### 5.1 主结果：Headroom 与实际节省

| 数据集 | 领域 | Headroom（完美知识） | 本方法 vs 中位定价 | Capture |
|---|---|---|---|---|
| LiveCodeBench | 代码 | 40.1% | **27.8%** [13.9, 35.6] | .69 |
| Omni-MATH | 数学 | 51.9% | **31.5%** [23.9, 37.7] | .61 |
| MMLU-Pro | 知识 | 58.0% | **23.4%** [17.1, 29.0] | .40 |
| AIME 1983–2024 | 数学 | 29.2% | **14.9%** [10.8, 20.1] | .51 |
| APPS | 代码 | 34.4% | **16.8%** [4.2, 30.4] | .49 |
| BigCodeBench | 代码 | 10.0% | 0.4% [−9.5, 9.1] | .04 |
| CodeContests | 代码 | 35.8% | **9.4%** [0.4, 19.8] | .26 |
| SuperGPQA | 知识 | 60.6% | **33.0%** [14.6, 45.7] | .54 |
| BIG-Bench Extra Hard | 混合推理 | 38.1% | **23.5%** [9.4, 35.2] | .62 |

解读：8/9 数据集上完美知识能省 29–61%，本方法捕获其中的四成到近七成。**BigCodeBench 是唯一失败者，但败因是 headroom 本身只有 10%**（其任务是库调用函数生成，解法短而相似）——无蛋糕可分，而非不会切蛋糕。

绝对成本视角（LiveCodeBench）：本路由器以 deepseek-v4-flash **49% 的成本达到其 90% 的精度**，而中位数定价需要 69%。

### 5.2 对外部估计器的全面胜利

72 项与外部估计器（Prompt-feature GBM、MixLLM 式嵌入、CARROT 式 kNN、Route-To-Reason、ZeroRouter 两种配置、SCX 式单一长度、消融项等）的对比中，本方法**领先 69 项、显著领先 50 项、无一项显著落后**。在 LCB、Omni-MATH、MMLU-Pro 三个主力数据集上，每个外部估计器都要输 14–34 个百分点。

几个有代表性的差距（vs 中位定价的节省 %，本方法 / 对方）：

- vs MixLLM 式嵌入：LCB 27.8 / 16.2；MMLU-Pro 23.4 / 15.5；BBEH 23.5 / −1.3
- vs ZeroRouter（己方成功预测）：LCB 27.8 / 16.8；BBEH 23.5 / 18.2
- vs 消融"从成功概率反推长度"：MMLU-Pro 23.4 / 18.4（领先 18.4 点中的一部分）；BBEH 23.5 / 22.6 领先 22.6→即消融只有 0.9 附近

### 5.3 部署场景四连测：少标签、新模型、新基准、混合流量

这是论文实验设计最"接地气"的部分——一个真实路由器不会永远活在全量标注的域内世界。

**（1）少标签**。只用 **20 个标注问题**重训所有成本估计器：本方法保住全量节省的 51–81%（LCB 22.3%、Omni 22.5%、MMLU-Pro 11.9%、SuperGPQA 19.5%、BBEH 14.2%），而所有外部估计器最多只省 10.3%。50 个问题时本方法已接近全量水平（除 MMLU-Pro 外差距 4.0–6.7 点）。

**（2）新模型 onboarding**。模型池换血时，新模型只需要 10 个标注样本拟合两个参数（相对其他候选的 log 长度偏移 + 从平均成功 logit 到自身的一层逻辑映射）：4 个数据集省 19.2–26.7%（BBEH 9.7%），在所有数据集上平均领先 ZeroRouter 的 onboarding 流程 5.2–13.0 点。

**（3）零标签迁移到新基准**。整套探针迁到没见过的基准（在同类域的其他数据集上训练，无目标标签）：LCB 保留域内节省的 96%（26.0%），MMLU-Pro 甚至超过域内（26.6% vs 23.4%），APPS 超域内（31.5% vs 16.8%）；4/7 基准保住节省。而"从成功概率反推长度"的迁移差得多——难度到长度的映射跨基准不稳定，但"激活到长度"的映射更通用。

**（4）混合流量**。九个基准混成一锅流量、不给基准身份：单一探针省 31.8%，比"按基准身份给每个基准定中位价"（一个乐观基线，真实系统还得推断基准身份）多省 22.4%，比 MixLLM 多省 14.9%。这说明探针捕获的信息**超过基准身份加难度**。

### 5.4 Scout 该多大？

从 Qwen3-0.6B 到 14B：0.6B 的长度预测明显更差（本方法领先 7.3–8.2 点），1.7B 与 4B 相当，**4B 以上收益不再增长而前向成本线性上涨**——14B scout 反而因为自身开销在 LCB 和 MMLU-Pro 上显著更贵（差 7.3–10.5 点）。论文结论：节省在约 2B 处饱和，"4B 以上，更大的 scout 得不偿失"。

### 5.5 控制实验：为什么不是文本嵌入或微调小模型？

- **同尺寸文本嵌入模型**（Qwen3-Embedding-4B）：无论用什么探针读它，都比 scout 激活差 6.8–23.1 点——嵌入模型为语义相似度优化，丢掉了"生成轨迹"信息；
- **全量微调小编码器**（DistilBERT 66M / jina 137M / Qwen3-0.6B）：比冻结+线性探针差 6.5–25.6 点。有趣的对照：**同一个 Qwen3-0.6B，冻结+线性探针打败了它的微调版**——与 Kumar et al. (2022) "微调会扭曲预训练特征"的结论一致。

## 六、效果优势的根源解释

### 6.1 因果链：方法差异 → 机制变化 → 指标提升

**方法差异**：本方法用冻结生成式 LLM 的 prefill 激活 + 每候选线性探针；对照方法要么用文本嵌入模型（MixLLM/CARROT/Route-To-Reason），要么微调小编码器，要么用 prompt 表面统计特征（GBM），要么从难度分箱间接定价（ZeroRouter）。

**↓**

**机制变化**：scout 的激活在"读题"过程中同时编码了三样东西——(a) 问题的难度，(b) 该问题对各候选模型意味着多长的推理（含候选间长度差异），(c) 任务的格式特征（如 BBEH 的 23 种任务格式）。而文本嵌入只保留语义聚类信息（哪类问题像哪类问题），微调编码器则会在小数据上扭曲预训练特征，GBM 的 44 个手工统计量（长度、行数、数字个数……）更是只看表面。一个关键佐证：SCX 式消融（同一激活、但每个 query 只预测一个跨候选共享长度）在 LCB/Omni/MMLU-Pro/AIME 上少省 8.8–21.1 点——**说明 scout 激活里确实有"候选间差异"信息，逐候选探针把它挖了出来**。

**↓**

**指标提升**：(a) log 长度预测的 R² 在所有数据集所有候选上超过所有预生成估计器（如 LCB 上 .71–.75）；(b) 匹配精度下省钱 9.4–33.0%，72 项对比 69 项领先；(c) 尤其在长度与难度脱钩的 MMLU-Pro 上，专门长度探针比"从成功反推"多省 18.4 点——那里成功信号无法替代长度信号，而文本类方法都隐式依赖"难度→长度"的映射。

**两个结构性根源**（论文诚实地承认了方法不是魔法）：

1. **池子里需要一个"便宜且能解相当比例问题的候选"**：去掉 gpt-oss-20b-low 后，LCB 节省从 27.8% 崩到 6.5%。省钱本质上是"把简单题从贵模型手里抢回来派给便宜模型"——没有便宜模型接盘，就没有节省可言。
2. **需要一个长度方差大的强候选**（deepseek-v4-flash）：它的输出长度在不同问题上波动巨大，正是逐 query 定价的用武之地。但去掉它换入其他三族模型后，LCB 仍省 29.5%，说明不依赖特定模型。

另一个常被质疑的解释——"省钱是不是只是价格差？"——被否定了：把所有候选按同一 token 单价计费、保留真实长度，本方法仍在 LCB/Omni/MMLU-Pro 上省 13.3%/14.3%/36.3%。

### 6.2 两类失败的机制剖析

- **BigCodeBench（无 headroom）**：库调用函数任务，解法短且相似（90/10 百分位长度比仅 2–4），完美知识也只能省 10%。任何估计器都无能为力。
- **CodeContests（有 headroom 但无人能捕获）**：headroom 35.8% 与 APPS 相当，但最好的估计器也只捕获约四分之一。其长度确实由问题决定（问题间方差 .92–.96）且跨候选共享（.67–.88），探针 R² 却只有 .35–.52——竞赛题的难度太难从 prompt 预测。论文还发现 headroom 无法从"长度和价格分布的简单统计量"预测（leave-one-dataset-out R² ≤ .25），**必须实测**——这给从业者一个诚实的提醒：上路由系统前，先花小钱测一下你流量的 headroom。

### 6.3 外部检索交叉验证

为了检验论文结论的独立性与边界，我检索了相关工作：

**（1）相互印证的证据**：

- **Lugoloobi et al. 2026（"LLMs Encode Their Failures", arXiv:2602.09924）**：用生成前激活上的线性探针预测模型自身成功率，探针引导的路由在 MATH 上省约 70% 成本、AIME 上省 37%（[alphaxiv 概览](https://alphaxiv.org/abs/2602.09924v4)、[Lacuna 摘要](https://lacuna.tiptreesystems.com/paper/llms-encode-their-failures-predicting-success-from-pre-generation-activations/art_231a82aec2e04731b90fb116085f79a3)）——独立团队用相似技术（prefill 激活+线性探针）在"成功预测"一侧得到同量级结论，且同样发现该信号显著优于长度/TF-IDF 等表面特征，与本文"激活包含表面文本没有的信息"的机制解释一致。
- **NVIDIA prefill 路由器（Varshney et al., arXiv:2603.20895）**：报道 prefill 激活路由可关闭 45.58% 的精度差距并省 74% 成本（[Ginger Labs 技术博客](https://www.gingerlabs.ai/blog/prefill-activation-routing)）——产业界独立复现了 prefill 激活作为路由信号的有效性。
- **CARROT（arXiv:2502.03261）**：在 RouterBench/SPROUT 上发现"逐 query 成本相对平均成本增益很小"（[论文原文](https://arxiv.org/pdf/2502.03261v2.pdf)）——表面相反，实则与本文互补：其模型池几乎无推理模型，输出长度方差小，正好落在本文"非推理候选 headroom 小 1.3–2.3 倍"的结论区间内。两个工作合起来划定了适用边界：**成本预测的价值随候选池中推理模型的长度方差而伸缩**。

**（2）张力与相反方向的证据**：

- **"长度是不可靠的质量代理"**一线工作（如 ICML 2026 "Think Deep, Not Just Long"，arXiv:2602.13517，[页面](https://icml.cc/virtual/2026/poster/64256)）报告 token 数与精度的相关性可正可负（GPT-OSS-120B 上 token 数与精度平均相关 −0.544）——与本文"知识数据集上长度与难度脱钩"的发现同向，但更激进。这提示"长度探针"捕获的是成本信息而非质量信息，恰好是本文把它用于定价而非评估的正确性佐证。
- **过度思考（overthinking）文献**：LLMThinkBench 系列工作测得推理模型在基础数学上生成约 18 倍于需要的 token（[综述](https://www.edgechat.ai/overthinking-reasoning-models)）；DIET（arXiv:2505.19217）等训练侧工作则把难度感知的长度压缩做进 RL。这些是**供给侧**方案（让模型少写），本文是**路由侧**方案（预测会写多少再定价）——R2-Router（arXiv:2602.02823）走第三条路：把长度当作可控预算，联合选模型+预算，声称成本再降 4–5 倍（[概览](https://alphaxiv.org/abs/2602.02823v2)）。三条路线并不互斥：预测、控制、压缩可以叠加。
- **"路由收益大部分是任务类型"** 的质疑（Li et al. 2026a；Lee 2026 "Most of the LLM Routing Gap Is Task Type"）：静态任务类型分配就能关闭大部分到 per-query oracle 的差距。本文用混合流量实验正面回应：在给定真实基准身份（乐观基线）的定价之上，单一探针仍多省 22.4%——**成本侧的逐 query 信息超越了基准身份**。

**（3）本次检索范围内未发现**：公开的第三方对"跨模型长度共变（.42–.96）"这一具体机制统计的独立复现——该机制发现目前主要来自本文与单模型长度预测文献（ALPS/OUTLETS 等）的间接支持。

## 七、必要知识反推

读懂这篇论文并复现其实验，需要以下知识拼图（按"缺了哪块会卡住"排序）：

**第一层：基础设施与 API（工程门槛）**

1. **LLM API 计费模型**：输入/输出 token 分开计价、不同 provider 对同一开源模型的端点在精度/长度/价格上都有差异（论文钉死 deepseek-v4-flash 到 StreamLake 就是为此）——需要 OpenRouter 级别的多模型调用与账单记录能力。
2. **推理模型的 effort 档位**：同一模型（gpt-oss-20b/120b）的 low/medium/high 档是不同候选——理解"候选 = 模型 × 档位 × 端点"。
3. **HuggingFace Transformers 的输出隐藏状态提取**：`output_hidden_states=True`，取中间 8 层的 mean-pooling 与 last-token 激活。

**第二层：统计与机器学习方法（方法门槛）**

4. **线性探针方法论**：Alain & Bengio (2016) 的传统——冻结表征 + 线性读出，以及"线性可分 ⇒ 信息存在"的推断逻辑。
5. **概率校准（Platt scaling）**：为什么路由公式需要校准概率而非仅排序——V·p̂ 的乘法结构对概率尺度敏感。
6. **log 变换的再变换偏差与 Duan smearing**：E[exp(log y)] ≠ exp(E[log y])，回归对数长度后直接指数化会系统性低估——计量经济学的经典修正。
7. **配对实验设计与 bootstrap 推断**：匹配精度比较、上凸包前沿插值、配对 bootstrap 区间、多训练集平均。
8. **方差分解**：把 log 长度方差拆成"问题间 vs 采样间"、用其他候选长度做 R²——机制分析的全部统计工具。

**第三层：评测领域知识（数据门槛）**

9. **九个基准的领域能力**：LCB/APPS/BigCodeBench/CodeContests（代码）、Omni-MATH/AIME（数学）、MMLU-Pro/SuperGPQA（知识）、BBEH（23 种混合格式任务）——特别是各基准的评分器（代码执行 vs 答案匹配）。
10. **路由评测协议**：RouterBench 建立的前沿比较方法论、随机混合基线（凸包上任一点可用固定概率混合达到——路由器必须打败它才算有用）。

**第四层：论文的隐性前提**

11. 每个候选需要少量输出长度标注（几十个样本），标注来自真实调用记录——**没有历史调用数据的团队需要先花一笔"标注预算"**。
12. 价格与 provider 行为随时变化（论文的账单价格几天内就会漂移），复现的是方法而非具体数字。

## 八、通用性灵感

即使你不做模型路由，这篇论文的方法论视角也值得带走。以下七条灵感按"离你项目的距离"从近到远排列：

### 灵感一：先测 headroom，再上系统

论文最朴素也最通用的一条工程纪律：任何优化系统上线前，先测量"完美信息能带来多少收益"（headroom）。如果完美知识只能省 10%（BigCodeBench），再聪明的估计器也是白费——**先算蛋糕多大，再决定要不要买刀**。这个思路适用于缓存替换、负载均衡、任何"预测 X 以优化 Y"的系统。

### 灵感二：方差结构决定预测策略

"问题间方差占 .71–.99 ⇒ 一份共享特征 + 每目标轻量探针就够"——这是一个可直接迁移的推理模式：**先做方差分解，看信号主要在实体间还是实例间**。如果主要在实体间（本题 vs 他题），一个共享编码器就能服务所有预测头；如果在实例间（同题不同采样），任何预生成预测都注定失败。很多预测任务的可行性争论，其实一次方差分析就能终结。

### 灵感三：相关性的边界条件要主动划定

"长度≈难度"在数学/代码上成立、在知识/混合格式上崩塌——论文没有停留在平均值结论，而是系统划定了每条相关性的适用域。做特征工程时同样要问：**我依赖的这层相关关系，在哪个数据子空间会失效？**失效的地方往往就是专门化组件（这里是长度探针）的价值所在。

### 灵感四：冻结大模型 + 线性头，是被低估的基线

全量微调的 Qwen3-0.6B 输给了冻结的自己加线性探针。在小标签量场景（几十到几百样本），"冻结预训练模型 + 线性读出"应该成为默认起点而非可选项——它更快、更稳、不会扭曲预训练特征，还顺便给你可解释性。

### 灵感五：零增量复用是部署的关键杠杆

成本探针对已有 prefill 路由器是零额外推理开销（激活已存在）。设计系统时优先识别"**哪些昂贵中间产物可以服务多个下游**"——一份激活喂成功、成本、难度多个探针，比每个任务单独跑编码器优雅得多。

### 灵感六：把"评估条件"当作实验变量

论文的三条件设计（无模拟器证据/扰动证据/参考证据）证明了：**改变证据、固定任务，能把"能力"和"证据利用能力"分离开来**。任何依赖外部信号（工具返回、检索文档、模拟器输出）的 agent 系统都值得做这个三明治实验——你在测的可能不是模型能力，而是证据质量。

### 灵感七：诚实的失败分析比胜利更有信息量

论文用同等篇幅解剖了两类失败（无 headroom / 有 headroom 无人能捕获），并给出"headroom 不可从简单统计量预测，必须实测"的反结论。写论文或做技术报告时，**划定方法的失效边界是与展示峰值成绩同等重要的贡献**——它直接决定下一个人该不该在你的方向上继续投入。

## 结语

这篇论文讲了一个"把成本当作一等公民"的故事：在推理模型让输出长度方差爆炸的时代，固定均价定价浪费了 29–61% 的潜在节省，而一个 4B 冻结模型的 prefill 激活加上每候选一个线性头，就能以 19–28 毫秒的代价捕获其中的四到七成。它的价值不在某个单点技术——线性探针、Platt 校准、smearing 修正都是教科书内容——而在于**问题定义的时机（推理模型主战场）、实验设计的完整度（上下界锚定+四类泛化+机制分析）和对失效边界的诚实**。对从业者，最有行动价值的也许是那条最朴素的建议：先花小钱测一下你流量的 headroom，再决定要不要造这个侦察兵。
