## 一、论文背景

### 1.1 编码 agent 与 SWE-bench 式评测：只看"做没做对"

过去两年，"编码 agent"（coding agent）从代码补全助手进化成了能独立干活的软件工程师：给它一个真实 GitHub 仓库和一个 issue 描述，它会自己搜代码、读文件、改代码、跑测试、提交补丁。支撑这类评测的是 [SWE-bench](https://arxiv.org/abs/2310.06770)（ICLR 2024）一族的基准——从真实开源仓库收集 issue 与对应的测试用例，agent 生成的补丁只有通过测试才算"解决"，汇总成**解题率（solve rate / resolve rate）**。

这个范式极其有效，排行榜因此繁荣。但它有个与生俱来的盲区：**执行过程是黑箱**。两个解题率都是 45% 的 agent，一个可能像谨慎的老工程师——反复浏览代码、小步修改、频繁回归测试；另一个可能像赌徒——粗暴全局替换、只跑一次目标测试就提交。解题率完全无法区分这两者。

社区也早有不满。[AI Agents That Matter](https://arxiv.org/abs/2407.01502)（TMLR 2025）批评 agent 基准忽视成本与可复现性；[AgentLens](https://arxiv.org/abs/2605.12925) 揭示了 SWE-agent 评测中的"侥幸通过"（lucky pass）问题；[On Randomness in Agentic Evals](https://arxiv.org/abs/2602.07150) 则量化了同一 agent 重复运行的随机波动。这些工作都指向同一件事：**单一的二元结果指标不足以刻画 agent**。

### 1.2 轨迹分析为什么难：异构 harness 的"方言"问题

要看过程，就得分析**执行轨迹（trajectory）**——agent 与环境交互的完整记录：每一步的工具调用、命令、输出。但轨迹分析有个棘手的工程问题：不同 agent 框架（论文称之为 **harness/脚手架**，如 SWE-agent、Claude Code、Codex）暴露不同的工具、用不同的命令格式、按不同的 schema 记录交互。

举论文里的真实例子：同样是"编辑文件"，Claude Code 的 agent 走原生 Edit API；SWE-agent 里的 agent 可能用 `cat << 'EOF' > file.py` 的 shell 重定向；GPT 系模型则爱写一段内联 Python 脚本做程序化替换。如果直接按工具名或原始命令对比，你比较的不是"agent 在做什么"，而是"框架怎么记录这件事"——**语义动作被实现细节污染了**。

### 1.3 数据基础：SWE-rebench 的持续评测语料

要在跨框架的大尺度上做这件事，还需要数据。作者所在的 Nebius 团队维护着 [SWE-rebench](https://arxiv.org/abs/2505.20411)：一条从最新 GitHub 活动自动收集任务、构建隔离测试环境的流水线，专门对抗数据污染（任务持续更新，模型没机会在训练时背过答案）。其排行榜对每个模型-任务组合跑多次独立 rollout，积累了海量的原始轨迹。这些轨迹以往只用来算解题率——本文把它们变成了研究对象本身。

**一句话总结动机**：解题率告诉你 agent 考了多少分，本文要回答的是——它是怎么答题的？不同 agent 的"答题风格"差异是真信号还是噪声？这种风格能不能反过来标识一个 agent？

## 二、论文定位和关联工作

论文的 Related Work 部分梳理了四条研究脉络，结合外部检索，可以扩展成如下谱系：

### 2.1 基准与评测方法论批评

- **[SWE-bench](https://arxiv.org/abs/2310.06770)**（ICLR 2024）：确立了"真实 issue + 测试验证 + 解题率"范式，是本文数据的上游生态。
- **[AI Agents That Matter](https://arxiv.org/abs/2407.01502)**（TMLR 2025，Kapoor et al.）：系统批评 agent 基准忽视成本、可复现性与统计严谨性，倡导多维评测。本文"把行为作为评测维度"的立论直接呼应这一主张。
- **[On Randomness in Agentic Evals](https://arxiv.org/abs/2602.07150)**（Bjarnason et al., 2026）：量化了同一 agent 重复 rollout 间的行为发散。本文的 split-half 零假设校准正是为了把"真差异"与这种随机波动区分开。
- **[SWE-rebench](https://arxiv.org/abs/2505.20411)**（Badertdinov et al., 2025）：本文的数据来源与反污染评测基建，一作连续工作。

### 2.2 过程级分析（process-level analysis）

这是与本文最贴近的脉络：不看最终 pass 率，看中间执行模式。

- **[Understanding Software Engineering Agents](https://arxiv.org/abs/2506.18824)**（Bouzenia & Pradel, ASE 2025）：对 thought-action-result 轨迹做人工行为研究，规模较小、依赖人标。
- **[AgentBoard](https://arxiv.org/abs/2401.13178)**（Ma et al., NeurIPS 2024）：提出多轮 agent 的分析式评测板，覆盖中间进度等细粒度指标，但面向通用 agent 任务而非 SWE。
- **[What Resolve Rate Hides](https://arxiv.org/abs/2607.06184)**（Shu et al., 2026）：标题几乎就是本文论点的同义反复——用轨迹结构诊断揭示解题率掩盖的信息。
- **[Beyond Resolution Rates](https://arxiv.org/abs/2604.02547)**（Mehtiyev & Assunção, 2026）与 **[Understanding Code Agent Behaviour](https://arxiv.org/abs/2511.00197)**（Majgaonkar et al., 2025）：分别用主题建模与成功/失败轨迹对比研究行为驱动因素。
- **[How to Interpret Agent Behavior](https://arxiv.org/abs/2605.13625)**（Gao et al., 2026）：提出人工校验的行为词汇表。

### 2.3 失败诊断与归因

- **[TrajAudit](https://arxiv.org/abs/2605.26563)**（Wang et al., 2026）：参考感知信号定位失败点。
- **[Failure as a Process](https://arxiv.org/abs/2607.09510)**（Zhao et al., 2026）：把错误累积与恢复建模为动态过程。
- **[Model or Harness?](https://arxiv.org/abs/2607.28802)**（Raj et al., 2026）：论证 agent 能力绑定于 harness/工具/运行时的整体，而非孤立模型权重——与本文"agent stack"概念高度共鸣。

### 2.4 本文的位置

| 维度 | 之前的路线 | 本文的突破 |
|---|---|---|
| 分析尺度 | 小规模人工研究（数百轨迹）或单框架内分析 | **143,209 条轨迹、125 配置、117 模型**的跨栈大尺度分析 |
| 可比性 | 按工具名/原始命令对比，跨框架不可比 | **规则 parser 归一为语义动作分类**，跨 harness 可比 |
| 实验控制 | 直接对比，混淆性能差异与行为差异 | **outcome-matched 配对 + split-half 零假设校准**，隔离出纯行为差异 |
| 研究问题 | 描述行为或诊断失败 | 额外验证**行为画像可跨库跨语言检索部署栈**（行为即签名） |

**定位结论**：本文不是"又一个轨迹分析"，而是第一条在受控配对设计下、跨异构框架证明"解题率不唯一刻画行为"的大规模实证证据链，且全部工具开源、可复现。

## 三、问题定义

### 3.1 从具体场景到抽象问题

**具体场景**：排行榜上两个解题率相同的 agent，行为到底一不一样？如果不一样，差异是真信号还是随机波动？这种行为模式能不能作为 agent 的"指纹"？

论文的**核心洞察**在于一个深层结构相似性：**agent 行为画像 ≈ 文档的词频主题向量**。正如一段文档的主题可以由其词分布刻画、且这个分布在不同章节间保持稳定，一个 agent 的"操作风格"可以由其动作分布刻画，且这个分布应当在不同的代码仓库、不同的编程语言间保持稳定——因为风格来自 agent 栈本身（模型习惯 + harness 约束 + 推理力度配置），而非来自任务。

### 3.2 形式化定义

论文实际求解的是三个递进的问题：

1. **归一化问题**：给定异构轨迹事件 $e$（shell 命令/API 调用 + 执行输出对），求确定性映射 $f: e \mapsto (op, role, mut, read)$，其中 $op \in$ 10 类主操作、$role$ 为目标文件角色、$mut$ 为变更类型、$read$ 为读取模式——**约束是 $f$ 必须不依赖 harness 特定元数据**，只看命令与输出的语义内容。

2. **行为分化检验问题**：给定配对集合 $\{(A_i, B_i)\}$，其中每对的两个 agent 栈共享 scaffold 且 $|\Delta solve| \le 1$pp（≥50 共享任务），在六项工作流指标上检验 $A_i$ 与 $B_i$ 的分布差异是否显著超过**同一配置自身随机分裂**（split-half A/A 检验）的差异。

3. **行为签名检索问题**：给定 agent 栈 $s$ 在仓库集 $R_1$ 上的聚合行为向量 $\phi(s, R_1)$（8 维，**严格排除**解题结果、token 数、原生工具名），在 $R_2$（与 $R_1$ 不相交）上的一组候选向量中做余弦最近邻检索，问能否找回 $s$ 自己。随机基线为 $1/N$。

### 3.3 这个抽象的精妙之处

- **排除法设计**：特征向量刻意排除一切"结果性"与"标识性"信息（结果、token、工具名），剩下的只有"过程风格"。如果检索仍然成功，那就证明执行风格本身就是栈的签名——这是干净的反证法式设计。
- **A/A 校准**：用同配置自身分裂作为经验零假设分布，回答了"行为差异会不会只是随机波动"这一必然质疑——这是统计上最扎实的一步。
- 论文也很诚实：跨仓库检索无法完全控制任务组成差异（confound），作者在正文与结论中反复标注这一点，不把结论说过头。

## 四、问题解法

整个研究管线可以类比为"给 14 万条执行录像做统一的动作编码，然后做对照实验"。按数据流分四步：

### 4.1 第一步：规则 parser——把"方言"翻译成"普通话"

**类比**：就像把不同医院的病历格式统一编码成 ICD 疾病代码，parser 把异构轨迹事件编码成统一动作分类。

输入是一条工具调用及其执行输出（原始命令 + stdout/exit code），parser 用**确定性规则匹配**（正则 + 路径启发式，无 LLM 参与、可完全复现）输出四个正交属性：

| 属性 | 取值 | 例子 |
|---|---|---|
| **主操作**（10 类） | exploration / search / file reading / file mutation / formal test / workspace inspection（git diff/status/show）/ package build / other / no-repo-op / unknown | `pytest tests/test_x.py -q` → RUN_FORMAL_TEST |
| **目标文件角色** | 非测试文件 / 常规测试文件（`tests/`、`test_*`、`*_spec`、conftest 等启发式）/ 混合 / 未解析 / 不适用 | 修改 `src/api.py` → non-test |
| **变更类型** | create / edit / delete / mixed | `rm foo.py` → delete |
| **读取模式** | 直接读 / 视口续读；read_scope 另分全文件 vs 有界行区间 | `sed -n '1,800p' file.py` → 有界行区间读 |

两个关键计数口径：**动作总数**包含所有尝试过的调用（含格式错误与被拒绝的）；**动作占比**只算执行成功的语义操作（排除 UNKNOWN 与非仓库操作）。这个区分很重要——前者度量"努力总量"，后者度量"精力分配"。

### 4.2 第二步：六项工作流指标——把动作序列压缩成可比较的数字

| 指标 | 定义 | 衡量什么 |
|---|---|---|
| 操作动作数 | 每次 rollout 的非终止工具调用总数（含失败尝试） | 交互总量/努力程度 |
| 探索占比 | 探索+搜索+读文件占语义动作比例 | 多少精力花在"看"上 |
| 非测试仓库写入 | 无失败迹象的非测试文件修改次数 | 有效产出节奏 |
| 正式测试调用 | 识别出的测试框架调用次数 | 验证频率 |
| 连续重复失败 | 相邻同签名失败次数（签名=归一化命令+排序路径） | 卡壳/循环倾向 |
| 无产出尾部 | 最后一次有效动作（写入或通过测试）之后的尝试数 | "做完还在磨蹭"的浪费 |

其中"连续重复失败"的计数规则设计得相当精细：`(A,fail)→(A,fail)→(B,fail)→(A,success)→(A,fail)` 这个序列只记 1 次重复失败——严格相邻、同签名、成功会重置计数器，避免把"重试后成功"的正常迭代误判为循环。

### 4.3 第三步：LLM 共识审计——不请人来标注，请六个模型投票

规则 parser 的标签可信吗？传统做法是人工标注抽样验证，14 万条轨迹显然标不动。论文的替代方案：**六模型共识面板**（claude-opus-5、gpt-5.6-sol、gemini-3.7-flash、Kimi-K3、DeepSeek-V4-Flash、MiniMax-M3），在分层抽样的 500 个动作上盲评（隐藏 parser 预测与任务结果），**≥5/6 模型一致才产生参考标签**，再算 parser 与之一致率。

结果（Table 1）：主操作一致率 82.4%（Macro-F1 88.8%）、读模式 96.6%、目标文件角色 77.0%、变更类型 68.8%、四字段全对的精确匹配率 77.5%。作者据此明确降级了路径解析相关指标的置信度——凡强依赖路径解析的指标（如非测试写入数）只作"诊断代理"而非断言。这种诚实的不确定性标注本身就是好科学的示范。

### 4.4 第四步：两类实验设计

**outcome-matched 配对 + 零假设校准**：找同 scaffold、解题率差 ≤1pp、共享 ≥50 任务的模型对（共 60 对），比较六指标差异（任务级配对 95% bootstrap CI）。同时做 **split-half A/A 检验**：把同一配置的多次 rollout 随机对半分裂（100 个随机种子），量出"自己 vs 自己"的固有波动作为基线。

**行为画像检索**：8 维画像 = 4 个归一化动作坐标（探索、读文件、非测试写、正式测试）+ 4 个序列/验证特征（归一化动作熵、工具切换率、写后工作区检查、未验证终止）。413 个 Python 仓库对半分，111 个栈在 A 半库算画像，到 B 半库做余弦最近邻检索；多语言场景用 12 维画像做 3-vs-2 语言拆分（共 10 种拆法、320 个方向查询）。

一个容易被忽视的细节：**检索完全不使用任何工具名**（多语言特征中工具身份仅用于区分 shell/非 shell 残差类），也排除 token 与动作总量——防止"靠工具名认人"这种平凡解。

## 五、评估指标与实验证据

### 5.1 主实验一：解题率相同，行为分化（Table 2 + Figure 2）

60 对 outcome-matched 配对中：

| 分离标准 | split-half 零假设（同配置自身分裂） | 真实匹配对 |
|---|---|---|
| ≥1 项指标显著分离 | 30.53% | **100%** |
| ≥2 项指标显著分离 | 6.40% | **100%** |
| ≥3 项指标显著分离 | 0.781% | **96.7%** |

这是全文最硬的一张表：如果行为差异只是随机波动，≥3 指标同时分离的概率不到 1%；而真实配对中 96.7% 都做到 ≥3 指标分离。**"解题率不唯一刻画行为"由此从直觉变成了统计事实。**三个案例研究进一步展示：即使双方五次 rollout 全部解题成功，差异依然巨大（如任务 pypsa-1653 上 Opus 5 用 62.4 个动作、48.4% 走 shell 重定向编辑、跑 12.4 次测试；GPT-5.6 Sol 用 15.0 个动作、100% 内联 Python 编辑、只跑 3.4 次测试）。

### 5.2 主实验二：行为画像跨库跨语言检索部署栈（Table 5/7/8）

| 设定 | 特征 | Top-1 | Top-3 | 随机基线 |
|---|---|---|---|---|
| 跨仓库（111 栈，413 库对半分） | 8 维全画像 | **85.1%** | 96.8% | 0.9% |
| 同上 | 仅动作坐标（4 维） | 62.6% | 86.5% | 0.9% |
| 同上 | 仅序列/验证特征 | 56.8% | 79.7% | 0.9% |
| 同上 | 限定通用 SWE-agent harness（107 栈） | 85.5% | 97.7% | ~0.9% |
| 跨语言（16 栈，Go/Java/Python/Rust/TS，10 种 3v2 拆分） | 12 维全画像 | **90.3%** | 98.8% | 6.25% |
| 同上 | 仅动作组成（10 维） | 87.5% | 98.4% | 6.25% |
| 同上 | 仅过程动力学（熵+切换率） | 36.3% | 71.9% | 6.25% |

三条关键读数：

1. **消融揭示信息载体**：判别信号主要由动作组成携带（87.5%），熵/切换率只是边际补充（36.3%）——是"精力怎么分配"而非"节奏多乱"在标识 agent。
2. **限定同 harness 后仍 88.5%**：排除了"靠 scaffold 工具语法认人"的平凡解释，签名来自栈本身的操作风格。
3. **跨语言比跨库还高**（90.3% vs 85.1%）：语言变了、任务变了，风格不变——强烈支持"操作签名属于 agent 栈"的解读。但论文同时明确警示：跨仓库设定未完全控制任务组成，检索性能可能部分来自任务组成差异，不能据此宣称"任务无关的行为签名"。

### 5.3 主实验三：什么因素在系统性地移动行为（Table 3/4/12）

- **代际演化**：Claude Opus 4.6→5，`sed -n` 行级读取从 6.9% 升至 57.7%，`pytest -q` 静默测试从 22.7% 升至 99.8%；GPT-5.4→5.6 Sol 总动作从 24.4 压缩到 12.8，72.1% 的编辑走内联 Python——新一代模型在"压缩交互、精确定位、减少输出噪声"方向上收敛。
- **推理力度**：Opus 4.8（Claude Code）从 Low 到 xHigh，总动作 31.3→54.4，其中探索与阅读 +12.71（占增量 55.2%），写后工作区检查比例 12.7%→66.8%，而**无产出尾部几乎不变**（−0.5，CI 含 0）——更多思考换来的是更多检查而非更多空转。
- **scaffold 塑形**：Opus 4.7 在 Claude Code 下 92.4% 编辑走原生 API，在 SWE-agent 下只有 37.0% 走原生编辑、大量落到 shell 重定向与 Python 脚本；GPT-5.5 在 Codex 下 54.6% 编辑走 Python 脚本——同一模型在不同 harness 里表现出几乎不同的"肌肉记忆"。

### 5.4 实验设计为何能证明论点

这套证据链的过人之处在于**每一步都有对应的"平凡解释"被排除**：差异会不会是随机波动？→ split-half 零假设给出 0.78% vs 96.7% 的对照。检索成功会不会靠工具名？→ 特征里根本没有工具名，限定同 harness 依然成功。parser 标签可信吗？→ 六模型共识审计给出分字段一致率，弱项指标降级处理。唯一的缺口（任务组成混淆）作者自己也点明了——这比许多基准论文严谨得多。

## 六、效果优势的根源解释

本文是实证分析型论文，其"效果"是论证力度。以下按模板要求分三小节，对核心结论"解题率相同的 agent 行为可稳定分化"做根源解释与外部交叉验证。

### 6.1 根源机制与证据链

**因果链**：harness 定义的动作空间不同 + 模型训练出来的命令偏好不同 + 推理力度配置不同 → agent 在"探索/编辑/测试/验证"四个环节上的资源分配策略不同 → 六项工作流指标系统性分化 → 相同的解题率只是"殊途同归"，而"途"本身是可测量、可复现的签名。

拆开来看每一环：

1. **harness 决定动作空间**（论文实验已支持）：Table 4 直接显示同一模型在不同 scaffold 下编辑机制剧变（92.4% vs 37.0% 原生编辑）。机制上，harness 提供的工具菜单就是 agent 的"可行动作词汇表"，词汇表不同，表达必然不同。这与 [Model or Harness?](https://arxiv.org/abs/2607.28802) 的"能力绑定于交互整体"结论一致。
2. **模型决定命令偏好**（论文实验已支持）：Table 3 的代际数据显示每个模型家族有稳定的命令习惯（GPT 系爱内联 Python、Claude 系转向 sed -n 行级读），且这种偏好跨仓库跨语言稳定（检索实验 85-90% 成功本身就是稳定性的证明）。
3. **同解率掩盖路径差异**（论文实验已支持）：60/60 配对在 ≥2 指标分离、96.7% 在 ≥3 指标分离，而零假设下 ≥3 指标分离仅 0.78%——分化远超噪声，不是统计假象。
4. **"行为特征 ≈ 风格签名"的泛化性**（论文实验部分支持 + 阅读者推测）：跨语言检索成功说明签名主要来自栈而非任务；但跨仓库检索的任务组成混淆未被完全控制，"签名完全任务无关"仍是推测，作者自己也如此声明。

**反事实检验**：如果去掉"排除工具名/token/结果"的设计，检索当然会更容易，但那只能证明"工具名能认人"（平凡解）；论文的排除法设计正是为了让"纯风格也能认人"这一强命题成立。如果去掉 split-half 校准，60/60 的分离率就无从区分真差异与噪声——0.78% vs 96.7% 的对照是该结论统计意义的全部来源。

### 6.3 综合判断与未决问题

**多研究共同支持的机制**：(a) 解题率/结果指标不充分（本文 + Resolve Rate Hides + Beyond Resolution Rates + AgentLens 独立收敛）；(b) 行为签名可标识 agent（本文 + Oderinwale + GitHub 指纹工作，方法不同结论一致）；(c) harness 强塑形行为（本文 + Model or Harness?）。

**仍属推测的部分**：行为差异是否与能力差异因果相关（本文只证明分化存在，未证明哪种风格"更好"）；签名是否在分布外任务（非 SWE、真实工业场景）中稳定——论文承认单一基准 regime 的局限，模型可能识别出评测环境本身。

**优势成立条件与失效条件**：结论在"多 harness、多模型、真实仓库任务"的评测语料内成立；若任务组成与栈强相关（某些栈只跑某类仓库），检索性能可能被夸大；若未来模型显式模仿其他栈的风格，或 harness 完全统一工具接口，签名判别力可能下降。

## 七、必要知识反推

假设一个没有任何背景的人要复现这项研究，他最少需要掌握什么？

### 7.1 领域知识层

- **编码 agent 的运行机制**：模型 + harness（工具菜单、记录 schema）+ 推理力度参数如何组成一个"栈"；不理解这一点就无法定义研究单元（stack），也无法解释为何同一模型在不同 harness 下行为不同。
- **SWE 评测生态**：issue → 补丁 → 测试验证 → 解题率的完整链路，以及测试文件 vs 源码文件、正式测试 vs 随手脚本的区别——这直接决定 parser 的目标文件角色分类与"正式测试调用"的识别规则。
- **shell 命令的语义光谱**：`grep`/`find`/`sed -n`/`cat << EOF`/`python - << PY` 各自在做什么——没有这层知识，规则 parser 一行都写不出来。这可能是最容易被忽视但最不可缺的知识：论文本质上是在给 Unix 文本处理习惯做语义编码。

### 7.2 方法论知识层

- **配对实验设计**：为什么要控制 scaffold 与解题率（否则行为差异可能只是性能差异的影子）。
- **A/A 检验与 bootstrap 置信区间**：如何用 split-half 构造经验零假设分布、用任务级配对 bootstrap 检验分离——没有这一步，96.7% 的数字毫无说服力。
- **向量检索与消融**：余弦最近邻、Top-k 召回、随机基线对照、特征消融定位信息载体——这是行为签名实验的方法骨架。
- **标注审计的替代方案**：理解 LLM 共识标注的原理与局限（共识率 ≠ 正确率），才能正确解读 82.4% 这类数字。

### 7.3 工程知识层

- 大规模轨迹解析的工程：确定性规则（可复现）优于 LLM 解析（不可复现）的取舍；解析 14 万轨迹只需 1-2 小时、20GB 内存的单机设计——成本意识贯穿始终。
- 分布式评测基建：SWE-rebench 的容器化隔离环境、每任务 5 次独立 rollout 的数据生产协议（约 205 亿 token、约 $7.1k API 成本）。

### 7.4 知识融合的关键节点

最有创造性的融合点有两个：**其一**，把"异构轨迹不可比"这个工程障碍，翻译成"需要一个语义动作分类学"这个表征问题—— Unix 命令知识 + 分类学思维的化学反应；**其二**，把"agent 重复运行有随机波动"这个已知噪声源（On Randomness in Agentic Evals），反转利用为 split-half 零假设校准工具——把敌人变成尺子，这是全文方法论上最漂亮的一步。

## 八、论文中可以提取的通用性灵感

**灵感一：黑箱结果相同 ≠ 过程相同，评测要给过程留位置。**
论文证据：解题率差 ≤1pp 的 60 对 agent，96.7% 在 ≥3 项过程指标上显著分化，而自身随机分裂仅 0.78%。
推广场景：(1) 自动驾驶评测——到达率相同的规划器，风险行为模式可能天差地别；(2) RAG 系统——检索到相同答案，检索路径与证据可靠性不同；(3) 学生教育评测——答对率相同，解题策略与思维习惯不同；(4) 手术机器人——手术成功率相同，操作创伤路径不同。

**灵感二：把噪声源反转为校准工具（A/A 检验思维）。**
论文证据：用同配置 rollout 的随机对半分裂构造经验零假设分布，量出"差异多大才算真差异"。
推广场景：(1) A/B 测试中先跑 A/A 测试估计假阳率；(2) 模型评测中用同模型多次采样分裂校准指标显著性；(3) 传感器网络中用冗余读数互检估计测量噪声底；(4) 临床试验的随机化安慰剂组本质上是干预效果的零假设校准。

**灵感三：风格即签名——排除结果信息后的过程分布可以标识系统。**
论文证据：不含结果/token/工具名的 8 维画像跨库 Top-1 检索 85.1%、跨语言 90.3%。
推广场景：(1) 作者身份识别（文体学）——词分布签名标识作者，与 agent 动作分布标识栈同构；(2) 代码溯源——编译产物指纹追溯工具链；(3) 异常检测——系统调用分布偏离历史签名即预警；(4) 模型输出水印与检测。

**灵感四：归一化表征是跨体系比较的前提，"排除法"能强化命题。**
论文证据：规则 parser 抹平 harness 方言后才可能跨栈比较；特征里刻意排除工具名/token/结果，防止平凡解，让"纯风格可辨识"这一强命题成立。
推广场景：(1) 多医院电子病历统一编码后才能跨院对比疗效；(2) 日志分析中先做语义动作归一化再比较异常模式；(3) 跨语言文本比较先用主题模型去除词汇表面差异；(4) 任何"排除法消融"设计——把最容易的解法禁掉，剩下的成功才证明深层机制。

**灵感五：标注审计可以用共识替代人力，但要诚实标注其局限。**
论文证据：六前沿模型 ≥5/6 共识产生参考标签，分字段报告一致率（82.4%-96.6%），并主动把弱字段指标降级为"诊断代理"。
推广场景：(1) 大规模内容审核的多人仲裁机制设计；(2) 合成数据质量把关；(3) 任何"金标太贵"场景下的分级置信度标注实践——不把弱证据当强证据用，本身就是可迁移的科学卫生习惯。

## 附录：读这篇文章可以顺手带走的技巧

- `sed -n '1,800p' file.py` 是高效的大文件分段阅读手段（新 Claude 模型 57.7% 的读取走这条路，比全文件 cat 省 token）。
- `pytest -q` 静默模式可大幅减少输出 token（新模型 99%+ 采用）；测试输出膨胀时值得考虑。
- 用内联 Python（`python - << 'PY'`）做程序化文本替换，比 shell heredoc 更不易踩转义坑，且常能压缩交互轮数——这是 GPT 系 72% 编辑选择的路线。
