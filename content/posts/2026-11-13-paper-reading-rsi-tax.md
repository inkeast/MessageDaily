## 一、论文背景

### 1.1 RSI 是什么：不训模型，让 Agent 自己攒经验

LLM Agent 在实际部署中往往是连续干活的：今天在同一个仓库里修第十个 bug，明天在终端里配第五个服务。既然任务之间有相关性，一个自然的想法是——把上次踩的坑记下来，下次别再踩。这就是递归自我改进（Recursive Self-Improvement, RSI）：用智能体自己的任务经验去更新它带到后续任务中的状态，而模型权重保持不变。

按更新的对象，RSI 分两大流派：

- **记忆/技能流**：维护一组不断进化的记忆或技能，供后续任务取用。代表工作有 ReasoningBank（从轨迹中提炼策略记忆并可检索）、Dynamic Cheatsheet（维护一张不断演化的笔记）、EvoSkill（在可复用技能文件夹上做搜索）、更早的 Voyager（把成功代码结晶成技能库）。
- **Harness 流**：直接改 Agent 的执行骨架——提示词、工具接口、控制代码。代表工作有 GEPA（用执行反馈进化指令）、Meta-Harness（在控制器代码上搜索）、RRSI（对 harness 变更加正则约束）。

类比一下：前者像给新员工攒岗位操作手册，后者像直接改公司的标准作业流程（SOP）甚至流水线控制代码。

### 1.2 被忽略的问题：改进过程本身是要花钱的

这些方法汇报成绩时几乎都只看准确率：自进化后 Terminal-Bench 涨了几个点，SWE-bench 涨了几个点。但每次"自我改进"都不是免费的——在支持任务上反复验证候选方案、额外采样轨迹、生成并物化新技能，每一步都在烧 token。更微妙的是，在连续任务流上，每笔更新开销都发生在它的价值兑现之前：你先花一百万 token 验证一个新 harness，然后才知道它对后面几十个任务有没有用。

近期的相关工作开始触碰这个问题：有人在资源约束下比较在线记忆模块与任务级搜索（Hajimiri 等，EMNLP 2026）；有人研究验证任务选择与技能搜索成本的摊销（Task-CoEvolve、SkillMOO）；HarnessPro 和 RRSI 在选择 harness 时已经把执行成本算进目标。但没有人把"改进过程自身的成本"单独拎出来，端到端地核算它到底占比多大、花在哪、换来了什么。

### 1.3 本文的切入点：给 RSI 做一次诚实的审计

这篇论文做的就是这件事。作者提出 **RSI Tax（RSI 税）**：自我改进过程消耗的 token 成本——包括那些最终被拒绝、从未部署的更新尝试。端到端成本 = 任务执行 token + RSI 税。然后在连续任务流上问一个此前没人系统回答的问题：把税算进去之后，昂贵的 RSI 方法还划算吗？

答案是出人意料的否定：一条不超过 2048 token、无搜索、无验证、无嵌入的笔记基线（SRN），在四个模型-环境设置中的准确率全部持平或超过三个昂贵的候选搜索式方法，而总 token 平均省 65.6%–71.0%。

| 维度 | 之前的路线 | 本文的突破 |

## 三、问题定义

### 3.1 从具体场景到抽象问题

具体场景：一个 Agent 在任务流 x1…xT 上连续干活，每完成若干任务就花一些 token 尝试改进自己，然后继续干活。传统评测只问"最后准确率多少"。

核心洞察：**RSI 的价值判断本质上是一个投资决策问题**——更新开销是投资，后续任务的能力增益与执行节省是回报，而投资必须发生在回报兑现之前。这和深度学习里训练成本与推理成本的关系、企业会计里研发费用与营业成本的关系，结构上完全同构：

| RSI 语境 | 深度学习类比 | 企业会计类比 |
|---|---|---|
| RSI 税（验证+探索+写作） | 训练/微调成本 | 研发费用 |
| 任务执行 token | 推理成本 | 营业成本 |
| 端到端总 token | 全生命周期成本 | 总成本 |
| 更新未被后续使用 | 学到的特征没被下游用到 | 研发投入未转化成产品 |

形式化定义：任务流上固定模型参数 θ，状态 st 随更新演化，执行产生轨迹与二元结果 τt ~ πθ(·|xt, st)，yt = V(xt, τt)。更新只许读已完成历史 Ht（公开指令、可见轨迹、标量结果），不许碰未来任务、参考答案、隐藏测试。把模型调用划分为不相交的任务执行集 Ctask 与自我改进集 CRSI，则：

- N_task = Σ n(c)，N_RSI = Σ n(c)，总成本 N_total = N_task + N_RSI
- RSI 税率 ρ_RSI = N_RSI / N_task（100% 意味着改进过程烧掉了和干正事一样多的 token）
- 关键记账规则：花在尝试更新上的 token 一律计入税——即使最终保留了原状态；重新执行已完成任务用于验证的 token 也计入税，不覆盖原有正式结果

### 3.2 这个抽象的精妙之处

两点。第一，"先评分、后入反馈"的流式协议（每项任务的结果在其反馈被用于更新之前就已锁定）从协议层面根除了测试集泄漏——这使 SRN 和昂贵方法之间的比较在信息边界上公平。第二，税率 ρ_RSI 把"改进贵不贵"从绝对数变成相对数，直接可比：税率 300% 就是说你每干一块钱的活，要额外花三块钱自我改进。这两个设计让后续所有反直觉的数字（税超过任务执行本身）变得可解释、可审计。

## 四、问题解法

论文的"方法"由三块组成：记账分解框架、SRN 基线、严格受控的评测协议。

### 4.1 RSI 税的三分解：Verify / Explore / Write

类比研发流程：验证=候选方案的测试试验，探索=调研与头脑风暴，写作=把方案写成文档。

| 类别 | 定义（包含什么） | 各方法的具体归属 |
|---|---|---|
| Verify 验证 | 在已完成支持任务上评估现任/候选以辅助选择：基线验证、候选冒烟测试与进一步验证、既有技能前沿重估 | Meta-Harness 的现任+候选验证；EvoSkill 的初始/新技能/前沿验证；RRSI 的现任+候选验证 |
| Explore 探索 | 收集或分析经验以提出更新：额外任务 rollout、无产物编辑的提案生成、轨迹判断、嵌入调用 | ReasoningBank 的轨迹判断+嵌入；Meta-Harness 的轨迹分析+候选搜索；EvoSkill 的额外 rollout+技能提案 |
| Write 写作 | 创建或修订持久状态：harness 代码、技能、笔记、记忆 | Meta-Harness 候选代码编辑；EvoSkill 技能物化；ReasoningBank 记忆抽取；SRN 笔记分析修订（合并计一处） |

每笔成本只计一次；执行中读取已学状态算任务执行而非税。

### 4.2 后续使用追踪：这笔钱有没有下文

对税中每笔成本，标注其关联的状态或产物在下次重置或流结束前是否被后续任务实际使用——跑了更新的 harness、执行中用到的技能、注入上下文的笔记或记忆。注意这是"使用"标签而非"效果"标签：被使用不证明提升准确率，未被使用也不证明可以无代价删除。

### 4.3 SRN：一条笔记的极简自适应

SRN（Simple Reflection with Notes）基于 Dynamic Cheatsheet 的累积笔记思想裁剪到极简：

- **输入**：上一次笔记 m、公开指令、固定轨迹摘录（每条失败轨迹取前 2 万+后 1 万字符）、标量结果。失败任务由官方标量结果选择——不是模型自判。
- **操作**：每 4 个任务一次更新窗口，把失败任务 F_t 的摘录交给同一骨干模型，产出替换笔记；无效回复则保留原笔记。公式化即 m+ = Limit2048(Gθ(m, Excerpt(F_t)))。
- **硬约束**：笔记不超过 2048 token（超限截断）；无额外采样、无候选验证、无检索搜索、无嵌入。
- **提示词纪律**（值得注意的工程设计）：要求区分观察到的事实与假设；禁止推断隐藏测试或参考答案；禁止替下一个任务解题；零分不构成根因诊断。这些约束把笔记的内容压在"有证据支持的可复用教训"上。

类比：昂贵 RSI 像请了一个内部改进委员会，每四周开一轮评标会（生成候选、答辩、多轮评审）；SRN 像只让一线员工更新一页 A4 纸的经验教训。委员会的开销是委员会自己的，不管最后有没有采纳任何提案。

### 4.4 实验协议要点

- 6 方法（Static / ReasoningBank / Meta-Harness / EvoSkill / RRSI / SRN）× 2 模型（DeepSeek V4.1 Flash、GPT-6 Luna）×（SWE-Chain-Evo 105 位 + Terminal-Bench 2.1 89 任务）= 2328 个评分方法-任务对。
- 仓库流：7 条 15 任务链（Click、CoreDNS、NATS、Fiber、Loki、Istio、Prometheus），链内状态保持、链间重置，每任务从规定快照起步。终端流：89 个异质任务固定顺序，学习状态全程保持。
- 更新节奏统一：每 4 个完成任务一个更新机会（每链 3 次、终端流 22 次），窗口内状态冻结；支持集为最近 2 个任务（DeepSeek/SWE）或最近 4 个（其余设置）。
- 公平性控制：同设置内共享任务顺序、初始 KIRA 智能体、名义执行限额（262144 上下文、100 轮）。EvoSkill 的固定验证集流程被适配为滚动支持集重打分（全部成本记账）；Meta-Harness 部署规则要求严格准确率改进才换 harness。

## 五、评估指标与实验证据

### 5.1 指标体系

| 指标 | 定义 | 方向 | 衡量什么 |
|---|---|---|---|
| A(T) 最终准确率 | 流式协议下通过任务占比 | 越高越好 | 真实服务能力（无测试泄漏） |
| N_total 总 token | 任务执行 + RSI 税 | 越低越好 | 端到端经济性 |
| ρ_RSI 税率 | 100×N_RSI/N_task | 越低越好 | 改进过程相对负担 |
| 三分构成 | Verify/Explore/Write 占税比例 | 诊断 | 钱花在哪个环节 |
| 无后续使用占比 r_no-use | 关联产物未被使用的税占比 | 越低越好 | 投资转化率 |

基准选择理由：SWE-Chain-Evo 提供链内相关任务（经验复用有真实空间），Terminal-Bench 2.1 提供异质独立任务（考察跨任务泛化的经验蒸馏），两者合起来覆盖 RSI 声称有效的两类场景。

### 5.2 主结果：准确率与端到端成本

四设置等权平均准确率：**SRN 59.18% > Meta-Harness 57.10% > EvoSkill 55.35% ≈ Static 54.46% ≈ RRSI 54.94% > ReasoningBank 53.56%**。SRN 在三个设置中准确率最高、第四个与 EvoSkill 并列。

| 设置（准确率% / 总token M） | Static | Meta-Harness | EvoSkill | RRSI | SRN |
|---|---|---|---|---|---|
| DeepSeek / SWE-Chain | 43.8 / 487.92 | 45.7 / 976.61 | 41.0 / 1,166.51 | 44.8 / 1,092.94 | **48.6 / 492.56** |
| GPT-6 Luna / SWE-Chain | 38.1 / 179.69 | 40.0 / 495.81 | 40.0 / 612.39 | 39.0 / 574.07 | **41.0 / 157.07** |
| DeepSeek / Terminal | 69.7 / 185.55 | 77.5 / 762.57 | 71.9 / 898.72 | 74.2 / 605.75 | **78.7 / 214.65** |
| GPT-6 Luna / Terminal | 66.3 / 78.86 | 65.2 / 317.99 | 68.5 / 358.85 | 61.8 / 454.30 | **68.5 / 87.08** |

SRN 相对 Meta-Harness/EvoSkill/RRSI 分别省 65.6%/71.0%/68.2% 总 token；相对 Static 平均准确率 +4.7 个点、token 仅 +3.6%。四设置 token 合计：SRN 951M vs EvoSkill 3036M、RRSI 2727M、Meta-Harness 2553M。

**漏记税会反转成本结论**——论文给出的最有冲击力的例子：DeepSeek 终端流上，Meta-Harness 任务执行 token（184.13M）其实比 SRN（214.37M）更少；但它 578.45M 的 RSI 税把总成本推到 762.57M，是 SRN 214.65M 的 3.5 倍，且准确率反而更低（77.5% vs 78.7%）。只看执行账本，你会得出 Meta-Harness 更省钱的相反结论。

### 5.3 税率与分解

| 方法 | 税率区间（四设置） | 验证占税 | 探索占税 | 写作占税 | 无后续使用占比 |
|---|---|---|---|---|---|
| Meta-Harness | 109%–329% | 74.83% | 18.01% | 5.56% | 52.78% |
| EvoSkill | 144%–393% | 78.13% | 21.65% | 0.22% | 37.91% |
| RRSI | 126%–347% | 93.58% | 2.55% | 3.86% | 23.70% |
| ReasoningBank | 4.5%–7.4% | — | 50.25% | 49.75% | 63.57% |
| SRN | 0.04%–0.36% | — | — | 100% | 0.00% |

三个关键读数：

1. **验证是税的主体**。三个候选搜索式方法 74.8%–93.6% 的税花在验证上。EvoSkill 在 DeepSeek 终端流上仅刷新旧前沿就花 497.45M token——比服务全部 89 个任务（182.26M）还多 2.7 倍。输入 token 占两方法税额约 98.1%，印证重复处理膨胀的执行上下文是主因。
2. **大量投资没有下文**。RRSI 23.7%、EvoSkill 37.9%、Meta-Harness 52.8%、ReasoningBank 63.6% 的税对应产物从未被后续任务使用。Meta-Harness 无使用成本中验证 564.85M、探索 217.60M、写作 69.22M——连没被采用的候选写作也计在账上。
3. **SRN 的 1.21M 税 100% 有后续使用**——笔记每次更新后必然注入后续任务上下文，这是一条结构保证而非运气。

### 5.4 三个病理切片（附录 D）

论文用三条诊断规则解剖了税是怎么浪费的：

- **无提案搜索**：EvoSkill 第 68 任务后一轮，花 58.16M token 重估前沿+补采样两个成功轨迹——没有失败样本触发提案器，整轮零产出，部署保持 iter-skill-7。
- **决策不变验证**：Meta-Harness 第 72 任务后，现任支持集准确率 100%，选择规则要求严格改进——任何候选分数都不可能被接受，但仍花了 60.4 万 token 给候选做冒烟+验证。接受函数在此条件下恒为零，评估纯烧钱。
- **未检索记忆**：ReasoningBank 第 55 任务存了一个 24.2 万 token 的记忆包（判断+抽取），此后 34 个任务零检索。按此诊断，ReasoningBank 终端流 53.1%–61.5% 的税花在从未被检索的记忆构造上。

这三张切片共同说明：税不是被某个环节"合理地"贵掉的，而是搜索-验证范式在流式设置下的结构性浪费。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**对比对象**：Meta-Harness/EvoSkill/RRSI 代表"候选搜索式 RSI"——生成多个候选、在支持任务上验证、择优部署。它们此前有效的原因：部署前验证保证了单调性（不部署更差的版本），离线场景（固定任务集优化、held-out 考试）中这笔验证成本是一次性摊销的。

**根本局限**：流式部署改变了成本结构。滚动支持集要求每个更新窗口都重新验证（EvoSkill 适配版前沿刷新），验证成本 = 候选数 × 支持任务数 × 轨迹成本 × 更新窗口数，随流线性增长；而窗口内任务只有 4 个，验证跑了大量与后续任务无关的程序。更致命的是接受率的饱和：现任 100% 准确后，严格改进规则使一切验证变决策不变（论文实验已支持）。

**SRN 的本质改变**（因果链，逐步标注证据等级）：

1. 更新空间坍缩为单条有界笔记、无候选生成 → 无验证环节 → 税率 0.04%–0.36%【论文实验已支持：SRN 税全部为写作 1.21M】
2. 笔记每次更新后结构性注入后续上下文 → 无使用占比 0%【论文实验已支持】
3. 总成本 ≈ 执行成本，且笔记作为紧凑上下文方向盘可缩短执行：GPT-6/SWE 上 SRN 执行 token 156.67M < Static 179.69M，总成本反比 Static 低 12.6%【论文实验已支持】
4. 失败教训的蒸馏本身提供学习信号（与 ReasoningBank 的发现同向）→ 准确率 +4.7pp【论文实验已支持；但"笔记内容因果性"论文未消融——作者自己声明实验未隔离各设计选择的贡献，此为论文明确的局限】
5. 【阅读者推测】2048 上界是关键：无界笔记会膨胀上下文推高执行成本，论文未做上界消融，此为推测

**反事实推理**：去掉全部学习（Static）→ 平均掉 4.7 个点，说明适应本身有价值；去掉验证循环（SRN vs Meta-Harness）→ 准确率不降反升、成本降 65.6%，说明在评测的流长度内验证循环的收益没有兑现。

### 6.3 综合判断与未决问题

**多项研究共同支持**：（a）更新/学习成本必须进入评测目标（GEPA 摊销成功、Hajimiri、TradeLens、ServeLearnBench）；（b）失败蒸馏是真实的学习信号（ReasoningBank、ExpeL、SRN 一致）；（c）输入端的重复上下文处理是 Agent 成本主导项（本文 98.1% 与 2604.22750 互证）。

**仍属推测**：SRN 的优势在更长任务流上能否保持——链内只有 3 次更新机会，验证式方法的学习曲线可能未展开（论文自己列出该局限）；2048 上界与提示纪律各自的贡献未消融；无使用≠可删除（论文承认归因是描述性的）。

**适用条件与失效条件**：当任务流足够长、候选改进可被大量后续任务摊销、且单次验证便宜（如确定性快速评估器）时，搜索式 RSI 的经济性可能反转（AlphaEvolve 是活例）。反之在短流、昂贵验证、异质任务下，SRN 式有界笔记是结构性占优的。另需注意 alphaXiv 讨论中的提醒：SRN 与昂贵方法并非等预算比较，而是各自实现精度下的观测结论——作者也在原文注明了这一点。

## 七、必要知识反推

假设一个零基础的人要复现这项工作，最少必须知道什么？

### 7.1 领域知识层

- **RSI 方法谱系与各自实现细节**：不知道 ReasoningBank 的判断-抽取-检索回路、EvoSkill 的提案-物化-前沿维护、Meta-Harness/RRSI 的搜索-验证-部署流程，就无法把它们各自的开销正确归类到三个税目——分类错误直接毁掉整个分解分析。
- **流式评估协议**：必须理解为什么"先评分后入反馈"是防泄漏的关键，否则所有准确率数字没有意义。

### 7.2 方法论知识层

- **成本会计的划分不变式**：Ctask 与 CRSI 不相交、每笔成本恰好计入一个税目、重执行不覆盖原结果——这是会计不重不漏的三条公理，来自审计方法论而非机器学习。
- **诚实基线的设计原则**：SRN 的价值在于它是"控制变量"而不是"竞争方法"——作者明确说它不隔离各设计选择的效应。懂得构造极简反例基线（counterexample baseline）是这类审计型论文的核心手艺。

### 7.3 工程知识层

- **大规模评测编排**：2328 个方法-任务对、跨两模型两基准的统一限额（上下文 262144、100 轮）、每 4 任务更新窗口与支持集管理——没有这种工程能力，记账精度（请求身份去重、缓存 token 口径）无法保证。
- **在线适配离线方法**：EvoSkill 原用固定验证集，Meta-Harness 原是种群搜索——把它们适配到滚动窗口并把适配成本全额记账，需要既懂原方法又懂流式部署的边界。

### 7.4 知识融合的关键节点

真正的化学反应在"会计学 × 在线学习"的交叉点：把企业研发费用归集的思想（尝试即入账、拒绝也不豁免）移植到 Agent 更新的 token 记账上，才同时诞生了 RSI 税的定义和"决策不变验证"这类只有审计视角才能发现的浪费模式。第二个节点是"信息边界设计"：先评分后入反馈 + 严格改进规则，恰好制造出饱和接受率这一自然实验，让验证浪费从账面数字变成可复现的病例。

## 八、论文中可以提取的通用性灵感

### 灵感一：投资必须在回报前支付 → 一切自改进系统都需要净收益核算

- **核心思想**：任何"先花成本改进、后兑现价值"的循环（训练、搜索、自适应）都应按 端到端成本 = 执行成本 + 改进成本 评估，而非只看改进后的性能。
- **论文证据**：漏记 578.45M 税使 Meta-Harness 看起来比 SRN 便宜，实为 3.5 倍贵。
- **推广场景**：① 推理模型的测试时搜索（搜索 token vs 准确率增益）；② 自动特征工程/AutoML（搜索预算进总账）；③ RAG 系统的索引更新成本；④ 量化交易策略的回测-实盘改参成本；⑤ 企业研发项目立项审计。

### 灵感二：验证成本随 (候选数×支持任务数×窗口数) 爆炸 → 搜索式改进在短摊销流上结构性亏损

- **核心思想**：候选搜索的验证开销是乘法性的，而收益兑现是线性（甚至更慢）的；摊销长度决定范式生死。
- **论文证据**：EvoSkill 刷新旧前沿 497.45M > 服务整个任务流 182.26M；验证占税 74.8%–93.6%。
- **推广场景**：① 编译器/超参的自动调优（每次评估=一次完整编译或训练）；② 芯片设计空间搜索；③ 供应链策略仿真比选；④ 大规模 A/B 测试的流量成本；⑤ 科学实验的候选筛选（高通量实验的批内验证预算）。

### 灵感三：有界单产物 + 结构性复用 > 无界多产物 + 择优部署

- **核心思想**：把改进产物约束为单一有界对象并强制后续使用，可将"投资转化率"从工程运气变成结构保证。
- **论文证据**：SRN 税 100% 有后续使用、0% 无使用；ReasoningBank 63.6% 的记忆构造从未被检索。
- **推广场景**：① 个人知识管理（一张复盘表 vs 无限收藏夹）；② 代码库文档（一份 ADR vs 散落的 wiki）；③ 会议纪要制度（一页决议 vs 全程录音）；④ 模型缓存策略（单热路径缓存 vs 多级未命中缓存）；⑤ 制造业的标准化作业单更新流程。

### 灵感四：诊断规则让浪费从"平均数"变成"病例"

- **核心思想**：给系统性浪费定义可判定的谓词（无提案搜索、决策不变评估、未检索存储），浪费才可被点名和修复。
- **论文证据**：三条切片规则各自抓到千万级 token 的具体浪费事件，且与总量分解互相印证。
- **推广场景**：① 数据管道的死分支检测；② CI 里永不改变合并结论的必跑测试；③ 缓存中零命中的预计算；④ 广告投放的零转化定向；⑤ 法规合规中的无效申报流程。

### 灵感五：先评分后入反馈——评测协议本身就是防作弊机制

- **核心思想**：数据使用时序（反馈何时可用）比数据划分（训练/测试集）更能决定评测是否被污染。
- **论文证据**：流式协议下六方法信息边界严格一致，比较公平性由协议保证。
- **推广场景**：① 在线推荐系统的防标签泄漏；② 量化回测的时点数据边界；③ 竞赛评测的提交即锁定；④ 渐进式交付产品的反馈隔离；⑤ 自动评分 LLM 的输出缓存时序。
