## 一、论文背景

### 1.1 游戏是视觉智能体的"全能考场"

基于视觉-语言模型（VLM）的智能体近年来在计算机操作（computer-use）和具身任务上进展迅速，但视频游戏对它们提出了更全面的挑战：每一款游戏都有自己独特的画面风格、规则体系和操控方式，智能体必须**从屏幕上推断规则**、**在动态变化的场景中推理**、还要**以精确的时机按键**。相比网页操作"点按钮、填表单"这种离散而缓慢的交互，游戏同时考验感知、长程规划和实时控制——正因如此，游戏经验本身就是训练通用视觉智能体的宝贵数据源。

一个类比：如果说网页任务是"填表格"，游戏任务就是"开赛车"——后者要求你一边看路况（感知）、一边想路线（规划）、一边打方向踩油门（精确控制），三者缺一不可。

### 1.2 获取大规模游戏经验的三条老路及其瓶颈

要让模型从游戏经验中学习，需要**配对"动作 + 明确目标 + 可靠成功信号"** 的轨迹数据。现有三条路径各有硬伤：

| 数据来源 | 代表工作 | 核心问题 |
|---|---|---|
| 人工录制 | MineRL、Atari-Head、Plaicraft | 收集成本极高，规模上不去 |
| 在线游戏视频 | VPT 等 | 视频里**没有动作标注**，需用逆动力学模型或隐动作模型反推；目标和结果只能事后补标 |
| 交互式游戏环境 | GameWorld 等基准 | 目标、动作、验证天然齐备，但**每接入一款新游戏都需要游戏定制工程**，覆盖面受限 |

### 1.3 用编码智能体改造"野生"游戏的诱惑与陷阱

编码智能体（coding agent）看起来能自动化这一切：它们已经能从代码仓库和网站合成可验证环境、能从零写游戏、能写可执行的游戏策略。把互联网上可下载的**现成网页游戏**（itch.io、Newgrounds 等门户上的海量作品）改造成训练环境，只需：在引擎特定代码中定位内部状态，再用它定义任务初始化、进度度量和成功判定。

但这里有个隐蔽的陷阱：**编码智能体自己测试自己造的环境，测不出所有问题**。它用自己设计的输入、读自己暴露的变量——任务可能根本无法完成、进度函数可能永不更新、成功判定可能过早触发，而这些缺陷**只有真正去"玩"的时候才会暴露**。这就是本文的核心动机：环境与玩家必须协同开发（co-development），让"玩"同时充当环境验证与数据收集。

### 1.4 关键概念速览

- **状态探针（state probe）φ(st)**：从运行中的游戏里读出一小组命名变量（如玩家生命值、已交付的铁），**只有打分器读它**；
- **玩家观测（player observation）ψ(st)**：命名字段的集合（如可见物体的位置），只包含人从屏幕上能看到或推断出的信息，**只有代码策略读它**，不含隐藏信息（如未翻开的牌）；
- **进度函数 p 与成功判定 g**：都只读状态探针，因此打分**不需要人类裁判或模型裁判**；
- **Coding Player / VLM Player**：分别通过 ψ 和截图来玩游戏的两种玩家，后文详述。

## 二、论文定位和关联工作

### 2.1 谱系一：交互式游戏基准

- **VideoGameBench**（10 款商业游戏）、**LMGame-Bench**（6 款）：规模小，无状态验证或仅部分支持；
- **GameWorld**（NUS + Oxford，ECCV 2026）：34 款浏览器游戏、170 个任务，通过注入 JavaScript 桥读取序列化游戏状态实现**基于状态的验证**，是本文最重要的外部评测基准。其报告的最强智能体进度仅 41.9%，远低于人类新手 64.1%；
- **PlaySuite**（5,734 款开源游戏）：规模大但用视频-语言裁判评分，非状态验证。

**关键区别**：GameWorld 需要游戏源码可得且手工插桩，Game2Player 则**自动适配任意可下载游戏**，把环境构建本身变成了可扩展的流水线。

### 2.2 谱系二：游戏数据与游戏专用模型

- **VPT / NitroGen / GameScaling**：从人类录像或预训练中学习。GameScaling（米哈游 + 清华，arXiv 2610.28698）用最多 1,600 小时游戏数据做持续预训练，但其结论明确指出"模仿学习有边界，远迁移世界持续存在差距"；
- **PLAYER-1**（腾讯等，arXiv 2610.20584）：172 款游戏的示范 + 16 个合成环境中的 PPO 强化学习，是本文在模型层面的直接竞争对手（PlayerBench 上 19.0 vs 本文 31.2）；
- **GameHorizon Suite** 等 gameplay QA 基准：只测感知不测操作，且离线高分不等于会玩。

**关键区别**：上述工作的数据要么缺动作、要么缺目标、要么缺稠密进度信号；Game2Player 的轨迹从诞生起就带着任务指令和逐步进度值。

### 2.3 谱系三：智能体的环境合成

- **R2E-Gym / SWE-smith**（代码仓库）、**Endless Terminals / Seta**（终端）、**AutoWebWorld / CUA-Gym / WebArena 复刻**（网站）：把现有软件变成可验证环境；
- **AI GameStore**（人类参与生成 100 款游戏）、**GameReplica**（从观察复刻游戏）；
- **POET / OMNI-EPIC / EnvGen**：开放式学习，环境与智能体共同进化。

**关键区别**：开放式协同进化靠智能体自我生成环境，而 Game2Player 的修复反馈来自**两个视角不同的真实玩家玩遍每款现有游戏的每个任务**，且 Builder 修复前必须对照录像核验每份报告。

### 2.4 谱系四：代码策略与特权教师蒸馏

- **Voyager**：代码即策略，在 Minecraft 中维护可执行技能库；
- **π-Distill / 特权信息蒸馏**（ServiceNow 等）：教师拿特权信息，学生只看常规输入；
- **RE-0**：对 Code-as-Policy 智能体做局部验证的递归改进。

Game2Player 中的 Coding Player→像素学生的蒸馏正属于"特权教师"路线：**读状态的代码策略做老师，只看像素的 VLM 做学生**。

### 2.5 谱系五：步级过滤/加权

- **WebSTAR**（arXiv 2512.10962）：对智能体轨迹做步级评分过滤，只保留正确步骤训练，7B 模型超越 UI-TARS-1.5-7B 15 个点。它证明了"轨迹级二值过滤不如步级细粒度监督"；
- Game2Player 的进度加权 SFT 与之精神相通，但权重来源不是模型裁判而是**游戏状态中实测的进度事件**——更客观、零裁判成本。

### 2.6 定位总结

| 维度 | 之前的路线 | Game2Player 的突破 |
|---|---|---|
| 环境来源 | 手工插桩（GameWorld）或从零生成（AI GameStore） | 自动改造**现有野生网页游戏** |
| 验证方式 | 模型裁判（PlaySuite）或人工审计 | 状态探针直接读引擎变量，免裁判 |
| 环境质量保障 | Builder 自测 | **玩家报告 + 录像核验**的协同开发闭环 |
| 数据收集 | 人类录制 / 视频反推动作 | 代码策略重跑（零模型调用）+ VLM 玩家（带注释思考） |
| 训练信号 | 轨迹级 0/1 | **步级进度加权** |

## 三、问题定义

### 3.1 从具体场景到抽象问题

**具体问题**：如何为视觉智能体收集大规模、多样、可验证的游戏经验？

**深层洞察**：环境构建与数据收集不是两个阶段，而是同一件事——**"玩"本身就是对环境最严格的测试**。一个任务如果连玩家都玩不过去，要么环境有缺陷，要么任务定义有误；玩的过程同时产生训练数据与缺陷报告。

**抽象问题**：给定互联网上可下载的野生游戏集合，构造一个三元组流水线（环境 E、玩家 P、蒸馏目标 D），满足：

1. **可验证性**：每个任务的进度 p: φ(st)→[0,1] 与成功 g: φ(st)→{0,1} 只读状态探针，g=1 ⟹ p=1，无人类/模型裁判；
2. **公平性**：玩家观测 ψ 只含屏幕可见信息（防作弊），评分探针 φ 对玩家不可见（防信息泄露）——ψ 与 φ 的分离是"可验证且公平"的同时成立的关键；
3. **可扩展性**：环境修复由玩家报告驱动、闭环自动化，无需人工审计每个环境；
4. **蒸馏有效性**：从混合来源轨迹中，用进度信号给每一步分配权重 w_t，最大化训练出的像素智能体在未见游戏上的进度。

### 3.2 形式化定义

游戏被建模为部分可观测过程：隐藏状态 st、键鼠动作 at、截图 ot。**任务**是四元组 τ = (ι, c, p, g)：自然语言指令 ι、起始例程 c、进度函数 p、成功判定 g。**轨迹** ξ = (τ, {(ot, at, zt, pt)})，其中 zt 是 VLM 玩家的注释与思考。一个 episode 得分取其达到的最好进度 p̄ = max_t pt——**未达成功的尝试也能获得部分分数**。

### 3.3 这个抽象的精妙之处

- φ/ψ 双视图分离，把"打分的客观性"与"玩家的公平性"解耦成两个独立接口，各自可独立审计；
- 进度函数让"部分成功"可度量，使得失败的 VLM 玩家 episode 也有训练价值；
- 报告协议约束（不许要隐藏信息、不许要捷径、不许要更简单的任务）把"环境修复"限制在诚实方向上。

## 四、问题解法

### 4.1 总体循环：Build → Play → Report → Repair

Game2Player 的流水线由四个角色构成（类比：一个自动化游戏工作室——星探、策划、两名测试员）：

| 角色 | 职责 | 输入 → 输出 |
|---|---|---|
| **Scout（星探）** | 从 itch.io、Newgrounds 等门户筛游戏：可单人离线玩、可可靠重启、目标可拆成短任务、状态可读 | 门户 → 候选游戏 |
| **Builder（策划）** | 沙盒化游戏、写状态探针与控制指南、定义任务并冻结计划 | 游戏源码 → 环境 + 任务集 |
| **VLM Player（测试员 A）** | 只看截图玩每个任务，游戏暂停等它思考 | 截图 → 动作 + 一句注释 |
| **Coding Player（测试员 B）** | 为每款游戏写一个 Python 策略，读 ψ 实时玩，不调用任何模型 | ψ → 逐帧键鼠指令 |

循环四阶段：**Build**（Builder 四阶段流程：Discover→Implement→Evaluate→Revise，任务计划一经提出即冻结——难题不许删除或简化，最多退役三分之一）→ **Play**（双玩家玩遍每个任务）→ **Report**（玩家上报缺陷或观测请求，附录像证据）→ **Verify, then repair**（Builder 先回放录像核验报告真伪，标记 fixed / disproved / unresolved，再修复）。环境在所有报告被解决并通过脚本化门检（scripted gate：检查状态契约类型、任务定义与冻结计划一致、固定种子两次重置等）后才被接受。

### 4.2 引擎技能库：让 Builder 会修各种引擎

流水线维护 **13 个技能文件**：1 个 Builder 技能 + 8 个引擎技能（HTML5 capture、Unity WebGL、Flash、PICO-8、GameMaker、Godot、Construct、Defold）+ 4 个策略技能。每个技能是带工具引用的简短指令，例如 Godot 技能会指路用 GDRETools 从 PCK 恢复 GDScript、通过给游戏源码加钩子重建 PCK 来暴露状态。Builder 按检测到的引擎选择技能——这相当于给施工队配备了**八种引擎的"维修手册"**。

### 4.3 双玩家：互补的两位老师

两个玩家看同一个游戏的两个视图，形成互补：

**Coding Player（高效量产型）**：
- 为每款游戏写一个代码策略，只读玩家观测 ψ，逐帧实时运行，**零模型调用**；
- 写好后可换种子无限重跑：重跑成本仅 **$0.13/小时**，而 VLM 玩家每小时游戏成本 $3.2～$54.7（GPT-6.1 Sol 达 $54.7）——写策略花 $10.8 后，**12 分钟即回本**；
- 每小时墙钟时间记录 **7,775 个 harness 步**，是 VLM 玩家（354 步）的 **22 倍**（因为游戏为 VLM 暂停等决策）；
- 提供了训练数据中 **87.7% 的步**（1,372.1K / 1,563.6K），其精确计时的按键与长按（timed holds）是学生模型学会时机控制的范本。

**VLM Player（言传身教型）**：
- 通过统一 harness 只看截图 ot 玩游戏，游戏每步暂停；输入含任务指令、当前截图、近期步骤与 Builder 写的控制指南；输出一个动作 + **一句"为什么"的注释**（保留原生 thinking）；
- 其 episode 格式与评测时完全一致（暂停式、截图输入），且覆盖代码策略完不成的任务；
- 样本效率高：仅 0.19M 样本就把 4B 模型从 12.7% 拉到 25.1% 进度（代码策略 1.37M 样本只到 17.3%）。

### 4.4 报告协议：受约束的环境反馈

| 报告类型 | 谁能提 | 内容 | 修复动作 |
|---|---|---|---|
| 缺陷报告 | 两种玩家 | 菜单挡画面、按键无效、进度卡死、成功过早触发、崩溃 | 改游戏代码 / 状态探针 / 控制指南 |
| 观测请求 | 仅 Coding Player | 策略需要但 ψ 读不到的量（含义 + 屏幕位置） | 给 ψ 加字段 |
| **禁止** | —— | 隐藏信息、成功捷径、更容易的任务 | 拒绝 |

核验机制防玩家"甩锅"：玩家可能把自己的失误当成缺陷，所以 Builder 必须先回放录像对照状态轨迹核对，矛盾则标记 disproved 并引用证据。全集合 298 款有完整构建记录的游戏中，23 款因 VLM 报告修复、125 款因 Coding 反馈重新打开环境。

### 4.5 数据统一：一个格式装下两种老师

代码策略连续按键，VLM 玩家一步一动——两者输出如何合并？录制器记录每次按键/释放的时间戳，把连续按键日志**切成 harness 步**（held 输入对齐到 0.05～7.8 秒的 26 档时长；短于 0.075 秒算点按；相邻键段合并为链式动作）。于是两种玩家产出同构的训练样本 (x_t, y_t)：x 是 harness 上下文，y 是动作（VLM 样本还带注释与思考）。代码策略样本的思考前缀置空且损失权重为零。

### 4.6 进度加权 SFT：把训练火力对准"推进任务的少数动作"

一条轨迹里大量步骤在等待、游荡、纠错，真正推进任务的只有少数几个关键动作（一次精准跳跃、一次正确转向）。进度加权 SFT 用轨迹里记录的 p_t 区分它们，权重：

**w_t ∝ ρ_t · max(1, c_t)**

- **信用 c_t**：进度事件或成功前最后三个动作加权（≥3、2、1.5）；
- **惩罚 ρ_t**：失败结尾动作 ×0、超时结尾 ×0.25、无进度重复动作 ×0.35、连续等待 ×0.7^k；
- **游戏平衡**：大游戏按 B_j = min(n_j, round(M^{1−α} n_j^α))（α=0.8445）压缩预算，防少数长游戏垄断。

实现上不改损失权重，而是把 w_t 随机舍入成整数倍数 m_t（E[m_t]=w_t）做**重采样**，从 2.05M 合格步中抽出 1.56M 训练样本。训练配方：Qwen3.5-4B/9B 全量微调（冻结视觉编码器），1 个 epoch、9,237 步、lr 1e-5 余弦衰减、8×80GB GPU。

## 五、评估指标与实验证据

### 5.1 指标体系

- **主指标：Progress（进度）**——episode 达到的最好进度 p̄ 按游戏等权平均。衡量"离目标走了多远"，即使没通关也能区分好坏；
- **主指标：Success（成功率）**——任务完成比例。Progress 高 + Success 低 = 会推进但收不了尾；
- **消融指标**：正确实现任务率（环境忠实还原原游戏且 start/progress/success 如实）、可解任务数、每美元/每小时的步数产出、thinking 开关增益。

### 5.2 基准构成

- **PlayerBench**（自建，留出测试集）：50 款游戏、287 个任务，7 引擎、4 难度层（98 easy / 105 medium / 67 hard / 17 very hard），与训练集 518 款游戏零重叠；
- **GameWorld**（外部）：34 款游戏、170 任务，独立构建、零重叠，检验迁移能力。

难度分层有人类数据背书：人类成功率从 easy 的 76.5% 一路降到 very hard 的 11.8%，中位尝试时长从约 1 分钟涨到 6 分钟——**Builder 标的难度与人类体感一致**。

### 5.3 实验一：协同开发真的能造出更对的环境吗？（20 款游戏、145 个冻结任务）

| 设置 | 正确环境 | 可解任务 |
|---|---|---|
| 通用编码智能体（同模型、无技能工具） | 25 | 1 |
| 无报告（Builder 交付后不再修） | 94 | 34 |
| **完整闭环** | **105** | **46** |

- 通用智能体 120 个环境做错、只解 1 个任务——**同样的模型，没有技能/工具/玩家就只能造出废环境**；
- 玩家报告把错误环境从 51 降到 40、可解任务从 34 升到 46，仅增加 20% 成本（$17.7→$21.3/游戏）；
- 换 GPT-6.1 Sol 当 Builder：正确数不变（136），但可解任务 62→82——报告带来的更丰富观测让策略能解更多任务；
- 典型案例 *There Is No Game*：Coding Player 发现字母 O 掉落后进度卡在 0.9（Builder 在变量存在前就挂了钩子），修复后 9 个任务全部正确且可解，不修则 9 个全错。**一款游戏的任务共享插桩，一个缺陷毁全部、一次修复救全部**。

审计还给出边界：Terra Builder 正确率 72%、Sol Builder 94%；PlayerBench 全部 287 任务经人工复查**未发现环境或评分错误**。

- *Kingdom Rush*（塔防）：0% → 100%，学会在路边草地开建造菜单、金币不足时等待；
- *Forward*（卡牌）：20% → 100%，学会拖拽而非乱点，出牌前悬停读牌。

## 六、效果优势的根源解释

### 6.1 因果链一：状态探针 → 免裁判验证 → 数据可信且稠密

- **机制**：进度/成功直接读引擎内部变量（如 resources.iron），无需 VLM 裁判或 OCR；
- **效果**：每一步都携带客观进度值 p_t，使（a）失败 episode 也有部分分数、（b）步级加权成为可能；
- **证据等级**：论文实验已支持——游戏平衡消融显示加权采样在同量数据下稳定优于均匀采样（9B +4.7 进度）；PlayerBench 287 任务人工复查零评分错误；
- **外部佐证**：GameWorld 证明了基于状态的验证比启发式/VLM 裁判更可靠可复现，但其 233 个状态字段平均每游戏 6.85 个**手工设计**——Game2Player 把这一成本自动化了（Builder 写探针 + 玩家报告逼它写对）。

### 6.2 因果链二：ψ/φ 分离 + 特权教师蒸馏 → 廉价量大的高质量示范

- **机制**：代码策略读 ψ（特权视图）实时玩，零模型调用可重跑 → 单位成本骤降（$0.13/h vs $54.7/h，22× 步/小时）；蒸馏成只看像素的学生时，特权信息通过动作示范传递而非直接输入；
- **效果**：87.7% 训练步来自代码策略，其精确计时动作教会学生"hold 多久"（案例研究：47% vs 1% 定时按键）；
- **证据等级**：论文实验已支持（数据源消融、案例研究）；
- **外部佐证**：π-Distill（ServiceNow）证明特权信息蒸馏"把测试时不可得的信息转化为可学习的行为"；RE-0 在 Code-as-Policy 场景验证了"教师局部干预 + 环境验证"优于全轨迹模仿。**差异与边界**：π-Distill/RE-0 面向通用智能体任务，Game2Player 的教师特权来自游戏状态接口而非教师模型更强——且消融显示纯代码数据在 PlayerBench 上不如纯 VLM 数据（20.1 vs 25.6），说明特权示范的**格式差距**（实时连续 vs 暂停分步）会折损部分迁移，混合才最优。

### 6.3 因果链三：玩即验证 → 环境正确性 → 迁移增益

- **机制**：玩家用"以后产出训练数据和评测分数的同一接口"测试环境，缺陷只有真正玩才暴露（Builder 自测盲区），报告经录像核验后修复；
- **效果**：正确任务率 65%→72%、可解任务 34→46；环境正确使轨迹的进度标签真实，训练信号不掺假；
- **证据等级**：论文实验已支持（协同开发对照实验三设置）；反事实：无报告设置 51 个错误环境——去掉报告机制，28% 的任务带着错误评分进入训练集；
- **外部佐证**：GameScaling 的"模仿学习有边界"结论从反面支持——**脏的/弱验证的数据堆量有天花板**；WebSTAR 证明合成轨迹中大量步骤是错的、朴素模仿会学到错误行为，步级去噪后小数据集反而更强——与本文"失败结尾 ×0、重复 ×0.35"的降权逻辑一致。

| 研究 | 相似尝试 | 相关结论 | 与本文差异/边界 | 对根源解释的影响 |

### 6.5 综合判断与未决问题

**多研究共同支持的机制**：(1) 状态验证优于裁判验证（GameWorld + 本文）；(2) 步级细粒度监督优于轨迹级（WebSTAR + 本文消融）；(3) 特权教师→盲学生的蒸馏可行（π-Distill + 本文）。

**仍属推测的部分**：ψ/φ 分离对最终分数的具体贡献未单独消融（推测：防止代码策略学到"读不了屏幕但赢了"的作弊示范）；"进度事件前 3 个动作最可能是原因"的时间窗假设（5 秒窗口）没有与替代信用分配方案对比。

**适用条件**：优势建立在"游戏可插桩 + 任务有可读进度变量 + 单人离线可玩"三个前提上；**可能失效的场景**：进度只能从屏幕估计的游戏（论文自己排除）、需要实时延迟的玩法（VLM 玩家全程暂停决策，分数不反映实时压力）、多人在线游戏（许可与运行时约束未解决）。此外 SFT 天花板明显：训练后模型（31.2）仍远低于闭源前沿（62.7）与人类（69.4），PLAYER-1 的 RL 路线暗示在这套环境上叠加 RL 是显然的下一步。

## 七、必要知识反推

假设让一个完全没有背景的人重做这项工作，TA 必须掌握：

### 7.1 领域知识层

- **游戏引擎的内部结构**：Unity WebGL 的调用约定、Flash 的显示对象树、Godot 的 PCK 打包与 GDScript、PICO-8 的内存布局——不知道"状态藏在哪"，探针无从写起（八份引擎技能就是这部分知识的固化）；
- **游戏评测协议设计**：暂停式交互、固定种子、步数预算、部分进度的含义——不理解就无法设计出可复现的 harness。

### 7.2 方法论知识层

- **可验证环境合成谱系**：R2E-Gym/SWE-smith（代码）、AutoWebWorld（网站）证明"改造现有软件为可验证环境"可行——本文是把该范式推进到游戏引擎生态；
- **特权蒸馏与代码即策略**：Voyager/π-Distill 一线工作说明"教师看的多、学生看的少"的蒸馏结构有效；
- **步级信用分配**：WebSTAR 等工作的结论——监督粒度必须细到动作级；
- **SFT 训练工程**：重采样替代损失加权、游戏级平衡、上下文构造（50 步文本历史 + 6 张历史截图）。

### 7.3 工程知识层

- **浏览器沙盒与录制**：同一运行时录两种玩家、输入日志与视频/状态同钟采样、"游戏忽略的输入既不丢失也不虚构"；
- **动作离散化**：held 输入对齐 26 档时长、短按合并、链式动作切分——没有这一步两种玩家的数据无法同构；
- **智能体流程编排**：任务计划冻结、有界修复（最多三轮）、退役上限三分之一、验收门槛（≥2 成功 episode、⌊n/4⌋+1 任务）——这些约束是防止 Builder"糊弄评测"的制度设计。

### 7.4 知识融合的关键节点

1. **"玩=测试"的洞察**：把软件工程的"用户反馈驱动修复"与 RL 的"环境=数据源"合二为一——环境正确性与数据质量变成同一件事；
2. **ψ/φ 双接口设计**：把"评测要客观"（读内部状态）与"玩家要公平"（只见可见信息）这对矛盾拆成两个通道——这是整个系统里最精巧的一次关注点分离；
3. **两种老师的数据同构化**：连续按键日志 → 暂停式步，让"特权教师的廉价量产"与"同格式教师的言传身教"进同一个 SFT 损失——融合点在录制器的时间轴。

## 八、论文中可以提取的通用性灵感

### 灵感 1：使用即验证——让消费者测试生产者

**核心思想**：构建系统的智能体自测有结构性盲区（它用自己设计的输入、读自己暴露的接口），让**下游使用者以真实使用方式**去测试，并给上游提带证据的报告，是打破该盲区的通用机制。
**论文证据**：玩家报告把正确任务率 65%→72%、可解任务 34→46；Builder 自测通过的 51 个环境实际有缺陷。
**推广场景**：(1) 软件工程——CI 之上加"以调用方真实调用模式跑的集成验收智能体"；(2) 数据集构建——用下游训练任务的性能反推数据标注缺陷；(3) API 设计——让 consuming agent 上报"文档没写清的行为"；(4) 教育内容生成——学员做题行为本身暴露讲义漏洞。

### 灵感 2：双视图接口分离——公平性与客观性不必二选一

**核心思想**：当"评测需要特权信息"与"被评测者只能见公开信息"冲突时，把两份信息做成**两个显式接口**（φ 只给打分器、ψ 只给玩家），并禁止跨通道索取。
**论文证据**：ψ/φ 分离使代码策略不能读隐藏牌、打分不能被屏幕糊弄；观测请求协议把"需要更多可见信息"与"要隐藏信息"区分开。
**推广场景**：(1) 竞赛评测系统——judge 读 ground truth、选手读题目；(2) 合规审查——审计视图与业务视图分离；(3) 多智能体协作——信息隔离下的公平考核；(4) 医疗 AI——诊断辅助视图与金标准视图分离。

### 灵感 3：特权教师的"一次性成本、无限重跑"经济学

**核心思想**：与其按次付费请专家（每步都花钱），不如花一次钱把专家能力**固化成可重跑的程序**（代码策略），边际成本趋零后靠量取胜；同时保留少量"按次专家"（VLM 玩家）产出带解释的示范补格式差距。
**论文证据**：$10.8 写策略 vs $54.7/小时请 VLM，12 分钟回本；每小时 7,775 步 vs 354 步；混合数据优于任一单源。
**推广场景**:(1) 企业知识沉淀——顾问咨询固化为内部工具；(2) 数据标注——写一次标注脚本重跑全量；(3) 自动化测试——专家探索性测试固化为回归用例；(4) 教学——名师课程固化为可反复练习的交互教材。

### 灵感 4：稠密进度信号是数据工程的乘数

**核心思想**：给每条轨迹配上 [0,1] 的连续进度（而非 0/1 结果），可以让"失败样本的大部分步骤"与"成功样本的少数关键步骤"都被正确利用——**进度让部分成功可交易**。
**论文证据**：进度加权在同量数据下 9B +4.7 进度；失败结尾 ×0 / 重复 ×0.35 的降权把训练集中到推进动作。
**推广场景**：(1) 长程任务管理——用里程碑完成度而非二值验收评估进展；(2) 招聘 funnel——用流程进度而非最终 offer 评估渠道质量；(3) 课程学习——按知识点掌握度而非考试及格分组织练习；(4) RL 奖励设计——凡有内部状态的系统都该问"能否读出稠密进度"。

### 灵感 5：冻结任务契约 + 有界修复 = 防止"造环境的人降低考纲"

**核心思想**：验收标准一旦可以随意改，构建方就会通过降低难度来通过验收。把任务定义**提前冻结**（难题不许删不许简化），修复只许改实现不许改契约，是从制度上保证评测不退化。
**论文证据**：任务计划冻结后"一个任务只有在 Builder 无法实现时才可移除"；探测到捷径/隐藏信息的报告一律拒绝。
**推广场景**：(1) 基准维护——防 benchmark 污染的契约化任务定义；(2) 外包开发——冻结需求规格防止供应商偷工；(3) AI 对齐评估——防被评估模型修改自己的评分标准；(4) 目标管理——OKR 一经锁定不许回溯降标。

### 灵感 6：把野生存量资产变成训练资源

**核心思想**：互联网上已有海量人类创造物（游戏、网站、文档、工具），与其从零生成合成数据，不如**自动化地"插桩+验证"存量资产**——多样性来自真实世界，验证来自内部状态。
**论文证据**：568 款野生游戏 × 25+ 类型 × 7 引擎的多样性，是任何合成管线难以复制的；对比通用智能体从零构建 120/145 做错。
**推广场景**：(1) 桌面软件智能体——插桩存量应用产出训练环境；(2) 机器人仿真——把真实建筑/工厂的 BIM 模型变成可验证任务；(3) 法律/医疗——把存量判例/病历改造成带验证的推理训练集；(4) 教育——把开源项目改造成带隐藏测试的编程作业。
