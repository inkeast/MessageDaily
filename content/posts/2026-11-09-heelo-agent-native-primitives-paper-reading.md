**先说结论**：这篇论文诊断了当前 LLM agent 的一个结构性病灶——**资源已经够得着，但「会用资源」的能力全押在调用方身上**。模型可以通过 Codex、Claude Code 这些 harness 够到 API、代码库、证明库、文档和别的 agent，可一旦要在具体任务里把这些资源用对（给工具调用绑定正确参数、把检索到的代码改适配、判断证明方法的前提条件是否成立），前沿组合照样翻车：Terminal-Bench 4.0 上 GPT-5.6 Sol + Codex 只解出 37.3%，Claude Opus 5 + Claude Code 也只有 51.8%。论文的药方是**agent-native primitive：给每个可复用资源配一个驻留 LLM**，资源从「躺在库里的死物」变成「会说自然语言、会自己干活、会跟同伴传话的活体组件」；外层再用 HEELO 框架的三个机制（按需组合成任务图、证据驱动执行与反责修订、验证后入库演化）把它们组织起来。八个 primitive 族、20 多个基准、外加一个 46 项真实任务的落地平台 heelo.dev，构成了目前关于「harness 应该工程化」这个命题最完整的论证。对初学者来说，这篇论文最值得学的不是某个数字，而是一个视角转换：**agent 系统的下一个竞争力来源，可能不在模型里，而在模型周围那些可复用组件的设计里**。

## 一、论文背景：为什么「够到资源」不等于「完成任务」

要理解这篇论文，先得理解 2026 年 agent 领域的基本盘。

**什么是 LLM agent 和 harness。** LLM agent 是让大模型不止聊天、还能动手干活的系统：模型通过调用工具（查数据库、发邮件、执行代码）对环境施加动作，直到任务完成。而 **harness（挽具/马具）** 是论文反复使用的术语，指**包在模型外面的控制程序**——它决定模型看到什么、能调用哪些工具、结果怎么返回、失败后重试几轮、什么时候停止。OpenAI 给 GPT 配的 Codex、Anthropic 给 Claude 配的 Claude Code，本质都是 harness。经验上，同一个模型换个好 harness，成绩可以差出几十分——这就是 2026 年行业热词「harness engineering」（挽具工程）的由来。

**真实任务基准有多难。** 论文开头给了三组扎眼的数字：

| 基准 | 任务形态 | 前沿组合成绩 |
|---|---|---|
| Terminal-Bench 4.0 | 在命令行环境完成 66 项长链真实工作 | GPT-5.6 Sol + Codex（最大推理力度）**37.3%**；Claude Opus 5 + Claude Code **51.8%** |
| DevOps-Gym 四阶段 | 构建/监控/修 issue/生成测试 | 同上两对平均 **49.9% / 52.1%** |
| τ²-Bench 航空域 | 在对话中按航司政策订机票等 | Claude-4.6-Sonnet 仅一半任务能四次试验全部成功 |

订一张符合政策的机票、填一份后字段依赖前答案的表格——对人平平无奇的任务，最强 agent 组合就是做不稳。

**失败发生在哪一步？** 论文的核心诊断是：这些任务**不是败在「够不到资源」，而是败在「够到之后不会用」**——作者称之为**通往真实世界的最后一公里（the last mile to the real world）**。拆开看是三重困难：

1. **上下文中的应用（application in context）**：一次工具调用的每个参数都要正确接地（grounding）——往往要引用上一次调用的输出；检索来的代码必须适配目标仓库的签名、数据结构和依赖；一个证明方法只在前提条件成立时可用（论文举了个数学例子：对实数上的 Σaᵢ²≥(Σaᵢ)²，相似度检索会推荐需要 aᵢ≥0 的 AM-GM 不等式，但题目没给这个条件，真正适用的是 Cauchy-Schwarz）；从文档里抽的答案必须忠于原文。
2. **组合（composition）**：一步的产出必须以消费者能用的形式到达下一步。工具 A 返回的订单号要能填进工具 B 的参数；一个文件的修改要传导到依赖它的所有组件。
3. **证据驱动的修订（evidence-driven revision）**：任务失败时，环境只报「测试没过」或「编译失败」，不告诉你该怪谁。必须把失败回溯到被牵连的工作，**只重做那部分**，而不是整个推倒重来。

**现有方案为什么不够。** 此前的进展主要让资源「更容易够到」：工具学习让模型学会调 API，RAG 和记忆系统把知识送进上下文，技能库和代码库积累了可复用产物，多智能体框架和 harness 生成器自动设计协作结构。但论文点出它们的共同盲区：**资源留在原地，应用资源的能力留在调用方（caller）**。后果是三连：调用方要读的东西随库膨胀（几千个工具的 schema 塞进上下文，性能反而下降）；一个任务里学到的用法随任务结束而作废；每个 harness 都要为每类任务重新建一遍这种能力。这就自然引出论文的问题——**一个 agent 怎样端到端地完成一件真实世界任务？**

## 二、论文定位和关联工作：八条研究线汇成一个问题

这篇论文实际上是把同一个团队 2026 年的**八篇伴随研究**（companion studies，引用 [44]–[51]）统合进一个框架。理解它在研究版图上的位置，要看六条相关线：

**① 工具调用与接口协议线。** ToolBench/ToolLLM（清华，1.6 万真实 API 的基准）、τ-bench/τ²-Bench（Sierra，对话式工具使用）刻画了工具调用能力；OpenAPI、**MCP（Model Context Protocol，Anthropic 2024 年发布的开放协议）**、Agent Skills 规范让服务、工具、打包指令可被发现。这条线的共同点：**每次调用的参数绑定都由调用方自己写**。Tool Primitives 反转了这个负担——让工具说模型的语言，而不是让模型说 API 的语言。

**② 代码复用与仓库工程线。** 从软件工程的组件复用（Szyperski 的组件软件、Meyer 的 design by contract）到 DreamCoder/LEGO-Prover 的库学习，再到 RepoCoder 等检索增强生成和 SWE-agent/OpenHands 等仓库级 agent。共同点：**复用的工件是死的，怎么用由中央 agent 决定**。Code Primitives 把「适配目标」变成组件自己的操作，Dev-Primitives 让需求沿仓库自身的依赖图路由。

**③ 检索、记忆与知识线。** RAG、RAPTOR 摘要树、HippoRAG 2 图记忆、Agent Workflow Memory 经验记忆。共同点：**留下的是语料、结构或经验，重复使用一个源仍被当作重复访问**。Knowledge Primitives 把它变成「源学习」——为每个权威源维护一个可修订的源模型。

**④ 形式化证明线。** Lean 4 + Mathlib 提供 Checked 证明语言；LeanDojo、前提选择、lemma 库增长、LLM reranker。共同点：**检索按相关性排序，怎么用留给 prover**。Math Primitives 引入 Method Contract（方法契约），让每个方法先「自荐」如何在当前目标上使用。

**⑤ 多智能体系统线。** AutoGen/MetaGPT 的角色框架、GPTSwarm 的图优化、MAS-GPT 的按查询生成配置、LatentMAS 的潜空间（KV cache）通信。共同点：**设计单元是 agent 或团队整体，复用性差**。Agent Primitives 把「反复出现的多智能体计算模式」做成可复用单元，内部用 KV cache 通信。

**⑥ Harness 设计与自动化线。** ReAct/Reflexion/Self-Refine 的经典循环、DSPy 的声明式管线编译、AFlow/MetaHarness/MemoHarness 的 harness 搜索或测试时生成。共同点：**一个 harness 用于所有任务，或测试时生成新控制代码（要现写现调，风险叠加）**。Harness Primitives 让控制操作在开发期实现并验证，测试时只做选择和编译。

**与 Anthropic Agent Skills 的对照**值得单独说（初学者最容易混淆）。Agent Skills 是「带 SKILL.md 的文件夹」：说明书 + 脚本，靠渐进披露（progressive disclosure）按需读进 agent 的上下文——本质上**能力还是留在调用方，只是文档分层加载**。而 agent-native primitive 给资源配驻留 LLM，**能力随资源走，调用方上下文里根本不出现资源细节**。一个是「给你一本操作手册自己照着做」，一个是「柜台后坐着一位懂行的店员，你说需求他来操作」。

| 维度 | 既有路线（工具学习/RAG/技能库/harness 生成） | 本文：agent-native primitives + HEELO |
|---|---|---|
| 能力放哪 | 调用方上下文里 | 资源内部（驻留 LLM/程序） |
| 调用方负担 | 读资源细节、绑定参数、适配代码 | 只用自然语言说需求 |
| 库变大时 | 调用方要读的越来越多 | 只有被激活的 primitive 运行，成本有界（有定理） |
| 任务间 | 能力随任务结束丢弃 | 验证后入库，跨任务复用、持续演化 |
| 失败后 | 整体重试或从头重建 | 按证据反责，只重做被牵连的 primitive |

**定位结论**：这篇论文不是在单条线上刷点，而是提出一个**统一抽象层**——把上述六条线里「可复用的单元」全部改造成「自带应用能力的活体组件」，再证明这个抽象在八类任务上都成立。它接续的是软件工程里「组件 + 契约」的经典思想，把 Meyer 的 design by contract 推广到 LLM 单元上。

## 三、问题定义：把「最后一公里」抽象成一个构造问题

论文的形式化值得细品，因为它把纷繁的真实任务收敛成了一个干净的数学对象。

**具体场景**：一个真实世界任务 q 带着上下文 c_q 到来——输入、环境、约束，以及**验收标准**（任务自己的测试、证明检查器或答案 key）。agent 通过 harness H 作用于任务，产生轨迹 τ，由任务的验收程序打分 R_q(τ)∈[0,1]。

**抽象问题**：固定 harness（一个通用 coding agent）对所有任务用同一个 H。论文改成：**从一个可复用单元库 L 里，为每个任务构造它自己的 harness**：

- H_q = F(q, c_q; L)——构造过程 F 从库里组装出任务专属 harness，预算受限（模型调用数或修订轮数）；
- 目标是逼近 H*_q = argmax R(q, H)——该任务在兼容 harness 集合上的最优解。

**最后一公里就藏在这个式子的两个层面**：库里的每个单元必须被**应用到任务自己的对象上**（谁来做绑定/适配？）；F 必须决定**哪些单元被需要、结果怎么组合**（谁来编排？）。前者由 agent-native primitive 回答，后者由 HEELO 的机制回答。

这个抽象的精妙之处在于**它让「库的大小」与「单个任务的成本」解耦**。直觉上库越大越好，但若每个任务都要扫描全库，库就是负担。论文的伴随研究证明了**需求有界激活**（demand-bounded activation）：|A_q| ≤ K(q) ≤ ρD(q)——被激活的 primitive 数不超过路由事件数，而路由事件数不超过「需求个数 × 每个需求的最大路由次数 ρ」。**库再大，任务只需要它需要的那几个**。这一条是整套方案经济上成立的数学地基。

另一个关键理论结果是**固定 vs 按任务组合的分界**（Proposition 3.2）：在加性收益模型下，一个 primitive 在它的适用域内带来增益 ḡ、域外带来惩罚 κ̄；最优固定 harness 与 oracle 按任务选择的差距是 Γ_fixed = Σ min(μᵢḡᵢ, (1-μᵢ)κ̄ᵢ)（μ 是适用域出现率）。**按任务组合胜过最好的固定 harness，当且仅当组合器的选择损失小于这个差距**。这解释了为什么「没有一个万能 harness」不是工程遗憾而是数学必然——只要 primitive 的适用域不是全覆盖，固定方案就必然在域外白白交罚金。

## 四、问题解法：primitive 是什么，HEELO 怎么用它们

### 4.1 Agent-Native Primitive：给资源配一位「驻店师傅」

**定义**（论文 Definition 3.1）：一个 agent-native primitive P_i 由三样东西构成——

- **资源 a_i**：它拥有的可复用资产，可以是工具的 schema+函数、代码组件、证明方法、源模型、多智能体模式、仓库文件、控制操作；
- **驻留 LLM M**：以资源为条件的语言模型，充当资源的**自然语言接口**；
- **接口 d_i**：harness 用来发现和调用它的方式（比如工具的 schema 描述符）。

调用时，给 primitive 一个自然语言请求 x_i 和上下文 c_i，它返回结果 r_i **和发给其他 primitive 的消息 m_i**：

> (r_i, m_i) = P_i(x_i; c_i) = M([a_i; c_i; x_i])

**类比**：传统工具库像图书馆——书（资源）躺在书架上，读者（调用方模型）借回去自己啃，啃懂了才能用；agent-native primitive 像专家工作台——每张桌子后面坐着一位师傅（驻留 LLM），你递一张字条（自然语言需求），他当场把手头的家伙什（资源）用到你的活上，还会转头跟隔壁桌喊话（消息 m_i）：「你那边的法兰盘尺寸得改，我这管道对不上！」

三个附属设计让这个定义落地更稳：

- **自评相关性（relevance assessment）**：接口相似不等于适用。primitive 可以先自我评估「我适用于这个请求吗、我会怎么用」，从源头避免相似度检索的误选；
- **自带验证（carried validation）**：资源自带测试或 schema 的，primitive 返回前先自检，失败时报告结构化错误——「我这步成功了」和「结果对任务有用」分开负责；
- **程序替代**：领域有精确程序的（如 Harness Primitives 的控制操作），用实现的代码替代驻留 LLM——不为了「LLM 化」而放弃确定性。

### 4.2 HEELO 三机制：组合、执行反责、入库演化

**机制一：库选择与组合（COMPOSE）。** 任务进来，先通过接口检索（或一次读全部接口）找候选，读它们的相关性自评，然后产出一张**任务专属图**：激活集 A_t（哪些 primitive 运行）+ 依赖边 E_t（结果和消息沿什么路径流动）。只有被激活的 primitive 运行——成本跟随 |A_t| 而不是库大小 N。

**机制二：证据驱动的执行与改进（EXECUTE / VERIFY / 修订）。** 图在任务环境里按轮运行：每轮激活的 primitive 各干各的活、消息在轮内送达；EXECUTE 运行任务能运行的（构建、测试、编译）并记录证据；VERIFY 把整合状态和证据变成裁决 v_t∈{PASS, FAIL} 加结构化反馈 φ_t=(失败现象 e_t, **被牵连的 primitive 集合 I_t**, 修订指导 u_t)。**关键规则：失败的构建或测试就是 FAIL，任何模型判断不能推翻它**。失败后 COMPOSE 只重排被牵连的部分——重规划受影响的步骤、重新激活被牵连的 primitive、重定向未满足的需求，**保留未被新证据推翻的工作**。预算 B 轮耗尽或 PASS 则结束。

**类比**：这像一家有质检的工厂流水线。产品下线过检（VERIFY），不合格时质检单上写的不是「重做整条线」，而是「问题出在 3 号工位的焊接，牵连 5 号工位的组装」——只有 3 号和 5 号返工，其他工位继续。

**机制三：验证与发布（VALIDATE / 入库）。** 库在任务之间演化：新 primitive 可以从既有工件挖掘、从验证过的运行中收获、从失败轨迹中提炼，但**只能走一条与任务执行分离的发布路径**——通过测试、编译器、源忠实性检查或开发任务上的匹配运行，才能入库或替换旧版。这保证了库的单调改进而不被坏组件污染。

### 4.3 八个 primitive 族：同一抽象的八种实例化

每个任务领域对最后一公里的要求不同，论文用八个族分别落地（每族对应一篇伴随研究的完整系统）：

| 族 | 资源是什么 | 驻留 LLM 干什么 | 代表系统 | 库规模 |
|---|---|---|---|---|
| **Tool** | 工具的 schema–函数对 | 把自然语言请求映射成类型化调用 | HEART + ToolFace | 25,519 个工具（16,464 个包装真实 API） |
| **Code** | 可执行组件（实现+契约+依赖闭包+自带测试+出处） | 评估并**适配**组件到目标仓库 | LEGO + CodeFace | 1,424 个，每个都过隔离验证 |
| **Math** | Method Contract（证明方法：参数/前提/目标/Lean 脚手架/剩余义务） | 「自荐」如何在当前目标上使用该方法 | 自广告式方法选择 | 82 个，Lean 编译通过 |
| **Knowledge** | 单个权威源的**源模型** | 激活任务相关区域；持续学习源 | SourceLearn | 每源一个 |
| **Agent** | 多智能体计算模式（Review / 投票选择 / 规划执行） | 内部 agent 共享一个 LLM、交换 KV cache | Organizer 按查询组合 | 3 个模式 + 45 对结构知识池 |
| **Dev** | 仓库组件（默认一个文件） | 编辑自己的工件、给被牵连组件发定向消息 | HERMES | 由任务仓库现场诱导 |
| **Navigation** | 信息空间的一个「领地」（territory） | 搜自己的领地、报告证据与不确定性 | ANTMAN + Need Graph | 按查询划分诱导 |
| **Harness** | 实现好的控制操作（作用域+组合契约） | 确定性程序执行（无需 LLM） | STITCH | 测试时 8/6 个条目 |

几个族的设计细节值得展开：

**Math Primitives 的「自广告」**是全文最有想象力的机制之一。传统检索按相似度排序方法库，reranker 只能重排检索池内的候选——池子没有的，reranker 再强也无能为力（这就是 Proposition 3.3 证明的「检索池上限」）。自广告让**全库 82 个契约各自提案**「我会怎么用在这个目标上：打哪、做什么动作、需要什么条件」，一批调用完成，然后排序。它把「这个方法适用吗」从文本相似度问题变成了「提案可否被检验」的问题。

**Dev-Primitives 的反责路由**解决了软件工程的要害：程序状态散布在相互依赖的源码、配置和测试里，单一 agent 在一条越来越长的轨迹里反复重建这个分布式状态，导致上下文爆炸和语义漂移。Dev-Primitives 让每个组件就自己的职责推理、直接互发消息，诊断（Bug Diagnosis）把仓库级失败路由回负责的组件，重新激活它们——B=3 轮内修订。

**Harness Primitives 的「先实现后选择」**避开了测试时生成 harness 代码的可靠性陷阱：每个控制操作（如 State Guard、Check Replay、First-Failure Localizer）在开发期实现并通过机制测试；测试时 composer 读目录、给组合意图，确定性编译器把它接进种子图——选中的 primitive 全部无运行时错误地生效，而组合成本只有一次 actor 尝试的 4.3%/2.7%（对比从头写整个 harness 的 token 下界是它的 543 倍/638 倍）。

**Agent Primitives 的 KV cache 通信**利用「所有 agent 跑在同一个 LLM 上」这一条件，让 agent 之间直接交换键值缓存而非文本——论文的应力测试显示，长上下文中段注入的指令，文本通道只有 15.6% 被遵循，KV cache 通道有 73.3%。这呼应了同期 LatentMAS 的发现，但采用了更保守的通信设计以避免跨模型崩溃。

### 4.4 heelo.dev：把研究打到真实世界

研究基准之外，团队建了 heelo.dev 平台——把航班、日历、邮件、社交发布、公司调研、浏览器自动化等第三方动作，全部按 agent-native 设计封装成工具，经 MCP 服务器暴露给 Claude Code、Codex、Cursor 等外部 agent。平台的真实任务组织成**四个端到端闭环**：distribution（发布跨渠道内容并归因点击）、acquisition（找潜在客户并发多步外联）、assistant（从发票邮件到审批、入账、开收据）、validation（挖掘真实问题并验证市场需求），共 26 项能力、46 项任务，每项任务的通过标准**在首次运行前固定**为人可核验的事实。这是对「真实世界」的严肃对待：live 服务、真实账户、失败路径（比如错误的联系人 ID 必须返回干净的报错）都在测试范围内。

## 五、评估指标与实验证据：26 项对比全胜，但要会看门道

### 5.1 指标体系：三层证据

论文的评估分三层，层层递进：

- **主指标**：每个族在自己的任务基准上，与**同骨干模型**的 reference baseline 对比（Dev/Harness 族锁定 backbone 与 Codex/Claude Code 对比，隔离 harness 因素；其他族与该 setting 的最强 baseline 比）。Figure 1(a) 的 26 项对比中 HEELO 全部领先。
- **效率指标**：每个族报告成本/延迟/token 曲线（Figure 1(b)），证明增益不是烧钱买来的。
- **消融与机制指标**：一族一族地拿掉 primitive 或机制、做预算匹配对照，定位增益来源——这是全文最有证明力的部分。

### 5.3 实验设计为什么有证明力：三个「对照做对了」的地方

**① 预算匹配对照把「多花算力」解释杀死了。** 最自然的质疑：primitive 多了一次驻留 LLM 调用，增益是不是就是多花了一次推理？HEART 的对照实验把 Tool Primitives 的调用预算**原封不动转给调用方自精炼**（在原始 schema 上反复打磨参数）——同骨干、同调用数、同 token，结果 ToolBench pass 只有 34.2%，对比带 primitive 的 75.1%。**增益不在算力，在能力放置的位置。**

**② 访问 vs 应用的对照把「看到资源」解释杀死了。** LEGO 的消费对照：同样的检索、同样的组件，只读作上下文 0.3544，原样 import 调用 0.3430（最大的 D5 带跌到 0.060），带适配的 primitive 0.5134。**光把代码给模型看没用，甚至不如不看；有用的是有人替它改适配。**

**③ 规模干预把「库大必贵」的直觉证伪了。** ANTMAN 的空间干预：把干扰物空间从 32K 撑到 512K（16 倍）而需求不变，活跃协调只增长 1.23×（对照 LongAgent 15.29×、CoA 15.33×）；反向把需求从 1 单位增到 16 单位而空间固定，worker 从 5.0 涨到 8.0 且证据 100% 找齐。**参与度跟需求走，不跟空间走**——Proposition 3.1 的前提在真实系统里成立。

另有两处诚实值得肯定：Harness Primitives 的固定 primitive 对照显示同一个 primitive 在 Django 上提升 69.2%<种子 75.0%、在其他仓库 77.9%>69.1%——**正面展示了作用域外的惩罚**，恰是 Prop 3.2 的 κ̄ 实测；Knowledge 族在 GPT-OSS-120B 骨干下有两个 setting 输给 baseline（AppWorld 27.4% vs 30.4%），论文如实报告，没有藏。

## 六、效果优势的根源解释：能力放在哪里，为什么结构上必然赢

### 6.1 根源机制与证据链

把第六部分的因果链完整铺开——**方法差异 → 机制变化 → 指标提升**，每步标注证据等级：

**因果链 1：能力随资源走 → 调用方上下文与库规模解耦 → 工具/代码任务的大幅提升**

- 机制：baseline 里调用方必须在单一上下文里持有所有用到的资源细节（几千个 schema、组件契约、方法条件）。库越大上下文越长，而长上下文对证据的利用随位置劣化（lost in the middle，论文引用 [39]）。primitive 把绑定/适配移入资源内部，调用方只收发自然语言。【论文实验支持：去 ToolFace 后 pass 75.1→16.1，是最大降幅；预算匹配自精炼 34.2% 证明剩余增益不可由调用方算力替代】
- 外部印证：Anthropic 的 Agent Skills 同样以「上下文不随技能数膨胀」为核心设计目标（渐进披露），从侧面确认这是真实瓶颈；但 Skills 用文档分层解决，能力仍在调用方——与本方案形成机制差异的天然对照。

**因果链 2：消息直达负责组件 → 组合不再经过中央轨迹 → 长程任务的反责修订有效**

- 机制：单 agent 系统里「一个文件的修改要传导到依赖方」靠同一条越滚越长的轨迹传递，语义会漂移；Dev-Primitives 的定向消息把需求直接送到负责组件，诊断把仓库级失败路由回责任人，修订只重做被牵连者。【论文实验支持：去诊断反馈 TB4.0 51.8→41.2（四种机制移除中降幅最大）、Refactor 31.0→20.0；去互发消息 Refactor 31.0→23.5；单编辑器吃同样计划只有 38.8%，匹配算力也只 45.5%——组件局部推理 + 直接通信在同等算力下胜出】
- 外部印证：SWE-agent 的经典结论「agent-computer interface 设计显著改变 agent 表现」（NeurIPS 2024）支持「接口/组织方式是第一性变量」这一前提，但它是单一固定接口；本论文把它推广为按任务组合的接口族。

**因果链 3：候选者自荐突破检索池上限 → 冷门但适用的候选可见 → 数学方法选择与证明提升**

- 机制：两阶段「相似度检索 + rerank」的结构缺陷是 reranker 永远只能在池内重排（Prop 3.3(ii) 证明 hit@k 被池内是否含真答案封顶）。自广告让全库各自提案，把「适用性判断」变成可核验的提案比较。实验中最强 reranker 的 hit@5 封顶在 0.842–0.858 而自广告随骨干增强升到 0.975——上限行为完全符合理论预测。【论文实验支持，且 Figure 17 展示被相似度排到 10 名开外的方法进入自广告前五】
- 外部印证：适应引导检索（adaptation-guided retrieval，Smyth & Keane 1998；论文引用 [128]）早在 CBR 时代就发现「相似 ≠ 可适配」，与本机制结论同源。

**因果链 4：需求驱动激活 → 成本有界 → 平台经济性**

- 机制：由 Prop 3.1，激活集 ≤ ρ×需求数；库增长不迫使活跃部分增长。heelo.dev 的「每完成任务成本反降」依赖两个效应：完成率提升（分子）+ 有界激活（分母不随能力数爆炸）。【论文实验支持：ANTMAN 1.23× vs 15×；Dev 过度激活对照——保持初始全激活反而降 1.2–3.0 分、成本 1.61–1.88×，说明激活宁缺毋滥】

**因果链 5：驻留可用小模型、协调诊断用强模型 → 模型分配的经济学 → τ²-Bench 成本优势**

- 机制：绑定参数/适配组件是「局部、条件化于单个资源」的任务，8B–20B 模型即可（GPT-OSS-20B 驻留保留 95.1% 交付、省 24% 成本）；而「失败归因给谁」的诊断最吃模型能力（Qwen3-8B 全角色 TB 27.6%，仅把诊断换强模型即回到 44.5–47.9%）。【论文实验支持：模型分配消融 Tables 50–51】这是「强模型花在刀刃上」的定量版。

**相反或限定性证据**（同样重要）：

- **单任务 token 并非处处占优**：heelo.dev 上连接运行的每任务 token 显著高于单独运行（16 万 vs 1.9 万），省钱完全依赖完成率——若任务本来就简单到 baseline 能稳定完成，primitive 开销是净增；
- **Knowledge 族非全条件占优**：GPT-OSS-120B 骨干下 SWE-QA 输 HippoRAG 2、AppWorld 输 Hybrid RAG——源学习的增益依赖骨干模型的可靠性；
- **lead discovery 全军覆没**：46 项真实任务中唯一无任何 arm 超过 20% 的能力，说明 primitive 化不能无中生有能力边界外的能力（在公开平台上找「自述有匹配需求的人」目前对所有系统都太难）；
- **自广告的精度代价**：Putnam hit@1 上 reranker（0.692）仍优于朴素自广告（0.658），需要 runoff 二次重排才追平——「全库自荐」买的是召回上限，不是排序精度。

### 6.3 综合判断

**多项证据共同支持的机制**：① 应用能力随资源走消解调用方上下文膨胀（链 1，有预算匹配消融 + 外部领域共识）；② 需求驱动激活使成本有界（链 4，有定理 + 两方向干预实验）；③ 失败反责优于整体重试（链 2，四个族的机制移除消融一致指向）。

**仍属合理推测的部分**：驻留 LLM 设计在**跨任务同库复用**下的边际收益递减速度、八族在**同一任务上混合组合**时的干扰情况——论文附录 E 给出了跨族组合评估协议但主实验尚未覆盖，跨族增益是否可加仍待验证（Prop 3.2 的加性模型在那里只是假设）。

**优势成立的前提条件**：任务有可判定的验收证据（测试/编译器/固定标准）；库的构建成本可被多任务摊销；资源确实需要「应用」而非仅仅「读取」。若任务是一次性的、无验证手段的、或资源只是被引用而不被使用的，primitive 化的额外结构可能得不偿失。

## 七、必要知识反推：做这项工作最少得懂什么

假设把一个聪明但零背景的人放到这个课题上，他必须掌握什么？

**领域知识层**：
- **LLM agent 技术栈全景**——function calling 的 schema 机制、ReAct 循环、harness 与 actor 的分工。不懂这些就无法定位「能力留在调用方」这个病灶；
- **六条相关研究线的深度**——工具学习、RAG/记忆、形式化证明（Lean 4 + Mathlib 的编译检查语义）、多智能体、仓库级软件工程、harness 优化。八族每一族都要跟该领域最强 baseline 公平对比，不懂行连对比协议都设计不出来；
- **基准评测方法论**——Terminal-Bench、SWE-bench Verified、τ²-Bench 的评测协议与陷阱（为什么必须同骨干对比、为什么留出集要与库构建隔离、为什么标签要人工复核——论文的 Putnam 标注就是 GPT 提议 + 人逐条检查后才让任何 selector 运行）。

**方法论知识层**：
- **软件工程的组件复用理论**——Szyperski 的组件软件、Meyer 的 design by contract、Sutton 的 options（时间扩展动作）。「primitive = 资源 + 契约 + 驻留执行者」的定义直接建立在这三者之上；
- **证明规划与案例推理**——Bundy/Melis 的 proof planning、adaptation-guided retrieval 的「相似≠可适配」教训，Math Primitives 的思想源头；
- **组合优化的基本结论**——次模性、贪心 1−1/e 近似（Prop 3.3(iii) 的技术工具）、加性效用分解（Prop 3.2 的模型假设）。

**工程知识层**：
- **MCP 服务器与平台工程**——heelo.dev 要对接真实第三方服务（邮件、日历、社交 API），处理会话、缺字段追问、robots.txt 合规、同意与抑制名单；
- **大规模实验工程**——8 个系统 × 20+ 基准 × 多骨干的统稿，成本以 API 价精确记账，每族消融保持 backbone/预算/环境只动一个变量。

**知识融合的关键节点**（知识不是叠加而是化学反应的地方）：
1. **把「design by contract」翻译到 LLM 单元**：契约不再是类型签名，而是「驻留 LLM + 自然语言接口 + 自带验证」——软件工程 30 年的复用直觉与 LLM 的自然语言能力在这一步对接；
2. **把八个各异系统重写为同一 F 的实例**：需要同时看到 HEART 的三段 COMPOSE、LEGO 的检索-激活、ANTMAN 的 Need Graph 在数学上是同一个构造过程——这是框架论文最难的一步，也是 102 页篇幅的主要去向；
3. **理论-实验的互锁**：Prop 3.1 的前提（每步至多路由一个未满足需求）不是先验成立的，ANTMAN 的实现刻意满足它，干预实验再验证它——理论指导实现、实现反哺定理的闭环。

## 八、通用性灵感：能带走的东西

**灵感 1：瓶颈常在「够到」与「会用」之间，解法是让能力随资源走。**
论文证据：ToolBench 上同样的预算给调用方自精炼只有 34.2%，放进 Tool Primitive 是 75.1%。
推广场景：API 设计（给接口配一个「驻留的语义层」而非更厚的文档）；企业知识管理（每位专家沉淀的不仅是文档，还有「随文档走的问答代理」）；教育（教材之外配「就地讲解」的陪练）；医疗器械/工业设备（说明书之外内嵌情境化操作指导）。

**灵感 2：系统扩容不必等于成本扩容——让参与量由需求而非资源总量决定。**
论文证据：信息空间 16 倍膨胀时协调仅 1.23× 增长（Prop 3.1 + ANTMAN 干预）。
推广场景：微服务按流量而非服务总数扩缩；图书馆「需求驱动的开架」而非全量巡架；投资研究按「未回答的问题」分配调研精力，而非按行业覆盖度平均用力。

**灵感 3：失败要反责到人，只重做被牵连的工作。**
论文证据：HERMES 去掉诊断路由，TB4.0 掉 10.6pp——四机制中最大；CI 系统的增量构建、局部测试选择是同一思想在工程界的先例。
推广场景：团队复盘（失败归因到具体环节而非全组加班重做）；供应链（质量事故只召回受影响批次）；编辑流程（审稿意见路由到负责章节而非全文重写）。

**灵感 4：演化系统必须「入库先验证、发布与执行分离」。**
论文证据：VALIDATE 独立于任务执行的发布路径；CodeFace 每个组件隔离验证后才入库。
推广场景：模型注册表与灰度发布；团队知识库的「信源审核后归档」；开源依赖的准入 CI 门禁。凡是会积累资产的系统，都需要这条与使用场景隔离的质量闸门。

**灵感 5：让候选者自荐，突破「先筛池再排序」的天花板。**
论文证据：reranker 的 hit@5 被检索池封顶在 0.842–0.858，全库自广告升到 0.975（Prop 3.3 的池上限在实验中显形）。
推广场景：招聘（简历关键词初筛会系统性漏掉「不相似但适配」的候选人，让候选人提交「我会怎么干这个岗」的提案）；论文评审匹配；推荐系统的召回多样化；内部竞标（让团队提案而非只靠历史相似项目匹配）。

**灵感 6：没有万能固定方案是数学必然，不是工程遗憾。**
论文证据：Prop 3.2 给出固定方案与按任务选择的差距 Γ_fixed；STITCH 实验里最优固定 primitive（76.0%）确实低于按任务组合（80.5%），随机组合（73.3%）退化回固定方案水平。
推广场景：产品策略（一套配置吃遍所有细分市场必然交「域外罚金」）；医疗方案（指南化固定路径 vs 按病人组合）；任何「平台 vs 垂直」的架构决策——固定方案的选择损失小于组合差距时才值得平台化。

**灵感 7：强模型花在协调与诊断，小模型驻留在资源里。**
论文证据：诊断换强模型单独把 TB4.0 分辨率从 27.6% 拉到 44.5–47.9%，而驻留/适配位用 20B 模型保留 95% 效果、省 24% 成本。
推广场景：组织管理（资深人做 case 诊断与资源调度，执行层标准化）；云成本优化（重推理用于路由、轻推理用于内容生成）；教育（名师讲诊断思路，助教做练习陪跑）。

---

**一句话收尾**：这篇论文把 2026 年 agent 领域的一个集体直觉——「模型周围的设计和模型本身一样重要」——推到了它的逻辑终点：**把每一份可复用资源都变成一个自带能力、可被组合、能被反责、可入库演化的活体组件**。无论 HEELO 这个具体框架未来命运如何，「能力随资源走」「激活由需求界定」「失败按证据反责」这三条原理，都已经在 26 项基准对比和 46 项真实任务上挣得了被认真对待的资格。对从业者，下一步值得盯住的是附录 E 那份跨族组合协议——八族增益能否在同一个任务里叠加，是这个框架从「统一叙事」走向「统一系统」的试金石。
