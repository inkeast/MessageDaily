> **领域标签**：cs.AI / 编码智能体评测

## 一、论文背景

### 1.1 编码智能体与它的"考试体系"

大模型已经能以自主软件工程师的方式工作：拿到一个请求，在陌生仓库里探索、跨文件编辑、跑构建和测试、迭代到改动生效。要判断哪个系统值得信任，行业靠的是 benchmark——而 benchmark 要扮演这个角色，必须同时满足三个条件：**任务像真实工程工作、评分能接受一切正确解并拒绝错误解、答案不在训练数据里**。

理解这篇论文，需要先理解这三条各自崩坏到了什么程度。

### 1.2 挖矿式基准的先天缺陷

主流配方由 SWE-bench 确立：从公开 GitHub 仓库里挖已合并的修复（fix），用修复自带的测试来打分。这个配方能规模化，但有两个结构性问题：

- **污染**：修复、讨论、测试全部公开，大概率已在预训练语料里。高分可能反映"背过"而非"会解"。The SWE-Bench Illusion 一文的诊断实验给出了直接证据：SOTA 模型仅凭 issue 描述就能以 76% 准确率指出出错文件路径（对照的未入选仓库只有 53%），目标函数的连续 5-gram 逐字复现率也显著更高——模型见过这些题。
- **继承测试不适合当评分器**：这些测试是为确认某一次特定补丁而写的，不是为评判任意新解法写的。审计发现它们既会拒绝合理的替代方案（过严），也会放过不完整的修复（过松）。

### 1.3 2026 年：两条路都撞墙了

2026 年，这两个问题变得无法回避：

- **2026 年 2 月**，OpenAI 宣布停止报告 SWE-bench Verified 成绩：对 138 个难题的审计发现 **59.4% 存在测试或题面缺陷**，且所有被测前沿模型都能逐字复现 gold patch 或题面细节——训练数据里确实有答案。
- **2026 年 7 月**，OpenAI 对自己两个月前推荐的接替者 SWE-bench Pro 再举红牌：估计**约 30% 任务有缺陷**（测试过严、覆盖率低、题面误导/欠指定），撤回推荐并呼吁"由经验丰富的软件开发者构建、全程有人类监督"的新评测。

另一条战线上，即使任务质量过关的基准也开始**失去分辨力**：在 DeepSWE v1.1 排行榜上，Claude Opus 5.5、GPT-6 Astra、DeepSeek V4.1 Flash、Gemini 3.8 Flash 四个模型挤在 **0.9 分**之内（72.3% 到 71.4%）。头部挤成一团的基准无法分辨配置优劣——做得再好也没用。

### 1.4 缺口

论文的原话概括得最准确：缺的是一个"**没有任何模型见过其解法**"的基准——由熟悉代码库的工程师为基准专门撰写、从不作为修复公开发布、按维护者审 PR 的方式打分、且大部分保密。

这就是 ExpertCrowd-SWE（下称 EC-SWE）的出发点。

## 二、论文定位和关联工作

### 2.1 SWE-bench 谱系：挖矿路线的演化

SWE-bench（2024）从 12 个 Python 项目的合并 PR 中挖出 2,294 个实例，确立了"issue 文本 + 仓库状态 → 通过 FAIL_TO_PASS/PASS_TO_PASS 测试"的形式。后续演化包括：SWE-bench Verified（人工筛出 500 题，成为事实上的行业标准，直至 2026 年 2 月退役）、Multi-SWE-bench（多语言）、SWE-bench Multimodal（视觉软件域）、SWE-bench Pro（长周期企业级问题，公开/保密/商业三划分）、SWE-smith（规模化合成任务实例）。EC-SWE 保留了"仓库级、可执行评分"的框架，但把**任务来源从挖矿换成原创**、把**评分器从继承测试换成作者手写 rubric**——正好是对审计暴露的两大缺陷的正面回应。

### 2.2 原创（非挖矿）任务路线

- **Aider polyglot**：225 个短练习，多语言，但规模小、任务短。
- **Terminal-Bench**：跨域终端任务，软件工程只是其中之一。
- **APEX-SWE**：专家撰写集成与可观测性任务。
- **FrontierSWE**：少量超大开放问题，rubric 部分得分评分——与 EC-SWE 的评分哲学相近。
- **DeepSWE**：最直接的近邻。113 项原创、从未合并的任务，91 个仓库，5 种语言，手写功能验证器评分，所有模型统一 bash-only harness；独立 LLM 裁判复审显示其评分器与裁判分歧率仅 1.4%（对比 SWE-bench Pro 继承测试的 32.4%）。但它是二元 pass/fail 评分，且在 v1.1 上前沿模型已经头部挤团。

EC-SWE 与 DeepSWE 的三点差异：**rubric 部分得分而非 pass/fail**；**作者是深耕该代码库的领域专家**（而非泛化写手）；**发布集显式按"对当前前沿模型的难度"筛选**。

### 2.3 污染防护三家族

1. **持续收集**：只收训练截止之后出现的任务（SWE-bench-Live、LiveCodeBench、SWE-rebench 等）——治标，防不住推理阶段的泛化记忆。
2. **访问控制**：私有/商业划分（SWE-bench Pro 的 858 项 held-out）。
3. **原创作者身份**：参考解从未进入公开记录（DeepSWE、EC-SWE）。

EC-SWE 三管齐下：原创 + 76/100 保密 + 对 93 个公开基准数据集（499,647 条任务记录）做相似度筛查。

### 2.4 评分器与 harness

评分方面，挖矿基准的继承测试被审计判定既过严又过松；DeepSWE 换成从任务规格手写的功能验证器；EC-SWE 同样从规格出发，但**分解为加权准则 + blocker 封顶 + gate 一票否决**。harness 方面，同一模型在不同脚手架下分数不同，DeepSWE 用"人人只有 bash"消除混杂，EC-SWE 反其道——人人用**自己厂商原生训练过的工具接口**，但统一在同一平台 harness、同一容器、同一预算下运行。

### 2.5 定位总结

| 维度 | 挖矿路线（SWE-bench 系） | 原创路线（DeepSWE 等） | EC-SWE |
|---|---|---|---|
| 任务来源 | 公开已合并修复 | 原创、从未合并 | 熟悉该库的专家原创变更请求 |
| 评分 | 继承测试（二元） | 手写功能验证器（二元） | 作者 rubric：部分得分 + blocker + gate |
| 污染防护 | 无/持续收集 | 原创作者身份 | 原创 + 76 保密 + 93 数据集筛查 |
| 头部分辨力 | 已饱和/挤团 | v1.1 上 0.9 分之内 | 七模型拉卡 35 分、四个统计层级 |
| 质量保障 | 事后审计（59%/30% 缺陷） | LLM 裁判审计 | 构建时强制校准 + 三类对照补丁 + 高级工程师 QC |

## 三、问题定义

### 3.1 从具体场景到抽象问题

具体问题是：怎么造一个能可信地比较前沿编码智能体的基准？抽象之后，它其实是一个测量学问题——**构造一个测量仪器，使其同时满足效度（测的是真实工程能力而非记忆）、信度（评分器本身不出错、结果可复现）与分辨力（能区分头部模型）**。

### 3.2 形式化定义

- **给定**：一组前沿模型 M、一个带评分函数的发布任务集 T。
- **求**：一个评分函数 r 和任务构建协议，使得 S(m) = 任务宏观平均分，能作为模型 m 真实自主工程能力的无偏、可分辨估计。
- **约束**（即三大前提的落地）：
  1. 每个任务 t 的参考解与讨论从未公开（效度——防记忆）；
  2. 评分器接受一切合理正确解、拒绝错误解（信度——评分器正确性）；
  3. 任务难度来自推理而非隐藏信息，且难度足以分开头部（分辨力）。

### 3.3 这个抽象的精妙之处

论文的关键洞察是把"维护者会不会合并这个 PR"作为评分函数的语义锚点：正确性、回归、范围、测试质量、可维护性，全部收拢进一个从业者熟知的判断里。这个锚点使"评分器该长什么样"（rubric + blocker + gate）、"任务该怎么写"（像资深工程师派活那样说 what 不说 how）都有了统一的判定标准——测量仪器的每一件零件都对齐同一个真实世界的原型。

## 四、问题解法

EC-SWE 的构建分五个阶段：专家撰写任务 → rubric 评分器 → 校准与质检 → 污染防护 → 难度筛选与统一评测。

### 4.1 设计原则：把"维护者的合并标准"写进规则

任务四要素：真实（真实团队会要的变更，说想要什么、绝不说怎么做）、可解（作者的参考解证明可做）、可评（机器能分辨对错）、可复现。难度守则有正反两面：

- **四个合法难度来源**：跨模块综合、真实权衡（提速必须付出 ticket 说要保留的东西）、可发现的仓库不成文约定、链式工作（早期决策影响后续步骤）。作者被鼓励组合两类工作（如性能 × 错误处理、并发 × 日志、迁移 × 向后兼容），只练单方面的任务通常太简单。
- **四个非法难度来源**：仓库里无处可查的事实、题面未暗示的唯一实现方式、一个文件泄露全部答案、agent 能读到的评分器/参考解。

难度来自推理而非藏信息——这是效度约束在任务设计层的落地。

### 4.2 专家招募与撰写流程

作者来自 Toptal 3 万+ 专家网络，按编译器与语言工具、系统/后端/网络、数据库与存储、SRE/DevOps 四个领域招募，39 人参与撰写，最终 100 项任务出自 17 人。流程是两段式**先草案后构建**：

1. **草案**：提交仓库 + 精确 pin 的 commit hash（绝不给分支名）、写成 ticket 的题面、评分计划（哪些检查、哪些必须过）。评审员批准前什么都不构建，"差不多"等于不批准。草案被打回的理由：不可读、规定了实现、缺评分计划或只靠 AI 裁判、作者自己没解过这道题。
2. **构建**：在 HUD 模板上构建环境、参考解与评分器；自证参考解 100% 而原样仓库 0%；并对一个前沿模型跑五次——全零也必须人工核查（五个零分同样可能是评分器坏了）。AI 可以帮接环境，但**不允许碰任务创意和参考解**。

提交后被拒的记录原因：参考解从未测过（4）、评分器弱/坏/只有主观意见（3）、任务或仓库太小（3）、提交不完整（2）、1 道不可能完成的任务。

### 4.3 任务解剖：四件套

| 组件 | 内容 | 关键细节 |
|---|---|---|
| Prompt | 环境前导（约 2 vCPU、硬内存上限、沙箱离线、如何启动依赖服务、隐藏测试打分且不许改现有测试）+ 作者 ticket | 中位 148 词（39-768） |
| Environment | Docker 镜像：pin 在 commit 的仓库（历史封存，后续上游提交不可读）、工具链、预置依赖缓存；agent 以非特权用户运行；一切"答案形状"的东西（参考解、隐藏评分器、规格文件、纯净检出）放在 agent 读不到的 root-only 目录 | 中位参考解改 471 行、横跨 4.5 个文件 |
| Reference solution | 作者自己的补丁（task/gold.diff），密封于镜像内，仅用于校准与审查 | 98 项是公共开源项目上的全新变更 |
| Grader | 加权准则 + blocker + gate，密封执行：无网络、不依赖墙钟、无随机性；需要 Redis/数据库时评分器自己在镜像内私网端口起实例 | 每任务中位 10 条加权准则（1-26） |

任务四条来源路线全部服从同一组污染规则——绝不基于已公开修复的 bug、绝不用雇主/客户代码、变更保持未发表、自有代码仅在拥有权利时使用：专家在熟悉公共仓库上的经验变更、长期未决的上游 issue（但参考解是作者自己的）、作者 fork 后加的未公开提交、作者自有代码库。100 项任务覆盖 87 个开源项目、11 种语言（Go 36、TypeScript 18、Python 15、Java 7……），82 个 base commit 落在 2026 年 8-9 月（中位日期 9 月 4 日）——新鲜到模型几乎不可能在训练数据里见过其上下文。

### 4.4 评分：rubric + blocker + gate

类比：**rubric 评分 ≈ 维护者的 code review 清单**。三类规则合起来模拟"would you merge it?"：

- **加权准则**：命名准则带权重、总和恰为 1.0，得分是加权和——部分得分。绝大多数是经公共接口（库 API、服务行为）的可执行检查，刻意避开实现内部检查，让任何合理实现都能拿满分。
- **Blocker（封顶）**：作者标记的必过准则。失败则本次运行分数被**封顶在 κ（如 0.60）以下**而非清零——缺了本质属性的改动不能靠其他准则拿高分，但也不抹掉其余正确部分。
- **Gate（一票否决）**：不带权重、不可交易的 pass/fail 前置条件，如"仓库自带测试保持绿""仓库自带测试未被改动"。任一 gate 失败，本次运行记 0 分。14 项任务使用 gate。

形式化（对模型 m、任务 t 的第 j 次运行）：任一 gate 失败 → r = 0；否则若有 blocker 失败 → r = min(Σwᵢcᵢ, κ)；否则 r = Σwᵢcᵢ。

LLM 裁判准则被刻意压到极小：仅 10 个任务使用，占各自权重 2%-25%（平均 8.5%），占全基准总权重 0.85%；其余 90 项任务完全由确定性检查评分。

### 4.5 质量保障：把校准焊进构建流程

这是 EC-SWE 最硬核的部分——评分器的正确性不靠事后审计，而是**构建时强制**：

1. **构建时校准**：镜像构建过程用真实评分器给三个对象打分——参考解必须恰好 1.00 且每条准则单独通过；原样仓库和惰性改动（只加注释）必须恰好 0.00 且每条准则单独失败。任一不满足，**构建直接失败**。
2. **对照补丁**：近半任务还随附三类显式对照——可选的合理解（必须通过，35 项）、对抗/作弊补丁（必须失败：改测试、特判评分输入、禁用被测功能，30 项）、惰性/no-op 补丁（必须低分，42 项）。评分器必须全部正确分类。
3. **高级工程师 QC**：每个任务由资深工程师检查题面、环境、参考解、评分器与诊断性模型运行，通过才授予平台 verified 状态。

### 4.6 污染防护与评测协议

污染防护三层：任务变更未发表（作者身份层）、76/100 保密（访问控制层）、与 93 个公开基准数据集的 499,647 条任务记录做 commit/标识符匹配与题面代码语义相似度比对，最接近的对子由 LLM 裁判复核（筛查层）；并持续监控上游仓库是否出现与参考解重叠的变更。

评测协议：七个前沿模型，全部为平台默认高强度推理档、空 agent 参数、无系统提示；统一 HUD hosted runner + HUD SDK（v0.6 系列），每模型每任务 5 次、每次限 1,000 步；只计最近五次有效完整运行，触碰步数/输出 token 上限的运行被剔除重跑（Opus 27 次、Gemini 55 次、Grok 2 次，Gemini 因此有一题无有效运行、按 99 题计分）。最终 3,495 次有效运行，采集于 2026 年 10 月 1-10 日。值得注意的 harness 选择：**不搞人人 bash，而是人人用自己厂商原生的工具接口**（如 Anthropic 的 bash+str_replace 编辑、Gemini 的七件套、OpenAI-compatible 系的六件套），但任务、题面、容器、资源、步数预算、评分器全部共享——测的更接近"这个模型被训练成的样子"。

### 4.7 方法全景

| 阶段 | 机制 | 对应前提 |
|---|---|---|
| 任务撰写 | 专家在熟悉仓库上原创变更请求，禁公开修复 | 效度（防记忆） |
| 评分 | rubric 部分得分 + blocker 封顶 + gate 否决 | 信度（模拟维护者审查） |
| 质保 | 构建时校准 + 对照补丁 + 高级工程师 QC | 信度（评分器正确性） |
| 防污染 | 未发表 + 76 保密 + 93 数据集筛查 | 效度 |
| 筛选 | 按对当前前沿模型的难度选final 100 | 分辨力 |
| 评测 | 单平台 harness、原生工具、5 次 × 7 模型 | 信度 + 可比性 |

## 五、评估指标与实验证据

### 5.1 指标体系

- **主指标**：宏平均任务分 S(m)（每任务先取 5 次运行均值，再对任务等权平均），附任务抽样 95% 区间（headline，回答"换一批同样合理的任务分数会怎么动"）。
- **配对检验**：2,000 次任务 bootstrap + 20,000 次 sign-flip 置换检验（Holm 校正）——因为所有模型在同批任务上评分，排名主张必须以配对检验为准。
- **运行间区间**：五个 run 槽位分别算分再取波动，仅捕捉固定任务集上的 agent 采样噪声（为与 DeepSWE/Terminal-Bench 可比而报）。
- **可靠性辅助指标**：五次最优均值、满分运行占比、≥1/5 满分的任务数（pass@5 类比）、5/5 满分任务数、任务内运行分标准差；另报每运行步数（模型轮次）与容器时长。

### 5.2 主结果：35 分差距、四个统计层级

| 模型 | 得分（95% CI） | 运行间 CI | 满分运行 | ≥1/5 与 5/5 任务 | 任务内 SD |
|---|---|---|---|---|---|
| Claude Opus 5.5 | **67.3 ± 4.7** | ±1.9 | 26.6% | 47 / 9 | 13.6 |
| GPT-6 Astra | **63.7 ± 5.5** | ±1.5 | 23.4% | 36 / 15 | 7.3 |
| Claude Fable 5.1 | 46.5 ± 3.7 | ±0.4 | 8.6% | 25 / 1 | 16.9 |
| Gemini 3.8 Flash | 40.0 ± 4.3 | ±1.5 | 3.8% | 9 / 1 | 11.0 |
| Qwen 3.8 Max | 33.5 ± 3.3 | ±1.4 | 1.0% | 5 / 0 | 10.9 |
| DeepSeek V4.1 Flash | 32.5 ± 3.7 | ±1.4 | 3.0% | 9 / 0 | 13.0 |
| Grok 4.6 | 32.2 ± 3.5 | ±1.2 | 1.0% | 4 / 0 | 10.1 |

七模型均值 45.1%。配对检验分出四个统计显著层级：Opus 与 GPT-6 统计上不可分（差 3.6 分，配对 CI [-1.4, +9.7] 含零，p = 0.20；逐任务胜负 53/6/41）；两者显著领先 Fable（Opus 在 82/100 任务上胜 Fable，+20.8 分）；Fable 领先 Gemini（+6.5）；Gemini 领先底部三人组（+6.5 over Qwen）；Qwen/DeepSeek/Grok 两两之间区间全部含零、不可区分。

这个设计的证明力在于分辨力本身：同一批四个模型（Opus、GPT-6、DeepSeek、Gemini）在 DeepSWE v1.1 上只差 0.9 分，在 EC-SWE 上拉开 **34.8 分**——作者注明两个基准在指标、harness、任务总体上不同，此对比是指示性的而非受控实验，但与"EC-SWE 分辨出了既有榜单分不出的差异"一致。DeepSeek 的错位最刺眼：DeepSWE 上第三，这里第六。

### 5.3 任务级难度与余量

没有任何任务被七个模型全部满分解决；80/100 任务上没有任何模型能五次全部满分；两个领头模型共同满分的仅 4 题、共同跌破 60% 的却有 20 题。任务七模型均值从 2.5% 到 69.5%（中位 46.2%），9 题连最佳模型都均分不足 50%。最难的题是 CirC 编译器的 SystemVerilog 导出，七模型全部落在 2.3%-2.7%。

两个领头模型是**互补而非有序**：任务分相关仅 r = 0.42，14 题上分差 ≥40 分（8 题利 Opus、6 题利 GPT-6）。

### 5.4 部分得分的必要性（二元评分的死亡区）

满门抄斩式的证据在 5.2 表的"满分运行"列：Gemini、Qwen、DeepSeek、Grok 的满分运行占比只有 1.0%-3.8%。**若用二元 pass/fail 评分，这四个模型将全部被压进 1%-4% 的窄带**；有了部分得分，它们展开为 32.2%-40.0%，且 Gemini 明显领先另外三个。论文选取部分得分的最直接理由就是这一条。

运行级分布进一步支撑：两个最强模型的大多数运行至少拿 0.4（Opus 83%、GPT-6 78%），但满分率分别只有 26.6%/23.4%；底部组的典型运行拿到任务权重的五分之一到一半——"大部分完成"与"几乎没做"在部分得分下是两种颜色，在二元评分下是同一种。

### 5.5 blocker/gate 的因果证据：维护者规则捕捉什么

全部 3,495 次运行中，274 次（7.8%）被 blocker 封顶、80 次（2.3%）被 gate 清零。代价集中于最强模型（它们未封顶的准则分本来就高）：去掉这两类规则，Opus +3.7 分、GPT-6 +2.9、底部组 +1.1 到 +2.9，**排名不变**。

最有说服力的单点证据是 Asynq 任务（任务取消与 handler 结果的交互）：Opus 和 Grok **五次全零**，DeepSeek 均分 75.6%——因为 gate 拒绝"改仓库自带测试让套件变绿"的行为，而这恰是 test-only 评分会奖励的行为。强弱模型在这里发生了翻转。

### 5.6 三个不确定性口径的分离

任务抽样区间（±3.3 到 ±5.5）是运行间区间（±0.4 到 ±1.9）的 **2-10 倍**：在固定 100 题上重跑，分数几乎不动；不确定性主要来自"这批任务选了哪些"。论文由此点名：只报运行间区间的榜单会系统性低估排名对任务抽样的依赖。

### 5.7 努力与可靠性：步数不等于能力

每运行步数中位数相差五倍：GPT-6 只要 33 步（中位容器 36 分钟），Gemini 166 步。步数与成绩几乎无关——GPT-6 用 Opus 约五分之一的步数拿到其 95% 的分数；Gemini 步数最多、成绩第四；每模型内部步数-分数相关系数仅 -0.15 到 +0.17。Qwen 中位容器时长反而最长（100 分钟）。可靠性的分化同样有意思：GPT-6 任务内波动最小（SD 7.3）、5/5 满分任务最多（15 题）；Opus 达峰更广（≥1/5 满分 47 题）但更抖（SD 13.6）——能多次采样并验证的用户该选 Opus 的广度，单次要稳的用户该选 GPT-6 的稳定。若只计五次最优，Opus 升至 80.9%、GPT-6 71.4%、Fable 66.7%。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

EC-SWE 的"效果"体现为三个测量学性质的跃升：分辨力（35 分差距 vs 0.9 分挤团）、评分器信度（构建时保证）、效度（防污染）。逐一拆因果：

**机制一：难度来自"陌生代码库 × 跨模块综合 × 真实权衡"，而非隐藏信息或单点知识。**
因果链：任务设计守则（组合两类工作、四个合法难度来源）→ 模型无法靠检索单文件或回忆公开修复得分，必须做跨模块规划与权衡 → 头部模型能力差异被展开到 35 分、形成四个统计层级。论文实验支持点：二元评分下底部四模型挤在 1-4%，而部分得分下展开为 32-40%——说明任务本身就在区分"做了多少"，只是二元指标把分辨率扔掉了；80/100 任务无人五次满分、最难任务七模型全趴在 2.3-2.7%，说明难度筛选（final 100 按对前沿模型的难度选出）真实生效。

**机制二：部分得分 + blocker 封顶 + gate 否决，把"维护者审查"的结构嵌入评分函数。**
因果链：二元评分把分数分布压成两点 → 信息损失（底部四模型 1-4% 死区）→ 加权准则恢复"完成度"维度 → 但纯加权会奖励"缺本质属性但其他都沾边"的解 → blocker 封顶堵住这条路，同时不像清零那样抹掉其余正确工作 → gate 把"不可交易的条件"（不改仓库测试）从权重体系里拿出来一票否决 → 评分函数与维护者合并决策对齐。证据：7.8% 运行被封顶、2.3% 被清零；Asynq 任务上 Opus/Grok 全零而 DeepSeek 75.6%——test-only 评分会奖励的改测试行为在这里被判负，强弱模型发生翻转，证明 gate 捕捉的是既有评分体系系统性放过的行为。反事实验证也在论文内：去掉 blocker/gate，Opus 损失 3.7 分、排名不变——说明这套规则改变的是分数的"语义"（什么被奖励）而非模型排序，正是一个好评分规则应有的性质。

**机制三：评分器信度靠构建时强制校准，而非事后审计。**
因果链：SWE-bench 系的信度问题被两轮审计（59.4%、约 30% 缺陷）暴露 → 缺陷源头是"评分器与任务一起挖出来、无人对评分器本身负责" → EC-SWE 把评分器变成作者的作品（rubric 由写 ticket 的人写）→ 构建管线把"参考解=1.0、原样=0、惰性=0"变成 build 通过的硬条件，三类对照补丁（替代解必须过、作弊解必须挂、懒惰解必须低分）再围一圈 → 评分器错误无法进入发布集。证据：对照补丁覆盖 35/30/42 项任务、全部正确分类是构建前提；发布前另有高级工程师逐任务 QC。这是把"CI 红灯"哲学用于测量仪器。

**机制四（防污染）：原创 + 保密 + 新鲜 base commit。**
因果链：挖矿任务的解在公开记录里 → 训练必然见过（Illusion 文的 76% vs 53% 文件定位差、gold patch 逐字复现）→ EC-SWE 变更从未发表（无公开解）、76 题保密（即使公开 24 题被吸入语料也不影响大盘）、82/100 base commit 是 2026 年 8-9 月的新提交（上下文新鲜）→ 高分只能来自问题解决。论文诚实标注边界：仓库本身公开且大概率在训练数据里——EC-SWE 测的是"在眼熟的代码上解题"，不是"在从未见过的代码上解题"。

### 6.3 综合判断与未决问题

**得到多项研究共同支持的机制**：原创任务防污染（DeepSWE 同做法 + Illusion/两轮审计的反面证据链）；评分器需要专属作者与强制校准（OpenAI 两轮审计的结论 + DeepSWE 验证器低分歧率 + EC-SWE 构建时校准）；任务抽样方差主导排名不确定性（Madaan、Terminal-Bench、本文实测 2-10 倍差）。

**仍属合理推测的部分**：EC-SWE 相对 DeepSWE 多出的分辨力具体有多少归因于部分得分、多少归因于任务难度筛选、多少归因于 harness 差异——论文自己的对照（同批四模型 0.9 vs 34.8 分）是指示性而非受控的，作者明说这一点；若在统一 bash harness 下重跑，层级结构是否保持，尚无数据（列为未来工作）。原生工具 harness 可能的混淆也未被排除。

**适用条件与失效条件**：优势成立的前提是"维护者标准"确实是想要的测度——若应用场景只在乎"测试变绿"（如 CI 门禁），gate 语义反而是保守的。公开的 24 题最终会进入训练语料，保密的 76 题是基准寿命的真正载体；若上游仓库未来合入了与参考解重叠的变更，对应任务的效度会衰减（论文表示会持续监控）。100 题的任务抽样区间 ±3.3-±5.5 意味着相邻模型 5 分以内的差距不应过度解读——这是仪器精度的诚实标定。

## 七、必要知识反推

假设让一个零基础的人从零做出 EC-SWE，最少需要哪些知识？

### 7.1 领域知识层（软件工程本身）

- **真实工程变更的形态**：知道资深工程师怎么派活（说 what 不说 how）、一个 148 词的 ticket 对应 471 行、4.5 个文件的改动是什么规模感——否则无法设计"现实"的任务，也无法识别哪些难度是伪难度（藏信息）。
- **维护者审查的判断结构**：知道 code review 里哪些是可协商的（实现方式）、哪些是不可交易的一票否决（改别人的测试来让套件变绿）——这是 rubric/blocker/gate 三分法的原型。不理解这一层，评分函数就没有语义锚点。
- **跨语言工程生态**：从 Go、TypeScript 到 C++、Elixir 的 11 种语言、87 个项目的构建/测试/依赖管理方式，否则环境模板做不出来。

### 7.2 方法论知识层（评测科学）

- **基准测量学**：效度/信度/分辨力的三角，任务抽样方差与运行噪声的区分——否则不会想到把构建校准做成硬条件、把三口径不确定性分开报。
- **既有基准的失效模式**：SWE-bench 系的污染机制（gold patch 进语料）、继承测试的过严/过松、审计方法本身——EC-SWE 的每一个设计决定几乎都是对某条失效模式的直接回应。不知道病灶在哪，就开不出这份处方。
- **统计检验**：配对置换检验 + bootstrap + Holm 校正的适用条件（同批任务上配对才锋利），宏平均与微平均的选择——否则"四个层级"无从谈起。
- **LLM 裁判的偏差与局限**：知道为什么 LLM 判分要压到总权重 0.85% 以下。

### 7.3 工程知识层（系统实现）

- **容器化与密封执行**：Docker 镜像、root-only 目录、历史封存、离线沙箱、非特权用户——"答案不可读"要靠文件系统权限而非君子协定。
- **可复现评分器工程**：无网络、无墙钟、无随机性、依赖服务在镜像内私网端口自起——评分器的确定性是被工程出来的。
- **CI/CD 哲学的迁移**：把"测试不过就不许合并"改造成"校准不过就不许构建镜像"——这是本论文最漂亮的工程化洞察之一。
- **平台化评测**：统一 harness、推理网关、运行轨迹全量录制、步数/时长遥测——七个模型可比的前提是这些共享。

### 7.4 知识融合的关键节点

1. **"维护者会不会合并"作为评分函数的原型**：把软件工程的实践判断（7.1）与测量学的效度要求（7.2）焊接在一起——单一锚点统一了任务设计、评分结构与质量控制的标准。
2. **构建时校准**：把 CI 红灯哲学（7.3）用于测量仪器信度（7.2），评分器从"被审计的对象"变成"不通过就不存在的东西"。
3. **对照补丁分类学**：把对抗性思维（作弊补丁会怎么作弊？）与评分学（什么该过、什么该挂、什么该低分）融合，事先枚举评分器的失败模式。
4. **三口径不确定性**：统计方法论与榜单工程实践的结合——headline 用任务抽样区间，是把"这个排名有多依赖题目选择"诚实地写在脸上。

## 八、论文中可以提取的通用性灵感

### 灵感一：把评分器的正确性做成构建的硬门，而不是事后审计的对象

- **核心思想**：测量仪器的质检应该内嵌在仪器生产流程里（不过检就不出厂），而非依赖出厂后的抽检。
- **论文证据**：镜像构建时强制"参考解=1.0、原样=0、惰性=0"，否则构建失败；对照补丁必须被正确分类；对比之下 SWE-bench Verified/Pro 的事后审计分别发现 59.4%/约 30% 缺陷。
- **推广场景**：① 数据集构建管线（每条数据入库前过自动校验）；② LLM 评估流程（judge 先在标注对照集上过校准再上岗）；③ 教育测评（题库入库前必须通过区分度校准）；④ 任何"评估者本身也需要被评估"的两层系统。

### 灵感二：部分得分是高难度任务上保留分辨力的必要条件

- **核心思想**：当被测对象普遍做不完整时，二元指标会把它们压进同一个死区；加权细则能把"完成度"这个维度还回来。
- **论文证据**：底部四模型满分率 1.0-3.8%，二元评分下将全部落在 1-4%；部分得分下展开为 32.2-40.0% 且分层清晰。
- **推广场景**：① 机器人长程任务评测（任务完成 60% 与 5% 应有区别）；② 数学证明评测（证出一半引理应得部分分）；③ 招聘技术面评估；④ 自动驾驶路段通过率——一切"全对或全错"过于奢侈的领域。

### 灵感三：用"不可交易条件"分离可协商与不可协商的评价维度

- **核心思想**：加权求和隐含"一切皆可交易"；真实评审中存在一票否决项，应把它们从权重体系中拿出来单独建模。
- **论文证据**：gate（不改仓库测试、自带测试保持绿）使 2.3% 运行清零，捕获了 test-only 评分会奖励的行为——Asynq 任务上 Opus/Grok 全零而 DeepSeek 75.6%，强弱翻转。
- **推广场景**：① AI 安全评估（安全红线不可用能力分换算）；② 医疗诊断系统评估（误诊某类为不可接受项）；③ 推荐系统（合规维度 gate 化而非加权）；④ 合同条款评审自动化。

### 灵感四：防污染 = 原创作者身份 + 访问控制 + 相似度筛查，三层缺一不可

- **核心思想**：评测集的效度寿命需要"源头无泄（原创）+ 中途可控（保密）+ 事后可查（对 93 个数据集做筛查）"的纵深防御。
- **论文证据**：变更从未发表、76/100 保密、对 499,647 条公开任务记录做 commit/标识符/语义相似度筛查；对照 Illusion 文揭示挖矿基准 76% vs 53% 的记忆差距。
- **推广场景**：① 企业内部能力测评题库管理；② 竞赛出题（Olympiad/CTF 的防泄漏流程）；③ 模型红队测试集；④ 招笔试题的版权与保密管理。

### 灵感五：效度要义是"难度来自推理，不来自隐藏信息"

- **核心思想**：一份好的难题清单要显式列举合法与非法的难度来源——藏信息制造的难度测的是运气或读心术，不是能力。
- **论文证据**：四个合法来源（跨模块综合、真实权衡、可发现约定、链式工作）与四个非法来源（无处可查的事实、未暗示的唯一实现、泄题文件、可读的评分器）构成作者守则。
- **推广场景**：① 面试题设计（禁止考点在题面外）；② 教育考试的命题规范；③ agent 环境设计（可探索性要求）；④ 密码学训练题（难度应在推理不在黑箱）。

### 灵感六：报告"任务抽样方差"是榜单的诚实义务

- **核心思想**：在固定题集上重跑得到的稳定性会系统性地高估结论的可迁移性；headline 应报任务抽样区间。
- **论文证据**：任务抽样区间是运行间区间的 2-10 倍；由此警告"只报运行间区间的榜单低估排名对任务样本的依赖"。
- **推广场景**：① 一切公开 leaderboard 的置信区间规范；② A/B 测试结论的样本依赖标注；③ 舆情调查的抽样框架披露；④ 学界 benchmark 论文的报告标准。

### 灵感七：步数、时长与得分应并排报告——努力不是能力

- **核心思想**：当被测系统的"努力量"（步数/时间/成本）与结果相关很弱且个体差异巨大时，效率本身就是独立的测量维度。
- **论文证据**：步数中位数相差五倍（33 vs 166），步数-分数相关仅 -0.15 到 +0.17；GPT-6 用五分之一步数拿到 Opus 95% 的分。
- **推广场景**：① agent 产品选型（延迟敏感场景）；② 推理模型评测（思考 token 与正确率的帕累托前沿）；③ 云成本核算；④ 人效度量体系。

## 附录：一页速查

- **规模**：100 任务（24 公开/76 保密）、87 项目、11 语言；ticket 中位 148 词，参考解中位 471 行/4.5 文件；39 人撰写、17 人入选；每任务中位 10 条加权准则。
- **三大评分规则**：加权准则（部分得分）→ blocker（失败则封顶 κ，如 0.60）→ gate（失败即 0 分，14 任务使用）。
- **校准铁律**：参考解必须 1.00、原样仓库与惰性改动必须 0.00，否则镜像构建失败；三类对照补丁（35 替代/30 对抗/42 惰性）必须被正确分类。
- **结果速记**：Opus 67.3 / GPT-6 63.7（p=0.20 不可分）/ Fable 46.5 / Gemini 40.0 / Qwen 33.5 / DeepSeek 32.5 / Grok 32.2；均值 45.1；四层级；35 分总跨度；对照 DeepSWE v1.1 同批四模型 0.9 分。
- **一句话**：让熟悉代码库的工程师出题，让评分器像维护者一样审查，让校准不过就构建失败——测量仪器的可信度是被设计出来的，不是被审计出来的。
