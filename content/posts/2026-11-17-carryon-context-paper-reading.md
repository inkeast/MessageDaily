## 一、论文背景

### 1.1 从 LLM Agent 说起

大语言模型（LLM）Agent 是一类让模型不再只回答一次问题、而是**连续做多步决策**的系统：模型观察环境返回的结果（observation），决定下一个动作（action，通常是调用某个工具或 API），执行后再观察、再决策，循环往复直到任务完成。这种『推理—行动』交织的范式由 ReAct（[arXiv:2210.03629](https://arxiv.org/abs/2210.03629)）确立，如今已是编码助手、办公自动化、客服机器人等应用的基本骨架。

**长程（long-horizon）任务**指的是需要几十甚至上百步才能完成的任务。论文开篇给了一个例子：『通过 Venmo 给我每位同事转 20 美元，备注 For Lunch，如果余额不够请先充值』。完成它需要：找到所有同事的账号 → 查余额 → 可能绑一张新卡 → 充值 → 逐笔转账。在论文记录的真实轨迹中，第 9 步查到的同事账号记录，要到第 33 步才真正用上。

### 1.2 上下文：Agent 的桌面，也是 Agent 的账单

模型每次被调用时能看到的全部文字叫做**上下文（context）**。对 Agent 来说，上下文通常包含：任务描述、系统指令、工具定义，以及**到目前为止的全部交互历史**（每一步的动作和环境返回）。

这里有两个现实约束：

1. **成本约束**：LLM 按输入 token 计费，且每次调用都要重新提交完整上下文。历史越长，第 N 步的一次决策就要为前 N-1 步的历史全部付费，成本随步数线性膨胀。
2. **注意力约束**：无关信息会稀释关键信息的权重。长上下文中的『迷失中间』（Lost in the Middle）现象表明，模型对位于输入中部的信息利用率明显偏低（见 [arXiv:2412.10079](https://arxiv.org/abs/2412.10079) 在多跳问答中的复现）。

于是业界提出了**上下文工程（context engineering）**这一概念——LangChain 把它定义为『在 Agent 轨迹的每一步，往上下文窗口里装恰好合适的信息的艺术与科学』（[blog](https://www.langchain.com/blog/context-engineering-for-agents)），Anthropic 也发布了同主题研究文章（[链接](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)）。核心问题只有一个：**每一步该让模型看见什么？**

### 1.3 已有路线与共同困境

| 路线 | 代表做法 | 问题 |
|---|---|---|
| 全量保留（Full History） | 什么都不丢 | 输入成本高，长任务后期历史里大量无关记录 |
| 摘要/压缩 | 把旧历史总结成一段话，或按信息量删 token | 摘要必然有损——后续动作需要的往往是**精确数值**（一个 9 位的请求 ID、一个卡号、一个时间戳），一总结就没了 |
| 选择完整交互步 | 挑出若干『步』整段保留 | 一条 API 返回可能有几十条记录，其中只有 2 条与后续相关；整段保留等于把噪声也带上了 |

困境的根源在于一个时序上的两难：**你在第 t 步不可能完全确定第 t+k 步会需要什么**。论文统计了一个数字：在 909 条任务轨迹中，40.2% 的轨迹发生过『先前被剔除的证据后来又被重新选中』。一旦压缩是不可逆的，这类需求就只能靠重新执行之前的交互来弥补——这比省下的 token 贵得多。

这就是本文的出发点：能不能设计一个上下文管理器，**既把上下文压小，又不丢任何将来可能用得上的精确细节，还不在上下文管理本身上再花一次大模型调用的钱？**

## 二、论文定位和关联工作

CarryOn 属于**外部上下文管理器**这条线：管理器独立于执行任务的模型（论文称之为 Actor），通过决定 Actor 每步看什么来工作，**不需要微调 Actor**。下面按研究谱系梳理。

### 2.1 谱系一：通用提示压缩

- **LLMLingua**（[arXiv:2310.05736](https://arxiv.org/abs/2310.05736)）用小语言模型给 token 打困惑度分，从低信息量处删起，最高 20 倍压缩；**LongLLMLingua**（[arXiv:2310.06839](https://arxiv.org/abs/2310.06839)）针对长上下文做了问题感知的改进；**LLMLingua-2**（[arXiv:2403.12968](https://arxiv.org/abs/2403.12968)）把压缩变成 token 二分类，用蒸馏数据训练，压缩器很小很快。
- **关键区别**：这类方法压缩的是『一段给模型的提示』，衡量标准是语义保真；而 Agent 场景需要的是『下一步工具调用的参数能不能原样取到』。后续研究（在扩散语言模型上评估 LLMLingua-2，[DOI](https://doi.org/10.1145/3816713.3818806)）发现：即使语义相似度很高，压缩导致的**信息遗漏**仍会让数学推理大幅退化——语义保真不等于下游可用。

### 2.2 谱系二：Agent 专用压缩/剪枝

- **ACON**（[arXiv:2510.00615](https://arxiv.org/abs/2510.00615)，Meta）在自然语言空间迭代优化压缩指南，把观察和历史统一压缩成简洁表示。
- **SWE-Pruner**（[arXiv:2601.16746](https://arxiv.org/abs/2601.16746)）模仿程序员『选择性略读』，用 0.6B 轻量模型按当前目标提示动态剪掉代码行，在编码 Agent 任务上省 23–54% token。
- **关键区别**：这两者仍是**有损变换**——ACON 产出摘要、SWE-Pruner 产出删减后的文本。论文的案例研究直接展示了它们的失败模式：ACON 的摘要漏掉了 9 个合格付款请求中的 2 个 ID，SWE-Pruner 剪掉了笔记的 tags 和 pinned 两个字段，都导致任务判分失败。CarryOn 保留的是**未改动的原文片段**。

### 2.3 谱系三：历史选择与结构化/分层记忆

- **MemGPT**（[arXiv:2310.08560](https://arxiv.org/abs/2310.08560)）借鉴操作系统分级存储，把上下文分为主上下文与外部上下文，靠模型自主换页；**MemOS**（[arXiv:2507.03724](https://arxiv.org/abs/2507.03724)）进一步把记忆做成可管理的系统资源。
- **AGORA**（[arXiv:2605.26596](https://arxiv.org/abs/2605.26596)）训练打分器**选择完整的交互步**；**ContextWeaver**（[arXiv:2604.23069](https://arxiv.org/abs/2604.23069)）构造步骤间的依赖结构支持选择性检索。
- **关键区别**：选择粒度上，AGORA 以整步为单位（噪声随之而来），CarryOn 细到单条记录；换页策略上，MemGPT 依赖 LLM 自己决定换入换出（引入额外推理），CarryOn 用一个冻结的 0.6B 选择器离线打分，**上下文管理零 LLM 调用**。

### 2.4 谱系四：训练 Actor 自管记忆（对照组路线）

- **MEM1**（[arXiv:2506.15841](https://arxiv.org/abs/2506.15841)）用强化学习训练 Agent 每轮把记忆与推理合并进一个常数大小的内部状态；**HiAgent**（[arXiv:2408.09559](https://arxiv.org/abs/2408.09559)）按子目标组织分层工作记忆；**ReSum**（[arXiv:2509.13313](https://arxiv.org/abs/2509.13313)）用 GRPO 训练模型从摘要上下文中继续执行。
- **关键区别**：这些方法要动 Actor 的权重，对闭源模型不可行，且一个训练出的 Actor 换个环境就要重训。CarryOn 反其道而行：Actor 完全冻结，一个 benchmark 训练出的选择器可以跨 3 个不同厂商的 Actor 复用。

### 2.5 谱系五：评测方法论（本文的另一处贡献）

Kapoor 等人的《AI Agents That Matter》（[arXiv:2407.01502](https://arxiv.org/abs/2407.01502)）批评 Agent 评测只看成功率不看成本；《Efficient Agents》（[arXiv:2508.02694](https://arxiv.org/abs/2508.02694)）提出 cost-of-pass（每次通过的成本）视角。CarryOn 的两个新指标 Sα 与 NCS 正是顺着这条线设计的（详见第五部分）。

### 2.6 定位总结

| 维度 | 之前的路线 | CarryOn 的突破 |
|---|---|---|
| 管理位置 | 训练 Actor 内部记忆（MEM1/HiAgent） | 外挂管理器，Actor 冻结 |
| 保留内容 | 摘要（ACON）或删减文本（LLMLingua/SWE-Pruner） | 未修改的原文证据片段 |
| 选择粒度 | 完整交互步（AGORA）或 token | 观察内部的单条记录 |
| 决策时机 | 一次性压缩/剪除 | 每步重算，被剔除证据可回流 |
| 管理开销 | 可能引入 LLM 调用（MemGPT、ACON） | 0.6B 冻结选择器，零 LLM 调用 |
| 进度跟踪 | 与证据混在同一份上下文里 | 独立的五字段控制状态 |

一句话定位：**CarryOn 把『登机行李』的隐喻做成了一套系统——托运行李（历史档案）始终在，登机箱（证据包）只装本次决策需要的物品，且登机牌（控制状态）永远写着下一步去哪。**

## 三、问题定义

### 3.1 从具体到抽象

具体场景是：一个 Agent 在手机 App、办公软件、客服系统里执行几十步的任务。抽象之后，这其实是一个**逐决策点的信息供给问题**：

> 在每个决策步 t，为一个固定的消费者（Actor）组装一份工作输入 X_t，使得它既能正确行动，又不会为无用信息付费。

形式化：设任务为 q，截至第 t 步的交互档案为 H_t，当前观察为 o_t。求一个组装函数：

```
X_t = Compose(q, m_t, W_t, R_t)
```

其中 m_t 是控制状态（进度），W_t 是从 H_t 中选出的历史证据，R_t 是必须保留的近期交互。约束与目标：

- **给定**：q、逐步增长的 H_t、每步的 o_t；
- **求**：每步的 m_t 与 W_t（以及组装方式）；
- **约束**：不微调 Actor；上下文管理本身不引入额外 LLM 调用；W_t 的体积受预算 B 限制；
- **目标**：最大化任务成功率，同时最小化 token 与调用成本。

### 3.2 核心洞察：上下文里装着两种性质不同的信息

论文最关键的抽象，是发现『上下文』这个笼统概念实际混合了两类信息，而它们的最优处理方式截然相反：

| | 控制状态（进度） | 证据（原料） |
|---|---|---|
| 回答的问题 | 我做到哪了？下一步干什么？ | 具体数值是什么？ |
| 信息性质 | 持久、粗粒度、**可压缩**（用概述就够） | 情境化、细粒度、**不可压缩**（必须原文） |
| 例子 | 已找到 7 位同事，待各转 20 美元 | 某同事的 Venmo 账号、卡号 479 |
| 时变性 | 单调累积（做完的事越来越多） | 需求随时切换（这步要账号，下步要卡号） |

一个贴切的类比是**操作系统**：进程控制块（PCB）是紧凑持久的『状态』，内存页是按需调入的『数据』——没人会把整块磁盘塞进内存，也没人会用一句话摘要代替要处理的数据页。

| 操作系统概念 | CarryOn 对应物 |
|---|---|
| 进程控制块 PCB | 五字段控制状态 MEMORY（≤128 token） |
| 磁盘 / 交换区 | 交互档案 Archive（全量保留） |
| 内存工作集 | 证据包 W_t |
| 按需调页 | 相关性重排 + 临时扩容，每步重算 |
| 驻留集 | 近期保留 R_t（最近 1–2 步必进上下文） |

### 3.3 这个抽象精妙在哪

因为证据需求**随动作变化且不可预知**，任何**一次性、不可逆**的压缩（摘要、删 token）在信息论上必然有损且无法补救。CarryOn 的抽象把问题改写成：**不是决定『丢掉什么』，而是决定『这一步带什么』——档案永远全量在，选择每步都可重做。** 这一步从问题结构上消除了『删错无法挽回』的风险，代价只是维护一个档案（纯存储，不占模型上下文）。

## 四、问题解法

CarryOn 系统由四个部分组成：历史档案（①）、证据选择（②）、带状态的执行（③）、选择器训练（④，离线）。下面逐个拆解。

### 4.1 历史与证据单元：先切碎，再贴上出处标签

原始观察往往是一条大 JSON——比如一次 API 调用返回 47 条付款请求。CarryOn 把每条观察**切分成细粒度证据单元**（例如单条请求记录），每个单元保留三样东西：

1. **原文内容**（不做任何改写）；
2. **来源引用**（它来自第几步交互）；
3. **产生它的动作**（哪个 API 调用返回的这条记录）。

未选中的单元继续留在档案里，后续决策可以再选。这相当于把一整块托运行李改成了带编号的独立包裹，需要哪件取哪件。

### 4.2 双分数选择器：一个管『值不值得带』，一个管『下一步就要用』

选择器基于 Qwen3-Reranker-0.6B（一个 6 亿参数的重排序模型），LoRA 微调后冻结。它读入『任务 q + 最新观察 o_t』作为查询，对每个候选证据单元 u 输出两个分数：

- **相关性分数 r_t(u)**：这个片段与当前决策有多相关？用于排序装填。
- **下一动作使用概率 p_t(u)**：这个片段会不会马上被下一个动作用到？取值 0–1，用于临时扩容。

直觉上这是两个不同的问题：『这段话和任务相关』不等于『下一秒就要引用它』——前者决定进不进基础包，后者决定要不要破格带上。

### 4.3 证据打包与临时扩容：预算内装填 + 破格加塞

每步的打包流程：

1. **预留近期窗口 R_t**：最近一次交互永远保留；若 Actor 上一轮输出了无效动作或状态更新失败，则扩大为最近两次（给它看见自己刚犯的错的机会）。
2. **预算内装填**：基础预算 B = 16,384 字符，减去 R_t 占用后，按 r_t(u) 从高到低装填旧证据，装不下的跳过；若多条片段来自同一次观察，产生它的动作只带一份。
3. **临时扩容**：对没进基础包的单元检查 p_t(u)，凡 p_t(u) ≥ 0.5（阈值 τ）的一律加进来，**允许超出预算**——因为预测它马上就要用，省下的是一次重试。

论文给了一个真实例子：任务是把最爱的菜谱名发给丈夫，丈夫的联系人记录（含电话号码）塞不进基础包了，但选择器给它的下一动作使用概率是 0.695 > 0.5，于是破格加入；Actor 当步就用这个号码发了短信，任务完成。

**每步重算**是回流的来源：这一步没选中的证据，下一步分数重算后完全可能重新入选。论文记录了一个完整案例：一张 Discover 卡记录在第 21 步获得、22–25 步可见、26–28 步被挤出包、第 29 步凭相关性排序**重新回流**，Actor 用它的六个字段绑卡、充值 100 美元，最终在第 33 步完成全部 7 笔转账。

### 4.4 带状态执行：五字段 MEMORY

Actor 每轮输出两样东西：一个动作，和一份**不超过 128 个代理 token**（按词和标点本地计数）的控制状态更新。状态固定五个字段：

| 字段 | 含义 | 示例 |
|---|---|---|
| done | 已完成的工作 | headers、rows 2–3 已填 |
| open | 未了的义务 | row 4 所有列 |
| next | 下一步操作 | 继续填 row 4 |
| answer_mode | 任务是否要求返回值 | none |
| known_apis | 已查过的 API 端点 | calendar、excel |

设计上有一条明确的纪律：**状态里不存精确数值**（密码、长 ID、列表、回执都不进 MEMORY），精确值永远从原文证据里取。状态是导航仪，证据是原料库，两者不混。若状态更新无效或被截断，系统保留上一份状态（宁缺毋滥），并触发近期窗口扩大。

### 4.5 选择器训练：后见之明的监督

片段级的『将来会被用到』标签并不存在，CarryOn 用了两层巧思：

**第一层：用成功轨迹的未来回溯标注过去（future-use labels）。** 在官方训练集的成功轨迹上，用 Claude Sonnet 5 离线生成逐步状态标注（一个比运行时五字段丰富得多的 schema，含执行不变量、已验证事实、工具证据引用等）。一个历史证据单元若是被状态标注引用、或其内容确实出现在后续动作的参数里，就是正例；两者皆无则是弱负例。『下一动作使用』标签则只认紧跟下一个动作就用到的证据。

**第二层：块级训练、片段级推理。** 训练时以完整的『动作—观察』块为候选（与标注引用对齐），损失函数是两项之和：

- 成对排序损失（margin γ=0.2）：正例块分数应高出弱负例至少 γ；
- 下一动作使用的二元交叉熵。

测试时，同一个冻结选择器改给切碎的片段打分——块级监督就这样迁移到了片段级选择，绕开了逐片段标注的成本。

两个阶段训练合计只需单卡 H100 上一小时上下（AppWorld 4.87 小时、OfficeBench 0.59 小时、Tau2 0.79 小时）。**每个 benchmark 训一个选择器，三个 Actor 共用同一个**——这是『管理与执行解耦』最直接的证据。

### 4.6 CarryOn-E：本地部署扩展

附录 I 给出了面向本地部署的变体：冻结 27B 的 CarryOn Actor 作为教师，用 SFT + DAgger 式蒸馏（学生自己跑轨迹，教师为访问到的每个状态补标注）把能力蒸进 Qwen3.5-9B 学生，选择器与保留策略原封不动。9B 学生在三个基准上拿到 47.0% / 46.3% / 67.5% 的成功率——证明这套状态—证据接口本身是可迁移的执行协议。

## 五、评估指标与实验证据

### 5.1 指标体系：成功率之外，还要算账

**主指标：Success（任务成功率）**。按各 benchmark 官方评估器判定，全量任务（含失败任务）为分母。

**辅助指标一：Sα（成功—效率综合分），报告 S0.8。** 动机来自 Kapoor 等人对『只报成功率』的批评：先用 token 与调用成本给成功率打折得到 S0，再与原始成功率按 8:2 混合：

```
S0 = TGC / (1 + 0.5·T̄/B_T + 0.5·C̄/B_C)     （B_T、B_C 为 Full History 的均值基准）
S0.8 = 0.8·TGC + 0.2·S0
```

成功率占 80% 权重，保证『把任务做完』仍是中心，同时奖励更省的执行。越高越好。

**辅助指标二：NCS（归一化单次成功成本）。** 沿 cost-of-pass 思路，把总成本（含失败任务的消耗）除以成功数，再对照 Full History 归一：

```
NCS = 0.5·(C/s)/(C_FH/s_FH) + 0.5·(T/s)/(T_FH/s_FH)
```

调用与 token 各占一半权重，Full History 恒等于 1，越低越好。它专治两种报表错觉：『成功率高但 token 爆炸』和『总成本低但其实早早失败了』。

### 5.2 实验设置

- **基准**：AppWorld（跨 App 数字生活任务，[ACL 2024](https://doi.org/10.48448/aq5q-2n10)，168 个测试任务：57 易 / 48 中 / 63 难）；OfficeBench（办公自动化，95 任务，分 L1–L3）；Tau2 Telecom（对话式客服，40 任务，配用户模拟器）。
- **Actor**：Claude Sonnet 5、Qwen3.8-27B、Gemma-4-31B——三家厂商、三个规模。
- **基线（7 个）**：Full History、FIFO-5（只留最近 5 步）、Retrieval（嵌入检索 4 条历史）、LLMLingua-2（保留率 0.3）、ACON、AGORA、SWE-Pruner（阈值 0.4）。
- 每个设置单次运行；token 计数包含被上下文超限拒绝的输入，选择器等本地小模型的 token 不计。

### 5.3 主结果：9 个设置上的宏平均

| 指标（宏平均） | CarryOn | 最强基线 | Full History |
|---|---|---|---|
| Success | **75.7%** | 69.0%（SWE-Pruner） | 62.4% |
| S0.8 | **68.45** | 65.07（SWE-Pruner） | — |
| NCS | **0.792** | 0.812（SWE-Pruner） | 1.000 |

成功率 9 个设置中 7 次第一、1 次并列第一。几个代表性单点（Success %）：

| 基准 | Actor | CarryOn | 最强基线 |
|---|---|---|---|

两组值得注意的数字：

- **效率增益最纯粹的地方是 OfficeBench**：Qwen 上成功率与 Full History 打平（66.3%），但 NCS 从 1.000 降到 0.476——同样的成功率，单位成功成本几乎砍半；Gemma 上 NCS 低至 0.338。
- **诚实报告的例外**：Tau2 + Claude 上 LLMLingua-2 成功率 80.0% 高于 CarryOn 的 75.0%；AppWorld + Qwen 的 NCS（1.634）也高于 ACON（1.553）。宏平均领先不等于逐项全胜。

**跨 Actor 复用**是实验设计上的关键一环：同一个冻结选择器换三个 Actor 都有增益（如 AppWorld 上 Qwen +19pp、Gemma +3pp），而需要按 Actor 定制的基线（AGORA 的 Claude 标注打分器迁移到 Qwen/Gemma 后从 55.4% 掉到 41.1%）则明显退化。

AppWorld + Claude 上的组件消融：

| 变体 | Success | 说明 |
|---|---|---|
| **CarryOn 完整版** | **79.8** | — |
| w/o MEMORY | 66.1 | 去掉控制状态，**降幅最大**（−13.7pp） |
| Ranking only | 76.8 | 去掉下一动作训练与临时扩容 |

MEMORY 容量敏感性：64 / 128 / 256 代理 token 分别对应 77.4% / 79.8% / 78.0%——128 是甜点，64 截断频繁（284 次截断），256 反而无增益。

### 5.5 行为统计：证据真的在回流吗

- **旧证据占比**：被选中证据中，来源距当前 ≥10 步的占 AppWorld 30.7%、OfficeBench 31.2%、Tau2 48.8%（Tau2 上 Claude 更高达 81.7%）——长程依赖真实存在且被接住了。
- **回流频率**：909 条轨迹中 365 条（40.2%）发生过『证据离开证据包后再次被选中』。
- **临时扩容触发率**：AppWorld 4.4% 的步、OfficeBench 12.2% 的步。
- **调用效率**：宏平均工具调用每任务 16.53 次 vs Full History 18.38 次（−10.1%），Actor 调用 14.99 vs 15.12。

### 5.6 案例研究：有损压缩的三个失败现场

- **Case 1**：批准室友本月全部付款请求，9 条合格。ACON 摘要丢了 2 个 ID，Actor 只批了 7 条（6/7 需求）；CarryOn 保留完整 9 条 ID 列表，还把状态里的预期数从 8 修正为 9，全对（7/7）。
- **Case 2**：复制昨日习惯笔记、仅改一个字段。SWE-Pruner 剪掉了 tags 和 pinned 字段，新建笔记时这两个字段丢了（7/9）；CarryOn 原文全保留（9/9）。
- **Case 3**：往按时间倒序排列的开销笔记里插当月条目。CarryOn 保住原文笔记，插入位置正确（10/10）；ACON 内容更新对了，最终作答检查失败（9/10）。

这些案例与消融一起，把『为什么原文片段 + 状态分离』从口号落到了可检查的失败模式上。

## 六、效果优势的根源解释

### 6.1 根源机制与证据链

**因果链 1：有损压缩破坏行动所需的精确值 → 原文片段保留消除这一损失。**
LLM Agent 的下一步动作常需把历史里的精确值原样填进工具参数。摘要与删 token 的目标是『语义保真』，但语义保真不保证参数可复原。本文 Case 1/2/3 是直接证据；外部研究（扩散 LM 上评估 LLMLingua-2）同样发现压缩失败主要由**信息遗漏**而非语义漂移驱动。标注：论文实验与外部研究均支持。

**因果链 2：证据需求随时序切换 → 每步重算 + 档案全保留，使选择可逆。**
40.2% 轨迹发生证据回流、≥10 步旧证据占选中量三到五成——如果压缩是不可逆的，这部分需求只能靠重发 API 补救（更贵也更慢）。Recency packing 消融（76.2 vs 79.8）说明仅靠『最近的』接不住长程依赖。标注：论文实验已支持；『可逆性本身』的独立贡献无法从消融中完全分离（下述）。

**因果链 3：进度与原料是两类信息 → 状态分离避免用证据包承担导航职能。**
去掉 MEMORY 成功率掉 13.7pp，是所有消融中最大的降幅——当证据包每步都在换内容时，若没有一份持续存在的状态，Agent 很容易忘记『还剩什么没做』。这与 MEM1（RL 训练 Agent 维护紧凑内部状态，性能提升 3.5 倍同时内存降 3.7 倍）从另一条技术路线得出一致结论：**紧凑状态跟踪是长程执行的必要组件**。标注：两条独立路线均支持。

**因果链 4：管理器与 Actor 解耦 → 学习到的选择知识可跨模型迁移。**
同一冻结选择器在三个 Actor 上全部带来增益，而 Actor 相关的基线（AGORA）跨 Actor 迁移即崩。外部佐证：AdaCoM（[arXiv:2605.30785](https://arxiv.org/abs/2605.30785)）也训练外部 LLM 管理冻结 Agent 的上下文并观察到跨 Agent 复用可行。标注：论文实验与外部研究支持，但迁移边界见 6.3。

**反事实检验**：去掉任一环节（状态 −13.7pp、学习选择 −3.6pp、下一动作监督 −3.0pp、块级监督 −6.6pp）都退化，说明没有哪个组件是搭便车的。

**诚实说明**：所有消融为单次运行、无显著性检验；Recency packing 与完整版的 3.6pp 差距是『学习排序 + 临时扩容 + 回流』三者的合并效应，回流机制的单独特异性贡献是**阅读者推测**，论文未单独消融『禁止回流』这一条件。

### 6.3 综合判断与未决问题

**多项研究共同支持的机制**：(a) 摘要/删减对精确值的破坏是压缩路线的结构性缺陷（Case 1/2 + 扩散 LM 评估 + SWE-Pruner 案例）；(b) 紧凑进度状态是长程执行必要组件（本文消融 + MEM1 + HiAgent）；(c) 外部管理器跨 Actor 复用可行（本文 + AdaCoM）。

**仍属推测或部分限定的**：(a) 『可回流』的独立贡献未能从合并消融中分离；(b) Tau2 + Claude 上 LLMLingua-2 反超提示：对话型短历史场景中，简单压缩可能恰好够用甚至更优——CarryOn 的优势集中在历史长、参数依赖重的任务（AppWorld 跨 App、OfficeBench 多级办公流）；(c) AdaCoM 的保真—可靠性权衡提示弱 Actor 上高保真策略未必最优，而本文 Qwen/Gemma（较弱的两个 Actor）也获益，与该权衡的边界尚待对齐；(d) 2511.05850 显示新一代模型长文检索已大幅改善——若趋势持续，『替模型压缩』的必要性窗口可能收窄，但 Agent 多跳依赖场景（2412.10079）仍证实退化存在。

**可能的失效条件**：多模态观察（证据单元如何表示未定义）；训练分布外的新工具界面（论文自述每个 benchmark 需单独训练选择器，跨环境泛化未验证）；单次运行设置下小于 ~4pp 的差距应谨慎解读；保留的原始观察含敏感信息时需要访问控制与人工确认机制（论文 Limitations 明示）。

## 七、必要知识反推

假设一个完全没有背景的人要完成这项工作，最少需要知道什么？

### 7.1 领域知识层

- **Agent 执行循环**：理解 ReAct 式『观察—行动』循环、工具/API 调用的输入输出形态——不知道这些就无法定义『证据单元』这种概念。
- **上下文窗口经济学**：知道每次调用都要全量重付输入 token、以及 lost-in-the-middle 现象——这是整套方法的成本—注意力双重动机。
- **三个基准的成功判据**：AppWorld 的状态单元测试、OfficeBench 的条件检查、Tau2 的奖励制评估——评估口径决定了什么算『精确值被保住』。

### 7.2 方法论知识层

- **上下文管理研究谱系**：压缩（LLMLingua 系）、选择（AGORA）、Actor 内训练（MEM1）三条路线的优劣——定位空白（外部 + 原文 + 细粒度 + 可回流）全靠对谱系的把握。
- **学习排序与 reranker**：成对排序损失、margin、LoRA 微调、BCE 分类头——选择器的双目标训练是标准组件的组合。
- **DAgger 与蒸馏**：CarryOn-E 需要懂得『学生到访教师没见过的状态』这一分布漂移问题及迭代聚合解法。
- **成本敏感评估方法论**：Kapoor 的批评与 cost-of-pass 视角——Sα 与 NCS 不是拍脑袋，是接着已有批评往下走。

### 7.3 工程知识层

- **离线标注管线**：如何用强模型生成结构化状态标注并引用证据步号，且标注 schema 要防住『事后诸葛亮』（只允许引用 ≤t 步的证据）。
- **预算装填算法**：字符预算、去重（同观察多片段动作只带一次）、预留近期窗口的优先级规则。
- **成本核算纪律**：token 计入被拒输入、排除本地小模型开销、失败任务计入分母——评估可信度全在这些细则里。
- **三套执行接口的适配**：AppWorld 的 Python 代码动作、OfficeBench 的 JSON 字典动作、Tau2 的对话 + 原生工具调用，同一协议要在三种形态下落地。

### 7.4 知识融合的关键节点

1. **『两类信息』的洞察**（融合点）：把 OS 的 PCB/调页类比 + Agent 执行循环知识叠合，得出『状态可压缩、证据不可压缩』的分离设计——这是全文的创造性核心。
2. **块级训练 → 片段级推理**（融合点）：标注成本知识 + 迁移学习直觉，解决『片段级标签不存在』的死结。
3. **后见之明监督**（融合点）：把『成功轨迹的未来』当作免费标注机，与 RL 的 hindsight 思想同源，但用在了监督选择器上。
4. **双分数对应双决策**（融合点）：排序分数管预算内装填、使用概率管破格扩容——两个工程决策各配一个学习信号，而不是一个分数硬扛两个目标。

## 八、论文中可以提取的通用性灵感

**灵感 1：把混合概念拆成正交的两类信息，分别用最优策略处理。**
核心思想：当一个『笼统资源』（上下文）里混着性质不同的两类内容时，不要用同一种策略处理它们——可压缩的交给状态，不可压缩的交给原件。
论文证据：w/o MEMORY 消融 −13.7pp；状态纪律（不存精确值）与证据原文保留的分工。
推广场景：编辑器设计（可折叠大纲 + 原文跳转）；协作系统（任务看板 + 附件原文）；数据库（索引 + 数据页）；人脑工作记忆（心理计划 + 随手查的便签）。

**灵感 2：删除要可逆——不做一次性裁剪，做每步可重选的装箱。**
核心思想：当未来需求不可预知时，把『永久丢弃』改成『暂不携带』，档案全量保留、选择每步重算。
论文证据：40.2% 轨迹发生证据回流；Discover 卡记录 26–28 步出局、29 步回流的完整案例。
推广场景：版本控制（软删除/历史可恢复）；缓存设计（可换出可换入的分页）；推荐系统（被滤掉的商品保留在候选池）；邮件归档（移出收件箱而非删除）。

**灵感 3：用后见之明构造监督信号。**
核心思想：结果已知的成功过程里，藏着『当时的哪个信息导致了后来的哪一步』的免费标签。
论文证据：future-use labels——状态标注引用 + 后续动作参数回溯，二者皆无为弱负例。
推广场景：RL 的 hindsight relabeling；软件工程的故障回溯（哪个日志字段预测了事故）；销售分析（哪次触达成交了）；医学随访（哪个早期指标预示了结局）。

**灵感 4：粗粒度训练、细粒度推理。**
核心思想：当细粒度标注太贵时，在粗粒度上学出判断力，部署时下放到细粒度。
论文证据：块级成对排序训练 → 冻结后给单条记录打分，效果优于纯细粒度训练（79.8 vs 73.2）。
推广场景：多示例学习（袋子标注→实例预测）；病理图像（切片级标签→细胞级分类）；代码评审（模块级反馈→行级应用）。

**灵感 5：评估必须把成本放进分母。**
核心思想：只报成功率会奖励『不计成本地堆算力』，单位成功的成本才是可比的量。
论文证据：OfficeBench Qwen 上成功率并列（66.3%）但 NCS 从 1.000 降到 0.476——纯效率改进在成功率报表上完全隐形。
推广场景：推理服务选型（延迟/成本/准确率三维权衡）；招聘 funnel 分析（单位录用的筛选成本）；营销（单位转化的触达成本）。

**灵感 6：与执行器解耦的外挂管理器可跨执行器复用。**
核心思想：把『策略知识』从执行器里抽出来放到外部轻量组件，冻结执行器也能受益，且一份知识多处复用。
论文证据：同一 0.6B 选择器跨 Claude/Qwen/Gemma 三 Actor 全部带来增益；对照 AGORA 按源模型定制后迁移即崩。
推广场景：数据库查询优化器与存储引擎解耦；编译器 pass 与目标架构解耦；浏览器扩展不改内核增强任意网站。
