## 一、论文背景

要理解这篇论文，需要先弄清楚三件事：核（kernel）是什么、昇腾 NPU 上的核开发是什么样的工作、以及为什么"评测 agent 优化核的能力"会成为一个独立问题。

**核：大模型算力的最底层单元。** 大模型训练与推理的几乎所有计算——矩阵乘、归一化、注意力、MoE 路由——最终都落到运行在加速芯片上的小程序里，这些小程序就是核。核的执行延迟直接决定了模型训练多快、推理多便宜。同一算法的两种核实现，性能差 2 到 10 倍并不罕见，所以核优化是系统效率工程里价值密度最高的环节之一。

**昇腾 NPU 与 Ascend C。** 论文的目标硬件是华为昇腾（Ascend）NPU，软件栈是 CANN（Compute Architecture for Neural Networks）。类比 CUDA 之于英伟达 GPU，昇腾上的核用 Ascend C 语言编写：这是一种基于标准 C/C++ 扩展的异构并行编程语言，Host 侧（CPU）负责调度，Device 侧（NPU 的 AI Core）执行核函数。与 GPU 的 SIMT 线程模型不同，昇腾 AI Core 以 SIMD 为主，核函数遵循"数据搬入—计算—数据搬出"的三级流水范式，开发者必须显式管理 Global Memory、L1 Buffer、L0A/L0B 等多级存储，做 Tiling 分块、双缓冲、多核负载均衡。一位昇腾算子开发者的学习体会很典型：刚开始只写计算逻辑直接读写全局内存，精度能跑通但性能很差；瓶颈往往不在计算而在数据搬运。这种"软硬协同"的显式控制意味着，优化一个昇腾核需要的知识组合相当深——这也是为什么它适合作为 agent 能力的试金石。

**核优化工程师的日常工作。** 论文关注的场景不是从零写核，而是优化已有实现：拿到一个正确的 Ascend C 核，分析它在目标输入配置和硬件特性下的性能瓶颈，反复修改、编译、执行、验证。这个过程依赖专门知识（存储层级、指令调度、流水线重叠）和持续的工程投入。论文开篇引用的行业观察指出，这类优化通常从现有代码出发，需要开发者结合目标输入配置与硬件特性定位瓶颈，再迭代验证。

**Coding agent 带来的机会与评测缺口。** 编码模型和 agent 有望自动化这个过程，但现有基准有一个系统性偏差：它们几乎都评"从规格生成核"。KernelBench 给 PyTorch 程序让模型生成等价 CUDA 核；昇腾生态的 NPUKernelBench 给功能描述和代码模板让模型补全；CANN Bench 给算子规格评生成核的正确性与性能。而真实工程中更常见的场景是"已有一个能跑的实现，能不能在可接受成本内让它更快"——这个优化任务形态缺少系统评测。同时还有一个被普遍忽视的维度：搜索成本。SWE-bench 类 agent 基准的实测成本研究显示，单个 agent 轨迹动辄消耗数万到数十万 token，一次全量评测可达数千美元，agent 基准比知识型基准贵 100 到 1000 倍；普林斯顿 HAL 团队跑 2 万多条 rollout 花了约 4 万美元。核优化这种需要反复试错的搜索型任务，token 成本问题只会更尖锐——花一百万 token 换来 10% 加速是否划算，现有指标完全不回答。

**一个类比帮助理解。** 现有生成型基准像"驾照路考"：考你能不能从无到有把车开起来；AscendGYM 像赛车工程的"圈速提升赛"：给你一台已经调校过的赛车（现有正确实现）、一条真实的赛道（真实负载的输入配置）、有限的燃油预算（token），看你能再快多少、花多少油。论文的全部设计——任务来源、沙箱、STS 指标——都是围绕这个任务形态展开的。

## 二、论文定位和关联工作

AscendGYM 处在三条研究脉络的交汇处：核生成基准、核优化评测、负载驱动任务设计。另外它还与 agent 基准的成本问题研究相呼应。

### 谱系一：核生成基准（从规格到实现）

- **KernelBench**（Stanford，ICML 2025）：250 个 PyTorch workload，评模型生成正确且快的 CUDA 核，提出 fast_p 指标（正确且加速比超过阈值 p 的任务占比）。核心发现是前沿模型零样本只有不到 20% 的任务能打平 PyTorch 基线，而执行与 profiler 反馈的迭代精修是最有效杠杆。它同时贡献了"执行反馈闭环"的评测环境设计范式，AscendGYM 直接继承。社区后续还发现它的 reward hacking 问题（提交里偷调 cuBLAS 等高层算子），催生了防作弊设计。
- **TritonBench / MultiKernelBench**：把核生成评测扩展到 Triton 语言和多硬件平台。
- **NPUKernelBench / AscendKernelGen**（2026，含北大团队）：昇腾生态首个系统的核生成评测，配套 Ascend-CoT 数据集与执行反馈强化学习，把复杂核的编译成功率从 0% 提到 95.5%（Pass@10）。CANN Bench 的分析指出其静态形状赛道每个任务只对应单一固定输入配置，针对一个形状特化的核即可通过。
- **CANN Bench**（华为，2026）：53 算子 1060 测试用例，编译/正确性/性能三维加权复合分，性能对照解析式硬件锚定极限（HAP），内建防 reward hacking 设计，随 CANN 官方仓库版本化演进。这是当前昇腾生成核评测的最强工程化代表。

**关键区别**：这一整条谱系评的都是"无中生有"，AscendGYM 评"锦上添花"——前者对参考实现的依赖是语义等价判据，后者把初始实现本身作为性能基线。

### 谱系二：核优化评测与优化 Agent（从实现到更快实现）

- **AMD GEAK 系列**：GEAK-OpenEvolve 做 Triton-to-Triton 优化，在 TritonBench-modified 上平均 3.42 倍加速、ROCm-bench 上 7.02 倍（仅计成功核）；GEAK v3 走向仓库级优化；GEAK v4 进一步用 Amdahl 优先级做端到端服务吞吐优化——局部核变快不等于模型变快。AMD 的实践（对应论文引用的 Wang et al. 2025）正是 AscendGYM 对标的"已有核优化"任务形态，但用的是标准 Triton 基准的核集合，输入配置不绑定真实负载。
- **PRAGMA / AutoKernel / GPU Kernel Scientist**：优化 agent 方法论——profiling 反馈进推理环、按瓶颈优先级选题、只靠端到端计时的进化搜索。这些是 AscendGYM 要服务与度量的那类系统。
- **Kevin**（ICLR 2026）：多轮强化学习训练模型生成 CUDA 核，代表"训练侧"路线；AscendGYM 的 model 评测模式（固定 AuraKernel harness 换模型）正是为这类模型对比设计的。

### 谱系三：负载驱动的任务设计（让分数映射回应用）

- **SOL-ExecBench**：从真实模型提取核任务，对照硬件性能极限评估剩余优化空间。
- **Atrex-Bench / FlashInfer-Bench**：从真实推理服务的执行轨迹构造评测任务，把核与输入配置关联到具体部署场景。FlashInfer-Bench 明确展示了输入配置与应用场景的对应关系——比如注意力计算在 prefill 与 decode 阶段数据规模不同，最优组织方式也不同。

### 谱系四：agent 基准的成本意识（STS 的精神同盟）

SWE-bench 成本测算（单任务 5 万到 20 万 token、全量运行数百到数千美元）、HAL 的 4 万美元账单、以及 Efficient Benchmarking of AI Agents（arXiv 2603.23749）主张可丢弃七成任务保持排名——这些工作都指向同一个事实：agent 评测的经济学已经成为一等公民问题。但它们讨论的是"评测本身怎么省钱"，AscendGYM 的 STS 讨论的是"agent 搜索过程本身的成本效率怎么进分数"，后者在核基准里是首创。

### 定位总结

| 维度 | 生成型基准（KernelBench/NPUKernelBench/CANN Bench） | AMD 优化评测（TritonBench-modified 等） | **AscendGYM** |
|------|------|------|------|
| 任务起点 | 规格/模板 | 已有 Triton 核 | 已有 Ascend C 核（CANN 算子库/vLLM-Ascend） |
| 输入配置 | 多为固定或合成 | 基准自带形状 | **真实负载 profiling 提取**（模型、阶段、TP、dtype 全保留） |
| 目标硬件 | GPU / 昇腾 | AMD GPU | 昇腾 NPU（910C） |
| 成本度量 | 无 | 无 | **STS/CTG 内建 token 成本** |
| 执行环境 | 各自 harness | 依托 AMD 工具链 | AscendForge 四层沙箱 |
| 评测对象 | 模型 | agent | **模型与模型加 harness 双模式** |

**定位结论**：AscendGYM 是首个把"真实负载输入配置 + 已有实现优化 + token 预算感知评分"三者合为一体的昇腾核优化基准，站在这四条谱系的交叉点上。

## 三、问题定义

论文从三个具体设计问题出发（任务怎么设计、评测怎么可靠、性能怎么评估），但背后是一个统一的抽象。

**具体问题**：给定一个正确的昇腾核实现，agent 能否在可接受的预算内、保持正确性的前提下，让它在目标工作负载的输入配置下跑得更快？

**核心洞察**：核优化的本质是一个**预算约束下的序列搜索问题**，而现有基准只度量搜索的终点，不度量搜索的路径成本。两个系统可以到达相同的最终加速比，一个几次尝试就命中改进，另一个烧掉海量 token 长搜——从终点指标看它们无法区分，但工程价值完全不同。

**类比**：核优化 ≈ 深度学习训练。加速比对应最终精度，token 消耗对应训练计算量，改进出现的时刻对应损失下降的早晚。深度学习社区早就知道"最终精度"和"收敛效率"是两个维度；AscendGYM 把这个认识搬进了核基准。

**形式化**：给定初始实现 I、输入配置 X（来自真实负载）、正确性判据 C、token 预算 B_max，agent 产生候选序列，第 k 次评估完成时累计消耗 B_k、可得的最优已验证加速比为 S_k（S_0 = 1，无改进则保留 1）。论文用 STS 把双目标合成单目标：

```
STS = 100·log2(S_n)  −  50·Σ_k (B_k / B_max)·Δg_k ,  Δg_k = log2(S_k) − log2(S_{k−1})
```

第一项是最终性能（对数加速比），第二项是延迟惩罚：每一段改进增量 Δg_k 按它出现时已经烧掉的预算比例 B_k/B_max 加权扣分——同样的增量，早出现几乎不扣，晚出现重扣。

**这个抽象的精妙之处**有三层。第一，把"优化能力"从结果属性重定义为过程属性：不是"能到多快"，而是"以什么代价、多早到多快"。第二，惩罚项的数学结构（预算归一 × 增量对数）保证分数对预算规模不变，10M 与 50M 预算下的行为可以直接对比。第三，正确性不进公式而是进定义域：只有通过正确性验证的加速比才计入 S_k，无任何有效改进时 STS = 0——正确性是入场券而非加权项，避免"快但错"与"对但慢"被错误地折中。

## 四、问题解法

AscendGYM 的解法是一个四件套：任务集与测试用例、AscendForge 执行沙箱、指标体系、双模式评测流程。

### 4.1 任务集：从真实负载 profiling 反推评测任务

48 个核优化任务分三批难度递进：Batch 1（17 个）聚焦基础核的访存优化，Batch 2（17 个）覆盖归一化、量化等多步计算，Batch 3（14 个）针对复杂注意力与融合计算（含稀疏注意力）。本报告实验在 Batch 1 上完成。

任务不是拍脑袋选的，而是对 MindSpeed-LLM、vLLM-Ascend 等昇腾框架上的真实训练推理任务做 profiling，取 top-k 瓶颈核，再把每个核的输入张量形状、数据类型、计算参数原样搬进测试用例。论文给了一个完整示例：AddRMSNorm 任务捕捉 Qwen3-0.6B 推理前向中残差加加 RMS 归一化，测试用例保留全部部署上下文——prefill 阶段、无量化、eager 执行、单卡、TP 1、BF16、batch 1、序列长度 32，分支输出与残差张量形状 [32, 1024]，归一化权重 [1024]；profiling 显示该核每次前向被调用 56 次、占总计算时间 8.77%、按累计执行时间排进 top-5。

这个设计的直接后果是**分数可回溯**：基准上对某核某形状的加速倍数，直接映射回真实工作负载里那次算子调用的加速倍数。同时它逼着优化必须针对目标负载：同一核在 prefill 和 decode 的形状差异可能大到值得两套实现，通用改写拿不到高分。

### 4.2 AscendForge 沙箱：把 NPU 开发循环封装成评测服务

类比：如果说 KernelBench 的执行环境是"单机脚本运行器"，AscendForge 就是一个小型持续集成集群。它在 SandboxFusion（FullStack Bench 开源的多语言程序评测基础设施）之上，为昇腾增加四层能力：

| 层 | 职责 | 关键机制 |
|------|------|------|
| 执行构建层 | Ascend C 与 Python NPU 后端；适配 CANN 算子库（ops-math/cv/nn/transformer）与 vLLM-Ascend | 管理 host 侧注册、device 侧核、目标 SoC、自定义核包之间的依赖；自动完成源码提交、编译安装、Python 接口绑定、测试执行 |
| 资源编排层 | 调度代理 + 任务队列 + 多执行节点 | 按 NPU 数量、芯片型号、节点偏好分配资源，支持资源预留与负载管理下的并发评测 |
| 开发反馈层 | 静态分析 + 性能 profiling | 返回构建日志、正确性结果、性能测量、测试工件，帮 agent 定位瓶颈 |
| 部署运维层 | 服务可用性 | 硬件健康监控、配置热重载、进程自动恢复、离线依赖准备 |

两个对 agent 迭代至关重要的细节。其一，**反馈分类**：编译与执行结果分开上报，agent 能区分三类失败——构建失败（编译日志）、数值错误（正确性比对）、性能回退（计时结果）——诊断信息不同，修复方向也不同。其二，**评测与计分分离**：搜索过程中的候选测量服务于 agent 迭代，而 run 结束后由 AscendGYM 对最终选定的实现做独立复评（五次额外性能评估，不占预算、不回流反馈），防止测量过程被暗中污染——这与 SOL-ExecBench 防测量过程被篡改的思路一致。

### 4.3 指标体系：一个主指标 + 一组分面指标

STS 之外，指标体系还包括：

- **CTG（Cost-to-Gain）**：在参考检查点 r 之后，把加速比再提升 δ（1%、5%、10%）所需的最小额外 token。空集（未达成）记为无穷大。它回答"下一档改进的边际成本"，越低越好。
- **fast_p**（沿用 KernelBench）：正确且加速比严格大于 p 的任务占比，p 为可调阈值。
- **GM Speedup**：各任务最优已验证加速比的几何平均，无改进任务保留 1 倍。
- **预算指标**：累计与平均 token 消耗、模型交互轮数、墙钟时间，全部包含失败尝试。
- **可靠性指标**：Candidate Pass Rate（候选中编译、执行、通过全部正确性检查的比例）与 Task Pass Rate（任务中至少产出一个过检候选的比例，无提交的任务留在分母）。

主指标管总分，分面指标管解释——为什么输、输在性能还是成本还是正确性，各有各的读数。

### 4.4 双评测模式与 AuraKernel 默认 harness

- **model–harness 模式**：用户配置现成编码 agent（Claude Code、Codex CLI、OpenCode）或自定义 harness，评测模型加 harness 的完整系统。共享任务提示词（附录 C 给出节译：声明工作区、可编辑文件、baseline/candidate/status 三条命令、80 次候选上限、50 个实质不同提案的软目标、禁止改容差与参考答案等），但保留各 harness 自己的系统提示与工具接口——agent 用自己的读文件、搜索、编辑、终端工具自主工作，不输出逐步工具 JSON 等外部程序驱动。
- **model 模式**：用户提供模型 API，AscendGYM 用内置 AuraKernel（称 Default）做 harness，支持策略搜索与经验沉淀，保证跨模型评测条件一致。Default 有四个配置：cold（无初始经验、完整搜索）、warm（预导入 5 条策略经验）、no lessons（无经验、关闭经验积累与动态搜索图）、code only（只积累代码经验）。GPT-5.6 Luna 在 reasoning effort xhigh 下分别跑四配置。

warm 的经验来源有讲究：CANN 任务从其他核导入 5 条策略经验；三个特殊核（fused_gdn_gating、hc_post、hc_pre_sinkhorn）从同核 cold run 导入 5 条有实测正收益的验证经验。warm 从任务初始实现起步，不继承 cold 的代码或检查点——考的是经验迁移，不是代码搬运。

### 4.5 测量协议

基线与候选用同一协议：每次测量 8 轮执行（model 模式 warm 配置 11 轮），前 3 轮预热，其余轮次取设备侧核执行时间算术平均，msprof 计时。硬件 Ascend 910C，每次评测请求分配一枚 NPU，结束即释放。搜索终止条件是资源预算耗尽或最大迭代数；每 run 至多 80 次候选评估，失败提交照占预算。

## 五、评估指标与实验证据

### 5.1 实验设置总览

- **被测系统**：6 个模型（Claude Opus 5、GPT-5.6 Terra、GLM-5.3、Qwen3.5-122B-A10B、Qwen3.6-35B-A3B、DeepSeek-V4-Flash）× 3 个 harness（Claude Code、Codex、OpenCode；Codex 不支持 Opus 5 故为 17 个组合）；model 模式为 GPT-5.6 Luna × Default 四配置。
- **任务**：Batch 1 的 17 个核任务，来自 CANN ops-nn、ops-transformer 与 vLLM Ascend。
- **预算情景**：紧（10M）/中（20M）/宽（50M）三档每任务 token 预算。

### 5.2 关键实验数据

| 指标 | 关键读数 | 含义 |
|------|------|------|
| GM Speedup（整体） | 约 70% 组合 < 1.2×；最强 Codex/GPT-5.6 ≈ 1.69×（全 17 任务通过）；Claude Code/Opus 5 ≈ 1.05×（同为全覆盖） | 任务整体有挑战性；覆盖率相同不代表幅度相同（前者 3 个任务超 2×，后者 7 个） |
| 单核极值 | 最高 fused_gdn_gating ≈ 3.29×；最低 moe_gating_top_k ≈ 1.17×；13 任务各组合中位加速 < 1.1× | 增益集中于少数核，多数核改进空间被现有实现锁死 |
| STS（预算分档） | Opus 5 在 10M 下 Claude Code 与 OpenCode 得分相近；预算放大后 Claude Code 性能项持续增长，OpenCode 增长有限；50M 下 Claude Code 性能项更高但成本扣分也更大，分差被收窄而未消除 | 只报终点性能无法刻画不同预算下的可得增益；STS 让"高投入高产出"与"低投入快达成"同图可比 |
| CTG（50M 预算、10% 目标） | Opus 5 + OpenCode 达成任务中位 3.8M tokens（仅部分任务达成）；+ Claude Code 中位 6.6M（全 17 任务达成） | 低条件中位成本 ≠ 同任务上更高效，达成集不同；CTG 必须与达成数同读 |
| token 消耗 | Codex/GPT-5.6 ≈ 140.4M/任务；Claude Code/Opus 5 ≈ 81.75M/任务，后者加速更高 | 性能排名不随 token 消耗走，两个量必须一起报 |
| 交互轮数 | Claude Code/Opus 5 轮数多于 Codex/GPT-5.6 而 token 更少，后者每轮 token 成本约高 3 倍 | 轮数与 token 刻画资源使用的两个正交轴 |
| 墙钟时间 | Qwen-35B：OpenCode 11.1 小时/任务 vs Codex 2.2 小时/任务，GM Speedup 相当（≈1.06× vs 1.05×）、token 相当 | 相近 token 与性能可伴随 5 倍周转差异，时间窗口受限时这是决定性指标 |
| 可靠性 | GPT-5.6 三 harness 全任务通过，但 GM Speedup 从 1.69×（Codex）到 1.05×（Claude Code）不等；全部记录中 31 条保留 1×：17 条有正确候选但无性能改进、14 条未产出一个过检候选 | 通过率与性能增益解耦；无改进任务保留 1× 的记法使加速比无法区分这两种失败，pass rate 补上这一层 |
| model 模式 | warm 在 10M/20M/50M 三档 STS 均最高；10M 下 warm 性能项已超 cold 且扣分更小；预算放大后 cold 追近但 50M 下 warm 仍保持分数与性能项双高；code only 全档优于 no lessons，两者均低于 cold | 5 条策略经验让改进更早出现（B_k 小、惩罚轻）；经验积累机制（策略+代码）本身有效；harness 配置会显著影响结论，跨模型比较必须固定配置 |

### 5.3 指标如何支撑论文主张

论文的核心主张有三条，实验设计的针对性如下：

1. **"优化已有实现仍是真实挑战"**——由 70% 组合低于 1.2×、13 任务中位不足 1.1× 支撑。这个数字的说服力来自任务来源：这些核已在 CANN 算子库和 vLLM-Ascend 里被工程化打磨过，低垂果实早已摘掉，剩下的提升空间天然更窄。若是合成任务或新手实现，这个数字就无法说明真实难度。
2. **"最终加速比不足以刻画优化行为"**——由 STS 分档图、CTG 达成集差异、token/轮数/墙钟三轴成本分化共同支撑。每一组对照（Claude Code vs OpenCode、OpenCode/Qwen-35B vs Codex/Qwen-35B）都是"性能相近而过程迥异"的实证。
3. **"STS 能度量预算感知的优化能力"**——由 warm 全档领先与"warm 在紧预算下优势最大"支撑。经验导入不改变模型，只改变改进出现的时刻，而 STS 恰好对时刻敏感（延迟惩罚项），这个消融近乎 STS 区分度的直接验证。

值得注意的一个诚实细节：论文明确提醒 model 模式各配置各有预算与测量设定，比较的是"各配置在其协议下的整体表现"，跨模型用 Default 比较时必须保持设置与先验经验一致，否则会把配置差异误记为模型能力。

## 六、效果优势的根源解释

本节解释三件事的根源：为什么任务难、为什么 STS 有区分力、为什么 warm 赢。每条因果链标注证据等级（论文实验已支持 / 阅读者推测）。

### 6.1 根源机制与证据链

**（1）为什么约七成组合加速不足 1.2×**

- 因果链：任务核来自生产算子库且输入配置绑定真实负载 → 初始实现已经历人工调优（低垂果实已摘）+ 输入形状具体化压缩了通用优化技巧的适用面 → 剩余改进需要针对特定 shape 与昇腾存储层级的深度定制 → 通用型 coding agent 的泛化改写难以命中。【任务来源与初始实现出处：论文已支持；"剩余空间需要深度定制"：论文结合单核极值（1.17× 到 3.29× 的巨大方差）与 13 任务中位 <1.1× 的证据推断，属合理推断】
- 旁证：KernelBench 上前沿模型零样本不足 20% 打平 PyTorch 基线——连"生成"成熟基线的等价高效实现都难，"再优化"成熟实现只会更难。【外部证据，任务设定不同，作方向性参照】
- 阅读者推测：moe_gating_top_k 这类核可能已接近访存或同步下界，改进天花板本身低；fused_gdn_gating 的 3.29× 可能源于原实现未做充分融合。论文未给出逐核瓶颈归因，此为推测。

**（2）为什么 STS 能区分终极指标区分不了的系统**

- 因果链：STS 惩罚项 = Σ(B_k/B_max)·Δg_k → 数学上等价于对每段对数增益按出现时刻的预算占比打折 → 两条到达同一 S_n 的路径，早改进路径的惩罚积分更小 → 分数差呈现"快达成 vs 长搜索"的结构差异 → Claude Code/Opus 5（性能项大、扣分也大）与 OpenCode/Opus 5（反之）在 STS 上同图可见，而 GM Speedup 看不见后者。【公式结构：论文已支持；两 harness 的行为分化：Figure 3 已支持】
- 反事实：若去掉惩罚项，STS 退化为 100·log2(S_n)，即对数刻度的 GM Speedup，warm 与 cold 的差异将只剩性能项，"经验让改进更早"这一维度的信息全部丢失——warm 在 10M 紧预算下性能项本身已超 cold（论文已支持），但三档全领先的稳定格局由惩罚项放大。【推测，基于公式与 Figure 8 的合成推理】

**（3）为什么 warm 赢、且紧预算下赢得最多**

- 因果链：warm 预导入 5 条经实测验证的策略经验 → 首轮迭代即按高概率方向改码 → 首个有效改进出现在 B_k 小的早期 → 该增量 Δg_1 的惩罚系数 B_1/B_max 极小，几乎全额计入分数 → 紧预算下（10M）优势最大；宽预算下 cold 靠持续搜索追近但 50M 仍落后。【warm 的经验构成与三档 STS 结果：论文已支持；"首轮改进更早"的逐步机制：由 STS 公式与 warm 优势的必要条件反推，属论文公式支持的机制解释】
- code only > no lessons 说明经验积累里"代码层经验"单独也有效，但策略+代码（cold 的完整配置）更强——经验的两个层面（怎么想 vs 怎么写）都有贡献。【论文已支持】

**（4）为什么通过率与加速比解耦**

- 因果链：pass rate 度量"能否产出正确候选"，speedup 度量"正确候选是否更快"——两个随机变量本就没有必然耦合；GPT-5.6 三个 harness 全通过而 GM Speedup 从 1.69× 到 1.05×，说明 harness 的搜索策略（而非模型的正确性能力）主导增益幅度；31 条 1× 记录中 17 条"对而不快"、14 条"连对都没有"，进一步证明单一加速比指标掩盖两种性质不同的失败。【论文已支持，含附录 E.3 的任务级核算】

### 6.3 综合判断与未决问题

**多项证据共同支持的机制**：(a) 真实负载来源 + 成熟初始实现 → 高挑战性（KernelBench/CANN Bench/AscendOptimizer 的量级旁证 + 本文 70% 数据）；(b) 反馈闭环驱动迭代（KernelBench、GEAK、GPU Kernel Scientist 与本文设计一致）；(c) 成本维度进评测的必要性（SWE-bench 成本研究与 STS 从不同侧面到达同一结论）。

**仍属合理推测的部分**：STS 延迟惩罚与"早改进"偏好是否会在长尾任务上诱发 agent 过早收敛于次优解（论文无此消融）；warm 优势中"策略经验质量"与"经验条数"的归因分解；逐核的改进天花板归因。

**优势的适用条件**：STS 的区分度依赖预算档设置合理（B_max 远大于首个有效改进的 B_1，否则惩罚普遍轻微）；真实负载映射的有效性依赖被 profiling 的负载集合代表性——Batch 1 的 17 任务主要来自特定模型与框架，泛化到更广负载谱系有待 Batch 2/3。**可能的失效条件**：若某系统的改进机制天然需要长前置探索（如先建完整 profiling 再批量改写），STS 的早改进偏好会系统性低估它；这正是论文同时报告性能/成本/可靠性分面指标的原因。

## 七、必要知识反推

假设一个完全没有相关背景的人要复现这项工作，最少必须掌握什么？

### 领域知识层

- **昇腾硬件与 CANN 软件栈**：AI Core 的 Cube/Vector 单元、多级存储（GM/L1/L0）、SIMD 为主的编程模型。没有它就无法理解为什么核优化难、难在哪（数据搬运与流水线而非算术）。
- **Ascend C 编程与构建**：host/device 协同构建、核注册、Python 接口绑定。没有它做不出 AscendForge 的执行构建层——这是 GPU 基准经验无法直接平移的部分。
- **LLM 训练推理负载解剖**：prefill/decode 的形状差异、TP 并行对张量形状的影响、归一化/注意力/MoE 各算子在负载中的时间占比。没有它无法从 profiling 数据里挑出有代表性的瓶颈核并还原部署上下文。
- **性能测量方法论**：预热轮次、多次测量取均值、设备侧计时（msprof）与端到端计时的区别。没有它测出的基线不可信，一切加速比失去意义。

### 方法论知识层

- **基准设计谱系**：KernelBench 到 CANN Bench的任务与指标设计、已知坑（静态单形状可被特化通过、reward hacking、测量污染）。没有它会重蹈覆辙。
- **指标理论**：为什么用对数加速比（几何平均的可分解性）、预算归一化的尺度不变性、把过程信息折进分数的积分式设计。这是 STS 的数学前提。
- **评测协议设计**：基线与候选同协议、终态独立复评、失败尝试计入预算与成本。没有它分数可被博弈。
- **Agent harness 生态**：Claude Code/Codex/OpenCode 的接口约定与配置方式、model–harness 双模式各自要控制什么变量。没有它实验结论会混入 harness 配置差异（论文自己就警告了这一点）。

### 工程知识层

- **沙箱与资源调度**：SandboxFusion 的复用与扩展、多节点 NPU 分配、并发评测的队列与预留。48 核 × 多组合 × 多预算档的实验量（单组合单任务可达上亿 token、十余小时）没有这套基础设施跑不动。
- **经验迁移工程**：策略经验的抽取、验证（只导有实测正收益的）、导入隔离（warm 不继承代码与检查点）。这是 warm 消融可信的前提。
- **防博弈细节**：禁改容差/参考/接口、输入清单外的临时文件不进构建、request_id 幂等。Appendix C 的提示词工程本身就是必须的知识。

### 知识融合的关键节点

1. **"负载画像 → 评测任务"的转译**：把 profiling 工具链（领域层）与基准设计（方法论层）融合，产生"每个测试用例携带部署上下文"的核心设计——这是分数可回溯的根源。
2. **"训练收敛观 → 评测积分式"的转译**：把深度学习里"精度与收敛效率并重"的直觉（方法论层）翻译成 STS 的延迟惩罚积分——跨域类比直接塑造了指标数学。
3. **"CI 基础设施 → NPU 评测服务"的转译**：SandboxFusion 的通用程序执行（工程层）与昇腾 host/device 协同构建（领域层）融合成 AscendForge——通用基建无法直接用，但架构可继承。
4. **"消融设计 → 因果归因"的转译**：warm/cold/no lessons/code only 四配置不是拍出来的，是把"经验"拆成策略/代码/在线/离线四维后设计的控制实验——方法论知识决定实验能回答什么问题。

## 八、论文中可以提取的通用性灵感

**灵感一：把结果指标升级为预算感知的过程指标。**
核心思想：对任何搜索型 agent 任务，"多早以多少代价拿到多少改进"比"最终拿到多少"更能刻画能力，改进出现时刻应当按已消耗预算加权折价。论文证据：STS 公式与 Figure 3 的三档预算分化、warm 在紧预算下优势最大（Figure 8）。推广场景：(1) SWE 类基准按"首个通过测试的提交时刻"折价；(2) 数学推理基准按推理 token 数给正确答案分档；(3) 自动超参搜索把试验预算进分数；(4) 具身 agent 把探索步数折进成功率；(5) 数据库查询优化器评测按优化耗时扣分。

**灵感二：评测任务从真实负载反推，并完整保留部署上下文。**
核心思想：任务的价值密度取决于分数能否映射回真实收益；profiling 真实系统、把输入配置连同其来源（模型、阶段、并行度）一起搬进测试用例，是建立这种映射的通用配方。论文证据：AddRMSNorm 用例保留 56 次调用/8.77% 占比等完整上下文，性能提升直接对应工作负载收益。推广场景：(1) 编译器优化基准从真实软件的 profiling 热点选函数；(2) 数据库索引调优基准从生产查询日志抽负载；(3) RPC 框架评测从线上 trace 还原调用分布；(4) 端侧推理基准从真实 App 帧率 trace 选算子组合。GEAK v4 的 Amdahl-first 从相反方向（端到端验证）论证了同一原理。

**灵感三：反馈分类返回，让诊断信息对齐失败类型。**
核心思想：把"编译失败 / 数值错误 / 性能回退"三类失败分开上报，agent 的修复动作空间才能与失败原因对齐；混合反馈迫使学生盲目试错。论文证据：AscendForge 开发反馈层的分离设计及候选/任务通过率的分层核算（31 条 1× 记录拆成 17+14 两类）。推广场景：(1) 代码补全训练把类型错误/运行时错误/断言失败分通道反馈；(2) 自动修 Bug 基准按失败阶段分层计分；(3) SQL 生成系统区分语法错误/权限错误/结果错误；(4) 硬件设计 EDA 反馈分语法/综合/时序三类。

**灵感四：先验经验的验证式迁移在紧预算下是杠杆。**
核心思想：跨任务迁移的经验必须经过实测验证（只保留正收益条目）且与代码/检查点解耦，其收益机制是让首个有效改进提前出现，因此在预算越紧时价值越大。论文证据：warm 只导 5 条验证过的策略经验，不继承任何代码，却在 10M/20M/50M 三档 STS 全部最高。推广场景：(1) 编码 agent 的跨仓库策略库分级（验证过/未验证）；(2) 推理系统的历史调参结论按负载特征检索复用；(3) 实验 science agent 的假设库带成功率标注；(4) 运维 agent 的故障处理剧本要求先在小流量验证再入库。

**灵感五：单指标必然失真，指标组合的互补性要显式设计。**
核心思想：GM Speedup 看不见快达成与长搜索的差别，pass rate 看不见对而不快与全无候选的差别，token 看不见墙钟差别——每个指标只覆盖一个切片，主指标+分面指标的分工要预先设计而非事后补。论文证据：五组"性能相近而过程迥异"的对照贯穿 4.2 与附录 E。推广场景：(1) 模型评测把准确率、token 成本、时延、拒答率组成仪表盘；(2) 检索系统把召回、延迟、索引成本并报；(3) 自动化测试把缺陷发现率与维护成本并报；(4) RL 训练把回报与样本效率并报。

**灵感六：正确性做入场券而非加权项。**
核心思想：在"性能优化"类评测中，把正确性设为定义域约束（不过检的候选其加速比根本不进入指标），优于把正确性与性能折中成加权分——后者允许"快但错"与"对但慢"互相掩盖。论文证据：S_k 只计 correctness-validated 的加速比、无改进记 STS=0、pass rate 单独成指标的三层设计。推广场景：(1) 代码生成基准以测试通过为门槛再评 token 效率；(2) 安全评测以无高危漏洞为门槛再评功能分；(3) 生成式艺术系统以约束满足为门槛再评美学分。

**硬件与软件环境（Appendix D）**：Ascend 910C NPU（Ascend910_9392）、AArch64 主机、Linux 5.10.0、Python 3.11.15、PyTorch 2.10.0+cpu、torch_npu 2.10.0.post2、CANN 9.0.1、Ascend C 编译器 ccec（Clang 15.0.5）、msprof 26.0.0、NPU 驱动 25.5.5。每次评测请求一枚 NPU，用毕释放。
